# What every agent is told: agent conduct

Keryx tells every agent it starts the same five rules, whether you talk to it directly or another agent dispatched it. Nothing else in the agent's instructions overrides them.

1. **No attribution.** No `Co-Authored-By:` trailers and no "Generated by …" / "Generated with …" lines in commit messages, PR or ticket descriptions, or comments. A model name given as technical provenance, such as the list of reviewers that ran and their models in a review report, is allowed.
2. **No commit, push, merge or release without an explicit ask.** Asking for an orchestrator (flow, job, autodoc or review) counts as asking for that orchestrator's own commits at task boundaries. Merging and releasing always need their own ask.
3. **Never destroy others' work.** No `git stash` in a dirty tree, no blanket `git add -A` while other agents share the checkout, no force-push to a shared branch.
4. **No secrets or personal data** in output, logs or commits.
5. **Honest reporting.** The agent says what failed, what it skipped and what it did not verify.

The full rule, with the reasons and examples, is installed at `.metaproject/rules/process/agent-conduct.mdc`.

## Where the rules reach

The text is kept once in Keryx and copied into every path that gives an agent its instructions:

| Agent | Gets the rules from |
|---|---|
| Your top-level agent (Claude Code, Codex, and others) | `.metaproject/index.md` and the managed block in `CLAUDE.md` / `AGENTS.md` |
| `keryx shell`, `keryx trigger`, `keryx schedule`, ACP sessions | the system instruction |
| Shell subagents (`spawn_subagent`) | the subagent's system instruction |
| External agents (`keryx agents external run`) | the runtime directive, read-only and write runs alike |
| Review agents, the review bot, Herdr children | their prompts |
| Workers and reviewers an orchestrator dispatches | a required entry in the dispatch: a `constraints` item in `subagent-dispatch`, the `conduct` field in a reviewer input |

Run `keryx update` after upgrading to regenerate `index.md`, the `CLAUDE.md` / `AGENTS.md` block and the installed rule.

A reviewer payload without the `conduct` field, or a worker dispatch whose `constraints` lack the entry, now fails `keryx review dispatch-check` and `keryx skills contracts validate`. Copy the line from the rule's "Dispatch form" section.

## Merging a flow's pull request

A flow with `completion_outcome: create-pr-and-merge` runs the review loop to a mergeable pull request, then merges only on an explicit ask: you picked "Create a PR … merge it" in the session, or the dispatch carries `operator_confirmed`. Without either, the flow stops at the mergeable pull request, reports it, and stays in progress until you ask.

## The commit-msg hook

`keryx init` and `keryx update` install a Keryx-managed `commit-msg` git hook. It refuses a commit whose message has:

- a `Co-Authored-By:` trailer (any capitalisation), or
- a line that starts with "Generated by" or "Generated with", also after an emoji or markdown emphasis.

It does not match a product name on its own: `docs: update CLAUDE.md routing` or `feat: Claude runtime adapter` commit normally. Lines starting with `#` (git's comment lines) and text below git's scissors line are ignored.

The hook is a marked block in `.git/hooks/commit-msg`, so content you put in that file yourself stays. `keryx sync uninstall-hooks` removes the block.

### When the hook does not run

Git skips the hook when:

- `core.hooksPath` points somewhere else (Husky, lefthook and similar tools set it), or
- the commit uses `--no-verify`.

`keryx doctor` reports the `commit-msg-hook` check as a warning when the block is missing (fix: `keryx update`) or when `core.hooksPath` sends git to another directory. In that case, call the Keryx hook from your hook manager's `commit-msg` step, or add the same two checks there.
