# What every agent is told: agent conduct

Keryx tells every agent it starts the same five rules, whether you talk to it directly or another agent dispatched it. Nothing else in the agent's instructions overrides them.

1. **No AI attribution.** No `Co-Authored-By:` trailer and no "Generated by …" / "Generated with …" line that names an AI model, agent or tool, in commit messages, PR or ticket descriptions, or comments. A human co-author, a code-generator note such as "Generated by protoc", and a model name given as technical provenance (such as the list of reviewers that ran and their models in a review report) are allowed.
2. **No commit, push, merge or release without an explicit ask.** Asking for an orchestrator (flow, job, autodoc or review) counts as asking for that orchestrator's own commits at task boundaries. Merging and releasing always need their own ask.
3. **Never destroy others' work.** No `git stash` in a dirty tree, no blanket `git add -A` while other agents share the checkout, no force-push to a shared branch.
4. **No secrets or personal data** in output, logs or commits.
5. **Honest reporting.** The agent says what failed, what it skipped and what it did not verify.

The full rule, with the reasons and examples, is installed at `.metaproject/rules/process/agent-conduct.mdc`.

## Where the rules reach

The text is kept once in Keryx and copied into every path that gives an agent its instructions:

| Agent | Gets the rules from |
|---|---|
| Your top-level agent (Claude Code, Codex, and others) | `.metaproject/index.md` and the managed block in `CLAUDE.md` / `AGENTS.md` |
| `keryx shell`, `keryx trigger`, `keryx schedule`, ACP sessions | the system instruction |
| Shell subagents (`spawn_subagent`) | the subagent's system instruction |
| External agents (`keryx agents external run`) | the runtime directive, read-only and write runs alike |
| Review agents, the review bot, Herdr children | their prompts |
| Workers and reviewers an orchestrator dispatches | a required entry in the dispatch: a `constraints` item in `subagent-dispatch`, the `conduct` field in a reviewer input |

Run `keryx update` after upgrading to regenerate `index.md`, the `CLAUDE.md` / `AGENTS.md` block and the installed rule.

A reviewer payload without the `conduct` field, or a worker dispatch whose `constraints` lack the entry, now fails `keryx review dispatch-check` and `keryx skills contracts validate` (`subagent-dispatch` contract 1.1.0). The entry must carry all five numbered constraints, so an unfilled template placeholder fails too. Copy the line from the rule's "Dispatch form" section.

## Merging a flow's pull request

A flow merges its pull request only on an explicit ask. In a session that is your answer "Create a PR … merge it" to the completion question; a dispatched flow with `completion_outcome: create-pr-and-merge` must carry `operator_confirmed` naming the person who asked, and the input contract refuses the dispatch without it.

## The commit-msg hook

`keryx init`, `keryx update` and `keryx sync install-hooks` install a Keryx-managed `commit-msg` git hook. It refuses a commit whose message has:

- a `Co-Authored-By:` trailer naming an AI model, agent, tool or vendor (Claude, Anthropic, GPT/ChatGPT/OpenAI, Codex, Copilot, Gemini, Bard, Cursor, Devin, Aider, Windsurf/Codeium, Amazon Q/CodeWhisperer, Tabnine, Keryx agent — including those vendors' noreply addresses), or
- a line that starts with "Generated by", "Generated with" or "Generated-by" (also after an emoji or markdown emphasis) and names one of them.

It lets through a human co-author (`Co-Authored-By: Jane Doe <jane@example.com>`), a code-generator note (`Generated by protoc`, `Generated by the OpenAPI generator`), and product names elsewhere (`docs: update CLAUDE.md routing`, `feat: Claude runtime adapter`). Words match whole, so "Claudette" or "OpenAPI" do not match; a human co-author whose name is one of the listed words (say, "Cursor") is refused. Every line of the message is checked, including `#` lines and text below git's scissors line, because whether git strips them depends on `commit.cleanup`.

The hook is a marked block in `.git/hooks/commit-msg`, so content you put in that file yourself stays. `keryx sync uninstall-hooks` removes the block; `keryx update` puts it back.

Keryx does not add the block to an existing `commit-msg` hook it could not run in: a symlink, a hook whose shebang is not `sh`, `bash`, `dash` or `zsh` (a Python or Node hook), or a hook whose last command is `exec …` or `exit`. It prints a warning and leaves the file alone.

### When the hook does not run

`keryx doctor` reports the `commit-msg-hook` check as a warning, with the reason, when:

- the block is missing (fix: `keryx update`);
- the existing hook is one of the kinds above, so the block was never added or can no longer be reached;
- `core.hooksPath` points somewhere else (Husky, lefthook and similar tools set it), so git never runs `.git/hooks`;
- `git` cannot be found or asked where its hooks live.

Git also skips the hook for `git commit --no-verify`. With a hook manager, call the Keryx hook from its `commit-msg` step, or add the same two checks there.
