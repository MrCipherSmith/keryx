# What every agent is told: agent conduct

Keryx tells every agent it starts the same five rules, whether you talk to it directly or another agent dispatched it. Nothing else in the agent's instructions overrides them.

1. **No AI attribution.** No `Co-Authored-By:` trailer and no "Generated by …" / "Generated with …" line that names an AI model, agent or tool, in commit messages, PR or ticket descriptions, or comments. A human co-author, a code-generator note such as "Generated by protoc", and a model name given as technical provenance (such as the list of reviewers that ran and their models in a review report) are allowed.
2. **No commit, push, merge or release without an explicit ask.** Asking for an orchestrator (flow, job, autodoc or review) counts as asking for that orchestrator's own commits at task boundaries. Merging and releasing always need their own ask.
3. **Never destroy others' work.** No `git stash` in a dirty tree, no blanket `git add -A` while other agents share the checkout, no force-push to a shared branch.
4. **No secrets or personal data** in output, logs or commits.
5. **Honest reporting.** The agent says what failed, what it skipped and what it did not verify.

The full rule, with the reasons and examples, is installed at `.metaproject/rules/process/agent-conduct.mdc`.

## Where the rules reach

The text is kept once in Keryx and copied into every path that gives an agent its instructions:

| Agent | Gets the rules from |
|---|---|
| Your top-level agent (Claude Code, Codex, and others) | `.metaproject/index.md` and the managed block in `CLAUDE.md` / `AGENTS.md` |
| `keryx shell`, `keryx trigger`, `keryx schedule`, ACP sessions | the system instruction |
| Shell subagents (`spawn_subagent`) | the subagent's system instruction |
| External agents (`keryx agents external run`) | the runtime directive, read-only and write runs alike |
| Review agents, the review bot, Herdr children | their prompts |
| Workers and reviewers an orchestrator dispatches | a required entry in the dispatch: a `constraints` item in `subagent-dispatch`, the `conduct` field in a reviewer input |

Run `keryx update` after upgrading to regenerate `index.md`, the `CLAUDE.md` / `AGENTS.md` block and the installed rule.

A reviewer payload without the `conduct` field, or a worker dispatch whose `constraints` lack the entry, now fails `keryx review dispatch-check` and `keryx skills contracts validate`. The entry must carry all five numbered constraints, so an unfilled template placeholder fails too. Copy the line from the rule's "Dispatch form" section.

## Merging a flow's pull request

A flow merges its pull request only on an explicit ask. In a session that is your answer "Create a PR … merge it" to the completion question; a dispatched flow with `completion_outcome: create-pr-and-merge` must carry `operator_confirmed` naming the person who asked, and the input contract refuses the dispatch without it.

## The commit-msg hook

`keryx init`, `keryx update` and `keryx sync install-hooks` install a Keryx-managed `commit-msg` check. It refuses a commit whose message carries AI attribution:

- a `Co-Authored-By:` trailer whose **identity** is an AI: the display name is exactly an AI product or model name (`Claude`, `Claude Code`, `Claude Opus 4.5`, `ChatGPT`, `GPT-5`, `Codex`, `Copilot`, `Gemini`, `Cursor`, `Devin`, `Aider`, `Amazon Q`, `Tabnine`, `Qwen`, `Keryx agent` and similar), or the address belongs to an AI vendor or agent: a vendor domain (`@anthropic.com`, `@openai.com`, `@cursor.com`, `@cognition.ai`, `@codeium.com` and similar), `gemini@`/`jules@`/`bard@google.com`, `copilot@github.com`, or the GitHub noreply address of an AI agent (`copilot-swe-agent[bot]`, `copilot-pull-request-reviewer[bot]`, `claude[bot]`, `cursor[bot]`, `devin-ai-integration[bot]`, `chatgpt-codex-connector[bot]`, `google-labs-jules[bot]`, `gemini-code-assist[bot]`, and the `copilot` and `cursoragent` user accounts);
- a "Generated by", "Generated with" or "Generated-by" line whose object is one of those names, as in `🤖 Generated with [Claude Code](…)` or `Generated by Codex`.

It lets through a human co-author even when the first name matches a product (`Co-Authored-By: Claude Monet <claude@example.org>`, `Devin Smith <devin@example.com>`), a code-generator note (`Generated by protoc`, `Generated with a cursor-based script`), and product names anywhere else (`docs: update CLAUDE.md routing`). Other bots pass: `dependabot[bot]`, `renovate[bot]`, `github-actions[bot]` and every bot not on that list. A co-author whose address is at an AI vendor's domain counts as AI even if a person. The tables are `AI_PRODUCT_NAMES` and `AI_EMAIL_DOMAINS` in `src/lib/managed-git-hook.ts`.

Comment lines and the `git commit -v` diff are handled as git handles them: reading stops at git's scissors line when an editor was used (or under `commit.cleanup=scissors`), and comment lines are skipped when git will strip them (`strip`, or the default cleanup with an editor). Under `verbatim`, `whitespace`, `scissors`, or `-m`/`-F` with the default cleanup, comment lines stay in the commit, so they are checked. A `--cleanup=` flag on the command line is not visible to the hook.

### How it is installed

The check is a script, `.git/hooks/keryx-commit-msg`. Keryx calls it from `.git/hooks/commit-msg` only when that file is absent or already carries the Keryx block. Keryx never edits any other `commit-msg` hook (a hook manager, the pre-commit framework, a symlink); it writes the script and prints the one line to add to your hook, before any `exec` or `exit`:

```sh
"$(git rev-parse --git-path hooks)/keryx-commit-msg" "$1" || exit 1
```

`keryx sync uninstall-hooks` removes the Keryx block and the script (it keeps the script while a hook still calls it, and never edits through a symlink).

### Turning it off

Set `hooks.commitMsg` to `false` in `.metaproject/metaproject.json`:

```json
{ "hooks": { "commitMsg": false } }
```

With the setting off, `keryx init`, `keryx update` and `keryx sync install-hooks` (from any directory of the project) do not install the check and remove an existing Keryx block and script, and `keryx doctor` reports the check as disabled by config. The conduct rule itself still applies to every agent.

Only `true` and `false` are valid. If `metaproject.json` is not valid JSON, or `hooks.commitMsg` holds anything else (`"false"`, `0`), Keryx leaves the hook as it is and warns, `keryx update` leaves the file untouched instead of rebuilding it, and `keryx doctor` asks you to fix the file.

### When the hook does not run

`keryx doctor` reports the `commit-msg-hook` check as a warning, with the reason and the fix, when:

- the check is missing, or the block is there but the script is gone or not executable (fix: `keryx update`);
- an existing `commit-msg` hook does not call `keryx-commit-msg` (fix: add the line above to it);
- a hook calls `keryx-commit-msg`, but Keryx cannot tell that the line runs: it comes after an `exec`, `exit`, `.`/`source` or `eval`, inside an `if`, loop, `case` or function, or without `|| exit` while not being the last line. Doctor reports it **unverified**; put the line right after the shebang. Keryx reads the hook as text, not as a shell, so a hook that does run the line can still show as unverified;
- `core.hooksPath` points somewhere else (Husky, lefthook and similar tools set it), so git never runs `.git/hooks`;
- `git` cannot be found or asked where its hooks live.

The check also does not run for `git commit --no-verify`.
