# Keryx vs. the Field — coding-agent harness comparison

**Date:** 2026-08-20
**Method:** eight parallel research agents, one shared 17-dimension rubric (0–3
depth scale), each working read-only from a local git clone under
`~/sandbox/forks/*` (no network access, no vendor docs, no README claims taken
at face value without code backing). A ninth agent synthesized the matrix and
narratives from the eight structured profiles. Every depth score traces to
file-path evidence supplied by the profiling pass.

**Scope:** Keryx vs. Cline, Codex, DeepSeek-Harness (dsh), Gemini CLI,
Grok-Build, oh-my-claudecode (OMC), OpenCode. `aider` was excluded — its local
clone was incomplete (`.git/shallow.lock` only, no working tree).

## Where Keryx leads

1. **Security scanning** — only project with secret + PII + prompt-injection + exfiltration detectors wired into a redaction-before-persistence seam.
2. **Knowledge/docs (wiki)** — only project with a staleness-aware (content-hash based), generated architecture wiki + ask-the-docs Q&A. OMC (depth 2) is the closest, but keyword/tag search only.
3. **Code intelligence** — tree-sitter symbol graph + blast-radius/affected-files analysis + cycle/orphan detection + pagerank; deepest of the field. Grok-Build has goto-definition but no blast-radius; Codex has no code graph at all.
4. **Task/flow management** — strict state machine with a completion gate tied to PR-and-merge, no bypass. No peer gates completion on merge.
5. **Quality gates** — single weighted risk score (lint/type/test/complexity/coverage/hotspots) checked in CI against a main baseline. Gemini CLI's `preflight` chains checks but doesn't roll into one score.
6. **Governance/audit** — SAC lifecycle (immutable proposals, correlation-bound receipts, review-confirm tokens, redaction-before-persistence). OMC's merge-readiness gate is the closest analog but is self-documented as advisory only.

## Where Keryx lags

1. **MCP client capability** — Keryx exposes an MCP server but has no code path to consume external MCP servers itself. All 7 peers ship MCP clients; Cline, Codex, dsh, Grok-Build add OAuth.
2. **Provider breadth** — 8 providers via one generic OpenAI-compatible adapter, no native OpenAI/Gemini integration. Cline: 150+ provider ids. OpenCode: 20+ via Vercel AI SDK.
3. **UX / distribution surface** — CLI + TUI + offline dashboard + loopback HTTP daemon, no VS Code extension or desktop app. Cline: VS Code Marketplace + Tauri desktop. OpenCode: VS Code ext + desktop + web app + Zed ACP integration.
4. ~~Multi-agent provider diversity~~ — **CORRECTED, see below**: this was a research miss. Keryx has a real external-agent runtime (`src/harness/external/`, flow 176) that spawns actual `codex`/`claude` CLIs as children. It is not a lag; see the "Closing the gaps" section for the code-verified comparison.
5. **Community/adoption evidence** — effectively single-author, no visible external contributors. Codex/Gemini CLI are large-org products (PR numbering in the tens of thousands); OpenCode reports 100K+ downloads/month.
6. **Testing intelligence ceiling** — ties Gemini CLI at depth 2 for related-test selection, but Gemini CLI additionally has CI-integrated flaky-test detection/quarantine (`scripts/deflake.js` + a dedicated workflow) that Keryx lacks entirely.

## Open questions flagged across profiles

- Whether Keryx's OpenTUI-based TUI is robustly usable end-to-end in real interactive sessions (CI only checks binary resolution).
- Whether `keryx serve`'s HTTP daemon remains strictly read-only as documented.
- Most competitor local clones were shallow (depth 1), so true commit/contributor cadence for Cline, Codex, dsh, Gemini CLI, OMC could not be independently verified — PR numbering in commit messages was used as an indirect signal.

## Closing Keryx's gaps — competitor approaches

Follow-up research (7 agents, code-verified against the local clones in
`~/sandbox/forks/*`, not README claims) into concretely how competitors solve
each of the six "Keryx lags" dimensions above. Where fewer than 4 genuinely
distinct, verified solutions exist, the list is not padded — see the italic
notes under each table.

### Recommended priority order

1. **MCP client capability** — model deepseek-harness's `mcp-client` plugin (generation-swap reconnect supervisor + registry-bridging `tools.ts`). Highest impact (foundational — Keryx today only *serves* MCP, so closing it unlocks the entire external-tool ecosystem for every downstream tool call) combined with the highest ease of any dimension studied — Keryx already carries the SDK dependency and a matching tool-registry shape to plug straight into.
2. **Provider breadth** — model opencode's `packages/llm` protocol/provider split (native protocol module per real wire format, generic reuse for the compat long tail). High ease (slots directly into the existing `ProviderPort` contract, no architectural rewrite) paired with solid impact: native OpenAI/Gemini support broadens who can run Keryx without abandoning its SDK-free design.
