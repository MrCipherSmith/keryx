# keryx: зависание shell с MiniMax

2026-09-17

С MiniMax-M3 `keryx shell` выглядит зависшим. Провайдер не стримит, у запросов нет таймаута, а инлайновые `<think>` модели попадают в подсказку ввода и в вики. За этим стоит общий пробел: keryx почти не умеет работать с рассуждениями моделей — ни у Anthropic, ни у OpenAI, ни у Gemini они не запрашиваются, нигде не возвращаются в историю и не показываются вживую. Нужны 6 исправлений зависания в keryx 0.2.112 и отдельная доработка обработки и визуализации рассуждений.

Живая версия документа: https://claude.ai/code/artifact/d88abba4-ee03-48d2-b0fa-8f565f3ff5d0

## Симптом и окружение

Пользователь дважды подряд видел, что `keryx shell` «зависает» на запросе изучить документацию проекта olimpyx. Сам ход при этом доходит до конца и сохраняется.

| Параметр | Значение |
| --- | --- |
| keryx | 0.2.112 (`f4cd8bd8`), запуск через bun |
| Провайдер | пользовательский `MiniMax`, OpenAI-совместимый, `https://api.minimax.io` |
| Модель | `MiniMax-M3`, рассуждения идут в `content` внутри `<think>…</think>` |
| Проект | `/home/altsay/olimpyx` |
| Сессии | `5e57d10e…d6edb107` (39 сообщений), `439cc06e…f7e7837b` (75 сообщений) |
| Запрос | «изучи документацию что реализовано какой роадмап есть реквайрменты?» |

Ещё пользователь заметил, что после ответа модель подставляет в поле ввода текст, начинающийся с `<think>`.

## Улики из сессии

Модель дописала ответ и он сохранён, поэтому «зависание» происходит не в основном ходе, а до первых байтов ответа или после хода.

| Время (UTC) | Наблюдение |
| --- | --- |
| 07:53:25 | Сессия f7e7837b сохранена с финальным ответом, но воспринята как зависшая |
| 07:55:10 | Пользователь запускает новую сессию d6edb107 с тем же запросом |
| 07:58:30 | Сессия d6edb107 сохранена: последнее сообщение — финальный ответ ассистента без `toolCalls`, ~41 КБ, начинается с `<think>` |
| 08:01 | Процесс 275227 (`keryx shell`, cwd olimpyx) в состоянии `S`, CPU не растёт, держит ESTABLISHED TLS к `api.minimax.io` (Akamai 2.16.44.35) и локальные соединения к MCP на портах 3847 и 3011 |

Открытое TLS-соединение в 08:01 — слабая улика. `fetch` в Bun держит соединения в пуле для повторного использования, поэтому ESTABLISHED не доказывает, что запрос ещё идёт. Подтвердить висящий запрос могли бы строка «worked for Xs» на экране (её нет — ход не завершён), очереди сокета в `ss -tip` или `strace` процесса.

Что ещё видно в транскрипте d6edb107:

- Сообщение 20 (результат `read_file` страницы вики `project-map.md`) содержит чужое рассуждение: `<think> The user wants me to rewrite a wiki page stub…`.
- Сообщение 29 ассистента заканчивается лишним `</think>\n\n</think>` — модель сбита с разметки.
- Результаты инструментов доходят до 41 КБ на сообщение, `context.jsonl` — 153 КБ.
- У всех 39 сообщений одинаковый `ts` (07:58:30.637Z). Сессия записывается целиком в `.finally` хода (`flushSessionCheckpoint`, `tui-shell.ts:5306`), и метка ставится в момент записи, — по сессии нельзя восстановить хронологию хода.

## Корневые причины

Причин четыре, и по отдельности ни одна не завешивает shell. Зависание получается из их сочетания. Пути — относительно корня репозитория keryx.

| # | Дефект | Где | Последствие |
| --- | --- | --- | --- |
| 1 | Нет потокового вывода и таймаутов: тело SSE читается целиком через `await response.text()`, события отдаются одной пачкой в конце. Ни `fetch`, ни чтение тела не ограничены по времени | `src/harness/provider/compat/openai-compat-provider.ts:450-503` (чтение тела `:488`), `:713-719`; то же в `src/harness/provider/openai/openai-provider.ts:400-449` (`:446`) | Весь ход — спиннер без вывода. Если сервер не закроет соединение, `text()` не завершится никогда |
| 2 | `budget.maxOutputTokens` не передаётся: в payload нет `max_tokens` | `openai-compat-provider.ts:414-433`; в `openai-provider.ts:379-395` так же нет `max_output_tokens` | Лимит 40 токенов у подсказки фиктивный, MiniMax делает полный ход с рассуждениями. Касается всех OpenAI-совместимых провайдеров и OpenAI Responses |
| 3 | Инлайновые `<think>…</think>` не распознаются. В `reasoning_delta` попадают только поля `delta.reasoning` / `reasoning_content`; в `src` нет ни одного упоминания `think>` | `openai-compat-provider.ts:622-632`; `src/harness/provider/single-turn.ts` (`runModelTurn` склеивает все `text_delta`) | Рассуждения попадают в ответ, в историю, в подсказку и в страницы, которые пишет `keryx wiki enrich` |
| 4 | Подсказка следующего шага `suggestNextStep` запускается после каждого хода без `signal` и без таймаута, хотя комментарий (`:5261`) обещает таймаут, а `runModelTurn` принимает `signal` (`single-turn.ts:161`). Очистка — только `trim().split(/\s+/).slice(0, 20)`. Enter в пустом поле отправляет подсказку как запрос | `src/tui/tui-shell.ts:5264-5285` (вызов `:5322-5324`); `src/tui/shell-chrome.ts:1027-1034`, `:1126-1146` | В поле ввода видно `<think> The user wants me to…`. Enter отправляет этот мусор новым ходом, и вступает в силу дефект 1 |

Подсказка берёт провайдера и модель из `sel` (`tui-shell.ts:5270`, выбор при старте — `:2399`), а не из текущего выбора. Что `sel` не обновляется при смене модели, отдельно не проверялось.

Что проверено и исключено: после сохранения финального ответа в `.finally` хода (`tui-shell.ts:5291-5332`) нет ни одного блокирующего `await`: `stopBusy()`, сохранение и строка «worked for Xs» выполняются синхронно, остальное запускается без ожидания. Отрисовка большого текста тоже синхронная, а CPU у процесса нулевой.

## Как это складывается в зависание

```mermaid
sequenceDiagram
    participant U as Пользователь
    participant T as keryx TUI
    participant P as compat-провайдер
    participant M as MiniMax API
    U->>T: «изучи документацию»
    T->>P: ход (контекст ~150 КБ)
    P->>M: POST stream:true, без max_tokens
    Note over T: спиннер, 0 байт на экране
    M-->>P: SSE целиком (дефект 1)
    P-->>T: все события сразу, <think> в тексте
    T->>P: suggestNextStep, 40 токенов (дефект 2)
    P->>M: POST без max_tokens и таймаута
    M-->>T: "<think> The user wants…" (дефект 3)
    T->>U: подсказка с <think> в поле ввода
    U->>T: Enter в пустом поле (дефект 4)
    T->>P: новый ход с мусорным запросом
    Note over T,M: снова без вывода; сокет не закрыт — висит навсегда
```

Пока идёт длинный ход, на экране ничего не появляется минутами (d6edb107 — 3 мин 20 с). Состояния различаются по строке «worked for Xs»: есть — ход завершён, нет — висит запрос в провайдере.

## Почему именно olimpyx и документация

Вики olimpyx уже испорчена дефектом 3, а запрос про документацию даёт самый тяжёлый и долгий ход. Дефекты общие для любого проекта с MiniMax.

- **Вики сгенерирована через MiniMax.** Команда `keryx wiki enrich --all --force --concurrency 4 --provider MiniMax --model MiniMax-M3` (в сессии «проиндексируй граф») записала блок `<think>…</think>` сразу после frontmatter в 9 страниц: `architecture/project-map.md`, `architecture/testing-map.md`, `components/apps-server-test.md`, `components/apps-server-src.md`, `components/tests-e2e.md`, `components/packages-client-test.md`, `components/apps-web-src.md`, `components/packages-client-src.md`, `components/apps-web-src-lib.md`.
- **Запрос про документацию читает именно их.** Маршрутизация metaproject отправляет модель в вики, и она получает в контекст чужие рассуждения и теги. Дальше она сама путается в разметке (лишние `</think>` в сообщении 29).
- **Большой контекст.** Спека v2 и MVP-документы весят 13–24 КБ на файл, за ход контекст дорастает до ~150 КБ. Ход идёт минутами, и при дефекте 1 это всё время пустой экран.
- **Длинный ответ с рассуждениями.** Финальный ответ (~41 КБ) сам начинается с `<think>`. Подсказка строится по последним 3000 символам ответа и тоже возвращается с `<think>`.

## Как keryx обрабатывает рассуждения сейчас

Дефект 3 — частный случай. Провайдеры отдают рассуждения четырьмя разными способами, и у трёх из них есть обязательство вернуть рассуждение или его подпись обратно в следующем запросе. keryx полноценно поддерживает только один способ и ни одного обязательства.

| Протокол | Как отдаёт рассуждения | Что запрашивает keryx | Что разбирает keryx | Возврат в историю | Итог |
| --- | --- | --- | --- | --- | --- |
| Anthropic Messages | Блоки `thinking` (`thinking_delta`, `signature_delta`) и `redacted_thinking`; включаются параметром `thinking`. В цикле с инструментами блоки надо вернуть без изменений вместе с подписью | Ничего | Ничего: `content_block_delta` разбирает только `text_delta` и `input_json_delta` (`anthropic-provider.ts:478-501`), `reasoningMetadata: false` (`:243`) | Нет | Рассуждений нет. Включить `thinking` без возврата подписей нельзя — сломается цикл инструментов |
| OpenAI Responses | Элементы `reasoning`; текст — только сводка, и только при `reasoning.summary`. Без хранения на сервере для продолжения нужен `include: ["reasoning.encrypted_content"]` и возврат элементов | Ни `reasoning.effort`, ни `summary`, ни `max_output_tokens` (`openai-provider.ts:379-395`) | `response.reasoning_summary_text.delta` (`:544-551`) | Нет | Парсер есть, но событие не придёт: сводка не запрошена. Рассуждение теряется между вызовами инструментов |
| Gemini | Части `thought: true` при `thinkingConfig.includeThoughts: true`; `thoughtSignature` на частях. Для Gemini 3 при function calling подпись обязательна, иначе HTTP 400 | Только `maxOutputTokens` и `temperature` (`gemini-provider.ts:466-469`) | `thought: true` (`:600-603`) | `thoughtSignature` не разбирается и не возвращается | Парсер есть, но сводки не запрошены. Gemini 3 с инструментами по документации должен падать с 400 (живым запросом не проверялось) |
| OpenAI-совместимый, отдельное поле (DeepSeek, OpenRouter, vLLM с reasoning parser, Ollama `/v1`) | `delta.reasoning_content` или `delta.reasoning` (у OpenRouter ещё `reasoning_details`). DeepSeek в режиме рассуждений с инструментами требует вернуть `reasoning_content` во всех прошлых сообщениях ассистента, иначе HTTP 400 | Ничего | Оба поля (`openai-compat-provider.ts:622-632`) | Нет | Показывается. DeepSeek с инструментами по документации падает с 400 (не проверялось) |
| OpenAI-совместимый, инлайн `<think>` (MiniMax по умолчанию, Qwen3 и дистилляты R1 без reasoning parser) | В `content` внутри `<think>…</think>`. MiniMax требует при вызовах инструментов сохранять `content` с `<think>` полностью; с `reasoning_split: true` отдаёт рассуждение в `reasoning_content` / `reasoning_details`, их тоже надо сохранять | Ничего | Не распознаёт | Случайно да: `<think>` остаётся в тексте | Утечка в ответ, подсказку, вики. Простое вырезание тегов нарушит требование MiniMax сохранять рассуждение в истории |

Остальные пробелы:

- **Нет места для рассуждения в истории.** `NormalizedMessage` (`types.ts:118-136`) хранит только `content`, `toolCalls`, `toolCallId`. Ни текст рассуждения, ни непрозрачные подписи хранить негде, поэтому вернуть их провайдеру невозможно.
- **`options.reasoning` никто не читает.** Поле есть в `NormalizedRequestOptions` (`types.ts:151`), но ни один адаптер его не использует.
- **Токены рассуждений не видны.** Они приходят только как `openai.reasoning_tokens` и `gemini.thoughts_tokens` в `unknownExtensions` (`openai-provider.ts:601-607`, `gemini-provider.ts:631-651`).

### Визуализация сейчас

- **Рассуждение не показывается вживую.** `runAgentTurn` копит `reasoning_delta` в строку и отдаёт её в `onReasoning` один раз: при первом `text_delta` или в конце раунда (`src/commands/agent.ts:1478-1500`, `:1544`; то же `:2130-2160`). Даже после исправления потокового чтения пользователь видит спиннер, пока модель думает.
- **Фаза «thinking» включается, когда модель уже закончила думать.** `setBusyPhase("thinking")` вызывается из `onReasoning` (`tui-shell.ts:2913-2916`), то есть на сброс накопленного текста. Пока модель действительно думает, фаза остаётся «waiting for model».
- **Свёрнутый блок без длительности и токенов.** В shell рассуждение — тусклый блок `thought` с ограничением строк и раскрытием через `/think` / `ctrl+o` (`tui-shell.ts:674-689`); в не-блочном выводе — строка `◆ thought (N lines)` (`:612-617`). Сколько секунд и токенов ушло на рассуждение, не видно.
- **Скрытое рассуждение никак не отмечается.** `redacted_thinking` у Anthropic и зашифрованные элементы у OpenAI не имеют представления, пользователь не узнает, что модель думала.

## Исправления

### Зависание

Порядок — по влиянию. Обязательны первые четыре: п.1 убирает пустой экран и вечное ожидание, пп.2–4 — мусор в поле ввода и случайный запуск нового хода.

1. **Настоящий потоковый вывод и таймаут простоя** в `openai-compat-provider.ts` и `openai-provider.ts`.
    - Читать `response.body.getReader()`, кормить `AnthropicSSEParser.push` по чанкам и отдавать события сразу.
    - После `[DONE]` или `finish_reason` завершать ход, не дожидаясь закрытия сокета (`reader.cancel()`).
    - Таймаут простоя между чанками (например 120 с, настраиваемый) и таймаут до первого байта → `provider_error` вида `unavailable`, retryable.
    - Сохранить контракт flow-019: аборт → ровно одно `cancelled`, без `model_end`.
2. **Распознавать инлайновые `<think>` в compat-провайдере.** Сделать парсер с состоянием поверх `delta.content`: текст между `<think>` и `</think>` отдавать как `reasoning_delta`, остальное — как `text_delta`.
    - Тег может быть разрезан между чанками (`<thi` + `nk>`).
    - Незакрытый `<think>` на `finish_reason` = весь ответ был рассуждением, текста нет.
    - Лишний `</think>` без открытия — отбрасывать.
    - Включать только явным флагом провайдера в `llm-providers.json` (см. п.R3). Автоопределение по «ответ начинается с `<think>`» не использовать: модель может честно ответить про сами теги, например разбирая этот баг, и парсер съест часть ответа.
    - Для MiniMax предпочтительнее `reasoning_split: true` (п.R3): рассуждение приходит отдельным полем, разбор тегов не нужен.
    - Это чинит сразу shell, подсказку и `wiki enrich`, потому что `runModelTurn` склеивает только `text_delta`. Сохранение рассуждения в истории — п.R1.
3. **Передавать лимит вывода** из `request.budget.maxOutputTokens`: `max_tokens` в `openai-compat-provider.ts:414` (для MiniMax допустим и рекомендуемый `max_completion_tokens`), `max_output_tokens` в `openai-provider.ts:379`. У рассуждающих моделей лимит съедается рассуждением: 40 токенов подсказки, скорее всего, дадут пустой ответ — это приемлемо, подсказка просто не покажется.
4. **Исправить `suggestNextStep`** (`tui-shell.ts:5264`).
    - Передать `signal: AbortSignal.any([foregroundOperation.signal, AbortSignal.timeout(8000)])` и отменять запрос, когда пользователь начал печатать или запустил новый ход.
    - Отбрасывать подсказку, если после очистки она пустая, длиннее 80 символов или содержит `<`/`>`.
    - Брать текущую модель, а не `sel` со старта.
    - Подумать, стоит ли оставлять отправку подсказки по Enter в пустом поле (`shell-chrome.ts:1030`): одно нажатие запускает запрос, который пользователь не писал. Минимум — Enter только после Tab.
5. **Защита `wiki enrich`.** Перед записью страницы вырезать `<think>…</think>` и отклонять результат, если после frontmatter идёт не заголовок/текст страницы. Для уже испорченных проектов — перегенерация или предупреждение в `keryx wiki status`.
6. **Метки времени в сессии.** Ставить `ts` в момент появления сообщения, чтобы такие зависания можно было разбирать по файлам.

### Рассуждения: обработка

R1–R3 — одна доработка провайдерного слоя; п.2 выше — её первый шаг, который можно выпустить отдельно.

- **R1. Место для рассуждения в истории и событиях.**
    - Добавить в `NormalizedMessage` поле `reasoning?: { text?: string; redacted?: boolean; replay?: ProviderReplayItem[] }`, где `replay` — непрозрачные данные провайдера: блоки `thinking` с подписью у Anthropic, `thoughtSignature` у Gemini, `encrypted_content` у OpenAI, `reasoning_details` у MiniMax, `reasoning_content` у DeepSeek.
    - Добавить событие для непрозрачных данных (например `reasoning_replay`), чтобы адаптер мог передать подпись, не смешивая её с текстом.
    - `runAgentTurn` сохраняет рассуждение в сообщение ассистента, в том числе в раунде, где есть только вызовы инструментов.
- **R2. Возврат рассуждения по правилам провайдера.** Каждый адаптер сам решает, что возвращать:
    - Anthropic — блоки `thinking` / `redacted_thinking` с подписью, без изменений, как минимум в текущем цикле инструментов;
    - Gemini — `thoughtSignature` на тех же частях `functionCall`, на которых он пришёл;
    - OpenAI Responses — элементы `reasoning` с `encrypted_content`;
    - DeepSeek — `reasoning_content` во всех сообщениях ассистента, если в запросе есть `tools`;
    - MiniMax — `reasoning_details` при `reasoning_split` или `content` с `<think>` в режиме инлайн-тегов;
    - остальные — не возвращать. Рассуждения старых ходов, где провайдер не требует их, выкидывать для экономии контекста.
    - Сжатие контекста и `/resume` не должны терять `replay` у сообщений текущего цикла инструментов.
- **R3. Включение рассуждений в запросе и настройка провайдера.**
    - Связать `options.reasoning` с параметрами: Anthropic `thinking`, OpenAI `reasoning: { effort, summary: "auto" }` + `include`, Gemini `thinkingConfig: { includeThoughts: true, thinkingBudget }`.
    - Для OpenAI-совместимых провайдеров описать формат в `llm-providers.json`, например `"reasoning": { "format": "field" | "inline-tags" | "split", "requestParams": { "reasoning_split": true }, "replay": "deepseek" | "minimax" | "none" }`. У MiniMax по умолчанию `split`.
    - `capabilities.reasoningMetadata` выставлять по факту: сейчас у OpenAI и Gemini он `true`, хотя рассуждения не запрашиваются.
- **R4. Рассуждения не уходят в производные данные.** Подсказка, `wiki enrich`, память, заголовки сессий и итоги субагентов строятся только из `text_delta`. Это проверяется тестом на `runModelTurn` с рассуждающей фикстурой.

### Рассуждения: визуализация

Зависит от п.1: без потокового чтения показывать вживую нечего.

- **V1. Живое рассуждение.** Отдавать `reasoning_delta` в интерфейс сразу (`onReasoningDelta`), а не копить до первого текста. Пока модель думает, показывать открытый тусклый блок «thinking…» с таймером и последними 1–3 строками рассуждения.
- **V2. Фаза «thinking» по первому `reasoning_delta`**, а не при сбросе текста (`tui-shell.ts:2913`). После первого `text_delta` или вызова инструмента — обычная фаза.
- **V3. Итоговый блок с длительностью и токенами.** По завершении сворачивать в `◆ thought for 12s · 1.8k tokens`, токены брать из `openai.reasoning_tokens` / `gemini.thoughts_tokens` и аналогов. Раскрытие через `/think` / `ctrl+o` и копирование `y` сохранить.
- **V4. Скрытое рассуждение.** Для `redacted_thinking` и зашифрованных элементов показывать `◆ thought · скрыто провайдером` с длительностью и токенами, если они известны.
- **V5. Режим показа.** `/think auto | expand | hide` с сохранением в настройках: свёрнуто (по умолчанию), всегда развёрнуто, не показывать. Тот же режим — для не-блочного вывода `keryx agent` и для панели субагентов, где уже есть вид работы `reasoning` (`src/tui/subagent-bridge.ts:6`).

## Критерии приёмки

Зависание:

- [ ] Сервер, который отдал `[DONE]` и не закрыл соединение, не держит ход: `model_end` приходит сразу.
- [ ] Сервер, который молчит дольше таймаута простоя, даёт retryable `provider_error`, а не вечный спиннер.
- [ ] Первые символы ответа появляются в TUI до завершения хода.
- [ ] SSE-фикстура MiniMax с `content: "<think>…</think>Ответ"` при `format: "inline-tags"` даёт `reasoning_delta` с рассуждением и `text_delta` только с «Ответ», включая случай, когда тег разрезан между чанками.
- [ ] Payload compat-провайдера содержит `max_tokens`, payload OpenAI Responses — `max_output_tokens`, равные `budget.maxOutputTokens`.
- [ ] Подсказка с `<think>`, пустая или после таймаута не показывается; запрос подсказки отменяется при начале нового хода.
- [ ] `keryx wiki enrich` с моделью, отвечающей `<think>`, не пишет рассуждение в страницу.
- [ ] Ручная проверка: `keryx shell` с MiniMax-M3 в olimpyx, запрос «изучи документацию…» — есть потоковый вывод, строка «worked for», подсказка без `<think>` или без подсказки.

Рассуждения:

- [ ] Для каждого протокола из таблицы есть фикстура с рассуждением, и оно приходит как `reasoning_delta`, а не как `text_delta`.
- [ ] Цикл с инструментами возвращает провайдеру рассуждение по его правилам: подписи Anthropic, `thoughtSignature` Gemini, `reasoning_content` DeepSeek, `reasoning_details` MiniMax. Проверяется фикстурой, которая отвечает 400 при отсутствии этих данных.
- [ ] После `/resume` и сжатия контекста цикл инструментов с рассуждающей моделью продолжается без 400.
- [ ] `runModelTurn` с рассуждающей фикстурой возвращает текст без рассуждения.
- [ ] В TUI рассуждение видно до первого текста ответа, фаза «thinking» включается по первому `reasoning_delta`, итоговый блок показывает длительность и, если известны, токены.
- [ ] Ручная проверка с MiniMax-M3 (`reasoning_split`), Claude с `thinking` и Gemini 3 с инструментами: рассуждение видно вживую, цикл инструментов не падает.
