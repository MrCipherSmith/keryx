# Review в Keryx Desktop

Рабочая концепция для обсуждения · 19 ноября 2026 · Keryx `a634d4478`, релиз 0.4.39.

## Какую задачу решает раздел

Когда я открываю проект, я вижу PR подключённого репозитория, включая PR коллег без моего участия. Я могу найти работу конкретного автора или исполнителя, увидеть, у кого запросили ревью, какие PR вернули на доработку и где упал CI. С карточки я могу прочитать переписку, открыть PR или начать проверку конкретной версии. После следующего push я вижу, что изменилось с прошлой проверки.

Предлагаемая единица доски — **один PR**. Карточка существует с момента обнаружения. Она объединяет причины моего участия, переписку, раунды Keryx и ссылку на Flow реализации, если он есть. Закрытие локального раунда означает, что готов его результат. Закрытие PR определяется в GitHub.

### Что делает review-orchestrator после нажатия «Начать ревью»

Процесс определяет цель, base/head и необходимость раунда, собирает контекст и существующие комментарии. Для раунда он оценивает объём, выбирает роли, проверяет соответствие требованиям и запускает профильных ревьюеров. Затем сверяет замечания, проверяет их основания, сводит дубли и сохраняет отчёт, покрытие и структурированные findings. Хост и режим влияют на доступный путь выполнения. Для автономного запуска уже предусмотрены прогресс, бюджет, отмена и ссылка на пакет. [Процедура оркестратора](../../.metaproject/skills/gdskills/review/review-orchestrator/SKILL.md), [контракт автономного запуска](../../src/review/autonomous-run.ts)

В карточке достаточно показать цель, фазу, проверенный коммит и результат с переходом к доказательствам. Повторный запуск использует механизм Keryx для выбора предыдущего раунда. При переписанной истории механизм может выбрать полное ревью. Показательный случай из репозитория — пакет PR #1052 с суффиксом r02 имеет статус draft, а в данных раунда записано round 1. Номер раунда и вердикт берутся из содержимого пакета. [Манифест](../../.metaproject/reviews/2026-10-19-review-flow-github-com-mrciphersmith-keryx-pull-1052-r02/manifest.json), [раунд](../../.metaproject/reviews/2026-10-19-review-flow-github-com-mrciphersmith-keryx-pull-1052-r02/round.json)

## Как выглядит доска

В навигации проекта появляется **Review** рядом с **Flows**. По умолчанию видны все открытые PR, у которых базовый репозиторий подключён к проекту, включая черновики и PR из форков. Связь с Flow и участие текущего пользователя необязательны. Предлагаемый фильтр «Состояние PR» также открывает историю закрытых и слитых PR с постраничной загрузкой.

| Фильтр | Что выбирает пользователь |
|---|---|
| Автор | Кто открыл PR. Быстрый выбор «Я» показывает мои PR |
| Исполнитель | Любой из назначенных assignees, включая варианты «Я» и «Без исполнителя» |
| Запрос ревью | Конкретный пользователь или команда, у которых сейчас запрошено ревью. Доступны также «У любого» и «Запросов нет» |
| Решение ревью | Текущее решение GitHub по PR, в том числе «Запрошены изменения» (changes requested) и «Одобрено». История прежних решений доступна в карточке |
| CI | Итог проверок текущего head SHA: «Прошли» (зелёный), «Упали» (красный), «Выполняются», «Проверок нет». При неполных данных показывается «Неизвестно» и давность последней синхронизации |

Между фильтрами действует «И», внутри множественного выбора — «ИЛИ». Например, «Автор Анна» + «Запрошены изменения» + «CI прошёл» находит PR Анны, где сборка зелёная, но ревьюер ждёт правок. Сброс фильтров возвращает всю исходную выборку. После отправки ревью PR исчезает из фильтра запросов к этому ревьюеру и остаётся на общей доске. [Поведение GitHub](https://docs.github.com/en/rest/pulls/review-requests#get-all-requested-reviewers-for-a-pull-request)

| Колонка | Как сюда попадает PR | Основное действие |
|---|---|---|
| Требует внимания | По PR ожидают ревью или правок, упала проверка CI либо появилась обратная связь для текущего пользователя | Посмотреть причину, открыть обсуждение или начать ревью |
| На проверке | Идёт локальный раунд Keryx | Открыть ход проверки или остановить запуск |
| Открыто | Остальные открытые PR, включая черновики, PR без исполнителя и PR, по которым я закончил свой ход | Посмотреть последний ответ и отслеживать изменения |
| Завершено | GitHub подтвердил merge или закрытие PR | Открыть историю. Reopen возвращает карточку в активную часть |

Карточка раскрывает причину положения на доске: «Анна запросила ваше ревью» или «CI упал на проверке build». На лицевой стороне — репозиторий и номер, заголовок, автор, исполнители, ожидаемые ревьюеры, решение ревью и краткий текстовый статус CI. Подробности проверок и переход к упавшему запуску открываются в карточке. В деталях — обсуждения со ссылками на GitHub, локальные проверки по SHA, покрытие/отчёт и связанный Flow. Новая активность видна и во время выполняющегося раунда. Приоритет для одной позиции на доске: подтверждённое закрытие → активная проверка → требующее внимания событие или готовый к рассмотрению результат → «Открыто». Отдельная метка сообщает о новом head.

**Пример входящего ревью.** Коллега запросил ревью PR #42. Карточка появляется в «Требует внимания». Я запускаю проверку, читаю локальный отчёт, отправляю одобрение через GitHub. Если других причин для внимания нет, карточка переходит в «Открыто». Автор отвечает и пушит исправление. Эта же карточка снова требует внимания и показывает ссылку на ответ, предыдущий SHA и действие «Проверить изменения».

**Пример своего PR.** Мой PR #57 появляется в «Открыто» сразу после подключения проекта. Ревьюер оставляет два замечания в одном треде и общий комментарий. Карточка переходит в «Требует внимания». В деталях доступны один тред с двумя репликами и отдельный комментарий. Прочтение снимает отметку «новое». Собственный ответ или явная отметка «Обработано» завершает локальное действие; состояние треда по-прежнему берётся из GitHub.

## Ручной запуск и автоматическое наблюдение

На доске видны все PR выбранной команды в подключённом к проекту репозитории, включая PR коллег. Фильтры экрана управляют только отображением. У правила автоматизации своя сохранённая область действия, поэтому просмотр PR одного автора не приостанавливает наблюдение за остальными.

- **С карточки** можно выбрать «Запустить ревью сейчас» для текущей ревизии или включить «Авто для этого PR» и выбрать правило. Разовый запуск оставляет текущую настройку наблюдения.
- **В проекте** можно включить автоматический режим сразу для подходящих PR. Правило задаёт область действия, период опроса, событие и условия запуска. На карточке видны применившееся правило, причина последнего запуска и переключатель «По правилу проекта / Авто для этого PR / Только вручную». Предлагаемый приоритет — явная настройка карточки поверх проектной.
- **Watcher** по расписанию обновляет состояние PR, запросов и обсуждений, head SHA и CI. На первом опросе он фиксирует исходное состояние. Когда обнаружено подходящее событие, watcher передаёт PR и ревизию существующему процессу ревью. Повторное чтение того же состояния сохраняет тот же результат. Если CI ещё выполняется, событие остаётся ожидающим до успешных проверок на том же SHA.
- **Пример правила** — каждые 10 минут проверять открытые PR, где ревью запросили у выбранной команды. После запроса или нового коммита запускать ревью, когда CI этого коммита станет зелёным. Период и условие CI здесь иллюстрируют настройку.
- **Совпадение запусков.** Клик и срабатывание правила на одну ревизию открывают один активный раунд. Следующий push во время проверки сохраняет новый SHA в ожидании. Перед следующим запуском watcher заново проверяет состояние PR и правило. Закрытие PR снимает ожидающий запуск, повторный опрос после перезапуска не дублирует обработанное событие. В карточке доступны история запусков и их источники.

В Keryx обычные расписания может вызывать системный таймер, а сбор GitHub-дайджеста уже запускается из работающего `keryx serve` с сохранением обработанного интервала. Для Review предлагается использовать существующий механизм планирования и добавить обработчик событий PR. **Решение для первой версии.** Watcher работает локально на включённом компьютере независимо от процесса Desktop. После полного выхода из приложения он продолжает опрашивать PR и запускать ревью по расписанию. При следующем открытии Desktop показывает результаты этих запусков в карточках PR. [Команды расписаний](../../src/commands/schedule.ts), [планирование дайджеста](../../src/scheduler/digest-ticker.ts)

## Границы данных и синхронизации

- **Git-проект** предлагает репозиторий по remote. Для fork с origin и upstream человек видит выбранный target и может сменить его. Личность пользователя берётся из активного для проекта аккаунта gh. Доска показывает аккаунт и репозиторий.
- **GitHub** владеет PR, ревизией, review requests, отзывами, тредами и их состоянием. Для карточки сохраняются host, стабильный ID базового репозитория и номер PR. Одинаковый номер в разных репозиториях даёт разные карточки. Непрочитанное, наблюдение и обработку хранить локально с привязкой к аккаунту; два worktree одного репозитория не должны порождать два уведомления.
- **Keryx** владеет запусками и артефактами. У карточки 0..N запусков; у запуска есть собственная идентичность, проверенные base/head и ссылка на пакет. Для MVP — отдельный контекст проверки нужного SHA, без переключения пользовательской ветки. Повторный клик во время активного запуска открывает его. После смены head предыдущий результат получает пометку «Для предыдущей версии». Решение агента и GitHub review decision подписаны раздельно.
- **Синхронизация** загружает исходный снимок, затем обновляет его при открытии, возврате фокуса, вручную и по расписанию watcher при включённом автоматическом режиме. Сверяет уже отслеживаемые PR напрямую. Уход PR из поисковой выдачи может означать снятый запрос, исчерпанную страницу или изменение прав. Архивировать можно по подтверждённому состоянию. При офлайне или ограничении API сохранять последний снимок с временем обновления. Первичная загрузка наполняет доску без шквала уведомлений.
- **Интеграция** предлагается через проектный сервис чтения в Keryx с типизированным результатом и тонким мостом Desktop. Одинаковая форма данных нужна Tauri и browser dev bridge. Основой служит постраничный список PR базового репозитория. Поля фильтров нужны для всего списка, переписка и отдельные CI-чеки загружаются при открытии деталей. Для наблюдаемых обсуждений обновлять признаки активности и сверять страницы по стабильным ID. Периодический опрос объединяет события между двумя проверками; полная хронология мгновенных запросов потребует серверных событий.
- **Действия** в первой версии — открыть PR или конкретный тред, прочитать, обработать, запустить Keryx, настроить наблюдение и открыть результат. Просмотр работает без модели. Отправку ответа, approve и request changes в MVP пользователь завершает на GitHub. Будущий редактор ответа может подготовить черновик и показать его перед публикацией.

Выбор автора, исполнителя или ревьюера сужает результат на экране. Серверный вариант предпочтителен, если обязательны назначения от имени команды, круглосуточная работа при выключенных пользовательских машинах или единая история на нескольких машинах. Просмотрщик пакетов полезен как вкладка «Проверки» в обоих вариантах.

## Роль PR-Agent

PR-Agent — отдельный community-maintained проект. Его интерфейс поддерживает вопрос о PR, подготовку описания и независимое ревью. Для Keryx наиболее дешёвый эксперимент — дать ему зафиксированный diff, забрать результат в JSON и показать источник рядом с локальным отчётом. Это позволяет проверить пользу второго мнения до внедрения Python-среды и настройки второго провайдера модели у пользователей. CLI поддерживает plain-diff и файловый вывод. [README](https://github.com/the-pr-agent/pr-agent/blob/fee932335f15714a7c93ceadba246d881d12b84b/README.md), [CLI](https://github.com/the-pr-agent/pr-agent/blob/fee932335f15714a7c93ceadba246d881d12b84b/pr_agent/cli.py)

Сравнить на одних и тех же небольших и крупных PR: сколько дополнительных замечаний человек подтвердил, сколько пришлось отбросить, сколько занял запуск и во что он обошёлся. Отдельно проверить пропущенные части большого diff и совпадения с findings Keryx. Интересны реализации бюджетирования diff и учёта замечаний между ревизиями. Решение о включении адаптера принять по результатам сравнения. Для первоначальной доски достаточно GitHub и собственного оркестратора. [Подготовка diff](https://github.com/the-pr-agent/pr-agent/blob/fee932335f15714a7c93ceadba246d881d12b84b/pr_agent/algo/pr_processing.py), [состояние замечаний](https://github.com/the-pr-agent/pr-agent/blob/fee932335f15714a7c93ceadba246d881d12b84b/pr_agent/algo/review_finding_state.py)

## Первый сквозной срез и приёмка

1. **Подключение и чтение.** При первом открытии видны свой PR, входящий запрос и PR коллеги без моего участия и привязки к Flow. PR другого базового репозитория остаётся за пределами выборки. Повторный опрос и второе окно не создают копии. Отсутствие gh, авторизации или доступа отличается от пустой выборки.
2. **Работа с обсуждениями.** Inline-тред с ответами, тело отправленного ревью и общий комментарий доступны из одной карточки; повторное чтение страниц не увеличивает счётчики. После собственного ответа он виден в истории. При неполной выборке интерфейс показывает неполноту.
3. **Один локальный раунд.** Из входящей карточки можно начать проверку, видеть ход и открыть отчёт для конкретного SHA. Прерванная проверка допускает повтор. После нового push старая проверка сохраняется в истории и появляется действие проверки изменений.
4. **Жизненный цикл.** После отправки ревью запрос исчезает из очереди GitHub, и PR остаётся в отслеживаемых. Повторный запрос или ответ возвращает его в активную работу. Подтверждённые merge/close архивируют карточку; потеря сети сохраняет её с давностью данных.

5. **Фильтры.** На PR с разными автором, исполнителем и запрошенным ревьюером каждый из трёх фильтров находит правильную роль. Сочетание «Запрошены изменения» и «CI прошёл» находит карточку даже на второй странице. После нового push результат CI предыдущей ревизии остаётся в истории. При недоступном CI карточка не попадает в выборку зелёных, красных или PR без проверок.

6. **Автоматический режим.** При заданном правиле запрос ревью у команды и зелёный CI запускают один раунд на актуальном SHA. Повторный опрос и одновременный ручной запуск не дублируют раунд. Изменение фильтров доски не меняет правило. В режиме «Только вручную» тот же PR обновляется на доске и запускается кнопкой.

7. **Работа при закрытом Desktop.** Включить расписание и полностью выйти из приложения, оставив компьютер включённым. После выхода создать событие PR, подходящее под правило. В следующий интервал watcher запускает ревью. После повторного открытия Desktop в карточке виден ровно один запуск на соответствующем SHA, с временем запуска и источником «По расписанию».
