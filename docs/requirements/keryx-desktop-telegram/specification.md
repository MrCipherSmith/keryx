# Keryx Desktop Telegram Specification
Version: 0.4.0

**Status: spec ready.** The contracts below are proposed.

## Identity and existing integration

Module `keryx-desktop-telegram` extends the local ACP shell profile used by [Desktop Client](../keryx-desktop-client/README.md). [The existing Telegram guide](../../docs/guides/drive-keryx-remotely.md#remote-control-from-telegram) describes today's shipping terminal path. Its `serve` owns the Bot API poller, allowlist, topic registry, and outbound delivery. ACP currently implements status-only Telegram commands. The native headless catalogue separately marks Telegram control unavailable without a delegated principal. [ACP command runners](../../../src/acp/shell-command-runners.ts) · [Native command availability](../../../src/session/commands/tasks-integrations.ts)

| Owner | Planned responsibility |
| --- | --- |
| Desktop UI and native host | Integrations view, local service bootstrap and supervision, write-only bot-token action, per-chat controls and projected runtime state |
| ACP shell-profile process | Attach a Telegram bridge to a held session lease, admit remote turns, drive approvals and publish session events |
| `keryx serve` | Pairing and validation of Telegram sender/chat/topic, transport, heartbeats and outbound delivery |
| Session store | Existing transcript and optional connected interval. The live binding belongs to its ACP owner and is not restored from the interval. |

Reuse [ChannelsClient](../../../src/remote/channels-client.ts), [RemoteBridge](../../../src/remote/shell-bridge.ts), and the loopback [remote HTTP surface](../../../src/remote/http-surface.ts). [Existing topic registration](../../../src/remote/hub.ts) documents the behavior the new registration capability must preserve for the terminal. Desktop launches the bundled local executable and uses the existing Telegram poller in that process. No separate system installer is required.

## Configuration and storage

The existing user-global `serve.json` remains canonical for the local listener. For Telegram, introduce a versioned, owner-only committed channel record under the existing `remote/` directory. It holds the active revision, verified bot identity, credential and full existing RemoteConfig as one atomic activation unit. Preserve group, allowlist, orphan and run limits, permission mode, approval timeout and message rendering. Import valid legacy `remote/bot-token` and `remote/config.json` under the channel lock at first use. Verify and persist the stable bot ID on the first authenticated connection. Once migrated, new serve must read only the committed record for live credentials. Legacy writes and reloads cannot replace it. Refuse mutation requests that lack the revisioned capability after migration, with guidance to update the client. The supported terminal release retains its `/channels`, `/remote-policy` and `/rendering` workflows through the same current channel controller as Desktop. Move supported runtime reads to the committed revision, including live rendering and policy reads. Writers lacking the capability receive upgrade guidance. Disconnect retains an incremented disconnected record with no bot credential, so stale legacy files cannot be re-imported on restart.

The token uses a dedicated write-only local action and owner-only storage, including any temporary staging needed for local IPC. Telegram bot credentials, local HTTP API credentials, and pairing challenges remain separate. Leave the token out of slash commands, CLI arguments, prompts, diagnostics and events. Clear its input after submission. Desktop never accepts account or group IDs as form input. Resolve IDs from the authenticated local pairing result.

A pending pairing is identified by current service state and may be resumed before expiry. Test sends to the existing General topic. A machine-level Disconnect confirms the impact on all topics before invoking existing behavior. A session-level Detach archives only its binding and preserves history.

## Bot pairing and token changes

**Connect bot** accepts a token from BotFather through the write-only input. Validate it with Telegram `getMe` and use the returned bot identity and username. From a private, one-time pairing challenge, generate a QR code locally and offer **Open in Telegram** and **Copy code**. The QR and link open the bot's Telegram deep link with the challenge as the `start` parameter. The manual path sends the same code in the bot's private chat. The challenge is single-use, expires after ten minutes, and is invalidated on regeneration or cancellation. The QR submits `/start <code>` and both paths claim the same authenticated pairing generation, and the operator confirms the claimed account in Desktop before saving it. Then verify membership and Manage Topics in the forum. Only the authenticated pairing result may supply the account and group IDs. If Telegram cannot open the link or scan the QR, the manual path remains available. The QR, link, diagnostics and events exclude the bot token. Treat the challenge and its QR/link as sensitive. Keep them out of logs, telemetry and exported evidence. Clear them from the pending state and display on consumption, expiration or cancellation. The QR is rendered locally without sending the link to an image service. [Telegram bot deep links](https://core.telegram.org/bots/features#deep-linking) · [Telegram getMe](https://core.telegram.org/bots/api#getme)

**Change bot token** validates the candidate with `getMe` and checks its forum rights before activation. Compare the stable bot ID with the authenticated active or committed identity. A name change alone does not require pairing. With insufficient identity evidence require new pairing.

| Operation | Prepare | Activate |
| --- | --- | --- |
| Same verified bot | Keep the active binding IDs, group and allowlist. Preflight without starting a second poller for that bot. | Pause Telegram admission and invalidate outstanding Telegram approval projections. Desktop remains able to resolve eligible pending decisions. Stop the old poller before starting the candidate. Keep the exact live bindings and resume them only after activation succeeds. |
| Different or unverified bot | Pair the candidate account and forum in isolation. Keep the old channel working during pairing when the bot IDs are known to be distinct. When prior identity is unknown, defer candidate polling until the old poller has stopped. Ask before interrupting a still-running channel. The candidate cannot route session input or approvals. | After explicit operator confirmation and successful readiness for the candidate runtime, revoke the old channel generation before enabling candidate dispatch. Cancel old Telegram-origin turns and pending decisions as on detach. Desktop-origin turns continue. Close the old bindings without deleting Telegram history. Sharing any Desktop chat with the new bot requires explicit attachment to a fresh topic. |

**Readiness.** Wait for the candidate pairing poller to exit before starting its runtime poller. Keep the candidate dispatch disabled until the runtime poller returns its first successful `getUpdates` response after preparation, including an empty batch. A pairing poll, `getMe`, and the local service readiness probe each have their own purpose and cannot satisfy this condition. Poller conflict (HTTP 409), timeout or failure after the old poller has stopped triggers a revision-checked recovery. If the old token remains valid, restart the old poller and prove its readiness before showing it as connected. If Telegram has already revoked it or recovery cannot be confirmed, keep remote dispatch closed and show a retryable failure. On an uncertain response, fetch the actual committed revision and operation status before retry or rollback. Keep input closed while the active channel cannot be proven.

**Isolation.** Scope queues, callbacks and update receipts to verified bot identity and binding generation. A different bot starts with empty control state, even in the same forum. Retire old callbacks before enabling the new generation. Accept only input proven to belong to a live binding under the active generation. Staging must discard pre-activation input and fail closed on ambiguous delivery at cutover. Same-bot replacement preserves the exact attachment identity but invalidates the old poller generation. Preserve deduplication for already admitted input so the handoff cannot start that work again.

**Concurrent mutations.** Serve owns channel changes and serializes the final activation or disconnect with a per-user lock. Desktop and compatible terminal clients submit an authenticated operation generation and the expected active revision. Candidate validation or pairing leaves the active revision in place. At activation recheck both identities under the lock before pausing or stopping any active channel. Serialize the bounded handoff through confirmed commit or recovery. Atomically commit the record and publish at most one active dispatcher. The first successful mutation wins. A stale caller gets a typed conflict and refreshes state. Recovery may only restore state owned by its operation and cannot overwrite a newer revision. An interrupted process resumes from the last committed record after proving readiness. Stage secrets without rewriting the active record and clean them up on cancellation. Channel mutations do not change the local HTTP API credential. [Existing channel controller](../../../src/remote/channels.ts) · [Telegram getUpdates](https://core.telegram.org/bots/api#getupdates)

## First launch and service management

On a clean machine, **Set up and start** runs a native, app-level supervisor operation. Use the bundled Keryx executable by absolute path with fixed arguments and no shell interpolation. Reuse the CLI configuration and credential helpers through a local bootstrap entry that returns typed status and never prints the credential secret. The current interactive `serve token issue` prints that secret once, and `serve status` describes configuration, so neither output is suitable as the Desktop control protocol. [Current CLI implementation](../../../src/commands/serve.ts)

Bootstrap runs under a per-user lock and rechecks state before writing. For a clean machine it creates the existing loopback configuration, using `127.0.0.1:7377`, and issues the required local API credential silently. Persist only the normal credential verifier and reference. Reuse valid existing settings and credentials. If a valid configuration has no credential and the machine has no live owner, offer explicit completion of setup, preserving the bind and policy. A partial write can be retried without replacing an existing credential. Desktop supports loopback binds for both managed and external instances. A disabled service, invalid configuration or non-loopback bind is preserved and blocked with recovery guidance. Never silently overwrite, rotate, enable or widen them. The Telegram token is a separate input in the pairing step.

Expose machine status independently of the current project and chat. The native supervisor serializes operations across windows and concurrent Desktop launches. Before spawning, it probes the configured local endpoint with the existing authenticated shell-side protocol and checks the required capability. Show **Running** only after the expected instance proves readiness. Bound startup and shutdown waits. On timeout show Failed or blocked with a retry or recovery path. Keep any owned-child handle and prevent a replacement while its exit is unconfirmed. If an unknown process occupies the port, retain the configuration and report the conflict. Turning on Telegram pairing follows successful startup and does not start a second instance. Show service state separately from the channel state. A running service can have an unpaired bot, a pairing in progress or a failed Bot API connection.

| Service state | Operator actions and behavior |
| --- | --- |
| Not configured | Set up and start |
| Stopped | Start using the persisted configuration |
| Starting or stopping | Show operation in progress and coalesce duplicate actions |
| Running · Desktop managed | Stop and Restart. Use the held child-process handle, wait for graceful shutdown and confirmed exit. Only then start a replacement. Stop and Restart preserve configuration, credentials and bot pairing. |
| Running · external | Reuse the service for pairing and sessions after verifying compatibility. Stop and Restart apply to the owning process outside Desktop. |
| Failed or blocked | Surface a redacted reason and the available retry or recovery action |

Warn before stopping or restarting a managed instance with active remote bindings. Closing Settings or switching projects keeps the service running. On normal app quit stop the managed instance through its owned child handle and wait for bounded shutdown. An external instance continues running. The first release allows explicit starts from the app and does not install a login item or schedule automatic startup. The supervisor never signals an instance based solely on a PID, a port or an endpoint file. If ownership cannot be proven, display external or unavailable as appropriate. Stopping service delivery is separate from removing the bot connection. The split between an attached session and the app-level service is retained during reconnect.

## Controls and data contract

Proposed capability `_keryx/telegram/session`, available to the local Desktop client on the ACP shell profile. The [JSON Schema](schemas/telegram-session-control.schema.json) defines request and projected state shapes. `status`, `attach`, and `detach` apply to a held session ID. Publish the same state shape in a session update when it changes; on subscription or reconnect the client reads a fresh status. Capability absence leaves terminal instructions available. Use current `keryx serve`, `/channels`, and `/remote-control` for the terminal path. There is no planned new public CLI command in this release.

Project root and session identity come from the live ACP registry. The UI supplies a display name only. At most one in-flight attach and one active binding exist per held session. Repeated attach reuses the active binding. Internally bind the lease, registered topic and connection generation. Invalidate that generation on detach, owner loss, session archive, or shutdown. Late results from an invalidated generation cannot mutate the current binding. Desktop requires an exact-binding registration capability in serve. Existing terminal registration can reclaim an inactive topic by name, so it is unsuitable for Desktop isolation. Store a versioned ownership marker for Desktop registrations in the existing serve registry. During reconnect reuse a topic only on an exact match of session, owner incarnation, binding generation and thread identity. For a new attachment or a mismatch, allocate a fresh topic or refuse. Never dispatch queued updates from a previous binding, even if the display names match. An older serve without this capability reports incompatibility. Preserve legacy reuse for terminal-owned and unmarked records. Terminal registration must skip a Desktop-owned record when choosing a default name and refuse an explicit collision, including for inactive or archived Desktop topics. Status rendering never returns credentials or allowlist contents.

| Session state | Behavior |
| --- | --- |
| Detached | No active binding. Attach is explicit. |
| Attaching | The bridge is registering a topic. Duplicate attach coalesces. |
| Active | Inbound and outbound are enabled for the bound topic. Open topic appears when its link is known. |
| Reconnecting | Stop accepting new inputs until the same binding is confirmed. If the archive/registration no longer exists, return to detached and explain why. |
| Unavailable | Explain the service, capability or lease problem. An explicit attach can retry once resolved. |

## Turn admission and delivery

Both sources enter the same ACP turn execution path and synchronously acquire the existing per-session turn slot before mutating history. Tag Telegram input at the trusted transport boundary. The current terminal bridge passes only text and update ID to its host callbacks and resolves the actor at turn start. Extend ingress for Desktop to pass the verified sender identity, source, update identity and binding generation to ACP before admission. Refuse inputs with missing or unverified identity and record the delegated actor in local audit evidence. ACP callers cannot supply Telegram provenance or bypass the delegated check through prompt metadata. Desktop receives a server-originated start event and updates busy state for that session even when it is not selected. Stop, finish and error events clear only the matching turn. A late local send rejected as busy keeps its text for retry.

v1 chooses **busy refusal for Telegram**. If the slot is occupied, reply with Busy and ask the operator to resend after completion. No additional backend queue is introduced, and the existing Desktop composer queue continues to behave as a Desktop feature. Simultaneous sends contend for the same slot. Never start both. Key ingress deduplication to update and binding, retaining a bounded receipt under the live owner. A duplicate or an input recovered after an uncertain delivery never silently triggers a fresh turn. If the existing transport cannot prove whether an event belongs to the live binding after reconnect, require new input. Distinguish a busy refusal from an uncertain outcome in the topic.

Project final assistant text through the existing redaction and Telegram rendering pipeline. Mirror one logical reply per completed turn, with existing message splitting. Delivery of an already-produced reply may be retried using the existing transport queue; it never repeats the model turn. For uncertain outbound delivery show its state. No cross-restart exactly-once claim is made for Telegram messages. Forward progress summaries with the existing rate limits. `/status` and `/stop` are the v1 topic commands. `/stop` is scoped to the current Telegram-origin turn of the same binding. Always show whether a cancellation finished.

## Authority and questions

Model Telegram as a delegated principal derived from verified transport identity and bound to the session and generation. The default and ceiling for Telegram turns is Ask, constrained further by session policy and existing mandatory gates. A project-policy denial cannot be granted through either interface. A typed, explicitly eligible approval or operator question shares a single server-side decision record between Desktop and the topic. Use request identity, capture the active operation and deadline, validate the callback and settle once. On answer, expiry, cancellation, or detach invalidate callbacks and close projections. If a pending eligible question originated locally and Desktop remains attached to the session after Telegram detach, the Desktop projection can still resolve it up to its original deadline. On turn interruption or owner loss, unresolved execution approvals fail closed. Detach or authenticated machine disconnect revokes the binding, cancels its active Telegram-origin turn and invalidates pending decisions from that turn. Machine disconnect must reach every live Desktop binding through an authenticated control event. Each ACP owner must also refuse new remote work immediately if its connection cannot prove access. A Desktop-origin turn stays under Desktop control. While the service is reconnecting, revoke the Telegram projection of pending decisions and keep their Desktop projection available under its original deadline.

Keep durable grants, permission escalation, credential entry, git publication and destructive or privileged confirmations on Desktop. A Telegram confirmation never creates a persistent rule. For Desktop-only prompts, the topic may show that the session is waiting for the desktop operator. The topic does not receive sensitive prompt contents, private tool inputs/results or internal reasoning. The release excludes history export. Do not copy past turns automatically on attach, reconnect or chat reopen.
