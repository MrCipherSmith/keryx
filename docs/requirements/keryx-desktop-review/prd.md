# PRD · Review v1
Version: 0.1.0

## Проблема и цель

Сегодня доска Flows организует работу по локальным задачам. Статус PR текущей ветки, запросы ревью и результаты агентных проверок доступны в разных местах. Когда коллега просит повторное ревью после исправления, трудно сразу увидеть его запрос, новый коммит, состояние CI и результат прошлой проверки.

Цель v1 — из одного раздела проекта понять, какие PR требуют действия, проверить конкретную ревизию и увидеть результат на той же карточке. Пользователь может передать повторяющуюся проверку локальному watcher и закрыть Desktop.

## Кто пользуется

| Пользователь | Сценарий |
|---|---|
| Ревьюер | Выбирает запросы своей команды с зелёным CI, запускает проверку, читает подтверждённые замечания и переходит в нужный тред |
| Автор PR | Находит свои PR с запросами изменений. Видит, кто оставил отзыв, на какой коммит и где появился новый ответ |
| Ответственный за проект | Просматривает очередь коллег по автору или исполнителю. Включает правило на репозиторий и проверяет утром, какие PR обработаны и почему |

## Требования

**R1. Охват проекта.** В открытом проекте пользователь переключается между Sessions, Flows и Review. Все три раздела сохраняют контекст выбранного проекта. Начальный вид содержит все доступные открытые PR базового репозитория проекта, включая черновики, PR коллег без личного назначения и PR из форков. Одна карточка соответствует одному PR независимо от числа комментариев, worktree, запусков или связанных задач. История закрытых и слитых PR доступна по фильтру.
Verification: judged

**R2. Доска и фильтры.** Режимы «Доска» и «Список» используют одну выборку. Пользователь ищет по номеру или заголовку и сочетает фильтры по автору, исполнителю, получателю запроса ревью (человек или команда), текущему решению GitHub, состоянию PR и CI текущего коммита. Доступны «Без исполнителя», «Запросов нет», «Запрошены изменения», «Одобрено». Для CI различаются успех, ошибка, выполнение, отсутствие проверок и неизвестное состояние. Фильтры охватывают все страницы. Цвет сопровождается текстом.
Verification: judged

**R3. Причина и обсуждения.** В колонках «Требует внимания», «На проверке», «Открыто», «Завершено» карточка показывает причину своего положения. В деталях доступны общая дискуссия, текст отправленного ревью и треды по строкам, включая собственные ответы, ссылки в GitHub и связанный Flow при наличии. Новое сообщение, прочтение и разрешение треда различимы. Из карточки и из агентного контекста по PR доступны материалы рабочего Flow, если он явно связан с этим PR. Агент может найти задачу, план, журнал и свидетельства выполнения из основного checkout, в том числе при работе в другом ворктри. Для PR без связи агент получает самостоятельный контекст с ревизией и историей ревью. При неполной синхронизации видны давность и доступные данные.
Verification: judged

**R4. Запуск с карточки.** «Запустить ревью» запускает review-orchestrator для выбранного PR и ревизии, показывает фазу, даёт остановить проверку или повторить прерванную. При одновременном запросе из второго окна или watcher пользователь попадает в тот же активный запуск. Рабочая ветка пользователя сохраняется. Во время работы видны активность, текущая волна и прогресс по заданиям. До появления плана индикатор показывает ожидание. Пользователь может открыть сессию конкретного ревьюера и проследить, какие операции тот выполняет.
Verification: judged

**R5. История и доверие к результату.** Карточка хранит историю запусков с источником, временем, проверенной ревизией, исходом, покрытием и ссылкой на доступные результаты. После push видны прежний результат с пометкой об устаревшей ревизии и действие «Проверить изменения». Решение ревьюера в GitHub и локальный результат Keryx отображаются отдельно. Карточка показывает входные и выходные токены за запуск, отдельно для оркестратора и каждого ревьюера. В просмотре сессии доступны роль, статус, доступные сведения о модели, журнал действий, номер волны, время и расход токенов. Неполные данные явно отмечаются. При наличии данных о цене указывается стоимость и её источник. Причины отказа, отмены и исчерпания бюджета доступны без чтения служебного лога.
Verification: judged

**R6. Локальное наблюдение.** Пользователь включает, приостанавливает и возобновляет расписание, видит последний успешный опрос и состояние watcher. При включённом компьютере и доступных GitHub и Keryx процесс продолжает обнаруживать изменения и выполнять разрешённые проверки после полного выхода из Desktop. После сна или сбоя выполняется сверка актуального состояния. При первом открытии проекта вотчер выключен. Фоновый опрос начинается после нажатия Enable watcher или Resume watcher. Кнопка Refresh на доске разово загружает данные GitHub и сохраняет текущее состояние расписания.
Verification: judged

**R7. Правила.** Расписание проекта задаёт общий период опроса. Каждое правило определяет область PR, событие и условия запуска. Базовые события v1 — запрос или повторный запрос ревью и новый head SHA. Условия включают получателя запроса и состояние CI. На карточке доступны «По правилу проекта», «Авто для этого PR» и «Только вручную». Разовый запуск доступен в каждом режиме. Для новых ручных и автоматических запусков по умолчанию нет лимита токенов. Пользователь может задать положительный лимит в правиле. Ранее сохранённый числовой лимит продолжает действовать. Фильтры текущего экрана влияют только на вид доски.
Verification: judged

**R8. Предсказуемая автоматизация.** При включении правила исходный снимок фиксирует отправную точку. Новое подходящее событие порождает один запуск на ревизию либо ссылку на уже полученный результат. Если правило ждёт зелёного CI, оно сохраняет ожидающий PR. При close, смене SHA, выключении правила и неполных данных очередь пересматривается. История объясняет, что вызвало запуск или почему он ожидает.
Verification: judged

## Критерии выпуска

- На репозитории с несколькими страницами PR пользователь находит PR коллеги со второй страницы по сочетанию автора, запроса изменений и зелёного CI. При обрыве связи виден последний доступный снимок.
- На одном PR проверены запуск, отмена, повтор и новый push. По истории видно, какой SHA проверен, каким процессом и где открыть отчёт. Гонка двух окон и watcher даёт один активный раунд.
- На включённом Mac полностью завершить Desktop, затем создать подходящий запрос ревью и дождаться зелёного CI. После открытия приложения в карточке виден один завершённый запуск с источником «По расписанию», проверенным SHA и доступным отчётом.
- На том же наборе PR черновой или неполный результат различим от завершённого ревью. Опубликованные решения и комментарии в GitHub изменяются только действиями пользователя в GitHub.

## Как оценить пользу после выпуска

- **Поиск работы.** В первую неделю пилота ревьюер и автор на своём репозитории находят входящий запрос и PR, возвращённый на доработку. Наблюдатель фиксирует путь от открытия Review до выбора правильной карточки.
- **Польза watcher.** После недели использования владелец сопоставляет историю последнего сработавшего правила с PR, SHA и временем в GitHub. Для повторных опросов отдельно считает лишние запуски и пропущенные подходящие изменения. Если событий не было, оценка переносится до первого срабатывания.

## Границы и риски

Рекомендуется выпустить четыре этапа в порядке из [плана](implementation-plan.md). Первая версия использует GitHub и существующий review-orchestrator. Публикация выполняется через ссылки в GitHub. Серверная работа при выключенной машине, командное распределение запусков между компьютерами и второй движок PR-Agent отложены.

Основные риски — неполная выборка GitHub, недоступные фоновые учётные данные и повторная трата бюджета при гонке. Их проверяют соответственно на пагинации и сбоях, при закрытом Desktop и при конкурирующих запусках. Опрос видит наблюдаемые состояния. Запрос ревью, выставленный и снятый целиком между опросами, может остаться незамеченным.
