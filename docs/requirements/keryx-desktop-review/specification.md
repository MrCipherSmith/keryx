# Review v1 · Контракты и интеграция
Version: 0.1.0

Спецификация первой версии. Связанные контракты — [клиент Desktop](../keryx-desktop-client/specification.md) и [пакет результатов ревью](../managed-review-feedback-loop/specification.md).

## Проект, карточка и данные GitHub · R1–R3

Проект предлагает репозиторий по Git remote и показывает активный аккаунт gh. Для fork пользователь может выбрать upstream. Ключ PR состоит из хоста, ID базового репозитория и номера PR. Переключение аккаунта изолирует кэш приватных данных, отметки прочтения и настройки наблюдения. При потере доступа UI показывает причину и предлагает переподключение. При временной ошибке сети показывает время снимка.

| Запись | Минимальные данные | Кто обновляет |
|---|---|---|
| Снимок PR | Ключ, URL, состояние и draft, заголовок, автор, исполнители, запрошенные пользователи и команды, решение GitHub, base/head SHA, CI с полнотой, время чтения | Сервис чтения GitHub в Keryx |
| Обсуждение | Тип, внешний ID, тред и родитель при наличии, автор, время, ссылка, текст, признак resolved для треда | GitHub. Локальная отметка прочтения хранится на пользователя |
| Запуск | Стабильный ID, ключ PR, запрошенная и фактически проверенная ревизии, источник, правило при наличии, время, фаза, исход, причина и ссылка на пакет | Общий сервис запуска Keryx |
| Состояние watcher | Настройка проекта и аккаунта, интервал, правила и исключения PR, предыдущий успешный снимок, ожидающие события, отметки обработки, состояние последнего опроса | Локальный исполнитель |

Служебные снимки, правила и журнал запусков хранятся в пользовательских данных Keryx вне Git, с общим доступом из worktree одного проекта. Существующие managed review packages остаются источником отчёта и findings. Ссылки на результаты переживают очистку временного checkout. Результаты прошлых запусков доступны после перезапуска приложения. Секреты поступают через существующее окружение gh и Keryx.

Доска загружает страницы открытых PR базового репозитория, включая личные PR и PR коллег. Закрытые и слитые запрашивает по фильтру. Между измерениями фильтра — «И», внутри одного — «ИЛИ». Приоритет колонки: закрыт или слит → идёт проверка → есть запрос ревью, правок, провал CI, новый адресованный ответ или готовый результат к просмотру → открыт. Reopen возвращает карточку в активную выборку. Выход из списка запрошенных ревьюеров обновляет поля существующей карточки.

CI относится к последнему head SHA. Для полной выборки провал имеет приоритет над выполнением, затем следует успех, а при пустом наборе — «Проверок нет». Для частичной выборки итог неизвестен. Переписка загружается по запросу, с пагинацией и устранением дублей по внешним ID. Для списка уже есть каталогизированный запрос gh, для одного PR — чтение CI и тредов текущей ветки. Для доски требуется общий контракт полноты, обслуживающий и Tauri, и browser dev bridge. [Каталог gh](../../../src/trigger/granted-tools.ts), [текущий виджет](../../../apps/desktop/src-tauri/src/pullrequest.rs), [сбор комментариев](../../../src/review/pr-comments.ts)

## Обвязка review-orchestrator · R4–R5

Для каждого запуска фиксируются входные и выходные токены оркестратора и отдельных исполнителей. Общее значение складывается из уникальных измерений. Повторные события о завершении запроса и чтение кэша не добавляют токены сверх уже учтённого входа. При прерывании сохраняются доступные значения и признак неполного учёта. Стоимость, сообщённая провайдером, и оценка по известному тарифу должны различаться. У подписки может отсутствовать цена конкретного запроса. В истории запусков видна общая сумма. Разбивка по агентам свёрнута по умолчанию и раскрывается с мыши или клавиатуры. Длинная таблица прокручивается внутри карточки, при этом заголовки колонок и итог остаются видимыми.

Карточка показывает фактическое число завершённых заданий относительно известного плана и обозначает текущую волну. До появления плана индикатор показывает активность без процента. Сессии открываются отдельно для каждого исполнения роли. Журнал содержит наблюдаемые события запуска, названия инструментов и исход работы. Внизу доступны волна, время и измеренный расход. Для старых запусков источником служат сохранённые результаты. Если события или время отсутствуют, UI указывает это. Анимация учитывает системную настройку уменьшения движения.

Токены по умолчанию только учитываются. Явный числовой лимит правила останавливает запуск после достижения порога. Лимит времени применяется независимо.

Оба источника используют один набор операций в Keryx: запросить запуск, получить состояние/историю, остановить запуск, открыть результат. Desktop и watcher передают ссылку на PR, ожидаемые base/head, источник и причину. Для автоматики дополнительно передаются ID правила и наблюдаемого события. Действующие входы CLI сохраняют совместимость.

| Есть сегодня | Что требуется для v1 |
|---|---|
| Автономный runner разрешает head, держит блокировку каталога, передаёт прогресс, соблюдает бюджет и возвращает готовое summary при том же head. [Runner](../../../src/review/autonomous-run.ts), [summary](../../../src/review/autonomous-summary.ts) | Общий индекс и идентификатор запуска между окнами, watcher и worktree. До старта проверить актуальность base/head, использовать изолированный checkout, вернуть ID активного запуска при конкурирующем запросе. Для карточки и watcher вводится режим фиксированного диапазона: один запуск работает только с переданными base/head. Следующую ревизию ставит в очередь общий диспетчер. При реализации адаптер передаёт это ограничение в автономный профиль, который сегодня допускает ещё один раунд при смене head. Существующие прямые вызовы CLI сохраняют прежнюю политику. Правила проекта, навыки и права фонового исполнителя загружаются из доверенной установки и конфигурации проекта, в том числе при проверке PR из fork. [Профиль автономного ревью](../../../src/review/autonomous-profile.ts)

Заявка сначала атомарно регистрируется, затем передаётся runner. Пока один раунд PR активен, вызов для той же ревизии возвращает его ID. Новая ревизия становится следующей ожидающей. Перед передачей повторно сверяются состояния PR и правила. Если SHA изменился до старта, ручная карточка предлагает актуальную версию, watcher пересчитывает заявку. При восстановлении процесс сверяет заявку с блокировкой runner, состоянием процесса и результатами на диске. Сбой между записью заявки и стартом допускает повторную диспетчеризацию только после такой сверки. Гарантия дедупликации относится к одной рабочей машине.

Фаза и вердикт отображаются раздельно. Завершённый процесс может сообщить о блокирующем замечании. Черновик, пропущенный раунд, неполное покрытие, отмена, истёкший бюджет и ошибка имеют собственное объяснение. Нулевой счётчик замечаний сам по себе не даёт положительного вердикта. Источником истины служат фактически проверенный диапазон и результат пакета. При несовпадении ожидаемого и проверенного диапазонов результат сохраняется с пояснением. Вывод в GitHub остаётся действием пользователя.

## Watcher и правила · R6–R8

Для v1 предлагается один системный таймер macOS на включённое проектное расписание. Он вызывает задачу Keryx из устойчивой установки с доступом к настройкам проекта после выхода из Desktop. Операции управления доступны из приложения: включить, проверить состояние, приостановить, возобновить. Пользователь видит состояние установки таймера, время попытки, время успешной синхронизации и последнюю ошибку. Этот вариант переиспользует OS-schedule путь для ревью. Дайджест в существующем Keryx использует другой механизм исполнения, который требует работающего serve. [Пути выполнения расписаний](../../../src/commands/schedule.ts), [таймер дайджеста](../../../src/scheduler/digest-ticker.ts)

Правило хранит ID, включённость, область репозитория, событие, условия получателя ревью и CI, а также бюджет запуска. Период опроса задаётся расписанием проекта. В карточке «По правилу проекта» применяет совпадающие проектные правила, «Авто для этого PR» выбирает конкретное правило для карточки, «Только вручную» исключает PR из автоматических запусков. При выключении всего расписания фоновые запуски приостановлены. Открытие фильтра доски и разовый ручной запуск сохраняют эти настройки.

1. Первый полный опрос после включения задаёт исходную точку. При возобновлении после явной паузы watcher устанавливает новую исходную точку. После временной недоступности хоста он сверяет текущее состояние с последним успешным снимком.
2. Новый запрос/повторный запрос ревью или push создаёт ожидающее событие. Запрос определяется по наблюдаемому новому назначению либо идентичности события, когда она доступна. Несколько подходящих правил и повторное чтение одного снимка дают одну работу на PR и проверяемый диапазон. Повторный запрос на уже проверенной неизменной ревизии может сослаться на готовый результат.
3. Если условие требует зелёный CI, событие ждёт подтверждённого успеха для своего SHA. После нового push устаревшее ожидание заменяется последним подходящим. Закрытие, снятие нужного запроса, пауза и отключение правила снимают соответствующее ожидание. При неполной выборке watcher сохраняет снимок и показывает причину задержки.
4. На срабатывании исполнителю передаётся общий запрос запуска. Допускается один активный раунд на PR. Источник и результат записываются до следующего опроса. Ручной повтор после ошибки создаёт связанную попытку. Автоповторы требуют ограниченной политики с задержкой и учитывают уже потраченный бюджет.

## Приёмка интеграции

| Сценарий | Наблюдаемое доказательство | Требования |
|---|---|---|
| Две страницы, fork, PR без назначения, запрос команде, смешанные состояния CI | В обоих режимах видны одинаковые номера карточек с правильными фильтрами. Ошибка одной страницы обозначена | R1–R3 |
| Отзыв, inline-ответ, общий комментарий, затем ответ пользователя | Типы и история сохранены, повторное чтение не меняет счётчики | R3 |
| Ручной и фоновый запрос на один PR одновременно, затем смена SHA | Один активный ID, максимум один следующий раунд для актуальной ревизии, старый отчёт доступен | R4–R5, R8 |
| Завершение Desktop и последующее срабатывание на включённом Mac | Время старта после выхода, источник «По расписанию», верный SHA и доступный отчёт после открытия | R6–R8 |
| Пауза, отмена, потеря сети и перезапуск между заявкой и выполнением | Причины видны, карточки сохраняются, оплаченный запуск не дублируется | R4–R8 |
