# Remote agent transport, API and recovery protocol
Version: 0.2.0

Status: planned, normative companion to specification.md. Paths below are relative to /hub/v2; every route is new unless explicitly identified as existing. Schemas are in schemas/machine-protocol.schema.json and schemas/control-api.schema.json; their readable copies are in schemas.md.

## Transport and principals

Serve initiates WSS /machines/socket with subprotocol keryx.hub.machine.v2 and a machine Bearer header. Native-client Origin may be absent; an unexpected browser Origin is rejected. Browser events use WS /events/socket with same-origin HttpOnly human session and strict allowed Origin; browser Bearer/query-token access to the machine socket is rejected. Browser sockets send no commands. Authentication, project filtering and size checks occur before upgrade. No secret belongs in Sec-WebSocket-Protocol, URL or payload. Protocol version 2 is an application protocol, independent of MCP and local Telegram SSE.

Every application frame has v, type, messageId, epoch and payload; unknown fields/types are rejected. hello uses epoch 0; welcome establishes the positive epoch for subsequent frames. machineId is taken from authentication, never from a caller's assertion. Validate payload ownership on every frame. Direction is explicit:

| Frame | Direction | Meaning |
|---|---|---|
| hello | serve → Hub | Stable ledger identity, fresh daemonId, supported adapter versions, last durable Hub cursor and per-run event cursors. |
| welcome | Hub → serve | Admitted machine/epoch, heartbeat constants and replay/resync mode. |
| heartbeat / heartbeat-ack | serve → Hub / Hub → serve | Liveness only; neither grants execution nor acknowledges undelivered commands. |
| inventory | serve → Hub | Versioned allowlisted project/checkout/profile readiness projection. No arbitrary paths/env/executable arguments. |
| command | Hub → serve | Closed start-turn, cancel-run or answer-approval operation; durable commandId, sequence, exact target, authority and expiry. |
| command-receipt | serve → Hub | Durable received/admitted/rejected/applied/not-applied result. A transport receipt alone is not process start, approval consumption or terminal stop. |
| run-event | serve → Hub | Durable per-run local seq and typed state, safe log, approval question/outcome or result-ready reference. |
| run-event-ack | Hub → serve | Highest contiguous local seq actually durably admitted for that run. Never accept a cursor for unsent events. |
| context-changed | Hub → serve | Project revision invalidation only. Fetch authoritative context via existing REST. |
| error | either | Closed sanitized code plus related message ID when known; no raw exceptions/content. |

Browser event frames are a separate closed invalidation shape (v, type=resource-changed, projectId, resource, resourceId, version). They tell TanStack Query what to refetch. Authoritative run/event data is fetched by scoped HTTP; project selection/auth changes cancel stale requests and close obsolete subscriptions.

## HTTP surface and roles

Human mutation means role operator, current authenticated session, Origin protection and Idempotency-Key. Human reviewer can inspect permitted project data but cannot launch/cancel/answer machine approvals in this feature. Existing Flow acceptance permissions are not changed. Existing agent MCP principals cannot impersonate human actions; adding MCP control tools is a later explicit decision. Machine auth only authorizes self-owned scoped reads, inventory/events/receipts and result uploads.

| Route | Principal | Contract |
|---|---|---|

| POST /machines/enroll | One-use pairing capability | EnrollmentRequest; atomically consumes code and creates machineId plus secret once. Rate limited; no human/agent fallback. |
| GET /machines, GET /machines/:id | Scoped human | Metadata, inventory, lastSeen and readiness; no credentials/local absolute paths. |
| POST /machines/:id/revoke | Human operator | Expected machine version; revokes immediately, closes socket and records audit; local downloaded data is not erased. |
| GET /projects/:p/runs, GET /projects/:p/runs/:r | Scoped human | Bounded paginated summaries/details, with exact selected references and separate connection state. |
| POST /projects/:p/runs | Human operator | StartTurnRequest; atomically records session-bound turn/run, immutable request digest and durable start command, or refuses before dispatch. |
| POST /projects/:p/runs/:r/cancel | Human operator | CancelRequest; expected run version, idempotent cancellation request, no false cancelled response. |
| GET /projects/:p/runs/:r/events?after=N | Scoped human | Up to 500 events/512 KiB; cursor is highest contiguous admitted seq, with explicit retained-range gap metadata. |

| POST /machines/:id/commands/:commandId/authorize | Owning machine | AuthorizeCommand; current authority check and command-bound AuthorizationGrant valid at most5seconds, no execution by Hub. |

All JSON mutations except enrollment require operation keys; changed-payload reuse conflicts. Enumeration, individual resources, browser invalidations and replay are project-scoped. Known bad IDs cannot leak another project's existence/content. Missing/stale versions/digests return visible errors; no unrestricted status setter. Existing context/document/revision/Evidence endpoints retain their current contracts and guards. Machine reads of existing context/spec/Flow-reference routes require the new machine scope gate; do not reclassify machines as agent:connector.

Protocol errors: invalid-frame, unsupported-version, wrong-direction, stale-epoch, unauthorized, forbidden, scope-denied, stale-reference, machine-offline, machine-busy, checkout-dirty, setup-required, command-expired, payload-conflict, approval-expired, approval-not-applied, quota-exceeded, replay-gap, recovery-required and internal-error. HTTP uses existing 400/401/403/404/409/413 conventions; sanitized 429 handles rate limiting. Socket close codes follow RFC semantics (1000 normal, 1008 policy, 1009 size, 1011 internal, 1012 restart); never include private diagnostic data in close reasons.

## Request and state binding

StartTurnRequest binds an existing persistent session, session/controller/config/history versions, owned workspace baseline, message identity and Flow-or-ad-hoc association. Hub and machine independently verify canonical records and local mapping/policy. For Flow association criteriaDigest is SHA256 of the UTF-8 JSON.stringify serialization of the ordered frozen criteria array (no reordering/normalization). IDs, project, versions and per-turn snapshots remain immutable. V2 run/session command digests and new foundation APIs are defined below; there is no sessionless launcher. Limits come from local profile plus Hub ceilings; browser cannot raise them. Browser logout/role revocation cannot undo completed effects; every new application/approval/cancel requires current authority and bounded grants.

Hub state vs observed runtime:

| Transition | Required evidence |
|---|---|
| dispatching → received | Local command claim durably stored; receipt does not claim execution. |
| received → starting | Validation passed, checkout lease and pre-start marker durably stored. |
| starting → running | Actual executor accepted, with local turn/session identity. |
| running ↔ waiting-approval | Exact broker question/consumption; unresolved question never counts as allow. |
| active → paused | Control disconnect reached a safe boundary; running tool may still be finishing until then. |
| active → cancelling → cancelled | Request, executor stop acknowledgement, then confirmed supervised work cessation. |
| active → succeeded/failed | Durable native result and actual outcome; checks and Flow acceptance remain separate. |
| uncertain → unknown | Lost process ownership or unreconciled crash; do not infer stopped/running. |
| unknown → running/terminal/lost | Authenticated reconciliation with actual local identity/absence, plus explicit human resolution when ownership remains ambiguous. |

reject is terminal for a start refused before execution. All terminal records are monotonic; an incompatible late terminal report is an explicit reconciliation incident, not silent replacement. Native tool side effects and external human filesystem edits cannot be made exactly once by a transport protocol. A running state event must carry nativeIdentity (sessionId, turnId, daemonId, supervisorHandleId); later state events retain it. These are opaque local references, not executable process identifiers or permission to kill.

## Local ledger and crash matrix

Keep unique identities for Hub command, run, native session/turn, daemon generation and supervised task. Do not substitute a vendor session handle or PID for any of these. Local SQLite claims/lease changes and outbox writes must be transactional and cross-process serialized; existing serve turn idempotency alone is only same-process safe.

| Crash boundary | Recovery |
|---|---|
| Before Hub transaction commit | No accepted run; replay HTTP with same key. |
| After Hub commit, before delivery | Durable outbox may redeliver while online, authorized and unexpired. |
| After local claim, before pre-start marker | Revalidate and admit the same run once; no distinct new run. |
| After pre-start marker, before/after spawn | Unknown until proven ownership/absence; never automatic spawn retry. |
| After start, before receipt reaches Hub | Replay stored events/receipts and reconcile existing runtime; never relaunch. |
| After durable approval decision, before local consumption | Re-deliver only while exact waiter/action/policy valid; expired/orphan approvals deny/abandon. |
| After local result, before Hub ack | Idempotently replay exact result/events; checks/revision are not duplicated. |
| After Hub result transaction, before response | Same key returns original exact revision/check receipt. |

Daemon restart makes unresolved in-process executions unknown, not resumable promises. Reconciliation may attach only to a still-provable supervisor identity; otherwise preserve lease and require local recovery. Native session history is context, not proof that a suspended action may be rerun. No autonomous requeue of unknown starts.

## Bounded delivery, retention and reconciliation

Max 64 KiB encoded frame/32 KiB prompt/8 KiB log chunk. Output buffers have a 256 KiB per-connection high-water mark. Retain at most 10 MiB log data per run and seven days after terminal; use explicit dropped range/gap records. Critical receipts, approvals, terminal states and launch tombstones have separate durable storage. Do not acknowledge unpersisted critical events or prune unresolved launches. If a critical quota (1000 pending commands per machine or 100000 retained launch identities locally) is reached, refuse new launches with quota-exceeded; operators retain a recovery/export path. V2 has no automatic launch-identity pruning.

Both peers send/ack contiguous sequence cursors; sequence gaps trigger bounded replay. A log-gap frame at localSeq B+1 may cover the next unacknowledged range A..B only if A equals Hub cursor+1, no known critical event lies in the range and the local ledger retained the discarded records as log-only metadata. Hub transactionally records the explicit gap before advancing the cursor across A..B and then B+1. Overlapping, regressing, fabricated ranges or any range covering critical receipts/state/approvals are rejected; do not advance based on a numeric cursor alone. Log-only discard metadata is replayable until acknowledged. Critical events stay durable and are never represented by gaps. If retained logs cannot satisfy replay, send current state plus an explicit missing log range; do not regenerate or rerun execution. Each Hub command is additionally rechecked for expiry before local admission. Start TTL is 60 seconds; cancel delivery TTL is 60 seconds and an expired unresolved request remains visibly unconfirmed; the operator may issue a new idempotent cancel operation after refreshing state. Approval TTL is the local broker deadline, at most five minutes, and cannot be extended by delivery retries. Application heartbeat is not a durable-event acknowledgement.

On welcome resync-required, fetch every scoped RecoveryPage, compare stable ledger/run/command identities, submit ReconciliationReport for unresolved runs and replay retained critical events plus explicit log gaps. Do not infer executor state from Hub state alone. Reconciliation observations are owned-running, confirmed-stopped or unknown, with optional nativeIdentity; they are authenticated machine assertions, not tamper-proof proof of OS state. Hub stores a receipt bound to machine/ledger/daemon/project/checkout/run/expected version and received time. Human resolve-run must reference a matching receipt received within30seconds. Unknown cannot resolve to running/stopped/lost without additional actual local ownership/absence verification; an operator label alone cannot clear a filesystem lease.

Immediately before start, cancel application or approval consumption, call authorize with commandId/target/commandDigest and current local policy digest (plus actionFingerprint for an approval). Hub rechecks current machine scope, stored command integrity/expiry, current actor/session/role and applicable run/action state, then returns grantId plus command/target/controller/digest/policy/action/actor and an expiry no more than5seconds away. Verify exact binding, local monotonic elapsed time since authorization request less than5seconds, server deadline and local policy/broker state. Do not persist a grant for restart or apply it after reconnect; failed authorization stops that application. Cancellation is allowed under a tightened policy when it only stops a provably owned run; start/approval require matching pinned policy. Idempotency keys distinguish authorization attempts; lease renewal always performs a fresh authority check. A later role revocation may race with a live grant for at most5seconds; this bounded window is explicit.

Inventory is a versioned complete projection of only locally allowed mappings; missing entries become unavailable, never auto-delete local work. Reconnect first reconciles capabilities/policy/run state and missing events before admitting new starts. Stale epochs cannot update progress or consume approvals. A ledgerId mismatch on an enrolled machine is recovery-required and blocks dispatch; credentials alone do not assert that old execution claims survived.

## Persistence and migration

Add normalized tables in existing hub.sqlite: remote_schema_version, remote_machine, remote_pairing, remote_inventory, remote_run, remote_command (unique machineId/commandId and project/request-key scope), remote_event (unique runId/localSeq), remote_approval_projection, remote_authorization_grant, remote_reconciliation and remote_result_receipt. Store payload hashes alongside keys. Use parameterized SQL, foreign keys/project associations, indexed project/status/run cursors and the existing single mutation authority. The new store API must atomically update remote tables and existing hub_state when a result creates Code Revision/Evidence; two separate connections/cached snapshots are not a transaction.

Local checkout exclusivity additionally uses an atomic owner-nonce lock in the resolved per-worktree Git administration directory, shared across Hub enrollments and serve config roots; it must not be scoped only to a per-Hub database. No timeout-based stealing. Local control.sqlite stores ledger metadata, received commands/payload digests, runs/start markers, checkout leases, event outbox and ack/recovery cursors. Secret file is separate, 0600, parent0700. Real local canonical paths remain local. Hub stores request provenance and actor, last observed state/time, run pins and sanitized events, not local model/provider secrets. Open connections, active abort controllers and process handles are runtime-only and never reconstructed from a numeric PID.

Migration is additive/versioned and backed up consistently, with rollback on failure and explicit rejection of unsupported versions. One-process SQLite remains the scale boundary. Backup/restore reconciles machine local ledgers before dispatch: restored Hub cursors do not authorize replay of old side effects. Compatibility testing must include current JSON aggregate, sessions, SSO identities, Flow pins and integration line remaining unchanged.

## Persistent SessionHost contract (v2)

This new package supersedes the planned v1 transport; v1 was never implemented. The old `hub-remote-agents` requirements package remains unchanged for provenance. No v1/v2 negotiation, downgrade or claim of an existing v1 deployment is permitted. SessionHost and these endpoints are planned foundation work required now; full browser chat rendering is a later client. Neither terminal input/rendering nor a scraped CLI subprocess is part of execution. All 16 original guard areas remain normative, with only the explicitly stated session continuation and per-turn association extensions: outbound transport/auth; pairing/scope/revocation; trusted checkout mapping and containment; real executor lifecycle; durable idempotent delivery; safe output/replay; exact tool approvals; actual cancellation; crash/ownership reconciliation; immutable revision/check provenance; scoped browser/auth; transactional storage; Flow/spec pinning; policy/budget/credential boundaries; recovery/retention limits; and proof-based acceptance.

`SessionHost` owns history, configuration, queue, confirmations, native execution and leases; terminal/headless clients call the same domain services. Agent-command metadata alone is not an executable registry: publish the catalogue only from actual shared handlers and their argument schemas. The current complete RemoteCommandHost is TUI-wired and ACP exposes only four commands; extracting shared handlers/host is required work, not existing parity.

### Identity, admission and history

`sessionId` is allocated by Hub before the durable create command and remains stable across open, idle, subsequent turns and daemon restarts. A session is bound to project/machine/checkout/profile; reassignment requires a separately admitted fork, never an in-place path override. `nativeIdentity.sessionId` must map to this same persistent SessionHost identity; vendor handles remain separate local mapping data. `runId` and `turnId` identify one admitted execution; `operationId` identifies the user's durable HTTP operation and `commandId` one machine delivery. Queue submission does not invent a run/turn. Only atomic admission allocates the run/turn pair and ordinal, records a pre-start marker and claims the single executor slot. Concurrent controllers, local terminal and remote clients cannot admit two turns in one session. Checkout and native session leases remain cross-process and cross-enrollment; controller permission grants neither lease.

First session admission requires the selected clean checkout, HEAD, inventory, capability and policy checks. Later turns accept that session's own uncommitted edits: revalidate its durable owned workspace baseline (base SHA plus tracked/untracked owned change digests and provenance), native session/checkout lease and absence of external interference. An unexpected external change is `workspace-conflict` with explicit local reconciliation, never force reset, blind overwrite, or demand that the agent erase/commit its own prior changes. Baseline changes are committed to the ledger only with actual owned turn effects; a browser-supplied digest is only an expectation, never proof.

`open` attaches a reader to an existing session and returns its projection/history; it does not start a turn, resume tools or claim control. `resume` reopens an idle/paused durable session after reconciliation and version/baseline checks; uncertain executions stay recovery-required. The fork-session machine body includes Hub-preallocated newSessionId plus the exact validated SessionFork request; target identifies the source session and its expected version. `fork` requires an idle source and an exact history cursor/version, creates a new identity with a durable ancestry reference, and admits a separately mapped clean target checkout. It does not clone active tasks, approvals, executor ownership, secrets, controllers or Flow evidence. `close when-idle` seals the queue against further submissions and closes after current confirmed work ends; `cancel-and-close` uses the normal cancellation/cessation handshake. Unknown ownership prevents closed/released claims. History survives close according to retention/export policy.

Messages are literal text, including slash-led text, and never parse into commands. Explicit catalogue command invocation is a different endpoint; parse/validation failure cannot fall through to the model or OS shell. Current text messages preserve multiline content up to 32 KiB; SessionCapabilities explicitly reports attachments=false and typed-artifact-contract-required. Attachments are explicitly unsupported in v2 and rejected as unknown fields, rather than silently discarded. Future attachment support requires a versioned typed artifact capability contract. History includes human messages, safe assistant/tool summaries and structured receipt references, never hidden reasoning, secrets or raw provider payloads. History pages are at most 100 records/512 KiB; ordering is persistent `historyCursor`, distinct from session-event cursors and run localSeq. Compaction is a registered confirmed command at idle: retain original message identities/provenance and an explicit compaction marker/range; it never silently rewrites executed history or existing pins.

### Controllers, queue and safe boundaries

A controller lease has a monotonically increasing controller version, authenticated human operator actor, expiry of at most 60 seconds and explicit lease ID. Claim is compare-and-swap against session/controller versions. Renewal every 20 seconds uses the explicit /controller/renew operation, requires the same currently authenticated human holder, exact controllerLeaseId, controller generation and expectedSessionVersion, and extends expiry by at most 60 seconds. Machine heartbeat never renews human control. Release requires holder, lease and expected versions and returns a stored receipt. Takeover is an explicit operation referencing that release receipt or a separately locally verified recovery receipt; an expired/disconnected browser alone is not proof of executor cessation or ownership release. A lease can expire, making future mutation unauthorized; only safe pause/cancellation rules apply to running work, not fabricated terminal state. No last-connection-wins behavior, automatic claim on websocket connect, observer mutations, or takeover through a fresh tab. Session/checkout/supervisor ownership remains independently mandatory even after controller transfer. Local terminal ownership participates in the same arbitration; remote takeover cannot steal its native lease.

Queue mutations require session/controller plus queue/item versions. Edit/remove is allowed only while the item is still queued and unclaimed; edit applies only to literal message content. Ordering is FIFO for work and configuration operations, with a bounded 100 pending items per session. Reject overflow visibly. An idle-boundary configuration/command operation cannot overtake earlier messages. An operation entering the queue gets a durable receipt; reusing its operation key cannot enqueue twice. At application, recheck actor authority, lease, policy, schema/catalogue, confirmation expiry and relevant versions; rejected queued operations remain visible with a reason and cannot become model prompts. Controller change suspends queued work until the new holder explicitly reauthorizes it as a new operation referencing the original queue item; no inherited approvals or silent execution on behalf of the old holder. QueueReauthorize references the path queueItemId, originalOperationId and exact item/queue/session/config/controller versions plus a freshly pinned association. Atomically mark the old suspended item superseded/removed and create a new queued operation with replacesOperationId lineage and preserved content/position; do not reuse the old command, grant, confirmation or execution identity. Recheck current schema/policy/authority and request fresh confirmations. The session-command target additionally includes the queueItemId inside its body; this identity cannot be changed on replay. New admitted work then follows FIFO among still-authorized items. A queued operation is not a durable execution grant: at every actual application/admission mint a new command envelope bound to the current controller generation and current target versions and obtain a fresh ≤5-second grant. Retain the original operation identity/payload hash to prevent duplicate effects. Never replay an old controller grant to authorize a future turn; expired deliveries stay tombstoned and renewed delivery uses a distinct immutable command identity tied to the same unexecuted operation.

Configuration changes, routing changes, compaction, model selection and session identity commands apply at a confirmed idle boundary. Busy policy is explicit reject or queue-at-idle as permitted by catalogue metadata. Config receipts report queued/applied/rejected and exact `effectiveFromTurnOrdinal` when applied; queued receipts use null rather than guess a future version. `configVersion` increments only on applied changes; `sessionVersion` increments on accepted queue/controller changes too. Each queued change compares the pinned expected config version again at application; a preceding config update may make it stale and require an explicit new operation. Configuration never changes an active turn's immutable snapshot. Before each message becomes a turn, snapshot baseline candidate, routing profile/candidates, reasoning effort, config/policy/capability digests and decision receipt. Candidate selection and later fallbacks publish actual provider/model, selection reason and final usage; if the actual provider differs, record a new selection receipt before that provider call and recheck consent/budget. Manual model selection changes the baseline while routing may stay enabled; classifier failure falls back to that baseline only if still locally permitted.

### Catalogue and routing authority

`capability-page` is a machine→Hub frame carrying CapabilityPage from the authenticated local registry/provider state, keyed by project/checkout/profile and projectionVersion with inventory/policy/capability/catalogue digests. Catalogue and routing pages carry at most 16 entries and 64 KiB per frame, bounded total entries (1000 catalogue, 128 candidates), cursor and nullable nextCursor. Persist staging pages by projection/kind/cursor; duplicate identical pages are idempotent, changed payload conflicts. Require contiguous page indexes and exact counts, recompute the canonical catalogue digest, and publish only after both complete sets for the same trusted inventory/projection exist. No partial/fabricated availability is executable. Missing/stale/offline projection means unavailable/setup-required; Hub never guesses connected providers or constructs handlers from metadata. Reconnect retransmits the complete current projection before new work; invalidations announce its version. Digest is SHA256 over UTF-8 JSON.stringify of command entries sorted by commandName with recursively sorted object keys; IDs are unique and all published schemas are checked within the byte/depth budget. Oversized entries are explicit implementation/setup gaps, never silently omitted from the coverage inventory. Routing and catalogue reads expose only the last complete scoped machine projection and freshness.

The catalogue is versioned and digest-bound, derived from the actual registered commands/subcommands and shared domain handlers; each entry carries input and result schemas, handler ID, mutation class, allowed states, busy policy, confirmation and availability reason. Every command/subcommand needs a coverage classification; a missing required handler is `implementation-gap`, a release gap rather than permanent TUI-only parity. Discovery cannot expose handler closures, paths, tokens or arbitrary route names. The restricted `ArgumentSchema` language permits only bounded primitives, arrays and closed objects, no remote `$ref`, expressions, code, custom executable validators or shell interpolation. The generic `BoundedJson` argument/result carrier is limited to 32 KiB encoded, depth 8, 64 properties per object and 128 items per array. It is **not** sufficient validation: both Hub and SessionHost compile/validate against the exact selected entry's published input schema before dispatch, reject unknown fields/types, and validate the structured result against its result schema. Published object schemas must have additionalProperties=false and required names must exist in properties; reject malformed/deep/unbounded catalogue schemas. Stale digest, unknown command or invalid arguments reject without model/OS-shell fallback. Catalogue and capability digests are rechecked at queued application. Commands that initiate agent execution or workspace mutation allocate real runId/turnId at admission and use the same per-turn association, snapshot, executor slot, checkout lease, grant and result rules as messages. Pure read/config/controller commands have no run identity. The catalogue cannot route workspace effects around the Flow/ad-hoc guard.

Routing candidates are local opaque allowlisted IDs representing connected provider/model capabilities; no client-supplied base URL, provider key, executable, env or network destination. The local policy allowlist, provider consent, privacy/egress constraints and spend ceilings intersect Hub limits. Routing cannot widen any of them, machine permission mode, sandbox, tool trust or external adapter authorization. Cost/privacy changes require an exact single-use human confirmation bound to operation digest, before/after config versions, candidate set, policy, actor/controller and expiry (at most five minutes); a reusable boolean `confirmed` is invalid. ### v2 command digests, events and recovery

For run command envelopes (`start-turn`, `cancel-run`, `answer-approval`), the digest is SHA256 over UTF-8 JSON.stringify of fixed-order tuple `[2,"run",kind,commandId,hubSequence,sessionId,runId,turnId,projectId,checkoutId,expectedSessionVersion,expectedRunVersion,controller,expiresAt,authorizedBy,canonicalBody]`. For session-command envelopes the tuple is `[2,"session",kind,commandId,hubSequence,projectId,checkoutId,canonicalTarget,expiresAt,authorizedBy,canonicalBody]`. `canonicalTarget` is the closed typed `CommandTarget`; create uses a preallocated session target with expectedSessionVersion=0, never a fake run. Bodies retain exact validated values and recursive Unicode code-point key sorting; arrays remain ordered. Duplicate keys reject before canonicalization. Expected versions, target, actor, expiry, operation details and controller binding are immutable; transport epoch/messageId and fresh grant IDs are excluded. Body digest confirmations do not include their own receipt ID (compute the operation digest from the exact request with confirmationReceiptId omitted); delivery commandDigest includes the receipt ID when present. A retry cannot renew expiry or replace pins.

`AuthorizeCommand`/`AuthorizationGrant` use a closed run-or-session target and controller binding. For create or explicit controller-claim operation only, controller may be null: Hub checks current human operator, expected versions and ownership transition; every existing controlled mutation requires the exact held controller lease. Authorize immediately before each domain application, including queued item admission/config application and command confirmation consumption. The server rechecks scope/role/session/controller and exact immutable command/policy/target digest and returns an actor-bound grant valid no more than five seconds. Verify deadline and local monotonic elapsed time; grants are never reused after restart/reconnect. The same bounded revocation race remains explicit. A stop-only cancellation can use tightened policy for provably owned work. A session command authorization grants no arbitrary handler, runtime path or process control.

New `session-command` (Hub→serve), `session-command-receipt` (serve→Hub), `session-event` (serve→Hub) and `session-event-ack` (Hub→serve) frames coexist with typed run events. `hello.sessionCursors` separately replays highest contiguous durable session-event seq. Session events persist messages, turn admission/config snapshots, queue/config/controller receipts and command outcomes. `sessionEventSeq`, `historyCursor`, `hubSequence` and each run's `localSeq` are distinct namespaces; none acknowledges another. Command lifecycle replay uses durable command identity/receipt, not history text. Hub acknowledges only contiguous persisted session events. Critical session events cannot be pruned as log-only gaps; retention exhaustion rejects new work until export/recovery, never executes silently. Persist sessions, messages/history cursors, turns, queue items, config versions/snapshots, controller versions/releases, command catalogue digest snapshots, confirmations and session-event outbox/cursors in normalized versioned storage in addition to the existing run ledger. ### Flow and ad-hoc result provenance

Every executing turn snapshots `association`: either current managed Flow ID/version/spec/ordered criteria digest or explicit ad-hoc mode allowed by the local profile/consent version. Flow association is per turn; queueing does not freeze a right to run stale work. At admission and before mutation, revalidate the current Flow/spec/criteria and mutable Flow status. A reviewed/terminal Flow cannot silently receive another mutating turn; require a new valid managed association or a separately explicit locally permitted ad-hoc operation. Flow-free work is never labeled a Flow task or accepted Evidence.

`ResultUpload` always names sessionId/turnId and exact per-turn association. Managed results use the existing pinned Flow/Code Revision/Evidence transaction and cannot fabricate accepted checks. Ad-hoc results atomically create a Code Revision plus honestly labeled RunChecks/receipt only: `checksKind=RunChecks`, `flowId=null`, `evidenceId=null`; never FlowEvidence. `ResultReceipt` carries this distinction. Enforce it semantically: managed FlowEvidence requires the exact non-null stored Flow/evidence IDs; RunChecks requires both null. Receipt fields are assigned by Hub from the transaction, never accepted as caller assertions. Actual check exit/output provenance, revision path/content/symlink/mode/size restrictions, partial-result handling, no automatic checkout apply/commit/push/merge and explicit human acceptance remain unchanged. Continuation snapshots the resulting owned workspace baseline separately from Flow acceptance; success of a turn never asserts acceptance of the whole Flow.
