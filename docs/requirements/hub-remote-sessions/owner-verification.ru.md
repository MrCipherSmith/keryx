## 3. Подключение машин (AC1, AC2, AC15)

На каждой машине:

1. В Hub откройте «Машины» и создайте подключение для тестового проекта. Код одноразовый и живёт 10 минут.
2. На машине:

   ```sh
   export KERYX_PAIR_CODE='<код из Hub>'
   keryx hub machine pair --url <hub-url> --code-env KERYX_PAIR_CODE
   unset KERYX_PAIR_CODE
   keryx hub machine allow --project <project-id> --checkout <checkout-id> --path /abs/checkout --profile remote-restricted
   keryx hub machine configure --candidate current --ad-hoc allow --max-runs 1
   keryx serve
   ```

Проверьте:

- [ ] В Hub машина в статусе online. Видны checkout, его HEAD и признак clean, профиль ready.
- [ ] Повторный `pair` с тем же кодом отклоняется (код одноразовый).
- [ ] Вендоры без адаптера и недостающая локальная настройка видны с причиной и не выбираются.
- [ ] После перезапуска `keryx serve` машина возвращается сама. Секреты лежат вне репозитория в owner-only файлах.
- [ ] Из Hub нельзя ослабить локальную политику: профиль, лимит ходов и ad-hoc задаются только на машине.

## 5. Падение и восстановление (AC4, AC8, AC22)

1. Начните ход на машине A и в середине убейте serve: `kill -9 <pid serve>`.
2. В Hub ход остаётся последним известным, не закрытым и не освобождённым. После перезапуска serve пишет `machine-busy`, это ожидаемо.
3. Выполните по [recovery-runbook](recovery-runbook.md#after-a-serve-crash):

   ```sh
   keryx hub machine recover --hub <hub-id> --action release-stale-daemon
   # при необходимости удалить устаревший owner-control.sock (см. runbook), затем снова keryx serve
   keryx hub machine recover --hub <hub-id> --action confirm-run-absence --run <runId> --request-id <новый-id>
   ```

4. Пока живы процессы хода, `confirm-run-absence` отказывает с `owned-process-live`. После него Hub показывает ход как unknown.
5. В Hub человек разрешает ход как `lost`. На это даётся 30 секунд, иначе повторите шаг с новым request id.
6. Снимите локальные заборы:

   ```sh
   keryx hub machine recover --hub <hub-id> --action release-resolved-run --run <runId> --reconciliation <reconciliationId> --request-id <новый-id>
   ```

7. Посмотрите `keryx hub machine recover --hub <hub-id>`. Если в `unresolved` осталась команда с `runId: null` (serve упал, пока применял сообщение в очередь, захват или продление контроллера, смену настроек или очереди), сессию на этом checkout вернуть нельзя: продление или resume отказывают, в диагностике ledger видно `rehost-uncertain-local-work`. Закройте эту команду явно, по [runbook, шаг 5](recovery-runbook.md#5-settle-a-session-command-the-crash-left-unresolved):

   ```sh
   keryx hub machine recover --hub <hub-id> --action settle-crashed-command --command <commandId> --request-id <новый-id>
   ```

   Ответ — одна строка JSON с `outcome` и `resubmit`:
   - `applied`, `resubmit: "no"` — ledger упавшего serve записал эффект команды, и Hub его принял. Повторять не нужно: сообщение из очереди после `lost` вернётся как `suspended`, его переподтверждают или удаляют как обычно.
   - `not-applied`, `resubmit: "yes"` — команда не начиналась или хост записал отказ. Отправьте её заново.
   - `unknown`, `resubmit: "if-absent"` — эффект установить нельзя. Сначала верните сессию, и только если эффекта нет, отправьте команду заново.

   Пока живы процессы упавшего serve, команда отказывает с `owned-process-live`; для команды, которую держит сам работающий serve, — `daemon-live`. Повтор с тем же request id возвращает тот же ответ, с тем же id и другой командой — `payload-conflict`.

8. Возобновите сессию из веба (Resume или `/sessions resume`).

Проверьте:

- [ ] Новый ход проходит. История и файлы checkout сохранены, git status не изменился без вашего участия.
- [ ] Сообщение, стоявшее в очереди до падения, до модели не дошло.
- [ ] Claim или resume до шага 6 сразу отказывает с понятным кодом и не вешает сессию на 60 секунд.
- [ ] Если упасть, пока serve ставит сообщение в очередь (сообщение уже видно в очереди Hub), шаг 7 нужен: до него продление отказывает, после `settle-crashed-command` с `outcome: "applied"` сессия возвращается и сообщение в очереди стоит `suspended`.
- [ ] Если ответ `outcome: "unknown"` (Hub не получил записи об эффекте команды), Hub держит сессию занятой (`session-busy`): снять это человеку в Hub пока нечем. Отметьте такой случай отдельно.
- [ ] Машина B не затронута.
- [ ] Перезапуск Hub при работающих машинах проходит без повторной работы и перехвата управления; отмена и Allow once после этого применяются ровно один раз.

## 6. Инвентарь и общий контекст (AC2, AC10)

- [ ] Закоммитьте в checkout машины A, не останавливая serve. Не больше чем через 10–15 секунд Hub показывает новый HEAD, и новая сессия на нём запускается.
- [ ] Сделайте незакоммиченную правку. Hub показывает checkout «грязным», новая сессия на нём отклоняется с `checkout-dirty`. Уже идущая сессия свои правки продолжает.
- [ ] Измените вики-документ проекта в Hub. Машина получает его без 15-секундного опроса, `hub_context` в сессии видит новую ревизию. После переподключения ревизия не откатывается.
- [ ] Отслеживаемый `.metaproject/index.md` в checkout машины после синхронизации не меняется.

## 10. Что записать и куда вернуть

По каждому пункту запишите:

- результат: прошло, не прошло или не проверялось;
- коммит кандидата и версию Bun;
- id квитанций, сессий и ходов;
- короткое описание и скриншоты, где это полезно.

Не включайте токены, cookie, заголовки Authorization и коды подключения.

Пришлите результаты агенту. По ним он:

1. Оформит Evidence для 24 критериев. Без живой проверки критерий остаётся pending.
2. Исправит найденное в ветке и снова прогонит CI в PR.
3. Подготовит Code Revision только для ревью и отправит её вам на ревью (S8). Для записи в Hub агенту нужен ваш токен с правом записи; без него этот шаг остаётся за вами.

Агент не принимает Flow, не публикует npm и не разворачивает Hub.

## 11. Принятые решения, которые видны при проверке

- Варианты Jev без локальной настройки, `queue force`, `triggers run`, `guard` details и `ci.detail` — явные границы (spec 3.1). Они честно отвечают «не поддерживается», а не изображают успех.
- Забор not-applied с recovery-required держится, пока его не снимет человек; по таймеру он не истекает.
- Длинный `/help` обрезается по байтам, без маркера обрезки.
- Команда, результат которой не прошёл схему, отчитывается как rejected, и в причине сказано, что изменение видно в состоянии сессии.
- Грязный checkout виден как ready-but-dirty; новые сессии на нём отклоняются.
- `settle-crashed-command` с исходом unknown снимает локальный забор и предлагает переотправить команду, если её не видно в сессии.
- Известное ограничение этого Flow. Если serve упал посреди команды, которую Hub так и не увидел применённой, Hub держит сессию в pending (`session-busy`). Ни одно сообщение замороженного протокола не снимает это честно. Маршрут, по которому человек разрешает такую команду, вынесен в следующий Flow со своим решением по спецификации.
