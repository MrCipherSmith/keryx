## Проблема

Чтобы узнать о новом тикете на себя, запросе ревью, упавшем CI или комментарии в своём PR, оператор сам открывает GitHub. Флоу C присылает сводку по расписанию, но сводка только сообщает: действовать приходится вручную, и между «увидел» и «взял в работу» нет ни следа, ни кнопки.

## Цель

Агент по расписанию замечает события и на каждое присылает в Telegram одну карточку: что произошло, ссылка, короткая оценка, предложение действия. Под карточкой кнопки. Нажатие «Взять в работу» запускает обычный цикл keryx: `flow init --issue <url>`, дальше PRD и AC оператору до заморозки. Любое решение по карточке записывается с автором и временем. Без человека агент только наблюдает и предлагает.

## Не цели

- Любая запись в GitHub от имени оператора: комментарии, метки, ревью, merge.
- Автоматический `flow init`, push, PR без нажатия кнопки или подтверждения в топике.
- Второй планировщик: опрос — ещё один trigger на машине flow 295/389.
- GitHub Action и вебхук: отдельный флоу D2 после недели опроса (решение 3).
- Установка чего-либо в рабочие репозитории: для них только опрос.
- Живые запуски внешних агентов (правило 1): тесты на фейках.

## Решения оператора

Приняты 2026-10-04 в опросе 84 (все пять ответов: рекомендованный вариант). PRD и AC согласованы целиком.

1. **Куда слать карточки.** Отдельный служебный топик «Intake». Цена: hub сейчас отбрасывает нажатия из топиков без сессии как `update-unrouted`, нужен новый маршрут callback для служебного топика (AC18).
2. **Порядок и гейт.** Заморозить D после подтверждения PRD и AC и начинать, не дожидаясь закрытия флоу 389: зависимость только кодовая.
3. **GitHub Action и вебхук.** Не входят в D. Выносятся в отдельный флоу D2 после недели работы опроса и замера задержки. D2 сейчас не создаётся, отложено записью в журнале D.
4. **Журнал решений.** Собственный реестр intake: предложение, выбор, время ответа, автор; формат экспорта совместим с `keryx decisions export`, без текстов. Плечи F2 в первой версии не применяются.

## Что делается

1. **Опрос.** Новый trigger на механике флоу 295/389. Собирает через те же granted gh-tools (фиксированный argv, только чтение, список репозиториев в конфиге) события пяти видов: новый тикет на оператора, запрос ревью, упавший CI на его PR, комментарий в его PR, движение на доске (product index, не HTML). В каталог добавляются два чтения: тикеты, назначенные на оператора, и комментарии в его PR. Аккаунт GitHub выбирается по пути проекта, `gh auth switch/login` не вызывается никогда.
2. **Личность события.** Ключ события: `issue:<repo>#<n>`, `review:<repo>#<n>`, `ci:<repo>:<runId>`, `comment:<repo>#<n>:<commentId>`, `board:<id>`. Одно событие — одна карточка: повторный опрос и перезапуск serve дубль не дают; изменение `updatedAt` у уже показанного тикета новую карточку не создаёт.
3. **Оценка и предложение.** На каждое новое событие один вызов модели без инструментов. Вход: вид, заголовок и тело, обрезанные и прогнанные через редактор секретов `src/security`. Выход: оценка до 400 символов и предложение из закрытого набора для этого вида карточки. Текст тикета — недоверенные данные: модель не добавляет кнопок и ссылок, предложение вне набора отбрасывается. Если модель недоступна или ответила мусором, карточка уходит без предложения («оценка недоступна»), а не задерживается.
4. **Карточка.** Telegram HTML с экранированием: вид, репозиторий, заголовок, ссылка, оценка, предложение. Кнопки:
   - тикет: «Взять в работу» / «Отклонить» / «Позже»;
   - запрос ревью: «Открыть ревью-flow» / «Пропустить»;
   - упавший CI: «Разобрать» / «Игнорировать»;
   - комментарий и доска: «Понятно».
   `callback_data` содержит только короткий id карточки и код действия (не длиннее 64 байт), никаких URL и заголовков. Что именно выполнить, берётся из реестра карточек, не из данных нажатия.
5. **Действия.**
   - «Взять в работу»: serve запускает `keryx flow init --issue <url из реестра>` в корне проекта, сопоставленного репозиторию через пользовательский реестр проектов. Flow встаёт в `initializing`, AC не заморожены, дальше обычный цикл: PRD и AC оператору до freeze. Push, PR и merge — только по подтверждению.
   - «Открыть ревью-flow»: flow `Review <repo>#<n>` со ссылкой на PR в описании, без записи в GitHub; ревью-комментарии остаются отдельным решением.
   - «Разобрать»: советующий `keryx review ci-triage` по упавшему запуску под лимитом бюджета; результат (обрезанный, с редакцией секретов) приходит в топик. Ничего не создаётся и не пишется в GitHub.
   - «Отклонить», «Пропустить», «Игнорировать», «Позже», «Понятно»: только запись решения.
   После решения карточка правится на месте («✅ взято 10:42, flow 412»).
6. **Защиты нажатия.** Повторное нажатие и нажатие после истечения ничего не делают и отвечают коротким текстом. Параллельные нажатия исполняются один раз (блокировка файла реестра, состояние `taking` → `taken`). Нажатие от id вне allowlist и нажатие с чужого чата или сообщения игнорируются и журналируются с id и временем, без текста. Перезапуск serve между приёмом нажатия и завершением действия не создаёт второй flow.
7. **Реестр решений.** `.metaproject/data/intake/ledger.jsonl`, дозапись. В записи: id карточки, ключ события, вид, предложение, выбор, `decidedBy` (id пользователя Telegram или `tui`), `decidedAt`, `timeToAnswerMs`, id созданного flow. В журнал созданного flow добавляется строка с `decided-by`, временем, id карточки и предложением. Отчёт `keryx intake report --json` и экспорт без текстов.
8. **Маршрут в hub.** Нажатия из служебного топика уходят в обработчик intake, нажатия в топиках сессий не затронуты (кнопки согласования работают как раньше).
9. **Лимиты и отказы.** Тихие часы, лимит карточек в час, бюджет и таймаут запуска. Сбой `gh`, модели или доставки — запись в отчёт запуска и строка статуса в топике; остальные источники продолжают работать, недоставленное повторяется с нарастающей задержкой.
10. **TUI.** Для каждой функции есть поверхность (правило оператора 2026-09-23). Детали в AC19.
11. **Документация.** Руководство intake (настройка, тихие часы, лимиты, гарантия «только чтение без человека», второй этап), README, cli-reference, wiki, commands-by-task, сайт документации, CHANGELOG.
