# PRD · Review v3
Version: 0.1.0

## Проблема

Владелец 2026-11-25 запустил ручные ревью Desktop на трёх PR репозитория Presight-AI/vantage-frontend (9249, 9320, 9264). За десять попыток ни одна не дошла до ревьюеров: у каждой `rounds: 0`, `reviewers: []`, 0,5–0,7 млн токенов координатора, итог `partial` или `blocked`. Источник — локальное хранилище `~/.local/share/keryx/desktop-review/runs.sqlite` и `attempts/<id>/run/{summary.json,child.log,progress.json}`.

1. **Продолжение начинает с нуля.** Каждое «Continue» запускало новый отсоединённый `keryx shell --no-tui --print` в новой копии репозитория для попытки. `plan.json` и `slices/manifest.json` прошлого пакета там отсутствовали (ENOENT), и координатор сам писал, что Desktop должен восстановить исходный пакет.
2. **Разрешение некому дать.** `shell_exec` упёрся в порог разрешений, который в отсоединённом процессе никто не может подтвердить; попытка стала `blocked`.
3. **Ошибка провайдера превращается в холодный перезапуск.** На ответ OpenAI 403 пользователь нажимал «Continue», и это был ещё один запуск с нуля.
4. **Вопросы пользователя остаются без ответа.** Текст «что это значит?» уходил в поле `guidance` нового процесса; ответа никто не давал.
5. **Сессия не та.** Сессия ACP, созданная при старте, только владеет попыткой (`DeskRun.sessionId`). Сообщение в неё получает агент, который ревью не ведёт.
6. **Статусы не сходятся.** Слот на доске, вкладка Reviews, карточка в сессии и запись попытки используют четыре разных словаря состояний; «in progress» не говорит, что происходит.

Тот же скилл `review-orchestrator` внутри `keryx shell` или Claude работает хорошо, потому что сессия живая.

## Цель

Ручное ревью PR из Desktop — это живая сессия агента на каждый раунд с понятной карточкой. Пользователь видит, что делает ревью сейчас, разговаривает с ним в той же сессии, продолжает с того места, где оно остановилось, и не теряет пакет раунда.

## Кто пользуется

| Пользователь | Сценарий |
|---|---|
| Ревьюер | Запускает ревью PR с доски, видит план и ревьюеров, отвечает на вопрос агента в сессии, публикует результат |
| Ревьюер после сбоя | Ошибка провайдера или закрытое приложение: продолжает тот же раунд, агент берёт пакет из постоянного места |
| Автор PR | Получает новый раунд после своего коммита; прошлые находки перенесены или перепроверены |
| Ответственный за проект | Во вкладке Reviews видит один статус на ревью, один словарь везде |

## Требования

**R1. Ревью — сессия.** «Запустить ревью» на доске Pull requests, во вкладке Reviews и в диалоге `/review` открывает сессию, привязанную к PR (существующую или новую с привязкой `subject`), и отправляет в неё ход ревью. Отсоединённого процесса для ручного ревью нет.
Verification: judged

**R2. Продолжение — ход.** «Продолжить» отправляет ход в сессию текущего раунда с текстом пользователя. Новая попытка, новый процесс и новая копия репозитория не создаются.
Verification: judged

**R3. Состояние в `review.json`.** У каждого ревью PR есть один `review.json` в постоянном месте проекта и журнал рядом. Пакет раунда лежит в проекте, а не во временной копии.
Verification: judged

**R4. Пишет только CLI.** `review.json` меняется только командами `keryx review state …`. Скилл `review-orchestrator` вызывает их на каждом шаге раунда. Desktop файл не пишет.
Verification: judged

**R5. Раунды.** Новый раунд открывается только при новом head PR или изменённых настройках ревью. Перезапуск на том же head после сбоя сессии остаётся в том же раунде, открывает новую сессию и берёт пакет из постоянного места.
Verification: judged

**R6. Один словарь статусов.** Статус ревью вычисляется из `review.json` и состояния сессии раунда (ход идёт, ждёт ответа или разрешения, простаивает) и одинаков в слоте доски, вкладке Reviews и карточке.
Verification: judged

**R7. Полезная карточка.** Карточка показывает PR, проверенный коммит и отставание от head; статус; план текущего раунда (срезы, волны, назначения сделано/всего); ревьюеров (идут/готовы); токены и стоимость по раундам и всего; находки по мере появления по тяжести, с пометкой «перенесена» или «перепроверена»; список раундов с коммитом, вердиктом и ссылкой «открыть сессию»; действия «Продолжить», «Новый раунд», «Опубликовать», «Исправить находки».
Verification: judged

**R8. Старые данные видны.** Review, раунды и попытки v2 из `runs.sqlite` продолжают отображаться; на этапе 2 они переносятся в `review.json`.
Verification: judged

**R9. Нет отсоединённого пути для ручных ревью.** Удаляются `desk-run worker` и `runAutonomousReview` для ручных ревью, мост вопросов через SQLite, продолжение как новая попытка и копия репозитория на попытку. Фоновый исполнитель остаётся только для ревью по расписанию и пишет тот же `review.json`.
Verification: judged

**R10. Публикация как сейчас.** «Опубликовать» использует существующий `keryx review publish` и защиту публикации (`publish-guard.ts`); запись о публикации попадает в `review.json`.
Verification: judged

## Критерии выпуска

- На PR без ревью: «Запустить ревью» открывает сессию, привязанную к PR, отправляет ход ревью; через минуту в проекте есть `review.json` с раундом 1 и пакетом раунда; в списке процессов нет `keryx shell --no-tui --print`.
- Агент задаёт вопрос: он виден в сессии, ответ пользователя — следующий ход той же сессии, ревью продолжается.
- Закрыть приложение посреди раунда, открыть снова, нажать «Продолжить»: тот же раунд, пакет на месте, ревьюеры не перезапускаются с нуля.
- Новый коммит в PR: «Новый раунд» открывает раунд 2 в новой сессии с прошлыми находками.
- Статус ревью одинаков в слоте доски, во вкладке Reviews и в карточке.

## Критерии пользы

- **Ревью доходит до ревьюеров.** За первую неделю владелец на своих PR считает долю ручных ревью, у которых есть хотя бы одна волна ревьюеров. Источник — `review.json` (`rounds[].reviewers`). Ожидается не меньше 9 из 10 (сегодня 0 из 10).
- **Продолжение не стоит заново.** Токены координатора на продолжение раунда — порядка одного хода, а не 0,5 млн. Источник — `rounds[].usage` до и после продолжения.

## Риски

- **Сессия занята пользователем.** Ход ревью нельзя отправить, пока в сессии идёт другой ход. Desktop говорит об этом и не ставит ход в очередь молча.
- **Скилл не записал состояние.** Если агент пропустил вызов CLI, `review.json` отстаёт от сессии. Живой статус сессии остаётся верным; карточка показывает время последней записи.
- **Два аккаунта.** Ключ ревью включает аккаунт ревьюера (D3 v2); сессия без известного аккаунта получает ревью без аккаунта в ключе.
- **Миграция истории.** Перенос из `runs.sqlite` проверяется на копии рабочей базы до включения (этап 2).
