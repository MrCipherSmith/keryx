# План реализации · Review v3
Version: 0.1.0

Статус: этап 1 реализован в Flow 524 (`.metaproject/flows/524-2026-11-25-desktop-review-v3-live-review-session-pe/`) и влит в `main` через PR #1317 (merge-коммит `a37b779d1`, CI на head `fd2e7e0aa` зелёный); этапы 2–4 не начаты. Номера требований — из [PRD](prd.md), разделы — из [спецификации](specification.md). Каждый этап выпускается отдельно и не ломает данные v2.

## Этапы

| Этап | Что делается | Требования | Что показать на выходе |
|---|---|---|---|
| 1. Живая сессия | Хранилище `review.json`, журнал и CLI `keryx review state`. Раздел «Desktop review state» в `review-orchestrator`. «Run review» на доске и во вкладке Reviews и диалог `/review` открывают привязанную к PR сессию (или новую с `subject`) и отправляют ход ревью; отсоединённый исполнитель для них не запускается. «Continue review» — ход в ту же сессию. Данные v2 только читаются | R1, R2, R3, R4, R5, часть R8 | «Run review» на PR → ход в привязанной сессии → `review.json` с раундом 1 и пакетом в проекте; «Continue» — ход в ту же сессию |
| 2. Карточка и статус | Desktop читает `review.json` (расширение ACP `_keryx/review_state` или поле в `keryx review reviews`, без новой Rust-команды). Единый `ReviewStatus` в слоте доски, вкладке Reviews и карточке. Карточка из спецификации. `keryx review state import` переносит v2 | R6, R7, R8 | Один PR с историей v2 и новым раундом v3 — одна карточка, один статус везде |

| 4. Удаление отсоединённого пути | Удалить для ручных ревью `desk-run worker`, `runAutonomousReview`, мост вопросов через SQLite, продолжение как новую попытку, копию репозитория на попытку. Исполнитель по расписанию пишет `review.json` | R9 | В коде нет пути, запускающего `keryx shell --no-tui --print` для ручного ревью |

## Состояние этапа 1

Реализован в Flow 524 и влит в `main` через PR #1317 (merge-коммит `a37b779d1`). Flow 524 — `implemented`: `flow complete` отказывает по гейтам owner, health и review (раунды ревью шли субагентами, а не пакетами `keryx review`), решение за оператором. Сделано: хранилище `review.json` и `journal.md` (`src/review/review-state.ts`), CLI `keryx review state open|round|publish|mark|note|show|list`, раздел «Desktop review state» в обеих копиях `review-orchestrator`; «Run review» на доске, во вкладке Reviews и в диалоге `/review` отправляет ход ревью в привязанную к PR сессию, «Continue review» — ход в ту же сессию (для попытки v2 без `review.json` ход называет попытку, её диапазон и команду `state open`). Ревью: два раунда; после первого исправлены три major (совпадение id у разных PR, переход `paused → ready`, продолжение попытки v2), второй раунд — без blocker и major. Двенадцать minor отложены и перечислены в `journal.md` Flow 524.

Что не проверено:

- В собранном приложении и на реальном PR не запускалось: ни одна живая сессия ещё не провела скилл до записи `review.json`; CLI проверен пробой во временном проекте.
- Слот ревью на доске после «Run review» обновляется при следующем чтении доски, а не сразу: попытки нет, пока скилл не зарегистрирует пакет.
- Запуск из вкладки Reviews идёт тем же путём `boardReviewRun`, но App-фикстурой не прогоняется.
- Rust-часть Desktop не менялась; тесты — в CI.

## Решения владельца

| № | Вопрос | Решение |
|---|---|---|
| V1 | Сколько карточек у ревью PR | Одна: один Review на PR (и аккаунт, D3 v2), одно состояние `review.json`, как `flow.json` у Flow |
| V2 | Кто пишет состояние | Только CLI `keryx review …`, который вызывает скилл `review-orchestrator` на каждом шаге, как flow-orchestrator вызывает `keryx flow`. Desktop только читает. Рядом — журнал, как `journal.md` Flow |
| V3 | Где живёт пакет раунда | В постоянном месте проекта, никогда во временной копии попытки. Пакет остаётся в `.metaproject/reviews/<package-id>/`, раунд хранит путь к нему (решение исполнителя в рамках V3: перенос под `rounds/rNN/` сломал бы поиск прошлого раунда и гейты — см. спецификацию, «Хранение») |
| V4 | Что такое раунд | Одна сессия на раунд; продолжение внутри раунда — ход в той же сессии, не новая попытка и не новый процесс. Новый раунд — новая сессия и `keryx review advance`, прошлые находки — через пакет |
| V5 | Когда растёт номер раунда | Только при новом head или изменённых настройках ревью. Перезапуск на том же head после сбоя сессии — тот же раунд, новая сессия, пакет из постоянного места |
| V6 | Откуда живой статус | Из сессии раунда (`SessionMark`: busy, waiting, subagents): идёт ход — «работает», ждёт вопрос или разрешение — «ждёт вас», сессия свободна при открытом пакете — «пауза». Вместе с `review.json` — один словарь везде |
| V7 | Что на карточке | Заголовок, статус, план раунда, ревьюеры, токены и стоимость, находки по тяжести с пометкой «перенесена»/«перепроверена», список раундов со ссылкой на сессию, действия «Продолжить», «Новый раунд», «Опубликовать», «Исправить находки» |
| V8 | Что удалить | Для ручных ревью Desktop: `desk-run worker` и `runAutonomousReview`, мост вопросов через SQLite, продолжение как новую попытку, копию репозитория на попытку. Фоновый исполнитель — только для ревью по расписанию, он пишет тот же `review.json` |

Решения V1–V2 и V4–V8 приняты владельцем и координирующей сессией 2026-11-25 по доказательствам из локального хранилища ревью. В V3 владелец задал принцип («постоянное место, не временная копия»); раскладка каталога — решение исполнителя, его нужно подтвердить на ревью этапа 1.

Решения исполнителя этапа 1 (подтверждаются на ревью PR):

- Ход ревью — текст, называющий скилл, а не `/review`: в shell ACP `/review` — представление «что ждёт ревью», а не скилл (спецификация, B8).
- `review.json` лежит в `.metaproject/reviews/pr/<review-id>/`: каталог без `manifest.json`, сканеры пакетов его пропускают.
- Неизвестный ключ настроек (`null`) совпадает с любым: ход из сессии агента без Desktop не знает ключа и не должен открывать лишний раунд.
- Занятая сессия: ход не отправляется и не ставится в очередь.

## Что v3 заменяет в плане v2

| В v2 | В v3 |
|---|---|
| Attempt — единица запуска и продолжения (`DeskRun`, «повтор и `continue` — новые Attempt того же Round») | Ход в сессии раунда; Attempt только для старых данных и расписания до этапа 4 |
| Состояние Review выводится из последней попытки (`queued`, `running`, `needs_answer`, `stopped`, `ready`, `published`, `closed`) | Состояние хранится в `review.json` (`draft`…`closed`) и вместе с сессией даёт `ReviewStatus` |
| Хранение: `runs.sqlite` (`reviews`, `runs.review_id`, `round`) | `review.json` + `journal.md` в проекте; `runs.sqlite` — только чтение, перенос на этапе 2 |
| «Единый реестр»: пакет сессии копируется в попытку `session` | Пакет остаётся на месте, раунд ссылается на него; регистрация как попытки остаётся до этапа 4 для совместимости публикации |
| Ответ на вопрос ревьюера — `review_run answer` через SQLite | Ответ — ход в сессии (`ask_user` сессии) |
| «Продолжить» с `guidance` — новая попытка | «Продолжить» — ход в сессию раунда |
| Отсоединённый исполнитель в копии репозитория для ручных ревью | Только для ревью по расписанию (этап 4) |

Остаются без изменений: вкладки Pull requests и Issues, строка работы Keryx, привязка сессий к PR (`subject`), правила смены head (`keryx review advance`, режимы `delta`/`fallback-first`, D1, D2), ключ Review с аккаунтом (D3), общий код публикации и `publish-guard`, действие «Исправить находки» (Flow 522).

## Зависимости

- Этап 2 требует этапа 1: карточка читает `review.json`.
- Этап 3 требует этапа 2: «Новый раунд» и публикация — действия карточки.
- Этап 4 требует этапов 1–3: удалять отсоединённый путь можно, когда все действия ручного ревью идут через сессию.
