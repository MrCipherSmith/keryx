Три отклонения от PRD сделаны сознательно и записаны здесь:

- (a) R12 говорит, что индикатор вкладки Pull requests загорается для запроса ревью на пользователя «или его команду». На этапе 0 сопоставляется только логин пользователя; запросы на команды не сопоставляются, пока не появится членство в командах (планируется вместе с этапом 1).
- (b) До появления вкладки Reviews (этап 2) индикатор вкладки Pull requests загорается также от локального ревью, которое ждёт пользователя (вопрос ревьюера или решение о публикации). Закрыто этапом 2: локальное ревью больше не зажигает этот индикатор.
- (c) Панель инструментов доски не гарантированно остаётся в одну строку, и меню для второстепенных элементов нет. Вместо этого подписи кнопок скрываются, когда внутренняя ширина панели (без отступов) не больше 1100px — это панель шириной около 1140px; текст состояния вотчера скрывается при внутренней ширине не больше 760px — панель около 800px, а счётчик pull request'ов остаётся голым числом, и поле поиска сужается до 80px; счётчик активных фильтров остаётся видимым. Измерено на разметке панели с реальными стилями и заглушками вместо данных: одна строка без выхода за край при ширине панели 560, 620, 700, 760, 820, 1101, 1180 и 1380px; при 340px — две строки. Когда показана подсказка о скрытых фильтрами запросах (d) («Show N waiting on you», уже 1100px — «N hidden»), панель переходит на вторую строку при ширине 340–646, 810–908 и 1150–1290px, то есть и при панели 560px в окне по умолчанию с открытой панелью PR; ничего не обрезается. В приложении с реальными данными не измерялось.
- (d) Решения оператора от 2026-11-23: кнопка на карточке с устаревшим ревью называется «Review again», пока этап 2 не свяжет раунды между собой (на этапе 2 подпись — «New review round»); индикатор вкладки считает каждый pull request, которому нужен пользователь, а если часть из них скрыта фильтрами, на панели инструментов показывается подсказка с числом скрытых и кнопкой, которая сбрасывает фильтры и поиск.

Решение оператора от 2026-11-23: закрытый или слитый pull request с идущим ревью скрывается при фильтре по умолчанию «Open + Draft».

## Состояние этапа 1

Этап 1 реализован в Flow 517 (`.metaproject/flows/517-2026-11-23-desktop-review-v2-stage-1-github-slice-a/`) и влит в main через PR #1300 (merge-коммит `2f3cd17ee`; CI на head `6449683d1` зелёный). Ревью: четыре раунда по PR, после каждого — раунд исправлений; пакеты — `.metaproject/reviews/2026-11-2*-review-flow-*-pull-1300*`, журнал — `journal.md` Flow 517. Критерии AC1–AC19 подтверждены на влитом main.

- **Pull requests.** Колонки и порядок только по GitHub: группировка «Status» (Draft · Waiting for review · Changes requested · Approved, Merged и Closed — по фильтру состояния) и «My role» (Requested from me · Mine · Others). Быстрые фильтры «Requested from me», «Mine», «CI failed» и переключатель группировки стоят в строке контекста, не в тулбаре, поэтому замеры отклонения (c) остаются в силе. Колонка внимания и колонка «In review» убраны (D6). Строка причины на карточке — только по GitHub.
- **Строка работы Keryx** (`apps/desktop/src/review/PrWorkRow.tsx`): три места фиксированной высоты 24px — ревью («Review · <состояние>» из `localReview`, без раунда и отставания; открывает текущую панель ревью), Flow (по `prUrl` или через флаг `flow` привязанной сессии), сессии (число, последняя, меню со всеми и «New session»). Пустое место — подписанное действие. «Fix review comments» не показывается (этап 4).
- **Привязка сессии к Subject.** `subject` хранится в `flags.json` сессии и пишется через `_keryx/session_flags` (`src/session/organize.ts`); сессия Issue получает `subject` при привязке в `withIssueBinding`. keryx сохраняет новую сессию только после её первого хода, поэтому Desktop держит привязку в ожидании и повторяет запись после хода. Старый keryx без поддержки `subject`: сессия открывается и работает, а уведомление, что привязка не сохранена, появляется в ней не позже конца первого хода. Запись `flags.json` идёт под блокировкой `flags.json.lock` на сессию: параллельный писатель ждёт; блокировка старше 2 секунд считается брошенной и перехватывается; если взять блокировку за 3 секунды не удалось, запрос получает ошибку «retry». Сервер ACP ждёт асинхронно, не останавливает другие сессии и применяет записи одной сессии в порядке поступления. Блокировка не создаёт папку сессии: запись в сессию, которую уже убрали в корзину, получает «no session» и папку не возвращает. Сессии Issue, привязанные старым keryx без `subject`, получают его при следующем открытии через Issues, если пользователь не снял привязку сам (снятие хранится отметкой; снятие, сделанное до этой версии, отметки не имеет и может быть перезаписано один раз). После первой привязки эта запись необязательна: если она не удалась, задача всё равно открывается. Заголовок сессии показывает ссылку на PR или Issue и на Flow.
- **Создание из сессии.** `/review` без цели в сессии, привязанной к PR, открывает диалог запуска с этим PR. «Create Flow» открывает привязанную сессию с подготовленным текстом (не отправляет его). Запрос ждёт пакет 15 минут с нажатия и регистрируется, только если текст действительно подставлен в эту сессию (переключение на другую сессию во время открытия — ни текста, ни запроса). Если ждёт ровно один запрос и появился ровно один новый пакет, строка работы PR спрашивает «Link Flow #N · <название>?» с кнопками Link и Dismiss: флаг `flow` сессии пишется только по Link, вопрос остаётся, пока запись не удалась (причина показывается, Link можно нажать снова, сам после хода запись не повторяется); Dismiss ничего не пишет и больше не предлагает этот пакет. Показанный вопрос не истекает. Несколько новых пакетов или несколько ждущих запросов — не предлагается ничего, и все ждущие запросы завершаются; если списка Flow ещё не было — тоже.
- **Issues.** По умолчанию колонки по состоянию GitHub (Open · Closed по фильтру), источник по умолчанию — репозиторий проекта (`keryx issues list` с `source: "repository"`, D5; запрос читает до трёх страниц, если на странице одни pull request'ы); сохранённый выбор источника важнее; группировка по статусу GitHub Project не изменилась; фильтр по стадии Flow убран, стадия — ссылка в строке работы (слоты Flow и сессии). Если источник «репозиторий проекта» недоступен (нет удалённого репозитория GitHub.com, удалённый репозиторий не называет годного репозитория, Issues выключены в репозитории — ответ 410, или keryx старше Desktop не знает источник), Issues показывают причину и кнопку «Show issues assigned to me»; для старого keryx — ещё подсказку обновить keryx или выбрать Bundled keryx в настройках. Это не зависит от того, выбран ли источник явно; любая другая ошибка показывается с Retry. Выбор источника хранится для проекта и аккаунта, поэтому кнопка в одном проекте не меняет источник в другом. Заголовочная ссылка на PR, которого нет в загруженном списке (например, его состояние отфильтровано), показывает уведомление и больше не срабатывает сама.

Отклонения и ограничения этапа 1:

- (a) остаётся открытым: членства в командах этап 1 не ввёл, запросы ревью на команды индикатором не сопоставляются.
- (b) остаётся: индикатор Pull requests по-прежнему загорается от локального ревью, ждущего пользователя; снимается на этапе 2.
- (e) У Issue нет выбора другой или новой сессии: бэкенд привязки задачи (`withIssueBinding`) держит одну сессию на задачу и аккаунт. Требование R5 для Issue в части «с выбором другой или новой» не выполнено.
- (f) Flow, созданный вне окна ожидания «Create Flow» (или в другой сессии), к PR не предлагается и не привязывается, пока у него нет `prUrl`. При двух и более ждущих запросах «Create Flow» не предлагается ни один пакет.
- (g) `subject` не называет аккаунт GitHub: сессии Issue, привязанные под разными аккаунтами, считаются вместе. У Issue из GitHub Enterprise (URL не github.com) `subject` нет, и строка работы такие сессии не считает.
- Не проверялось в приложении с реальными данными: строка работы в узких колонках (в очень узкой колонке место Flow обрезает Dismiss, а не налезает на место сессий), положение меню сессий, ширина списка (1000px); ширины из замечаний LY-002, LY-004 и LY-005 в приложении не измерялись.
- (h) keryx до этой версии, переписывая `flags.json`, теряет и `subject`, и отметку о снятии привязки; после этого следующее открытие задачи через Issues может снова привязать снятый `subject` (LG-014).
## Состояние этапа 2

Этап 2 реализован в Flow 519 на ветке `feat/desktop-review-v2-stage2` (Draft PR, не влит). Журнал решений — `.metaproject/flows/519-2026-11-24-desktop-review-v2-stage2/journal.md`.

Что сделано:

- **Хранилище.** Таблица `reviews` с ключом (репозиторий, PR, аккаунт ревьюера без учёта регистра, D3); в `runs` добавлены `review_id`, `round`, `previous_run_id`. Миграция в `src/review/desk-run-store.ts` выполняется при открытии на запись и после каждой новой попытки одним правилом: продолжение попадает в раунд предыдущей попытки; повтор диапазона `base..head` текущего последнего раунда — в этот раунд; иначе — новый раунд. Диапазон, вернувшийся после других (A, B, A), открывает новый раунд, поэтому номера раундов идут по времени (решение оператора D-R1 от 2026-11-24). Запрос, вытесненный из очереди до старта, своего раунда не держит: следующий запрос получает его номер, а в списке Review такой запрос не показывается. Правило трогает только строки без `review_id` и не перенумеровывает раунды: пакет, импортированный позже с более старым `createdAt`, получает следующий номер раунда. Хранилища только для чтения старую базу не мигрируют.
- **CLI.** `keryx review reviews --json [--repo owner/name] [--include-closed]` — список Review с состоянием, freshness, раундами, проверенным диапазоном (`reviewed`), находками последнего проверенного раунда, публикацией и источником. Архивные попытки остаются в раундах с пометкой `archived` и не влияют на состояние; Review, все попытки которого в архиве, показывается с `archived: true`. Карточки PR для Review, закрытых локально, читаются только с `--include-closed` (Desktop передаёт его при «Show closed»; решение оператора от 2026-11-24). Desktop читает список через `review_board` с флагами `reviews_only` и `include_closed`.
- **Вкладка Reviews** (порядок вкладок по D4). Колонки: Выполняется · Ждёт вас · Отстаёт · Опубликовано · Закрыто (только при «Show closed»); есть вид списком. Фильтры: состояние, freshness, источник, поиск по заголовку и номеру, «Show closed». Фильтры по публикации, автору PR, Flow и периоду из спецификации не сделаны. Панель Review показывает раунды и интерфейс ревью, перенесённый из панели PR: история, отчёт, ответ, отмена, продолжение, публикация. Кнопка Review rules перенесена сюда с панели инструментов Pull requests. В панели PR без Review остаются прежние кнопки запуска, с Review — «Open in Reviews».
- **Индикаторы.** У вкладки Reviews свой индикатор: Review ждёт ответа, готов с публикацией в состоянии `pending` или остановлен; Review с непрочитанной карточкой PR зажигает его только ожиданием ответа, архивный — никогда. Индикатор Pull requests больше не зажигается от локального ревью (закрыто отклонение (b)).
- **Не сделано на этапе 2.** Ссылка ревью на карточке PR с состоянием, раундом и отставанием (остаток R4) сюда не вошла: она появится вместе со строкой работы Keryx этапа 1. Данные для неё уже есть — `outdated.round` в бейдже карточки и `keryx review reviews`.

Решения, принятые на этапе:

- Freshness `unknown`, когда head PR неизвестен (карточка не прочитана или PR не найден): карточка показывает «head unknown», Review не попадает в «Отстаёт». Решение оператора от 2026-11-24; отклонение от двух видов freshness в спецификации, спецификация дополнена.
- `budget` с проверенным диапазоном считается `ready` или `published`, а не `stopped`.
- Неудачная или отменённая попытка в раунде, где уже есть завершённая проверенная попытка, не делает Review `stopped`: состояние остаётся `ready` или `published` этой попытки (строка `stopped` спецификации: «и у раунда нет принятых находок»).
- Ответ `review reviews` сохраняет `version: 1`, как у доски; версия протокола не повышалась.

Миграция проверена на копии рабочей базы (`runs.sqlite`, копия не закоммичена): попыток до и после — 17, Review — 13 (равно числу ключей), раундов 1 — 13, раундов 2 — 4; повторное открытие ничего не меняет.

Что не проверено:

- Собранное приложение не запускалось. В браузерной сборке для разработки вкладка Reviews открыта на реальном GitHub (этот репозиторий, копия рабочей базы): список пуст, потому что все Review копии относятся к другому репозиторию; карточки Review с реальными данными не видели. Остальное покрытие — модульные и DOM-тесты.
- Rust-часть (`review_board`, `reviews_only`) проверяется только в CI.
- Панель инструментов Reviews измерялась только в браузерной сборке для разработки, с пустым списком: одна строка без выхода за край при ширине панели 760, 800, 820, 900, 1000, 1100, 1101, 1180 и 1380px; при 700px и уже — две строки (при 340px — три), ничего не обрезается. При 560px (окно по умолчанию с открытой панелью) нужно 648px даже при минимальной ширине всех элементов, поэтому одна строка там невозможна без скрытия элемента.

### Как запускать

### Порядок и параллельность

- Этапы 1 и 2 не зависят друг от друга, их можно вести параллельно. Оба трогают карточку PR (`apps/desktop/src/review/ReviewResults.tsx`, `ReviewBoard.tsx`): этап 1 добавляет строку работы Keryx и ссылку на ревью, этап 2 переносит интерфейс ревью из панели PR и добавляет к ссылке раунд и отставание. При параллельной работе договоритесь, какой Flow владеет этими файлами, или ведите этап 2 после слияния этапа 1.
- Этап 3 начинается только после слияния этапа 2, этап 4 — после этапов 2 и 3.

### С чего начать каждый этап

- **Этап 1.** Сначала прочитать, как сейчас хранится связь Issue ↔ сессия ↔ Flow (при подготовке не читалось, см. «Что не проверено»). Ссылка ревью на карточке строится из `localReview` и открывает текущую панель ревью. Здесь же закрывается отклонение (a): сопоставление запросов ревью на команды пользователя, если появится членство в командах. Колонка внимания убирается по D6, Issues по умолчанию показывают репозиторий проекта по D5.
- **Этап 2.** Начать с миграции запусков (`src/review/desk-run-store.ts`) в раунды и попытки на копии рабочей базы. После появления вкладки Reviews индикатор вкладки Pull requests перестаёт загораться от локального ревью — это снимает отклонение (b). Подпись «Review again» из решения (d) меняется на «New review round» вместе со связью раундов.
- **Этап 3.** Действие «New review round» заменяется раундом обновления того же Review; диалог публикации получает варианты по D1; `on_head_move` по умолчанию `ask` (D2).
- **Этап 4.** Процедура «Head сдвинулся» добавляется в `review-orchestrator`; публикация из Desktop и из сессии использует общий код.

### Что этап 0 оставил в коде и что нельзя сломать

Правило для следующих этапов: любое изменение этой логики сопровождается мутационной проверкой собственных строк, а не только зелёным набором тестов. На этапе 1 колонки перестают зависеть от Keryx, но индикатор остаётся — переносите его вместе с тестами.
- **Устаревший результат на карточке** (`localReview.outdated`, `reviewNote` и `laneReason` в `apps/desktop/src/review/model.ts`). - **Тулбар доски** (`apps/desktop/src/styles/review.css`): контейнерные запросы на 1100 и 760px, подсказка о скрытых запросах, голое число. Замеры — в отклонении (c); при добавлении элементов в тулбар перемеряйте.
