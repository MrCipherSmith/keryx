## Состояние этапа 0

Этап 0 реализован в Flow 516 (ветка `feat/desktop-review-v2-stage0`, PR #1294).

Три отклонения от PRD сделаны сознательно и записаны здесь:

- (a) R12 говорит, что индикатор вкладки Pull requests загорается для запроса ревью на пользователя «или его команду». На этапе 0 сопоставляется только логин пользователя; запросы на команды не сопоставляются, пока не появится членство в командах (планируется вместе с этапом 1).
- (b) До появления вкладки Reviews (этап 2) индикатор вкладки Pull requests загорается также от локального ревью, которое ждёт пользователя (вопрос ревьюера или решение о публикации).
- (c) Панель инструментов доски не гарантированно остаётся в одну строку, и меню для второстепенных элементов нет. Вместо этого подписи кнопок скрываются, когда внутренняя ширина панели (без отступов) не больше 1100px — это панель шириной около 1140px; текст состояния вотчера скрывается при внутренней ширине не больше 760px — панель около 800px, а счётчик pull request'ов остаётся голым числом, и поле поиска сужается до 80px; счётчик активных фильтров остаётся видимым. Измерено на разметке панели с реальными стилями и заглушками вместо данных: одна строка без выхода за край при ширине панели 560, 620, 700, 760, 820, 1101, 1180 и 1380px; при 340px — две строки. Когда показана подсказка о скрытых фильтрами запросах (d), панель переходит на вторую строку при ширине около 560, 820 и 1180px; ничего не обрезается. В приложении с реальными данными не измерялось.
- (d) Решения оператора от 2026-11-23: кнопка на карточке с устаревшим ревью называется «Review again», пока этап 2 не свяжет раунды между собой; индикатор вкладки считает каждый pull request, которому нужен пользователь, а если часть из них скрыта фильтрами, на панели инструментов показывается подсказка с числом скрытых и кнопкой, которая сбрасывает фильтры и поиск.

Решение оператора от 2026-11-23: закрытый или слитый pull request с идущим ревью скрывается при фильтре по умолчанию «Open + Draft».

## Зависимости

- Этап 0 независим и не меняет модель данных.
- Этап 1 не требует этапа 2: ссылка ревью на карточке на этом этапе строится из существующего `localReview` и открывает текущую панель ревью.
- Этап 3 требует этапа 2: раунд обновления принадлежит Review.
- Этап 4 требует этапов 2 и 3: сессия использует ту же команду обновления.

## Проверка

- Этапы 0–1: модульные тесты функций колонки и фильтра (`apps/desktop/src/review/model.test.ts`, `apps/desktop/src/issues`), DOM-тесты доски.
- Этап 2: тест миграции на копии рабочей базы; DOM-тесты вкладки Reviews.
- Этап 3: тесты `prior-round` на частичный прошлый раунд и на смену настроек; сценарий на реальном PR с коммитом во время раунда. Rust-часть Desktop проверяется только в CI.
- Этап 4: сценарий на реальном PR — ревью в сессии, публикация из Desktop.

## Решения владельца

| № | Вопрос | Решение |
|---|---|---|
| D1 | Разрешать ли публикацию «как есть» для прошлого коммита, когда head сдвинулся | Да, только вердикт «Комментарий» и с первой строкой о проверенном коммите |
| D2 | Значение `on_head_move` по умолчанию для ручного ревью | `ask` |
| D3 | Входит ли аккаунт ревьюера в ключ Review | Да: публикация выполняется от аккаунта, два аккаунта — два Review |
| D4 | Порядок вкладок и горячие клавиши после добавления Reviews | Sessions, Flows, Reviews, Pull requests, Issues, Metaproject |
| D5 | Показывать ли во вкладке Issues по умолчанию только репозиторий проекта | Да, источник «Assigned to me» по всем репозиториям оставить выбором |
| D6 | Оставить ли в Pull requests колонку внимания | Нет: её заменяют группировка «Моя роль» и быстрые фильтры |

Все шесть решений приняты владельцем 2026-11-23. PRD и спецификация им соответствуют.
