## Состояние этапа 0

Этап 0 реализован в Flow 516 и влит в main через PR #1294. Ревью: раунд по ветке и пять раундов по PR; после первого раунда ни один не нашёл blocker или major. Пакеты раундов — `.metaproject/reviews/2026-11-23-review-flow-*-pull-1294*`, журнал решений — `.metaproject/flows/516-2026-11-23-desktop-review-v2-stage0/journal.md`.

Три отклонения от PRD сделаны сознательно и записаны здесь:

- (a) R12 говорит, что индикатор вкладки Pull requests загорается для запроса ревью на пользователя «или его команду». На этапе 0 сопоставляется только логин пользователя; запросы на команды не сопоставляются, пока не появится членство в командах (планируется вместе с этапом 1).
- (b) До появления вкладки Reviews (этап 2) индикатор вкладки Pull requests загорается также от локального ревью, которое ждёт пользователя (вопрос ревьюера или решение о публикации).
- (c) Панель инструментов доски не гарантированно остаётся в одну строку, и меню для второстепенных элементов нет. Вместо этого подписи кнопок скрываются, когда внутренняя ширина панели (без отступов) не больше 1100px — это панель шириной около 1140px; текст состояния вотчера скрывается при внутренней ширине не больше 760px — панель около 800px, а счётчик pull request'ов остаётся голым числом, и поле поиска сужается до 80px; счётчик активных фильтров остаётся видимым. Измерено на разметке панели с реальными стилями и заглушками вместо данных: одна строка без выхода за край при ширине панели 560, 620, 700, 760, 820, 1101, 1180 и 1380px; при 340px — две строки. Когда показана подсказка о скрытых фильтрами запросах (d) («Show N waiting on you», уже 1100px — «N hidden»), панель переходит на вторую строку при ширине 340–646, 810–908 и 1150–1290px, то есть и при панели 560px в окне по умолчанию с открытой панелью PR; ничего не обрезается. В приложении с реальными данными не измерялось.
- (d) Решения оператора от 2026-11-23: кнопка на карточке с устаревшим ревью называется «Review again», пока этап 2 не свяжет раунды между собой; индикатор вкладки считает каждый pull request, которому нужен пользователь, а если часть из них скрыта фильтрами, на панели инструментов показывается подсказка с числом скрытых и кнопкой, которая сбрасывает фильтры и поиск.

Решение оператора от 2026-11-23: закрытый или слитый pull request с идущим ревью скрывается при фильтре по умолчанию «Open + Draft».

## Передача следующим этапам

Раздел для агента, который начинает этап 1, 2, 3 или 4. Всё, что ниже названо «сейчас», проверено по коду после слияния этапа 0.

### Как запускать

- Один этап — один Flow через flow-orchestrator (`.metaproject/skills/gdskills/orchestration/flow-orchestrator/SKILL.md`), ветка от свежего `main`, свой PR. Критерии приёмки замораживаются из строки этапа в таблице «Этапы» и из требований PRD, которые она называет.
- Входные документы: [PRD](prd.md) (R1–R12), [спецификация](specification.md), этот план, решения D1–D6 выше. Раздел спецификации «Основания» описывает код на коммите `1b994df18`, то есть до этапа 0; где этап 0 его изменил, верен раздел «Состояние этапа 0» этого плана.
- Ревью — review-orchestrator по PR. Составы раундов 3–5 этапа 0 были сокращены решением оператора, и такие пакеты не проходят гейт завершения инструмента; если нужен полный пакет, запускайте полный состав.
- Rust-часть Desktop (`apps/desktop/src-tauri`) локально не собирается — проверяется только в CI.

### Порядок и параллельность

- Этапы 1 и 2 не зависят друг от друга, их можно вести параллельно. Оба трогают карточку PR (`apps/desktop/src/review/ReviewResults.tsx`, `ReviewBoard.tsx`): этап 1 добавляет строку работы Keryx и ссылку на ревью, этап 2 переносит интерфейс ревью из панели PR и добавляет к ссылке раунд и отставание. При параллельной работе договоритесь, какой Flow владеет этими файлами, или ведите этап 2 после слияния этапа 1.
- Этап 3 начинается только после слияния этапа 2, этап 4 — после этапов 2 и 3.

### С чего начать каждый этап

- **Этап 1.** Сначала прочитать, как сейчас хранится связь Issue ↔ сессия ↔ Flow (при подготовке не читалось, см. «Что не проверено»). Ссылка ревью на карточке строится из `localReview` и открывает текущую панель ревью. Здесь же закрывается отклонение (a): сопоставление запросов ревью на команды пользователя, если появится членство в командах. Колонка внимания убирается по D6, Issues по умолчанию показывают репозиторий проекта по D5.
- **Этап 2.** Начать с миграции запусков (`src/review/desk-run-store.ts`) в раунды и попытки на копии рабочей базы. После появления вкладки Reviews индикатор вкладки Pull requests перестаёт загораться от локального ревью — это снимает отклонение (b). Подпись «Review again» из решения (d) меняется вместе со связью раундов.
- **Этап 3.** Действие «Review again» заменяется раундом обновления того же Review; диалог публикации получает варианты по D1; `on_head_move` по умолчанию `ask` (D2).
- **Этап 4.** Процедура «Head сдвинулся» добавляется в `review-orchestrator`; публикация из Desktop и из сессии использует общий код.

### Что этап 0 оставил в коде и что нельзя сломать

- **Набор внимания вкладки Pull requests** (`carriedAttention`, `seeded`, `seedFor`, загрузка «seed», `attentionPrs`, обратная запись, флаг `stale` в `apps/desktop/src/review/ReviewBoard.tsx`). Его правили шесть раз, и три правки внесли новый дефект, который нашёл только следующий раунд ревью. Сейчас каждая защитная строка закреплена DOM-тестом: шестнадцать однострочных мутаций, каждая валит хотя бы один тест `ReviewBoard.dom.test.tsx`. Правило для следующих этапов: любое изменение этой логики сопровождается мутационной проверкой собственных строк, а не только зелёным набором тестов. На этапе 1 колонки перестают зависеть от Keryx, но индикатор остаётся — переносите его вместе с тестами.
- **Устаревший результат на карточке** (`localReview.outdated`, `reviewNote` и `laneReason` в `apps/desktop/src/review/model.ts`). SQL в `attachBadges` (`src/review/desk-run-store.ts`) обязан давать тот же результат, что `localBadge` (`src/review/board-badges.ts`); store-тест сравнивает их на фикстуре для каждого условия запроса.
- **Тулбар доски** (`apps/desktop/src/styles/review.css`): контейнерные запросы на 1100 и 760px, подсказка о скрытых запросах, голое число. Замеры — в отклонении (c); при добавлении элементов в тулбар перемеряйте.

### Открытые заметки ревью этапа 0

- F-024 (info): вторая строка об устаревшем ревью отбрасывается сравнением текста с причиной (`secondaryNote` в `apps/desktop/src/review/ReviewResults.tsx`). Не исправлено сознательно; уйдёт вместе с переносом интерфейса ревью на этапе 2.

## Зависимости

- Этап 0 независим и не меняет модель данных.
- Этап 1 не требует этапа 2: ссылка ревью на карточке на этом этапе строится из существующего `localReview` и открывает текущую панель ревью.
- Этап 3 требует этапа 2: раунд обновления принадлежит Review.
- Этап 4 требует этапов 2 и 3: сессия использует ту же команду обновления.

## Проверка

- Этапы 0–1: модульные тесты функций колонки и фильтра (`apps/desktop/src/review/model.test.ts`, `apps/desktop/src/issues`), DOM-тесты доски.
- Этап 2: тест миграции на копии рабочей базы; DOM-тесты вкладки Reviews.
- Этап 3: тесты `prior-round` на частичный прошлый раунд и на смену настроек; сценарий на реальном PR с коммитом во время раунда. Rust-часть Desktop проверяется только в CI.
- Этап 4: сценарий на реальном PR — ревью в сессии, публикация из Desktop.

## Решения владельца

| № | Вопрос | Решение |
|---|---|---|
| D1 | Разрешать ли публикацию «как есть» для прошлого коммита, когда head сдвинулся | Да, только вердикт «Комментарий» и с первой строкой о проверенном коммите |
