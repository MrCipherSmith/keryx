# PRD · Review v2
Version: 0.1.2

## Проблема

Наблюдения сделаны на коммите `1b994df18`. Ссылки на код — в [спецификации](specification.md#основания).

1. **Одна карточка — две сущности.** Колонка карточки PR вычисляется из состояния GitHub и состояния локального ревью одновременно. «На проверке» означает «Keryx сейчас выполняет ревью», а не статус PR. «Требует внимания» объединяет готовый результат Keryx, запрос ревью, запрошенные изменения и упавший CI.
2. **Карточки меняют место без изменений в PR.** Запуск, завершение и публикация ревью переносят карточку между колонками, активные ревью поднимаются наверх списка.
3. **Фильтры ненадёжны.** PR с активным ревью показывается вопреки всем фильтрам, кроме поиска. По состоянию ревью отфильтровать нельзя. Колонка «Завершено» при фильтре по умолчанию всегда пуста.
4. **Новый коммит обрывает ревью.** Запуск привязан к одной паре base..head. Если автор добавил коммит, результат нельзя опубликовать, а действия «перепроверить находки на новом коммите» нет. Кнопка «Проверить изменения» запускает обычное ревью; Desktop передаёт ему прошлый пакет, только когда прошлый запуск завершён с полным покрытием и теми же настройками. После нового коммита прошлый результат пропадает с карточки на доске и остаётся только в истории внутри панели PR.
5. **Ревью из сессии и из Desktop — разные объекты.** У них разные хранилища и разные пути публикации. Ревью, проведённое агентом в сессии, в Desktop нельзя ни продолжить, ни опубликовать.
6. **Нет простого входа «поработать с агентом».** «Открыть в сессии» для PR каждый раз создаёт новую сессию и не запоминает связь с PR. Из такой сессии созданное ревью или Flow не возвращается на карточку.
7. **Issues повторяют проблему.** Колонки вкладки Issues — стадии Flow, поэтому задачи без Flow лежат в одной колонке независимо от их состояния в GitHub.

## Цель

Во вкладках Pull requests и Issues пользователь видит прозрачный срез работы в GitHub и из любой карточки начинает работу Keryx: сессию, ревью или Flow. Ревью живёт во вкладке Reviews как одна сущность на PR, переживает новые коммиты и одинаково ведёт себя в Desktop и в сессии агента.

## Кто пользуется

| Пользователь | Сценарий |
|---|---|
| Ревьюер | Видит запросы ревью на себя в GitHub-срезе, запускает ревью, после нового коммита автора обновляет то же ревью и публикует результат на актуальный head |
| Автор PR | Видит свои PR с запрошенными изменениями, запускает исправление замечаний как Flow или открывает сессию по PR |
| Разработчик с задачей | Открывает Issue или PR в сессии, разбирается с агентом и уже из сессии создаёт Flow или ревью |
| Ответственный за проект | Во вкладке Reviews видит все ревью проекта: какие идут, какие устарели, какие ждут публикации |

## Требования

**R1. Pull requests — только GitHub.** Колонка, порядок и набор карточек во вкладке Pull requests определяются только данными GitHub: состояние, черновик, решение по ревью, CI, запросы ревью, автор, исполнитель, время обновления. Событие локального ревью, Flow или сессии не меняет колонку, порядок или видимость карточки.
Verification: judged

**R2. Фильтры без исключений.** Каждая показанная карточка удовлетворяет всем выбранным фильтрам и поиску. Фильтры Pull requests и Issues содержат только измерения GitHub. Колонки, которые при текущем фильтре не могут содержать карточек, не показываются.
Verification: judged

**R3. Issues — только GitHub.** Группировка во вкладке Issues по умолчанию отражает состояние задачи в GitHub или статус GitHub Project, если выбран проект. Стадия Flow показывается ссылкой на карточке, а не колонкой.
Verification: judged

**R4. Ссылки на работу Keryx.** Карточка и панель PR и Issue показывают в отдельной строке фиксированной высоты ссылки: ревью (состояние и номер раунда), Flow (номер и стадия), сессии (число связанных). Нажатие открывает соответствующий объект. Появление или изменение ссылки не меняет высоту и положение карточки.
Verification: judged

**R5. Открыть в сессии.** На каждой карточке PR и Issue есть действие «Открыть в сессии», независимо от наличия Flow или ревью. Если связанных сессий нет, создаётся новая сессия, привязанная к этому PR или Issue, с его контекстом. Если есть — открывается последняя, с выбором другой или новой. Привязка сохраняется и видна в заголовке сессии со ссылкой обратно.
Verification: judged

**R6. Создание работы из сессии.** Из сессии, привязанной к PR или Issue, пользователь или агент создаёт ревью или Flow без повторного указания цели. Созданный объект наследует привязку и сразу появляется ссылкой на карточке PR или Issue и в заголовке сессии.
Verification: judged

**R7. Действия на карточке.** На PR доступны «Запустить ревью» (или «Открыть ревью», если оно есть), «Создать Flow», «Открыть в сессии», а на собственном PR с запрошенными изменениями — «Исправить замечания». На Issue доступны «Создать Flow» и «Открыть в сессии». Каждое действие подписано текстом.
Verification: judged

**R8. Review — одна сущность на PR и ревьюера.** Все запуски ревью одного PR от одного аккаунта принадлежат одному Review. Review состоит из раундов, каждый раунд привязан к своей паре base..head. Находки имеют постоянные идентификаторы и статус, прослеживаемый между раундами. Вкладка Reviews показывает доску и список Review с собственными колонками и фильтрами.
Verification: judged

**R9. Новый коммит не обрывает ревью.** Когда head PR сдвинулся, Review получает признак «отстаёт на N коммитов» и действие «Обновить до нового head». Обновление — новый раунд того же Review: изменённый код проверяется, находки по затронутым местам перепроверяются, остальные переносятся со своим статусом, отчёт обновляется. Это работает и когда прошлый раунд завершён частично, и когда изменились настройки запуска.
Verification: judged

**R10. Смена head во время и перед публикацией.** Если head сдвинулся, пока раунд выполняется, пользователь узнаёт об этом в ревью и выбирает: дождаться конца и обновить, либо остановить и начать на новом head. Автоматические ревью обновляются сами. Если head сдвинулся перед публикацией, диалог публикации предлагает обновить ревью, а не только сохранить черновик локально. Решения по находкам, принятые в диалоге, сохраняются при обновлении.
Verification: judged

**R11. Одно ревью в Desktop и в сессии.** Ревью, начатое агентом в сессии через review-orchestrator, появляется во вкладке Reviews как раунд того же Review, и его можно продолжить, обновить и опубликовать из Desktop. Процедура при смене head одна и та же в сессии и в Desktop и опирается на одну команду CLI.
Verification: judged

**R12. Раздельные индикаторы.** Индикатор вкладки Pull requests загорается только от событий GitHub, адресованных пользователю: запрос ревью на него или его команду, запрошенные изменения в его PR, новый ответ ему. На этапе 0 сопоставляется только логин самого пользователя; см. [план реализации](implementation-plan.md), «Состояние этапа 0». Индикатор вкладки Reviews загорается от событий Keryx: вопрос ревьюера, ожидание решения о публикации, остановленный раунд.
Verification: judged

## Критерии выпуска

- На PR с активным ревью фильтр по другому автору скрывает карточку; запуск, завершение и публикация ревью не меняют колонку и позицию карточки во вкладке Pull requests.
- На одном PR: ревью завершено, автор добавил коммит, пользователь нажал «Обновить до нового head». Во вкладке Reviews остаётся одна карточка с двумя раундами; находка в неизменённом коде перенесена, находка в изменённом коде перепроверена; публикация проходит на новый head.
- На одном PR: коммит добавлен во время выполнения раунда. Ревью показывает отставание, после завершения предлагает обновление, опубликовать можно без запуска ревью с нуля.
- PR без Flow и ревью: «Открыть в сессии» создаёт привязанную сессию; повторное нажатие открывает её же; `/review` в этой сессии открывает запуск с уже выбранным PR; созданное ревью видно ссылкой на карточке PR.
- Ревью того же PR, проведённое агентом в сессии, видно во вкладке Reviews и публикуется из Desktop.
- Во вкладке Issues задачи без Flow распределены по колонкам GitHub, а не лежат в одной.

## Критерии пользы

- **Устойчивость доски.** Через две недели использования владелец на своём репозитории проверяет по записи экрана одного рабочего дня: сколько раз карточка PR сменила колонку без события в GitHub. Ожидается ноль.
- **Ревью переживает коммит.** За первый месяц владелец считает во вкладке Reviews долю ревью с двумя и более раундами, опубликованных без запуска с нуля. Источник — история раундов и публикаций Review.
- **Вход через сессию.** not measured — в Desktop нет телеметрии действий; оценивается на словах владельца после месяца использования.

## Риски

- **Миграция истории.** Существующие запуски нужно сгруппировать в Review без потери отчётов. Проверяется на копии рабочей базы до включения.
- **Перенос находок на изменённый код.** Перенос может ошибочно пометить находку закрытой или оставить устаревшую. Статус закрытия подтверждается перепроверкой кода, а не текстом коммита; находки без подтверждения остаются открытыми.
- **Стоимость обновлений.** Частые коммиты порождают частые раунды. Обновление проверяет только дельту и затронутые находки; автоматическое обновление подчиняется лимитам правила.
- **Привычка к старой доске.** По решению D6 колонка «Требует внимания» исчезает из Pull requests. Её заменяют быстрые фильтры по роли и индикаторы вкладок.
