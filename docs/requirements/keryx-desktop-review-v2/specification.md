## Идентичность модуля

Изменение затрагивает Desktop (`apps/desktop/src/review`, `apps/desktop/src/issues`, оболочку вкладок), бэкенд ревью (`src/review/desk-run-*`, `src/review/board*`, `src/review/desk-publication.ts`, `src/review/prior-round.ts`) и скилл `review-orchestrator`. Состав ревьюеров и устройство волн не меняются; исполнитель получает только сверку head между волнами. Формат пакета раунда не меняется: идентификаторы находок и запись раунда (`round.json`) уже существуют. Машинных схем в черновике нет; они добавляются на этапе 2 вместе с повышением версии протокола.

Смежные спецификации: [Review v1](../keryx-desktop-review/specification.md), [пакеты управляемого ревью](../managed-review-feedback-loop/specification.md).

## Сущности

```text
PullRequest (GitHub)        Issue (GitHub)
      │ subject                   │ subject
      ├── Review ── Round ── Attempt
      ├── Flow
      └── Session
```

- **PullRequest, Issue** — отражение GitHub. Локальных полей состояния нет.
- **Subject** — ссылка на PR или Issue: `{kind: "pr" | "issue", repositoryId, repo, number, url}`.
- **Review** — ревью одного PR одним аккаунтом. Ключ: `{repositoryId, number, viewer}`; `repo` (имя) хранится рядом для отображения. Аккаунт входит в ключ по решению D3 плана.
- **Round** — проверка одной пары base..head внутри Review. Режим: `first`, `delta`, `fallback-first` (значения из существующего `round.json`).
- **Attempt** — один запуск раунда. Сегодняшний `DeskRun` становится Attempt без изменения формата; повтор и `continue` — новые Attempt того же Round.
- **Finding** — находка с постоянным идентификатором в пределах Review и статусом по раундам: `open`, `closed`, `partial`, `regressed`, `withdrawn` (существующие dispositions). Находка, которую раунд не перепроверял, помечается перенесённой и сохраняет прежний статус (существующий список `carried` в записи раунда).

### Состояние Review

Состояние выводится из последнего раунда и публикаций; отдельного ручного поля нет.

| Состояние | Условие |
|---|---|
| `queued` | последний Attempt в очереди |
| `running` | последний Attempt выполняется |
| `needs_answer` | выполняющийся Attempt ждёт ответа пользователя |
| `running` | также `cancelling` — до фактической остановки |
| `stopped` | последний Attempt закончился как `failed` (включая прерванный, `recoverable`), `cancelled`, `blocked`, `budget`, `skipped` и у раунда нет принятых находок |
| `ready` | последний раунд дал принятые находки (`completed` или `partial`), решение о публикации не принято; частичное покрытие показывается пометкой |
| `published` | последний раунд опубликован |
| `closed` | PR слит или закрыт, либо пользователь закрыл Review |

Отдельный признак **freshness**: `current`, если head последнего проверенного раунда равен head PR, иначе `behind` с числом коммитов и признаком `rewritten` при force-push. Freshness не зависит от состояния: Review может быть `running` и `behind` одновременно.

## Хранение

- `runs.sqlite`: к таблице `runs` добавляются `review_id`, `round` (порядковый номер), `previous_run_id`. Новая таблица `reviews` (`id`, `repo`, `pr`, `viewer`, `closed_at`, `on_head_move`).
- Миграция: существующие строки группируются по `(repo, pr, viewer)` в один Review; раунды нумеруются по первой встрече пары base..head в порядке `createdAt`; запуски с `continuation.previousId` попадают в раунд предшественника.
- Публикации остаются файлами в каталоге Attempt; Review читает их как историю.
- Привязка сессии к Subject хранится вместе с сессией. Предпочтительный вариант — метаданные сессии рядом с существующей привязкой к Flow (O17), поле `_meta.keryx.subject`; окончательный выбор делается в начале этапа 1 (см. ниже).
- Реестр сессионных ревью: при `keryx review start` для PR пакет в `.metaproject/reviews/<id>` регистрируется как Attempt соответствующего Review (см. «Единый реестр»).

Как хранится связь Issue с сессией и Flow сегодня (`issues-contract`, операция `workspace`), при подготовке пакета подробно не читалось; этап 1 начинается с её проверки и выбора: расширить её на PR или ввести `_meta.keryx.subject` для обоих.

## Конфигурация

- Параметр Review `on_head_move`: `ask` (по умолчанию для ручных), `follow` (по умолчанию для запусков по правилу), `ignore`.
- Параметры запуска раунда — существующие `DeskReviewOptions`. Смена параметров между раундами не разрывает связь с прошлым раундом.

## Поведение при смене head

### Обнаружение

- Исполнитель сверяет head PR на границе волны (перед каждым `keryx review next`) и перед завершением раунда. Сегодня между волнами проверки нет (O7): head сверяется до запуска ревьюеров и затем только на `review complete`, где срабатывает `complete-head-gate`.
- Доска PR и вотчер уже видят новый head; при обновлении доски freshness Review пересчитывается.

### Во время выполнения раунда

Идущий раунд не прерывается сам: его результат остаётся верным для закреплённого head.

| `on_head_move` | Действие |
|---|---|
| `ask` | Review показывает «head сдвинулся на N коммитов» и два действия: «Обновить после завершения» и «Остановить и начать на новом head» |
| `follow` | После завершения раунда автоматически ставится раунд обновления |
| `ignore` | Раунд завершается, Review остаётся `behind` |

### Раунд обновления

Команда `keryx review advance` (имя предварительное) открывает новый раунд того же Review на текущем head:

1. Прошлым раундом считается последний раунд с принятыми находками, включая частичный. Для этого меняются три существующих правила: условие Desktop «completed + complete + тот же ключ настроек» (O10), правило «частичный пакет не является прошлым раундом» (`round-record.ts:207`) и требование свидетельства завершения у кандидата в `prior-round.ts`.
2. Если прошлый head — предок нового, режим `delta`: изменённые участки, пересекающиеся с открытыми находками, идут на перепроверку; остальной изменённый код проверяется как новый; неизменённый код получает повторный взгляд; находки, которых раунд не касался, переносятся с прежним статусом. Это существующий механизм (O11).
3. Если история переписана, режим `fallback-first`: полная проверка с прошлыми находками в контексте.
4. Область, не покрытая частичным прошлым раундом, добавляется в план нового раунда как непроверенная.
5. Статус `closed` ставится только после перепроверки кода; находка без подтверждения остаётся `open`.
6. Отчёт раунда содержит таблицу прошлых находок со статусами (шаблон скилла уже её предусматривает).

### Перед публикацией

Если head сдвинулся после завершения раунда, диалог публикации показывает:

- **«Обновить ревью до `<sha>`»** — основное действие, запускает раунд обновления; ответы «оставить/отклонить» по находкам сохраняются по идентификатору находки.
- **«Опубликовать как есть для `<sha>`»** — только вердикт «Комментарий», первая строка тела называет проверенный коммит и говорит, что PR ушёл вперёд (то же правило, что уже требует `complete-head-gate`). Действие разрешено решением D1 плана.
- «Сохранить локально» и «Пропустить» — как сегодня.

### В сессии агента

В `review-orchestrator` добавляется процедура «Head сдвинулся»: агент сообщает пользователю число новых коммитов и вызывает ту же `keryx review advance`. Фраза из O13 заменяется ссылкой на процедуру. Правило «новые коммиты — отдельный запрос» в промпте Desktop (O7) заменяется описанным поведением.

## Единый реестр

- Пакет, созданный в сессии для PR, регистрируется как Attempt с источником `session`. Источник `existing` остаётся только для пакетов, созданных до миграции.
- Attempt с источником `session` имеет те же действия, что ручной: открыть отчёт, продолжить, обновить, опубликовать.
- Публикация — один код: `review publish` использует приёмку, квитанцию и маркер дублей из `desk-publication` (O15). Подтверждение пользователя остаётся в обоих интерфейсах.

## Экраны

### Навигация

Вкладки проекта: Sessions, Flows, Reviews, Pull requests, Issues, Metaproject. Flows и Reviews — работа Keryx, Pull requests и Issues — срез GitHub. Порядок принят решением D4 плана; горячие клавиши следуют порядку вкладок.

### Pull requests

- **Группировка.** По умолчанию «Статус»: Draft · Ждёт ревью (нет решения или `REVIEW_REQUIRED`) · Запрошены изменения · Одобрено. Колонки Merged и Closed появляются, только когда их включает фильтр состояния. Переключатель «Моя роль»: Ревью запрошено у меня · Мои PR · Остальные.
- **Порядок.** По времени обновления, по убыванию. Локальные события порядок не меняют.
- **Фильтры.** Существующие измерения GitHub и период. Быстрые фильтры в строке: «Запрошено у меня», «Мои», «CI упал». Обход фильтров для активного ревью (O2) удаляется.
- **Карточка.** Номер, заголовок, метки состояния GitHub, автор, CI, запросы ревью. Ниже — строка работы Keryx фиксированной высоты с тремя местами: ревью, Flow, сессия. Пустое место показывает приглушённое действие («Ревью», «Flow», «Сессия»), заполненное — ссылку.
- **Ссылка ревью.** Состояние и раунд: «Ревью · раунд 2 · готово», при `behind` — «отстаёт на 3». Открывает Review во вкладке Reviews.
- **Ссылка Flow.** «Flow #488 · стадия». Открывает Flow.
- **Ссылка сессии.** Число связанных сессий. Нажатие открывает последнюю; меню — список сессий и «Новая сессия».
- **Действия.** Подписаны текстом в панели и в меню карточки: «Запустить ревью» / «Открыть ревью», «Создать Flow», «Открыть в сессии», «Открыть в GitHub», подписка. На своём PR с `CHANGES_REQUESTED` или неразрешёнными тредами — «Исправить замечания».
- **Панель PR.** Вкладки «Обсуждение» и «Проверки» — данные GitHub. Блок «Работа» со ссылками на Review, Flows и сессии и строкой режима автоматизации. Полный интерфейс ревью, история запусков и публикация из панели PR убираются во вкладку Reviews.
- **Индикатор вкладки.** Запрос ревью у пользователя или его команды, `CHANGES_REQUESTED` в его PR, непрочитанный ответ ему.
- **Панель инструментов.** Не переносится на вторую строку при открытой панели PR: второстепенные элементы уходят в меню. Перенос наблюдался при осмотре приложения в окне 1440×900; ссылки на код для него нет.
- **Вотчер.** Переключатель вотчера остаётся здесь: он синхронизирует данные GitHub.

### Issues

- **Группировка.** По умолчанию Open · Closed (Closed — по фильтру). При источнике «GitHub Project» — по статусу проекта, как сегодня. Группировка по стадии Flow убирается из умолчаний (O18).
- **Карточка.** Строка работы Keryx с двумя местами: Flow и сессия.
- **Действия.** «Создать Flow» (существующее `prepare-flow`), «Открыть Flow», «Открыть в сессии» (существующее `open-session`).
- **Область.** По умолчанию показываются задачи репозитория проекта (решение D5 плана). Источник «Assigned to me» по всем репозиториям остаётся выбором; сегодня он показывает задачи из любых репозиториев.

### Открыть в сессии

- Действие есть на каждой карточке и в панели PR и Issue, при любом сочетании Flow и ревью.
- **Нет связанных сессий.** Создаётся сессия с привязкой к Subject. В контекст сессии передаётся ссылка на материалы: для PR — результат `keryx review pr-context` (описание, обсуждение, head, CI, связанные Flow), для Issue — текст и обсуждение задачи. Поле ввода получает ссылку на PR или Issue; сообщение не отправляется автоматически.
- **Есть связанные сессии.** Открывается последняя неархивная. Меню ссылки показывает все и «Новая сессия».
- **Заголовок сессии.** Показывает Subject со ссылкой обратно на карточку и ссылки на Review и Flow этого Subject, если они есть.
- **Создание из сессии.** `/review` и инструмент `prepare_review` открывают диалог запуска с уже выбранным PR Subject. Создание Flow из сессии подставляет Subject как источник. Созданные Review и Flow записывают Subject и идентификатор сессии; ссылки появляются на карточке без обновления вручную.
- **Сессия по Issue и ревью.** Ревью создаётся только для PR. В сессии по Issue `/review` предлагает выбрать PR, как сегодня.
- Привязка не меняет поведение сессии и не ограничивает агента этим Subject.

### Reviews

- **Колонки.** Выполняется (`queued`, `running`) · Ждёт вас (`needs_answer`, `ready`, `stopped`) · Отстаёт · Опубликовано · Закрыто (по фильтру). Порядок выбора колонки: `closed` → выполняется → `needs_answer` → отстаёт (любой Review с freshness `behind`) → остальные по состоянию. `ready` и `published` с отставанием попадают в «Отстаёт».
- **Карточка.** PR (номер, заголовок, автор), раунд, проверенный коммит и отставание, число находок по тяжести, состояние публикации, источник (вручную, по правилу, сессия), связанный Flow, расход токенов.
- **Фильтры.** Состояние, freshness, публикация, источник, автор PR, Flow, период.
- **Панель Review.** Раунды (лента с диапазоном, режимом, покрытием, попытками) · Находки (сквозной список со статусом по раундам) · Отчёт последнего раунда · Публикации · Сессии ревьюеров · Автоматизация.
- **Основное действие** зависит от состояния: «Ответить», «Опубликовать», «Обновить до нового head», «Повторить раунд», «Открыть в сессии».
- **Правила ревью** (сегодня кнопка «Review rules» на доске PR) переезжают сюда.
- **Индикатор вкладки.** `needs_answer`, `ready` без решения о публикации, `stopped`.

### Исправить замечания

Действие на своём PR создаёт Flow исправления с привязкой к PR: источник — запрошенные изменения и неразрешённые треды. Существующие настройки автоматического исправления из подписки (O19) остаются как автоматический вариант того же действия; их перенос в правила — вне этого пакета.

## CLI и скилл

| Поверхность | Изменение |
|---|---|
| `keryx review board --json` | Карточка PR несёт `links` (review, flows, sessions) вместо `localReview`; `localReview` остаётся на время перехода |
| `keryx review reviews --json` (новая) | Список Review с состоянием, freshness, раундами |
| `keryx review advance` (новая) | Раунд обновления на текущем head |
| `keryx review desk-run start` | Создаёт Attempt в существующем или новом Review; принимает прошлый раунд по новым правилам |
| `keryx review desk-publish` | Возвращает варианты при сдвинутом head вместо одного запрета |
| `keryx review publish` | Использует общий код публикации |
| `review-orchestrator` | Процедура «Head сдвинулся»; регистрация пакета сессии в реестре |

## Контракты данных

```ts
interface WorkLinks {
  review?: { id: string; state: Review["state"]; round: number; behind?: number | null };  // null — отстаёт, число коммитов неизвестно
  flows: { id: string; dir: string; stage: string }[];
  sessions: { id: string; title: string; updatedAt: string | null }[];
}

interface Review {
  id: string;
  key: { repositoryId: string; repo: string; number: number; viewer: string };
  state: "queued" | "running" | "needs_answer" | "stopped" | "ready" | "published" | "closed";
  freshness: { kind: "current" } | { kind: "behind"; commits: number | null; rewritten: boolean };
  onHeadMove: "ask" | "follow" | "ignore";
  rounds: Round[];
}

interface Round {
  number: number;
  baseSha: string;
  headSha: string;
  mode: "first" | "delta" | "fallback-first";
  previousRound?: number;
  attempts: DeskRun[];           // существующий тип
  publication?: "pending" | "published" | "skipped";
}
```

Версия протокола ответов CLI повышается; Desktop проверяет её, как сегодня (`assertProtocol`).

## Интеграции

- **GitHub** — без новых прав: чтение PR, Issue, обсуждений; публикация ревью как сегодня.
- **Flows** — Flow хранит Subject; действие «Исправить замечания» создаёт Flow.
- **Сессии (ACP)** — метаданные сессии несут Subject; `prepare_review` получает Subject из сессии.
- **Вотчер и правила** — события `push` для PR с Review ставят раунд обновления, а не независимый запуск.

## Критерии приёмки

1. Функция колонки PR не читает ни одного поля локального ревью; тест перебирает состояния локального ревью и получает одну и ту же колонку.
2. Фильтрация PR не имеет ветки для активного ревью; тест с активным ревью и несовпадающим автором даёт пустой результат.
3. После нового коммита карточка PR показывает ссылку «Ревью · отстаёт на N», а не теряет её.
4. Раунд обновления после частичного прошлого раунда получает режим `delta` и непустой список прошлых находок.
5. Раунд обновления при изменённых настройках запуска получает прошлые находки.
6. Смена head на границе волны фиксируется в Review до завершения раунда.
7. Диалог публикации при сдвинутом head содержит действие обновления; ответы по находкам сохраняются после обновления.
8. Повторное «Открыть в сессии» для того же PR открывает существующую сессию; привязка к Subject переживает перезапуск приложения.
9. Ревью, запущенное из привязанной сессии, появляется ссылкой на карточке PR.
10. Пакет ревью, созданный в сессии, виден в `keryx review reviews --json` с источником `session` и публикуется через `desk-publish`.
11. Миграция на копии рабочей базы: число Attempt до и после совпадает, каждый принадлежит ровно одному Review.
12. Колонки Issues по умолчанию не зависят от стадии Flow.
13. Колонка PR или Issue, которая при текущем фильтре не может содержать карточек, не рисуется.
14. Строка работы Keryx имеет одну высоту при нуле и при трёх ссылках; появление ссылки не сдвигает соседние карточки.
15. Каждое действие карточки и панели имеет видимую текстовую подпись; «Исправить замечания» показано только на своём PR с запрошенными изменениями или неразрешёнными тредами.
16. Индикатор Pull requests не загорается от PR, где ревью запрошено у другого человека; индикатор Reviews загорается от `needs_answer`.
17. При `on_head_move: follow` после завершения раунда на устаревшем head раунд обновления ставится без действий пользователя.
