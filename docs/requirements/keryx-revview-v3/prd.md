# PRD: Keryx Review V3
Version: 0.2.0

Статус: spec ready; решения D1–D7 приняты, целевое поведение не реализовано.

## Проблема и цель

Большое ревью выполняется долго; плоские волны, последовательные вызовы spawn, повторное чтение контекста и ограниченные бюджеты мешают охватить изменения глубоко за один проход. Добавление агентов без общего плана создаёт дубли и пробелы. Цель — ускорить проверку без потери доказательности и покрытия, сохранив единый review-orchestrator на разных harness.

Пользователи: разработчик, запускающий ревью в терминале или Codex/другом harness; пользователь Keryx Shell/Hub Session; сопровождающий каталога агентов.

## Требования

### R1 — Подготовка перед ревью
Главный собирает контекст сам или через разведчиков/генералов/солдат: diff, требования, сценарии, зависимости, риски. Замораживает ревизию и план покрытия перед основным запуском.
Verification: judged

### R2 — Зоны ответственности и глубина
План распределяет области по владельцам, а проверки — по сценариям и аспектам. Межмодульные границы имеют явного владельца. Главный может назначать солдат напрямую; генерал делегирует только в пределах задания.
Verification: judged

### R3 — Сабагенты как сущности
Расширить текущий каталог, сохранив 12 существующих определений и проектные overrides. Добавить review-scout, review-coordinator, review-worker, review-validator; специализации проверок остаются skills.
Verification: judged

### R4 — Полномочия генерала
Генерал наследует эффективные инструменты и approval-политику главного, в review-фазе не меняет исходники (как и главный), не получает дополнительных прав и не разделяет его изменяемое рабочее состояние. Терминальные решения общего ревью принадлежат главному/оператору.
Verification: judged

### R5 — Переносимость и внешние исполнители
Одинаковый процесс доступен из Keryx Shell/Hub и внешних harness. Поддерживаются native и external исполнители. Первый выпуск обязательно включает Keryx runtime как внешнего генерала и native путь; Codex/Claude могут управлять через общий API, их process adapters требуют проверки, Pi отложен. Недоступные возможности и отсутствие авторизации приводят к явному blocked или согласованному fallback, а не фиктивному успеху.
Verification: judged

### R6 — Повышенные общие лимиты
Ввести профиль из policies.md: общие concurrency/count/time ceilings, локальные лимиты ролей, резерв проверки и адаптацию к rate limit. Новый генерал и новый ход не обнуляют бюджет одного review run.
Verification: judged

### R7 — Наблюдаемость, отмена, восстановление
Главный видит всё дерево, назначения и прогресс покрытия. Отмена распространяется на потомков. Восстановление не повторяет завершённую работу и не создаёт двойной учёт.
Verification: judged

### R8 — Результат с доказательствами
Каждая проверка оставляет полный результат, scope/slice IDs, ссылки на доказательства и статус. Генерал не заменяет ответы солдат своим summary. Финальный отчёт различает verified, blocked и not run.
Verification: judged

### R9 — Проверка находок и совместимость
Сохранить review readiness, premise decisions, ingest, completion и publish gates. Проверять находки независимым исполнителем; последующие раунды преимущественно delta. Не ослаблять существующие права и gates при миграции.
Verification: judged

### R10 — Доказанное улучшение
Сравнить плоский и иерархический запуск на одних ревизиях, моделях и наборах контрольных дефектов; измерить время, стоимость, полноту и повторы. Нельзя объявлять ускорение только по факту параллельного spawn.
Verification: judged

Verification: judged у R1–R10 временно обозначает приёмку будущих тестовых доказательств. До реализации соответствующего этапа P1–P5 автоматизируемые R3, R6–R9 должны получить exec/invariant с конкретными существующими командами; без этого этап не принимается. Исполнимые тесты этим docpack не созданы.

## Критерии выпуска

- Сценарии AC1–AC10 спецификации подтверждены результатами проверки, включая отказы и восстановление.
- Старые определения агентов и прямой spawn сохраняют совместимость.
- Есть матрица capabilities для каждого заявленного адаптера; не прошедшие проверку явно unsupported.
- Нет потерянных задач, превышения общих лимитов и обхода approvals в детерминированных тестах.
- Начальный профиль лимитов принят, wire API закреплён на этапе контрактов; документация не объявляет placeholders рабочими командами.

## Критерии результата после выпуска

- На фиксированном corpus минимум из 10 крупных ревью, по 3 повтора baseline/V3: целевое уменьшение медианы времени до проверенного отчёта ≥30%, без уменьшения recall контрольных дефектов; наблюдение — benchmark report в review package пилота, после завершения cohort и до пилотного выпуска.
- На том же corpus: стоимость на принятый finding не выше baseline более чем на 25%; при провале пересмотреть размер дерева/лимиты, не скрывать результат. Наблюдение — cost/quality таблица того же benchmark report в review package после cohort, до пилотного выпуска.
- На каждом прогоне: все обязательные пары scope×аспект имеют результат или явный blocked/not run; наблюдение — coverage artifact в review package каждого run перед readiness и повторно при завершении.
- Принятие пользователями: not measured — телеметрия использования не входит в этот пакет.

## Риски и рекомендация

Риски: rate limits, рост стоимости, дробление контекста, межобластные пробелы, привилегии через внешние CLI, ограничения вложенности harness. Рекомендация: общий план и host-owned scheduler раньше расширения fan-out; затем адаптеры, и только после проверок повышение профиля по умолчанию. Статистика выполнения текущей docpack-сессии выключена; будущие продуктовые измерения — отдельное требование R10.

Cost-unknown допускает эксплуатацию с явной неизвестной стоимостью, но не удовлетворяет AC10 и критерию стоимости release benchmark. Release-validation cohort должен использовать measured-cost; при отсутствии данных фиксируется not measured, соответствующий gate не пройден.
