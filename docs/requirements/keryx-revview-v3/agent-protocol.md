# Протокол подготовки и ревью
Version: 0.2.0

Статус: spec ready; решения D2/D4/D5/D7 приняты, runtime planned.

## Процесс

1. Preflight: определить revision, доступные entities/skills, capabilities host/adapters, auth readiness без чтения/вывода секретов, лимиты и исходный scope.
2. Подготовка: главный сам или через scouts/coordinators собирает изменения, требования, affected dependencies, пользовательские сценарии и risks. Общее неизменяемое evidence передаётся ссылками; каждому ребёнку — scoped context.
3. План: построить матрицу scope×aspect, отделить обязательное покрытие от дополнительных исследований, назначить владельцев границ. Главный утверждает рабочий план с соблюдением существующих operator gates.
4. Нарезка: распределять по связным сценариям и ответственности, не механически по папкам. Принято D5: генерал владеет связной областью поведения, а солдат — конкретным аспектом/сценарием. Для малого scope главный назначает прямых солдат. Размер задания ограничен context/time budget. Для общей зависимости создать отдельную проверку с владельцем; осознанное перекрытие пометить причиной.
5. Выполнение: главный запускает генералов и/или прямых солдат. Генерал дробит только свою область и не переопределяет глобальный план. Главный может менять назначения с новой plan version и отзывом старых leases.
6. Контроль: события и coverage показывают active/waiting/blocked/done. При rate limit снизить concurrency соответствующего provider, выдержать retry-after, затем восстанавливать постепенно. Выполненные assignments не повторяются.
7. Верификация: валидатор независимо проверяет находки; спорные выводы и premise decisions сохраняют существующие gates. Не запускать один и тот же экземпляр для проверки собственной находки.
8. Консолидация: главный собирает leaf evidence, дедуплицирует находки с сохранением источников, публикует coverage и not run. Только после readiness и operator decisions наступает completion.

## Жизненный цикл

Задание проходит planned → queued → running → waiting_children (только coordinator) → collecting → completed. Альтернативные терминальные состояния: blocked, failed, cancelled. Retry создаёт новый attempt с той же task identity и новым dispatch ID; admission считает каждый фактический запуск. Complete требует валидного результата и актуальной revision/plan version. Process exit=0 сам по себе недостаточен.

Spawn идемпотентен по task+attempt: повтор запроса после сетевого сбоя возвращает тот же run. Lease потерян — сначала reconciliation процесса, затем повтор; две активные попытки не могут независимо закрыть task. Завершённые части сохраняются при отмене, но не получают статус полного ревью.

## Управление деревом

Root имеет depth=0, general=1, soldier под general=2; прямой soldier=1 и всё равно leaf. General не создаёт general. Подготовка использует те же роли/ограничения. Root cancel отзывает authority leases дерева, останавливает descendants и ждёт bounded cleanup; неподтверждённый stop показывается как unresolved process, не successful cancellation.

Waiting coordinator не удерживает execution slot. Его elapsed deadline продолжает идти, но время ожидания не списывается как активное agent-time поверх уже учтённого времени детей. До выдачи slots scheduler атомарно резервирует глобальные и локальные лимиты. Root и validators получают возможность прогресса при насыщении worker очереди.

## Result и владение

Полный файл результата — истина; краткий текст spawn не используется как замена. Evidence включает revision, scope/slices, checks performed, findings, uncertainties и not run. Summary генерала ссылается на ответы солдат. Повторно поставленное задание сохраняет историю, не перезаписывает артефакт предыдущего dispatch. Главный не принимает заявленное покрытие без соответствующих evidence references.

Внешний процесс не получает ключ авторизации от родителя автоматически. Bridge выдаёт только scoped run token с expiry, parent/run binding и отзывом при cancel; не bearer credential провайдера. Проверка каждой bridge-операции использует текущую host authority. Произвольный shell launch без bridge не считается managed general.

## Владелец управления и review policy

Один Keryx controller сохраняет дерево и бюджеты на диск; native tools, CLI и MCP обращаются к одному версионированному API. Adapter не создаёт независимый ledger. Во всей review-фазе исходники read-only, включая root/general; права на tools проверяются по действию и assignment. Исправления требуют отдельной явно разрешённой фазы.
