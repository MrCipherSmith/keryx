#### F-001 — §6.3 lists four places for the new `sourceType: "probe"`, missing `apply.ts`

- **File**: `docs/requirements/keryx-learn-probe/specification.md:222–231`
- **Cross-ref**: `src/learning/apply.ts:48–55` (`EVIDENCE_TO_SOURCE_TYPE`),
  `src/learning/apply.ts:73` (`sourceTypeFor`).
- **Problem**: the spec says "Four places enumerate evidence source types and
  they must move together" and lists `src/learning/types.ts`,
  `src/learning/schema.ts`, `src/learning/learned-pattern.schema.json`, and
  `docs/requirements/keryx-agent-platform-expansion/schemas/learned-pattern.schema.json`.
  `src/learning/apply.ts` independently maintains a type-narrowing map:

  ```ts
  const EVIDENCE_TO_SOURCE_TYPE: Partial<Record<EvidenceSourceType, LearningSourceType>> = {
    review: "review", "reviewer-comment": "review",
    test: "test", failure: "failure", health: "health", memory: "memory",
  };
  ```

  Adding `"probe"` to the type union and the validator whitelist but **not** to
  this map lets a record write a valid evidence item whose `applyLearnedPattern`
  call resolves through the `DOMAIN_TO_SOURCE_TYPE` fallback rather than to a
  probe-specific entry. Probe itself never calls `apply`, but the spec's
  "four places" claim is a contract for the implementer and is wrong.
- **Why it matters**: the implementer following §6.3 will leave
  `EVIDENCE_TO_SOURCE_TYPE` unchanged and ship a partial patch — the failure
  only surfaces once a record with a probe-typed evidence item is later passed
  to `keryx learn apply`.
- **Suggested fix**:

  ```diff
  - Four places enumerate evidence source types and they must move together:
  + Five places enumerate evidence source types and they must move together:
    1. the type union `EvidenceSourceType` (`src/learning/types.ts`),
    2. the runtime validator whitelist `EVIDENCE_SOURCE_TYPES`
       (`src/learning/schema.ts`),
    3. the shipped schema `src/learning/learned-pattern.schema.json`,
  - 4. the documented schema
  -    `docs/requirements/keryx-agent-platform-expansion/schemas/learned-pattern.schema.json`.
  + 4. the documented schema
  +    `docs/requirements/keryx-agent-platform-expansion/schemas/learned-pattern.schema.json`,
  + 5. the type-narrowing map `EVIDENCE_TO_SOURCE_TYPE`
  +    (`src/learning/apply.ts:48`) — the only "outbound" site; probe never
  +    calls `apply`, but a record with a probe-typed evidence item later
  +    passed to `keryx learn apply` would otherwise resolve through the
  +    domain fallback.
  ```

#### F-002 — §7 verdict-resolution order lists five reasons and omits `gold-leak`

- **File**: `docs/requirements/keryx-learn-probe/specification.md:293–309`
- **Cross-ref**: `docs/requirements/keryx-learn-probe/specification.md:188–191` (§6.1)
- **Problem**: §7 has five numbered steps: `no-task` → `underpowered` →
  `environment-drift` → `run-failed` → `budget-exceeded` → delta-CI. `gold-leak`
  is described as a refusal-style check that happens **before** any arm starts
  (§6.1, AC8) but it does not appear in §7's numbered order. AC8 gives the
  expected shape — null arms, empty `runs` — which is a precondition the order
  must reach before seeding; the current §7 forces the reader to mentally splice
  §6.1 and §7.
- **Why it matters**: the resolution algorithm is the most consequential part
  of the spec. Without `gold-leak` in the order, an implementer can place the
  `checkGoldLeakage` call after the turn has started and lose the null-arm
  invariant, or collapse it into `run-failed` and lose the diagnostic.
- **Suggested fix**:

  ```diff
  Verdict resolution, in order:

    1. The task id is absent from the task set → `unmeasurable` / `no-task`.
    2. Fewer seeds than the task's `kind` requires → `unmeasurable` /
       `underpowered`.
  + 2.5. `checkGoldLeakage` reports a reachable gold path (the task's
  +       `goldArtifacts` survived removal, or never existed in the base ref)
  +       → `unmeasurable` / `gold-leak`. Arms are null; the comparison
  +       records the reachable path (see §6.1, AC8).
    3. Any arm's environment record missing or mismatched → `unmeasurable` /
       `environment-drift`.
    …
  ```

  Cross-reference §6.1 to make `gold-leak`'s source explicit:

  ```diff
  - "…yields `unmeasurable` / `gold-leak` (exit 3) with a comparison that
  -  records the reason and carries no arms — an unverified key is not a
  -  passing run."
  + "…yields `unmeasurable` / `gold-leak` (exit 3) with a comparison that
  +  records the reason and carries no arms — an unverified key is not a
  +  passing run. Resolution order: §7 step 2.5."
  ```

#### F-004 — `gold-leak` collapses two distinct root causes into one reason

- **File**: `specification.md:188–191`
- **Problem**: "does not exist in the base ref" (operator error: wrong path in
  `goldArtifacts`) and "survives removal" (runtime: file is locked / removal
  failed) both yield `reason: "gold-leak"`. The schema has no diagnostic
  sub-field and `runs[]` is empty under unmeasurable, so the operator cannot
  distinguish "fix the task set" from "fix the runner".
- **Fix** (pick one):
  - (a) extend the schema with `goldLeakDetail: { kind: "missing-in-base" |
    "survived-removal"; reachablePaths: string[] }` on the unmeasurable branch.
  - (b) document explicitly that `goldArtifacts[0]` is mirrored into the
    existing `reachablePaths` collector of the artifact, and the operator reads
    it from there.

#### F-005 — `--max-usd 0` is not specified

- **File**: `specification.md:120,137`
- **Problem**: §5 lists `--max-usd <n>` as required for a real run and says a
  missing value is refused with `probe-no-budget` (exit 2). `--max-usd 0` is
  formally present but zero. Two interpretations exist:
  (a) treated as missing (`probe-no-budget`, exit 2), or
  (b) accepted; the first token cross the ceiling and the run resolves to
  `unmeasurable / budget-exceeded` on seed 1.
- **Fix**: add one sentence to §5: "`--max-usd 0` is treated as `probe-no-budget`
  (exit 2); `--max-usd` must be a positive number."

#### F-006 — §3 storage layout does not validate `probes/tasks.json`

- **File**: `specification.md:48–49, 94–104`
- **Problem**: §3 marks `probes/tasks.json` as the optional default task set;
  §4 makes `.metaproject/data/learning/probes/tasks.json` the default
  `defaultTaskSet`. The schema requires `tasks.minItems: 1`. If the file is
  absent, unparseable, or fails validation, the behavior is unspecified.
- **Fix**: in §4, add: "An absent, unparseable, or schema-invalid
  `defaultTaskSet` is refused with `probe-bad-task-set` (exit 2), the same
  shape as `probe-no-budget`."

#### F-007 — §6.4 does not specify the baseline system instruction both arms share

- **File**: `specification.md:259–277`
- **Problem**: §6.4 says "the two arms differ by that text and nothing else"
  but does not pin down **what** the baseline is. AC13 verifies the diff but
  without a pinned baseline the diff is uniquely a black box.
- **Fix**: add: "Both arms receive `runAgentTurn`'s `systemPrompt` constructed
  with the same prefix, harness envelope, and tool list; the `<learned-pattern>`
  block is appended after `</system>` for the probe arm and replaced with
  `<!-- empty -->` for the base arm. The diff of the two strings is asserted
  to contain exactly one block in `runner.test.ts`."

#### F-008 — §7 step 4 does not cover partial-seed failure

- **File**: `specification.md:299–300`
- **Problem**: "Any seed's turn failed to produce an answer line at all →
  `unmeasurable` / `run-failed`" does not say what happens when **some** seeds
  succeed and others fail in the same arm.
- **Fix**: append: "A single failed seed in either arm is sufficient to make
  the verdict `unmeasurable / run-failed`. Per-arm `successes / seeds` is still
  recorded for diagnostics; the verdict ignores partial rates."

#### F-009 — §6.1 and AC8 diverge slightly on `runs` under `gold-leak`

- **File**: `specification.md:188–191` vs `:352–355` (AC8)
- **Problem**: §6.1 says "carries no arms"; AC8 says "arms.base and arms.probe
  both `null` and an empty `runs`". Schema (`runs: minItems: 0`) allows both,
  but §6.1 should reference AC8 for the empty-runs invariant.
- **Fix**: in §6.1, replace "carries no arms" with "carries null arms and an
  empty `runs`, per AC8".

#### F-010 — 12-hex probe-id birthday bound is not acknowledged

  probes per repo — acceptable for v1, where adoption criterion caps volume in
