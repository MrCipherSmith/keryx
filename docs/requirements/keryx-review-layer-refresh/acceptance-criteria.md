## Criteria

- AC1: Every managed review (`keryx review` start and `dispatch`) first refreshes the layers with no operator step: it rebuilds the code graph at the review head, runs `wiki refresh` and `memory index` (without `--embeddings`), and writes `layers.json` in the package: for each layer its commit, build time and counts (graph nodes/edges, wiki pages refreshed and pages with stale prose, memory entries). `keryx review layers refresh --package <pkg>` runs the same step by hand. No model is called: a provider that throws on any call is injected and never fires, and `wiki enrich` is not reachable from the review path (a test fails if the review modules import it). A failed rebuild is written to `layers.json` as `graph: failed` with the error and shown; the existing empty-graph refusal of `blast-radius` stays. [verify: exec `bun test src/review/layers.test.ts`]
- AC2: A review's refresh leaves the working tree and the PR untouched: the graph is built into the package's own graph directory (a data-dir option on `gdgraph build`; if T1 shows that is not feasible, the tracked artifacts are restored byte for byte after the build and the test below still holds), and after a refresh `git status --porcelain` of the review worktree is empty, `.metaproject/data/gdgraph/.provenance.json`, `artifacts/module-map.json` and `artifacts/summary.md` are byte-identical to before, and `git diff <base>...HEAD` is the same as before. Graph-reading commands used by a review (`blast-radius`, the layer block, `keryx gdgraph affected`) read the package's graph. [verify: exec `bun test src/review/layers-clean-tree.test.ts`]
- AC3: In a fresh worktree created for a PR head (tracked artifacts from another commit, no gitignored `storage/`), the refresh produces a graph whose recorded commit equals the PR head, and `layers.json` records both `graphCommit` and `prHead`. A graph from another commit is never read by a review: after the refresh the two commits are equal or the layer is marked `failed` (AC1). A test builds such a worktree from a fixture repository with two commits and a gitignored `storage/`. [verify: exec `bun test src/review/layers-worktree.test.ts`]
- AC4: Wiki and memory are read from the project working copy (the operator's `.metaproject`), not from the PR head's checkout. `layers.json` records a divergence mark for each of them against the PR head: the working-copy commit, the PR head, the number of commits between them and the wiki/memory paths changed in that range (`none` when equal). A PR whose head carries a different `.metaproject` is not read for wiki or memory. [verify: exec `bun test src/review/layers-divergence.test.ts`]
- AC5: Each driver payload carries a bounded `layers` block for that reviewer's files: graph-affected files (depth 1, then 2 while under the byte cap), symbol neighbours, related tests, wiki pages that describe those files and memory entries matched by module. The block states what was truncated and the command that fetches the rest, and is deterministic: the same inputs give byte-identical output. [verify: exec `bun test src/review/layers-payload.test.ts`]
- AC6: Every reviewer skill that reads code (`review-logic`, `review-regression`, `review-architecture`, `review-frontend`, `review-backend`, `review-performance`, `review-security-code`, `review-testing-practices` and the project overlays) carries one shared instruction block that names the exact commands (`keryx gdgraph affected <file>`, `keryx test related <file>`, `keryx wiki ask "<q>"`, `keryx memory search "<q>"`) and when to use them; the block is identical across skills, and the bundled and project copies are byte-identical. [verify: exec `bun test src/gdskills/reviewer-layer-block.test.ts`]
- AC7: For each reviewer run the package records `layersUsed` {graph, wiki, memory, ctx}, counted from the run's tool-call log and not from the reviewer's statement. A reviewer whose log is missing is recorded as `unknown` (never zero); `unknown` never blocks `ledger build`, `compare-reference` or `review complete`, and the panel shows it as `unknown` with a count of how many reviewers have no log. [verify: exec `bun test src/review/layers-usage.test.ts src/review/ledger.test.ts`]
- AC8: Chunked pass over the files the blast-radius cap cut (`dropped`; 753 of 793 on PR 7659). Nothing is skipped: the dropped files are split into chunks and the chunks run one after another, then merged. The file-count cap (default 40, the blast-radius cap) and the slice byte cap bound ONE pass (chunk size), not total coverage. (a) A deterministic chunk plan is written to the package before the first pass (`chunks.json`: chunk ids, files, order; same inputs give a byte-identical plan; every dropped file appears in exactly one chunk). (b) Chunks run sequentially, each through `review-regression` on the middle model tier (one tier below the session's flagship), reusing the slice and retry-plan machinery of flow 430; a failed chunk is retried per the retry plan and stays `pending` otherwise. (c) A merge step folds the chunk results into one ledger input (duplicates by file and line collapsed) and writes `chunk-pass.json` with per-chunk state (`done|failed|pending`) and the merged findings. A review with no dropped files writes no chunk plan. [verify: exec `bun test src/review/chunks.test.ts`]
- AC9: Scope A coverage is verified and stated: every changed file of the PR lands in some slice of the slice manifest, or in the manifest's `omissions` under a named reason (`lockfile`, `vendored`, `generated`, `data-ledger`, the other reasons of `src/review/slice.ts` and `src/review/scope.ts`). Files in `omissions` count as covered, are never read by a reviewer, and are listed in the package per file with their reason (`coverage.json`), so a lockfile or generated file never blocks `complete` and never disappears silently. `keryx review coverage` (and `layers status`) computes, for scope A and scope B together, the in-scope files, the files covered by a finished slice or chunk, the files covered by a named omission (with the reason counts), and the uncovered remainder, and prints all four counts. A fixture PR with a changed file that is in neither a slice nor a named omission fails the check. [verify: exec `bun test src/review/coverage-complete.test.ts`]
- AC10: `keryx review complete` refuses while any in-scope file is not covered by a finished slice or chunk, naming the uncovered count, the first files and the command that runs the missing chunks. The only way past is the operator's waiver recorded with a quote (`--waive-coverage "<the operator's own words>"`, the same shape as the mutation waiver: quote, time and the waived file list in the dispatch record); the waiver is shown in the report and the panel. There is no "unchecked remainder" outcome: a file is covered, or waived with a quote, or `complete` refuses. [verify: exec `bun test src/review/complete-coverage-gate.test.ts src/commands/review-ledger.test.ts`]
- AC11: Before a large chunk run starts, the operator sees an estimate: chunk count, files, estimated tokens and cost at the middle tier, and estimated duration (`review chunks estimate`, printed by `review` before the first pass). The automatic-mode ceiling is 25 passes of 40 files (1,000 files): in the automatic review mode of flow 429 a run at or under the ceiling goes through without a question (PR 7659: 753 files, 19 chunks), and a run over it stops and asks the operator once; in interactive mode a run over the ceiling waits for the operator's yes. The ceiling is set in `routing.config.json` with these defaults and stated in help and in the docs. The estimate and the answer are recorded in the package. [verify: exec `bun test src/review/chunks-estimate.test.ts`]
- AC12: TUI. The `/reviews` sidebar panel shows one line per review: `graph@<sha7> = head|differs`, wiki and memory divergence, `layers used n/m`, `unknown k`, and `chunks d/t, uncovered u`; the Review depth tab of the `/reviews` modal shows the full `layers.json` lines (commit per layer, divergence, per-reviewer counts) and the chunk pass: chunks done/total, per-chunk state, uncovered file count, any waiver and its quote; the `/reviews` menu has "Refresh layers" and "Run missing chunks" actions for the selected review; the slash command `/review layers` and the readline text print the same lines as the panel. All four read one projection. [verify: exec `bun test src/tui/review-panel.test.ts src/tui/reviews-inspector.test.ts`]
- AC13: `keryx help`, `README.md`, `docs/docs/cli-reference.md`, `docs/docs/guides/review-with-a-record.md` and the gdgraph/wiki guide describe the automatic refresh and `review layers refresh|status`, that the refresh leaves the tree and the PR clean, where wiki and memory are read from and the divergence mark, the layers block in payloads, the per-reviewer record and `unknown`, the chunked pass (plan, sequential run, merge, per-pass cap), the coverage check and the `complete` refusal with its quote waiver, and the estimate with its ceiling; they state plainly that the refresh uses no model and that `wiki enrich` is the only model step and is never automatic; the docs build passes. [verify: exec `bun test src/docs && mkdocs build --strict -f docs/mkdocs.yml`]
- AC14: Live: a managed review of PR 7659 on a fresh worktree of its head, started with one command, ends with `layers.json` showing `graphCommit` equal to the PR head and a clean worktree; the 753 dropped files are covered by a finished chunk sequence (or the operator's waiver) and `keryx review coverage` reports zero uncovered files; at least 12 of the 18 reviewers show non-zero graph or wiki use in `layersUsed` (`unknown` counted separately); and `keryx review compare-reference` against the Claude report reproduces no fewer items than the 12.10 run of flow 428 (4 of 19). Counts, chunk count, duration and estimate versus actual tokens are recorded next to the 12.10 run. [verify: judged]
- AC15: Control: the same flow on PR 7840 records a graph commit equal to its head, zero uncovered files, and raises no major finding that the operator rejects; the operator signs. [verify: judged]
