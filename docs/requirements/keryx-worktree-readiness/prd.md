# PRD · Готовность worktree
Version: 0.1.2

## Проблема

1. **Голый worktree.** `git worktree add` даёт рабочую копию без `.env`-файлов (их нет в git), без `node_modules` и с той же конфигурацией портов, что у основного checkout. Тесты и dev-сервер не поднимаются, два worktree дерутся за один порт. Установка зависимостей с нуля занимает минуты.
2. **Неполная память в worktree.** В git лежит только часть `.metaproject/`. Закоммиченные записи памяти (`.metaproject/memory/`) приходят с веткой, но незакоммиченные уроки основного checkout, индекс и эмбеддинги памяти, `runtime/`, `data/review-active/`, `data/learning/`, `data/ac-check/`, артефакты gdctx/gdwiki и история проверок в новый worktree не попадают. Хранилища памяти (`src/memory/store.ts:48`), flows (`src/flow/store.ts:8`) и активного ревью (`src/review/active-review.ts:9`) берут путь от текущего каталога. Агент в новом worktree не видит свежих уроков, а его собственные выводы оседают в копии, которую потом удаляют. Исключения уже есть: журнал решений идёт в основной checkout (`src/decisions/store.ts:26-36`), шина и номера flow — в общий git-каталог (`src/bus/paths.ts:64`, `src/flow/allocation.ts:53-69`). Общего правила нет.
3. **Конфликты обнаруживаются поздно.** Параллельные задачи правят одни и те же файлы. Ни keryx, ни Desktop не показывают пересечения до слияния. `git merge-tree` нигде не используется. В `flow.json` нет головной ветки и пути worktree, поэтому соседние задачи нельзя сопоставить.
4. **Чужие падения засчитываются задаче.** Падения, которые были в `main` до начала задачи, и нестабильные тесты выглядят как регрессия этой задачи. Базовая линия `keryx health` (`src/health/baseline.ts`) хранит оценки, а не прохождение тестов. Повтора упавших тестов нет.

## Цель

Новый worktree готов к работе одной командой и пользуется той же памятью, что основной checkout. Перед слиянием видно, с чем будет конфликт. Проверки задачи сравниваются с базовым коммитом, а не с нулём.

## Кто пользуется

| Пользователь | Сценарий |
|---|---|
| Владелец, ведущий несколько flow | `keryx worktree create flow-512` — через минуту в worktree проходят тесты, dev-сервер на своём порту, память та же |
| Агент или подагент в worktree | При старте получает корень worktree и путь к его `.metaproject/index.md`; `keryx memory search` находит уроки основного checkout |
| Ревьюер перед слиянием | Видит «main ушёл на 14 коммитов, конфликт в `src/a.ts`, этот файл правит ещё flow 509» |
| Исполнитель задачи | Получает «было 36 падений, стало 37 — новое: `rewind.test.ts > restores`» вместо 37 падений |

## Требования

**R1. Создание и подготовка.** `keryx worktree create <name>` создаёт worktree от указанной базы (по умолчанию `origin/main`), выполняет подготовку и выводит путь. `keryx worktree prepare` делает то же для уже существующего worktree. Повторный запуск безопасен.
Verification: exec `bun test src/worktree`

**R2. Файлы окружения.** Подготовка копирует из основного checkout файлы по списку проекта (по умолчанию найденные `.env*`, кроме `.example`, `.sample`, `.template`). Скопированные файлы не попадают в коммит: каждый проверяется `git check-ignore`, неигнорируемый не копируется и называется в выводе.
Verification: exec `bun test src/worktree/env-files.test.ts`

**R3. Зависимости.** Каталоги зависимостей из конфигурации (по умолчанию `node_modules`) копируются copy-on-write (`cp -c` на APFS, `cp --reflink=auto` на Linux). При совпадении хеша lock-файлов установка пропускается, иначе запускается команда установки проекта поверх копии. Без поддержки CoW копирование не выполняется, запускается установка.
Verification: exec `bun test src/worktree/deps.test.ts`

**R4. Порты.** Конфигурация называет порты (`web`, `api` …). Подготовка выделяет каждому worktree свободные порты из диапазона, записывает их в журнал клона (общий git-каталог) и в файл окружения worktree. Порт, занятый живым worktree, не выдаётся повторно. Удалённый worktree освобождает свои порты.
Verification: exec `bun test src/worktree/ports.test.ts`

**R5. Ссылка на metaproject.** Команда владельца (`keryx worktree create` или `keryx worktree link`) записывает явную связь worktree с домашним checkout после проверки, что оба принадлежат одному клону. В связанном worktree общие хранилища из таблицы политики (спецификация §5.2) читаются и из worktree, и из дома. Запись всегда локальная. В дом данные попадают только командой владельца `keryx worktree promote` после просмотра. Без связи поведение не меняется. Связь не выводится из соседства каталогов и не наследуется worktree, которые keryx создаёт сам (подагенты, `trigger run`).
Verification: exec `bun test src/worktree/metaproject-link.test.ts`

**R6. Агенту — корень и индекс.** Сессия, подагент и внешний агент, запущенные в worktree, получают в стартовом контексте абсолютный корень worktree и путь к его `.metaproject/index.md`; если worktree связан — ещё путь домашнего checkout с пометкой «только чтение». `keryx doctor` показывает связь и её исправность.
Verification: judged

**R7. Головная ветка flow.** `flow.json` хранит головную ветку и (если есть) путь worktree flow. Поля заполняются при `keryx worktree create --flow <id>` и при `keryx flow start` в worktree.
Verification: exec `bun test src/flow/schema.test.ts`

**R8. Проверка конфликтов.** `keryx worktree check [--target <ref>] [--json]` сообщает: на сколько коммитов цель ушла от базы ветки; файлы, которые дадут конфликт при слиянии (пробное слияние без изменения рабочей копии); открытые flow и PR, чьи ветки правят те же файлы. Desktop показывает результат в деталях flow и в футере сессии.
Verification: exec `bun test src/worktree/merge-check.test.ts`

**R9. Базовая линия проверок.** При `keryx flow start` (и по `keryx test baseline capture`) команды проверок проекта выполняются один раз на базовом коммите в отдельной временной копии. Результат хранится по flow. Проверка задачи сообщает «было N, стало M» и список новых падений. Проверка блокирует, только если падений стало больше или появились новые имена.
Verification: exec `bun test src/testing/baseline.test.ts`

**R10. Нестабильные тесты.** Красный тестовый прогон повторяется один раз. Если повтор прошёл, все упавшие тесты помечаются «нестабильный» и не блокируют. Если при повторе упал другой набор, нестабильными считаются тесты, упавшие только в одном из прогонов; тесты, упавшие в обоих, остаются падением. Все нестабильные тесты называются в отчёте.
Verification: exec `bun test src/testing/flaky.test.ts`

## Критерии выпуска

- На клоне keryx `keryx worktree create demo` заканчивается меньше чем за 60 с на APFS с готовым `node_modules`; `bun test src/lib` в новом worktree запускается без установки.
- Два worktree, созданные подряд, получают разные порты `web`; удаление первого освобождает его порт.
- В worktree с записанной связью `keryx memory search "<незакоммиченный урок основного checkout>"` находит урок с пометкой источника; в worktree без связи — нет (поведение прежнее). Новый урок из worktree появляется в доме только после `keryx worktree promote`.
- Ветка, правящая файл, который изменён в `origin/main` после её базы, получает в `keryx worktree check` этот файл в списке конфликтов. Второй flow, правящий тот же файл, назван в пересечениях.
- На ветке с одним заранее падающим тестом в `main` проверка задачи сообщает «было 1, стало 1» и не блокирует. Новое падение блокирует и называется.

## Как оценить пользу после выпуска

- **Время до первого зелёного прогона в новом worktree.** Владелец замеряет на трёх ближайших flow время от создания worktree до первого `bun test` без ошибок окружения. Наблюдение: метки времени в журнале flow.
- **Конфликты при слиянии.** За месяц владелец считает PR, где конфликт обнаружен только при слиянии, и сравнивает с предыдущим месяцем. Наблюдение: история PR и журналы flow.
- **Ложные регрессии.** not measured — до выпуска нет записи, сколько падений было чужими; после выпуска их число видно в отчётах, но сравнить не с чем.

## Риски

| Риск | Что делаем |
|---|---|
| `.env` с секретами копируется не туда | Только по списку проекта, только в worktree того же клона, только если файл игнорируется git; содержимое не выводится и не логируется |
| Общая память портится при одновременной записи из нескольких worktree | Автоматической записи в дом нет; `promote` пишет под файловой блокировкой, как у номеров flow |
| Уроки остаются в удалённом worktree | `keryx worktree remove` предупреждает о непереносённых записях и предлагает `promote` |
| Противоречие будущему SAC RP-08 | Связь создаёт владелец после проверки идентичности клона; дом только читается; публикация в дом — явная команда (спецификация §5.4) |
| Пробное слияние требует git ≥ 2.38 | При старом git проверка сообщает «нет точного ответа» и даёт только список пересекающихся файлов |
| Базовая линия дорогая | Выполняется один раз на flow, в фоне, с тайм-аутом; без неё проверка работает как сейчас |
| Метка «нестабильный» скрывает реальную гонку | Не скрывает: тест назван в отчёте, решение остаётся человеку |

## Рекомендация

Начать с подготовки и ссылки на metaproject (R1–R6): без них параллельная работа в worktree стоит дороже всего. Затем головная ветка и проверка конфликтов (R7–R8). Базовую линию и нестабильные тесты (R9–R10) делать последними: они меняют гейты flow и требуют аккуратной совместимости.
