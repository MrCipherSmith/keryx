# PRD · Готовность worktree
Version: 0.2.0

## Проблема

1. **Голый worktree.** `git worktree add` даёт рабочую копию без `.env`-файлов (их нет в git), без `node_modules` и с той же конфигурацией портов, что у основного checkout. Тесты и dev-сервер не поднимаются, два worktree дерутся за один порт. Установка зависимостей с нуля занимает минуты.
2. **Неполная память в worktree.** В git лежит только часть `.metaproject/`. Закоммиченные записи памяти (`.metaproject/memory/`) приходят с веткой, но незакоммиченные уроки основного checkout, индекс и эмбеддинги памяти, `runtime/`, `data/review-active/`, `data/learning/`, `data/ac-check/`, артефакты gdctx/gdwiki и история проверок в новый worktree не попадают. Хранилища памяти (`src/memory/store.ts:48`), flows (`src/flow/store.ts:8`) и активного ревью (`src/review/active-review.ts:9`) берут путь от текущего каталога. Индекс памяти в новом worktree пуст, пока его не перестроят. Агент не всегда знает абсолютный корень worktree и путь к его `.metaproject/index.md`. Его выводы оседают в копии, которую потом удаляют. Пользовательская область (`~/.keryx/memory`, обучение `scope: "user"`) уже есть, но пути туда из worktree нет, кроме `keryx learn promote` для обучения.
3. **Конфликты обнаруживаются поздно.** Параллельные задачи правят одни и те же файлы. Ни keryx, ни Desktop не показывают пересечения до слияния. `git merge-tree` нигде не используется. В `flow.json` нет головной ветки и пути worktree, поэтому соседние задачи нельзя сопоставить.
4. **Чужие падения засчитываются задаче.** Падения, которые были в `main` до начала задачи, и нестабильные тесты выглядят как регрессия этой задачи. Базовая линия `keryx health` (`src/health/baseline.ts`) хранит оценки, а не прохождение тестов. Повтора упавших тестов нет.

## Цель

Новый worktree готов к работе одной командой: окружение, зависимости, порты, перестроенные индексы, агент знает корень и index. Выводы, сделанные в worktree, не теряются при его удалении. Перед слиянием видно, с чем будет конфликт. Отчёт о проверках задачи сравнивает их с базовым коммитом, а не с нулём.

## Кто пользуется

| Пользователь | Сценарий |
|---|---|
| Владелец, ведущий несколько flow | `keryx worktree create flow-512` — через минуту в worktree проходят тесты, dev-сервер, запущенный через `keryx worktree exec` или Desktop, получает свой порт, индекс памяти построен |
| Агент или подагент в worktree | При старте получает корень worktree и путь к его `.metaproject/index.md`; `keryx memory search` работает по записям ветки |
| Ревьюер перед слиянием | Видит «main ушёл на 14 коммитов, конфликт в `src/a.ts`, этот файл правит ещё flow 509» |
| Исполнитель задачи | Видит в отчёте «было 36 падений, стало 37 — новое: `rewind.test.ts > restores`» вместо 37 падений |

## Требования

**R1. Создание и подготовка.** `keryx worktree create <name>` создаёт worktree от указанной базы (по умолчанию `origin/main`), выполняет подготовку и выводит путь. `keryx worktree prepare` делает то же для уже существующего worktree. Повторный запуск безопасен.
Verification: exec `bun test src/worktree`

**R2. Файлы окружения.** Подготовка копирует из основного checkout файлы по списку проекта (по умолчанию найденные `.env*`, кроме `.example`, `.sample`, `.template`). Скопированные файлы не попадают в коммит: каждый проверяется `git check-ignore`, неигнорируемый не копируется и называется в выводе.
Verification: exec `bun test src/worktree/env-files.test.ts`

**R3. Зависимости.** Каталоги зависимостей из конфигурации (по умолчанию `node_modules`) копируются copy-on-write (`cp -c` на APFS, `cp --reflink=auto` на Linux). При совпадении хеша lock-файлов установка пропускается, иначе запускается команда установки проекта поверх копии. Без поддержки CoW копирование не выполняется, запускается установка.
Verification: exec `bun test src/worktree/deps.test.ts`

**R4. Порты.** Конфигурация называет порты (`web`, `api` …). Подготовка выделяет каждому worktree свободные порты из диапазона, записывает их в журнал клона (общий git-каталог) и в файл окружения в git-каталоге worktree. Порт, занятый живым worktree, не выдаётся повторно. Удалённый worktree освобождает свои порты. Порты получают команды, запущенные через Desktop, `keryx worktree exec -- <cmd>` или после `eval "$(keryx worktree env)"` в терминале; команда, запущенная в терминале без них, портов не получает.
Verification: exec `bun test src/worktree/ports.test.ts`

**R5. Metaproject в worktree.** Подготовка перестраивает в worktree производные индексы, которых нет в git (по умолчанию индекс памяти), из файлов ветки. Данные metaproject и хранилища другого checkout keryx не читает и не пишет; единственное чтение из основного checkout — копирование перечисленных `.env`-файлов и зависимостей при `prepare` (R2, R3). Выводы worktree (незакоммиченные записи памяти, принятые записи обучения) владелец переносит в пользовательскую область командой `keryx worktree promote` после просмотра; `keryx worktree remove` не удаляет worktree с непереносёнными записями без `--force`.
Verification: exec `bun test src/worktree/metaproject.test.ts`

**R6. Агенту — корень и индекс.** Сессия, подагент и внешний агент, запущенные в worktree, получают в стартовом контексте абсолютный корень worktree и путь к его `.metaproject/index.md`. Существующая проверка `worktrees` в `keryx doctor` показывает метку checkout, порты и состояние подготовки.
Verification: judged

**R7. Головная ветка flow.** `flow.json` хранит головную ветку и (если есть) путь worktree flow. Поля заполняются при `keryx worktree create --flow <id>` и при `keryx flow start` в worktree.
Verification: exec `bun test src/flow/schema.test.ts`

**R8. Проверка конфликтов.** `keryx worktree check [--target <ref>] [--json]` сообщает: на сколько коммитов цель ушла от базы ветки; файлы, которые дадут конфликт при слиянии (пробное слияние без изменения рабочей копии); открытые flow и PR, чьи ветки правят те же файлы. Desktop показывает результат в деталях flow и в футере сессии.
Verification: exec `bun test src/worktree/merge-check.test.ts`

**R9. Базовая линия проверок (только отчёт).** При `keryx flow start` (и по `keryx test baseline capture`) команды проверок проекта выполняются один раз на базовом коммите в отдельной временной копии. Результат хранится по flow. Отчёт сообщает «было N, стало M», список новых падений и признак `regressed`. Пакет ничего не блокирует по этому отчёту: виды критериев сегодня только сообщаются (`src/flow/ac-kinds.ts`), а право гейтить по `exec` есть только у будущего W1 слоя приёмки после гейта G1.
Verification: exec `bun test src/testing/baseline.test.ts`

**R10. Нестабильные тесты.** Красный тестовый прогон повторяется один раз. Если повтор прошёл, все упавшие тесты помечаются «нестабильный» и не считаются падением в отчёте. Если при повторе упал другой набор, нестабильными считаются тесты, упавшие только в одном из прогонов; тесты, упавшие в обоих, остаются падением. Все нестабильные тесты называются в отчёте. Как и R9, это только отчёт.
Verification: exec `bun test src/testing/flaky.test.ts`

## Критерии выпуска

- На клоне keryx `keryx worktree create demo` заканчивается меньше чем за 60 с на APFS с готовым `node_modules`; `bun test src/lib` в новом worktree запускается без установки.
- Два worktree, созданные подряд, получают разные порты `web`; удаление первого освобождает его порт.
- После `create` в worktree построен индекс памяти; `keryx memory search` находит закоммиченную запись ветки без ручного `keryx memory index`. Незакоммиченная запись worktree попадает в `~/.keryx/memory` только после `keryx worktree promote`; рабочая копия основного checkout при этом не меняется.
- Ветка, правящая файл, который изменён в `origin/main` после её базы, получает в `keryx worktree check` этот файл в списке конфликтов. Второй flow, правящий тот же файл, назван в пересечениях.
- На ветке с одним заранее падающим тестом в `main` отчёт сообщает «было 1, стало 1», `regressed: false`. Новое падение даёт `regressed: true` и называется. Поведение `flow check-ac`, `flow ac confirm` и `flow complete` не меняется.

## Как оценить пользу после выпуска

- **Время до первого зелёного прогона в новом worktree.** Владелец замеряет на трёх ближайших flow время от создания worktree до первого `bun test` без ошибок окружения. Наблюдение: метки времени в журнале flow.
- **Конфликты при слиянии.** За месяц владелец считает PR, где конфликт обнаружен только при слиянии, и сравнивает с предыдущим месяцем. Наблюдение: история PR и журналы flow.
- **Ложные регрессии.** not measured — до выпуска нет записи, сколько падений было чужими; после выпуска их число видно в отчётах, но сравнить не с чем.

## Риски

| Риск | Что делаем |
|---|---|
| `.env` с секретами копируется не туда | Только по списку проекта, только в worktree того же клона, только если файл игнорируется git; содержимое не выводится и не логируется |
| Пользовательская память портится при одновременном `promote` из нескольких worktree | `promote` пишет под файловой блокировкой, как у номеров flow |
| Уроки остаются в удалённом worktree | `keryx worktree remove` перечисляет непереносённые записи и без `--force` не удаляет |
| Расхождение с будущим SAC RP-08 | Пакет не читает и не пишет данные metaproject других checkout (копирование `.env` и зависимостей по команде владельца — не данные оверлея) и не заявляет соответствия RP-08; оставшееся расхождение названо в спецификации §5.4 |
| Пробное слияние требует git ≥ 2.38 | При старом git проверка сообщает «нет точного ответа» и даёт только список пересекающихся файлов |
| Базовая линия дорогая | Выполняется один раз на flow, в фоне, с тайм-аутом; без неё всё работает как сейчас |
| Отчёт примут за гейт | В выводе и в Desktop он подписан как отчёт; гейтить может только W1 слоя приёмки |
| Метка «нестабильный» скрывает реальную гонку | Не скрывает: тест назван в отчёте, решение остаётся человеку |

## Рекомендация

Начать с подготовки и metaproject в worktree (R1–R6): без них параллельная работа в worktree стоит дороже всего. Затем головная ветка и проверка конфликтов (R7–R8). Базовую линию и нестабильные тесты (R9–R10) делать последними, как отчёт; превращать их в гейт — решение W1 слоя приёмки после G1.
