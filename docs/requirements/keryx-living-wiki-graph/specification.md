# Living Wiki + Graph — Specification
Version: 2.0.0

## 1. Идентичность модуля

LWG — не новый модуль, а сквозная возможность поверх двух существующих:
`gdgraph` (владеет графом) и `gdwiki` (владеет страницами). Код
распределяется так:

- `src/gdgraph/` — узлы `wiki-page`, ребро `describes`, контент-хэши,
  инкрементальная сборка (LWG-1, LWG-2, LWG-3).
- `src/wiki/freshness/` — новый подкаталог: очередь, классификация,
  распространение, отчёт (LWG-7…LWG-10).
- `src/wiki/` — provenance, управляемый блок, `refresh`, дельта-инрич
  (LWG-4, LWG-5, LWG-11, LWG-12).
- `src/sac/wiki-owner-writer.ts` — расширяется вторым видом intent
  (LWG-12, режим `--propose`).
- `src/health/` — метрика свежести (LWG-15).

## 1.1 Инвариант: независимость от политики VCS

Разные проекты обращаются с `.metaproject/` по-разному: keryx трекает почти
всё, vantage-frontend игнорирует целиком, а `src/commands/init.no-git.test.ts`
фиксирует, что проект вообще без git — поддерживаемое состояние. Поэтому:

> **Ни один механизм LWG не имеет права требовать, чтобы `.metaproject/`
> был под контролем версий, и ни один — чтобы git вообще существовал.**

Из этого следует разделение, которое легко спутать:

- **Версия и provenance страницы** (`Version`, `VerifiedAt`/`VerifiedScope`,
  `## Changelog`) живут **внутри файла страницы**. Они путешествуют вместе с
  ней, работают в любом режиме и никогда не выносятся во внешнее хранилище.
  Это и есть «версионирование внутри metaproject».
- **Детект свежести** имеет два эквивалентных по назначению механизма (§4.1):
  git-ревизия там, где git есть, и снимок контент-хэшей там, где его нет.
  Второй не хуже, он дороже.
- **История прошлых тел страницы** — единственное, что LWG **не**
  реализует сам. См. §1.2: собственный журнал ревизий сознательно отвергнут.

### 1.2 Три режима работы и почему нет четвёртого

**Режим A — вики версионируется в основном репозитории** (так устроен keryx).
Доступно всё: история, `git blame` по prose, ревью дельт в PR, CI-джоба.

**Режим B — `.metaproject/` в отдельном репозитории или submodule.**
Рекомендуемый ответ для проектов, которые не хотят видеть вики в diff
основного дерева. Даёт ту же историю и тот же шаринг, что режим A, ценой
одной дополнительной операции синхронизации. `VerifiedAt` при этом
по-прежнему ссылается на ревизию **основного** репозитория — того, чей код
описывается, — и потому от политики по `.metaproject/` не зависит.

**Режим C — вики локальная (игнорируется, или git отсутствует).**
Работают: детект свежести (через `VerifiedScope`), бэклог, детерминированный
`refresh`, валидация, дельта-инрич. Не работают: история прошлых тел,
командный шаринг, CI-джоба. Отчёт обязан объявлять это в `limitations`
(`not-a-git-repository`), чтобы пустой результат не читался как «всё свежо».

**Четвёртого режима — собственного журнала ревизий внутри
`.metaproject/data/wiki/history/` — здесь нет намеренно.** Он выглядит как
решение режима C, но им не является: в режиме C эта директория тоже
локальна, поэтому журнал дал бы undo на одной машине и ничего из того, ради
чего история нужна — ни ревью, ни командного доступа, ни CI. Цена (рост
хранилища, собственные retention и GC, собственные diff/blame инструменты,
дублирование того, что git уже делает лучше) платится в режимах A и B, где
выигрыш равен нулю. Проекту, которому нужна история, дешевле перейти в
режим B, чем получить второй, худший git внутри metaproject.

## 2. Структура хранения

```text
.metaproject/
  wiki/
    <folder>/<slug>.md            # страницы; формат — §4
  data/
    wiki/
      freshness-queue.jsonl       # LWG-9, append-only, ротируемый
      freshness/
        latest.json               # последний отчёт (схема §7.2)
        latest.md                 # человекочитаемая проекция
      enrich-resume.json          # существует; completedNodeHashes
    gdgraph/
      storage/
        nodes.jsonl               # существует; НЕ изменяется вики-слоем
        edges.jsonl               # существует; НЕ изменяется вики-слоем
        symbols.jsonl             # существует (символьный слой)
        calls.jsonl               # существует
        wiki-pages.jsonl          # LWG-1: узлы страниц (новый слой)
        describes.jsonl           # LWG-1: рёбра describes (новый слой)
        build-manifest.json       # LWG-2/3: contentHash + mtimeMs на файл
```

Очередь — `.jsonl`, потому что писатель (git-хук) должен быть
append-only и не читать файл целиком. Ротация: при превышении 10 000 строк
или 5 МБ хук переименовывает файл в `freshness-queue.1.jsonl`; разбор
читает оба.

### 2.1 Что из этого версионируется

Правило проекта, а не закон системы. keryx трекает 2336 файлов под
`.metaproject/`, и игнорирует узкий, осмысленный класс: производные,
крупные, перегенерируемые артефакты — `storage/`, `raw/`, `queries/`,
`summaries/`, `artifacts/`, `history/`, `logs/`, индексы и эмбеддинги.
`build-manifest.json` и отчёты `data/wiki/freshness/` попадают в этот класс;
страницы вики с их `VerifiedAt` — нет, они версионируются как контент.
Проект вправе решить иначе.

**Но для инкрементальной сборки это решение почти безразлично**, и на это
не стоит рассчитывать как на рычаг. Сборке нужен не манифест, а
**предыдущий граф**, из которого переносятся неизменённые узлы и рёбра
(`nodes.jsonl`, `edges.jsonl`, `symbols.jsonl`, `calls.jsonl` — в keryx на
сегодня 11.8 МБ, из них 9.7 МБ приходится на `calls.jsonl`). Манифест без
этих артефактов бесполезен: копировать не из чего. Поэтому:

- **В CI** механизм ускорения — кэш сборки между запусками, ключуемый по
  содержимому манифеста, а не git. Хранить 12 МБ производных данных в
  истории репозитория ради этого — плохой размен независимо от политики
  версионирования.
- **На свежем клоне** первая сборка полная всегда. Это не деградация: без
  предыдущего графа полная сборка — единственно возможная.
- **Перенос манифеста между машинами безвреден.** `mtimeMs` машинно-локален,
  но алгоритм §3.4 при расхождении `mtimeMs` сверяет `contentHash`, поэтому
  чужой манифест приводит к более медленной, а не к неверной сборке.

## 3. Модель данных: граф

### 3.1 Вики-слой — отдельный слой, а не новые виды узлов

**Исправлено по итогам реализации (flow 223, T7).** Версии 1.0–1.4 этой
спецификации предписывали добавить `kind: "wiki-page"` в `GraphNode` и
`kind: "describes"` в `GraphEdge`, то есть класть записи вики прямо в
`nodes.jsonl` и `edges.jsonl`. Это привело бы к регрессу.

Пять продакшн-мест считают исходником **любой** узел, кроме `asset`:
`validModuleNames` и `collectGraphWikiCandidates`
(`src/wiki/service.ts:365,412`), `computeModuleKeyFiles`
(`src/wiki/collect.ts:97`) и `src/commands/update.ts:869`. Узел страницы в
`nodes.jsonl` был бы сгруппирован `moduleNameFromProjectPath` в
несуществующий модуль `.metaproject/wiki/components` и **отравил бы
множество модулей**, по которому `wikiPruneOrphans` и
`src/sac/lifecycle-flag.ts` решают, что осиротело. Кроме того, сборка уже
следует правилу «аддитивный слой не переписывает легаси-артефакты» — так
устроен символьный слой (`src/gdgraph/build.ts`, enrichment после
неизменённой файловой сборки).

Поэтому вики — **отдельный слой**, по образцу символьного:

```ts
export type WikiPageNode = {
  id: string;          // "wiki:components/src-ctx.md"
  path: string;        // "components/src-ctx.md"
  title: string;
  pageType: string;
  status: string | null;
  version: string | null;
  undecidable: boolean; // describe-множество пусто: не свежая и не сирота
};

export type DescribesEdge = {
  id: string;
  from: string;        // WikiPageNode.id
  to: string;          // путь файлового GraphNode
  pattern: string;
  origin: DescribesOrigin;
};

export type WikiLayer = { pages: WikiPageNode[]; describes: DescribesEdge[] };
```

`GraphData` получает опциональные `wikiPages?` и `describes?` — ровно тот же
контракт, что у `symbols?`/`calls?`: отсутствуют ⇒ просто опущены, это не
ошибка. `GraphNode` и `GraphEdge` **не меняются вовсе**.

Обратный обход («какие страницы описывают файл X») строится индексом по
`DescribesEdge.to`, отдельного обратного ребра не заводится.

### 3.2 Контент-хэши — в манифест, не в узлы

`contentHash`/`mtimeMs` тоже не добавляются в `GraphNode`: это изменило бы
`nodes.jsonl` для всех существующих потребителей ради данных, которые нужны
одному будущему (инкрементальная сборка, LWG-3). Они пишутся в
`storage/build-manifest.json` как `FileFingerprint { path, contentHash,
mtimeMs }`.

Стоимость близка к нулю: `buildGraph` уже читает содержимое каждого файла в
`fileRecords` (`src/gdgraph/build.ts:104-107`), поэтому хэширование не
добавляет ни одного обращения к диску.

### 3.3 Источники ребра `describes`

1. **`frontmatter`** — поле `Describes:` (§4.1). Глоб-паттерны разрешаются
   относительно корня проекта.
2. **`related-code`** — ссылки на файлы в секции `## Related Code`.
3. **`key-files`** — результат `computeModuleKeyFiles` (`src/wiki/collect.ts`),
   уже используемый `computePageNodeHash`. Применяется только если для
   страницы нет источников 1 и 2.

**Обязательное переиспользование.** Множество валидных модулей берётся
**только** из `validModuleNames` (`src/wiki/service.ts:358`), а группировка
пути в модуль — только из `moduleNameFromProjectPath`. Эти функции были
специально выделены в отдельное, меньшее чтение (RP-13 FR3+FR4, flow 168,
Phase 2) именно ради того, чтобы «второй потребитель никогда не выводил
группировку модулей второй, потенциально расходящейся реализацией» — сегодня
их два (`wikiPruneOrphans` и `src/sac/lifecycle-flag.ts`), LWG становится
третьим. Собственный вывод множества модулей в LWG запрещён.

### 3.3.1 Категория `orphan` — не новая, а расширение существующей

`wikiPruneOrphans` (`src/wiki/service.ts:306`) уже находит страницы, чей
модуль исчез из графа, и уже проводит нужную границу: неизменённые
черновики удаляются, `accepted`/правленные руками — возвращаются в
`orphanedAccepted` и никогда не удаляются молча. LWG **не реализует эту
логику заново**. Категория `orphan` в отчёте свежести — проекция уже
существующего `WikiPruneResult.orphanedAccepted`, дополненная тем, чего там
нет: причинной цепочкой и уверенностью. Единственное расширение поведения —
охват: `wikiPruneOrphans` сканирует только `components/`, а отчёт покрывает
все папки вики (см. §4.7).

### 3.3.2 Посторона при недоступном графе

`validModuleNames` возвращает `undefined`, а **не** пустое множество, когда
граф ещё не собран, с явным обоснованием в коде: пустое множество сделало бы
осиротевшим всё подряд, что противоположно консервативной, report-only
позиции. LWG обязан унаследовать это правило целиком:

> **Недоступный, пустой или неразобранный граф означает «пока нечего
> сообщать», а не «всё устарело».**

Практически: при `validModuleNames() === undefined` отчёт свежести
возвращает пустой список `pages`, а в `limitations` — `graph-stale` с
пояснением. Категории `orphan` и `undocumented` в этом состоянии не
выдаются вообще: обе выводятся из отсутствия узла в графе, а отсутствующий
граф — не доказательство отсутствия узла (AC-24).

### 3.4 Инкрементальная сборка (LWG-3)

`build-manifest.json` хранит `{path, contentHash, mtimeMs, language}` для
каждого файла прошлой сборки. Алгоритм:

1. Обойти дерево источников, собрать `{path, mtimeMs}`.
2. Файл считается неизменённым, если `mtimeMs` совпадает с манифестом.
   При расхождении `mtimeMs` — прочитать и сравнить `contentHash`
   (mtime меняется чаще, чем содержимое: `git checkout`, `touch`).
3. Перепарсить только файлы с изменившимся `contentHash`, плюс файлы, чьи
   разрешённые импорты указывали на добавленный/удалённый путь.
4. Узлы и рёбра неизменённых файлов перенести из прошлого графа как есть.

**Обязательство корректности:** инкрементальная сборка обязана давать граф,
побайтово эквивалентный полной сборке после нормализации порядка (AC-4).
Расхождение — дефект, а не допустимый компромисс.

`--full` принудительно выполняет полную сборку и переписывает манифест.
Отсутствующий или повреждённый манифест — не ошибка: молча падаем на полную
сборку.

## 4. Модель данных: страница

### 4.1 Фронтматтер

Существующие поля (`WikiPage`, `src/wiki/types.ts`): `Version`, `Type`,
`Status`. Добавляются:

```markdown
# Flow Canvas
Version: 1.4.0
Type: component
Status: accepted
VerifiedAt: 9f2c1ab3d4e5f60718293a4b5c6d7e8f90a1b2c3
Describes:
  - src/core/flow/**
  - src/core/flow/canvas/FlowCanvas.tsx
```

- **`VerifiedAt`** (LWG-4) — полный git sha ревизии **основного**
  репозитория, против которой страницу последний раз подтверждали. Ставится
  `refresh`, `enrich` и ручной командой `wiki verify`.
- **`VerifiedScope`** — снимок контент-хэшей области `Describes` на тот же
  момент, в форме `sha256:<хэш>`, вычисляемый существующим
  `computePageNodeHash` (`src/wiki/staleness.ts:51-77`), обобщённым с
  «top-6 ключевых файлов» на всю разрешённую область `Describes`.
- **`Describes`** — необязательный явный список путей/глобов.

**Приоритет и режимы (см. §1.1).** Оба поля пишутся всегда, когда доступны,
и читаются по правилу:

1. Есть git и есть `VerifiedAt` → свежесть определяется как непустой
   результат `git log <VerifiedAt>..HEAD -- <разрешённые пути>`. Дёшево,
   человекочитаемо, даёт число «на сколько коммитов отстала».
2. Git недоступен, либо `VerifiedAt` указывает на ревизию, которой нет в
   текущей истории (перебазирование, shallow clone, смена репозитория) →
   свежесть определяется сравнением `VerifiedScope` с пересчитанным
   снимком. Ответ бинарный: «менялась» / «не менялась», без числа коммитов
   и без классификации по §5, поэтому все затронутые страницы получают
   `review-suggested`, а не `must-refresh`.
3. Нет ни того, ни другого → категория `unknown`.

Отсутствие обоих полей означает «никогда не проверялась» и даёт категорию
`unknown`, а **не** «свежая» (AC-20). Расхождение между двумя механизмами не
является ошибкой: путь 2 строго грубее пути 1 и по построению может дать
ложное срабатывание там, где git-история показала бы `cosmetic`.

**Семантика, которую нельзя размывать:** `VerifiedAt` означает «код в области
`Describes` не менялся с этой ревизии», а не «текст страницы верен». Вывод
любой команды обязан формулировать это как «не проверялась с ревизии X», а не
«актуальна».

### 4.2 Управляемый блок (LWG-5)

Секция `## Reference (from code graph)` (`src/wiki/service.ts:1100`)
оборачивается маркерами:

```markdown
<!-- keryx:reference:begin v=1 hash=<sha256 содержимого блока> -->
## Reference (from code graph)

### Public API
...
<!-- keryx:reference:end -->
```

Правила:

- Всё между маркерами — машинная территория. `refresh` заменяет регион
  целиком, **включая страницы со `Status: accepted`**.
- Всё вне маркеров принадлежит человеку и не изменяется детерминированным
  писателем никогда.
- `hash` в открывающем маркере — контрольная сумма содержимого блока на
  момент последней машинной записи. Несовпадение означает ручную правку внутри
  блока: `refresh` в этом случае **не перезаписывает молча**, а сообщает
  конфликт и требует `--force` (AC-9). Человек, отредактировавший машинную
  секцию, скорее всего знал, что делает.
- Страница без маркеров (все существующие сегодня) обрабатывается
  миграцией: `wiki migrate-markers` находит секцию по заголовку и
  расставляет маркеры, ничего не меняя в содержимом.

### 4.2.1 Основание: контракт уже записан, но код его не исполняет

Маркеры не вводят новое правило, а чинят существующее противоречие.
`.metaproject/skills/gdwiki/SKILL.md` в двух соседних пунктах одной
процедуры утверждает:

- шаг 4: «Leave the `## Reference` section untouched (**it is graph-owned and
  regenerated**)»;
- шаг 5: «Set `Status: accepted` … This marks the page human-owned;
  `keryx wiki collect --force` will **never overwrite it**».

Оба утверждения одновременно исполнимы только если «страница» и «секция
Reference» — разные единицы владения. Код такого различения не делает
(`writeCollectedPage` работает файлом целиком), поэтому документация обещает
регенерацию, которую рантайм выполнить не может. LWG-5 не отменяет правило
«accepted принадлежит человеку» — он вводит границу, без которой уже
записанный контракт «Reference принадлежит графу» неисполним.

### 4.2.2 Миграция: чего в корпусе может не быть

На корпусе keryx (42 страницы в `components/`) секцию `## Reference` имеет
41. `wiki migrate-markers` обязан:

- отсутствующую секцию **не создавать** — страница без Reference остаётся
  без управляемого блока и без `stale-reference`; создание секции задним
  числом изменило бы содержимое, чего миграция делать не вправе;
- отказаться и сообщить, если заголовок встречается более одного раза;
- быть идемпотентным: повторный прогон на уже размеченной странице не
  меняет ни байта (AC-25).

### 4.3 Классы prose (LWG-6)

- **Долгоживущие:** `## Overview`, `## Key concepts`.
- **Волатильные:** `## How it works`, `## Main flows`.

Дельта-инрич по умолчанию предлагает изменения только волатильных;
`--include-durable` снимает ограничение.

### 4.4 Anti-entropy якорь (LWG-13)

Абзац, обёрнутый в `<!-- keryx:human:begin -->` / `<!-- keryx:human:end -->`,
передаётся модели как контекст, но никогда не входит в редактируемую область.
Инрич, вернувший текст с изменённым якорем, считается неуспешным для этой
страницы.

### 4.4.1 Страницы, у которых нет описываемого кода

Механизм спроектирован вокруг страниц модулей, но вики состоит не только из
них. В самом keryx на сегодня: 42 страницы в `components/`, 7 в
`architecture/`, по одной-две в `testing/`, `templates/`, `decisions/` —
то есть **каждая пятая страница** не имеет модуля, из которого выводится
`describes`. Без явного правила все они навсегда осели бы в `unknown`, а
метрика M7 (`pagesFresh / pagesTotal`) оказалась бы структурно ограничена
сверху.

Правило: страница участвует в оценке свежести, **только** если её
`describes`-множество непусто. Иначе она получает `freshnessBasis:
"undecidable"` и:

- **не попадает** ни в `pages`, ни в знаменатель M7;
- попадает в отдельный счётчик `totals.pagesUndecidable` и в
  `limitations` с кодом `page-without-describes`.

Для таких страниц единственный способ участвовать — явный `Describes:` во
фронтматтере. Это осознанный выбор в пользу ручного, а не выведенного
сопоставления: у страницы `architecture/*` нет «своих» файлов, есть только
те, которые автор считает существенными, и угадывать их система не должна.

**Папки вне `WIKI_PAGE_TYPES`.** На диске существуют `testing/` и
`templates/`, которых нет в списке типов (`src/wiki/types.ts`). Ни
валидация, ни отчёт не вправе падать или молча пропускать такие папки:
страница из неизвестной папки обрабатывается как `undecidable` и
объявляется в `limitations` (AC-26).

### 4.5 Версионирование и история

- **patch** — механическое обновление Reference (`refresh`).
- **minor** — изменение prose (`enrich`, принятый proposal).
- **major** — смена типа страницы или структурная переработка.

Каждое изменение дописывает строку в `## Changelog` в формате
`- <version> - <что> (<rev или scope-хэш>)`. Эта запись — **и есть**
независимое от VCS версионирование: она внутри страницы, путешествует
вместе с ней и одинаково читается во всех трёх режимах §1.2. Она отвечает
на вопросы «когда последний раз трогали», «что именно поменяли — машину или
prose» и «против чего проверяли».

Чего она не даёт — прошлых тел страницы. Это осознанная граница, а не
пробел: собственный журнал ревизий внутри `.metaproject/` отвергнут в §1.2 с
разбором причин. В режимах A и B прошлые тела даёт VCS; в режиме C их нет, и
отчёт обязан это объявлять.

## 5. Классификация изменений (LWG-7)

Для каждого изменённого файла определяется один класс:

- **`added`** — файл появился.
- **`removed`** — файл удалён.
- **`moved`** — путь изменился при неизменном `contentHash`.
- **`signature`** — изменился набор или сигнатура экспортируемых символов.
- **`body`** — символы те же, содержимое тел изменилось.
- **`cosmetic`** — после нормализации (удаление комментариев и незначащих
  пробелов средствами уже подключённого tree-sitter) содержимое не изменилось.

**Источник сигнатур.** Символьный слой уже хранит их:
`SymbolNode.signature` (`src/gdgraph/types.ts`, поле `signature?: string`,
материализуется в `storage/symbols.jsonl` при активной capability
`gdgraph.treesitter`). Классификация `signature` vs `body` выполняется
сравнением множеств `{id, signature}` до и после — отдельного AST-диффа не
требуется.

**Деградация.** Если символьный слой недоступен (tree-sitter выключен),
классификатор обязан возвращать `body` для любого содержательного изменения
и `cosmetic` только при точном совпадении нормализованного текста. Тихо
выдавать `signature` без данных запрещено.

### 5.1 Класс → действие

- `cosmetic` → ничего. Ни записи в бэклог, ни бампа версии.
- `body` → `stale-prose` **только** для страниц, где изменённый символ
  упомянут в тексте prose; иначе ничего.
- `signature`, `added`, `removed` → `stale-reference` для всех страниц,
  описывающих файл, плюс `stale-prose` для страниц, упоминающих символ.
- `moved` → `stale-reference` плюс задача починки ссылок.

## 6. Распространение влияния (LWG-8)

Вход: множество изменённых файлов с классами. Выход: множество страниц с
категорией и цепочкой причин.

```text
frontier := изменённые файловые узлы
для каждого узла в frontier (BFS, по возрастанию расстояния):
    для каждого инцидентного ребра:
        если политика ребра (§6.1) разрешает распространение
           для класса изменения:
              добавить соседа в affected и в очередь
              записать причину: (сосед <- узел, ребро, класс)
```

Обход в обе стороны. Ограничение — политика ребра, а не фиксированное число
прыжков: приём взят у RepoDoc («the algorithm naturally discovers components
ordered by distance from the original change, avoiding arbitrary threshold
limits»).

### 6.1 Политика по типу ребра

- **`describes`** — распространяется всегда, в обе стороны. Это то самое
  ребро, ради которого построен LWG.
- **`imports`, входящие (зависящие от изменённого)** — распространяется для
  `signature`, `added`, `removed`; результат помечается ослабленно
  (`review-suggested`, не `must-refresh`), потому что зависящий модуль
  документируется своей страницей и мог не заметить изменения.
- **`imports`, исходящие (зависимости изменённого)** — не распространяется.
  Изменение потребителя не делает документацию зависимости неверной.
- **`asset`** — не распространяется.
- **`unresolved`** — не распространяется; фиксируется как причина неполноты в
  поле `limitations` отчёта.
- **Символьные `calls`** — распространяются для `signature` и `removed` на
  один уровень вызывающих, чтобы поймать страницы, описывающие вызывающий
  модуль.

### 6.2 Затухание

Каждый шаг понижает уверенность: `must-refresh` → `review-suggested` →
`fyi`. Ниже `fyi` распространение прекращается. Это ограничивает взрывной
рост множества на сильносвязанных графах без введения искусственного лимита
прыжков.

## 8. CLI и skill-поверхность

Все команды регистрируются в `src/standard/command-registry.ts` (единый
источник правды для агент-вызываемых команд) с честным флагом `json`.

- **`keryx wiki freshness [--since <rev>] [--json] [--category <c>]`**
  (LWG-10). Read-only. Разбирает очередь (или диапазон `--since`), строит
  отчёт, пишет `data/wiki/freshness/latest.{json,md}`. Код возврата всегда 0 —
  это отчёт, не гейт. Записи сортируются по убыванию `commitsBehind`:
  замер на корпусе keryx (`metrics-and-validation.md` §2.1) показал крайне
  перекошенное распределение — медиана 6, максимум 228, — при котором
  алфавитный или случайный порядок скрывает весь реальный долг в хвосте.
- **`keryx wiki refresh [--page <p>] [--from-queue] [--force] [--dry-run]`**
  (LWG-11). Детерминированно, без модели. Обновляет управляемые блоки, бампает
  patch, дописывает `## Changelog`, ставит `VerifiedAt`. `--force` нужен при
  несовпадении `hash` маркера.
- **`keryx wiki verify --page <p>`** (LWG-4). Ставит `VerifiedAt: HEAD` без
  изменения содержимого — «человек посмотрел и подтвердил».
- **`keryx wiki enrich --from-queue [--propose] [--include-durable]`**
  (LWG-12). Берёт только `stale-prose` из бэклога. `--propose` направляет
  результат в SAC вместо прямой записи.
- **`keryx wiki migrate-markers [--dry-run]`** (LWG-5). Разовая миграция.
- **`keryx gdgraph build [--full]`** (LWG-3). Инкрементальная по умолчанию.
- **`keryx wiki validate`** (LWG-14). Расширяется проверками §9.

Skill `gdwiki` (`.metaproject/skills/gdwiki/SKILL.md`) дополняется
маршрутом: «перед чтением страницы как контекста — свериться с
`data/wiki/freshness/latest.json`; страница из категории `stale-*` читается с
оговоркой». MCP: `wiki_freshness` как read-only ресурс, рядом с
существующими `wiki_query`/`wiki_ask`.

## 9. Валидация (LWG-14)

`wiki validate` дополняется правилами (все — детерминированные, без модели):

- каждая страница имеет `Version`; при наличии управляемого блока — и
  `VerifiedAt`;
- управляемый блок корректно открыт и закрыт, `v` известен, `hash` разобран;
- каждая цель `describes` существует на диске;
- внутренние ссылки `## Related Wiki` резолвятся в существующие страницы;
- `## Changelog` не содержит убывания версий;
- ни одна страница не помечена `accepted` без хотя бы одной непустой
  prose-секции.

Опциональный `--deep` добавляет проверку моделью: противоречит ли prose
текущему содержимому Reference. Дорогой, по умолчанию выключен, никогда не
входит в CI-гейт.

## 10. Точки интеграции

- **git-хуки и CI** — `ci-protocol.md`.
- **health** — метрика `wiki_freshness` (`fresh_pages / total_pages`) и
  `wiki_backlog_size` в `data/health/artifacts/latest.md`. По умолчанию
  **не** влияет на гейт (LWG-15); порог включается явно.
- **SAC** — `src/sac/wiki-owner-writer.ts` сегодня умеет ровно один сценарий:
  создать `decisions/sac-<id>.md` из принятого proposal. Добавляется второй
  вид intent — обновление существующей страницы: `persist()` применяет дельту
  prose к указанной странице, проходит тот же `guardOutput` с
  `target: "wiki"`, пишет receipt. Ограничение на авторитет
  (`owner`/`editor`) и идемпотентность переиспользуются как есть.
- **RP-13 (SAC lifecycle flag)** — `src/sac/lifecycle-flag.ts` уже потребляет
  тот же graph-diff сигнал в report-only режиме для workspaces, memory-entries
  и `wiki/decisions/*`. LWG — третий потребитель того же `validModuleNames`,
  с той же позицией «сообщать, не действовать». Два отчёта намеренно
  остаются раздельными: LWG отвечает за свежесть страниц относительно кода,
  RP-13 — за живучесть SAC-контента относительно исчезнувших компонентов.
  Общий у них только источник множества модулей.
- **flow/tasks** — бэклог свежести может открывать flow; связь односторонняя:
  LWG не читает состояние flow.
- **security** — любой новый путь записи в вики обязан проходить
  `guardOutput` + `prepareOutputForPersistence`, как это уже делают
  `writeCollectedPage` и `wiki-owner-writer`.

## 11. Acceptance criteria

- **AC-1.** Граф, собранный после LWG-1, содержит узел `wiki-page` для каждой
  страницы и хотя бы одно ребро `describes` для каждой страницы, у которой
  есть `Describes`, ссылки `## Related Code` или вычислимые ключевые файлы.
- **AC-2.** Граф, собранный предыдущей версией keryx (без новых полей),
  загружается без ошибок; отсутствие `contentHash` не приводит к падению.
- **AC-3.** Обратный запрос «страницы, описывающие файл X» возвращает
  корректное множество для файла, покрытого несколькими страницами.
- **AC-4.** Инкрементальная сборка после произвольного набора правок даёт
  граф, эквивалентный полной сборке (после нормализации порядка узлов и
  рёбер).
- **AC-5.** Коммит, изменяющий только комментарии и форматирование,
  классифицируется как `cosmetic` и порождает пустой бэклог.
- **AC-6.** Изменение сигнатуры экспортируемой функции порождает
  `stale-reference` для страницы её модуля и `stale-prose` для страницы, где
  имя функции встречается в prose.
- **AC-7.** Распространение влияния возвращает для каждой затронутой страницы
  непустую цепочку причин с указанием ребра и класса изменения.
- **AC-8.** `wiki refresh` обновляет управляемый блок на странице со
  `Status: accepted`, не изменяя ни одного байта вне маркеров (проверяется
  диффом).
- **AC-9.** `wiki refresh` на странице с ручной правкой внутри блока
  (несовпадение `hash`) завершается без записи и сообщает конфликт; с
  `--force` — перезаписывает.
- **AC-10.** `wiki refresh` не выполняет ни одного обращения к провайдеру
  модели (проверяется тестом с фейлящимся провайдером).
- **AC-11.** `wiki freshness` не изменяет ни одного файла вне
  `data/wiki/freshness/`.
- **AC-12.** Хук `post-commit` дописывает строку в очередь и завершается
  быстрее 50 мс на p95 на репозитории размера keryx.
- **AC-13.** Отчёт `--json` валиден по
  `schemas/freshness-report.schema.json`.
- **AC-14.** `wiki enrich --from-queue` обрабатывает только страницы из
  категории `stale-prose` и пропускает страницы, чей hash-гейт RLM сообщает
  «не изменилась».
- **AC-15.** `wiki enrich --propose` не пишет ни одной страницы напрямую;
  каждая предлагаемая правка становится proposal, а запись происходит только
  после `review --decision accepted`.
- **AC-16.** Абзац внутри `keryx:human` маркеров идентичен до и после
  инрича.
- **AC-17.** `wiki validate` падает на странице с оборванным управляемым
  блоком, с несуществующей целью `describes` и с убывающей версией в
  Changelog.
- **AC-18.** Метрика `wiki_freshness` присутствует в health-артефакте и по
  умолчанию не меняет вердикт гейта.
- **AC-19.** `wiki migrate-markers` на существующем корпусе расставляет
  маркеры, не изменяя содержимого секций (проверяется диффом: меняются только
  строки маркеров).
- **AC-20.** Страница без `VerifiedAt` и без `VerifiedScope` попадает в
  категорию `unknown`, а не считается свежей.
- **AC-21.** В репозитории без git (`init.no-git` сценарий) `wiki freshness`
  строит отчёт по `VerifiedScope`, не падает, и объявляет
  `not-a-git-repository` в `limitations`.
- **AC-22.** Страница с `VerifiedAt`, указывающим на отсутствующую в истории
  ревизию, обрабатывается путём 2 (§4.1) и не приводит к ошибке.
- **AC-23.** Ни один путь LWG не читает и не пишет ничего внутри `.git/`
  напрямую, кроме уже существующего `graphMaybeStale`; проверяется тестом на
  дереве без `.git/`.
- **AC-24.** При несобранном графе (`validModuleNames() === undefined`)
  отчёт содержит пустой `pages`, объявляет `graph-stale` в `limitations` и
  не выдаёт ни одной записи `orphan` или `undocumented`.
- **AC-25.** `wiki migrate-markers` идемпотентен (повторный прогон не меняет
  ни байта), не создаёт отсутствующую секцию `## Reference` и отказывается
  при дублирующемся заголовке.
- **AC-26.** Страница без непустого `describes` (включая страницы из папок
  вне `WIKI_PAGE_TYPES`) не попадает ни в `pages`, ни в знаменатель метрики
  свежести, а объявляется через `page-without-describes`.
- **AC-27.** Категория `orphan` вычисляется через `wikiPruneOrphans` /
  `validModuleNames`, а не собственной реализацией: тест подменяет
  `validModuleNames` и убеждается, что вывод отчёта меняется вслед за ней.
