# Living Wiki + Graph — PRD
Version: 1.1.0

## Проблема

Вики устаревает без сигнала. Не «медленно обновляется» — а не обновляется
вовсе и не сообщает об этом. Проблема составная, и каждая часть проверена по
исходникам ветки `main` (`be70279e`).

### P1. Между вики и графом нет связи

`src/gdgraph/types.ts` определяет `GraphNode` как
`{id, kind: "file" | "asset", path, language}` и `GraphEdge` с
`kind: "imports" | "asset" | "unresolved"`. Ни узла документации, ни ребра
«описывает» нет; поиск `wiki` по всему `src/gdgraph/**` даёт ноль совпадений.

Связь page → code существует, но эфемерно: `computeModuleKeyFiles`
(`src/wiki/collect.ts`) считает top-файлы модуля на лету, `staleness.ts` их
хэширует, хэш уходит в resume-файл. Обратной связи code → page нет нигде.
Следствие: невозможно ответить на единственный вопрос, который нужен всем
остальным механизмам — «какие страницы затронуты этим изменением».

### P2. Машинная половина страницы заморожена вместе с человеческой

Страница, собранная `wiki collect`, состоит из prose-секций
(`## Overview`, `## How it works`, `## Key concepts`, `## Main flows`) и
машинной секции `## Reference (from code graph)` с подсекциями `Public API`,
`Key files`, `Depends on`, `Graph signals` (`src/wiki/service.ts:525-536`,
`1082-1100`).

`writeCollectedPage` (`src/wiki/service.ts:791-804`) перезаписывает страницу
только если это «немодифицированный черновик»: `Status: draft` **и** маркер
``Generated by `keryx wiki collect` ``. Комментарий кода объясняет намерение:
«Once a human accepts … the page is theirs and is left untouched». Намерение
правильное для prose и неправильное для `Reference`: секция, чей заголовок
буквально сообщает «from code graph», перестаёт отражать граф.

Наблюдаемый эффект (эксперимент на vantage-frontend, отчёт
`WIKI_FRESHNESS_2026-09-03.md`): `collect --changed --since HEAD~5` находит 43
сдвинувшихся модуля и обновляет 0 страниц. Это не сбой — это в точности
описанная политика.

### P3. Гейт устаревания выключен по умолчанию и потому невидим

`isPageUnchangedSinceLastEnrich` (`src/wiki/staleness.ts:85-92`) сравнивает
хэш ключевых файлов страницы с записанным в `ResumeState.completedNodeHashes`.
Но `completedNodeHashes` заполняется только из `entry.nodeHash`
(`src/wiki/enrich.ts:917-931`), а `nodeHash` выставляет исключительно
`runRlmPipeline`; комментарий там же: «On the RLM-off path `entry.nodeHash` is
never present». `rlm.enabled` по умолчанию `false`
(`src/wiki/config.test.ts:8`).

То есть в конфигурации по умолчанию гейт не может сработать никогда, а
`enrich --force` каждый раз переобогащает все страницы.

### P4. Сам сигнал устаревания слишком груб

`computePageNodeHash` (`src/wiki/staleness.ts:51-77`) — sha256 по содержимому
ключевых файлов (обычно ≤6, по связности). У него два вида ошибок сразу:
переформатирование или правка комментария меняет хэш и порождает ложную
работу; правка седьмого по связности файла модуля хэш не меняет и работу не
порождает вовсе.

`graphMaybeStale` (`src/gdgraph/staleness.ts`) сравнивает только mtime
`.git/HEAD` с временем сборки графа и, по собственному комментарию, не
срабатывает на обычных правках рабочего дерева.

### P5. Полная пересборка графа — единственный режим

`gdgraph build` не имеет инкрементального режима, а `GraphNode` не хранит ни
контент-хэша, ни mtime, по которым его можно было бы построить. Любой хук,
которому нужен свежий граф, вынужден оплачивать полную сборку — что делает
пер-коммитный триггер неприемлемым.

## Цель

Сделать вики **наблюдаемо свежей**: система сама знает, какие страницы
затронуты изменениями кода, показывает это как бэклог, умеет
детерминированно (без модели) чинить машинную половину и точечно, по дельте и
с ревью — человеческую. При этом история изменений сохраняется, а актуальная
версия страницы отражает актуальный код.

Не-цель: сделать вики полностью автоматической. Цель — сделать её
**поддерживаемой**.

## Пользователи

- **Разработчик.** Хочет знать, что его изменение затронуло документацию, не
  открывая 514 страниц; хочет, чтобы `git commit` не замедлялся.
- **Агент (keryx runtime, Claude Code, Codex, любой MCP-клиент).** Читает вики
  как контекст. Устаревшая страница для него хуже отсутствующей: он
  сгенерирует код против несуществующего API. Нуждается в машинном ответе
  «свежая ли эта страница» до чтения.
- **Ревьюер.** Хочет видеть в PR список затронутых страниц и принимать
  изменения prose как дельту, а не как заново сгенерированный текст.
- **CI.** Нуждается в детерминированной, не-мутирующей проверке свежести с
  кодом возврата.

## Требования

Приоритет: **M** — must для v1, **S** — should, **C** — could.

### Граф

- **LWG-1 (M) — Узлы `wiki-page` и ребро `describes`.** Граф должен содержать
  узел для каждой страницы вики и ребро `describes` от страницы к файлам и
  символам, которые она описывает. Источники ребра: явный `Describes:` во
  фронтматтере, ссылки секции `## Related Code`, и вычисленные ключевые файлы
  модуля. Ребро должно быть обходимо в обе стороны.
- **LWG-2 (M) — Контент-хэш и mtime на file-узлах.** `GraphNode` для
  `kind: "file"` должен нести sha256 содержимого и mtime. Поля добавляются
  опциональными, как в своё время был добавлен символьный слой, — граф,
  собранный старой версией, обязан остаться валидным.
- **LWG-3 (S) — Инкрементальная пересборка.** `gdgraph build` должен уметь
  пересобирать только изменённые файлы, определяя их по хэшу и mtime, с
  идентичным результатом относительно полной сборки.

### Страница

- **LWG-4 (M) — Provenance, независимый от VCS.** Страница должна нести
  `VerifiedAt: <git sha>` — ревизию основного репозитория, против которой её
  последний раз подтверждали, `VerifiedScope` — снимок контент-хэшей той же
  области, и опциональный `Describes:` — явный список описываемых путей.
  Свежесть вычисляется через `git log <VerifiedAt>..HEAD -- <пути>` там, где
  git доступен, и сравнением `VerifiedScope` там, где нет. Оба поля живут
  внутри страницы: версионирование не должно зависеть от того, трекает ли
  проект `.metaproject/` и существует ли git вообще
  (`src/commands/init.no-git.test.ts` фиксирует последнее как поддерживаемое
  состояние).
- **LWG-5 (M) — Управляемый блок.** Секция `## Reference (from code graph)`
  должна быть ограничена машинными маркерами и объявлена машинной
  территорией. Детерминированный писатель обязан уметь заменить только этот
  регион, включая страницы со `Status: accepted`, и обязан не трогать ничего
  за его пределами.
- **LWG-6 (S) — Два класса prose.** Секции должны различаться по волатильности:
  `## Overview`/`## Key concepts` — долгоживущие, `## How it works`/
  `## Main flows` — волатильные. Авто-инрич по умолчанию предлагает изменения
  только для волатильных.

### Детект и распространение

- **LWG-7 (M) — Классификация изменения.** Для каждого изменённого файла
  система должна определить класс: `added`, `removed`, `signature`, `body`,
  `cosmetic`, `moved`. Класс `cosmetic` обязан не порождать работы.
- **LWG-8 (M) — Распространение влияния.** От изменённых файлов система должна
  обойти граф в обе стороны и получить множество затронутых страниц с цепочкой
  причин. Решение о продолжении обхода принимается по типу ребра, а не по
  фиксированному числу прыжков.

### Очередь и бэклог

- **LWG-9 (M) — Очередь свежести.** git-хук должен дописывать в append-only
  журнал факт изменения (`rev`, время, изменённые пути) и не делать больше
  ничего. Бюджет — единицы миллисекунд; ни сборки графа, ни обращений к
  модели.
- **LWG-10 (M) — `keryx wiki freshness`.** Read-only команда, разбирающая
  очередь и выдающая бэклог по категориям: `stale-reference`, `stale-prose`,
  `undocumented`, `orphan`, `unknown`. Не мутирует ничего. Поддерживает
  `--json` по схеме.

### Обновление

- **LWG-11 (M) — `keryx wiki refresh`.** Детерминированное обновление
  управляемых блоков затронутых страниц без обращения к модели. Бампает patch,
  дописывает строку в `## Changelog`, обновляет `VerifiedAt`.
- **LWG-12 (M) — Дельта-инрич prose.** `wiki enrich` должен уметь брать
  работу из очереди/бэклога, а не сканировать всю вики, и обязан
  использовать hash-гейт RLM. Режим `--propose` направляет каждое изменение в
  SAC propose/review вместо прямой записи.
- **LWG-13 (S) — Anti-entropy якорь.** Абзац, помеченный как человеческий,
  никогда не переписывается автоматикой; при инриче он передаётся модели как
  контекст, но не как редактируемый текст.

### Валидация и наблюдаемость

- **LWG-14 (M) — Валидация перекрёстных ссылок.** `wiki validate` должен
  проверять: внутренние ссылки резолвятся; цели `describes` существуют;
  управляемый блок корректен; `Version` и `VerifiedAt` присутствуют.
- **LWG-15 (S) — Метрика в health.** Доля свежих страниц и размер бэклога
  попадают в health-артефакт; порог настраиваемый и по умолчанию не блокирует
  гейт.

## Критерии успеха

- Косметический коммит (только форматирование и комментарии) порождает **ноль**
  записей бэклога. Сегодняшний sha256 порождает работу на каждой такой правке.
- Изменение сигнатуры экспортируемого символа порождает `stale-reference` для
  всех страниц, описывающих его модуль, и `stale-prose` для страниц, где этот
  символ упомянут в тексте.
- `wiki refresh` приводит `Reference` в соответствие графу на 100% затронутых
  страниц **без единого обращения к модели**.
- Дельта-инрич расходует не более 30% токенов от полного прогона на том же
  наборе изменений (базовая линия RepoDoc: −77%).
- Накладные расходы хука на `git commit` — менее 50 мс на p95.
- Ни один автоматический путь не изменяет prose на `accepted` странице без
  явной команды человека или принятого proposal.

## Риски

- **Энтропия текста.** Цикл «модель переписывает текст модели» через N
  итераций даёт дрейф без человеческого якоря. Митигация: LWG-13, режим
  `--propose` (LWG-12), diff-ревью вместо принятия целиком.
- **Шум в git-diff.** Если `refresh` бампает Reference на каждый merge, каждый
  PR тащит документационные изменения. Митигация: изменения локализованы
  управляемым блоком; политика «Reference-коммиты не требуют ревью» должна
  быть объявлена явно, иначе ревьюеры начнут их игнорировать целиком — включая
  те редкие случаи, когда смотреть стоило.
- **Неточность `describes`.** Ребро, выведенное из ключевых файлов, наследует
  их ошибку: страница, описывающая модуль лишь частично, получит ложные
  срабатывания. Митигация: явный `Describes:` во фронтматтере имеет приоритет
  над вычисленным.
- **Стоимость инкрементального графа.** LWG-3 — самая дорогая часть.
  Митигация: он не блокирует LWG-9/10/11 (очередь, бэклог и детерминированный
  refresh работают и на полной сборке, просто реже).
- **Вики вне git.** В проектах, игнорирующих `.metaproject/`, теряется не
  версионирование (оно внутри страницы, LWG-4), а история прошлых тел,
  командный шаринг и CI-джоба. Митигация — режим B из `specification.md`
  §1.2: отдельный репозиторий или submodule под `.metaproject/`, дающий
  историю без засорения основного дерева. Собственный журнал ревизий внутри
  `.metaproject/` рассмотрен и отвергнут там же: в игнорируемой директории он
  тоже локален и потому решает симптом, а не проблему.
- **Ложная уверенность.** Страница со свежим `VerifiedAt` выглядит проверенной,
  даже если её prose всё это время был неверен. `VerifiedAt` означает «код не
  менялся с этой ревизии», а не «текст правилен». Формулировки в выводе команд
  обязаны это различать.

## Рекомендация

Реализовывать в порядке «дешёвое и детерминированное — первым». Сначала
`describes` + `VerifiedAt` (фундамент, без модели), затем очередь и
freshness-отчёт (тоже без модели — они первыми покажут реальный масштаб в
цифрах), затем управляемый блок и `refresh`. Инкрементальный граф и
дельта-инрич prose — последними, когда уже известно, сколько страниц реально
этого требуют.

Отвергнутая альтернатива: начать с починки `enrich` и одного полного прогона
`--force`, как предлагал исходный отчёт. Она ставит самое дорогое действие
первым и при этом не решает P1 и P2 — Reference принятых страниц остался бы
замороженным. Включение `rlm.enabled` при этом остаётся нужным, но это
однострочное изменение конфигурации, а не фаза работ.
