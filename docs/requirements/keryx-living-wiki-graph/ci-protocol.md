# Living Wiki + Graph — CI and Hook Protocol
Version: 1.1.0

## 1. Принцип

Накопление событий — дёшево и непрерывно. Разбор — дорого и по требованию.
Хук никогда не строит граф, не читает очередь целиком и не обращается к
модели. Всё, что он делает, — дописывает одну строку.

Это отличает LWG от подхода «file-watcher + мгновенная регенерация»:
непрерывная реакция на каждое сохранение файла отвергнута сознательно
(см. non-goals в README) по стоимости, шуму и неизбежным гонкам с
незавершённой правкой.

## 2. Существующий хук

`.git/hooks/post-commit` уже установлен и управляется keryx
(маркер `keryx:gdwiki-post-commit`). Сегодня он печатает напоминание:
*«wiki drafts may be stale; run `keryx wiki collect --changed --since HEAD~1`»* —
не мутирует, требует ручного действия и, поскольку `collect` не обновляет
принятые страницы, предлагает команду, которая на них ничего не сделает.

LWG заменяет тело этого хука, не добавляя нового: одна точка расширения,
один маркер.

## 3. Поведение хуков

### 3.1 `post-commit`

1. Определить изменённые пути: `git diff-tree --no-commit-id --name-only -r HEAD`.
2. Если ни один путь не попадает в области, за которыми следит вики
   (источники и сама вики), — выйти, ничего не записав.
3. Дописать одну строку по
   [freshness-queue-entry.schema.json](schemas/freshness-queue-entry.schema.json)
   в `.metaproject/data/wiki/freshness-queue.jsonl`.
4. При превышении лимита списка путей — записать `truncated: true` и не
   перечислять пути: разбор восстановит их через `git diff`.
5. Выйти с кодом 0 **всегда**.

**Бюджет: 50 мс на p95** (AC-12). Хук, замедляющий `git commit`, будет
отключён разработчиками, и вся система превратится в мёртвый код.

### 3.2 `post-merge` и `post-checkout`

Та же запись с соответствующим `event`. `post-checkout` важен отдельно:
переключение веток меняет рабочее дерево целиком, и без записи очередь
получила бы дельту относительно чужой истории.

### 3.3 Отказоустойчивость

- Недоступный или нечитаемый файл очереди — хук молча выходит с кодом 0.
  Потерянное событие восстанавливается при следующем разборе через
  `--since <rev>`, поэтому терять их безопасно; ломать коммит — нет.
- Хук никогда не пишет в stderr при нормальной работе. Единственный
  допустимый вывод — однострочное уведомление, если бэклог превысил
  настраиваемый порог.

## 4. Разбор очереди

Разбор выполняет `keryx wiki freshness` — вручную, из CI, или лениво при
следующем обращении к вики. Он:

1. читает очередь и/или диапазон `--since`;
2. при необходимости обновляет граф (полностью до фазы 4, инкрементально
   после);
3. классифицирует изменения, распространяет влияние, строит отчёт;
4. пишет `data/wiki/freshness/latest.{json,md}`;
5. усекает разобранную часть очереди;
6. **завершается с кодом 0 независимо от результата.**

Код возврата 0 — намеренно. `freshness` — это отчёт, а не гейт. Гейт
описан в §6 и является отдельным, явно включаемым решением.

## 5. Что зависит от политики версионирования, а что нет

Полное разделение — в `specification.md` §1.1/§1.2. Здесь только следствия
для CI.

**Не зависит ни от чего.** Версия страницы, `VerifiedAt`/`VerifiedScope` и
`## Changelog` живут внутри файла. Детект свежести, бэклог, `refresh` и
валидация работают во всех трёх режимах, включая репозиторий без git вообще.

**Зависит от режима** (§1.2 спецификации):

- **Режим A — вики в основном репозитории** (keryx: 2336 файлов под
  `.metaproject/`, игнорируется только класс производных артефактов).
  CI-джоба §6 доступна полностью.
- **Режим B — `.metaproject/` в отдельном репозитории или submodule.**
  CI-джоба доступна, но требует шага синхронизации перед проверкой и
  отдельного решения, куда коммитить результат `refresh`. Рекомендуемый
  режим для проектов, не желающих видеть вики в diff основного дерева.
- **Режим C — вики локальная** (vantage-frontend: `.metaproject/`
  игнорируется целиком; либо git отсутствует). **CI-джоба §6 невозможна** —
  раннер не видит страниц. Всё остальное работает локально, `VerifiedScope`
  заменяет `VerifiedAt`.

Режим C — осознанное состояние, а не деградация по ошибке. `wiki freshness`
обязана объявлять его в `limitations` отчёта, иначе пустой результат
прочитается как «всё свежо». Именно поэтому §6 запрещает трактовать
отсутствие находок как успех без проверки `limitations`.

**Стоимость полного режима**, которую надо принять заранее: `refresh`
меняет управляемые блоки, и эти изменения попадают в diff PR. Если не
объявить явную политику «коммиты, меняющие только управляемый блок, не
требуют содержательного ревью», ревьюеры начнут пролистывать
документационные изменения целиком — включая те редкие, где смотреть
стоило.

## 6. CI-джоба

Запускается на PR, затрагивающих отслеживаемые области. Только в режимах A и
B (§5). Отсутствие находок трактуется как успех **только** при пустом
`limitations` в отчёте: непустой список означает, что проверка была неполной,
а не что расхождений нет.

1. `keryx gdgraph build` (инкрементально, если доступно).
2. `keryx wiki freshness --since <merge-base> --json`.
3. `keryx wiki validate`.
4. Опубликовать сводку в PR: затронутые страницы по категориям с цепочками
   причин.

### Политика гейта

- **`wiki validate` — блокирующий.** Оборванный управляемый блок,
  несуществующая цель `describes`, отсутствующий `Version` — это дефекты
  структуры, а не мнение.
- **`wiki freshness` — не блокирующий по умолчанию.** Устаревшая страница
  не должна останавливать поставку кода. Порог включается проектом явно и
  осознанно.
- **`--deep` валидация моделью в CI не запускается никогда.** Недетерминирована
  и платна; её место — ручной аудит.

Обоснование мягкого гейта: блокирующая проверка свежести на старте создаёт
давление «обновить страницу лишь бы прошло», что порождает мусорный prose
быстрее, чем устаревание. Ужесточать имеет смысл только после того, как
метрика фазы 5 покажет устойчиво низкий бэклог.

## 7. Автоматические предложения (опционально)

Проект может включить автоматический PR-комментарий или follow-up PR с
результатом `wiki refresh` — детерминированным, без модели. Прозе такой путь
не разрешён: изменения prose идут только через `--propose` и SAC-ревью
(LWG-12), потому что у детерминированной правки Reference диff проверяем
механически, а у сгенерированного текста — нет.
