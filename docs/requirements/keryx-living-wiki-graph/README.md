# Living Wiki + Graph (LWG)
Version: 3.0.0

## Назначение

Вики (`gdwiki`) устаревает молча. Причина не в одном баге, а в трёх
независимых, проверенных по коду фактах:

1. **Граф ничего не знает о вики.** Поиск `wiki` по `src/gdgraph/**` даёт ноль
   совпадений. `GraphNode` — это `{id, kind, path, language}`; ребра
   «страница описывает код» не существует. Значит на вопрос «я изменил
   `foo.ts`, какие страницы протухли» система не может ответить в принципе.
2. **`collect` никогда не обновляет принятые страницы.** `writeCollectedPage`
   (`src/wiki/service.ts:791-804`) пропускает страницу, если она не является
   «немодифицированным черновиком» (`Status: draft` **и** маркер
   ``Generated by `keryx wiki collect` ``). Это намеренно и записано в
   комментарии кода. Побочный эффект: машинная секция
   `## Reference (from code graph)` замораживается вместе с prose.
3. **Гейт устаревания в `enrich` физически не может сработать.**
   `completedNodeHashes` пишется только когда у результата есть
   `entry.nodeHash` (`src/wiki/enrich.ts:917-931`), а его выставляет
   исключительно `runRlmPipeline`. `rlm.enabled` по умолчанию `false`
   (`src/wiki/config.test.ts:8`, зафиксировано тестом как NFR-4 back-compat).
   Пустой `completedNodeHashes` в resume-файле — не потеря данных, а
   ожидаемое следствие выключенного режима.

Пакет описывает **Living Wiki + Graph**: связывание вики и графа ребром
`describes`, детерминированное обновление машинной половины страницы,
классификацию изменений вместо булева хэша, накопительную очередь свежести на
git-хуке и дельта-инрич prose через существующий SAC propose/review.

### Что отложено и почему

**Фаза 3 (дельта-инрич prose).** На диапазоне из 189 изменённых файлов дрейф
составил **100% `stale-reference` и 0% `stale-prose`**: всё протухшее чинится
бесплатным `wiki refresh`, а единственной фазе, которая тратит токены, работы
нет. Ноль проверен дважды на артефактность — все 53 страницы содержат
настоящий prose и все 53 упоминают символы графа (2137 упоминаний), то есть
детектор способен сработать и просто не сработал. Строить её следует тогда,
когда отчёт покажет ненулевой `stale-prose`, — и это решение примут данные,
а не план.

**Фаза 4 (инкрементальная сборка графа).** Чистая оптимизация. Полная сборка
занимает ~2.3 с, манифест для неё уже пишется с фазы 0. Брать, когда сборка
начнёт мешать.

## Что входит (v1)

- **LWG-1 — `describes`-ребро и узлы `wiki-page` в графе.** Страница
  становится гражданином графа, а не текстом рядом с ним.
- **LWG-2 — контент-хэш и mtime на file-узлах.** Фундамент и для
  инкрементальной сборки, и для устаревания страницы; сейчас `GraphNode` не
  хранит ни того, ни другого.
- **LWG-3 — инкрементальная пересборка графа.** Сегодня `gdgraph build`
  умеет только полную; хук на каждый коммит её звать не может.
- **LWG-4 — provenance страницы, независимый от VCS.** `VerifiedAt` (git sha)
  и `VerifiedScope` (снимок контент-хэшей) живут внутри самой страницы.
  Свежесть считается через `git log <VerifiedAt>..HEAD -- <файлы>` там, где
  git есть, и сравнением `VerifiedScope` там, где его нет. Без модели в
  обоих случаях.
- **LWG-5 — управляемый блок `## Reference`.** Машинная территория, явно
  размеченная маркерами; обновляется детерминированно даже на `accepted`
  страницах, prose не трогается. Это не новое правило: `skills/gdwiki/
  SKILL.md:110` уже объявляет секцию graph-owned и «regenerated», а
  `SKILL.md:113` тут же делает всю страницу неперезаписываемой — контракт
  записан, но неисполним, пока владение не разделено (specification.md
  §4.2.1).
- **LWG-6 — два класса prose** по волатильности: долгоживущий и волатильный;
  авто-инрич по умолчанию трогает только второй.
- **LWG-7 — классификация изменений** (`added`/`removed`/`signature`/`body`/
  `cosmetic`/`moved`) вместо одного sha256.
- **LWG-8 — распространение влияния по графу** в обе стороны, с политикой на
  тип ребра.
- **LWG-9 — очередь свежести**, append-only, пишется хуком за миллисекунды.
- **LWG-10 — `keryx wiki freshness`**, read-only бэклог по образцу
  `src/sac/catch-up.ts`.
- **LWG-11 — `keryx wiki refresh`**, детерминированное обновление Reference
  без модели.
- **LWG-12 — дельта-инрич prose**, включая режим SAC-proposal с человеческим
  ревью.
- **LWG-13 — anti-entropy якорь**: помеченный человеческий абзац автоматика
  не переписывает.
- **LWG-14 — валидация перекрёстных ссылок** в `wiki validate`.
- **LWG-15 — метрика свежести в health**, не блокирующая гейт по умолчанию.

## Что сознательно НЕ входит

- **File-watcher / настоящий realtime.** Накопление событий непрерывное,
  разбор — по требованию (pull-based, как `catch-up.ts`). Модель, дёргаемая на
  каждое сохранение файла, отвергнута по стоимости и шуму, а не забыта.
- **Автопринятие prose без ревью.** Запись prose всегда либо явная команда
  человека, либо принятый SAC-proposal.
- **Полная замена человеческого prose генерацией.** Подход DeepWiki
  («сгенерировать вики заново целиком») здесь неприменим: существующий
  человеческий текст — актив, который надо сохранять.
- **Мульти-репозиторные графы и вики.** Вне области v1.
- **Собственный журнал ревизий внутри `.metaproject/`.** Рассмотрен и
  отвергнут: в проекте, игнорирующем `.metaproject/`, он тоже локален и
  потому не даёт ни командной истории, ни ревью, ни CI — то есть решает
  симптом. Проекту, которому нужна история без вики в основном дереве,
  дешевле режим B из specification.md §1.2 (отдельный репозиторий или
  submodule), чем второй, худший git внутри metaproject.
- **Векторный/семантический индекс страниц.** Возможное v2; в v1
  распространение влияния строго структурное.
- **Ребро `semantic-impact` из RepoDoc.** Требует эмбеддингов или модели для
  построения; сознательно отложено, чтобы v1 остался детерминированным.

## Что берём у RepoDoc и что делаем иначе

Источник: [RepoDoc, arXiv 2604.26523](https://arxiv.org/html/2604.26523v1) —
knowledge-graph-фреймворк инкрементального обновления документации.

**Берём:** четырёхстадийный конвейер (детект изменения по AST →
распространение влияния по графу → селективная регенерация → валидация
перекрёстных ссылок); узлы документации и ребро `describes` внутри одного
графа с кодом; двунаправленный обход от изменённых компонентов с решением о
распространении **по типу ребра**, а не по фиксированному лимиту прыжков;
сохранение уже существующей документации с регенерацией только затронутого.

**Делаем иначе:**

- **Provenance внутри страницы, а не во внешнем индексе.** `VerifiedAt` даёт
  человекочитаемый и точный ответ «с какой ревизии страницу не проверяли»,
  `VerifiedScope` покрывает случай без git, и оба путешествуют вместе с
  файлом. Ни один механизм не требует, чтобы `.metaproject/` был под
  контролем версий (specification.md §1.1).
- **Человек в контуре.** RepoDoc регенерирует автоматически. Здесь изменение
  prose может идти через уже существующий SAC propose/review с receipt'ом и
  идемпотентностью (`src/sac/wiki-owner-writer.ts`) — у RepoDoc такого
  контура нет.
- **Разделение машинной и человеческой половины страницы** как явная граница
  записи. Это снимает конфликт с правилом «accepted принадлежит человеку»,
  из-за которого сегодня Reference не обновляется вовсе.
- **Класс `cosmetic`.** Отдельный класс, который гарантированно не порождает
  работы, — прямой ответ на текущее пересрабатывание sha256.
- **Защита от энтропии.** Явный anti-entropy якорь против цикла «модель
  переписывает текст модели»; RepoDoc этот риск не рассматривает.
