## AC7 — re-verification of the frozen-criteria claim

The August claim, restated exactly: *no comparable tool confirms acceptance
criteria by evidence, and ours are checksum-protected.*

That claim has two halves. **One half holds and is now verified against
competitor source. The other half overstates what our own code does, and the
correction is against us.**

### Half one: are competitors' criteria rewritable? — Still yes, but BMAD moved

**BMAD-METHOD v6.11.0 introduced a freeze concept, and the August note predates
it.** This is the most important market finding in this document.

`src/bmm-skills/ship/bmad-build/spec-template.md:16` opens a block:

```
<frozen-after-approval reason="human-owned intent — do not modify unless human renegotiates">
```

and `step-03-implement.md:11` instructs: *"Content inside
`<frozen-after-approval>` in `{spec_file}` is read-only. Do not modify."*
`step-04-review.md:60` routes any finding whose root cause is inside the block
to `intent_gap`, which reverts the code and returns to the human.

Two facts keep this from overturning the August claim, and both were checked in
source rather than inferred:

1. **The block does not contain the acceptance criteria.** The block closes at
   `spec-template.md:44`. The `## Tasks & Acceptance` section — which holds
   `**Acceptance Criteria:** - Given PRECONDITION, when ACTION, then
   EXPECTED_RESULT` — begins at line 64, *outside* it. What BMAD freezes is
   Intent, Boundaries & Constraints, and the I/O & Edge-Case Matrix. The
   acceptance criteria remain editable, and `step-04-review.md:61` describes
   `bad_spec` loopbacks that amend exactly those non-frozen sections, appending
   to a `## Spec Change Log`.
2. **The freeze is prose, not code.** `frozen-after-approval` occurs 13 times
   across 5 files, all Markdown agent instructions
   (`spec-template.md`, `step-02-plan.md`, `step-03-implement.md`,
   `step-04-review.md`, `step-oneshot.md`). It occurs in zero `.py`, `.js` or
   CLI files. No checksum is taken; nothing detects an edit. By this package's
   own Phase 7 taxonomy it classifies as **`prose-only`** — the same class as
   the `flow complete` task-gate sentence that Phase 0 found had never held, and
   that our own measurement caught failing in 24 of 184 flows.

So BMAD now expresses the *intent* to freeze human-owned intent. It does not
freeze acceptance criteria and it cannot detect a violation.

**GitHub Spec Kit v1.0.1 — no freeze, by explicit design.** Checked in source:
every `sha256` / `frozen` / `immutable` hit in `src/`, `templates/` and `docs/`
is either archive and bundle integrity (`verify_archive_sha256`,
`shared_infra.py`, `integrations/manifest.py`, extension and preset download
verification) or Python language constructs (`frozenset`,
`@dataclass(frozen=True)`). Nothing hashes spec content. The project is
directionally opposed to freezing: the v1.0.0 note states *"as agents make
adapting to change dramatically cheaper, the value moves from stability to
adaptability"*, and an *Evolving Specs* guide exists for revising specs when
intended behaviour changes. `/speckit.converge` explicitly *"assess[es] the
codebase against spec/plan/tasks and append[s] remaining work as new tasks"* —
convergence is achieved by adding work, not by holding a criterion fixed.

**AWS Kiro — no evidence of a freeze; cannot be verified either way.** Kiro is
closed source, so this row is `DOC`/`CHANGELOG` only and no source-level check
is possible. The docs (`kiro.dev/docs/specs/`, page updated 2026-08-27) describe
`requirements.md` / `design.md` / `tasks.md` with approval gates in the standard
Feature Spec flow, and a *Quick Spec* variant that generates all three
artifacts **without approval gates**. The documentation is silent on whether an
approved requirement can later be edited. The changelog points the other way
from freezing: CLI `2.18.0` (2026-08-12) added a spec review screen at phase
checkpoints where a user can *"read the phase document in place and stage line
comments on the parts you want changed"* — a revision affordance, built at the
checkpoint. **Honest limit: absence of a documented freeze is not proof there is
none.** Kiro should be treated as unverified, not as confirmed-rewritable.

**moai-adk v3.1.x — no freeze.** No checksum, immutability lock or SPEC
content hash found in the Go source. SPECs move through plan → run → sync with
audit gates between phases rather than any content lock.

**Verdict on half one: the claim holds, with a named qualification.** No
comparable tool checksums or otherwise tamper-protects acceptance criteria. The
qualification is that BMAD has adopted the *vocabulary* of freezing for a
neighbouring artifact, and any future re-measurement should check whether the
`<frozen-after-approval>` block grows to cover acceptance criteria or acquires
code enforcement. If either happens, this differentiator narrows sharply.

### Half two: "confirmed by evidence" — the claim overstates our own code

Re-verified against `src/flow/service.ts`, and the correction runs against us.

`freeze()` (`service.ts:222-236`) records `acChecksum`, and `assertAcIntact()`
is called on every subsequent mutating operation, so a hand-edit of
`acceptance-criteria.md` fails every gate and transition. `acUpdate()`
(`service.ts:342-351`) requires an explicit `--reason` and **voids all prior
confirmations** (`flow.acConfirmed = {}`). That machinery is real, is code, and
is what "checksum-protected" means. Half one of the claim is accurate.

But `acConfirm()` (`service.ts:329-340`) does this and only this:

```ts
flow.acConfirmed[target] = { at: now(), ...(note ? { note } : {}) };
```

A timestamp, and an **optional free-text note**. No artifact path, no run link,
no checkable reference is required to confirm a criterion. `evidenceRefs` exists
on tasks (`types.ts:76`, described in `schema.ts:188` as *"v2: artifact
paths"*), is settable via `taskDone`, and is required by nothing.

So "frozen acceptance criteria **confirmed by evidence**" describes the freezing
accurately and the confirming inaccurately. What genuinely requires evidence is
a *different* mechanism: the review gate (`src/flow/review-gate.ts`), whose
header states the rule directly — *"Each terminal disposition names the evidence
it requires, and a disposition without that evidence is NOT terminal"*, and *"A
condition that could not be observed fails the gate"*, with `unobserved` a
distinct failing status from `violated`. That is evidence-gating in code, and it
is a real differentiator — but it gates *findings*, not *acceptance criteria*.

The defensible form of the claim is therefore narrower than August's:

> Acceptance criteria are checksum-frozen and tamper-evident in code; findings
> must carry evidence to reach a terminal disposition. Confirming a criterion is
> an agent assertion with an optional note, and is not itself evidence-backed.

### Notes behind the table

**Spec Kit's workflow engine is genuine code.** `src/specify_cli/workflows/`
implements ten step types — `command`, `prompt`, `shell`, `init`, `gate`, `if`,
`switch`, `while`/`do-while`, `fan-out`/`fan-in`. The `gate` step
(`workflows/steps/gate/__init__.py`) pauses the run and requires a human verdict
supplied interactively or via `specify workflow resume <run_id>`; `on_reject`
must be one of `abort` / `skip` / `retry`, validated by the code. The CLI
enforces the *pause*. It does not compute the *verdict* — that is a human
choice, and the code merely parses and validates it. So Spec Kit has
code-enforced human checkpoints and no code-computed completion condition.

**BMAD's review loop is more developed than the August note implies.**
`step-04-review.md` requires, in prose: verify each finding at the cited
location before grading; render exactly one verdict from
`high`/`medium`/`low`/`false`/`maybe-false`; for `false`, *"write what disproves
this specific claim"*; for `maybe-false`, *"write what you would need to check";*
every finding gets a row in a `## Review Triage Log` with *"verdict plus its
evidence"*, and *"never drop, merge, or silently skip one."* Findings are then
grouped by shared root cause and routed to `intent_gap` / `bad_spec` / `patch` /
`defer`, with `review_loop_iteration` incremented before each loopback and a
HALT-and-escalate at 5. `references/claims-check.md` adds an epistemic control
worth quoting: *"The spec is the change's own account of itself: testimony, not
evidence — a claim repeated in a code comment is still the same claim, not
confirmation."*

All of it is Markdown executed by the model. The round counter lives in the spec
file's frontmatter and is written by the agent, so the cap of 5 is honour-system.
By our own taxonomy it is `prose-only` throughout — but the *design* is
sophisticated, and dismissing it because it is unenforced would be the mirror of
the error this package exists to correct.

**BMAD's Python is deliberately non-judging.** `git_evidence.py` states its own
boundary: *"This script only MEASURES — it never judges acceleration or
violations. The model interprets the numbers."* That is, independently arrived
at, the same refinement our roadmap reached — mechanical operations to code,
judgement to the model. Worth noting that the most-adopted practitioner tool
converged on our rule rather than contradicting it.

**moai-adk's gates are compiled and hook-wired.** Verified in source:
`internal/hook/quality/gate.go`, `internal/runtime/audit_gate.go`,
`internal/harness/regression_gate.go`, `internal/cli/gate.go`,
`internal/lsp/hook/gate.go`, each with adjacent test files. Gates are installed
as Claude Code hooks (`.claude/hooks/moai/sync-phase-quality-gate.sh`,
`handle-multi-review-gate.sh`) and fire at `PreToolUse` / `Stop`. The README
(`DOC`, not verified by running) states *"`/moai gate` runs lint + format + type
+ tests in one pass"* and that TRUST 5 *"applies to every change"*.

**But moai-adk's evidence gate does not block.** This matters, and cuts both
ways. `runEvidenceGate` is called from `internal/hook/stop.go:79` and reads the
session ledger to detect a success claim contradicted by an observed binary
outcome — the same failure mode EviBound targets. It is a **void** function; its
own test is named `TestRunEvidenceGate_ReadOnlyNoBlock` and the comment reads
*"runEvidenceGate is void: it surfaces advisories via slog/stderr only."* By our
taxonomy: **`advisory`, not `wired`**. moai-adk detects the lie and prints it;
it does not stop the turn.

## Dimensions where a competitor leads

Listed with the same prominence as anything above, per AC6.

1. **Spec Kit leads on human-approval checkpoints (D7).** It has a first-class
   `gate` step type in a real workflow engine: the run pauses, persists, and
   requires `specify workflow resume` with an explicit verdict. Keryx has **no
   equivalent primitive.** Every keryx gate is a machine-checked condition at
   `flow complete`; there is no step that halts mid-flow and waits for a human
   decision as a recorded, resumable artifact. On any question a machine cannot
   check, Spec Kit has a mechanism and we have none.

2. **moai-adk leads on enforcement point (D8).** Its gates run as agent-harness
   hooks at `PreToolUse` and `Stop`. Ours run inside a CLI subcommand the agent
   chooses to invoke. A hook fires whether or not the agent cooperates; a
   subcommand does not. This is a structurally stronger place to put a gate than
   where ours are, and it is the single most transferable idea in this sweep.

3. **BMAD leads on false-positive vocabulary (D6).** `false` and `maybe-false`
   are first-class verdicts, a `false` verdict requires a written refutation, and
   `maybe-false` requires naming what would settle it. Our August measurement
   found **0** occurrences of "false positive" anywhere in the review domain.
   BMAD's version is unenforced prose — but it is a designed answer to a gap
   where we did not have one.

4. **BMAD leads on recording why a spec changed.** The append-only
   `## Spec Change Log` records the triggering finding, what was amended, the
   known-bad state avoided, and KEEP instructions preserved across
   re-derivation. Our `acUpdate` requires a `--reason` and voids confirmations,
   but keeps no append-only history of what the criteria used to say.

5. **BMAD leads on treating the spec as testimony.** `claims-check.md` extracts
   the change's claims about itself and tries to *falsify* each against traced
   code. We have no equivalent: nothing in our pipeline treats the flow's own
   account of itself as a claim to be refuted.

6. **Spec Kit leads on ecosystem scrutiny.** 132,375 stars, 30+ supported
   agents, an extension and bundle system with sha256-verified archives, and a
   published newsletter and changelog cadence. Ours is a single-repository tool
   with one operator. Adoption is not correctness, but it does mean their
   failure modes have been found by more people than ours have.

7. **Kiro leads on reviewing the spec in place.** CLI 2.18.0's phase-checkpoint
   review screen with staged line comments is a better human-review surface than
   anything we offer for acceptance criteria. (`CHANGELOG` class — shipped, not
   verified by use.)

**On method.** This comparison does not find us ahead on everything, which is
the outcome AC6 says to expect from an honest frame. We lead clearly on exactly
one thing — tamper-evident criteria plus machine-checked completion conditions —
and we are behind on human-in-the-loop checkpoints, on where gates are
installed, and on the review vocabulary for wrong findings. A version of this
document that reported only the first would have been a marketing document.

## Re-verification of the two cited studies

The August note carried both as corroboration, not as our own measurement. Both
were re-read at source.

### EviBound (arXiv:2511.05524) — holds, with a caveat the note omits

*Evidence-Bound Autonomous Research (EviBound): A Governance Framework for
Eliminating False Claims*, Ruiying Chen. Submitted 2025-10-28, **v1 only, no
revision, no withdrawal or retraction notice** as of 2026-08-31.
<https://arxiv.org/abs/2511.05524>

The numbers the roadmap cites are accurate. The abstract states: *"Baseline A
(Prompt-Level Only) yields 100% hallucination (8/8 claimed, 0/8 verified).
Baseline B (Verification-Only) reduces hallucination to 25% (2/8 fail
verification). EviBound (Dual Gates) achieves 0% hallucination"*, *"all with
only approximately 8.3% execution overhead."*

**Caveat the roadmap does not state: n = 8 tasks.** "0% vs 100%" is 0-of-8
versus 8-of-8. It is a single-author arXiv preprint with no indication of peer
review. The mechanism it supports — an approval gate plus a verification gate
over declared acceptance contracts — is sound and matches what we built, but
"0% hallucinated completions" should be cited as *0 of 8 on the authors' own
benchmark*, not as a general rate. Recommend the roadmap's §0.1 corroboration
line be amended to carry the sample size. **Class: `3P`.**

### Greptile's 1,000-PR study — exists, but the roadmap's numbers could not be confirmed

*Models are worse at reviewing their own code*, Rodrigo Caridad, Greptile
Research, published **2026-07-21**.
<https://www.greptile.com/blog/model-inversion> No correction or retraction
notice is visible.

What is confirmed:

- **Method.** 1,000 PRs — 500 Claude-authored, 500 Codex-authored. Ground truth
  built from ~1,500 verified bug comments using sentiment analysis, voting
  ratios and "git archaeology". Three review runs per PR. Recall matched by
  **LLM-as-a-judge**. Figures are for **high-severity bugs only**.
- **The qualitative finding, verbatim from the prose:** *"The data shows that
  both models find more bugs in code written by the other model than in code
  they wrote themselves."*
- **The four percentages** cited in the roadmap — 53.7%, 62.0%, 50.5%, 60.0% —
  do all appear in the source.

**What could not be confirmed: which number goes with which pair, and therefore
the size of the effect.** The percentages appear only in a chart figure
("RECALL OF HIGH SEVERITY BUGS"), not in running prose — confirmed by a
targeted pass that asked for prose sentences containing percentages and returned
none. Two independent extractions of that chart disagreed with each other:

| Extraction | Claude-authored | Codex-authored | Implied cross-family gain |
|---|---|---|---|
| A | Claude 53.7% / GPT 60.0% | GPT 50.5% / Claude 62.0% | **+6.3 and +11.5 points** |
| B | Claude 60.0% / GPT 62.0% | Claude 53.7% / GPT 50.5% | **+2.0 and −3.2 points** |

The roadmap (`roadmap.md:412-414`) asserts *"~8–10 recall points"* with the
pairing *"Claude→Claude 53.7% vs GPT→Claude 62.0%; GPT→GPT 50.5% vs Claude→GPT
60.0%"* — a pairing that matches **neither** extraction, and whose stated
magnitude falls between extraction A's range and above extraction B's entirely.

**Conclusion: the direction of the finding is confirmed; the magnitude is not.**
Under extraction B the effect is small enough to change the cost-benefit of
Phase 5.4 (cross-family review). Nobody re-read this chart between August and
now, which is exactly the failure mode this re-verification was asked to look
for. The `~8–10 points` figure should be marked unverified in `roadmap.md`
§5.4 until a human reads the chart directly. Note also that the study's ground
truth is itself LLM-judged, so it is `3P` evidence with a soft label source.

## What this comparison does not establish

It does not establish that keryx's orchestrators are better than these tools,
and nothing in it should be quoted as though it did. No shared task was run
through any two systems, so **no recall, precision, accuracy, or comparative
success-rate number is claimed here for any tool including our own** — the four
Greptile figures are that vendor's measurement of two models, not a measurement
of any orchestrator, and EviBound's 0-of-8 is that paper's benchmark, not ours.
This document compares *mechanisms* — which guarantees are enforced by code that
can fail, which are described in prose, which are absent — because that is the
only comparison the available evidence supports. A mechanism advantage is not an
outcome advantage: it is entirely possible that BMAD's unenforced review
vocabulary produces better real-world results than our enforced gates, and
nothing here would detect that. The question the operator asked — *are these
orchestrators better than the competitors* — remains unanswered on outcomes, and
answering it would require running a common task set through each tool and
scoring the results, which this environment cannot do. What has changed since
August is narrower and worth stating plainly: we now know the frozen-criteria
differentiator survives contact with current competitor source, we know exactly
where it is weaker than we claimed, and we know seven specific things
competitors do better.
