# Configured Git and CI observations
Version: 0.1.1

The managed-work Git observer is opt-in server configuration. It reads metadata from a configured GitHub API identity, appends an immutable observation, and exposes that observation separately from ResultSubject and Evidence. An observed CI success never creates a human Decision, accepts a product requirement, approves a PR, or changes a contributor report into trusted CI Evidence.

Each administrator repository entry has `projectId`, stable local `id`, and `objectFormat` (`sha1` or `sha256`). Optional `github` configuration contains `apiOrigin`, `owner`, `repository`, numeric stable provider `repositoryId`, optional in-memory read token, and optional `trustedWorkflows` entries with exact numeric `workflowId`, repository workflow `path`, optional exact `ref`, and allowed trigger `events`. GitHub's `path@ref` response is split into stored `workflowPath` and `workflowRef`; trust requires both to match the administrator's policy. An absent configured ref only matches an absent response ref. No ref is silently stripped into trust. `requireCi` requires every configured workflow's newest permitted exact-subject run to have completed successfully. `maxAgeSeconds` bounds observation age (default 300, maximum 86400). This is an administrator policy; contributors cannot supply a URL, credential, repository identity, CI trust label, or freshness value.

The API origin supports HTTPS, including an explicit `/api/v3` enterprise prefix. HTTP is restricted to loopback for local integration tests and development. Requests use constructed repository paths, an overall 15-second abort deadline, GET only, no redirects, at most 500 requests, at most 1 MiB per response and 8 MiB total. Up to 100 exact-SHA workflow runs are considered; a larger or incomplete provider result is unavailable rather than silently truncated into a passing conclusion. No source files, checkout contents, environment dump, SSH command, provider response URL, provider message, or credential is persisted.

`POST /hub/work/v1/projects/{projectId}/subjects/{subjectId}/observe` takes the closed `{operationId,expectedVersions,payload:{subjectDigest}}` envelope and matching `Idempotency-Key`. It requires current contributor rights, same-project subject pins and exact Attempt version before and after bounded provider reads. Current authentication is checked before receipt replay. The original receipt survives restart, same-key changed input conflicts, and provider retries reuse the original operation. `GET .../subjects/{subjectId}/observations` returns bounded authorized observation pages; `GET .../operations/{operationId}` returns the original actor's observation result as well as ordinary command results. The OpenAPI document defines both response variants.

The HTTP layer allocates a monotonically increasing generation before provider I/O and appends the resulting safe observation and project event transactionally. Later completion of an older request can append historical metadata but cannot replace the highest-generation projection. Duplicate operation receipts do not repeat provider reads. A refresh re-fetches authoritative provider state; caller event timestamps and webhook payloads are not authority. This implementation uses explicit refresh requests; no webhook listener or background reconciliation scheduler is implied.

The adapter first checks the configured stable repository identity and full name, then resolves the exact commit and optional tree. It reads PR metadata before and after CI collection and retains the final fetched head. CI metadata identifies the run, attempt, workflow ID and path, head OID, repository identities, trigger event, status and conclusion. `trusted` means the metadata matches the configured workflow identity, event and exact repository/SHA policy; it does not certify test adequacy or confer product acceptance. Fork-origin or mismatched-SHA runs cannot satisfy this policy.

Unavailable, unauthorized, rate-limited, malformed, oversized and timed-out provider responses remain unavailable. A 404 does not prove deletion. A later outage shadows an older successful observation for current PR acceptance. Observations retain the original subject digest, so force pushes and later PR heads cannot rewrite old subjects or Decisions.

Current PR acceptance requires fresh, available proof whose observed head equals the immutable subject commit, plus configured CI when required. Each artifact stores a digest of the administrator's repository and workflow policy, excluding the credential; changing that policy requires a fresh observation. A changed head fails with `subject-drift`; stale proof requires refresh. Historical commit review remains possible through an explicitly separate immutable subject whose Git artifact has `pullRequest:null`; it makes no claim of current PR approval. Flow aggregate preview and acceptance recheck the same subject policy. No observation changes historical accepted Decisions.

The provider calls follow GitHub's documented [Git commit lookup](https://docs.github.com/en/rest/git/commits#get-a-commit-object), [pull request lookup](https://docs.github.com/en/rest/pulls/pulls#get-a-pull-request), and [workflow run listing with exact head SHA](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository). Requests pin API version `2022-11-28`, which GitHub currently [supports until March 10, 2028](https://docs.github.com/en/rest/about-the-rest-api/api-versions). Tests cover the official workflow `path@ref` shape through a real local fake provider; no live GitHub compatibility claim is made. Administrators must assess workflow content and trigger safety, including `workflow_run` and `pull_request_target`; matching API metadata is not a build attestation.
