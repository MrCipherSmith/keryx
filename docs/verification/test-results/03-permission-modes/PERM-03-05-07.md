**Verification of `/mode auto` with destructive command:**
- Permission mode confirmation: User typed `yes` to enable auto mode
- Warning displayed: "⚠ auto mode skips confirmation for EVERY action, including destructive commands."
- Auto-approval present: `◇ auto-approved (auto)` tag appears
- Destructive command executed: `rm -rf ./definitely-not-a-real-dir-xyz-perm05-test` ran with exit 0
- **Missing tag:** The expected `[destructive]` label is NOT present in the auto-approval line

### Summary

PERM-05 partially works. Auto-approval for destructive commands functions correctly—the `rm -rf` command was auto-approved and executed. However, the `[destructive]` tag expected by the test catalog is missing from the transcript output.

### Analysis

The functional behavior is correct: auto mode skips confirmation for destructive commands as designed, and the command executes cleanly. The warning message explicitly states that destructive commands auto-approve in auto mode. However, the transcript line lacks the `[destructive]` metadata tag that the test catalog expects in the auto-approval line. This suggests either:

1. The implementation does not include the `[destructive]` tag in the auto-approval output text, or
2. The tag exists but is stripped during output rendering/compression

The distinction is important for audit trails: the missing tag means an observer cannot easily distinguish at a glance whether an auto-approved command was destructive or benign, which could complicate permission audits.

### Improvement / fix suggestion

Add the `[destructive]` tag to the auto-approval line when approving a command classified as destructive, regardless of permission mode (ask, trust, or auto). This ensures audit clarity and matches the test catalog's documentation.

### Summary

PERM-07 works as expected. The test demonstrates the correct separation between a session's active permission mode and the stored per-project default. When `/mode trust save` is called, the default is persisted to `permission-mode.json`. When `/mode clear` is called in a subsequent session, the stored entry is removed from the file while the current session's mode remains unaffected.

### Analysis

The test confirms two distinct concepts:
1. **Session mode**: The active permission setting for the current shell session (persists within that session even after clearing the default)
2. **Project default**: A stored entry in `~/.local/share/keryx/permission-mode.json` that applies to future sessions

The `/mode clear` command correctly removes only the project default, not the session mode. The output "This session stays on: trust" explicitly acknowledges this distinction. The file verification shows that the project's entry was completely removed (projects object is now empty), while the session continued to operate at trust mode.

Note: The session starting with `trust` mode in session b0265bd2 is interesting—it may indicate that the session inherited the mode from before the clear, or there's some other session state involved. The key point is that the stored default was successfully removed.

### Improvement / fix suggestion

None — behaves as documented. The distinction between session mode and stored default is correctly implemented and clearly communicated in the output.
