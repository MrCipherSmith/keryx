# ADR-0001: Layered Rules Model — Process, Core, Stack Packs, Activity

**Status**: Proposed 2026-11-17

**Scope**: every rule Keryx ships under `src/gdskills/bundled/rules/` and installs into `.metaproject/rules/`, the stack packs under `src/gdskills/bundled/stacks/`, the review lenses and implementation skills that apply them, and every path that hands an agent its instructions.

---

## Context

All 40 bundled rules sit flat in `rules/core/`. The folder mixes four kinds of content:

| Kind | Examples today |
|---|---|
| Agent conduct and procedures | `git-rules`, `git-concurrency`, `commit-message-formatting`, `documentation-management`, `skill-authoring`, `model-selection`, `opus-5-5-prompting`, `jobs-documentation` |
| Language-neutral coding principles | `solid-principles`, `error-handling`, `clean-architecture`, `api-contracts`, `security-baseline`, `tdd-workflow`, `definition-of-done` |
| Language- or framework-specific | `mobx-store-template`, `nestjs-dto`, `playwright-testing`, `storybook-guidelines`, `code-style-patterns` (gated `react,mobx`), most of `async-patterns` and `concurrency-patterns` (Node values, ungated) |
| Activity discipline | spread across `tdd-workflow`, `definition-of-done`, `task-implementer`, reviewer briefs and lens SKILL.md files |

An audit of the universal layer (2026-11-17) found:

- **Coverage is deep on about six topics and absent on the rest.** SOLID and function design, errors, testing, definition of done and API contracts score 3.5–4 of 5. Types and null handling, immutability and side effects, resource lifetime, logging, configuration, back-compat, performance basics and KISS/YAGNI score 1–1.5. Overall about 2.8.
- **"Universal" is 35–40% TypeScript/Node in the rules and about 60% in the lenses.** A Python or Go project inherits `Promise.all`, `AbortSignal.timeout` and event-loop rules.
- **A universal lens depends on a stack-gated row.** `review-logic` rates `!` through `code-style-patterns.mdc`, which only exists when the stack is `react,mobx`.
- **Writers get less than reviewers.** `context-resolver.ts` always loads only `tdd-workflow`, `error-handling` and `solid-principles`; lens checklists (null, types, authz, injection) never reach the code writer; `service_api` loads a React/MobX rule for backend work.
- **Rule–lens drift.** Lenses carry rows no rule owns, and two lenses claim SOLID.
- **There is no agent-conduct rule at all.** Nothing Keryx ships forbids attribution trailers or "Generated with …" lines; that rule lives only in individual users' global agent files.

The stack packs already implement most of a language and framework layer. Each `pack.json` declares a `family` (`language`, `framework`, `tool`, `capability`), detection markers, its own `rules/` (`coding-style`, `testing`, `security`, `patterns`) and per-activity skills (`implement`, `test`, `review`, `build-fix`). Packs install to `.metaproject/rules/stacks/<pack>/` (`src/gdskills/manifest/plan.ts`). Most packs are `experimental`.

A rules-ab re-measure (three repetitions per arm, v0.4.29 vs main) showed the 2026-11 refactor held recall on testing, architecture, highload and performance, and that noise follows rows that fire outside the case they were written for. Earlier measurements showed that restating textbook canon in a rule adds noise without adding recall.

## Decision

### D1. Five layers, one direction of precedence

| Layer | Holds | Loaded | Location |
|---|---|---|---|
| **process** | Agent conduct (mandatory) and engineering procedures | Conduct: always, for every agent. Procedures: by activity | `rules/process/` |
| **core** | Language-neutral coding principles with severity tables | Always, for any work on code | `rules/core/` |
| **language** | Idioms and concrete values for core principles in one language | When the pack's detection markers match | stack pack, `family: language` |
| **framework** | Framework conventions; may override core and language | When detected | stack pack, `family: framework` |
| **activity** | How to apply the layers above in one role | By task type: `implement`, `test`, `review` | `rules/activity/` |

Precedence on conflict: framework > language > core. Process conduct is never overridden. Activity rules never change a severity; they change scope and method.

The language and framework layers **are the stack packs**. No parallel `lang/` or `stacks/` folder is created; `.metaproject/rules/stacks/<pack>/` stays the pack install target.

### D2. The mandatory process block

Five constraints apply to every agent Keryx starts, directly or through a dispatch:

1. **No attribution.** No co-author trailers (`Co-Authored-By: …`) and no "Generated by/with …" lines in commit messages, PR and ticket descriptions, or comments. A model name given as technical provenance (for example "reviewers that ran, with models" in a review report) is allowed.
2. **No commit, push, merge or release without an explicit ask.** Invoking an orchestrator is the explicit ask for that orchestrator's own task-boundary commits. Merge and release always need their own explicit ask; flow `completion_outcome: create-pr-and-merge` must not merge without it.
3. **Never destroy others' work.** No `git stash` in a dirty tree, no blanket `git add -A` while parallel lanes share a checkout, no force-push to a shared branch.
4. **No secrets or personal data** in output, logs or commits.
5. **Honest reporting.** What failed, was skipped or was not verified is named as such.

The text lives once, as a shared constant in `src/lib/`, and is rendered into every delivery path:

| Path | Injection point |
|---|---|
| `.metaproject/index.md` | `renderIndexGateMarkdown` (`src/lib/templates.ts`) — the generator, since `keryx update` rewrites `index.md` |
| `CLAUDE.md` / `AGENTS.md` managed block | `src/lib/agent-entrypoint-blocks.ts` |
| `keryx shell`, `trigger`, `schedule`, ACP | `buildAgentSystemInstruction` (`src/commands/agent.ts`) |
| External agents | `EXTERNAL_RUNTIME_DIRECTIVE` and `EXTERNAL_WRITE_RUNTIME_DIRECTIVE` (`src/harness/external/prompt.ts`) |
| Shell subagents, native review agents, review bot, herdr | their prompt builders (`spawn-subagent-tool.ts`, `native-adapter.ts`, `keryx-general-worker.ts`, `review/bot/run.ts`, `commands/herdr.ts`) |
| Orchestrator dispatches | a required conduct entry in `subagent-dispatch.schema.json` and `reviewer-input.schema.json`, plus one pointer line in the flow, job and autodoc dispatch templates |

The full rule with rationale and examples is `rules/process/agent-conduct.mdc`. The block in `index.md` stays within the orientation ceiling in `src/ctx/orient.ts` (3,200 characters, 60 lines); a test pins that `index.md` stays under it so `keryx shell` keeps embedding it verbatim.

### D3. A Keryx-managed `commit-msg` hook

`src/lib/managed-git-hook.ts` gains `commit-msg`, installed, detected and removed the same way as the security `pre-push` hook (`init`, `update`, `sync uninstall-hooks`). It rejects a message that carries a co-author trailer or a "Generated by/with …" line. It does not match bare product names: subjects that mention `CLAUDE.md` or a runtime by name are legitimate. The hook does not run under a foreign `core.hooksPath` or with `--no-verify`; `keryx doctor` reports when it is inactive.

### D4. Core holds principles, not idioms

- A core rule states a principle, its severity table, and the canon it builds on ("Canon applies: …"). It does not restate the canon.
- A core row must be applicable without knowing the language. Concrete values (`!`, `any`, `Promise.all`, `AbortSignal.timeout`) belong to the language pack and are rated there.
- Severity lives only in rules. A lens may point at a rule's row; it may not add, restate or re-rate one.
- Gaps the audit found are filled as new core rules, each measured before it ships: types, null and invariants; side effects and immutability; resource lifetime and logging; code-level back-compat and refactor scope.

### D5. The activity layer

- `rules/activity/implement.mdc`: order of work, change scope and opportunistic refactoring, back-compat, the link from "done" to the coding rules.
- `rules/activity/test.mdc`: test design — what to pin, boundaries, fixtures, determinism.
- `rules/activity/review.mdc`: review discipline independent of stack — review the change, not pre-existing debt; a finding names its failure scenario; `info` is not a defect; one finding per defect across lenses; how to calibrate severity.

Pack skills keyed by activity (`implement`, `test`, `review`) remain the place for stack-specific activity guidance.

### D6. Symmetric loading

`context-resolver.ts` resolves the same base for writers and reviewers: process conduct, core, the detected language and framework packs, plus the activity rule. Reviewers add their lens; writers add the task-type rules. The resolver stops returning an empty rule set for `--for review`.

### D7. Lenses become thin

A lens states which slice of core, language and framework it applies, and how (its method, its scope, its evidence bar). Checklists that today live only in `review-logic` and `review-security-code` move into core or language rule rows so writers see them too. The set of lenses does not change in this ADR.

## Migration

Each content phase is gated on the rules-ab bench: recall not lower and noise not higher than the arm it replaces, three repetitions per arm.

| Phase | Change | Measured |
|---|---|---|
| P1 | Process conduct: shared constant, every injection point, schema fields, `agent-conduct.mdc`, `commit-msg` hook, `create-pr-and-merge` merge gate | No (no review content changes) |
| P2 | Installer: install `rules/process/` and `rules/activity/`; teach retired-rule handling to record a **move** (old path and every shipped hash → new path) so projects drop stale `core/` copies | No |
| P3 | Move procedures (`git-*`, `commit-message-formatting`, `documentation-management`, `skill-*`, `model-selection`, prompting, jobs, requirements) to `rules/process/`; update skill and doc references | No |
| P4 | Move stack content into packs: `mobx-store-template` → `mobx`, `nestjs-dto` → `nestjs`, `playwright-testing` and `storybook-guidelines` → their packs, React/MobX rows of `code-style-patterns` → `react`/`mobx`, Node values of `async-patterns` and `concurrency-patterns` → `ts-js-node`; core keeps the neutral principle | Yes |
| P5 | Activity layer: extract review discipline from briefs and lenses into `activity/review.mdc`; `implement` and `test` from `task-implementer`, `tdd-workflow`, `definition-of-done` | Yes |
| P6 | Fill core gaps (D4), one rule per change | Yes, each |
| P7 | Resolver symmetry (D6) and thin lenses (D7) | Yes |

## Consequences

- An agent started by any Keryx path receives the five conduct constraints, not only the top-level session.
- A project in any language gets a core that applies to it; TypeScript projects get the same rows as today, from the `ts-js-node` pack.
- Writers and reviewers load the same standard, so a defect a reviewer can flag is one a writer was told about.
- Stack packs move from optional extras to the carrier of language and framework rules. Their detection and their `experimental` stability become load-bearing: a missed detection now drops rules a project used to get from core. P4 needs detection tests per moved rule.
- About 31 skill files and about 125 test and documentation files cite `rules/core/<name>`; P3 and P4 rewrite them. `rule-references.ts` (`KERYX_RULES_DIR`), `import-skills.ts` core shadowing and `install-manifest.json` change with them.
- `jev-rules` already uses `applies_to: process` as a category for process-type rules. The meaning matches the new layer; the category is kept and documented as the same concept.

## Rejected alternatives

- **New `lang/` and `stacks/` folders beside the packs.** Duplicates a mechanism that already has families, detection and per-activity skills, and collides with the `rules/stacks/<pack>/` install target.
- **Conduct only in `index.md`.** Only the top-level session reads it; workers, reviewers, shell subagents, external agents and scheduled runs do not.
- **Conduct only as a rule file.** Rule loading is per-path and partial today; the constant is what reaches every path.
- **One merged review lens.** Rejected earlier without a like-for-like measurement; this ADR keeps the lens set and changes only where lens content comes from.
