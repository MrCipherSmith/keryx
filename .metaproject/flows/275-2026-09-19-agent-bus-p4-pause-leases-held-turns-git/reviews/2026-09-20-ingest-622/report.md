## Major Issues

- [F-001] major: `ApprovalMeta.publishLeaseDetail` is computed in `executeCall` but NO approver ever reads it. Neither the TUI approver nor the readline approver renders the lease's holder or reason in the prompt; both show only a generic boolean-derived string (TUI title "⚠ a peer's git-publish lease applies — allow?", readline hint "a peer's git-publish lease applies — will not be remembered"). `ShellApprovalEval` does not carry the field at all, and `pickShellApproval` takes `publishLease` as a bare boolean.
  - impact: specification §4.3's `git-publish` row requires: "The prompt names the lease, its holder and its reason." It does not. The operator who is asked to approve a `git push` under `auto` mode has no way to tell WHICH peer asked them to hold off or why — exactly the information that makes an unattended-mode escalation actionable rather than a speed bump the operator learns to answer `y` to. `publishLeaseDetail` is dead code today: it is produced, typed, documented and unit-asserted, but never consumed by production.
  - suggested_fix: Thread the detail through: add `publishLeaseDetail?: string` to `ShellApprovalEval` (copied from `input.meta?.publishLeaseDetail` in `evaluateShellApproval`), pass it as a new optional arg to `pickShellApproval` and render it in the title or subtitle (e.g. `⚠ git-publish lease held by @alice — "cutting the release" — allow?`), and include it in `formatShellApprovalHints`'s `publishLease` line for readline. Add an assertion to `shell-approval.test.ts` and the TUI approval test so the field cannot go dead again.
  - evidence: Producer: src/commands/agent.ts:3280-3282 (`publishLeaseDetail: \`held by @${publishLeaseHolder.name} — "${publishLeaseHolder.reason}"\``) and its docstring at src/commands/agent.ts:94-105. - [F-002] major: Both `busLeasesFromClient` adapters wire `AgentDeps.busLeases.heldBy()` to `PauseLeaseView.heldBy()`, which is hard-scoped to `turns`: `active.find((lease) => lease.scope === "turns" && isOverridable(lease))` (src/bus/pause.ts:343-346). The only caller is the `git-publish` floor in `executeCall`, which calls it right after `appliesToMe("git-publish")` returned true. So the holder/reason attached to a publish prompt is read from the wrong lease.
  - impact: Two wrong outcomes, both in production only (the unit tests hand-write a stub `heldBy` that returns the right thing, so nothing catches this). (a) Common case — a `git-publish` lease applies and no `turns` lease does: `heldBy()` returns undefined, so `publishLeaseDetail` is omitted and the prompt has no holder/reason even once F1 is fixed. (b) A `turns` lease from a DIFFERENT holder also applies (possible: a turn already running when a `turns` lease lands keeps executing tool calls — spec §4.3 "A turn already running continues"): the prompt would name that unrelated holder and reason as the reason the push is being escalated. Misattributing a security prompt is worse than omitting the attribution.
  - suggested_fix: Give the adapter a scope-aware lookup instead of reusing `held()`'s `turns`-only accessor — e.g. add `appliesToMeLease(scope: LeaseScope): PauseLease | undefined` to `PauseLeaseView` (the existing `appliesToMe` already does the same `find` and discards the lease) and have both adapters call `appliesToMeLease("git-publish")`. Then narrow `AgentDeps.busLeases.heldBy()` to take the scope, or drop it in favour of one call that returns `{applies, holder, reason}`. Replace the stubs in `agent-permission-mode.test.ts` with a test that builds the real adapter over a real `createLeaseView` holding only a `git-publish` lease — that test fails today.

- [F-003] major: In the readline agent REPL, the task-notification wake starts a main-agent turn without consulting the `turns` hold. `runAgentRepl`'s loop has two `runAgentTurn` call sites: the operator line (src/commands/shell.ts:2315, reached through `runOperatorLine`, correctly gated by `isHeld()` at :2773) and the completion wake (src/commands/shell.ts:2383, reached when `readLineOrCompletion()` returns `kind: "completion"`), which checks only the auto-wake cap. The TUI gates the equivalent path (`leaseView()?.held() !== true` is part of the `idle` test at src/tui/tui-shell.ts:6957); readline does not.
  - impact: specification §4.3's `turns` row is normative per-instance: "No new main-agent turn starts from any source: an operator line ..., a `/queue force` item ..., a task-notification wake, or a bus wake." A peer holds this instance's turns; a background shell task finishes; the held readline shell starts a full main-agent turn anyway — the exact unattended activity the peer paused it to prevent, on the same shared checkout. It also makes the two surfaces behave differently under the same lease, which the specification treats as one enforcement rule. Worse, the woken turn can itself reach `shell_exec`, so the hold is bypassed for tool work as well, not just for the notification text.
  - suggested_fix: Gate the completion branch the same way the operator branch is gated — e.g. right after `if (input.kind === "completion")`, `if (isHeld()) { agentIo.onSystem?.(heldNotice-style line saying the completion will be reported once the lease ends); printPromptWithBusNotice(); continue; }` — without consuming the auto-wake budget. ## Minor Issues

- [F-004] minor: Three of the five publish rules match the subcommand by POSITION (`positionals[0] === "release"` / `"publish"`), while the other two match by MEMBERSHIP (`positionals.includes("push")` / `.includes("merge")`). A global flag that takes a SEPARATE value before the subcommand therefore shifts `positionals[0]` onto the flag's value and the rule misses: `gh -R owner/repo release create v1`, `gh --repo owner/repo release create v1`, `npm -w pkg publish`, `npm --loglevel warn publish`. `--flag=value` forms are unaffected (they are filtered as flags).
  - impact: AC6 requires `isPublishCommand` to match "gh release, gh pr merge, npm publish and bun publish" without qualifying the form, and specification §4.3's `git-publish` row lists the same five unqualified. `gh -R` and `npm -w` are ordinary spellings in a multi-repo / workspace checkout, so a real publish can skip the lease floor and run unattended under `auto`. This is an escalation-only classifier (ADR-0009), so it is a missed prompt, not a bypassed deny — hence minor, not a blocker — but the inconsistency with the two rules that already got it right looks like an oversight rather than a decision.
  - suggested_fix: Use membership for all five, matching `isGitPushSegment`/`isGhPrMergeSegment`: `v.positionals.includes("release")` for `gh`, `v.positionals.includes("publish")` for `npm`/`bun`. Cost is a false positive on e.g. `npm run publish-docs` (a single extra prompt, which is the direction ADR-0009 says to fail). Add `gh -R o/r release create v1` and `npm -w pkg publish` to the `PUBLISHES` table in src/lib/command-risk.test.ts.
  - evidence: src/lib/command-risk.ts:276-290 — `isGhReleaseSegment` (`positionals[0] === "release"`), `isNpmPublishSegment` (`positionals[0] === "publish"`), `isBunPublishSegment` (`positionals[0] === "publish"`) versus `isGitPushSegment` (`positionals.includes("push")`, :272-274) and `isGhPrMergeSegment` (`.includes("merge")`, :280-282). `positionals()` (src/lib/command-risk.ts:40-44) drops the command word and every `-`-prefixed token but keeps a flag's separate value. The new test table (src/lib/command-risk.test.ts:102-124) exercises only flag-free and `--flag value`-after-subcommand forms, so it passes.
  - confidence: high
  - class_scope:
    sites: ["src/lib/command-risk.ts:277", "src/lib/command-risk.ts:285", "src/lib/command-risk.ts:289"]
    enumeration_method: "Read every member of `PUBLISH_RULES` (src/lib/command-risk.ts:292-298) \u2014 the complete rule set consulted by `isPublishCommand` \u2014 and classified each by whether it indexes `positionals` or searches it. ## Nits

- [F-005] nit: `keryx bus pause --ttl`'s own error message advertises a form the command then refuses: `parseLeaseTtl` accepts a `s` suffix and the usage text says "--ttl must look like 30m, 2h or 45s", but `createPauseLease` refuses anything below `MIN_LEASE_TTL_MS` (1 minute) with `ttl-out-of-range`. `--ttl 45s` is therefore always rejected, by a different error than the one that suggested it.
  - impact: A confusing two-step refusal for an operator following the tool's own hint. No behavioural risk.
  - suggested_fix: Either drop `45s` from the usage string (and keep `s` parsing for a value like `90s`), or state the 1-minute floor in `PAUSE_USAGE` / the `--ttl` error text.
  - evidence: src/commands/bus.ts:196-203 (`parseLeaseTtl`) and :224 (the error text naming `45s`); src/bus/pause.ts:40 (`MIN_LEASE_TTL_MS = 60 * 1000`) and :116-121 (the `ttl-out-of-range` refusal).
  - confidence: high

- [F-006] nit: AC1's "targets never including the holder" is enforced only for the single-target case. `createPauseLease` calls `resolveRecipients`, which does not exclude the caller, and then refuses `recipient-is-self` only when `targets.length === 1 && targets[0] === holder.instanceId`. If a live `@name` were held by more than one instance, one of them the holder, the stored lease's `targets` would contain the holder's own id.
  - impact: No runtime effect: `createLeaseView`'s `isOverridable` independently excludes the holder (`lease.holder.instanceId !== options.instanceId`), so a holder is never held by its own lease whatever the file says. Probably unreachable anyway, since join uniquifies names (`nameWasTaken`). Reported only because AC1 states the invariant about the stored lease, not about the view.
  - suggested_fix: Filter the holder out of `targets` in `createPauseLease` before the `recipient-is-self` check, and refuse when the filtered list is empty. One line, and it makes the stored file match the AC's wording.
  - evidence: src/bus/pause.ts:124-127 (the single-target-only self check); src/bus/send.ts:103-122 (`resolveRecipients` never removes the caller); src/bus/pause.ts:325-328 (`isOverridable`, which is what actually holds the invariant today). Test coverage stops at the single-target case: src/bus/pause.test.ts:164 "the holder is never a target: an explicit @name resolving only to the holder is refused recipient-is-self".
  - confidence: medium
