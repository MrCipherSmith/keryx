## Round 2 findings

### R2-1 [info] The judge correctly generalizes to an unanticipated third-fix shape; not demonstrated to be a leniency bug

- **File:** `src/gdskills/bundled/stacks/ts-js-node/skills/nodejs-build-fix/evals.json` (`no-ts-ignore-suppression`).
- **Problem:** A live attack proposing a TypeScript getter accessor (`get total(): number;` added to the `OrderDraft` interface) passed 3/3. On inspection, this is not obviously wrong: the scenario's own rubric text explicitly allows either "adds a `total: number` (or the correctly-typed) property" OR a derived/computed read, and an interface getter literally adds a typed, non-`any`, non-suppressed `total` property that satisfies structural typing — it is a third concrete variant of the same two calibrated answers (`known_right`'s "stored" and "derived" branches), not a bypass. The judge's reasoning correctly points at the concrete declaration added, same as it does for the two calibrated `known_right` texts.
- **Residual uncertainty:** whether a getter-only (read-only) property would break some other, unshown call site that assigns to `order.total` cannot be determined from the scenario's own text — the prompt supplies no such context, so the answer cannot be faulted for not addressing it either.
- **Suggested fix (optional, not required for this PR):** if the authors want the calibration set to also pin this case, add a third `known_right`-equivalent (or extend the existing one) naming the getter-accessor form explicitly, so future prompt/rubric edits are tested against it too. No action required to close this PR; recorded as a follow-up.

### R2-2 [minor] The offline AG replay path (`recordedJudge`) does not itself reject an error-carrying "pass" sample, unlike the report gate

- **File:** `src/gdskills/governance/judge-recordings.ts:204` (`recordedJudge`), contrast `src/gdskills/governance/eval.ts` (`regradeRecordedReport`'s R1-8 check) and `src/commands/skills-governance.ts` (`judge-check`'s own `mismatch` computation, which does check `sample.error !== undefined`).
- **Problem:** `regradeRecordedReport` (the *eval.json report* gate) now correctly refuses a `TrialRecord.judge.error !== undefined && verdict === "pass"` combination (R1-8, verified above). `judge-check` (the *live* command that verifies AG holds) also treats an error-carrying sample as a mismatch. But `recordedJudge`, which turns a `JudgeRecordingFile` back into a `Judge` for OFFLINE replay (used by the integrity guard to prove AG without live calls), does not itself apply the same rule: constructing a recording whose `known-right` sample carries both `error: "..."` and `verdict: "pass"`, then calling `gradeScenarioAnswer` through `recordedJudge`, returns `passed: true` — i.e., a hand-edited recording with a manufactured error+pass combo replays as a clean pass rather than being rejected. This mirrors R1-8's forgery shape but in the recording file rather than the report file.
- **Context that limits severity:** `judge-recordings.json` files are already explicitly documented (this round's R1-2 fix, `cli-reference.md:2464`) as "a hand-writable file... proves the anti-gaming set was checked against a live judge at record time, not that nobody could have edited it afterward" — the same disclosed threat model as the eval report. `buildEvalJudge` also never produces this combination genuinely (an error is always paired with `verdict: "fail"`), so this is not reachable through any real `judge-check --record` run — only through direct hand-editing, which the docs already say is out of scope for what a recording proves.
- **Evidence:** `review2/ag2.ts` — `error-sample known-right: passed = true (EXPECT false/fail)`.
- **Fix (optional hardening, not blocking):** add the same guard `recordedJudge` (or a thin `validateJudgeRecordingFile`) applies before use: reject/throw on `sample.error !== undefined && sample.verdict === "pass"`, for consistency with `regradeRecordedReport` and `judge-check`.
