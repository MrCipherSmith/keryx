## Recommendation

Retain our delivery service, durable recovery model, bounded request admission and managed-lineage reconciliation as the integration baseline. Both snapshots contain useful native lifecycle and participant fixes; keep the shared behavior and compare tests rather than layering two implementations. Do not wholesale replace `server.ts`, `remote-v2/index.ts`, `mutation-queue.ts` or `work/execution.ts` from either branch: they combine several independent overlapping changes. Remote's injectable queue clock is a potentially useful isolated improvement; its unbounded internal queue and recovery retry policy are incompatible with our safety invariants.

## Native queue lifecycle and Attempt authority

Both snapshots now enforce the authenticated Attempt participant on start/report/submit/withdraw/subject/evidence. `work/handlers-attempts.ts:participant` differs in argument shape/message only; both reject participant mismatch and agent method=human. Retain one implementation and union meaningful cases; our `participant.authorization.test.ts` covers the six-command matrix with actual SQLite-backed Work commands; remote places cases in `handlers-attempts.test.ts`.

Both ingest native edit observations without deliberately throwing the old409 that wedged event ingestion; both handle in-place native edit then remove, original native reauthorization lineage and reserved pins. Remote `work/execution.ts:queueObserved`137–151 declines transfer if the reservation is already released, then `beforeAdmission` explicitly checks an edited original's released managed reservation. Ours stores a released replacement tombstone. These are different representations of the same no-silent-ad-hoc goal; test delayed multi-edit lineage before changing representation, do not install both transfer mechanisms.

Important difference: remote `remote-v2/queue.ts:drainSessionQueue` calls `admissionRefused` on caught HubFailure; `work/execution.ts:admissionRefused`236–247 releases on `forbidden`, `not-found`, `stale-catalogue`, `session-closed`, `recovery-required`, `work-association-stale`, `work-binding-authority`, `execution-proof-mismatch`. Our final T31 removes this callback: guard refusal is not a native terminal/removal fact, and reauthorization/config recovery can make the still-queued item admissible. Remote explicitly preserves many temporary/quota/stale-version codes, so it is not the original release-on-every-failure implementation; nevertheless the remaining code list conflicts with our stricter terminal-evidence invariant. Recommendation: keep ours release ownership and retry/configuration/native receipt tests.

Performance difference: remote `work/execution.ts:reconcileSession`84–112 has the important early `pendingReservationsForSession` gate (zero history reads when no pending work), then reads **all queue, command and operation rows in that session** and performs lineage scans. Ours `remote-v2/storage.ts:managedReconciliation`67+ restricts rows to pending managed roots and recursive relevant lineage using indexed IDs; `work/execution.reconciliation.test.ts` tests cold-session history is never parsed. Remote's test at `work/execution.test.ts:114` verifies zero-history empty case and one queue read, not bounded rows with one pending reservation plus large cold history. Keep ours indexed scoped read; do not downgrade to the empty-session optimization alone.

2. Keep our `delivery-service.ts`, job schema/archive and Git uncertain/inspection handling as one coherent unit with server routing/tests/docs.
3. Keep our `execution.ts` guard release policy and scoped repository API together. Retain shared native edit and participant fixes once, not duplicated hooks.
4. Keep our mutation queue +server admittedRequest forwarding +v2 auth ordering +1013 handling +native cleanup together. Remote whole-file replacement would remove these.
5. Remote tests are evidence of its contracts, not validation of ours; adapt only after choosing behavior. No integration or new shared tests performed in this comparison.
