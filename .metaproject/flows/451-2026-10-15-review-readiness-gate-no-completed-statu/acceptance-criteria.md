# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- Every criterion ends with [verify: exec `<command>`],
  [verify: invariant `<command>`], [verify: judged] or
  [verify: none — <reason>].
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: `keryx review readiness <review> [--json]` is read-only and prints one checklist with a verdict READY or NOT READY. Each item has an id, pass/fail/waived, the evidence it read and, when failing, the exact command that repairs it. The items reuse the existing checks and are: (1) every changed file is covered by a wave or a recorded waiver; (2) blast radius: no `dropped` file is left unreviewed (every dropped file is covered by a chunk pass, or the cut is waived); (3) every planned reviewer was dispatched AND its result ingested (no `dispatchErrors`, no reviewer whose JSON never came back); (4) the verifier checked every finding it was supposed to check, or the report states how many it did not; (5) the ledger is READY (no finding without a disposition); (6) `coverage.md` states ingest status truthfully (a reviewer that was dispatched but not ingested is not listed as "run"); (7) the report head matches the PR head; (8) pending mutation candidates and parity warnings are named in the report; (9) for a PR-bound package the changed-file count equals the PR's file list. [verify: exec `bun test src/review/readiness.test.ts`]
- AC2: A replay on a synthetic package shaped like `pr7932-r1` (25 changed files, 341 candidates, 301 dropped, ledger NOT READY with raw findings, four reviewers never ingested, one result missing, coverage.md listing everything as "run") yields NOT READY with exactly those items failing, each naming its repair command; the same package after the repairs is READY. [verify: exec `bun test src/review/readiness.test.ts`]
- AC3: `keryx review complete` runs the readiness checklist and refuses while an item fails, printing the failing items. A failing item can be waived only with `--waive <item> "<operator's own words>"`; the waiver is written into the manifest and into the first lines of `report.md` ("Partial review: <item> waived by the operator: <quote>"). A waiver without a quote is refused. Completion without a published review (report only) goes through the same checklist. [verify: exec `bun test src/review/readiness.test.ts src/review/completion-gate.test.ts`]
- AC4: `keryx review publish <review> [--event COMMENT|REQUEST_CHANGES|APPROVE]` is the only keryx path to GitHub: it runs the checklist, and with NOT READY it refuses and lists the items. `--partial` publishes anyway, but the posted body then starts with a "Partial review" header that lists each failing item and what was not covered, so the page itself says what is missing. The review body is shown to the operator before posting, as the project rules ask. [verify: exec `bun test src/review/publish.test.ts`]
- AC5: The keryx shell guard refuses a direct `gh pr review`, and `gh api` calls that create a pull request review (`POST .../pulls/<n>/reviews`, `PUT`/`POST` of review events), while a managed review package bound to that PR exists and is not READY; the refusal names `keryx review publish`. With no package bound to the PR the guard stays silent. [verify: exec `bun test src/hooks/review-publish-guard.test.ts`]
- AC6: When the blast radius cuts files, `keryx review blast-radius` prints the number cut and the next command (`keryx review chunks plan --package <review>`), and `review start` for a package with a non-empty `dropped` list creates the chunk plan. An autonomous run (`keryx review run --autonomous`) then runs every wave without asking, up to the existing 25-pass ceiling; an interactive run asks the operator first, as it does today above the ceiling. `review-orchestrator` `SKILL.md` has a numbered step "Cut blast radius: run the waves" instead of one sentence inside a paragraph, and `SKILL.md` does not grow past its recorded length ceiling. [verify: exec `bun test src/review/blast-radius.test.ts src/review/chunks.test.ts src/gdskills/review-orchestrator-skill-parity.test.ts`]
- AC7: A recount against a base that changes the file count by more than 3x the PR's own file list (the `--ref develop` case: 25 became 1547) is flagged by the checklist item 9 and by `review blast-radius` with both numbers, and does not overwrite the package's recorded scope. [verify: exec `bun test src/review/blast-radius.test.ts src/review/readiness.test.ts`]
- AC8: The checklist shows in the TUI and in `keryx review status`: a "Readiness" block in the review sidebar (verdict plus the failing items) and the `/review readiness` view, from the same projection the CLI prints, so no surface states a verdict another does not. [verify: exec `bun test src/review/parity.test.ts src/tui/review-readiness.test.ts`]
- AC9: The rule is stated once in `review-orchestrator` `SKILL.md` ("completed means the readiness checklist passed or each failing item is waived in the operator's words"), with the checklist in `SKILL.detail.md`, in `docs/docs/guides/review-with-a-record.md` (including the named limit: a publisher outside the keryx shell guard is not stopped), and the commands in `docs/docs/cli-reference.md`; a CHANGELOG entry records the behaviour change. [verify: exec `bun test src/gdskills/review-orchestrator-skill-parity.test.ts src/gdskills/review-skills-iron-laws.test.ts`]
- AC10: `bun run check` is green. [verify: exec `bun run check`]
