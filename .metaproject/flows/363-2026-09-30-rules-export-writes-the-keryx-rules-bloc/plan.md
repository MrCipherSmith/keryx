# Implementation Plan

Status: ready

## Approach

Reuse what flow 361 built instead of a parallel mechanism:

- **Target resolution** — the Claude and Codex rules-export adapters stop carrying a fixed `relativePath`. They follow the pattern T8 introduced for Claude settings (`relativePathFor(root)` + `relativePathCandidates` on `SurfaceAdapter`, one owner per candidate path in the registry, `assertRegistryCoherent` over all candidates), resolving through `normalizeEntrypointTargets` / `resolveProjectEntrypoints` (`src/rules/entrypoint-targets.ts`, `src/rules/entrypoint-writers.ts`). The same resolver feeds install, uninstall, probe, inspect, dry-run, doctor and install-state. `bundle import --render-for` goes through `renderRulesForHarnesses` and follows automatically.
- **Codex override** — `AGENTS.override.md` is regenerated by keryx (`renderCodexOverride`: provenance line, `keryx:index` block, `AGENTS.md` content). The regeneration carries an existing `keryx:rules` block from the current override into the new one (placed after the index block), so `update`/`rules sync` never drop it; the staleness hash stays the hash of `AGENTS.md` only. The rules block itself is written into the override by the rules-export surface through `markdown-block.ts` as today. With Codex `skip`, no `AGENTS.md`, or an override keryx did not generate, the Codex surface writes nothing and returns a warning naming why.
- **Migration** — extend flow 361's team-file migration (`moveBlockOutOfTeamFile` and its HEAD-restore / strip-only / committed-in-HEAD cases in `entrypoint-writers.ts`) to the `keryx:rules` marker pair, and have it re-install the block at the local target when it moved one (the rules-export install-state says the surface was installed). Committed in HEAD → untouched, no local duplicate.
- **Doctor** — `src/rules/entrypoint-inspection.ts` / `checkEntrypoints` gain the `keryx:rules` case.
- **Other readers** — `distill.ts` already preserves `keryx:rules` blocks; `review-jev-rules.ts` strips managed blocks from team files — check they still behave with the block gone from the team files. Security audit already scans `CLAUDE.local.md`/`AGENTS.override.md`.

## Steps

1. T5 — Target resolution for the Claude/Codex rules-export surfaces, override carry-over, skip/no-source warnings; registry, install-state, dry-run, doctor-integration and `bundle --render-for` follow.
2. T6 — Migration of an uncommitted `keryx:rules` block out of tracked `CLAUDE.md`/`AGENTS.md` in `update`; `keryx doctor` entrypoints warning; docs, CHANGELOG (0.3.46), version bump.
3. T7 — Verification: the branch CLI against throwaway git repos (fresh install with local scopes, shared scope, Codex skip, legacy migration, second-run idempotency, `update` regenerating the override keeps the rules block).
4. T3 — targeted suites, typecheck, lint; CI on the PR for the full suite. T4 — review.

## Risks

- `AGENTS.override.md` now has two keryx-managed blocks; the provenance/staleness logic and `stripManagedIndexBlock` must leave the rules block alone and vice versa.
- A developer who installed rules-export before 0.3.46 has the block committed or uncommitted in CLAUDE.md/AGENTS.md; both cases are covered by the migration rules above.
- main moves fast: check `compare/<base>...main` right before merging and rebase if needed.
