# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- Every criterion ends with [verify: exec `<command>`],
  [verify: invariant `<command>`], [verify: judged] or
  [verify: none — <reason>].
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: With `KERYX_AGENT_MAX_ROUNDS` unset, the round limit of a turn resolved for the `auto` permission mode is 200, for `trust` it is 200 (flow 418 T5) and for `ask` it is 40; a unit test asserts all three values. [verify: exec `bun test src/commands/agent.test.ts`]
- AC2: `KERYX_AGENT_MAX_ROUNDS` wins in every mode (a value of 50 gives 50 in `auto`), and a value above 200 is clamped to 200; a unit test asserts both. [verify: exec `bun test src/commands/agent.test.ts`]
- AC3: In `auto` mode, reaching the limit never calls `askUser`: with the env limit at 3, a scripted turn extends itself in allotments of 3, capped at 200, prints the `[budget]` line each time, and continues; a test asserts `askUser` was not called. [verify: exec `bun test src/commands/agent.test.ts`]
- AC4: In `auto` mode, a turn that reaches 200 rounds stops with `finishReason: "budget"` and a `[budget]` message naming 200 as the ceiling and `KERYX_AGENT_MAX_ROUNDS`; no further provider request is made after it. A test asserts the reason, the text and the request count. [verify: exec `bun test src/commands/agent.test.ts`]
- AC5: `ask` and `trust` keep the question: at the limit "Increase limit and continue / Cancel" is still asked, a reset grants one more allotment of the mode (40 in `ask`, 200 in `trust`), and without a wired `askUser` the turn still stops; the existing round-limit tests pass unmodified. [verify: exec `bun test src/commands/agent.test.ts`]
- AC6: The shell reads the permission mode at the start of each turn: after `/mode auto` the next turn runs with 200, after `/mode trust` with 200, after `/mode ask` with 40, without restarting the session; a shell test asserts the round limit applied to a turn in each mode. [verify: exec `bun test src/commands/shell`]
- AC7: Every surface that shows the mode also shows the effective round limit: the readline `/mode` output, the TUI mode indicator or its modal, and `/help` for `/mode`; the numbers come from one function, so the three cannot disagree. A test asserts the text on the readline and TUI paths. [verify: exec `bun test src/tui/ src/commands/shell`]
- AC8: README and the docs site page that describes permission modes say that `auto` allows 200 rounds per turn without a question, that `trust` allows 200 and `ask` 40 and both still ask before extending, and that `KERYX_AGENT_MAX_ROUNDS` overrides all three up to 200; both are updated in the same change, and the doc-link check passes. [verify: exec `bun run check:doc-links`]
- AC9: `bun run typecheck` and `bun run lint` pass, and a CHANGELOG entry under the next version states the change and the 40/200/200 split. [verify: exec `bun run typecheck && bun run lint`]
- AC10: In a live `keryx shell` in `auto` mode a scripted prompt that needs more than 40 tool rounds runs through without the round-limit question appearing; the operator sees the run end normally. [verify: judged]
- AC11: Automatic review is a run mode of a turn, separate from the permission mode and from subagents: a review package created with `keryx review start|attach|ingest --automatic` records `manifest.automatic: true` (shown by `review status`), and a turn that the operator opened by asking for an automatic review runs with a 200-round limit in any permission mode (ask, trust, auto), without the round-limit question, and stops at 200 with the same `[budget]` message as `auto`. A line that is not from the operator, a turn without the request, and an unattended trigger runner keep the mode limit (40 in ask). An explicit `deps.maxRounds` in `auto` still falls back to the question. The subagent 40/200 split is dropped: subagents keep 10 and 24 in every mode. Tests assert the 200 limit in ask, the unchanged 40 without the mark, the mark on the manifest and in `review status`, the request detection, and the unchanged subagent limits. [verify: exec `bun test src/commands/agent.test.ts src/commands/automatic-review.test.ts src/commands/review.test.ts src/commands/trigger-agent-task.test.ts src/harness/tool/builtin/spawn-subagent-tool.test.ts`]
- AC12: In an automatic review the shell approves, without a prompt, the review CLI set as `keryx review --help` lists it on main, in its real flag syntax, for the review package bound in that turn only: `start|attach|ingest --automatic` (once, before a package exists), `status|complete <this review>`, `ledger build <dir> --package <pkg>`, `severity-audit|context-collect|compare-reference|mutate --package <pkg>` (`mutate` only with a literal `bun test` as `--test`), `retry-plan --manifest <pkg>/...`, and `scope|blast-radius` writing only inside the package, plus `apply_patch` inside that package directory. A command that is not exactly one literal review command (any pipe, `;`, `&&`, redirect, substitution or newline), that names another review or a path outside the package, or any other `review` subcommand is asked as usual, and the hard floors (destructive, credentials, publish lease, read-only mode, untrusted origin, hook-asked) are never lowered. Tests assert approval for the bound package for each subcommand and refusal for each of those cases. [verify: exec `bun test src/commands/automatic-review.test.ts src/commands/agent.test.ts`]
- AC13: In an automatic review `ask_user` and the permission menu reach the operator only in an emergency, a closed list: (1) a command outside the review package or outside the review CLI set, (2) a destructive action, (3) a provider authentication failure, (4) a gate refusal that needs the operator quote (a waiver), (5) a decision on a reduced reviewer set, (6) a provider error after the retries. Every other `ask_user` is answered with its recommended option (else the first) and counted, except a question tagged irreversible/action or with a review `policy`, which passes to the host (the arbiter or the operator) and is counted as manual; cases (4) and (5) are accepted only after `review complete` has actually refused, and cases (3) and (6) end the turn with the error. The list is shown by `/mode` and written in the docs and CHANGELOG. Tests assert the default answer, the pass-through, the refused early claim and the emergency that reaches the operator. [verify: exec `bun test src/commands/automatic-review.test.ts src/commands/agent.test.ts`]
- AC14: Every automatic-review turn ends with a disclosure counter of manual inputs (the operator answered or approved) against automatic inputs (the shell answered or approved), written to `automatic-run-inputs.json` in the review package with every entry, and said as one line in the session; a test asserts the counts for a run with both kinds (flow 419 AC8 reads it). [verify: exec `bun test src/commands/automatic-review.test.ts src/commands/agent.test.ts`]
- AC15: No gate bypass: `review complete` and its refusals behave exactly as without the mark, nothing in the shell or the manifest flag completes, waives or skips a review gate, and the existing review tests pass unmodified. [verify: exec `bun test src/commands/review.test.ts`]
- AC16: Every surface names the automatic review run mode: the TUI sidebar Mode row shows `· automatic review` during such a turn, the readline `/mode` output and the TUI mode picker print its limit and emergency list, `/help` for `/mode` names it, and README, the permission-modes guide, the CLI reference (`--automatic`) and the CHANGELOG [Unreleased] are updated in the same change; the doc-link check passes. [verify: exec `bun test src/tui/tui-shell.test.ts src/commands/shell-agent-repl.test.ts src/standard/help-groups.test.ts && bun run check:doc-links`]
