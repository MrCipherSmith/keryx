# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: A line that starts with "/" in a topic goes to a command gateway with an explicit allowlist of commands. A command not on the list answers in the topic "not available remotely" with the reason; nothing is run. [verify: exec `bun test src/remote/command-gateway.test.ts`]
- AC2: Text commands (`/help`, `/status`, `/doctor`, `/new`, `/compact`, `/think`, `/goal`, `/queue`, `/plan`, `/reasoning`, `/theme <name>`, `/schedule`, `/rewind`, the jev text commands) run from the topic and their output (today a local transcript line or a toast) comes back to the topic, redacted and rendered like any reply. [verify: exec `bun test src/remote/command-output.test.ts`]
- AC3: `/model` in the topic answers with buttons for the models of the current provider (at most 8 rows, paged beyond that). A press switches the model, the topic gets a one-line confirmation, and the buttons are removed. [verify: exec `bun test src/remote/command-model.test.ts`]
- AC4: `/connect` answers with buttons for the connected providers, then for that provider's models; the choice switches provider and model as the local `/connect` does. No Disconnect, no key, URL or token step is offered remotely. [verify: exec `bun test src/remote/command-connect.test.ts`]
- AC5: Picker buttons carry an opaque `callback_data` of at most 64 bytes that never starts with the approval prefix, is single-use, expires, and is bound to the session and the message. A replayed press, a press from another user, topic or session, and an expired press change nothing and are answered. [verify: exec `bun test src/remote/picker-callbacks.test.ts`]
- AC6: `/mode trust|auto` and `/plan off` (typed or chosen from the `/mode` picker) run only after a Yes/No button press in the topic. No press within the expiry, or No, leaves the mode unchanged. [verify: exec `bun test src/remote/command-confirm.test.ts`]
- AC7: `/delegate` and `/external*` start an agent only after a Yes/No press whose prompt names the agent and states that it is paid or external. The apply step that asks for a typed hash stays local. [verify: exec `bun test src/remote/command-confirm.test.ts`]
- AC8: These commands are refused remotely with a reason, each covered by a test: `/exit`, `/quit`, `/channels`, `/provider`, `/search-provider`, `/search-connect`, `/remote-control off`, `/integrate`, `/copy`, `/game`, `/setup`, `/mcp trust`, `/guard`, `/route`, `/editguard`. [verify: exec `bun test src/remote/command-gateway.test.ts`]
- AC9: A command the shell refuses while a turn is running (`/new`, `/resume`, `/sessions`, `/compact`, `/model`) is refused from the topic with the same reason. A command that runs longer than a few seconds shows a running status, and a command that exceeds its limit is stopped and reported. [verify: exec `bun test src/remote/command-busy.test.ts`]
- AC10: The Bot API client can edit or remove a message's inline keyboard (`editMessageReplyMarkup`); the fake Bot API supports it; buttons are removed after a press and after expiry. [verify: exec `bun test src/remote/bot-api-edit.test.ts`]
- AC11: No secret reaches the topic through a command: output goes through the same redaction as replies, picker labels are redacted, and no remote path opens a credential prompt. [verify: exec `bun test src/remote/command-secrets.test.ts`]
- AC12: The bot's command menu (`setMyCommands`) lists exactly the commands the gateway allows, so "/" autocomplete in the topic matches what works. `/help` in the topic lists the same set. [verify: invariant `bun test src/remote/command-menu.test.ts`]
- AC13: TUI: the `/remote-control` modal lists the recent remote commands, including refused ones and unanswered confirmations, and the transcript marks a command that came from Telegram with the "tg" source label. [verify: exec `bun test src/tui/remote-control-surface.test.ts`]
- AC14: Every route and button flow is tested against the fake Bot API only; no test reaches Telegram or runs an external agent. [verify: invariant `bun test src/remote/no-live-network.test.ts`]
- AC15: The docs describe the remote commands, the confirmation rule and the commands that stay local: `docs/docs/guides/drive-keryx-remotely.md` and the CLI reference, README line if it lists remote control. [verify: exec `bun test src/docs/remote-commands-docs.test.ts`]
- AC17: `/new` and `/clear` from the topic start a fresh conversation in the same topic: the topic stays bound to the running shell, the topic gets one separator line ("new session"), the session history records the change, and `/resume` from the topic can return to the earlier session. No second topic is created and no topic is deleted. [verify: exec `bun test src/remote/command-session.test.ts`]
- AC18: Each operator message in the topic shows its state on the message itself through a Telegram reaction: received by serve (eyes), accepted into the shell session (reading), turn running (working), turn finished (done), refused or failed (cross). Each state replaces the previous one; a failed reaction call never blocks or delays the message. [verify: exec `bun test src/remote/message-state.test.ts`]
- AC19: While a turn for a topic is running the topic shows the "typing" chat action (`sendChatAction` with the topic's thread id), refreshed before Telegram drops it (about every 4 seconds) and stopped when the turn ends, fails or the shell exits. A queued message that waits behind a running turn shows the received state, not typing. [verify: exec `bun test src/remote/typing-indicator.test.ts`]
- AC20: The Bot API client supports `setMessageReaction` and `sendChatAction`; the fake Bot API records both; if the bot lacks the right to react in the group, the feature degrades to the typing action only and the hub records one event, not one per message. [verify: exec `bun test src/remote/bot-api-reaction.test.ts`]
- AC21: When the operator presses a button on an approval prompt (`ap:<id>:allow|deny`, including the approvals of flow 376) or on a picker or confirmation prompt of this flow, the original message is edited in place: the buttons disappear and the message text shows the result (allowed or denied, by whom, when) instead of a separate "Approval granted" message. A press on an expired or already answered prompt also edits the message to its final state and changes nothing else; a failed edit falls back to a single short reply and never leaves live buttons behind. [verify: exec `bun test src/remote/approval-edit.test.ts`]
- AC16: In the live topic of the real bot, the operator runs `/connect`, `/model` and `/mode` from buttons and judges the result usable for working without a terminal. [verify: judged]
