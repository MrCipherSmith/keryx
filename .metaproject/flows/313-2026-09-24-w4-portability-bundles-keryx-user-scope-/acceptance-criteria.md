# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: (W4-AC1) `keryx bundle export --scope <project|team|user> <out>` writes a manifest that validates against `portable-bundle.schema.json`, every `contents[].sha256`/`sizeBytes` matches the exported bytes, all six kinds (skill, rule, agent, learned-pattern, memory-entry, hook-config) are exportable, and `provenance.sourceProject` is never a raw absolute path (omitted or a hash); proven by an automated test.
- AC2: (W4-AC2) `keryx bundle verify` on a bundle with any single content byte altered reports that entry as a checksum failure and the bundle as not verified (non-zero exit); a missing/unresolvable entry is reported with a reason distinct from a checksum mismatch; proven by an automated test.
- AC3: (W4-AC3) `keryx bundle import` on a bundle with any checksum mismatch (or schema-invalid manifest, unknown `formatVersion` major, or a path escaping the bundle/target root) fails the whole import closed — zero files written in the target scope and no ledger change — and names the failing entries and reasons; proven by an automated test.
- AC4: (W4-AC4) `keryx bundle import` never overwrites a target file whose current sha256 differs from the sha256 Keryx last wrote there (per the applied-state ledger), or an unledgered existing file that differs from the incoming bytes, unless that exact path is passed to `--force`; a Keryx-written unmodified file is updated normally; `keryx bundle uninstall <bundleId>` removes only bundle-managed files that are still unmodified and keeps modified ones with a warning; proven by automated tests.
- AC5: (W4-AC5) `keryx bundle inspect` on an untrusted bundle performs no filesystem write and executes no script or command from the bundle, and reports per-entry new/identical/update/conflict status plus advisory `compat.targetHarnesses` warnings; proven by an automated test that snapshots the target tree and spies on process spawning.
- AC6: (W4-AC6) A memory entry's `source_harness` is set only from the harness identity the MCP server binds at launch (`keryx mcp serve --harness <id>` / `KERYX_HARNESS`); a guard test asserts that no MCP tool call argument can set or override it, and reads through the MCP server filter out entries whose `target_harnesses` exclude the bound harness.
- AC7: (W4-AC7) `keryx memory handoff --from <h> --target <h>` (and the MCP handoff read) against a memory root containing a malformed/unreadable entry or an unreadable folder reports `status: "incomplete"` with named problems and a non-zero exit, never a smaller result labelled complete; proven by an automated test.
- AC8: (W4-AC8) Writing into a private-scope memory directory (user-scope `~/.keryx/memory/`) whose `.gitignore` already exists with content Keryx does not manage is refused with a named reason, and that `.gitignore` is byte-for-byte unchanged; proven by an automated test.
- AC9: (W4-AC9) `keryx bundle import <catalog> --external` vets each Agent-Skills-standard skill read-only through W1 scout dedupe and the W8 audit; a skill failing either gate is not added in any form (neither copied nor referenced); a passing skill is recorded by reference only (no copy into `.metaproject/skills/` or the bundled catalog) and is reported by `keryx skills scout --include-imports`; proven by automated tests.
- AC10: (W4-AC10) Rendering canonical `.metaproject/rules/` into harness instruction files through the W5 registry (`rules-export` surfaces: CLAUDE.md, AGENTS.md, GEMINI.md, `.cursor/rules/*.mdc`, Kiro steering, Windsurf rules, Copilot instructions) inserts or replaces only its own managed block; pre-existing human content outside the markers (and any existing `keryx:index`/`keryx:instructions` block) is byte-for-byte unchanged; proven by automated tests per target file; capability matrix regenerated and its drift check passes.
- AC11: (W4-AC11) `keryx bundle import` never changes a learned-pattern entry's `scope`: a `scope: project` entry with `--target-scope user` is refused with a named reason and writes nothing; a `scope: user` entry imported at user scope is written under `~/.keryx/learning/patterns/` at `status: candidate` even when the bundle recorded `accepted`; import never writes `learning/index.json`; proven by automated tests.
- AC12: `keryx bundle import` runs the W8 audit on staged content (`imported-bundles` surface, `bundle-*` check ids inheriting per-check severity) before any write; an unsuppressed high/critical finding or an unscanned (error) surface refuses the import with zero writes; proven by automated tests in both the audit module and the import pipeline.
- AC13: (Wave-3 exit) On a checked-in fixture bundle, export → import → inspect is byte-identical for every checksummed entry (imported bytes equal bundle bytes; inspect reports every entry identical), and no import overwrites the file the fixture marks user-modified; proven by one automated end-to-end test.
- AC14: The user store resolves to `<KERYX_HOME or os.homedir()>/.keryx/` with the same resolver W6 uses for `hooks.json`; bundle import writes only inside the target scope root (never `learning/index.json` or `learning/observations/`); imported agents carry `origin.kind: imported` with `sourceRef` = bundle id and pass `keryx agents verify`; proven by automated tests.
- AC15: `keryx bundle`, its subcommands and `keryx memory handoff` are documented in `docs/docs/cli-reference.md` and the usage banner (CLI reference coverage test passes); targeted tests, typecheck and eslint on changed files pass; PR CI is green.
