# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: `keryx flow confirm <id>` mints a completion confirmation token only when stdin and stdout are both TTYs, the flow is `implemented` (or `in-progress` for a `--merged` completion), and its criteria are frozen and intact; it prints the flow id, title, AC checksum, confirmed-criteria count and PR/head being confirmed, requires a random challenge typed back via `/dev/tty`, and stores only the token's sha256 bound to `{flow id, kind: "complete", acChecksum}` with a TTL — tests cover each refusal (non-TTY, wrong status, unfrozen/tampered AC, wrong challenge) and that the plaintext token never reaches disk.
- AC2: A flow opts in via `gates.confirmation: true` — written by `flow init --require-confirmation`, or stamped by `flow init` into new flows when `.metaproject/tasks.config.json` has `completion.require_confirmation: true`; for an opted-in flow, `keryx flow complete` records a `confirmation` gate that fails (and the flow returns to `in-progress`, attempt recorded) unless `--confirm-token` is a valid, unexpired, unused token bound to this flow and its current AC checksum; an expired, reused, other-flow, or pre-AC-change token each fail with a named reason — covered by service tests.
- AC3: A token is consumed only on a passing completion, in the same save that appends the `complete` signature; that signature keeps its existing `identity` unchanged and gains an additive `confirmation` field (`mechanism: "terminal-token"`, a hash-prefix `tokenRef` — never the token —, `mintedAt`, `consumedAt`, `boundTo: {kind, acChecksum}`); `flow status`, the `flow complete` "Signed by" note and `keryx governance report` show it, and the `identity.basis` enum is not extended — schema test and docpack schema copy stay byte-consistent.
- AC4: No agent path can mint or bypass the token: no MCP or agent-native tool mints one (test enumerates `src/mcp/tools.ts` and the interactive tool roster); a shell command containing `flow confirm` resolves to `ask` under every permission mode including `auto` in keryx's own agent loop, the ACP permission classifier and the supervised-codex elicitation path; `flow confirm` and `flow recover` are refused by the unattended floor (`FORBIDDEN_FLOW_VERBS`), and a command or patch naming the token store is refused as a protected path — each asserted by a unit test.
- AC5: `flow complete` never leaves a flow in `completing`: an AC tamper caught during or after the gates (failing and passing paths) and any exception thrown by the merge, pull-request or base-branch gates each record a failed completion attempt naming the cause and return the flow to `in-progress` — tests reproduce all three and assert the on-disk status is `in-progress`, the attempt is recorded, and no `complete` signature exists; AC integrity is still enforced on every later forward transition.
- AC6: `keryx flow recover <id> --reason "<why>"` moves a flow from `completing` to `in-progress`, appends a `completion-recovered` history/journal event carrying the reason, the last event before the interruption and whether the AC file is currently intact, and never alters `signatures` or `completionAttempts`; it refuses without `--reason`, from any other status, and while another process holds the flow lock (a running `complete`) — covered by service and CLI tests; `flow status` labels a lock-free `completing` flow as interrupted and names the command.
- AC7: Backward compatibility: every existing flow package in this repository loads, validates against the flow-state schema and passes `keryx flow check` unchanged; a flow without `gates.confirmation` reports the confirmation gate `skipped` and completes with exactly the pass/fail outcome it had before; existing signatures (without `confirmation`) render unchanged; no `schemaVersion` bump and no on-read rewrite — asserted by a backward-compat test over a pre-change fixture and a sweep over `.metaproject/flows/*/flow.json`.
- AC8: The limits are stated, not implied: a decision record (TM-03, linked from TM-02 §7) and the CLI reference state that the token proves an interactive confirmation step outside the agent's tool roster within the TTL for this AC checksum — not that a human performed it — and name the known bypasses (a pty faked with `script`, forging the hash store, obfuscated command text evading the approval floor, agents running outside keryx supervision, hand-editing the opt-in flag in `flow.json`) and that a human who pastes the token to an agent has delegated the completion; `flow complete`'s note repeats the one-line caveat — checked by a docs test grepping the stated limits. The same decision record states that the existing SAC review-confirmation token (`keryx workspace confirm-review`) has the same limits — its hash store can be forged and its approval floor matched by text — so the docs of that mechanism stop implying more.
- AC9: CI is green on the PR and `keryx health run` passes on the branch.
