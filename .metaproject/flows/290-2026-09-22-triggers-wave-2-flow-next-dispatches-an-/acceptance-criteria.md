# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: A `flow-next` trigger entry with a `dispatch` block (provider, model, permissionMode, rates, ceilingUsd, maxSeconds) makes `keryx trigger run <name>` start a keryx agent on the flow's next ready task in a dedicated git worktree on a `trigger/<flow>-<task>` branch, with no TTY, and record the outcome. A test with a fake provider drives one task from `never-started` to a recorded end and asserts the attempt log, the run record and the branch commit. An entry without a `dispatch` block keeps today's report-only behaviour and `keryx trigger list`/`status` say "report-only".
- AC2: Before the model is called, the dispatch records `flow task attempt <flow> <task> --outcome started` with the trigger run id. After the run it records exactly one closing fact: `task done --disposition completed` with a `runLink` only when the turn ended normally, the trigger branch has a commit and `keryx health gate` passes in that worktree. Otherwise it records `task attempt --outcome failed|blocked` with the reason. Tests cover success, provider failure, timeout and health-gate failure.
- AC3: The dispatch refuses without calling a model, and records a distinct outcome with exit 0, when: the flow is not frozen and `in-progress`; `flow next` is `blocked` or `none`; the ready task's resume state is `unresolved` (an open attempt); the task's attempt count has reached its cap; or another dispatch holds the flow's dispatch lock. There is one test per refusal.
- AC4: An unattended run fails closed. `AgentDeps.unattended` is true. The permission mode comes only from the trigger entry (`ask` or `trust`; `auto` is rejected at config load). The project's stored default permission mode and the saved shell allowlist are ignored. Every call that would ask (including `ask_user`, the untrusted-content gate, and credential, SAC-confirm or publish-lease floors) is denied and never approved, and each denial is written to the run record with the tool and the reason. Tests seed a stored `auto` default and a saved `bash *` allowlist and show that neither takes effect.
- AC5: A hard unattended-forbidden floor is evaluated before the permission mode, so `trust` cannot lift it. It denies `git push` in any form, `git merge`, `git tag`, `gh pr merge`, `gh release`, `npm publish` and `bun publish`. It denies `keryx flow freeze`, `flow ac update`, `flow ac reseal`, `flow ac confirm`, `flow implemented`, `flow complete`, `flow renumber`, `flow block`, `flow unblock`, `flow task add` and `flow task depends`. It denies any write (via `apply_patch` or `shell_exec`) to `flow.json`, `acceptance-criteria.md`, `.metaproject/triggers.json` or `.metaproject/data/trigger/**`. A table-driven test runs each case under `trust` and asserts deny plus a recorded denial. After a dispatch test, the flow's AC checksum, status and `acceptance-criteria.md` are unchanged. The unattended tool roster also excludes `web_fetch`, `web_search`, `search_tool`/`use_tool` and `spawn_subagent` in this version, and a test enumerates it.
- AC6: Each dispatched run records its cost: input/output tokens always, and USD computed from the entry's declared rates. `TriggerRunCost` gains `tokens` additively and old `runs.jsonl` lines still read. A run that fails, times out or is aborted still records the tokens and USD it consumed. A `flow-next` entry with a `dispatch` block but no `rates` or no `ceilingUsd` is rejected at config load with a stated reason, so no unpriced dispatch can run.
- AC7: A per-trigger spend ceiling (`dispatch.ceilingUsd`) applies in addition to the project-wide ceiling. When the trigger's own recorded USD is at or over its ceiling, `keryx trigger run` refuses before any model call, records `budget-refused` naming the per-trigger ceiling, and exits 0. Another trigger under its own ceiling still runs, and the project-wide refusal still applies. An unreadable ledger still refuses both. Tests use a real seeded `runs.jsonl`.
- AC8: The remaining allowance (min of per-trigger and project-wide remaining) is enforced during the run. When the accumulated token cost reaches it, the turn is aborted, the task gets `attempt failed` with reason "spend cap reached", and the recorded USD does not exceed the allowance by more than one model response. A fake provider with fixed usage proves the stop.
- AC9: One shared maintenance lock is taken by interactive `keryx sync --apply`, interactive `keryx gdgraph build` (before local-runner delegation), triggered `reconcile`/`rebuild`, and `open-flow`'s check-then-create. A test runs an interactive `gdgraph build` and a `keryx trigger run rebuild` concurrently in two real processes. Exactly one builds at a time, the triggered one records `lock-refused`, and the interactive one waits (bounded) and then says which pid holds the lock rather than reporting a build failure.
- AC10: The shared lock is re-entrant within one async context and is not held across an agent dispatch. `keryx sync --apply`, which calls `gdgraph build` in-process, completes without self-refusal or a timeout wait, and so do triggered `reconcile`/`rebuild` that call those commands. Two unrelated concurrent acquires in one process still exclude each other. A dispatched agent that runs `keryx gdgraph build` via `shell_exec` can take the lock. Tests assert all four.
- AC11: The docs match the code. `keryx trigger --help`, `docs/docs/cli-reference.md` and `README.md` describe the dispatching `flow-next` (the `dispatch` block fields, worktree and branch, what the run may and may not do), the per-trigger ceiling, the cost recording and the shared lock (interactive waits, triggered refuses). The stale "flow-next only reports" text and the 286 claim that interactive commands already share the lock are corrected.
- AC12: CI is green on the PR, and `keryx health run` passes on the branch before completion.
