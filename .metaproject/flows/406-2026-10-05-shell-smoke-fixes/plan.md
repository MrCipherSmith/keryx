# Implementation Plan

Status: formalized; implementation not yet performed

## Approach

Воспроизвести замечания в runtime оператора и checkout, затем точечные исправления с регрессиями. Сопоставить token economy с flow 387, не дублировать его реализацию и не смешивать статусы.

Альтернативы: только документация не устраняет поведение; переписывание shell избыточно рискованно. Выбран единый пакет шести замечаний одного рабочего процесса.

## Steps

1. T1 context: установить версии/entrypoint runtime, воспроизвести routing и очередь, снять baseline старта подагента и входной нагрузки. Проверить /model, назначения и external без изменения разрешений. Перед кодом прочитать актуальные wiki/impact и related tests; при необходимости обновить граф.
2. T2 implement: точечные исправления routing/диагностики, граничного drain очереди, компактной slash-справки, /tasks, лишних ожиданий старта подагента и входной нагрузки (AC1–AC6).
3. T3 test: регрессии всех замечаний и отрицательных сценариев, связанные тесты и проектные type/lint/health; сравнимые замеры до/после, сохранение защит (AC1–AC7).
4. T4 review: review diff, повтор девяти smoke-пунктов с оператором в запускаемом shell, обновление журнала доказательствами, подготовка PR; AC подтверждать только по результатам (AC8).

## Risks

- Runtime может отличаться от checkout; сначала установить отличие, не добавлять дублирующую команду вслепую.
- Оптимизация входа не должна терять историю/инструментальные возможности; проверить compact/restore и tool-enabled запросы.
- Сеть/кэш искажают latency/cost; фиксировать условия и отделять локальное время и cached токены.
