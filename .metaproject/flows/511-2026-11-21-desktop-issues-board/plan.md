# План передачи реализации

## Решение

1. GitHub владеет тикетом, обсуждением и полем Status конкретного GitHub Project. Task Manager владеет пакетом и переходами Flow, Shell/ACP — долговечной сессией и диалогом. Desktop показывает эти данные и отправляет типизированные команды через Tauri. Связь между сущностями доступна CLI и восстанавливается после перезапуска.
2. В Issues две независимые команды. Open session открывает обсуждение. Create flow запускает подготовку в этой же основной сессии. Начало выполнения — отдельное действие. Доступ к карточке из списка, с доски и из Sessions даёт один результат.
3. Команда подготовки находит существующий пакет или создаёт его из тикета с выбранной базовой веткой. Координатор читает локальный index, проверяет доступ к тикету, запускает сбор контекста и декомпозицию, составляет задачи и критерии. Если политика или уточнение требуют человека, один вопрос приходит в сессию. Повторный запуск использует принятые ответы и проверяет, пригодны ли они после изменения исходных данных.
4. Ввести в общий навык явный интерактивный режим подготовки, завершающийся передачей плана. Существующее поведение полного запуска продолжает действовать для вызовов без этого режима. Если хосту недоступен нужный инструмент, вернуть объяснимое состояние и путь восстановления.
5. Обновление карточки зависит от событий Flow/сессии и отдельной синхронизации GitHub. Успешное чтение тикета, доступ на запись Projects и возможность создать локальный Flow проверяются независимо.

## Сравнение вариантов

| Вариант | Последствия |
|---|---|
| Заполнять поле сессии текстом команды | Подходит для ручного обсуждения. У Create flow остаётся лишний Enter, неясно, принял ли оркестратор работу. |
| Хранить жизненный цикл в React или в native-панели | Быстро отобразит прогресс. Shell начнёт видеть другой статус, а после падения окна понадобится второй механизм восстановления. |
| Один координатор Shell/ACP с Task Manager, тонкий Desktop | Выбран для реализации. Потребуются постоянные привязки и подтверждение принятия первого хода. Взамен Flow из CLI виден в Desktop, прежние ответы и доказательства доступны при продолжении. |

## Состояния и действия

| Состояние | Действие/событие | Что видит пользователь, что сохраняется |
|---|---|---|
| Загрузка личной очереди | Изменение аккаунта, фильтра или периода | Предыдущий запрос отменяется или его результат отбрасывается. Данные другого аккаунта сразу исчезают. |
| Есть ранее загруженные страницы | Нет сети / rate limit при следующем запросе | Карточки этого viewer сохраняются с временем обновления, указаны причина и доступный повтор. Явное лишение доступа скрывает приватные детали. |
| Нет результатов / нет прав / ошибка первой загрузки | Открытие Issues | Три различимых состояния с подходящим действием. Отсутствие прав Projects сохраняет доступную личную очередь. |
| Детали тикета раскрыты | Перейти Board → List → назад | Сохраняются выбор, фильтры и фокус. Длинное описание и обсуждение прокручиваются внутри панели. |
| Checkout отсутствует или неоднозначен | Создать сессию или Flow | Выбор/подключение нужного проекта и повтор того же действия. Чтение тикета доступно независимо. |
| Сессия есть, Flow ещё нет | Создать Flow / два клика из двух окон | Один источник, одна основная сессия, один активный пакет. Дубликат возвращает существующее состояние. |
| Потеря связи после создания пакета или первого хода | Перезапуск | Прочитать запись операции и подтверждённый ход. Продолжить с последней подтверждённой точки либо показать конкретное действие восстановления. |
| Координатор ждёт решения | Ответ из Sessions либо переход с карточки | Открывается один вопрос. Ответ пробуждает нужный ход, снимает индикатор после подтверждения и попадает в контекст. |
| Подготовка закончена | Открыть план / решить начать работу | Видны задачи, зависимости, критерии и базовая ветка. Только отдельное действие переводит к выполнению. |
| Конкурентный перенос в Projects / потеря прав | GitHub отвергает или итог расходится с ожидаемым | Перечитать фактическое поле, показать результат и причину. Локальный этап Flow сохраняется. |

## Последовательность для исполнителей

Использовать зависимости из [tasks.md](tasks.md). После T5 можно параллельно заниматься чтением GitHub и привязкой сессии. После сборки контрактов объединить работу в T11. T12 проверяет отказоустойчивость в CI; T13 — поведение в установленном Desktop и Shell на тестовом тикете. Документы [board-design.md](board-design.md) и [integration.md](integration.md) задают подробные контракты. Проверки и требуемые доказательства перечислены в [verification.md](verification.md).
