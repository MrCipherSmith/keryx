# Проверка готовой функции

Документ адресован исполнителям T12–T14. Указаны будущие проверки. При передаче Flow 511 проверена структура постановки.

## Набор данных и доказательства

Использовать два тестовых репозитория с одинаковым номером issue, один приватный, две учётные записи с разными правами, две связанные рабочие копии одного клона, старый Flow с URL источника, один issue в двух GitHub Projects. Подготовить длинный Markdown, пустое описание, более страницы комментариев и не менее трёх страниц результатов с PR среди них. Результат тестового чтения должен различать отсутствие доступа и успешное пустое тело хотя 404 GitHub может скрывать существование приватного тикета.

| Испытание | Что записать |
|---|---|
| Контракты портов и основной сервис | В GitHub CI добавить наборы `src/integrations/issues-board.test.ts`, `issues-launch.test.ts`, `issues-projects.test.ts`. Имитировать GitHub/диск/ACP на границе реальных сервисов, сравнивать запросы, события, записи. Прогоны UI и Rust дополнительно проверяют обычные точки входа. |
| Большая очередь | Счётчики запросов: первая страница без обхода всех репозиториев, без запроса на каждый issue. Проверить продолжение и обновление при изменении выдачи, неполные результаты явно помечены. |
| Гонки и восстановление | Завершать процесс после регистрации намерения, создания сессии, создания пакета, привязки и принятия первого хода, включая потерю ответа клиенту. После перезапуска проверить идентификаторы, количество реальных пакетов, подтверждённых ходов и отсутствие повторных сообщений. Одновременно открыть из двух окон и Shell. |
| Изоляция | Во время задержанного ответа сменить viewer, отозвать доступ, повторить после восстановления. Ни описание, ни история сессии, ни имя приватного проекта другого viewer не появляются на поверхности тикета. Отдельно поломать разрешение записи Projects. |
| Регрессия | Продолжить обычный Flow в Shell, открыть ранее созданный в CLI пакет и самостоятельную PR-сессию. Профили без Projects или с отключённым Task Manager сохраняют доступные функции. |

## Контракт автоматической приёмки

В T12 префикс имени каждого проверочного теста — ID и пробел, например `AC11 restart after initial turn acknowledgement`. Набор board покрывает AC1–AC3, AC5–AC6, launch — AC7–AC12, projects — AC13–AC14. Команда из acceptance-criteria.md запускает соответствующий набор из корня репозитория и сверяет сценарии критерия по JUnit. Отсутствующий набор, ноль совпадений, пропущенный сценарий критерия или ошибка теста дают ненулевой код. До поставки T12 критерии ожидают доказательств.

## Приёмка в реальном приложении

1. Открыть приватный тестовый issue другого подключённого репозитория. Сверить номер, исполнителей, Markdown и порядок комментариев с GitHub. Переключить список/доску, уменьшить окно, закрыть панель с клавиатуры.
2. Открыть сессию, сообщить ограничение для плана. Создать Flow с карточки. Записать sessionId, каталог Flow, базовую ветку и идентификатор первого хода через диагностическую поверхность. Перейти обратно через Sessions и Flows.
3. Довести координатор до уточнения, ответить в обычной сессии. Перезапустить Desktop во время подготовки. Проверить сохранение ответа, единственный пакет, готовый план и явный переход к выполнению.
4. В Shell из того же клона открыть статус и пакет. В обратном направлении показать в Desktop старый Flow из CLI. Проверить отсутствие молчаливого выбора между двумя подходящими пакетами.
5. На выделенном тестовом Project с правом записи передвинуть карточку и сверить поле на GitHub. Повторить в режиме чтения, при изменении поля вторым клиентом и при отказе сети. Keryx показывает фактический результат и сохраняет локальный этап работы.
6. Записать SHA, сборку Desktop и CLI, ОС, результаты CI, снимки основных состояний и фактическое наблюдение по каждому judged-критерию. В доказательства выносить только тестовые данные.

Сетевые публикации и изменения GitHub проверяются на предназначенных для этого тестовых ресурсах. Для приёмки достаточно изменить Status тестового элемента.
