# Issues → Sessions → Flows. Контракт интеграции

Проектное решение для Flow 511. Сначала тикет можно обсудить, затем из той же сессии подготовить Flow. Если пользователь сразу нажал **Create flow**, Keryx сам открывает сессию координатора и запускает подготовку. В обоих случаях сохраняются история разговора, пакет Flow и возможность продолжить после перезапуска. Ниже описаны существующие механизмы на ревизии `df73018d9` и предлагаемые изменения.

## Что уже предоставляет Keryx

## Предлагаемый публичный контракт

Имена ниже описывают операции и данные нового интерфейса. Их предстоит реализовать. Вызов из Desktop проходит через типизированный мост, вызов из Shell — через тот же сервис. Детали JSON не должны зависеть от формата вывода терминала.

| Тип | Данные и инвариант |
|---|---|
| IssueRef | Хост GitHub и подтверждённый GitHub node ID однозначно определяют тикет. Дополнительно храним ID репозитория, отображаемые owner/repo, номер и канонический URL. Короткий номер разрешается только при известном репозитории. Для старого Flow поддерживаем URL из `source.ref`. |
| Viewer | Установленный сервером GitHub пользователь и хост. Запрос, кеш и ответ несут контекст выбранного аккаунта. Клиентский идентификатор сам по себе не доказывает доступ. |
| ProjectRef | Зарегистрированный локальный проект, идентичность клона, выбранный worktree и базовая ветка. Несколько worktree одного клона делят идентичность клона, но сохраняют собственные пути. Для нескольких отдельных клонов пользователь выбирает цель. |
| FlowRef | Идентичность клона, имя каталога пакета, checkout или рабочая ветка, где пакет доступен. Числовой номер служит для отображения. При переезде пакета повторно обнаруживаем его по подтверждённому источнику и проекту. |
| SessionRef | Настоящий sessionId, локальный профиль пользователя и привязки к issue и опциональному Flow. Одна основная сессия обсуждения на связку пользователь/проект/тикет, дополнительные сессии и архив доступны через явный выбор. |
| Launch | Устойчивый launchId, ключ проект/тикет/цель подготовки, подтверждённые параметры, этап, привязанные ссылки и результат первой отправки. Повтор возвращает прежний результат или продолжает с сохранённого этапа. |
| IssueWorkspace | Снимок с разрешёнными действиями, доступными Flow, выбранной сессией, этапом подготовки и при необходимости причиной остановки. Артефакты, задачи и состояние читаются у Task Manager, ожидающий вопрос и ход разговора — у сессии. |

### Выбор проекта и полномочий

1. Для чтения борды достаточно подключённого аккаунта. Полные Markdown-описания и страницы комментариев подгружаются при открытии. Кеш приватных ответов разделён по хосту и пользователю. При смене аккаунта клиент отменяет запросы старого поколения, сразу освобождает его видимые данные и отбрасывает запоздалые ответы.
2. Для действий с файлами сопоставляем repository ID с зарегистрированными локальными проектами и проверяем remote выбранного checkout. При отсутствии checkout карточка предлагает подключить проект, при нескольких подходящих — выбрать. Если связанный аккаунт проекта отличается от аккаунта борды, показываем обе идентичности и просим явно выбрать авторизованное действие. Переключение борды само не меняет привязку проекта или глобальный активный аккаунт `gh`.
3. Используем выбранные в проекте учётные данные в CLI и воркерах с доступом к GitHub. Перед запуском проверяем чтение тикета в этом контексте. Пустой Markdown допускается, отказ чтения возвращает ошибку. Описание, комментарии и ссылки передаются агенту как данные с URL и временем чтения. Они не выдают разрешения на выполнение команд или публикацию.
4. Ключ существующего Flow одинаков для зрителей одного клона. Права на его чтение и доступ к приватной истории сессии проверяются отдельно. Переключение аккаунта не даёт другому зрителю доступа к переписке и кешу первого. Идентификатор аккаунта, токен, переписка и журнал запуска остаются в соответствующем локальном хранилище. В версионируемый пакет попадают утверждённые по правилам проекта контекст, план и источник задачи.
5. Для новой сессии применяются текущие провайдер, модель и режим разрешений Keryx. При продолжении читаем их из выбранной сессии. Desktop использует профиль ACP `shell`. Проверяем поддержку интерактивных вопросов, рабочего механизма делегирования и необходимой возможности записи по политике проекта. Если функция недоступна, возвращаем точную причину. Оркестратор и воркеры наследуют установленные ограничения.

## Два входа в одну работу

**Сначала обсуждение.** `Open session` разрешает проект и тикет, находит основную сессию или создаёт её и записывает ссылку. В контексте есть ссылка на issue и подтверждённое описание. Действие открывает вкладку Sessions. Пользователь пишет обычным способом. При нажатии `Create flow` повторно проверяем доступ, находим или создаём пакет и закрепляем его за тем же sessionId. Ответы и договорённости из обсуждения доступны координатору. Если сессия занята другим процессом, карточка показывает её владельца в интерфейсе или предлагает вернуться к ней после освобождения.

**Сразу подготовка Flow.** `Create flow` определяет целевой checkout и base, проверяет Task Manager и получает или создаёт основную сессию. Под одной операцией находит существующий пакет с этим тикетом или вызывает FlowService с подтверждённым URL. Агенту передаются конкретные package dir, base, источник и режим подготовки. При открытии уже созданного пакета оркестратор продолжает с его текущего этапа. Приложение само инициирует первый ход после привязки. Повторный клик открывает выполняющийся ход.

**Результат подготовки.** Координатор собирает контекст по индексам Metaproject, читает выбранные проектные правила, использует `context-collector` и `issue-analyzer`, записывает постановку, план, задачи и проверяемые критерии. Запрос контекста возвращается координатору. Общий вопрос задаётся один раз через обычный механизм сессии. Подтверждённый ответ доступен новым назначениям по тому же вопросу. На карточке ссылка ведёт к этому вопросу; решение сохраняется в сессии и, когда оно определяет требования, в пакете Flow с указанием источника.

Для этой команды предлагается отдельная точка передачи **План готов** перед переходом к разработке. Подготовка заканчивается валидным пакетом и показом задач и критериев. Действие **Начать выполнение** продолжает штатную последовательность freeze/start с положенными проверками. Для общего навыка это дополнительный явно запрошенный режим; действующие вызовы полного цикла в других харнесах сохраняют прежнюю семантику. Решение об окончании Flow, PR или публикации проходит через существующие разрешения.

## Конкурентность, совместимость и восстановление

| Событие | Требуемое поведение |
|---|---|
| Двойной клик, второе окно, Desktop и Shell готовят один тикет | Общий сервис атомарно регистрирует запуск под блокировкой клона с ключом тикета. Следующий вызов присоединяется к нему. При создании самого пакета проверка совпадения источника и выделение номера выполняются в одной сериализуемой операции. Обычное `flow init --issue` должно участвовать в этой сериализации при гонке с подготовкой. Явный авторский Flow-дубль или последующая работа возможны отдельным действием. |
| Процесс погиб после создания пакета, до обновления журнала | Ищем созданный пакет по сохранённому идентификатору операции либо по однозначному `source.ref` и проекту. Привязываем найденный пакет и продолжаем. Если совпадений несколько, показываем выбор с каталогом, веткой, этапом. Существующая связь пользователя сохраняет приоритет. |
| Создали сессию и потеряли ответ | Перед созданием сохраняем launchId. Сервис сессий атомарно записывает его в метаданные при создании и при повторе восстанавливает sessionId по ключу. Локальный флаг React не обеспечивает такую гарантию. |
| Перезапуск между отправкой первого сообщения и ответом ACP | На стороне принимающей сессии нужен устойчивый ключ первого хода. Под блокировкой сессии регистрируем ключ и запись хода. При повторном подключении клиент читает квитанцию и ход с этим ключом. Подтверждённый ход открывается, прерванный возобновляется с проверки артефактов. Дубликат сообщения не добавляется. |
| Старый backend не сообщает, принял ли он первый ход | После таймаута исход неизвестен. Сначала восстанавливаем историю сессии и состояние пакета. Если установить исход нельзя, показываем «Проверить запуск» с переходом в ту же сессию. Автоматическая повторная отправка в этом состоянии может второй раз запустить агентов. Транспортный ACK сам по себе также не доказывает окончание подготовки. |
| Shell держит lease на сессию или координатор уже работает | Сохраняем идентификаторы и владельца lease. Другой клиент предлагает открыть доступную сессию или дождаться освобождения. Захват живой сессии, второй координатор и автоматическое создание пустой замены недопустимы. |
| Старый Flow, удалённый или перемещённый checkout, несколько пакетов | Для старой схемы читаем `source.type/ref`, нормализуем GitHub URL и сопоставляем в рамках зарегистрированного проекта. После переноса или переименования issue обновляем локальные алиасы по подтверждённому GitHub ID. При отсутствии нужного checkout показываем путь подключения; для нескольких реальных Flow даём выбор, включая завершённые и архив. Исторические пакеты не переписываются при открытии борды. |

Гарантия одного логического запуска распространяется на локальные записи пакета, сессии и первого хода при поддержке ключа принимающей стороной. Выполнение модели или внешней команды после аварии может иметь неопределённый исход. Координатор сверяет сохранённый прогресс и результаты до повторного вызова. Долгая операция получает аренду с владельцем и поколением; при восстановлении новый владелец должен подтвердить право записи, а старый процесс не может позднее перезаписать его результат.

## Ответы для интерфейса и агентов

Сервис возвращает типизированный результат с кодом, безопасным объяснением, разрешённым следующим действием и доступными ссылками issue, session и Flow. Ошибка доступа не раскрывает чужие приватные данные. При повторе передаётся тот же launchId.

| Код результата | Что доступно пользователю или агенту |
|---|---|
| `project_required`, `project_ambiguous` | Открыть описание и выбрать локальный checkout целевого репозитория. |
| `account_mismatch`, `source_unavailable`, `rate_limited` | Проверить текущую привязку, переподключиться или повторить по указанному времени. Для недоступного приватного объекта допускается единая формулировка GitHub о недоступности. |
| `tasks_module_unavailable`, `capability_missing` | Открыть диагностику проекта с названием модуля или отсутствующей возможности выбранного харнеса. |
| `flow_choice_required`, `session_leased` | Открыть выбранный пакет, вернуться в удерживающую процесс сессию или повторить после освобождения. |
| `preparing`, `awaiting_answer`, `prepared` | Показать настоящий этап и ссылку на сессию, конкретный вопрос либо проверенный план. События watcher и ACP побуждают перечитать состояние после reconnect. |
| `launch_outcome_unknown`, `resume_required` | Проверить квитанцию, историю хода и артефакты, затем предложить оператору продолжение в той же сессии. |

## Контрольные сценарии

- Приватный backend-тикет открывают из frontend-проекта. Пользователь обсуждает требование, создаёт Flow и видит свой ответ в той же сессии; пакет, контекст и ветка принадлежат backend-проекту.
- В двух разных репозиториях есть issue с номером 42, а в одном клоне открыты два worktree. Одновременная подготовка одного тикета из Desktop и Shell даёт один пакет и один начальный ход; второй репозиторий сохраняет независимые связи.
- В существующем пакете Shell сохранён только URL источника. После открытия из Desktop карточка восстанавливает Flow. Если таких пакетов два, показывает оба и продолжает выбранный.
- Во время долгой загрузки комментариев меняется аккаунт. Ответ прежнего пользователя не появляется в новой выборке. При отказе доступа агент видит причину. Тикет с законно пустым описанием читается успешно.
- Процесс останавливают отдельно после выделения пакета, регистрации сессии и принятия начального сообщения. После запуска видны реальные записи, а повторное открытие не пересоздаёт ни один из трёх объектов. Для старого ACP без квитанции интерфейс показывает неопределённый исход.
- Вопрос виден на борде и открывается в сессии. После ответа там же продолжается сбор контекста, карточка получает этап «План готов». Передача в исполнение происходит по соответствующему действию оператора.
