# Issues в Keryx Desktop

## Что видит пользователь

Разработчик открывает Issues, выбирает GitHub-аккаунт и видит открытые задачи, назначенные ему в разных репозиториях. Он может прочитать обсуждение, открыть связанную сессию, подготовить Flow по тикету или изменить статус в выбранном GitHub Project. Открытие доски и чтение задачи не создают сессию, Flow или запись в GitHub.

В шапке показываются GitHub host и логин, выбор источника, поиск по номеру или заголовку, Filters, Board / List и Refresh. Рабочая папка нужна при переходе к локальной работе. Отсутствие checkout не мешает чтению доступного тикета.

## Источники и фильтры

| Источник | Какие задачи входят |
|---|---|
| Assigned to me | Назначенные выбранному пользователю. При первом открытии выбран этот источник и состояние Open. |
| Created by me | Автором является выбранный пользователь. |
| Mentioned | GitHub зафиксировал упоминание пользователя. |
| Subscribed | Задачи, на обновления которых подписан пользователь. |
| GitHub Project | Доступные пользователю GitHub Issues из явно выбранного Project. Настройка хранит host, владельца и ID Project. |

Личный источник охватывает доступные репозитории выбранной учётной записи. Для REST использовать соответствующие значения параметра `filter` у `GET /issues` и отдельный параметр `state`. Из результата исключать записи с `pull_request`. Идентичность задачи определяют host и GitHub node ID. Репозиторий и номер отображаются вместе, поэтому две задачи с номером 12 из разных репозиториев остаются различимыми. [GitHub Docs — Issues API](https://docs.github.com/en/rest/issues/issues#list-issues-assigned-to-the-authenticated-user)

Filters предлагает репозиторий, автора, исполнителя (включая Unassigned), метки, состояние GitHub Open / Closed / All, стадию Keryx и, для внешней доски, значение поля Project Status. Поиск принимает фрагмент заголовка, `#12` или `owner/repo#12`. Для одного поля несколько выбранных значений объединяются через «или», разные поля — через «и». Board и List используют один набор отобранных задач, единый порядок по времени обновления и стабильный ключ для совпадающих дат. Активные фильтры можно снять по одному или сбросить. Выбранные представление и фильтры восстанавливаются в пределах аккаунта и источника. Настройки поля Project привязаны к ID Project и ID поля. [Linear — Board layout](https://linear.app/docs/board-layout) · [Linear — Filters](https://linear.app/docs/filters)

### Страницы, пустые состояния и давность данных

- Первая страница появляется сразу. «Загрузить ещё» использует возвращённый GitHub адрес следующей страницы либо GraphQL `endCursor` / `hasNextPage`. Клиент проверяет origin каждого адреса до передачи учётных данных. Дубли при обновлении или пересечении страниц объединяются по ID.
- Поддерживаемые фильтры применяются в запросе. Для остальных фильтрация продолжается на следующих страницах. Пока страницы ещё есть, показывать «Совпадений среди загруженных задач пока нет» и действие продолжить. «Задач нет» или «Ничего не найдено» допустимо после исчерпания выборки. Счётчик «Загружено 40» отличается от полного количества. Смена фильтра инвалидирует курсор, привязанный к старому запросу.
- Refresh повторяет запрос для текущих аккаунта, источника и фильтров. Просроченный ответ от предыдущего выбора игнорируется. Сетевой сбой оставляет подтверждённые данные с временем снимка, пояснением и кнопкой повтора. Ограничение частоты учитывает время разрешённого повтора. Потеря доступа скрывает содержимое соответствующей области и её детали. Ошибка одной коллекции комментариев допускает повтор загрузки комментариев отдельно.
- Смена аккаунта сразу снимает выделение, закрывает детали и убирает предыдущие данные, включая заголовки, фасеты и счётчики. Ключ кеша включает host, ID пользователя, источник, параметры и репозиторий либо Project ID. После разрыва привязки или утраты доступа содержимое этой области удаляется из доступного кеша.

## Карточка, строка и подробности

В карточке видны `owner/repo#number`, заголовок, GitHub State, исполнитель и стадия Keryx. Метки занимают ограниченное число строк, остаток доступен через «+N» с текстовым списком. Блокировка сопровождается причиной и доступным следующим шагом. Строка List даёт те же свойства и действия и показывает время обновления. Номер и заголовок образуют одну точку перехода с понятным доступным именем.

По Enter или клику справа открывается изменяемая по ширине панель с заголовком и действиями. На узком окне она занимает рабочую область целиком. Заголовок содержит путь к репозиторию, номер, состояние, «Открыть в GitHub» и «Закрыть». Экраны чтения и обсуждения показывают автора, исполнителей, метки, полный Markdown, время создания и обновления. Комментарии с автором, датой и ссылкой загружаются страницами в хронологическом порядке. Счётчик учитывает загруженные страницы. Сбой дозагрузки оставляет прочитанные комментарии на месте. Код и длинные таблицы прокручиваются внутри блока. [GitHub Docs — комментарии к задаче](https://docs.github.com/en/rest/issues/comments#list-issue-comments)

Заголовок и комментарии считаются внешними данными. Используется очищенный Markdown-рендерер Desktop, с отключённым выполнением HTML-сценариев. Относительные ссылки разрешаются в контексте удалённого репозитория, `#N` — внутри него. HTTP(S)-ссылки передаются существующему маршруту Browser с контекстом текущего проекта, где он доступен. Неподдерживаемые схемы отображаются текстом. Между задачами можно переходить в пределах текущей отфильтрованной выборки. Закрытие панели возвращает фокус и позицию прокрутки к вызвавшей карточке или строке. Если фильтр уже исключил задачу, фокус получает заголовок прежней группы.

Блок «Работа в Keryx» показывает отдельные карточки сессии и Flow. Действия меняются по состоянию связи: «Создать сессию» / «Открыть сессию», «Создать Flow по тикету» / «Открыть Flow». Во время подготовки видны текущий шаг и ссылка в сессию оркестратора. Двойное нажатие присоединяется к уже начатой операции. Если для исходного репозитория есть несколько checkout, пользователь видит варианты и явно выбирает рабочую папку. Если подтверждённой папки нет, действие предлагает выбрать её. Потерянная локальная связь показывает причину и действие восстановления.

## Две доски и владельцы данных

**Keryx.** Колонки показывают ход локальной работы. Правила применяются к текущему связанному Flow и его подготовке. Одна связанная сессия без Flow оставляет задачу в «Без Flow».

| Колонка | Условие | Ближайшее действие |
|---|---|---|
| Без Flow | Нет привязанного Flow или активной подготовки | Создать Flow или открыть связанную сессию |
| Подготовка | Запущена подготовка, идёт сбор контекста или согласование плана | Открыть подготовку и посмотреть шаг |
| В работе | Flow выполняется или может продолжиться после принятия плана | Открыть Flow |
| Нужен ответ | Оркестратор ждёт решения или подтверждён нерешённый блокер | Ответить в связанной сессии либо выполнить действие рядом с причиной |
| Завершено | Связанный Flow достиг состояния завершения | Открыть итог Flow |

Незакрытый вопрос имеет приоритет над обычным ходом активного Flow. После ответа источник состояния перечитывается. Закрытый вопрос из истории не поддерживает индикатор ожидания. Для сбоя подготовки показываются причина и «Повторить» или «Выбрать папку» согласно типу ошибки. При отсутствии актуального подтверждения состояния отображается время последнего чтения. Переходы определяются фактическими событиями. В этой доске ручного перетаскивания между вычисляемыми колонками нет. GitHub State и причина закрытия, если GitHub её предоставил, показаны отдельно. Завершение Flow само по себе не закрывает issue.

**GitHub Project.** В выборе источника пользователь указывает конкретный Project организации или пользователя. Keryx разрешает его ID и читает поле Status типа single select, ID поля и упорядоченные варианты с их ID. Список полей и элементов читается со всеми страницами. Колонки соответствуют вариантам выбранного поля, включая пустые колонки и «Без статуса» для доступного элемента без значения. Входят задачи всех представленных репозиториев, доступных аккаунту. В обычной выборке показываются активные элементы типа Issue. PR, черновые и скрытые GitHub элементы, а также архивные элементы исключаются из обычных счётчиков. Колонки другого Project могут иметь другие названия и порядок. Локальная стадия остаётся отдельным атрибутом задачи. [GitHub Docs — чтение полей и элементов Project](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects#finding-information-about-projects)

## Перемещение в GitHub Project

1. Пользователь выбирает «Изменить статус Project» в карточке, строке или панели. Перетаскивание между колонками запускает ту же операцию. Выбор уже установленного значения завершает действие локально. Меню называет Project и целевой статус. Открытие issue, связывание с Flow, раскрытие списка и смена фильтров не выполняют запись в GitHub.
2. На стороне хоста проверить учётную запись привязки, доступ к задаче и выбранному Project, принадлежность item этому Project и issue, тип поля, доступность варианта и возможность записи. Перед изменением перечитать текущий option ID и сравнить с ожидаемым. При расхождении показать «Статус изменён на X», обновить обе поверхности и предложить пользователю выбрать переход ещё раз.
3. Вызвать `updateProjectV2ItemFieldValue` с ID проекта, элемента, поля и `singleSelectOptionId`. Переход в «Без статуса» у уже заполненного элемента использует `clearProjectV2ItemFieldValue`. Пока запрос выполняется, элемент сохраняет исходную позицию с индикатором «Сохранение…» и защищён от повторной отправки. У одной issue в двух Projects разные item ID. Перемещение адресуется только выбранному item. [GitHub Docs — обновление single select](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects#updating-a-single-select-field) · [GitHub GraphQL — Projects](https://docs.github.com/en/graphql/reference/projects)
4. После ответа перечитать значение и обновить Board, List и детали из него. Предварительное чтение уменьшает окно конфликта, но GitHub не предоставляет условную запись по ожидаемому старому статусу в этой мутации. При одновременном изменении показывается последнее считанное значение и доступен ручной Refresh. При тайм-ауте результат может быть уже записан. Сначала сверить состояние, повторить запись только по новому действию пользователя. Переименование или удаление варианта требует перечитать схему доски.
5. Issue вне выбранного Project может по-прежнему отображаться в личном источнике. Перемещение уже существующего элемента сохраняет членство issue в проектах. Для отдельного явного действия добавления GitHub требует сначала `addProjectV2ItemById`, затем обновление значения. Если такой сценарий будет включён, второй шаг повторяется на уже полученном item ID после проверки первого. [GitHub Docs — добавление элемента](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects#adding-an-item-to-a-project)

### Права и восстановление

| Ситуация | Что происходит в интерфейсе |
|---|---|
| Доступны Issues, Projects недоступны | Личные источники и локальные связи доступны. При выборе Project показать причину, переход в Integrations и возврат к личной доске. |
| Project доступен для чтения | Колонки, список и детали работают. У недоступного переноса видна причина. После изменения прав Refresh переоценивает доступ. |
| Поле удалено, изменило тип или недоступно | Показать доступные задачи списком и состояние «Поле статуса недоступно». Переносы блокируются до повторного выбора валидного поля. |
| Утрачен доступ к одной issue | Скрыть её карточку, детали и локальные сведения из этого контекста. Для отсутствующей или недоступной задачи показывать общее сообщение. |
| Пользователь сменил аккаунт во время записи | Исходный запрос может завершиться на стороне GitHub. Ответ не меняет экран другого аккаунта. При возврате к исходному аккаунту статус заново сверяется с GitHub. |

Для OAuth и classic PAT у GitHub CLI запросы к Projects требуют `read:project`, изменения — `project` и соответствующие права пользователя на конкретный Project. Другие типы авторизации проверяются по их модели разрешений. Desktop не запрашивает расширение прав при обычном просмотре Issues. [GitHub Docs — аутентификация Projects API](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects#authentication)

## Приёмка интерфейса

- На ширине 1440 px читаются колонки и открытая панель. При 720 px панель может занять всю область. При 390 px все действия доступны через меню, колонка целиком видна в горизонтально прокручиваемой области доски. Только доска, таблицы и блоки кода могут требовать горизонтальной прокрутки.
- Клавиатурой доступны выбор источника, фильтры, открытие и закрытие задачи, изменение статуса, создание и переход к сессии и Flow. Разделитель панели имеет доступное имя, значение ширины и управление стрелками. При показе панели как модального окна фокус ограничен панелью, Escape закрывает её, фокус восстанавливается. В широком немодальном виде доступен переход обратно к списку.
- Статусы читаются текстом с иконками. Контраст основного текста не ниже 4,5:1, границы интерактивных элементов и фокус — 3:1 относительно соседнего фона. Изменение числа результатов, завершение переноса и ошибки объявляются через доступный статус. При системном reduced motion перестановка обходится без анимации.
- На выборке с двумя одинаковыми номерами, задачей без исполнителя и тремя страницами фильтрация, выбор и переход Board → List → детали → назад сохраняют нужную задачу. Дозагрузка после страницы только с PR продолжает поиск Issues. Ни один результат старого аккаунта не появляется после переключения.
- Эталон разделения состояний: открытая GitHub issue с завершённым Flow и Project Status «In progress» одновременно показывает все три факта. Перенос в «Done» меняет только значение в выбранном Project. Запрос другой команды, отсутствие прав, переименование варианта и потеря ответа на запись дают наблюдаемые результаты из сценариев выше.
