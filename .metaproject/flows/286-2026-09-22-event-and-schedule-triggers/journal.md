- note (implementer): T7 decision (AC3) — a second `keryx trigger run` for the same project REFUSES immediately rather than waiting. `withTriggerRunLock` (`src/trigger/run.ts`) reuses `withFileLock` (`src/lib/fs.ts`) with `timeoutMs: 0`: one `mkdir` attempt, with `removeStaleLock`'s ordinary stale-reclaim still consulted (a lock abandoned by a killed process is still recovered), and on contention it fails over into the library's own `"Timed out waiting for lock: …"` error immediately instead of retrying — the same string `src/lib/routing-entrypoint.test.ts` already asserts on to distinguish lock contention from any other failure. Reasoning: `keryx trigger run` is fired unattended from hooks/cron/CI, where a blocking wait turns AC2's "exactly one pass" into "some pass, at an unpredictable time" and risks processes stacking up under a burst of triggers (e.g. several git hooks firing in quick succession). Refusing at once and letting the NEXT scheduled/triggered invocation retry keeps the contract simple: one pass, one exit code, right now. The refusal itself is a clean AC2 "nothing done this pass" outcome (exit 0), not a crash. Proven with real concurrency, not a stubbed lock: `src/trigger/run.test.ts` races two real promises against the same on-disk lock directory; `src/commands/trigger-run.e2e.test.ts` races two real spawned `keryx trigger run` processes end-to-end (AC3's own "a test drives both concurrently") and asserts the code graph is intact and built exactly once afterward.
- note (implementer): T7 scope note — this lock is new (`src/gdgraph/` and `src/wiki/` had no lock at all before this dispatch, per the T5 survey) and it is scoped to TRIGGERED runs only. `keryx sync --apply` / `keryx gdgraph build` invoked directly by a person still take no lock, so a person running one by hand while a trigger fires can still race it the same way two triggers could race each other before this dispatch. - note (implementer): T11 decision (AC7, "equivalent") — a second `open-flow` fire is skipped only when `action.skipIfOpen` is set AND another flow's `title` is EXACTLY this entry's `action.template` (set verbatim as the new flow's title by `runOpenFlow`, `src/commands/trigger.ts`) AND that flow's `status !== "done"`. `"initializing"`/`"blocked"` both count as open on purpose — a freshly-`init`ed, not-yet-`start`ed flow or a blocked one is exactly the noise AC7 exists to stop a second fire from adding. Matching on `title` rather than `slug` was chosen because `title` is the lossless key here (set verbatim from `template`), while `slug` runs through `slugify()` and two different templates can collide on it. `findEquivalentOpenFlow` in `src/commands/trigger.ts` is the single predicate; `src/commands/trigger.test.ts`'s "open-flow with skipIfOpen" test pins it: two fires of the same schedule-fired entry, the second a `no-op` (existing outcome kind — no schema change needed) with a stated reason, while the first flow is still `"initializing"`, and only one flow directory ever lands on disk.
- note (implementer): T11 decision (AC8, "flow-next" scope) — `flow-next` REPORTS `keryx flow next <flow>`'s decision (ready/blocked/none, plus unresolved tasks, via `describeNextTaskDecision`) into the fired-trigger record; it does not dispatch an agent turn. Chosen over "dispatch the next task" because an unattended trigger (a git hook, cron, CI) has no way to safely own a dispatch — model choice, tool access, and reviewing the result afterward all need an operator or an orchestrator present, none of which a bare `keryx trigger run` firing has. Reporting is the honest scope: it turns "an event happened" into "here is what should happen next", which is the gap description.md names, without claiming a dispatch capability this build does not have. A future dispatching `flow-next` is a larger, separate feature, not a variant reading of `NextTaskDecision`.
- note (implementer): T11 decision (AC8, budget refusal) — `open-flow` and `flow-next` are the only two action kinds gated on the spend ceiling (`../review/caps.ts`'s `evaluateSpendCap`, `DEFAULT_SPEND_CEILING_USD = 3`); `reconcile`/`rebuild` never call a model (T8's own `NO_MODEL_COST`) so gating them would check a number they can never move. "Spent" is read from this project's OWN fired-trigger record (`../trigger/record.ts`'s `runs.jsonl`) — summed over every record whose `cost.recorded` is `true`, across every trigger name and action kind (project-wide, not per-trigger). An ABSENT record file is a demonstrated `0` (nothing has ever fired, hence recorded, a cost); an UNREADABLE one reports `spent: undefined` (`"not-recorded"`, never coerced to 0) rather than pretending the ledger says nothing was spent. `evaluateTriggerBudget` (`src/trigger/run.ts`, core) returns the refusal reason; `refuseOnBudget` (`src/commands/trigger.ts`) records outcome `budget-refused` (T8's reserved kind — first producer) and leaves `process.exitCode` at 0, the same shape `lock-refused` already uses, per AC2's "non-zero exit is for the action itself failing" and AC8's "not as a crash". No new config knob: "the configured spend ceiling" is the existing default (no per-project override exists yet); adding one is a stated follow-up, not done here. Proven with a real seeded ledger, not a stub: `src/commands/trigger.test.ts`'s budget-refused test appends a real `TriggerRunRecord` at the ceiling via `appendTriggerRunRecord`, then asserts the next `open-flow` fire exits 0, opens no flow directory, and is itself recorded as `budget-refused`.
