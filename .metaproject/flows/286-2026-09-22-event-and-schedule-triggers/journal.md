- note (implementer): T7 decision (AC3) — a second `keryx trigger run` for the same project REFUSES immediately rather than waiting. `withTriggerRunLock` (`src/trigger/run.ts`) reuses `withFileLock` (`src/lib/fs.ts`) with `timeoutMs: 0`: one `mkdir` attempt, with `removeStaleLock`'s ordinary stale-reclaim still consulted (a lock abandoned by a killed process is still recovered), and on contention it fails over into the library's own `"Timed out waiting for lock: …"` error immediately instead of retrying — the same string `src/lib/routing-entrypoint.test.ts` already asserts on to distinguish lock contention from any other failure. Reasoning: `keryx trigger run` is fired unattended from hooks/cron/CI, where a blocking wait turns AC2's "exactly one pass" into "some pass, at an unpredictable time" and risks processes stacking up under a burst of triggers (e.g. several git hooks firing in quick succession). Refusing at once and letting the NEXT scheduled/triggered invocation retry keeps the contract simple: one pass, one exit code, right now. The refusal itself is a clean AC2 "nothing done this pass" outcome (exit 0), not a crash. Proven with real concurrency, not a stubbed lock: `src/trigger/run.test.ts` races two real promises against the same on-disk lock directory; `src/commands/trigger-run.e2e.test.ts` races two real spawned `keryx trigger run` processes end-to-end (AC3's own "a test drives both concurrently") and asserts the code graph is intact and built exactly once afterward.
- note (implementer): T7 scope note — this lock is new (`src/gdgraph/` and `src/wiki/` had no lock at all before this dispatch, per the T5 survey) and it is scoped to TRIGGERED runs only. `keryx sync --apply` / `keryx gdgraph build` invoked directly by a person still take no lock, so a person running one by hand while a trigger fires can still race it the same way two triggers could race each other before this dispatch. - note (implementer): T10 decision (AC6) — the printed line never says bare `keryx`. cron gives each line `/bin/sh -c '<line>'` with a MINIMAL PATH (often just `/usr/bin:/bin`) and no login-shell startup files, and this project's own `keryx` is routinely installed somewhere that PATH does not reach (nvm's `~/.nvm/versions/node/*/bin`, bun's `~/.bun/install/global/bin` — verified live on this machine: global `keryx` resolves to `~/.nvm/versions/node/v24.14.0/lib/node_modules/@mrciphersmith/keryx/dist/cli.js`, not `/usr/bin`). So `resolveKeryxInvocation()` bakes in `process.execPath` (the interpreter actually running) and `process.argv[1]` (the entry script actually running) by ABSOLUTE path into both the cron command and the systemd `ExecStart=`, and sets an explicit `PATH` (interpreter's own dir, then `/usr/local/bin:/usr/bin:/bin`) for what the action itself still shells out to (`git`, inside `sync --apply`/`gdgraph build`). Caught by the AC6 test itself, not anticipated up front: the printed `>> logPath 2>&1` failed outright on a FRESH project (`sh: cannot create .../data/trigger/x.log: Directory nonexistent`) because that directory does not exist until something has created it — fixed by prefixing `mkdir -p` (cron) / `ExecStartPre=-/bin/mkdir -p` (systemd) ahead of the redirect. Stated assumptions (also printed in the command's own output): the resolved interpreter/script paths stay stable at those absolute locations (an nvm prune / version switch after generation needs a regenerate+reinstall); `git` is reachable under `/usr/local/bin:/usr/bin:/bin`.
