- note (implementer): T7 decision (AC3) — a second `keryx trigger run` for the same project REFUSES immediately rather than waiting. `withTriggerRunLock` (`src/trigger/run.ts`) reuses `withFileLock` (`src/lib/fs.ts`) with `timeoutMs: 0`: one `mkdir` attempt, with `removeStaleLock`'s ordinary stale-reclaim still consulted (a lock abandoned by a killed process is still recovered), and on contention it fails over into the library's own `"Timed out waiting for lock: …"` error immediately instead of retrying — the same string `src/lib/routing-entrypoint.test.ts` already asserts on to distinguish lock contention from any other failure. Reasoning: `keryx trigger run` is fired unattended from hooks/cron/CI, where a blocking wait turns AC2's "exactly one pass" into "some pass, at an unpredictable time" and risks processes stacking up under a burst of triggers (e.g. several git hooks firing in quick succession). Refusing at once and letting the NEXT scheduled/triggered invocation retry keeps the contract simple: one pass, one exit code, right now. The refusal itself is a clean AC2 "nothing done this pass" outcome (exit 0), not a crash. Proven with real concurrency, not a stubbed lock: `src/trigger/run.test.ts` races two real promises against the same on-disk lock directory; `src/commands/trigger-run.e2e.test.ts` races two real spawned `keryx trigger run` processes end-to-end (AC3's own "a test drives both concurrently") and asserts the code graph is intact and built exactly once afterward.
- note (implementer): T7 scope note — this lock is new (`src/gdgraph/` and `src/wiki/` had no lock at all before this dispatch, per the T5 survey) and it is scoped to TRIGGERED runs only. `keryx sync --apply` / `keryx gdgraph build` invoked directly by a person still take no lock, so a person running one by hand while a trigger fires can still race it the same way two triggers could race each other before this dispatch. Recommending as follow-up (not done here, out of this task's scope): widen `withTriggerRunLock`'s lock (or an equivalent) to `src/commands/sync.ts`'s `syncCommand(["--apply"])` and `src/commands/gdgraph.ts`'s `gdgraphCommand(["build"])` themselves, so the interactive and triggered paths share one lock rather than two different ones that don't know about each other.
