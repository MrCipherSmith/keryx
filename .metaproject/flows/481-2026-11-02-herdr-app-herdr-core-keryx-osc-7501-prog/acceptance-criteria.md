# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- Every criterion ends with [verify: exec `<command>`],
  [verify: invariant `<command>`], [verify: judged] or
  [verify: none — <reason>].
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: `encodeOsc7501` in `src/tui/herdr-core-status.ts` emits the herdr-core wire format byte-exactly: `ESC ] 7501 ; state=<w>` then the present fields in the order `kind`, `progress`, `app`, `title`, `msg` joined by `:`, `title`/`msg` as base64 of UTF-8, terminated by `ESC \`; the test pins `\x1b]7501;state=working:app=keryx\x1b\\` and a `state=blocked:kind=permission:app=keryx:msg=<base64>` string, and an unknown state is refused. [verify: exec `bun test src/tui/herdr-core-status.test.ts`]
- AC2: `createHerdrCoreReporter` writes nothing when `HC_TERMINAL_ID` is unset or empty; with it set it writes one sequence per state change, skips an identical consecutive report, and a throwing writer never propagates an error to the caller. [verify: exec `bun test src/tui/herdr-core-status.test.ts`]
- AC3: The herdr-core mapper reports queued→`idle`, running→`working`, done→`done`, failed→`error`, an approval→`blocked` with `kind=permission`, `ask_user`→`blocked` with `kind=question`, exit→`clear`; `herdrStateFor` and the agent-bus status are unchanged (their existing tests pass unmodified). [verify: exec `bun test src/tui/herdr-core-status.test.ts src/tui/herdr-report.test.ts src/tui/tui-bus.test.ts`]
- AC4: The `msg` of a blocked report is the approval's command (shell_exec) or task (external spawn) or the `ask_user` question body, collapsed to one line, passed through keryx secret redaction and cut to at most 200 characters before base64; a test with a fake secret token in the command finds the token absent from the decoded `msg`. · sensitive: failure-scenario [verify: exec `bun test src/tui/herdr-core-status.test.ts`]
- AC5: The status writer goes through the live renderer's `writeOut` (one call per sequence) when the renderer has it, and uses `process.stdout.write` only when no renderer is live or it lacks `writeOut`; the guard is a structural check, not an unchecked cast, and is unit-tested with a fake renderer. [verify: exec `bun test src/tui/herdr-core-status.test.ts`]
- AC6: `keryx shell` reports `idle` only after the composer is ready (never while a provider, model or resume picker is on screen), reports the matrix states at the existing status points including the blocked sites with kind and text, and writes `clear` on every exit path that releases the old herdr reporter; the old Herdr TUI reporter behaves as before. [verify: exec `bun test src/tui/herdr-core-status.test.ts src/tui/tui-herdr-core-wiring.test.ts src/tui/herdr-report.test.ts`]
- AC7: `keryx shell "<task>"` accepts one positional non-flag argument as an initial prompt and submits it as the first turn once the composer is ready; two positional arguments fail with an error that names the problem; `-p/--print` behaves as before; in the readline fallback the prompt is either submitted as the first line or refused with a message, never dropped silently. [verify: exec `bun test src/commands/shell-initial-prompt.test.ts`]
- AC8: A submitted message that is exactly one `<hc from="…">…</hc>` block, whose `from` is shaped like an hc address and whose `reach` (if any) is one `hc send` line, is shown in the transcript as a message from that agent and reaches the model framed as a message from another agent rather than the user's words; with a `reach` attribute it is framed as a task from the parent and its reply instruction is kept; a message that starts like an `<hc` block but does not parse reaches the model framed as agent-shaped text from an unknown sender, never as the user's words; an agent-shaped message never opens the operator-only wiki-enrich picker or busy dialog; a Telegram line and any other message reach the model unchanged. [verify: exec `bun test src/tui/hc-message.test.ts`]
- AC9: With `HC_TERMINAL_ID` set, the shell agent's system context contains a herdr-core section of at most 1,500 characters naming the agent's own address, delegation with `hc run --bg`, collection with `hc wait`/`hc read`, reporting with `hc send`, and `hc --skill`; with `KERYX_SANDBOX_SHELL` on it also says the sandbox does not contain hc and that hc must never be used to get around a sandbox refusal; without `HC_TERMINAL_ID` the section is absent; no code path adds the herdr-core socket to a sandbox profile. [verify: exec `bun test src/tui/hc-message.test.ts src/harness/process/sandbox/seatbelt.test.ts`]
- AC10: `keryx herdr install` (temp HOME in tests) merges `programs.keryx` = `{name:"Keryx", icon:"keryx/keryx.svg", tint:true, run:["keryx","shell"]}` into `~/.config/herdr-app/programs.json` keeping every other key, writes the icon to `~/.config/herdr-app/keryx/keryx.svg` and the template `~/.config/herdr-core/templates/keryx.md` (`command: keryx shell`, default readiness); a second run changes nothing and says so; `--dry-run` writes nothing and lists the planned changes; `--json` output is real; `keryx herdr remove` deletes only files and the entry whose content still equals keryx's own; `keryx herdr status` reports each target. [verify: exec `bun test src/commands/herdr.test.ts`]
- AC11: `keryx herdr install` failure paths: an invalid `programs.json` makes it exit non-zero naming the file and leaves the file byte-identical; a missing `~/.config/herdr-app` or `~/.config/herdr-core` skips that target with a reason and creates nothing; a user-modified `programs.keryx` entry or `keryx.md` template is kept and reported unless `--force`; the first modification of an existing `programs.json` leaves a backup beside it. · sensitive: failure-scenario [verify: exec `bun test src/commands/herdr.test.ts`]
- AC12: `herdr install`, `herdr remove` and `herdr status` are registered in `src/standard/command-registry.ts` with honest `json`, `read` and `sideEffects`, and the registry, help-group and CLI-reference coverage tests pass. [verify: exec `bun test src/standard/command-registry.test.ts src/standard/command-registry.coverage.test.ts src/standard/help-groups.test.ts src/cli-reference-coverage.test.ts`]
- AC13: Live under an isolated herdr-core session (`HC_SESSION` + scratch XDG dirs), the dev `keryx shell` started with `hc run --bg` shows in `hc get --json`: `app=keryx` and `idle` after start, `working` during a turn sent with `hc send --wait` and `done` after it, `blocked` with `kind=permission` on a shell approval, no status after exit; `hc read` shows no stray escape text; transcript saved in the flow folder. [verify: judged]
- AC14: Live under the same isolated session, the `keryx.md` template started with `hc run --bg --name <n> keryx "<task>"` returns `first_message.sent: true` and the task becomes keryx's first turn; `hc run --bg <dev keryx shell> "<task>"` (positional) does the same; evidence saved in the flow folder. [verify: judged]
- AC15: In the operator's Herdr app, after `keryx herdr install`, Keryx appears in the "+" agent menu with its icon and `~/.config/herdr-app/programs.error` does not exist; done only with the operator's go-ahead, since it writes their real config. [verify: judged]
- AC16: `docs/docs/guides/herdr.md` explains the status protocol, `keryx herdr install/remove/status`, the template, delegation through hc, the sandbox caveat, coexistence with the old Herdr TUI, and carries the exact `defaults/programs.json` entry and icon for an upstream herdr-app PR; `docs/docs/cli-reference.md` lists `keryx herdr` and the positional shell prompt; doc checks pass. [verify: exec `bun run docs:check`]
- AC17: Type check, lint and the touched suites pass: `bun run typecheck`, `bun run lint`, `bun run test:client:terminal`. [verify: exec `bun run typecheck && bun run lint && bun run test:client:terminal`]
