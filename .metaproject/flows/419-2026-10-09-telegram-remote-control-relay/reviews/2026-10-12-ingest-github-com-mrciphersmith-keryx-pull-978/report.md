## Result

41 raw findings in 10 replies (12 replies reported none). After reading them against the post-merge code they reduce to 11 distinct defects (0 major, 9 minor, 2 info, labelled D-01 to D-11 below) and 10 maintainability observations (O-01 to O-10). No blocker and no major was raised.

Real defects in PR 978 (all open, deferred):

1. D-01 (minor): the shell still says closing remote control deletes the topic (tui-shell.ts:7036, :7044) although the PR made close archive it.
2. D-02 (minor): renaming a session still deletes the old topic (hub.ts:968) while the guide, changelog and wiki say only Disconnect deletes.
3. D-03 (minor): archive() forgets the record on any non-retryable refusal (a 403), leaving an open untracked topic.
4. D-04 and D-05 (minor): the status answer shows the Telegram-default mode instead of the running turn's mode; isStatusQuestion swallows 'готово', 'готов', 'закончил', 'update' so the model never sees them.
5. D-06 and D-07 (info): topic says denied after an hour while the dock is open; awaitIdle misses a final liveness re-check.
6. D-08 to D-11 (minor): weak or tautological test assertions, sleeps as negative checks, an untested fail-open path for a topic denial and an untested cross-session ownership check, and several other mutation survivors.

None of the open findings is fixed in this round, because the round targets a merged head and this change is limited to the flow close. They need a follow-up flow; the operator decides the order. D-01 and D-02 belong together (one wording and behaviour decision about archive versus delete).

## Deferred defects (follow-up descriptions)

- D-01 (minor, review-architecture, review-clean-code, review-style, src/tui/tui-shell.ts:7036 and :7044): The shell still tells the operator that closing remote control deletes the topic. Flow 419 changed close and /remote-control off to archive the topic, and remote-queue-wiring.ts, shell-bridge.ts, the guide and the README say 'archived'. Two strings in the /remote-control command path of tui-shell.ts were missed: line 7036 'closing the shell deletes the topic.' and line 7044 '◇ remote control off: the topic is deleted.'. Both are still present in the post-merge tree. Impact: The shell tells the operator that the topic and its history are gone when they are kept and readable (the AC7 behaviour of this PR), and contradicts the guide and README; operators may avoid or distrust /remote-control off. Follow-up: Reword line 7036 to 'closing the shell archives the topic.' and line 7044 to '◇ remote control off: the topic is archived.' (reuse the wording of remote-queue-wiring.ts or one shared constant), update any test that pins the old text, and fix the two stale comments at src/remote/shell-bridge.test.ts lines 178 and 216.
- D-02 (minor, review-logic, src/remote/hub.ts:968; docs/docs/guides/drive-keryx-remotely.md, CHANGELOG.md, .metaproject/wiki/architecture/remote-control.md): Renaming a session still deletes the old topic, but the docs say only Disconnect deletes. The guide, the changelog and the wiki state that only Disconnect in /channels deletes topics. In hub.ts doRegister, a session that registers under a different name calls `this.retire(existing, "renamed by the session")` (line 968), and retire calls deleteForumTopic (line 1057), so a rename deletes the old topic and its history. Impact: An operator who renames a session (for example `/remote-control <new name>`) loses the old topic's history although three documents promise it is kept: a wrong user-facing claim, and at worst a data loss that the operator was told cannot happen. Follow-up: Either archive on rename (call this.archive(existing, "The session was renamed.") instead of retire at hub.ts:968, with the matching test changes) or correct the three statements to 'Only Disconnect in /channels and renaming a session delete topics'.
- D-03 (minor, review-logic, src/remote/hub.ts:1021-1046): archive() treats any non-retryable refusal as 'topic closed' and forgets the record. Every closeForumTopic failure that is not a retryable BotApiError falls through to registry.remove and the 'topic-archived' event. A 403 (the bot lost its manage-topics right) or another refusal does not mean the topic is gone or already closed. retire() separates this case with its `strict` flag and isThreadGone; archive() does not. Impact: When the bot lacks the right to close topics, every closed shell and every orphan sweep forgets the record, logs 'topic-archived' and leaves an open topic that nothing tracks or retries, after the closing note told the operator it is archived. Follow-up: Treat a refusal as done only when the topic is gone or already closed (isThreadGone, or Telegram's TOPIC_NOT_MODIFIED); for any other BotApiError keep the record on the retry path (unavailable, expired) and emit 'topic-close-failed'. Add a test with a fake Bot API that answers 403.
- D-04 (minor, review-logic, src/tui/tui-shell.ts:10114): The status answer shows the Telegram-default mode instead of the mode of the running turn. sessionState uses formatModeInForce(modeForTurn(true)), the mode a Telegram turn would get, not the mode of the turn that is running. The shell already has modeNow() (modeForTurn(remoteBridge?.telegramTurnActive === true)). With no /mode used this session, modeForTurn(true) returns the Telegram default. Impact: An operator types a request in the shell (mode ask) and asks 'status' from Telegram while it runs; the reply says 'Mode: trust (Telegram default)' although the running turn is under ask. The permission mode is a trust boundary, so a wrong mode in a status line misleads the person deciding whether to walk away. Follow-up: Use modeNow() in sessionState so the running turn's mode is shown; if the intent is the next topic line, label it ('Next from Telegram: ...') and show both when they differ. Add a test with a shell-typed turn running.
- D-05 (minor, review-logic, src/remote/progress-notes.ts:231-253): isStatusQuestion swallows short lines that are answers or instructions ('готово', 'готов', 'закончил', 'update'). While the shell is busy, a line that matches the status patterns is answered from session state and never reaches the model or the queue, and report(updateId, 'done') marks it handled. The pattern list holds bare statements that are as likely to be an answer to the model as a question about progress: 'готово', 'готов', 'закончил', 'закончила' (line 241), and a bare 'update' or 'progress' (line 231). Impact: Silent loss of operator input: the agent waits for a typed confirmation or asked to be told when something is done, the operator replies 'готово', and the model never sees it while the topic shows a status text that looks like an answer to it. Follow-up: Drop the bare statements that are not questions ('готов', 'готово', 'закончил', 'закончила', bare 'update') from the list, or require a question form (a kept '?' or an interrogative such as 'уже' or 'is it'); if a bare word stays, also forward the line to the model queue. Add a test that 'готово' reaches the model.
- D-06 (info, review-logic, src/tui/tui-shell.ts:5944): The topic says 'denied' after an hour while the shell dock is still open and can still be allowed. The topic leg is capped at MAX_APPROVAL_TIMEOUT_MS (one hour); the dock has no cap. After an hour serve's expireApproval edits the topic message to 'Expired ... denied' and the topic leg ends with a plain deny, which raceApproval ignores, so the dock stays open and can still be answered with Allow. Impact: The topic reports a denial while the shell still waits and may proceed with the call; a person who read only the topic gets the wrong picture. Edge case (an approval left open for over an hour); the dock answer itself is not affected. Follow-up: When the topic leg ends without a press while the dock is still open, word the topic's expiry as 'no longer answerable here; still open in the shell', or re-arm the topic leg once on expiry.
- D-07 (info, review-security-code, src/remote/command-router.ts:318): awaitIdle does not re-check liveness after its last poll, so one accepted command can run after remote control went off. awaitIdle checks this.ctx.live?.() inside the loop body before each poll sleep. If remote control is switched off during the last 250 ms sleep and the main turn goes idle in the same window, the loop condition ends the loop and awaitIdle returns true without re-reading live(), so the queued command (/route, /external, /external-agents, /model) still runs. Impact: No attacker path: the command was sent and confirmed by the authenticated owner before it was queued, and the window is one poll interval. Effect: a deliberately switched-off remote session can still apply one already-accepted settings change. Defence in depth only. Follow-up: Re-check liveness once after the loop: if (this.ctx.live?.() === false) { this.ctx.record(`${line} dropped: remote control went off while it waited`); return false; } return true;
- D-08 (minor, review-clean-code, review-logic, review-style, src/remote/orphan.test.ts:74, src/remote/approval-mirror.test.ts:71): Two tests no longer check what their names claim after the move from delete to archive. orphan.test.ts line 74 is still titled 'cancels deletion' and still asserts deletedTopics is empty, but never closedTopics, so it cannot catch a sweep that archives a topic whose heartbeat came back. approval-mirror.test.ts line 71 repeats an assertion on textAfterShell, a string captured before the late press and already asserted at line 65-66, so it is true by construction and a rewrite of the message after the press passes. Impact: The tests give a false impression of covering the archive path and the late-press path; a regression in either is not caught. Follow-up: Rename the orphan test to '...cancels the archive' and add expect(h.api.closedTopics).toEqual([]) next to the deletedTopics assertion; replace the last approval-mirror assertion with expect(current(prompt.message.messageId).text).toBe(textAfterShell).
- D-09 (minor, review-testing-practices, src/remote/prompt-reminder.test.ts, approval-mirror.test.ts, command-queued.test.ts, src/tui/approval-mirror.test.ts): Absence assertions rest on fixed sleeps on a real clock. Negative claims ('no reminder after answer or close', 'no abort after a shell abort', 'queue drain after disable') are asserted by sleeping a fixed time (30 to 300 ms against a reminderMs of 150) and then checking nothing arrived; the sleep alone makes the claim. The TUI approval-mirror tests wait a fixed 15 ms and 5 ms inside the dock fake for the same reason. Impact: On a loaded runner a reminder due at 150 ms can arrive after the window, so a still-scheduled reminder passes the suite; it also costs about 1 s of dead time. Low for the TUI pair (microtask-resolved today). Follow-up: Replace each sleep with a positive barrier: start a control prompt in a second session with the same reminderMs, wait with until() for its reminder, then assert the first topic has none; for the TUI pair make the topic fake resolve through a promise the test controls and await one extra macrotask.
- D-10 (minor, review-testing-practices, src/tui/tui-shell.ts (mirror wrapper), src/remote/http-surface.ts closeApproval): Two permission-relevant gates survive mutation untested: a topic denial and cross-session close. Impact: A regression in the first turns a denial pressed in the topic into an approval of the tool call (fail-open on a permission decision); a regression in the second lets one shell strip the buttons from, and mark as answered, another session's pending approval. Neither is currently caught. Follow-up: Extract the post-race mapping into approval-mirror.ts (answerFromOutcome) and test topic deny -> false, topic allow without fingerprint -> true, with fingerprint -> { approved: true, fingerprint }, dock outcome unchanged. Add a test that posts the close route for session A's approvalId with session B's sessionId and expects closed:false, A's buttons intact, and a topic press still resolving A's askApproval.
- D-11 (minor, review-testing-practices, src/remote/client.ts, src/tui/tui-shell.ts, src/remote/bot-api-http.ts, src/remote/shell-bridge.ts, src/remote/progress-notes.ts): Further behaviours of the PR survive mutation: post-response abort gate, length guard, dock plumbing, closeForumTopic transport, cancel reason, openPrompts, progress lifecycle, queue figure.
