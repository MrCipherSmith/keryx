# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: A durable approval store follows `src/lib/serve-turn-store.ts` (owner-only files, atomic writes, append-only events): a record holds an opaque id, bounded action summary, scope, consequence, expiry, correlation id, the call fingerprint and a state (pending, allowed, denied, expired, undeliverable); it validates against `docs/requirements/keryx-remote-entry/schemas/pending-approval.schema.json`; the record carries no arguments that let a caller reconstruct the command. Modules live in `src/lib/serve-approvals*.ts`. [verify: exec `bun test src/lib/serve-approvals-store.test.ts`]
- AC2: In a `keryx serve` turn an `ask` no longer terminates the turn as `approvals-not-implemented-in-this-release`: the turn emits `approval.pending`, waits, and continues on an answer or denies at expiry (config `approval.expirySeconds`, default 300) or when `approval.maxPendingPerSession` (default 4) would be exceeded; the `pendingApprovals` counter in `/v1/status` is real. [verify: exec `bun test src/lib/serve-turn-approval.test.ts`]
- AC3: `GET /v1/approvals` and `POST /v1/approvals/{id}` follow `docs/requirements/keryx-remote-entry/api-protocol.md`: body `{"decision":"allow"|"deny"}`; a first valid answer is applied once; a replayed answer returns 200 with the original outcome and executes nothing; an expired approval returns 410 and is already denied; an answer from the turn that raised the approval returns 403; an unknown id, and an id the token may not see, both return 404 indistinguishably; a malformed body is rejected before any state change. [verify: exec `bun test src/lib/serve-approvals.route.test.ts`]
- AC4: An allow is bound to the pending call: it applies only to the call whose fingerprint (`actionFingerprint`) is on the record, cannot change arguments or broaden scope, is one-time only (never sets session MCP trust), covers this one call only so that a destructive, credentials or hook-ask call asks again the next time (the floors are recorded as labels, not lifted), and never overrides a policy deny; a tool call executes at most once per approval, including across a process restart. [verify: exec `bun test src/lib/serve-approvals-binding.test.ts`]
- AC5: Persistence and delivery: pending records survive a restart of `keryx serve`; on startup a pending record whose turn no longer exists is resolved as expired-deny with the reason on record, and its call is never re-executed; a delivery failure (the event append fails, or no consumer is attached when `approval.requireConsumer` is true, default true) resolves the approval as `undeliverable` deny immediately, not at expiry; every resolution appends an evidence event. [verify: exec `bun test src/lib/serve-approvals-durability.test.ts`]
- AC6: The TUI shows pending remote approvals: `/approvals` is in the slash registry and help and opens a modal listing pending and recently resolved approvals (summary, scope, consequence, expires in, state) where the operator can allow or deny one, the sidebar shows a section with the pending count, and readline has a text equivalent; `keryx approvals list|allow|deny <id>` works locally against the store and is in `GROUP_SUBCOMMANDS`. UI text is English. [verify: exec `bun test src/tui/approvals-inspector.test.ts src/commands/shell-slash-registry.test.ts`]
- AC7: The documented client contract for a chat bridge (list, answer, statuses, a curl example, the fingerprint and expiry rules) is added to the docs site; the R4d roadmap entry and the remote-entry requirements are updated from not started to implemented with the deviations named; README, CHANGELOG and the next patch version are updated. [verify: exec `bun run docs:links`]
- AC8: The change ships as the next patch release: CI green on the PR head, a review round against the PR head with the verifier on, and the installed build passes `keryx --version`, `keryx review tier`, `keryx mcp list` and a round trip through the real CLI route (a scripted serve turn raises an approval, `keryx approvals list` shows it, `keryx approvals allow` answers it, the tool runs once). Stock `keryx serve` registers no tools and so raises no approvals, which is why the turn is scripted. [verify: judged]
- AC9: The flow stops after the release smoke; the chat-bridge card in helyx waits for the operator's word. [verify: none — a stop is an absence of work; the journal entry and the operator report are the evidence]
