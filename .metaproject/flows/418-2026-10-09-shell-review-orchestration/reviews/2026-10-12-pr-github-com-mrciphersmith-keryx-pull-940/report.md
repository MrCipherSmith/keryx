## Deferred defects (follow-up descriptions)

- F-001 (major, review-logic, src/tui/tui-shell.ts): Busy slash lines are queued on mainQueue and run when the turn ends, but every drain site shifts ONE item and relies on a later turn-settle to shift the next. A queued slash command that starts no turn (/compact, /model, /goal, /connect) ends without a settle, so every line queued behind it stays in mainQueue. Impact: While a turn runs, '/compact' then 'continue with the review' leaves the second line stuck; the operator's next typed line runs ahead of it (order inversion). In an unattended trust-mode run a queued slash line silently stops the queue. Follow-up: after runQueued runs an item that starts no foreground operation, drain the next item (shared drainNext helper used by the three sites), stopping once an item starts a turn. Add a headless test that queues ['/compact', 'question'] and asserts the question is dispatched.
- F-002 (minor, review-logic, src/tui/busy-dispatch.ts): BUSY_REFUSED_COMMANDS lists /new, /clear and /resume as session-swapping commands refused while busy, but the alias /sessions takes the same resumeSessionInteractive path and is queued instead. Impact: Queue ['/sessions', 'q2'] while busy: when the turn ends the picker opens and, if the operator resumes another session, q2 (typed against the old history) is answered in the resumed session. Follow-up: add /sessions to the refused set, or derive the refused set from the handlers that swap the session so an alias cannot drift; add a test for the alias.
- F-003 (minor, review-clean-code, src/tui/tui-shell.ts): The enqueue sequence (mint `mq${mainQueueSeq++}`, push a QueuedMainQuestion, paintMainQueue) is now present three times in tui-shell.ts; main-queue.ts owns the queue shape but has no enqueue function. The PR added the third copy. Impact: A change to the queue entry shape or id scheme must be repeated at each site; a missed one makes one queue path behave differently. Follow-up: add an enqueue helper to main-queue.ts and call it from the three sites; keep the tests that pin the push text pointing at the helper.
- F-004 (minor, review-logic, src/commands/review-slice.ts): runSlice clears only slice-NN.diff files, so retry-state.json and the r1-<reviewer>-NN.diff retry slices survive a re-slice into the same directory, and retry state is keyed by reviewer name alone. runRetryPlan also reads and rewrites manifest and state without a lock. Impact: After a re-slice or in a later round, a reviewer with attempt 1 on record is planned not-run on its first failure (a false 'Not run' line); two retry-plan processes on a parallel-tool host can overwrite each other's additions. The failure direction is safe (reported as not run, never as clean). Follow-up: have runSlice remove retry-state.json and r1-* slices (or key the state by manifest hash), and serialise the read-modify-write of manifest and state (lock or compare-and-swap); add a two-round test.
- F-005 (minor, review-architecture, src/commands/review-slice.ts): runRetryPlan builds the extended manifest itself (spread of the old manifest plus retry slices); the totals (slices, bytes, files) are owned by buildSlices and are not recomputed on this path. Impact: After a retry, manifest.slices lists more entries than totals.slices reports and totals.bytes and totals.files omit the retry slices, so any reader of totals sees counts that disagree with the list. Follow-up: move manifest extension into src/review (retry-plan or slice) and recompute totals there.
- F-006 (minor, review-clean-code, src/review/retry-plan.ts): notRunLine always says the reviewer failed after a smaller-slice retry, but it serves all three not-run exits; two of them (no assigned slice in the manifest, assigned slice below the minimum after halving) dispatch no retry. Impact: The report line the orchestrator pastes tells a reader a retry happened when none did, which misstates the effort spent on the gap. Follow-up: make the line depend on the exit (retried or not) and add a test per exit.
- F-007 (major, review-security-code, src/lib/trust-routine-command.ts): The trust routine allow-list accepts `bun test` with any further arguments (and the same inside `keryx ctx run --`, and after `cd <dir> &&`). `bun test` runs repository code: test files, bunfig.toml preload and `--preload <file>`. Impact: With untrusted content in the turn, a prompt-injected model, or a checked-out PR whose bunfig.toml sets a preload, runs project code without approval, which is the capability the untrusted-content latch withholds. Follow-up: drop `bun test` from the routine list for the post-untrusted case or allow it only with no arguments and an unchanged bunfig; add a test with `--preload` and a foreign `cd`.
- F-008 (major, review-security-code, src/commands/review-slice.ts): `review slice`, `dispatch-check` and `retry-plan` are in the no-prompt routine list but write to paths taken verbatim from flags: slice --out (creates the directory, deletes slice-NN.diff, writes manifest.json), retry-plan --state and --manifest (overwrite the named file). Impact: After untrusted content, an injected model can overwrite or delete files outside the project through a command classed as routine, with no prompt. Follow-up: confine --out, --state and --manifest to the project root or .metaproject, or leave these verbs out of the routine list when a path flag is given; add tests for an outside path.
- F-009 (minor, review-logic, src/lib/trust-routine-command.ts): Any segment with an unquoted metacharacter is rejected, and `>`/`<` are metacharacters. The commands the PR itself prescribes (`keryx ctx run --raw -- keryx review scope --json > scope.json`, saving slices and payloads by redirection in the SKILL) are therefore never routine. Impact: In trust mode after untrusted content the documented shell-host commands still prompt, which defeats the purpose of the routine list for a long review run. Follow-up: either allow a single redirection to a path under the project, or change the SKILL and help text to name an output flag instead of a shell redirection.
- F-010 (minor, review-logic, src/session/ask-answer-notes.ts): A stored ask_user answer is keyed by the normalized question text only: the options are not part of the key, punctuation and path separators are collapsed ("Delete ./build?" and "Delete /build?" collide), and an answer longer than about 1700 characters is stored cut by the note limit and replayed as complete. The read side swallows failures silently. Impact: The same question with a different option set, or a lookalike question, gets a stale or truncated operator answer replayed without asking. Follow-up: include the option ids in the key, keep punctuation that carries meaning (or compare the stored question text), refuse to replay a truncated answer, and log a read failure.
- F-011 (minor, review-clean-code, src/commands/agent.ts): Docs and comments describe values or behaviour this PR changed: cli-reference says 25 requests at the cap (now 201); the JSDoc of DEFAULT_MAX_SUBAGENT_CONCURRENCY argues for a low single-digit ceiling while the value is 10; resolveAgentMaxRounds JSDoc omits the mode parameter and the trust fallback; shell.ts keeps the comment of a deleted maxRounds line; comments still equate onDestroy with one Ctrl+C; tool descriptions repeat the literals 40 and 200; permission-modes.md says follow-through continues 'in a row' while the counter is a per-turn total. Impact: A reader tuning concurrency or round budgets, or sizing a subagent from the docs, is told the opposite of what the code does. Follow-up: one docs and comments pass: fix the figure, the two JSDoc blocks, the orphan comment and the Ctrl+C comments, interpolate the constants into the tool descriptions, and reword 'in a row'.
- F-012 (minor, review-style, .metaproject/flows/418-2026-10-09-shell-review-orchestration/plan.md): The flow's plan.md was merged as the untouched scaffold (Status: draft, numbered placeholders) and tasks.md lists only the four scaffold tasks, while flow.json and the journal carry T5-T8 and the closed implementation. Impact: A reader opening the flow folder to learn the approach finds placeholders and a draft status that contradicts the journal. Follow-up: fill plan.md with the approach as built and bring tasks.md in line with flow.json.
- F-013 (minor, review-testing-practices, src/commands/agent-trust-orchestration.test.ts): Several new tests cannot fail for the claim they make: the 'ask mode control' uses `keryx review verify --run`, which is not in the routine list, so it prompts with or without the mode gate; the busy-dispatch tests assert substrings of tui-shell.ts source instead of driving the code; the /mode, /remote-control test never reaches deferredBusyAction; the okReply guard is dead; temp directories are never removed; two fixtures and two `gitFile` helpers duplicate setup. Impact: False assurance on the behaviours AC5 and the trust-mode gate depend on (including the queue drain in F-001, which these tests miss); leftover temp files on every run. Follow-up: use a real routine verb in the control, drive the queue drain with fakes, add a two-run slice test, remove the dead guard, clean up the temp dirs and share the fixtures.
- F-014 (info, review-architecture, src/harness/tool/builtin/spawn-subagent-tool.ts): The parent's round budget depends on permission mode, but the subagent ceilings are changed for every mode and provider: default rounds 10 to 40, cap 24 to 200, concurrency 3 to 10. After untrusted content the spawn batch is still gated, so review waves of 10 are not reachable without a prompt. Impact: Ask and auto mode quietly gain a 5x child budget and 10 simultaneous streams; a looping child sends its whole history for up to 200 rounds. Whether this is intended is a policy question, not a proven defect. Follow-up: decide whether the larger budgets are trust-only; if so make the constants mode-aware, and record the choice.
- F-015 (info, review-style, src/tui/tui-shell.ts): Readability points: long functions (buildSlices, runRetryPlan), four-positional-argument helpers, askUserQuestion named like an action, a duplicated four-clause guard in storedAskUserAnswer and rememberAskUserAnswer, a three-deep ternary, unnamed literals (3, 12, 200), an immediately-invoked fallback in onCtrlC, a second private schema resolver in dispatch-check, naming of followThroughOn and ctrlCPress, a repeated import and one missing JSDoc. Impact: Maintenance cost only; no behaviour is wrong. Follow-up: fold into the next change that touches these files; none needs its own change.
