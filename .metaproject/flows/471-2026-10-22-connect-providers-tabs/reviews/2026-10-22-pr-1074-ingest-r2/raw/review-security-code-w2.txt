### Clean Areas
- Injection, command, SSTI, eval: none introduced; all new strings are rendered as text chunks.
- Auth/authz: the Telegram hooks (testProvider, connectWithDeviceLogin, listAddableProviders) are thin wrappers; who may call them is decided by the gateway in other slices (not reviewed here). Within this slice, [Connect] from the chat cannot take a key: connect() refuses any provider where catalogAllows(id, 'device-code') is false.
- Secrets: no key, token, address or env-var name reaches the chat. remoteFailureText drops ModelsFailure.detail; the catch in createRemoteDeviceLogin returns fixed texts; the TUI's catch in runProvidersModal prints error.name only. The user code and verification URI are the only login values sent, and they are public by design.
- SSRF / path traversal / open redirect: the chat supplies only a provider id, looked up with connectionProviderByName / the catalog; unknown ids return 'unknown provider'. The verification URI comes from the catalog's fixed device endpoints.
- Secret keystroke handling (TUI): the Providers dialog is closed (finish -> surface.close) before the key step opens, and unsub() removes the dialog's keypress handler first, so the 1/2/Tab/x/a shortcuts cannot swallow or log typed key characters. ownsKeys() holds every key while a Disconnect is armed.
- Credential persistence: keys are still saved through saveApiKey (0600) and process.env only after the operator submits one; Esc at the key step saves nothing. The key is saved before the /models check by design (documented IMPORTANT note, unchanged).
- Concurrency: remote device login is single-flight (current !== undefined), time-limited, aborted on recordOff/onDestroy, and re-checks shellIsBusy() immediately before applyEnv so the environment is not changed under a running turn. connectedProviders cache is invalidated on connect, disconnect and device login; a failed load is not cached.
- Crypto, CSRF, React patterns, DoS caps: not applicable to the changed code.
