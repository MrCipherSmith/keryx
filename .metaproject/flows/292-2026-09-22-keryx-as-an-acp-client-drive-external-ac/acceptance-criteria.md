# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: A process test starts a scripted fake ACP agent. The agent is a repo fixture script driven by a JSON script. The test drives it through the existing `ExternalSpawnPort` over real stdin/stdout pipes, with no network. The run must complete `initialize` (protocolVersion 1), then `session/new`, then `session/prompt`, ending with stopReason `end_turn`. `session/new` must carry an absolute `cwd` equal to the run's disposable worktree. The streamed `session/update` messages must be folded into `ExternalEvent`s (`assistant_text`, `tool_call`, `tool_result`, `usage`), and the run must finish as `ExternalChildOutcome.status: "Completed"`. A second case has the fake agent reply with an unsupported protocol version. That run must end `Error` with a named reason, and the child must be killed.
- AC2: Every `session/request_permission` is decided by `resolveApprovalDecision`. Its risk comes from the tool call: - `read`/`search`/`think` → read; - `edit`/`move` → write; - `delete` → destructive; - `execute` → shell, or destructive when `isDestructiveCommand` matches; - `fetch` → denied; - `other` or a missing kind → shell with destructive set. Any `locations[].path` outside the worktree escalates a read to a prompt. keryx answers with the agent's `allow_once` option only when the gate says `auto`, or when a human approval echoes the prompt's fingerprint. keryx never selects `allow_always`. A table-driven unit test covers each kind × mode, and the fake-agent process test confirms the chosen `optionId` on the wire. Because the tool kind and inputs are the agent's own description, a foreign agent never runs under `trust` or `auto`: those modes are lowered to `ask` for ACP-client runs, and the run record says so.
- AC3: An unattended run fails closed. An unattended run is `--unattended`, a run with no TTY, or a run with no approver wired. In it, every permission that would need a prompt is answered with `reject_once`, or with `{outcome:"cancelled"}` when the agent offered no reject option. An approver that has not answered within the timeout is answered the same way. A human "no" is answered the same way. A process test shows that the fake agent received the rejection and did not report the tool as run. The test also shows that the run record holds one decision entry per request, with the mapped risk, the gate decision, the verdict, `timedOut` and the reason (policy, unattended, timeout or human).
- AC4: `clientCapabilities` in `initialize` advertises only what keryx serves: - a read-only run advertises `fs.readTextFile: true`, `fs.writeTextFile: false`, `terminal: false`, and no `elicitation`; - `--write` additionally advertises `fs.writeTextFile: true`; - this flow never advertises `terminal`. A process test has the fake agent call `fs/write_text_file` in a read-only run, and call `terminal/create` and `elicitation/create` in every run. Each call must get a JSON-RPC error with a named reason and be recorded. No file may be created and no process spawned.
- AC5: `fs/read_text_file` and an advertised `fs/write_text_file` run only inside keryx's own confined code. Paths are confined to the worktree by real path. For a file that does not exist yet, the check uses the nearest existing ancestor. Tests must cover: - a symlinked parent directory that points outside the worktree is refused; - `../` traversal is refused; - agent credential files (`touchesAgentCredentials`) and managed flow files are refused. Writes go through the AC2 bridge as risk `write`. After any run, a hash of the operator's project tree is byte-identical to the hash taken before it. In a `--write` run, the worktree's diff is saved as the run's patch artifact and is never applied.
- AC6: Context is offered through keryx's own MCP server. - `session/new` carries one stdio `mcpServers` entry. It launches the running keryx build (`process.execPath` plus the CLI entry, not `keryx` from PATH) as `serve-mcp --read-only --cwd <project-root>`. - A test shows that `serve-mcp --read-only` lists no tool marked `mutating: true`. - A process test has the fake agent echo back the `mcpServers` it received. - When the MCP module or SDK is unavailable, the run still proceeds and records `context: not-offered` with the reason. - The first prompt is built by `buildExternalPrompt`. Embedded resource blocks are sent only when the agent advertised `promptCapabilities.embeddedContext`.
- AC7: Every run is persisted as a keryx session that `keryx sessions` lists, with provider `acp:<agent-id>`. The session contains: - the redacted assistant text and the tool calls; - every permission decision, and every fs/terminal request with its outcome; - the argv, the worktree path, and the agent's name and version from `initialize`; - the token usage and the cost, taken from `usage_update` only when the agent reported them. A missing cost is recorded as missing, never as 0. A test asserts both the reported case and the missing case.
- AC8: A CLI command runs one registry agent over ACP: `keryx agents external run <id> --task "<text>" [--unattended] [--write]`. `runExternalChild` routes a registry entry with `transport: "acp"` to the ACP supervisor. The command is guarded by the existing `gdskills.external-agents` capability and the per-agent config. Tests show: - a named refusal when the capability is disabled, and in CI; - `Denied` with a named reason when the binary is missing; - on timeout, `session/cancel`, then a kill after a grace period, then status `Timeout`; - the disposable worktree is removed on every exit path, including a throw from the spawn port.
- AC9: A process test has keryx-as-client drive keryx-as-agent (`keryx acp --fixture <script>`) end to end. A gated tool in the inner keryx sends a real `session/request_permission` to the outer keryx. The outer keryx answers by its own policy: denied when unattended, allowed after an injected approval. The inner turn's record shows that outcome.
- AC10: The honest limit is tested and written down. - A test has the fake agent write a file with its own filesystem calls instead of ACP. The test shows that the file lands only in the disposable worktree, which is removed afterwards. The file must not be recorded as a keryx-mediated write, and the project tree must be unchanged. - The docs state: - keryx cannot see or gate an agent's internal tools that never call ACP; - an unadvertised capability is a request to the agent, not a boundary; - permission classification relies on the agent's own description of the tool call; - calls the agent makes to the MCP servers keryx gave it do not pass the permission bridge; - the agent process itself is not OS-sandboxed in this flow; - the disposable worktree is the load-bearing containment (D-08).
- AC11: README and the docs site gain an "ACP client" page. It covers usage, the permission mapping table, the advertised capabilities, the record format and the limits from AC10. `keryx agents external list` shows ACP entries with their transport. The docs for the external agent runtime (`docs/requirements/keryx-external-agent-runtime`) note the third transport.
- AC12: CI is green on the PR, and `bun run src/cli.ts health run` passes. The ACP client tests make no network calls and need neither `gemini` nor `claude` installed.
