# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: A new trigger action kind `agent-task` (a free-form prompt, a dispatch block with; provider, model, `ask`|`trust`, rates, `ceilingUsd` and `maxSeconds`, a grants block and a; report block) loads and validates the way the existing kinds do. A missing prompt, rates or ceiling is refused on load with the reason. `permissionMode: "auto"` is refused on load with the reason. A granted tool that is not in the built-in catalogue is refused on load with the reason. A granted tool whose argv the unattended floor refuses (for example `gh pr merge`) is; refused on load with the reason. Proven by `src/trigger/config.test.ts` cases.
- AC2: `keryx trigger run <name>` on an `agent-task` entry runs one unattended agent turn with; the entry's prompt, under the entry's own permission mode. The dispatcher, not the agent, writes the agent's final message to; `.metaproject/data/trigger/reports/<name>/<runId>.md`, with a header giving the outcome, cost, granted calls and denials. That directory is gitignored. The agent cannot write there, because the floor protects the path. Proven by a scripted-provider test through `runTriggerOnce`.
- AC3: Granted tools keep credentials out of the model's reach. Each granted command runs through `execFile` outside the sandbox, with a fixed argv; template, pattern-checked parameters (a value starting with `-` is refused), a timeout, an; output cap and secret redaction. The model receives only the output. In the same run, a `shell_exec` of `env`, `echo $GH_TOKEN`, or `cat` of the gh config; returns no token and no gh config. Proven by a test that sets a sentinel `GH_TOKEN` in the; dispatcher's environment and asserts the sentinel appears in no tool result, in no; provider request and in no report.
- AC4: The network grant is `off` (the default, `--unshare-net`) or `full` (today's host network, always shown with the NETWORK ON warning). An `allowlist` mode — shell commands reaching only listed domains through the loopback allowlist proxy, host loopback unreachable — is delivered by flow 301; until then an entry asking for it is refused on load with a reason naming that it is not yet available, and the capability matrix keeps `not-implemented`. Checking GitHub needs no sandbox network, because granted tools run outside the sandbox (AC3).
- AC5: The unattended posture and floor are unchanged by any grant, and a changed schedule; does not run. The existing `trigger/unattended` and `sandbox/unattended` tests pass unmodified. An `agent-task` run under every grant combination still refuses: push, merge, tag, publish, and mutating `gh api`; flow-state verbs, nested `trigger run`, and schedule create/install verbs; writes to `triggers.json`, `flow.json`, `acceptance-criteria.md`, `data/trigger/`, the; schedule store or the reports. `trust` without a working sandbox still refuses with `sandbox-unavailable`. At confirmation, keryx stores a hash of the entry's prompt, grants and dispatch block. `keryx trigger run` refuses an entry whose content no longer matches that hash. It records; `dispatch-refused` with refusal `grants-changed`, and calls no model.
- AC6: The operator can create a schedule from the TUI with the `/schedule` slash command. `/schedule` is registered in `AGENT_SLASH_COMMANDS`, and the registry tests are updated. It collects the prompt, cadence and grants, then shows ONE confirmation card listing: cadence as cron, plus the next three run times; prompt; provider and model; ceiling and max seconds; network mode; every granted tool with its resolved binary and account; the unit or crontab path and the exact `ExecStart`; linger status. Declining writes no config and installs nothing. Proven by a TUI handler test.
- AC7: The agent can create a schedule from natural language with a `schedule_create` tool; ("schedule a task every 4 hours to check GitHub"). The approval always asks and shows the same card as AC6, in every permission mode; including `auto`. The approval is never auto-approved from a saved allowlist, never remembered, and never; offers "always". The tool is not in the unattended roster. A test drives the tool under `auto` with an approver that declines, and asserts that; nothing was written or installed.
- AC8: A confirmed schedule is installed as a background timer, and installation is; idempotent. On Linux: systemd `--user` units, named `keryx-<projecthash>-<name>`, containing a real; `OnCalendar=` translated from the cron, `Persistent=true`, `WorkingDirectory=` set to the; project root, and an absolute interpreter and script. The units pass; `systemd-analyze verify`, including on a path with a space. On macOS: a LaunchAgent plist. Otherwise: a marked crontab block. Installing twice leaves exactly one unit, plist or block. Keryx never runs `loginctl enable-linger` itself. Proven by renderer tests plus an installer test against a temporary unit directory, with; a fake `systemctl`.; the same renderer serves `keryx trigger schedule`, so the unit it prints gains the real `OnCalendar=` (today it prints a timer with only a commented placeholder, which never fires) and the project-unique unit name — a test asserts the printed timer fires on the translated schedule by `systemd-analyze calendar`.
- AC9: `keryx schedule list|pause|resume|run|remove` work from the CLI. `list` shows name, cadence, enabled or paused, installed or not, next run, last outcome; with cost, and the last report path. `pause` disables the timer and marks the entry disabled. A fire while paused records; `no-op`. `resume` re-enables both. `run` performs one pass now. `remove` uninstalls the timer and deletes the entry after a confirmation, touching only; files that carry keryx's managed header for this project. Proven by installer tests.
- AC10: The TUI sidebar has a Schedules section, mounted in `sidebarTop` like the Plan and Jobs; sections. Each schedule is one compact row: name, next run, and last outcome (ok, failed or; refused, plus cost). The section is hidden when there are no schedules. Row text stays within `SIDEBAR_TEXT_WIDTH`. The colours come from theme slots, so a `/theme` switch recolours them. Clicking a row opens that schedule's detail modal. Proven by a panel test over a fixture ledger and schedule store.
- AC11: The detail modal opens through `modal-host` and has four tabs: Overview: cadence, next and last run, enabled, installed unit, linger. Grants: network mode, and each granted tool with its account. Runs: the last N ledger records, with outcome, cost and refusal reason. Report: the latest report, scrollable. Its actions: pause/resume works in one step; run-now and delete need arm then `y`, and any other key cancels; each action calls the same function as the CLI (AC9); the modal refreshes after an action. Proven by modal tests in the style of `mcp-inspector.test.ts`.
- AC12: Every schedule interaction is reachable without a mouse. `/schedules` opens a list modal: ↑/↓ selects, Enter opens the selected schedule's detail; modal, Esc closes. Every action in AC11 has a key, and the tab's first line shows those keys. Proven by a keypress-driven test that goes from `/schedules` to a paused schedule without; any mouse event.
- AC13: A scheduled run that finishes in another process updates the open TUI without a; restart. The Schedules section, and an open detail modal, poll the ledger and reports on an; injectable interval. They repaint only when the ledger or reports changed. The TUI shows a one-line notice once for each new report. Proven by a test that appends a record and a report to a fixture, fires the injected; timer, and asserts the row and the Runs tab changed and the notice appeared once.
- AC14: Every scheduled run is spend-bounded and visible in governance. Before its first model call, a run reserves spend under the project-wide lock, against; the smaller of the project ceiling and the schedule's `ceilingUsd`. Over either ceiling, it records `budget-refused` and calls no model. The sidebar row and; the modal show that outcome. Its closing record in `runs.jsonl` carries the runId, tokens and USD, and it closes the; reservation. `keryx governance report` includes that cost in project trigger spend. Proven by an; extended `governance/report.test.ts` case.
- AC15: Documentation is updated, and CI is green with `keryx health run` passing. `docs/docs/cli-reference.md`, `README.md` and the docs site no longer say that keryx only; prints schedules. They document creation with confirmation, grants, installation, list, pause/resume/delete, the sidebar and modal, and reports. They state the honest limits: the machine must be on; a sleeping laptop gets one catch-up run on wake through `Persistent=true`; cron does not catch up; without linger nothing runs while logged out; the hardened sandbox is Linux-only, so macOS schedules are `ask` with granted tools; only. An agent skill tells the agent when to propose `schedule_create`, and that it can never; confirm a schedule itself. CI is green on the branch, and `keryx health run` passes.
