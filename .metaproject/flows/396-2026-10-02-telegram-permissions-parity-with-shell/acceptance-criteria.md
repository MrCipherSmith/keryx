# Acceptance Criteria

Rules:

- Criteria lines use the exact format `- ACn: <criterion>`.
- After `flow freeze` this file is checksum-protected: any edit outside
  `keryx flow ac update` fails every gate and status transition.
- Completion requires every ACn to be confirmed via
  `keryx flow ac confirm <id> <ACn>`.

## Criteria

- AC1: With no `permissionMode` key in the remote config, a Telegram-started turn runs under `trust`: reads, non-destructive `apply_patch` inside the project and non-destructive `shell_exec` run without a prompt, each leaving a `◇ auto-approved (trust)` transcript line and an `approval` event in the remote panel carrying the Telegram user id. [verify: exec `bun test src/remote src/tui`]
- AC2: In a Telegram turn under `trust` the following still produce a prompt in the topic, and give the same decision as the same call in a local `trust` turn (one table-driven test): destructive command, privilege escalation, downloader, agent credential files, `flow confirm` and SAC confirm-review, a `git-publish` lease, a `PreToolUse` hook ask, a call following untrusted external content, destructive `apply_patch`, MCP `use_tool`. `/plan` read-only still denies every mutation. [verify: exec `bun test src/remote src/tui src/commands`]
- AC3: `apply_patch` with a target outside the project root is refused in a Telegram turn exactly as in a local turn. [verify: exec `bun test src/remote src/lib`]
- AC4: The remote config accepts `permissionMode` `ask` or `trust` only (`auto` and anything else are rejected with a reason, unknown keys are still rejected); an absent key means `trust`; `ask` restores today's behaviour (every non-read call asks). [verify: exec `bun test src/remote`]
- AC5: In a Telegram turn a `shell_exec` that matches a pattern in `permissions.json` or the session allowlist is auto-approved without a prompt, with the same exclusions as the local dock (destructive, credentials, SAC confirmation, lease, hook ask, untrusted origin). [verify: exec `bun test src/remote src/tui src/commands`]
- AC6: The default run limit is none: with no `runTimeoutMs` (or `0`) no timer is set and a Telegram turn is never stopped by time; a positive `runTimeoutMs` in an existing file still stops the run with the existing message. [verify: exec `bun test src/remote`]
- AC7: `/stop` in the topic cancels the running turn when it was started from Telegram and replies "Stopped by you."; with no running turn, or when the running turn is the operator's own, it replies why and cancels nothing; only `allowedUserIds` can use it; it appears in `/help` and in the bot command menu; the `/interrupt` refusal text points to `/stop` and no longer mentions a Stop button. [verify: exec `bun test src/remote`]
- AC8: The default approval wait is 15 minutes (900000 ms) and is set by the remote config key `approvalTimeoutMs` (30000 to 3600000), delivered to the shell at registration; an unanswered request is still denied (fail closed) and the expired message says it expired. [verify: exec `bun test src/remote`]
- AC9: The approval prompt for `shell_exec` shows `Allow | Always: <pattern> | Deny` only when the local dock would offer remembering (same validators and exclusions, `suggestShellPatterns` unchanged, so `docker *` and similar prefixes are never offered); pressing Always by an allowed user stores the pattern with `allowShellPattern`, approves that call, and edits the message to `Remembered: <pattern>`; a pattern the store refuses approves once and says it was not remembered. [verify: exec `bun test src/remote src/tui`]
- AC10: An Always press by a user outside `allowedUserIds`, an expired, replayed or other-topic button, and text produced by the model never persist anything or approve anything. [verify: exec `bun test src/remote`]
- AC11: `keryx permissions list` and `keryx permissions remove <pattern>` and the `/permissions` shell command list saved patterns (active, and inactive with the reason) and session grants, and remove one; a removed rule asks again at the next approval in a running shell. [verify: exec `bun test src/commands src/lib src/tui`]
- AC12: TUI visibility: `/settings` has a "Telegram" group with rows Permission mode, Run limit and Approval wait (value, scope label, actions that run `/remote-policy`); the sidebar remote panel shows the posture line and the count of saved rules and opens `/permissions` on click; `/permissions` opens a modal; every one is reachable by slash command and menu; the readline `/settings` table shows the same rows. `/remote-policy` and `/permissions` are refused from the topic with a reason. [verify: exec `bun test src/tui src/remote`]
- AC13: `keryx serve status` and `--json` print the effective Telegram posture (permission mode, run limit, approval wait, number of saved rules, number of allowed users) with no ids and no secrets. [verify: exec `bun test src/commands src/lib`]
- AC14: Existing configurations keep working unchanged: `serve.json` profiles `remote-restricted` and `remote-read-only` resolve to the same profiles (`resolveRemoteProfile` and `localBaselineProfile` untouched, HTTP serve turns unchanged); a remote `config.json` with explicit `runTimeoutMs`, `orphanMs` and without the new keys loads and keeps those values; the existing tests pass without edits to their expectations. [verify: exec `bun test src/harness/policy src/lib src/remote`]
- AC15: Every Telegram auto-approval and every persisted rule is recorded with who (Telegram user id), what and when in the transcript and the remote event ring, and no event or message contains a bot token, shell token or unredacted secret. [verify: exec `bun test src/remote src/tui`]
- AC16: README and the docs site (answer-remote-approvals, drive-keryx-remotely, cli-reference, commands-by-task, limitations) describe the new default, what stays gated and why, `/stop`, Always, `/permissions`, `/remote-policy` and the rollback to today's behaviour, in the same PR as the code. [verify: judged]
- AC17: The version in `package.json` is higher than the version on main at merge time. [verify: judged]
- AC18: Live acceptance by the operator in the topic geekom:keryx: a task that edits files and runs a Docker status check finishes with no prompt; a destructive step asks and its prompt is still answerable after 10 minutes; Always on a command means it is not asked again and the rule is listed and removable in the shell; a run past 30 minutes continues until `/stop` ends it. Only the operator confirms this. [verify: judged]
