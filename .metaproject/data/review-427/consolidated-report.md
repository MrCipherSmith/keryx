## Deferred defects (follow-up descriptions)

- D-01 (major, review-logic, review-security-code, src/review/ledger.ts): parseReviewResult can return the wrong object as the reviewer result. The bare-JSON branch scans every `{` and keeps the last balanced object with a string `status`. When the outer REVIEW_RESULT object is truncated or malformed (cut-off reply, trailing comma), the scan descends into nested objects and returns a `slices[]` entry such as {"id":"slice-03","status":"DONE"} as the reviewer's result. A trailing status-bearing object after the real result (a quoted snippet, an example) also wins over the real result, because the reviewer contract's ```json fence with a REVIEW_RESULT line does not match the labelled-block regex and always goes through the last-wins scan. Impact: In planRetry a DONE fragment is treated as a finished reviewer and a slice is marked accepted with no findings; a fragment with another status is stored as a permanent notRun entry; a BLOCKED or INCOMPLETE result followed by a forged or echoed {"status":"DONE"} is recorded as DONE. A damaged reply becomes a clean pass or a bogus not-run entry instead of a retry (AC5: malformed input must not give coverage). buildLedger stays fail-closed (a result with no reviewer and no findings array is ignored), so the harm is in the retry path. Follow-up: After an outer candidate fails to balance or parse, resume the scan after its end instead of descending into nested braces; accept only top-level objects that carry `reviewer` or a `findings` array; prefer the object that follows the REVIEW_RESULT marker (also inside a ```json fence) and treat two distinct status objects as ambiguous (undefined). Add tests: a truncated reply and a trailing-comma `slices` array must be unreadable; a trailing {"status":"DONE"} after a BLOCKED result must not override it.
- D-02 (major, review-testing-practices, .metaproject/flows/427-2026-10-11-review-autonomy-hardening/acceptance-criteria.md): AC2 and AC5 name an exec check on a test file that does not exist. Acceptance criteria AC2 and AC5 carry `[verify: exec `bun test ... src/commands/review-slice.test.ts`]`, but src/commands/review-slice.test.ts is not in the tree. `bun test` treats arguments as path filters, so the check exits 0 on the other listed file and passes while verifying nothing for src/commands/review-slice.ts, whose readResult now uses parseReviewResult (malformed input throws UnreadableInput) and whose plan output carries scopeFingerprint. Impact: The exec gate for 'malformed input gives no coverage' and for manifest/content invalidation reports green without covering the CLI path that reads reviewer results; a regression in readResult would fail no gate. Follow-up: Add src/commands/review-slice.test.ts covering readResult through the command (bare JSON, fenced REVIEW_RESULT and marked JSON accepted; a malformed or status-less result exits with the UnreadableInput message and records no coverage; the plan output carries scopeFingerprint and changes when a slice is rewritten with same-size content), or correct the two verify commands to name tests that exist.
- D-03 (minor, review-highload, review-performance, review-security-code, src/review/ledger.ts): parseReviewResult is quadratic on text with many unclosed braces. Every `{` is tried as a candidate start and the scan runs to the end of the text when the braces never balance (an unbalanced brace, or a lone double quote that flips the quoted state). The previous implementation was linear. Impact: Measured by three reviewers with bun: 40 KB of 'prose {not JSON yet' takes 157 ms and 160 KB takes 2.7 s; 20,000 `{` take 0.8 s and 80,000 take 11.9 s. It runs on every raw reply in `ledger build` and on every `retry-plan --result`; a large noisy or hostile reply stalls the review pipeline for seconds. Well-formed output takes 10-17 ms. Follow-up: Bound the work: skip starts that fall inside a region already shown not to close, or scan once with a stack that records candidate spans, or cap the scanned length. Add a test with 50,000 `{` under a time budget.
- D-04 (minor, review-logic, src/commands/agent.ts): Delegate and write denial-memory checks are not gated by review-auto and stay sticky. The operatorDenied checks added to the delegate (line 5700) and write (line 5745) branches are not gated by reviewAutoActive(), unlike the shell branch. Denials are recorded only by the wrapper installed under reviewAutoActive(), in a module-global Set that no non-test code resets (resetOperatorDenials has only test callers). Impact: After an operator refuses a write or delegate call in a review-auto run, the same call in a later non-review-auto turn of the same process is refused with REFUSED_EARLIER without the operator being asked, until the process ends. Follow-up: Gate both checks with reviewAutoActive() like the shell branch, or clear the denial set when review-auto ends; add a test that a denial recorded under review-auto does not refuse the call in a later ordinary turn.
- D-05 (minor, review-logic, src/review/ledger.ts): A labelled REVIEW_RESULT block is cut at the first inner triple backtick. The labelled form ends at the first ``` so a JSON string that embeds a fenced snippet (for example a suggested_fix with ```ts ... ```) cuts the block short; the labelled branch then returns undefined with no fallback to the balanced scan. Impact: A valid labelled reply is reported unreadable and the reviewer is retried needlessly. Fail-closed, so the cost is a wasted dispatch; no reviewer skill currently emits the labelled form. Follow-up: When the labelled block fails to parse, fall through to the balanced-brace scan over the text after the label; add a test with an embedded fenced snippet.
- D-06 (minor, review-logic, src/review/retry-plan.ts): A scope-binding failure in planRetry surfaces as an uncaught exception. planRetry throws a plain Error ('Reviewer result is not bound to the current scope ...' and 'Reviewer result belongs to a different reviewer.') but failUnreadable in src/commands/review-slice.ts converts only UnreadableInput and rethrows anything else. Impact: After a rebase or a new commit the CLI prints a stack trace instead of the intended message and exit code 2. No data is corrupted. Follow-up: Throw UnreadableInput (or a dedicated error handled by failUnreadable) for the two binding failures; add a command-level test for the exit code and message.
- D-07 (minor, review-testing-practices, src/commands/review-ledger.test.ts, src/review/ledger.test.ts, src/review/completion-gate.test.ts): Test gaps behind the hardening: runLedger wiring, the lifecycle fixture, the stall side of AC8. review-ledger.test.ts covers only the pure helper assignRawDispatch; the runLedger wiring (content hash taken from the file on disk, retry-state dropped on a fingerprint mismatch, per-driver dispatch counts) has no test. The 'deterministic lifecycle' test does not join planRetry to buildLedger (different fingerprints, state never passed on, attribution hand-set). The AC8 test asserts only the changed-signature side, not that unchanged nested content gives an identical signature and counts as a stall, nor the symlink and unreadable-file branches of dirSignature. Impact: The seam where a hash mismatch silently voids every saved retry state (or accepts a stale one) can regress without a failing test, as can a nondeterministic watchdog signature that would make progress look permanent. Follow-up: Add a tmpdir test of `ledger build` with matching, stale and legacy retry state; build the lifecycle manifest hash from the text planRetry hashes and pass the accepted state on; add an unchanged-twice stall case and a symlink case to completion-gate.test.ts.
- D-08 (minor, review-highload, review-performance, src/review/completion-gate.ts): The completion-gate watchdog hashes the whole review data tree on every gated turn end. dirSignature now reads and SHA-256 hashes every file under .metaproject/data/review (never pruned) and the open package, recursively and fully into memory, on every gated end of turn (up to 20 continues); before it did a readdir plus stat. Impact: I/O and memory grow with the retained review data (about 1.2 MB here, 7.8 MB in the main checkout: tens of ms today); a large log or diff in that directory is loaded whole on each turn end. Follow-up: Fingerprint by size plus mtimeMs (and ino) from stat, or cache digests keyed by (path, size, mtimeMs), or stream and cap the bytes hashed per file.
- D-09 (minor, review-highload, src/commands/review-slice.ts): retry-state.json and the manifest are read-modify-written without a lock (race pre-dates the PR). runRetryPlan reads retry-state.json, plans and rewrites the file from that snapshot; writeFileAtomic prevents torn files, not lost updates. With this PR a stale-snapshot write also resets the other reviewers' entries to {}. Impact: Two retry-plan invocations in parallel (parallel tool calls) can overwrite each other's attempt and covered entries and reopen the retry bound. Confidence 0.45; the race existed before the PR. Follow-up: Serialise the cycle per statePath with a lock file, or re-read and merge immediately before writing a keyed entry; document that retry-plan runs sequentially if no lock is added. Same follow-up as the lock item of F-004 in the PR 940 round (flow 418).
- D-10 (minor, review-clean-code, review-style, src/review/ledger.ts): Stale doc comment on parseReviewResult. The comment still says 'the last fenced block that parses to an object carrying `status`. Never guessed from prose.' The rewritten body prefers a ```REVIEW_RESULT block (malformed gives undefined) and otherwise accepts the last balanced JSON object with a string `status` anywhere in the text, prose included. Impact: Callers reasoning from the comment assume prose is never mined; the real contract is on a safety-relevant parser. (review-clean-code rated it major, rated minor here as documentation only.) Follow-up: Rewrite the comment to state the precedence and drop 'Never guessed from prose'; do it together with D-01.
