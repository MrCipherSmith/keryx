## 01 — границы чтения файлов: предложение к обсуждению

**Проблема.** Некоторые readers проверяют расположение указанного пути, но не фактического файла после разрешения символических ссылок. Файл, выглядящий как часть wiki/skills/artifacts, может указывать за разрешённый root. Это установлено статическим чтением кода; живое security-воспроизведение в аудите не проводилось.

**Предлагаемое поведение.** Каждый reader знает свой разрешённый root и проверяет реальный root и реальный target перед чтением. Ссылки внутри этого root разрешены; выход за него запрещён. Отсутствующие/нечитаемые пути дают понятную ошибку, а не обходной путь или пустой успешный ответ. Общий существующий helper используется последовательно; сам по себе realpath не доказывает защиту от конкурентной подмены файлов.

**Варианты.** (A) Запретить все symlink — просто, но ломает нормальное переиспользование локальных файлов. (B) Разрешить symlink только внутри разрешённого root — рекомендуемый базовый контракт. (C) Добавить явно доверенные внешние roots — полезно для общей библиотеки skills, но требует отдельного пользовательского доверия и жизненного цикла grants. Настройки самого недоверенного репозитория не должны самостоятельно выдавать такой доступ.

**Ответ пользователя.** «Разрешить ссылки внутри разрешённой папки». Выбран вариант B. Доверенные внешние roots в рамках этого решения не добавляются.

**Критерии реализации после согласования.** Обычный файл и внутренняя ссылка читаются; внешняя ссылка отклоняется; разрешённые roots сохраняют свою исходную узкую область; одинаковый результат для MCP wiki/memory/artifacts, harness read_wiki и skill_load. Регрессионные проверки используют только безопасные временные файлы. Ресурсная redaction обсуждается отдельно в пункте 02.

**Решение:** принято — вариант B. Проверять реальное расположение root и конечного файла; цепочка ссылок не должна приводить к чтению за пределами root. **Реализация:** не начата.

## 02 — проверка выходных данных MCP resources: предложение к обсуждению

**Проблема.** Tool output проходит redaction, а MCP resource content возвращается отдельным путём без этой проверки. Даже разрешённый проектный файл может содержать секрет; проверка пути не решает эту задачу.

**Предложение.** Использовать общий контракт проверки выходных данных для tools и resources. При допустимом частичном редактировании заменять чувствительные значения явными маркерами и сообщать, что содержимое изменено. Не превращать структурированные данные в синтаксически некорректные. Если безопасный результат сформировать нельзя, возвращать понятную ошибку вместо исходного содержимого. Ложные срабатывания детектора отдельно разбираются в пункте 15.

**Выбор для обсуждения.** При обнаружении секрета: (A) отдавать безопасную часть с замаскированным значением и отметкой изменения — рекомендуемый баланс полезности и защиты; (B) блокировать выдачу всего ресурса — проще сохранять правило «полный оригинал либо ошибка», но агент теряет весь полезный контекст этого файла.

**Критерии реализации после согласования.** Одинаковая политика на tool/resource путях, отсутствие исходного секрета в ответе и сообщении об ошибке, явное обозначение редактирования; JSON сохраняет валидность либо возвращается ошибка. Проверки используют синтетические значения.

**Решение:** принято — вариант A. Ответ пользователя: «Маскировать секрет и отдавать остальное». Безопасная часть выдаётся с отметкой редактирования; если безопасный корректно сформированный ответ невозможен, возвращается ошибка. **Реализация:** не начата.

## 03 — MCP HTTP: предложение к обсуждению

**Проблема.** MCP HTTP отключён по умолчанию и требует явного запуска. Но после включения конфигурация допускает внешний bind без аутентификации, хотя transport описан как localhost-only. Это отдельный интерфейс от `keryx serve`, у которого уже есть собственные guards.

**Выбор для обсуждения.** (A) На этом этапе жёстко ограничить MCP HTTP loopback-адресами — рекомендуемый небольшой объём исправления текущего заявленного контракта. (B) Поддержать внешний MCP как отдельный явно включаемый режим: аутентификация, защищённый транспорт, правила доступа к tools/resources и проверки клиентского доступа. Default остаётся loopback. Секреты аутентификации не должны передаваться открытым HTTP через недоверенную сеть.

Loopback-only уменьшает сетевую доступность, но сам по себе не доказывает изоляцию от других локальных процессов или браузерных запросов. Host/Origin checks и политика доступных операций требуют отдельной проверки в рамках реализации выбранного режима; redaction и containment из пунктов 01–02 действуют независимо от transport.

**Критерии реализации после согласования.** Для A: non-loopback bind отклоняется до открытия listener; корректно обрабатываются IPv4/IPv6 loopback; help/config docs совпадают с поведением. Для B: внешний bind возможен только с явно настроенной защищённой конфигурацией; отсутствие/неверная аутентификация блокирует tools и resources, а права на операции проверяются общим dispatcher. Отдельно решить доступность mutating tools, включая security.scan.

**Решение:** принято — вариант A. Ответ пользователя: «Только локальный доступ». Разрешены loopback-адреса, внешний bind отклоняется до открытия listener. Удалённый режим не добавляется. **Реализация:** не начата.

## 04 — зависимости: предложение к обсуждению

**Основание.** На момент аудита установленное дерево дало 28 advisories: 1 critical, 13 high, 13 moderate, 1 low. Critical относится к транзитивной dev-зависимости; high есть также в optional MCP tree. Это снимок аудита, не новое измерение и не доказательство достижимости каждого дефекта.

**Предлагаемый объём.** Исправлять обнаруженные риски целевыми обновлениями. Перед изменениями повторить audit и проверить dependency paths, назначение пакетов и достижимость уязвимых API; обновлять прямые зависимости до совместимых исправленных версий, затем транзитивные в lockfile. Не удалять действующую функцию только ради нулевого счётчика и не закреплять несовместимые overrides без проверки. Необязательные/неиспользуемые пакеты рассматривать на удаление после проверки их потребителей.

**Приоритет.** Учитывать одновременно severity, исполняемую поверхность и тип входных данных. Dev-зависимости также проверять: они могут исполняться при разработке/сборке. Optional runtime не считать безопасным только из-за optional-статуса.

**Выбор для обсуждения.** (A) Целевые обновления для найденных advisories с сохранением совместимости — рекомендуется. (B) Общая модернизация всех зависимостей, включая не связанные с advisories major upgrades — отдельный больший объём с риском миграций.

**Критерии реализации после согласования.** Сохранены audit до/после и объяснение каждого оставшегося advisory; пройдены типизация, нужные регрессионные тесты и проверки упаковки/затронутых optional функций. Если исправление требует major migration, отдельно описать несовместимость и предложить решение до такой миграции. Нулевой audit не является доказательством полной безопасности.

**Решение:** принято — полное обновление зависимостей, а не только advisories. «Сделай всё» относилось к пункту 04; последующее уточнение: сейчас не выполнять, фиксировать и идти к следующему вопросу. Major-переходы в будущем проверять последовательно с сохранением функций; ограничения совместимости фиксировать явно. **Реализация:** отложена; ошибочно начатые изменения первой группы отменены, package/lock и установленные версии восстановлены. Подготовительный job сохранён с явной отметкой остановки.

## 05 — достоверный health gate: предложение к обсуждению

**Проблема.** Health может показывать PASS, когда adapter не распознал формат Bun audit и вернул пустой список; required eslint в проверенном запуске также был skipped. Неизвестный результат не равен отсутствию проблем.

**Предлагаемый контракт.** PASS только если выполнены все обязательные проверки, их результаты успешно разобраны и не нарушают согласованных порогов. Если обязательная проверка недоступна, пропущена или её вывод неизвестен, общий результат INCOMPLETE (или эквивалентный статус), с причиной и неуспешным exit code для строгого CI gate. Найденное нарушение порога означает FAIL. Пропуск необязательной проверки даёт явное предупреждение, не ложное заявление о её прохождении.

**Проверяемый объём.** Явно перечислять, какие checks входили в запуск; ограниченный source-filter не позволяет объявлять весь проект проверенным. Набор required/optional задаёт конфигурация проекта, а не наличие исполняемого файла на машине. Сначала корректно разобрать Bun и npm formats, не менять threshold policy зависимостей неявно.

**Выбор для обсуждения.** Рекомендуется строгий контракт выше; альтернатива — считать техническую недоступность обязательной проверки только предупреждением и разрешать общий PASS, сохраняя риск ложной уверенности.

### Согласованное направление: Keryx как самостоятельный инструментальный слой

Пользователь предложил два слоя: скрипты/CLI и модель, которая ими пользуется, затем уточнил обязательный принцип: **«Keryx не должен знать и завязываться на модель»**. Модельный слой находится вне Keryx. Это согласованное архитектурное направление, не разрешение на немедленную миграцию/удаление существующих функций.

Принятая граница:

- Детерминированный слой владеет извлечением/поиском/графом/фрагментами/diff, бюджетами, freshness/provenance и машинными контрактами. CLI и скрипты — интерфейсы к общему сервисному ядру; JSON-ответ содержит результат, источники, состояние полноты и возможности дальнейшего чтения. Для обычных операций модель не обязательна.
- Внешний потребитель (человек, скрипт, coding agent или модель через свой host) выбирает инструменты, раскрывает недостающие фрагменты и интерпретирует результаты. Keryx не выбирает и не вызывает LLM, не владеет provider credentials, model registry или маршрутизацией моделей. Интерпретация внешнего агента не становится автоматически принятым знанием проекта.
- CLI и MCP не должны содержать две реализации одной операции. Существующие модули Keryx и его harness учитывать до введения нового слоя: не создавать второй параллельный движок.

Прежняя рекомендация об опциональном встроенном context agent снята: она противоречит уточнению пользователя. Keryx предоставляет стабильные CLI/структурированные контракты; MCP допустим как адаптер к тому же ядру без привязки к поставщику модели. Сжатие под вопрос реализуется алгоритмически по входным параметрам; LLM-суммаризация, если нужна потребителю, выполняется снаружи. Единицы бюджета и оценки размера должны быть явно описаны и не обещать точный биллинг произвольной модели.

Это направление относится ко всему продукту и влияет на пункты 19/24: существующие provider/model-dependent shell/harness функции требуют отдельного решения о выделении, миграции или прекращении поддержки. Способ перехода ещё не согласован; не удалять функции в рамках текущего обсуждения.

Дополнительный согласованный принцип пользователя: **«keryx должен быть максимально понятным для модели, и быть максимально удобными руками для модели»**. Внешний агент — основной сценарий проектирования интерфейса. Независимость от модели не означает отсутствие удобного агентного контракта: инструменты должны быть обнаруживаемыми, предсказуемыми и самодостаточно объяснять результат, ограничения и дальнейшие доступные действия. Модель планирует и интерпретирует снаружи; Keryx выполняет явно запрошенные операции. Это продуктовый принцип; конкретные изменения интерфейсов рассматриваются в пункте 16 и последующих.

Гарантия распространяется на согласованные пути записи через Keryx; произвольные внешние редакторы не участвуют автоматически в его блокировках, их изменения требуется обнаруживать без обещания полной транзакционной защиты от обходных записей.

Воспроизводимые сценарии: изменённое решение не выдаётся как действующее старое; конфликт источников виден; предложение агента не становится разрешением пользователя; исправление основания помечает зависимые выводы для проверки; параллельные изменения не теряются; передача задачи сохраняет ограничения и результаты; забытые данные не возвращаются из управляемого кэша; сжатие сохраняет обязательную оговорку, а доступные пропуски раскрываются.

Два уровня: детерминированные проверки контрактов внутри проекта и реальные задачи с внешними агентами. Модельная оценка смысла, если используется, показывается отдельно от строгих проверок. Сравнивать с простым поиском и работой без памяти, измерять правильность, время и повторные обращения. Каждый обнаруженный сбой пополняет регрессионный набор и становится основанием улучшения Keryx.

**Критерии будущей реализации.** Для сценариев заданы исходные состояния и ожидаемые результаты; повторный прогон обнаруживает возврат исправленного дефекта. Отчёт разделяет строгие проверки и внешние оценки, сохраняет условия сравнения и ошибки. Вызов/выбор модели не переносится в ядро Keryx.

**Статус:** решение принято; реализация не начата. Далее обсуждается последний пункт 32.

## 32 — скриптовая композиция операций: согласованное решение

**Решение пользователя:** «да» на тонкий SDK и пакетный интерфейс поверх общего ядра.

Скрипт объединяет операции, фильтрует результаты и выбирает нужные поля до передачи модели. Большие промежуточные результаты доступны по идентификатору с версией, областью доступа и сроком жизни. Независимые шаги могут выполняться параллельно, зависимые — последовательно. Ошибки и частичное выполнение видны по каждому шагу. Пакетирование сохраняет обычные проверки прав и версий; связанные записи используют механизм пункта 27. CLI, MCP и SDK вызывают одну реализацию операций.

Скрипт выполняется обычным внешним процессом или средой агента. Keryx предоставляет инструменты и контракты без зависимости от модели. Начать с композиции чтения и поиска, затем расширить на изменение данных с согласованными гарантиями. Пользу проверять по полной стоимости и успешности задач.

**Критерии будущей реализации.** Составной сценарий даёт сопоставимый результат с последовательными операциями, не требуя загрузки промежуточных данных в контекст модели. Недействительные/просроченные идентификаторы дают понятную ошибку; действуют проверки доступа и версии. Частичный результат отличается от полного успеха; обычный batch не обещает транзакционность произвольных шагов, а связанные изменения записей соблюдают пункт 27. Отчёт об испытаниях показывает полную стоимость и качество результата.

**Статус:** решение принято; реализация не начата. Все пункты 01–32 обсуждены и согласованы.

При resume валидировать run/task/arm identity, manifest и уникальность пары, не усреднять дубли и orphan; фиксация пары должна переживать crash между записями. **Готово:** guards воспроизводимо ловят каждую нарушенную предпосылку до дорогостоящего запуска; пустой/битый граф отклоняется, crash → resume → второй resume не меняет вес задач.
- [ ] **M08. Следующий протокол оценки зафиксировать до запуска.** Сохранить отрицательный результат исходного +10 п.п. критерия. Новый протокол дополнительно проверяет «не хуже по качеству при меньшей полной стоимости» с заранее выбранной границей допустимого ухудшения; не переименовывать старый FAIL в успех. Отдельные метрики recall/precision/F1, длина списка кандидатов, выполненная задача/patch checks, latency, P50/P95 стоимости и распределение выигрышей/проигрышей.
