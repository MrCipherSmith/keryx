## 2. Что и как измеряли

Задача — по subject и первому абзацу PR назвать production-файлы, изменённые этим PR. Gold получен из diff. Это поиск файлов, а не выполнение задачи или проверка правильности патча.

Каждая пара запускалась на исходном parent commit: один arm с project context, второй без него и без управляемых Keryx hooks. Один и тот же внешний агент и модель внутри пары; сторонние MCP отключены. Модели в отчётах различаются между задачами по заранее заданному порогу размера gold. Это не сравнение разных моделей между собой; модель и сложность коррелируют.

Порог успеха был зафиксирован до scored runs: минимум +10 процентных пунктов recall при не большей стоимости контекста. Контекст определён как сумма input + cache creation + cache read. Это накопленный по вызовам объём входа, не уникальные токены и не денежные расходы.

Испытания не включали SAC, orient или субагентов. Данные появились до оптимизации короткого gate; они не являются проверкой её эффективности.

## 4. Что нельзя переносить из отчётов без оговорок

1. **21 дорогая задача — не 21 задача без выигрыша.** Усиленная формулировка improvements ошибочна: без прироста recall 18, остальные 3 улучшили recall дорогой ценой.
2. **Порог не является тестом статистической значимости.** Невыполнение +10 п.п. не доказывает эквивалентность или отсутствие эффекта. «Ноль побед не может быть случайностью» тоже не следует из 13 пар; отдельно учитывать потолок recall и выборку.
3. **Не удалять 17 двойных нулей ради улучшения метрики.** Они остаются в primary result. Для нового опыта можно заранее определить независимые страты и дополнительный анализ, но не отбирать удобные задачи по результату сравниваемых arms.
4. **Наличие страниц не доказывает пользу wiki.** Основной arm имел только boilerplate. Второй содержит страницы, но эксперимент не изолирует wiki от routing/graph и не доказывает, какие знания агент получил и применил.
5. **Нет автоматической причинной атрибуции token gap.** Равное число tool calls не означает равное число model turns; пакетные вызовы, история, compaction и cache влияют на итог. Арифметика «~25 calls × размер gate объясняют половину gap» — гипотеза, не измеренное разложение.
6. **Прочитанный prefix и денежная цена различаются.** Повторное присутствие текста увеличивает накопленные context tokens, но cache и режим оплаты меняют деньги; runtime может сокращать историю. Уменьшать prefix полезно как гипотеза, его точный эффект проверяется реальными traces.
7. **Путь description → files не отсутствует полностью.** `src/gdgraph/find.ts:32–108` уже реализует lexical seed search по путям и символам. Его ограничения и композицию с wiki/affected надо улучшать, а не дублировать.
8. **Не приписывать README отсутствующие слова.** На текущем main строки 128–129 показывают структурный affected-пример; точной фразы «beats grep» нет. Нужен аудит фактических сравнительных обещаний, а не буквальный перенос пересказа исследователя.
9. **Git-изоляция не равна полному sandbox.** Отсутствие answer commit/remotes закрывает конкретный канал утечки, но само по себе не доказывает отсутствие доступа к соседним каталогам/сети через все tools. Границы окружения должны быть записаны и проверены.
10. Внешние статьи, упомянутые в improvements, здесь заново не проверялись; они не используются как независимое доказательство выводов. Основание дополнений — данные ветки, существующий код и уже принятые требования.

## 5. Какие идеи дают практическое улучшение wiki

Подтверждённая точка роста: `src/wiki/ask.ts:325–333` формирует кандидатов только из title/summary. Даже готовый подробный ответ внутри страницы может отсутствовать в поисковой выдаче. Это подкрепляет ранее согласованный пункт 07.

**Поиск внутри секций.** Индекс основного текста с устойчивыми адресами секций, точными терминами, доменными алиасами и поддержкой языка вопроса. Выдавать совпавшее объяснение, а не только общий summary страницы. Начать с детерминированного полнотекстового baseline.

**Понимание сценариев.** Вики должна добавлять то, чего нет в списке импортов: последовательность операции, правила и исключения, причины решений, ошибки и точки безопасного изменения. Генерируемые Reference-блоки полезны как опора, но количество страниц/символов не измеряет качество объяснения. Содержимое пишет внешний агент/человек; ядро остаётся независимым от модели.

**Связь смысла с кодом.** Явные проверяемые ссылки секция → файл/символ/тест/решение и обратное влияние изменения кода на объяснение. Сначала найти правило, затем получить ограниченный набор точек изменения. Граф не делает семантический вывод вместо модели.

**Компактный ответ с основаниями.** Фрагмент + версия + источник + freshness + ограничения + адрес продолжения. Сохранять исключения, различать draft/stale/conflict/no-answer. Не грузить всю вики для простого вопроса и не превращать неизвестность в уверенный ответ.

**Обновление по основаниям.** Изменение исходника помечает связанные объяснения для проверки, управляемый Reference обновляется отдельно, авторские решения сохраняются. Предложения применяются с атомарным expectedVersion; уже принятое решение не переутверждается человеком без причины.

**Отдельное доказательство пользы.** Испытания graph/wiki по отдельности и вместе на одинаковых snapshots, содержательная wiki против boilerplate, вопросы о причинах и правилах, корректность патча, handoff, конфликты и устаревание. Измерять правильность и cost of maintenance, а не только file recall. Детальные задачи и критерии W01–W06 внесены в план.

## 6. Инженерные уроки из harness

Полезны зафиксированные поправки: реальная абляция вместо удаления не тех файлов; построение graph из parent; inventory до/после; unreachable answer commit; симметричный набор tools; исключение тестов по правилам языка; корректный учёт cache tokens и первого обнаружения gold в output; изоляция от памяти оператора; сохранение/возобновление пар.

В этих механизмах обнаружены и оставшиеся дефекты: inventory признаёт существующую директорию graph доказательством базы; resume может сохранить orphan, затем повторную пару и при следующем запуске усреднить дубли. В опубликованных 126 записях эти искажения не обнаружены; это ограничения runner для будущего переиспользования, а не основание объявить текущие агрегаты неверными.

Переиспользовать следует исправленные guards, чистые контракты и воспроизводимость. Private dataset, комментарии и пути не переносятся автоматически в публичный проект. Новая цель «качество не хуже при меньшей стоимости» требует отдельной preregistration, не меняет задним числом исходный FAIL.

Ранее известные дефекты main включены в план явно: rules lifecycle отменяет compact gate; потребители всё ещё ожидают полное содержимое index. Отдельно выделены независимые fixes scripts, откатившиеся вместе с исследованием: tool cap, отсутствующий resolver в stress report, optional port, охват typecheck. Подробная проверка — в отчёте методики.
