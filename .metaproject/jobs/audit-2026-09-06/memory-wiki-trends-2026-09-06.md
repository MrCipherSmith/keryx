# Память, wiki и внешние агенты: исследование для Keryx
Дата среза: 2026-09-06. Статус: предложения к обсуждению, не согласованная реализация.

## Вывод и границы
Перспективное направление для Keryx — проверяемая память проекта: происхождение знаний, область их применения, связи с кодом и последствия исправлений. Модель интерпретирует сведения и предлагает изменения снаружи; Keryx предоставляет детерминированные CLI/скрипты/сервисное ядро и MCP-адаптер. Встраивать модель, выбирать провайдера или требовать embedding runtime для базовой работы не предлагается.

Исследование основано на первичных публикациях и документации. Свежие препринты служат источниками проверяемых гипотез, а не доказательством эффективности на Keryx. Синтетические задачи, авторские оценки и vendor-примеры явно отделены от результата на нашем проекте. Внешнему субагенту gpt-5.6-sol поручен ограниченный обзор новых memory-бенчмарков; предложения сопоставлены с уже прочитанным кодом.

Дополнительный практический пример: [Basic Memory Note Format](https://github.com/basicmachines-co/basic-memory/blob/main/NOTE-FORMAT.md), текущая документация на дату среза, использует Markdown как исходные данные, связи и устойчивые permalink. Это поддерживает простую переносимую основу; отдельная графовая СУБД из этого не следует.

## Что уже есть в Keryx
По чтению src/memory/types.ts и manifest памяти уже существуют MemoryClass, статусы, confidence, scopes, provenance, временные поля validFrom/validTo/recordedAt, supersedes-связи и поиск на дату. Повторно предлагать «добавить типы памяти/время/замену решений» неправильно.

В src/sac уже присутствуют proposals, revisions, workspace-границы, catchup и receipts. Новые предложения должны расширять и согласовывать эти механизмы, а не создавать второй движок управления памятью. Проверка была целевой, не повторным полным аудитом всех путей доступа/записи.

Пункты 06–08 и 14–16 уже покрывают lifecycle, поиск, обновление wiki, сжатие и удобный интерфейс. Ниже перечислено дополнительное поведение.

## Новые кандидаты в план
Все чекбоксы ниже не согласованы. Нумерация продолжает основной план.

### 25. Происхождение и полномочия каждого утверждения — приоритет P1
- [ ] Стабильный ID утверждения; автор/источник, revision/hash и точный фрагмент доказательства; различие наблюдения, гипотезы, принятого решения и инструкции.
- [ ] Полномочия задаются доверенным вызывающим контекстом и явными правилами, а не объявлением модели или текста wiki. Память сама не выдаёт разрешение на действие.
- [ ] Единые проверки области доступа для поиска, прямого чтения, export и context pack, до ранжирования.

Пример из этой задачи: «согласовали полное обновление зависимостей» и «реализация сейчас отложена» должны сохраняться вместе. Решение о будущем изменении не является разрешением выполнить его сейчас.

Критерий: после сжатия и передачи другому агенту предложение остаётся предложением; ссылка ведёт к той версии источника, которая подтверждала запись. Валидность ссылки не доказывает истинность интерпретации. Основание: AuthMem-Bench и GroupMemBench; продуктовая адаптация — наша.

### 26. Граф оснований и каскадная актуальность — P1
- [ ] Типизированные связи «основано на», «подтверждается тестом», «описывает символ», «заменяет», «противоречит» между memory/wiki/code/test.
- [ ] Изменение источника выдаёт список затронутых утверждений и страниц; производное знание помечается требующим проверки.
- [ ] Учитываются альтернативные основания: исчезновение одного источника не означает автоматическую ложность вывода.

Это дополняет freshness отдельных страниц и supersession записей. Начать с явных связей и пересобираемого индекса над Markdown. Смысловые связи предлагает внешний агент; Keryx проверяет их структуру и наличие целей. По изменениям текста нельзя автоматически доказать смысловой конфликт.

Критерий: исправление A показывает зависимые B/C и основание каждого перехода, сохраняя историю; повторный пересчёт идемпотентен. Основание: RECON; адаптация — наша.

### 27. Проверяемые изменения wiki через предложения — P1
- [ ] Внешний агент представляет пакет изменений wiki/memory с источниками и ожидаемой базовой revision.
- [ ] Keryx показывает diff, проверяет ссылки/схемы/статусы и применяет согласованный пакет с защитой от конкурентной перезаписи.
- [ ] Неоднозначные изменения формируют явный conflict set; частично применённый пакет не выглядит успешным.

Переиспользовать SAC proposals/revisions. Человеческое подтверждение определяется действующей политикой и разрешением задачи, а не запрашивается автоматически при каждом изменении. Извлечение смысла и написание prose остаются снаружи.

Критерий: два агента меняют одну базовую версию; второй получает конфликт вместо молчаливой потери первого изменения. Основание: LLM Wiki как направление; конкретный транзакционный контракт — наше инженерное предложение.

### 28. Переносимый пакет продолжения задачи — P1
- [ ] Компактный экспорт цели, ограничений, принятых решений, разрешённых действий, проверенных результатов, открытых вопросов и источников.
- [ ] Snapshot/worktree/task scope и точные ссылки для дополнительного чтения; изменения относительно известного пакета.
- [ ] Локальные заметки агента становятся общими знаниями только через явное принятие в нужную область.

Переиспользовать SAC catchup/receipts и существующее состояние задач. Пакет не требует чата целиком или знания модели. Для текущей беседы он сохраняет «01–16 согласованы; код не выполнять; 17–24 ожидают обсуждения».

Критерий: другой внешний агент продолжает работу без повторного интервью и не расширяет разрешённый объём действий. Основание: context engineering и multiparty/governance benchmarks; конкретный формат — наша гипотеза.

### 29. Управляемое забывание производных данных — P2
- [ ] Отличать архивирование, замену устаревшего знания и удаление чувствительного содержимого.
- [ ] Preview перечисляет затронутые записи, summaries, wiki fragments, индексы, кэши и сохранённые context packs под управлением Keryx.
- [ ] После удаления проверять остатки и предотвращать восстановление записи из старых управляемых производных данных.

Журнал сохраняет непрозрачные ID и факт удаления, а не само удаляемое содержимое. Переписывание Git-истории не включается автоматически. Честно перечислять границы проверки: внешние копии, чужие backups и память уже завершённых внешних агентов не контролируются Keryx.

Критерий: удалённое синтетическое значение отсутствует во всех перечисленных управляемых слоях; непроверенные места перечислены. Основание: Deployment-Time Memorization и GateMem.

### 30. Манифест потерь контекста — P2
- [ ] Context pack перечисляет включённые/опущенные record IDs или диапазоны, причины усечения и доступные handles продолжения.
- [ ] Отдельные метрики повторного чтения и восстановления потерянных данных.
- [ ] История чтения изолируется по потребителю; отчёт записывается явно, чистый поиск не становится скрытой записью.

Дополнение к пункту 14: машинно-проверяемый учёт потерь и восстановления, а не только пометка «truncated». Детальность манифеста также ограничивается бюджетом.

Критерий: можно понять, какой источник агенту не был показан, и измерить полную стоимость последующих чтений. Основание: Context Compression Cost.

### 31. Регрессионный набор для памяти и wiki — P1, начать до усложнения поиска
- [ ] Фикстуры: исправленное решение, конфликт источников, другой автор/область, старый worktree, передача задачи, удаление, потерянная при сжатии оговорка.
- [ ] Сравнение без памяти, с простым полнотекстовым поиском, текущим Keryx и каждым новым слоем отдельно.
- [ ] Метрики: правильность результата, stale reuse, происхождение/полномочия, утечки между областями, остатки удаления, качество продолжения, время, токены и повторные обращения.

Keryx хранит данные, ожидаемые структурированные результаты и traces. Внешние агенты запускаются внешним harness. Там, где нужен смысловой judge, результат маркируется отдельно от детерминированных проверок. До испытания заранее определить критерии, при которых усложнение отклоняется.

Это конкретизация пункта 23 для памяти/wiki. Основание: WiCER, GroupMemBench, GateMem, RECON и исследования стоимости контекста.

### 32. Скриптовая композиция с адресуемыми результатами — P2, после измерения накладных расходов
- [ ] Тонкий SDK или декларативный batch поверх общего ядра; фильтрация, объединение и выбор полей до возврата модели.
- [ ] Крупные промежуточные результаты доступны по scoped handle с revision, сроком жизни и правилами доступа.
- [ ] Сценарии запускаются обычными скриптами или внешним agent host; собственный универсальный sandbox/LLM runtime не требуется.

Дополнение к пункту 16: передачу больших результатов между операциями можно выполнить без промежуточной загрузки в контекст модели. Handles должны становиться явно недействительными при удалении/смене доступов.

Критерий: составной запрос даёт сопоставимый результат с последовательными операциями при меньшем контексте и без скрытых мутаций. Основание: Anthropic MCP и Cloudflare Code Mode; конкретная минимальная форма для Keryx — наше предложение.

## Рекомендуемый порядок обсуждения
25 → 26 → 31 → 28 → 27. Остальные — после проверки основных сценариев. Наибольшая ожидаемая ценность: доверие к решениям, видимые последствия изменений и подтверждённая польза памяти. Это приоритеты гипотез, не оценённая дорожная карта реализации.

Не включать по умолчанию: автоматическое принятие выводов модели, обязательные embeddings/GraphRAG, обязательное чтение всей wiki перед любой задачей, собственный LLM runtime. Решение об усложнении принимать по измеренным пробелам простого baseline.
