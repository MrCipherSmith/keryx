Дата аудита: 2026-09-06, Asia/Muscat. Исходники: `main@d0a2a011df93c2459cb4329a7dc152fb0fe625a6`, v0.2.80. Автор: основной агент. Измерения исходных функций выполнены через Bun; CLI-проверки — глобальная v0.2.80. Артефакты: [воспроизводимый probe](utility-probe.ts), [его результаты](utility-results.json), [пересчёт исторического эксперимента](benchmark-recomputed.json).

## Вывод

**Граф приносит конкретную структурную информацию, которую один текстовый поиск не даёт. Однако общий выигрыш обязательного процесса Keryx в поиске нужных файлов не подтверждён: доступное парное исследование показывает больше контекста без улучшения recall. Wiki как читаемая документация полезна; её текущий поисковый интерфейс существенно слабее содержания самих страниц.**

Не следует смешивать три утверждения: инструмент работает; инструмент иногда экономит шаги; весь процесс улучшает итоговый патч при меньшей полной стоимости. Первое подтверждено для многих компонентов, второе — для отдельных сценариев, третье этим аудитом не установлено.

Импортный граф также не доказывает реальное выполнение, динамические зависимости и бизнес-влияние.

## 3. Дефекты и ограничения практической пользы

### U-01 — major: поиск wiki обходит жизненный цикл памяти

`src/wiki/ask.ts:336–357`: фильтрация проверяет только `supersededBy` и истёкший `validTo`, но не `status` и не будущий `validFrom`. Временный пример вернул все шесть записей: accepted, draft, deprecated, conflict, superseded без ссылки на замену и accepted с `ValidFrom: 2099-01-01`. Статусы в выдаче не показаны. Для wiki `wikiCandidates` также берёт все страницы без отделения draft.

Последствие: агент получает неподтверждённое или уже отменённое знание в ответе «Based on the project's own wiki and memory», хотя accepted/current — заявленная граница влияния памяти. Это нарушение целостности контекста, не доказанный удалённый взлом. Class scope: `wikiCandidates`, `memoryCandidates`, `isCurrent`, `assembleAnswer` в одном модуле; перечисление получено поиском `status|validFrom|function wikiCandidates|function memoryCandidates` и чтением функций.

Исправление: общий фильтр актуальности/допуска с memory search; accepted/current по умолчанию; draft/conflict только явно и с маркировкой. Проверить CLI, MCP и встроенный wiki tool через единый сервис.

### U-02 — major: текст wiki вне Summary недоступен для поиска

`src/wiki/ask.ts:325–332` формирует searchable text только из title и summary; `src/wiki/collect.ts:41–62` не отдаёт основной текст страницы. Probe помещает уникальный термин в Details принятой страницы: `wikiAsk` возвращает 0 цитат, хотя информация существует.

Последствие: расширение документации не улучшает поиск, если важные сведения не попали в краткое описание. В рабочей wiki вопрос об HTTP-аутентификации вернул SAC demo, metrics и lesson о source guards. Точные слова `OS sandbox Seatbelt bubblewrap network` и `permission modes ask trust auto` находят нужную страницу первой.

Исправление: поиск по разделам с заголовками, исходными путями и ограниченными excerpt; первоначально достаточно BM25/лексического поиска по полному тексту. Embeddings не обязательны для исправления этого дефекта. Class scope: candidate construction для wiki и memory плюс `WikiPage`/collector; проверено чтением указанных функций.

### U-03 — minor: слабый отказ от нерелевантного ответа

`src/wiki/ask.ts:134–145` принимает любое округлённое Jaccard-пересечение больше нуля. Запрос о несуществующем `quuxneverexistingzz how does it work?` получает три обычные цитаты. Это не генерация выдуманных фактов, но нерелевантная выдача под видом ответа. Нужны обработка стоп-слов, оценка покрытия значимых терминов и явный ответ «достаточного контекста нет».

### U-04 — major для задачи change context: repomap тратит бюджет на нулевую релевантность

`src/gdgraph/repomap.ts:53–66, 118–151` использует направленные import edges, затем заполняет бюджет всеми ранжированными узлами. `src/gdgraph/pagerank.ts:126–129` сортирует нулевые оценки по пути.

При seed `src/lib/serve-credential.ts` и budget 1500: **151 файл, из них 148 с score=0**, около 1493 оценочных токенов; потребитель `serve-server.ts` не вошёл. После seed и двух зависимостей идут алфавитные fixtures/scripts. Это воспроизведено вызовом исходного `computeRepomap`, не только оценкой текста.

Исправление: убрать нулевые результаты, явный режим dependency/impact/balanced, добавить обратные связи для change context; отдельный бюджет для производственного кода и тестов. Class scope: `buildRankEdges`, `computeRepomap`, `personalizedPageRank`; исходный PageRank корректен для своей направленной модели, дефект — в полезности результирующего контекста и отсутствии отсечения.

### U-05 — minor: неизвестная цель выглядит как нулевой blast radius

`src/gdgraph/target.ts:28–57` возвращает нормализованную строку, когда узел не найден; `computeAffected` формирует пустые множества. Несуществующий путь даёт exit 0 и пустые dependencies/dependents. Нужны `target-not-indexed` и состояние полноты графа, чтобы отличать «никто не зависит» от «мы этого не знаем».

### U-06 — архитектурное ограничение: свежесть зависит от дисциплины оператора

`src/ctx/orient.ts:106–131` проверяет `git diff --name-only HEAD`: не видит уже закоммиченные изменения после прошлого build, не включает untracked и считает ошибку Git пустым результатом. «working tree clean» не означает «индекс соответствует HEAD». Это честно описано в manifest, но интерфейс легко интерпретировать шире. Нужны build commit/fingerprint и статус `fresh/stale/unknown` в самих ответах.

Свежесть wiki в этом аудите: 50 страниц, 34 fresh, 12 affected; отчёт имеет ограничения symbol-layer-unavailable и unresolved edges. Эти числа не гарантируют фактическую корректность прозы. Поиск `wiki ask` не выводит предупреждения свежести найденных страниц.

## 4. Накладные расходы

`gdctx` действительно сокращает длинный вывод и сохраняет raw для проверки: пример git fast-forward — 207829 байт → 6179 байт (97% меньше). Но сжатие не равно полезному выигрышу: outline JSON-схемы и Markdown-skill вернул «none» вместо значимых контрактов, из-за чего потребовалось дополнительное чтение. Короткая команда Git не нуждается в прохождении всей цепочки skills/wiki/graph.

Обнаружен побочный эффект redaction: дробь recall с 16 знаками после запятой (около `0.803114`) классифицируется как credit card и превращается в `0.[REDACTED:cc]`; GitHub Actions numeric IDs маскируются как phone. Это не настоящие PII. Для машинного JSON такой вывод уже невалиден. Нужны структурно-aware redaction и корпус безопасных метрик/идентификаторов.

Полный локальный job-orchestrator skill занимает около **95 KB и 2191 строки**; один его outline не несёт содержания. Если агент обязан читать этот документ и несколько каталогов ради небольшой задачи, предполагаемая экономия поиска может быть полностью съедена стартовыми инструкциями. Это объяснение формы результата A/B, а не измеренная причинность: для причинности нужны отдельные абляции routing/graph/wiki.

## 5. Как проверить улучшение следующей версии

1. Сначала устранить U-01/U-02/U-04: оптимизировать полезность существующего контекста.
2. Один короткий вход: compact graph + подходящие wiki sections + их freshness, без обязательного чтения всех каталогов на каждый запрос. Простые Git-вопросы обслуживать напрямую.
3. Сравнить одинаковые задачи в пяти вариантах: обычный поиск; только graph; только wiki; graph+wiki; полный Keryx. Одинаковая модель, лимит и инструменты, независимые процессы.
4. Минимум 50 пар на нескольких чужих репозиториях; несколько повторов; заранее фиксировать выбор задач. Отдельно считать уже существующие файлы и новые файлы, которых ещё нет в parent commit.
5. Кроме recall/precision: успех патча по независимым тестам, число регрессий, latency, совокупные billed/cached tokens, human correction time, стоимость подготовки и поддержки wiki. Набор метрик — предлагаемый эксперимент, не текущая телеметрия.
6. Сохранить отрицательные результаты. Уменьшение количества tool calls само по себе не является победой, если каждый вызов приносит больше ненужного текста.
