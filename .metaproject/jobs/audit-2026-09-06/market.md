# Рыночная актуальность и позиционирование Keryx

Проверено 2026-09-06. Основной агент. Это анализ возможностей и сигналов распространения по первичным источникам, не исследование готовности клиентов платить. Конкуренты не устанавливались и не проходили одинаковый практический benchmark.

## Вывод

Задача актуальна: coding agents нуждаются в точном контексте репозитория, истории решений и проверяемых границах действий. Но **graph, wiki, memory и MCP по отдельности уже не являются уникальным преимуществом**. Наиболее убедительное направление Keryx — переносимый, проверяемый в Git контекст для команды с несколькими агентами, связанный с тестами и результатами проверок. Главный барьер сегодня — доказать, что эта связка полезнее и дешевле обычного поиска с коротким AGENTS.md.

## Альтернативы

| Альтернатива | Подтверждённые возможности | Что это означает для Keryx |
|---|---|---|
| Обычный Codex / Claude Code / Cursor + инструкции проекта | Codex читает AGENTS.md; Claude поддерживает CLAUDE.md, rules и auto memory; Cursor поддерживает правила проекта и команды | Бесплатный по сложности внедрения baseline уже даёт устойчивые инструкции. Keryx должен доказывать дополнительный эффект, а не сравниваться с агентом вообще без контекста |
| Aider | Repo map с символами/сигнатурами, графовое ранжирование и token budget | Repo map и PageRank давно доступны. Нужны лучшая точность, свежесть и связь с решениями/проверками, а не сам факт наличия графа |
| Serena | MCP-инструменты символического поиска и редактирования на основе LSP либо JetBrains | Сильный конкурент именно по точному символическому контексту. Опциональный и отсутствующий по умолчанию symbol layer Keryx — заметное ограничение в этой нише |
| GitNexus | Graph/MCP, imports/calls/heritage, процессы, hybrid search, wiki, несколько языков, интеграции с агентами | Самый близкий конкурент по сочетанию graph + wiki + agent integration. Нельзя позиционировать эту комбинацию как свободную нишу |
| DeepWiki / Devin | Документация с диаграммами и ссылками на код, вопросы по репозиторию, публичный MCP; частные репозитории через Devin | Пользователь может получить понятную wiki и Q&A без поддержки большой системы правил. Keryx выгодно отличать локальное владение знаниями и их версионирование, а не только генерацию страниц |
| Sourcegraph Cody | Enterprise-контекст через поиск локальных/удалённых codebases и code graph | Для крупных организаций уже есть решения поиска по нескольким репозиториям. Keryx может выигрывать простотой локального внедрения, но это нужно измерять |

## Реальные сильные стороны продукта

1. **Контекст принадлежит репозиторию.** Markdown/JSON можно переносить, обсуждать в diff и читать без конкретного поставщика модели. Это проверяется локальной структурой `.metaproject/`, а не только рекламой.
2. **Детерминированный слой работает без model API.** Init, файловый граф, lexical retrieval, нормализация проверок и состояния доступны локально. Временный onboarding подтверждён функциональным аудитом.
3. **Связь знаний с инженерным процессом.** Кандидаты тестов, memory lifecycle, provenance и управляемые этапы работы потенциально полезнее отдельного «чата с кодом». Полезность зависит от устранения найденных нарушений свежести и фильтрации.
4. **Честное описание ограничений.** README и limitations раскрывают отсутствие noninteractive tools, remote approvals, grammar assets и живого подтверждения external agents. Это уменьшает риск неверных ожиданий, хотя формулировки нужно держать согласованными.
5. **Большой объём работающих регрессионных проверок.** Тесты и типизация зелёные в текущем checkout; есть отдельные CI-проверки native TUI и sandbox. Это сильная инженерная база, но не замена пользовательскому benchmark.

## Слабые стороны и угрозы

- **Стоимость обязательной маршрутизации.** Известный A/B на 13 задачах не показал улучшения поиска, а совокупные входные токены выросли на 32,49%. См. [пересчёт и ограничения](utility.md). Продаваемое обещание «меньше повторного изучения» пока не подтверждено для полного процесса.
- **Размытая продуктовая граница.** Context platform, свой runtime, TUI, child agents, sandbox, remote entry и workflow engine требуют очень разных компетенций. Они расширяют поддержку быстрее, чем укрепляют доказанный основной сценарий.
- **Неравномерная надёжность интеграций.** Файловый граф работает сразу; точные символы требуют дополнительных assets. Noninteractive harness имеет существенные ограничения. Пользователь должен понимать разницу до установки.
- **Контекст способен навредить.** Устаревшая wiki и memory без lifecycle-фильтра способны закреплять неверные решения и создавать уверенность в неактуальных данных. Для продукта про «общий мозг проекта» это центральный, а не периферийный дефект.
- **Простые альтернативы улучшаются.** Claude уже имеет автоматическую память и собственные subagents, Aider — ограниченный по токенам repo map, Serena — LSP, GitNexus — graph/wiki/MCP. Поэтому узкая измеримая специализация важнее списка функций.

## Сигналы распространения

GitHub API во время аудита вернул для Keryx: **0 stars, 0 forks**, repository создан 2026-07-06; последний push 2026-09-05. Это снимок счётчиков, не оценка качества и не число пользователей. Источник: [репозиторий Keryx](https://github.com/MrCipherSmith/keryx); точные поля получены командой `gh api repos/MrCipherSmith/keryx`.

Публичный npm downloads API вернул **9560 загрузок за 2026-07-31 — 2026-08-29**. Хотя запрашивался last-month, в отчёте сохраняется фактически возвращённый период, не выдумывается более свежий. Загрузки включают возможные CI/повторные установки и не равны активным людям или командам. Источник: [npm downloads API](https://api.npmjs.org/downloads/point/last-month/%40mrciphersmith%2Fkeryx).

Локальная история коммитов существенно сосредоточена на одной авторской идентичности: 1030 из 1139 коммитов; ещё 98 записаны тестовыми идентичностями. Это сигнал концентрации поддержки, не точный bus factor: несколько идентичностей могут принадлежать одному человеку, авторство коммитов не равно авторству решений.

В изученных источниках нет данных об удержании команд, DAU/WAU, paying users и времени до первого полезного результата. **Product-market fit не установлен.** Нельзя выводить его ни из числа функций, ни из числа загрузок.

## Для кого проверять ценность

Предлагаемый первый сегмент: команда с несколькими coding agents, повторными задачами в среднем или большом репозитории и требованиями хранить контекст локально. Конкретный job-to-be-done: «перед изменением за один запрос получить затронутые модули, актуальное объяснение и нужные тесты с указанием источников и полноты».

Менее убедительный первый сегмент: маленький pet-проект одного разработчика, где короткий README/AGENTS.md и поиск уже решают задачу. Также преждевременно обещать универсальную автономную платформу, пока noninteractive/runtime и external-agent пути ограничены.

Это гипотезы позиционирования. Проверка: 5–10 внешних команд, несколько репозиториев, одинаковые задачи с Keryx и baseline, замер успешных исправлений и полной стоимости. Числа — предлагаемый размер пилота, не найденная пользовательская база.

## Приоритет продуктовых инвестиций

1. Сделать graph/wiki/testing evidence актуальными и согласованными; использовать короткий единый query surface.
2. Доказать эффект в слепом сравнении и опубликовать отрицательные результаты наряду с положительными.
3. Упростить установку и первую полезную задачу; показывать, какие capability работают, какие отсутствуют и сколько стоит обновить знания.
4. Развивать интеграцию с существующими агентами как основной вход; собственный runtime оставить опциональным и оценивать отдельно.
5. Рассматривать командные функции/сервис сопровождения как возможную будущую монетизацию после подтверждения спроса; текущих данных недостаточно для прогноза выручки или назначения цены.
