## What in slice-02 reaches a rendered box

Most of slice-02 is backend code: publication logic, executor and service wiring, head-move policy, prior-round trust, the round registry and update-round selection. It has no rendered sizing and no geometry in this lane's scope. Three items do reach Desktop-rendered text. I checked each one statically:

1. The as-is body's first line (`headMovedLine`, desk-publication.ts) starts the draft `body` and renders in the dialog through `<Preview text={draft.body} />` (ReviewPublishDialog.tsx:250). The line holds two 40-character SHAs inside code spans. Each SHA is an unbreakable run of about 40ch of monospace. `.review-publish-markdown` (ReviewDetail.css:134) sets `overflow-wrap: anywhere` and `overflow: auto`, so the run can break inside the box. Even unbroken, it would scroll within the preview box rather than widen the dialog. No overflow of the dialog is expected. Not filed.
2. The new `blockedReason` strings are "Round N of this review is newer. Publish from that round. You can still save this draft locally." and "Enable General comment. Inline comments are not available when publishing for an earlier commit." Both render as a `p.review-detail-muted[role=status]` (ReviewPublishDialog.tsx:268). They are ordinary prose with no unbreakable runs, so they wrap. Not filed.
3. ReviewPanel.dom.test.tsx adds "the primary footer action follows the dialog state, and the head-moved alternatives sit together". It asserts the DOM order of the footer buttons and which one is primary. That locks in the source order behind wave 1's static resolution of round 2's LY-001. As SKILL.md's red-flags table says, a test on a DOM stub loads no CSS, so it cannot detect a button wrapping onto a second row. This is a known limitation, not a defect. Wave 1 already proposed a real-CSS probe as a follow-up, so it is not repeated here.

The docs change (desktop-app.md) is prose only and has no layout surface.
