### TM-04 re-check (prior-round.ts header): can data a PR commits narrow a round?
No. Checked path by path:
1. **Partial-round vouch (`partialRoundVouch`, packageTrust lines 335-340, localPackageCandidates 429).** A draft package is admitted only when a `desk-partial` entry in the machine-local registry matches its package id, manifest identity hash, findings.json hash (required non-null) and round.json hash. A PR can only meet that by committing byte-identical content to what Desktop recorded from the user's own run store, which yields the same reviewed head and findings as the genuine round: no gain.
2. **The weak backstop holds for every partial previous round.** `weakReasons` always adds `not completed (...)` when `completed.ok` is false, so in `findPreviousRound` the unchanged code of merge-base..head is appended to `newHunks` (lines 922-930). The union of delta + unchanged is the whole merge-base..head; a partial previous round can carry prior findings and fix-hunk mapping, never shrink the reviewed scope. This also neutralises a wrong `reviewedHead` (see F-001).
3. **Mixing PR files into the copied package.** The executor `cp`s the run-store package into `.metaproject/reviews/<reviewId>` of the PR checkout, which merges with any directory the PR committed under that id (the id is public in the round block). Files outside the hash set cannot help: a planted `published.json` or a `research.json` with `scopeReviewed:true` makes the candidate "completed", which leaves the partial path; `registryVouches` excludes `desk-partial`, and the git-log check sees the PR's commit in that directory, so it is untrusted and the round falls back to a full review (fail closed). A planted `research.json` without `scopeReviewed` leaves it partial, hence weak (point 2).
4. **No escalation from partial to full vouch.** `registryVouches` filters out `desk-partial`; `registryVouchesPackage` (used by `premise-question.ts:193` before re-recording as `decide-premise`) goes through it, so a premise answer on a partial package cannot mint a full-vouch entry. Enumerated every registry consumer (`keryx ctx rg 'readRoundRegistry|registryVouches|partialRoundVouch|recordPartialRound|matchingEntry|compactEntries|appendRoundRegistry' src`, non-test): round-registry.ts, prior-round.ts, desk-run-executor.ts, premise-question.ts. None reads `entries` directly other than through these two filters.
5. **Who writes `desk-partial`.** Only `recordPartialRound`, called only from the executor hand-on loop, for a run-store package (`prior.runDir`) with `prior.partial` and an array findings.json. Repo identity comes from the checkout's git config (not committed content). A write failure (lock contention included) returns `{error}`, `handOn` is false, and the loop tries the next candidate: fail closed.

### Other T14 surfaces checked
- **Registry lock (`appendRoundRegistry`).** Append, re-read and compaction all run under `withFileLock(file.lock)` (O_EXCL, nonce, stale recovery); `null` → throw. Callers catch it (`recordFinishedRound`, `recordPartialRound`) and report it. Compaction keeps the newest entry per package id whatever its event, so a later `desk-partial` for the same id could drop an older full vouch; that only costs trust (a full round), never grants it. No finding.
- **Superseded-round refusal (`newerRoundOf`, desk-publication 846-881).** A superseded attempt is never rendered as the as-is variant and gets a blocking reason; deleted/archived newer rounds still count (fail closed). Earlier-attempt directories come from `store.history(found.key)` of the verified attempt's own key and `store.directory(id)`; only `settings.answers` is read from them, and each answer is checked against the current question ids/option ids. No finding.
- **As-is publication on a moved head.** The compare call uses an argv array with `key.repo` (regex-checked), `run.headSha` (40-hex checked) and `pr.headRefOid` (40-hex checked); any failed or unknown status fails closed and is not cached. Submit does not read the preview cache file, so `headStatus` is fresh. The write re-verifies GitHub against `{base, currentHead}` with both connections, the digest binds `currentHead`, the verdict is forced to Comment with inline off, and automatic publication refuses a moved head before any further GitHub read and again in `blockedReason`. No finding.
- **One prior-attempt rule (`update-round.ts`).** Excludes `existing` sources, withdrawn attempts and attempts of the current round; requires `result.reviewed` and `findingsKnown`. Pure selection over the user's own store. No finding.

### Findings

### [F-001] The executor records a `desk-partial` vouch without matching the package to the attempt it came from
- **Severity**: minor
- **File**: src/review/desk-run-executor.ts:1090-1095 (slice lines; source ~527-533)
- **Attack vector**: none reachable. The precondition is a run-store package whose manifest names a revision other than the attempt's; `collectResult` keeps the package even when `matching` is false and `finishExecution` copies `checkedHead` from that manifest into `result.reviewed`, so such an attempt can end `partial` and be a candidate. Even then the partial round is always weak, so the next round still covers all of merge-base..head (`prior-round.ts` 922-930).
- **Problem**: `usable` checks `target.ref`, the review id shape and regular files, but not `manifest.target.base/head` against the prior attempt's `baseSha/headSha`, before `recordPartialRound` writes a trust record for whatever head the manifest names. The executor is the only writer of that record, and it has the attempt's revision at hand.
- **Why it matters**: a mismatched package would set the delta range and fix-hunk mapping of the next round from a revision the attempt did not review. Scope is not narrowed, because of the weak rule, so this is hardening only.
- **Fix**: pass each candidate's `baseSha/headSha` in `previousRunInputs` and require `manifest.target.base === prior.baseSha && manifest.target.head === prior.headSha` for the partial path, before calling `recordPartialRound`.
