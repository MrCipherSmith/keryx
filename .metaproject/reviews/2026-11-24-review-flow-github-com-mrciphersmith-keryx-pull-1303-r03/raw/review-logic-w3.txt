### Logic Bugs

### [F-001] The discussion test's "stale" comes from the digest, so the write-time discussion re-read is untested
- **Severity**: minor
- **File**: src/review/desk-publication.test.ts ("a moved head re-reads the discussion an overlay requires, and a changed discussion makes the submit stale"); code under test src/review/desk-publication.ts:202-205 and :422-424
- **Problem**: The test changes `FIXTURE_DISCUSSION` between the preview and the submit. The submit's `render()` gets a fresh cache (only `preview` reads the cache file), so `prepare` re-reads the discussion and puts the new hash into the digest (`hash([... discussion ...])`, :289); the request is refused at :406 "stale: The review preview changed". The check the overlay actually exists for — re-reading the discussion after the user confirmed and right before the POST (:422 "stale: The pull request discussion changed") — is never reached. `/^stale:/` accepts both. No other test in `src/review` sets `FIXTURE_DISCUSSION` (ctx rg over `*.test.ts`), so this is the only discussion test.
- **Why it matters**: Trigger: delete or break :422-424 (e.g. compare against the wrong value). Outcome: every backend test still passes, while a comment posted on the PR during the confirm dialog is no longer caught before an as-is (or current) review is published — exactly the window `reread_discussion` is for. The `|| headMoved` addition at :202 is pinned (reads `"xxx"` vs `""`), the write-time guard is not.
- **Fix**: add (or change this test to) a case that changes the discussion inside the confirm callback, mirroring the head-move test: `requestDeskPublication(project, key, { kind: "submit", id, settings, digest: preview.digest }, async () => writeFileSync(process.env.FIXTURE_DISCUSSION!, '[[{"id":1}]]\n'))` and assert `.rejects.toThrow("discussion changed")` plus no `FIXTURE_BODY`. Keep the current case but assert `toThrow("preview changed")` so each assertion names the guard it pins.

### Async & Concurrency

### [F-003] The B3 race test can pass without the lock when the child starts slowly
- **Severity**: info
- **File**: src/review/round-registry.test.ts ("T14 B3: an append from another process while a compaction runs survives it")
- **Problem**: The hook waits at most 2 s for the child's `appended` marker. Without the lock, the test only fails if the child imports `round-registry.ts` and appends inside that window; if it takes longer (cold CI, loaded host), the rename happens first, the child appends afterwards, and the expected order `["old","compactor","concurrent"]` holds anyway. The test never false-fails (stale threshold 10 s > 2 s hold), but its discrimination depends on host speed.
- **Why it matters**: no defect today; a regression that drops the lock could stay green on a slow runner.
- **Fix**: have the child write a `started` marker before calling `appendRoundRegistry`, wait for that marker (bounded) in the hook, then sleep a fixed short interval; without the lock the append then lands before the rename deterministically.

### Edge Cases

### [F-002] In the "no longer contains the reviewed commit" loop, previews 2-4 read the cached "diverged" status, not their own
- **Severity**: info
- **File**: src/review/desk-publication.test.ts ("a head that no longer contains the reviewed commit keeps the refusal and posts nothing")
- **Problem**: All four iterations use the same `movedHead`. The first preview caches `headStatus: { head: movedHead, ahead: false }` in `publication-preview-cache.json` (:111, :247-251), and `previewSubject` reuses it for 15 s, so the previews for `behind`, `fail:HTTP 404` and `fail:connection reset` never call compare; their `headMoved`/body/`blockedReason` assertions repeat the diverged result. Each status is exercised only by the submit (fresh cache), where a regression would surface as "stale: The review preview changed" and fail `toThrow("revision moved")` — so the test still fails on a regression, just not through the assertions that name it.
- **Why it matters**: no false pass today; the preview-side assertions for three of four statuses are vacuous, and the comment above the loop says each one is checked.
- **Fix**: pass `refresh: true` on the loop's preview (or remove the cache file per iteration) and assert one new compare read per iteration.

### [F-004] Update-round fixtures pair a partial attempt with a closed package manifest
- **Severity**: info
- **File**: src/review/desk-publication.test.ts (`updateRound`, `finishedAttempt`)
- **Problem**: Both end the attempt `state: "partial"` and write `status: "closed"` into its package manifest. The executor never produces that pair (desk-run-executor.ts:529: "A partial attempt's package never got past its draft"; coverage `complete` requires a closed manifest). The pre-existing round-1 fixture has the same shape.
- **Why it matters**: harmless for these tests — `prepare` checks only the manifest target, not its status, and the answer carry-over reads `earlierRoundAttempts`, which ignores package status. Recorded so a later test that starts reading status does not inherit an impossible state.
- **Fix**: none required; `status: "draft"` would match the producer.
