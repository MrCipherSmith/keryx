### [F-002] Update review uses the current head of a possibly stale preview
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewPublishDialog.tsx
- **Problem**: The Update button is disabled only on `writing || updateDisabled`, not on `previewStale`/a pending preview, and passes `headMoved.currentHead` from the last loaded draft. After a second push the user can click Update with the previous current head.
- **Why it matters**: The backend's strict subject check at run start refuses that range, so it fails closed with an action error instead of starting on the newest head; the user must refresh the preview. No wrong attempt is created. Recorded as an observation only.
- **Fix**: optional — also disable Update while `previewStale` or a preview is pending, or let the start error suggest refreshing the preview.

### [F-003] The existing-attempt guard reads the panel's last status snapshot
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewWorkspace.tsx (`updateReview`, `covering`)
- **Problem**: `covering` is computed from `local.runs`. An attempt on the target head started elsewhere after the last status read (a rule run, another window) is not seen.
- **Why it matters**: For an active/queued attempt the backend's `requestAttempt` returns the existing run, so nothing duplicates; only an attempt that already finished in that window would get a second attempt in the same round (a retry, which the store allows). No demonstrated user-visible harm.
- **Fix**: none required; a status read before the guard would close it if wanted.
