  - `request` now returns `done | skipped | failed`. `updateReview` refreshes the board only on `done`, and shows a toast on `skipped`.

  - The guard now matches any non-archived, non-imported attempt on the target range, in any state and whatever the board shows, preferring an active one.

  - When that attempt is not the latest, it opens the attempt's dialog.
  - A DOM test covers a failed attempt on the current head.

  - So no badge is misattributed.

### Findings

### [F-001] Keyboard focus is lost after "Update review" once the new attempt replaces the opener
- **Severity**: minor
- **File**: apps/desktop/src/review/ReviewRuns.tsx (`onUpdateReview` wrapper in `RunAttempt`); apps/desktop/src/components/ui.tsx `useFocusTrap`
- **Rule**: canonical rubric, accessibility. `.metaproject/rules/stacks/react/code-style-patterns.mdc` is still absent from this worktree; only `stacks/ts-js-node` exists.
- **Problem**: The sequence is:
  1. Clicking Update calls `setPublishOpen(false)`, then `updateReview(...)`.
  2. When the dialog closes, `useFocusTrap` restores focus to the element focused when it opened, if that element is still in the document. That element is the "Publish to GitHub" / "Review publication" button of the reviewed attempt's `<article>`.
  3. When the start answers, the new attempt on the current head becomes `latestAttempt` (`runActive && sameRange(card)`, or `runs.find(runActive)` when the board is behind).
  4. `<RunAttempt key={latest.id}>` remounts, which removes the button that holds focus.
  5. Focus falls to `<body>`.
- **Why it matters**: A keyboard or screen-reader user who presses the dialog's primary action loses their place in the panel. They have to tab from the start of the document to reach the new attempt. This is the main Update path, not an edge case. Round 2 ui-ux listed "where focus lands after the dialog closes on Update review" as not checked.
- **Fix**: After a `done` outcome, move focus to the new attempt. For example, give the Latest-review `<article>` `tabIndex={-1}` and focus it when `latest.id` changes after an update started from this panel. Alternatively, focus the panel's "Latest review" heading. Add a DOM assertion that `document.activeElement` is not `body` after the start answers.

### [F-002] (info) "Update review" stays enabled while the preview is loading or stale, so it can start on a head the draft no longer vouches for
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewPublishDialog.tsx (Update button)
- **Problem**: The button is disabled by `writing || updateDisabled` only. It reads `headMoved.currentHead` from the last draft. Two cases expose this:
  - After a submit fails with `stale:` (the head moved again), the old draft stays and `previewStale` is true. Update then starts a round on the intermediate head instead of the PR's current one.
  - While a refresh preview is in flight, Update also uses the older head.
- **Impact**: No data loss. The workspace comment says the backend validates the range again before admitting the run, so the start is either refused (the error shows in the panel) or reviews a real commit of the PR that is no longer the newest. Either way, the user's intent ("update to the current head") is not quite met.
- **Fix**: Also disable Update while `busy || previewStale`, or label the button from the refreshed preview only.

### [F-003] (info) The reason Update is disabled is only in a `title` on a disabled button
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewPublishDialog.tsx
- **Problem**: `title={updateDisabled ? "Another action of this review is still running." : undefined}` sits on a `disabled` button. Disabled buttons cannot take focus, so keyboard and screen-reader users never reach the tooltip. The state is transient, and the panel already shows `aria-busy` and "Updating review…", so the impact is low.
- **Fix**: Optional. Render the reason as visible helper text in the footer, or use `aria-disabled` with a guarded click so the button stays focusable and announces its description.
