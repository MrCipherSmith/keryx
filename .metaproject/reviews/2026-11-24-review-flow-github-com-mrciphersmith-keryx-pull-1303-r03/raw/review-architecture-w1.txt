### Summary
The T15 Desktop fixes keep the round-2 layering. `ReviewWorkspace` is still the one owner of the start path. The update round goes through the same `local.request({ kind: "start" })` that the launch form and "Review again" use, and the backend's `previousRunInputs`/`selectPriorAttempt` choose the prior round, so the Desktop holds no second prior-attempt rule. `ReviewPublishDialog` stays a presentational dialog with one optional callback and one boolean (`onUpdateReview`, `updateDisabled`). It never decides the range or the options. The "latest attempt" rule was extracted once (`latestAttempt` in ReviewRuns.tsx), and `ReviewRuns` and `ReviewWorkspace` both call it instead of keeping two copies. `useReviewRuns.request` now returns a typed `RunRequestOutcome`, so the caller reacts to the outcome without reading hook internals. The Sessions surface now builds its publication target in one named function, `sessionReviewPublication`, that leaves out `onUpdateReview` on purpose. That closes round-2 architecture-w1 F-002 by an explicit, documented decision. No blocker, major or minor in this lens. One info.

[F-001] info: the "an update round does not carry automatic publication" policy exists only in a Desktop view module
- File: apps/desktop/src/review/ReviewWorkspace.tsx:55 (`updateRoundOptions`), used at :144
- Problem: the rule that each round decides auto-publication again is a review-domain policy. It is implemented as a helper exported from a React component file and applied only on the Desktop "Update review" path. The backend start path (`desk-run-service` start, the options parser in `desk-run-options.ts:43-44`) accepts `autoPublish` from any caller unchanged.
- Why it is info, not a defect: no second entry point copies a previous round's options today. The launch form builds fresh options, and the `follow` auto-queue and watcher-driven update rounds are explicitly out of this PR's scope ("Not in this PR"). There is no failure path in this code (shared law 1). The PR body records the decision itself.
- What would settle it: when stage 4 adds the `follow` auto-queue (a second caller that starts round N+1 with the previous round's options), move this rule next to `selectPriorAttempt`/`previousRunInputs` in `src/review/`, or apply it in the service when it builds an update round, so both callers share it.
