## Findings

### [F-001] The B3 race test waits a fixed 2 s of wall-clock time on every passing run
- Severity: major. tdd-workflow.mdc, Review severities: "Sleep or fixed delay for async work (Rule 6) | always | major".
- File: src/review/round-registry.test.ts:87-88
- Problem: the `beforeCompactionWrite` hook spawns a child appender, then runs `const until = Date.now() + 2_000; while (!existsSync(marker) && Date.now() < until) Bun.sleepSync(20);`.
  With the correct (locked) code the child blocks in `withFileLock` until the compaction releases the lock. So the marker can never appear inside the hook, and the loop always runs out its full 2 s.
  Measured in the scratch worktree: the B3 test alone took 2.73 s, and the 2-test file took 2.79 s. A cold `import` of round-registry.ts in a child takes about 0.09 s.
- Why it matters:
  - The test pays a real, fixed delay on every green run.
  - Its ability to catch a missing lock depends on wall-clock timing: the unlocked child must land within 2 000 ms. On this Mac that margin is about 20x. On a loaded CI runner the margin shrinks, and the test would then pass with the lock removed.
  - A clock-bounded poll is the pattern Rule 6 and Rule 7 exclude.
- Fix: make the hook prove the property deterministically instead of racing a process.
  - Inside `beforeCompactionWrite`, assert that the lock is held: `expect(withFileLock(`${file}.lock`, () => true, { timeoutMs: 0 })).toBeNull()`. Optionally, assert in-process that an `appendRoundRegistry` with a 0 ms timeout is refused.
  - After the call, append the "concurrent" entry normally and assert `["old","compactor","concurrent"]` and that no lock file is left.
  - The lock's waiting behaviour belongs to lib/file-lock.ts's own tests. The contention throw is wave 1 F-003.
  - If a cross-process test is kept, have the child write a "started" marker before it calls append. The hook then waits on that marker (a state), and nothing waits on a fixed window.
- class_scope:
  - sites: ["src/review/round-registry.test.ts:87"]
  - enumeration_method: `keryx ctx rg "^\+.*(sleep|setTimeout|Date\.now|new Date\(\))"` over slice-03.diff found 2 added lines, both at round-registry.test.ts:87-88. That is one site. The other `Date.now() + …` deadlines under src/review/*.test.ts (layers-signal, layers-refresh-lifecycle, agents/controller, desk-run-executor:566) predate this diff and are out of scope.

### [F-002] "Another account or pull request never lends its answers" asserts only an empty result and passes with answer carry-over switched off
- Severity: minor
- File: src/review/desk-publication.test.ts:475
- Problem: the test's only assertion is `settings.answers` `toEqual({})`. Its setup has no same-Review draft, so `{}` is also the result when the carry-over never runs.
  Mutant `.slice(0, answerSourceLimit)` -> `.slice(0, 0)` (desk-publication.ts:357) leaves this test green (1/1). The same mutant fails 3 sibling tests in the whole file.
- Why it matters: the test names a filter (other viewer, other PR) but proves nothing about it on its own. If the carry-over regressed in the same change that broke the filter, this test would say nothing. This is the skill's "falsy-only assertion with no positive artifact" class.
- Fix: before creating the foreign attempts, write a round-1 draft for the same key, e.g. `roundOneDraft({ "fixture#F-002": "uphold" })`. The foreign attempts, which are newer and answer "dismiss", then sit between it and the update round.
  Assert `{ "fixture#F-002": "uphold" }`. That proves the carry-over ran and that the newer foreign drafts were skipped.

### [F-003] Executor fixture: the previous attempt's reviewed head equals the base
- Severity: info
- File: src/review/desk-run-executor.test.ts:797
- Problem: `previousAttempt` writes `target: { base: baseSha, head: baseSha }`. That is an attempt whose reviewed range is empty. The Desktop store records an attempt's own `baseSha..headSha` (desk-run-store `request`), and the PR's head is past its base.
  With head == base, the AC7 test's `range: { base: baseSha, head: headSha }` assertion holds for a delta round and for a merge-base..head first round alike. Only the explicit `mode: "delta"` assertion separates them.
- Fix: optional. Commit a middle commit in the fixture repo and use it as the previous head. Then the range assertion pins the delta on its own.

### [F-004] update-round fixtures carry a `round` with no `reviewId`, a shape the store cannot write
- Severity: info
- File: src/review/update-round.test.ts:50, :59
- Problem: the base `run()` builder has no `reviewId`. The two T14 B1 tests add only `round: 1/2`. desk-run-store.ts `place()` sets `round` only when `reviewId` is a string, so `{round, no reviewId}` never comes out of the store.
  `priorAttemptCandidates` keys rounds by `round` alone, so the outcome is the same, and that is why this is info.
- Fix: optional. Add `reviewId: "review-1"` wherever a fixture sets `round`, as desk-run-service.test.ts's builder already does.

### [F-005] prior-round tests without a `registry` read the developer's real round registry
- Severity: info
- File: src/review/prior-round.test.ts:271 (the new AC6 test). The same pattern is in the pre-existing siblings that omit `registry`.
- Problem: `findPreviousRound` without `deps.registry` calls `readRoundRegistryReport(repoIdentity(cwd))` with no dir. `keryxConfigDir()` then resolves to `$XDG_DATA_HOME/keryx` or `~/.local/share/keryx`. The suite sets neither, and `KERYX_CONFIG_DIR` is not read by `keryxConfigDir`.
  The read is harmless in practice, because the identity is `dir:<mkdtemp>/.git` and so unique per test. It is still a real-home read.
- Fix: optional. Set `XDG_DATA_HOME` to a temp dir in `beforeEach`, or pass `registry: []` where the test does not exercise the registry.
- What holds:
  - Every new test that writes a registry passes an explicit temp dir: round-registry.test `dataDir`, the prior-round AC7 record test `dataDir`, and desk-run-executor `registryDir`.
  - desk-publication.test isolates KERYX_CONFIG_DIR/KERYX_DATA_DIR, PATH (the fake `gh`), and GH_TOKEN/GITHUB_TOKEN. It restores them in `afterEach`.
