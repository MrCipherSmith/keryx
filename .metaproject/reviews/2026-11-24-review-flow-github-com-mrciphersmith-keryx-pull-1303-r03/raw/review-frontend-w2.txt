### Contract checks (hold)
- **Answer carry-over reaches the dialog.** The dialog's first request is `{ kind: "preview", id, refresh: true }` with no `settings`. So `saved` is the attempt's own draft or undefined, and `earlierAnswers(earlier)` fills the answers only when the new round has no draft of its own. Every later preview sends `currentSettings` derived from that first result, so the carried answers persist. Option answers match because the option id is `sha256([questionId, label])`, which is stable across rounds. This matches AC10 and the docs ("answers carry over by finding id").
- **The superseded-round state renders coherently.** When `newerRound` is set, `headMoved` is undefined. The dialog then shows no notice, no Update and no as-is button: it shows "Submit review", disabled with the "Round N of this review is newer" `blockedReason`. Nothing else is offered in that state.
- **The headMoved body and digest.** The body line is prepended before the overlay round block. The current head enters the digest, so a further push makes the dialog's digest stale (`stale:`), and the dialog sets `previewStale`.
- **The docs** match the UI labels: "Publish as is for", "Update review to", "Save locally", automatic publication not carried over, and an existing attempt shown instead of starting another.
- **TypeScript.**
  - No `any` in the new backend or test code.
  - `object()` narrowing is used for the earlier draft.
  - `HeadMoved = NonNullable<PublicationState["headMoved"]>` keeps one source type.
  - The new optional fields follow `exactOptionalPropertyTypes` (`newerRound?: number | undefined`, `previousRuns?: … | undefined`).
  - The `!` assertions are confined to the DOM test's fixtures and queries, as in the existing tests there.
- **DOM test hygiene.** Each new test unmounts with `root.render(null)` or closes the dialog. `deferred()` gates hold the in-flight states, and the disabled-button clicks assert that no `start` action ran.

### Findings

### [F-001] The feedback added for round 2 UX-102 (the toasts) and the shown existing attempt are not asserted by the DOM tests
- **Severity**: minor
- **File**: apps/desktop/src/reviews/ReviewPanel.dom.test.tsx (test "Update review from an earlier attempt does not start a second attempt when the current head already has one"); apps/desktop/src/review/ReviewWorkspace.tsx:139 and :148
- **Rule**: canonical rubric (test does not pin the behaviour the fix is about); `.metaproject/rules/stacks/ts-js-node/testing.mdc`
- **Problem**: T15 fixed round 2 F-002/UX-102 by adding user feedback:
  - the toast "Commit <sha> already has a review attempt", with the existing attempt shown instead of starting another;
  - the "Update review did not start" toast for a skipped request.

  No test asserts either toast; the test file never mentions `toast` or the titles. The test for the existing finished attempt (PR 51) asserts only negatives: no `start`, no dialog, and that the reviewed attempt's article is gone. It never asserts that `attempt-current` is shown. The failed-attempt variant (PR 54/55) does assert the attempt is shown.
- **Why it matters**: Removing the toasts, or the guard showing nothing at all (an empty panel), would pass the PR 51 test. The UX-102 defect was exactly "no feedback", so the regression the fix guards against is not pinned.
- **Fix**: In the PR 51 test, assert that `article[aria-label="Review attempt attempt-current"]` is present. Capture toasts through the test host's toast provider, or a spy on `useToast`, and assert the info toast title for the existing-attempt case and the "Update review did not start" title for a skipped request.
