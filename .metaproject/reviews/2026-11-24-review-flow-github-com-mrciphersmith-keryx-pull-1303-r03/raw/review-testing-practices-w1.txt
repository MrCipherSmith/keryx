## Findings

### [F-001] `newerRoundOf` round boundary unpinned: a same-round sibling is never in a fixture
- Severity: minor
- File: src/review/update-round.ts:85 (test src/review/update-round.test.ts:110-117)
- Problem: mutating `item.round <= current.round` to `<` leaves update-round.test.ts (11/11) and desk-publication.test.ts green. No fixture gives `newerRoundOf` a second attempt of the *same* round (a retry), and that is the input that separates `<=` from `<`.
- Why it matters: this gate was added in answer to round 2 (T14 B6). Under the mutant, a retry within round N would block publication of the round-N attempt with "Round N of this review is newer" and would suppress the as-is variant. Nothing would catch that regression.
- Fix: in update-round.test.ts, add `expect(newerRoundOf([run("retry", { reviewId: "review-1", round: 1 }), round1], round1)).toBeUndefined()`.

### [F-002] B5 compare-status allowlist unpinned: no fixture returns a non-definitive status string
- Severity: minor
- File: src/review/desk-publication.ts:110 (test src/review/desk-publication.test.ts:205-218)
- Problem: deleting `if (!["ahead","behind","diverged","identical"].includes(status)) return false;` leaves desk-publication.test.ts green. The refusal test drives `diverged`, `behind` and two `fail:` cases. The `fail:` cases make the gh call throw and take the `catch`, so they never reach the allowlist.
- Why it matters: T14 B5 promises that "a failed read is not cached, so the next preview asks again". Under the mutant, an unexpected status string would be cached as not-ahead for that head, and later previews would never re-ask GitHub. The suite would stay green.
- Fix: make the compare fixture print an unexpected status (for example an empty string) on the first preview and `ahead` on the second. Assert that the second preview has `headMoved` and that `FIXTURE_COMPARE_READS` holds two reads. Separately, assert that two previews against the same `diverged` head read the compare once, which pins the per-head cache.

### [F-003] Round-registry lock contention path unpinned
- Severity: minor
- File: src/review/round-registry.ts:170 (test src/review/round-registry.test.ts)
- Problem: `if (written === null) throw …` -> `if (false) throw …` leaves round-registry.test.ts green. The B3 test pins the lock around a compaction, but no test holds the lock while an append comes in.
- Why it matters: per the T14 B3 docblock, "A lock that cannot be taken throws", so the caller reports an unrecorded entry instead of silently returning `null` as a result. Under the mutant, `appendRoundRegistry` would return `null` to callers that read `.file`/`.warning`. Nothing would catch that.
- Fix: create a fresh `${roundRegistryFile(id, dir)}.lock` (held, not stale) and call `appendRoundRegistry`. Assert it throws `/locked by another keryx process/` and that the registry file is unchanged.

### [F-004] Update review's "attempt already covers the target head" selection is only partly pinned
- Severity: minor
- File: apps/desktop/src/review/ReviewWorkspace.tsx:135-136 (tests apps/desktop/src/reviews/ReviewPanel.dom.test.tsx:752, :902)
- Problem: three mutants of the T15 `covering`/`existing` selection leave the 45-test DOM suite green:
  - dropping `!reviewIsArchived(run)`;
  - dropping `run.source !== "existing"`;
  - `covering.find(runActive) ?? covering[0]` -> `covering[0]`.
  The two fixtures that drive this path use one covering attempt each: a failed one (:752) and a complete one (:902). Neither is archived or imported, and neither has a second covering attempt.
- Why it matters: each filter decides whether Update review starts a round or redirects to an old attempt. With the archived or imported filter gone, an archived or imported attempt on the new head would block every update round. With the active preference gone, the panel would show a stale failed attempt instead of the one running. None of this would be caught.
- Fix: add DOM cases on the headMovedFixture:
  - (a) the only attempt on currentHead is archived (`decision.action: "archive"`): `start` is sent;
  - (b) the only attempt on currentHead has `source: "existing"`: `start` is sent;
  - (c) the runs are `[failed on currentHead, running on currentHead]`: no `start`, and the running attempt is shown.

### [F-005] The "Update review did not start" race path is unpinned end to end
- Severity: minor
- File: apps/desktop/src/review/useReviewRuns.ts:38 and apps/desktop/src/review/ReviewWorkspace.tsx:148
- Problem: two mutants leave the DOM suite green:
  - the busy guard's `return "skipped"` -> `return "done"`;
  - the `outcome === "skipped"` toast -> `false`.
  The test at :714 proves that the disabled button stops the click, so the request is never issued. No test issues a start while another mutation is pending, which is the race the code comments say this branch covers.
- Why it matters: if the guard's return value regressed to `"done"`, a raced Update click behind a stale board would refresh the board as if a round had started, and the user would get no "did not start" message. The suite stays green either way.
- Fix: add a hook-level test of `useReviewRuns`: start one mutation with a deferred `invoke`, then call `request({kind:"start",…})` and expect `"skipped"`, with no second `invoke`. Optionally, render `ReviewPublishDialog` with `updateDisabled={false}` while a cancel is pending, and assert the info toast and `refreshed === 0`.

### [F-006] The answer-carry-over bound is unpinned
- Severity: info
- File: src/review/desk-publication.ts:357
- Problem: dropping `.slice(0, answerSourceLimit)` leaves desk-publication.test.ts green. No fixture has more than 8 earlier-round attempts.
- Why it matters: this is a performance bound only. Only the newest draft's answers are used, so there is no wrong user-visible outcome, and that is why it is info.
- Fix: optional. Add a fixture with 9 earlier attempts where only the 9th holds a draft, and assert its answers are not carried over.
