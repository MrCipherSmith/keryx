### [F-001] Stale-lock recovery in lib/file-lock.ts can let two writers into the registry's critical section
- Severity: minor (location_class pre-existing: the helper predates the PR; T14 chose it for the registry)
- File: src/lib/file-lock.ts:109-117 (reached from src/review/round-registry.ts:154)
- Pattern: Part 0 / concurrency-patterns.mdc, lock file stale recovery. The stale break is a stat-then-unconditional-rm (TOCTOU).
- Failure mode, step by step:
  1. A holder is killed inside the critical section and leaves `<registry>.jsonl.lock`.
  2. Waiters A and B both see it older than 10 s through `statSync`.
  3. A runs `rmSync`, then `openSync(wx)` succeeds, and A enters the critical section.
  4. B's `rmSync(lockPath, {force:true})`, issued on its earlier stat, removes A's fresh lock.
  5. 15 ms later B's `openSync(wx)` succeeds, and A and B are inside together.
  With the registry past 512 KB, one compaction's rename drops the other's append. That is round 2 F-001's outcome: a lost desk-partial, complete or publish vouch, so the next round on this machine falls back to a fuller review. No trust is granted wrongly. A's nonce check keeps it from deleting B's lock afterwards, but it does not stop the overlap.
- Why minor: the trigger needs a holder killed inside a critical section of a few milliseconds, at least two concurrent waiters and a file past 512 KB. The outcome is the registry's documented degradation (one fuller round), not one of the four blocker shapes. Under law 2 it is still recorded rather than dismissed as unlikely.
- Evidence: the repository already holds the fixed shape. src/lib/fs.lock-reclaim.test.ts ("two reclaimers racing over a dead owner never both hold the lock", review r1 F3 of flow 272) pins it for the async `withFileLock` in src/lib/fs.ts. That lock moves a stale lock aside by rename and checks the owner, so A's live lock is never removed. The same file also has the sync lease, `acquireLeaseSync`/`reclaimStaleLeaseSync`, with pid-based "gone" detection.
- Fix: take the registry lock through the sync lease in src/lib/fs.ts, which reclaims a gone holder safely. Or port its rename-aside reclaim into lib/file-lock.ts:
  - rename the stale lock to `${lockPath}.stale.<nonce>`, then re-check the moved file's mtime and nonce before deleting it;
  - add a test like fs.lock-reclaim.test.ts with an injected interleaving.

Lock Contention
### [F-002] After a lock timeout, the executor waits 15 s again on the same registry lock for each further partial candidate
- Severity: minor
- File: src/review/desk-run-executor.ts:525-537 (loop) and src/review/round-registry.ts:154-170
- Pattern: Part 0, retry with no cap. The same unavailable resource is retried once per candidate, each attempt costing the full timeout, synchronously.
- Failure mode: the loop calls `recordPartialRound` for each usable partial candidate in `previousRuns`. That list is every completed or partial attempt of the same Review's earlier rounds, with no count limit (update-round.ts:66-73). If the registry lock cannot be taken, each call spins in `withFileLock` until the 15 s deadline, using `Bun.sleepSync`, which blocks the event loop. It then returns `error`, and the loop tries the next partial candidate against the same lock. Two triggers make this happen:
  - the registry's `review-rounds` directory is not writable by the worker, so `openSync(wx)` fails every time with no stat match, until the deadline;
  - a lock file the worker cannot remove.
  With k partial candidates, the worker stalls for k × 15 s before the reviewer spawns. During that time its 500 ms cancel poll (desk-run-service.ts:349) and its SIGTERM/SIGINT abort handlers cannot run, so a Cancel from Desktop takes effect only after the stall. The run still ends correctly: it falls back to a closed candidate or a first review, and no wrong trust is granted.
- Why minor: the cost is degradation bounded by the number of partial attempts in one Review, normally a few. It needs a broken config directory or lock. Ordinary contention is resolved in milliseconds, and a crashed holder's lock is broken after 10 s.
- Fix: stop handing on partial candidates after the first lock failure (the registry error), because a retry hits the same lock. One way is to remember `registryUnavailable` in the loop and skip `prior.partial` candidates after it, while still accepting closed ones. Optionally, pass `timeoutMs` and `onWaiting` from this call site so the worker's phase line shows "waiting for the round registry lock" instead of a silent stall.

### [F-003] A writer built before T14 (a stale `keryx` on PATH) still compacts without the lock
- Severity: info
- File: src/review/round-registry.ts:151 (contract), relation to .metaproject/memory/constraints/stale-installed-keryx-binary.md
- Pattern: Part 0, mixed-version writers to one shared state file.
- Failure mode: the registry file is shared by every clone and worktree of the repository on the machine. A `keryx review complete`, `ingest` or `publish` run by a pre-T14 binary takes no lock. The accepted memory constraint says the keryx on PATH is a stale build. Such a run can still drop a Desktop worker's locked append during its own unlocked compaction while the file is past 512 KB. The outcome is the same as round 2 F-001: one fuller round, no wrong trust. It goes away once every keryx on the machine is at or past this change.
- Fix: no code change. Optionally, note in the PR body that the lock protects only writers built from this change onward.
