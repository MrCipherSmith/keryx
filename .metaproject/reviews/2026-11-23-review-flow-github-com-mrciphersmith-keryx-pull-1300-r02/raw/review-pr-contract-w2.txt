## Findings

### [PC-003] "Issue sessions get it when withIssueBinding binds them" — existing and non-github.com issue sessions never get a subject, so the new Issue work row shows them as unbound
- Severity: minor
- File: apps/desktop/src/issues/IssueWorkRow.tsx (claim in the PR body, "What changes" → Sessions bound to a Subject)
- Problem: The body says "Issue sessions get it when `withIssueBinding` binds them." The head writes the subject only once, at the first bind, and only for github.com issues: src/session/issues/issue-session.ts "Written once, when the session is bound: a subject the person later unlinks is not written back. An issue whose URL is not a github.com issue page (GitHub Enterprise) has no subject keryx can store." (`parseSessionSubject` requires `^https:\/\/github\.com\/...`). The new Issue work row counts sessions by `subject` only: IssueWorkRow.tsx `const bound = issueSessions(sessions, issue).length;` → `: stage === "needs_answer" ? "Open question" : "Open in session"`. So an issue session bound before this version (it has `hasIssue`, no `subject`), or one on a GitHub Enterprise host, reads "Open in session" with the empty-slot style although a bound session exists; the button still reaches that session through the backend binding.
- Why it matters: the owner reads the body as "every issue session is now visible on its card". After upgrade, all issue sessions created earlier show as unbound, and Enterprise issues never show a session; neither limit is in "Known gaps and choices for the owner".
- Fix: state both limits in the body (and in "Known gaps"), or backfill `subject` for existing issue bindings (e.g. when `issueContextForSession` reads one) and have the row fall back to `hasIssue`.
