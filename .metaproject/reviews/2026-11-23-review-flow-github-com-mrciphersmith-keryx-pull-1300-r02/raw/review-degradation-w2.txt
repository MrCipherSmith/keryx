### [DG-009] The "repository" source counts pull requests toward each 40-item page, so the default Issues board can load few issues or none

- **Severity**: minor
- **Class**: default-change
- **Evidence kind**: base-diff
- **File**: src/integrations/issues-board.ts (listUrl / listIssuePage)
- **Problem**: On base, every source listed `/issues?filter=<scope>&pulls=false&per_page=40`, and each page could hold up to 40 issues. The new repository source lists `/repos/{owner}/{repo}/issues` with `per_page=40` and no `pulls` parameter. Pull requests are removed only after the fetch (`data.filter((x) => !x.pull_request)`), so each page holds 40 minus the pull requests on it. This source is now the Desktop default (DEFAULT_SOURCE = "repository").
- **Why it matters**: In a repository where the most recently updated items are mostly pull requests (this repository has about 1300), the first page of the default board shows a few issues, or none. useIssueCollection.load does not continue on its own when a page comes back empty. IssuesBoard then shows "No matching issues on the loaded pages." and a "Load more issues" button, and the user has to click through pages of pull requests. Assigned-to-me on base never had this.
- **Fix**: For the repository source, keep fetching the next page until the batch reaches N issues or a cap of 3–4 requests. Or have useIssueCollection auto-load the next page when a page returns zero rows and nextCursor is set. Add a test with a page of PRs only that asserts issues still appear.

### [DG-010] Issue sessions bound before this change never get a `subject`, so their card's session slot reads "Open in session"

- **Severity**: info
- **Class**: behaviour-delta
- **File**: src/session/issues/issue-session.ts (withIssueBinding)
- **Problem**: bindIssueSubject runs only on the `registered` stage. An issue whose session was bound on base (stage `session_bound` or later) is reopened by the same binding, but no subject is written. IssueWorkRow counts sessions only through `subject`, so that card shows the empty, dashed "Open in session" while a bound session exists. The action itself is unchanged: open-session reuses the bound session. This is why it is info and not minor. Base showed "Open session" for every issue.
- **Fix**: On a non-registered reopen, write the subject when flags.json has none and no unlink was ever recorded. For example, store `subjectUnlinked: true` on unlink rather than inferring it from absence. Or name the gap in the known-gaps list.
