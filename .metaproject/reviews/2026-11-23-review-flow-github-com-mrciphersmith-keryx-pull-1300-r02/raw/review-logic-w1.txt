### [LG-007] AC9's text no longer matches the Create Flow linking rule
- **Severity**: minor
- **File**: apps/desktop/src/review/prWork.ts (`resolveFlowLinks`)
- **Problem**: Frozen AC9 says "the first new flow package that appears while that request is pending is linked to the session … when several new packages appear, none is linked". After T17, `resolveFlowLinks` links only when exactly one request is live (`const only = live.length === 1 ? live[0] : undefined`), and a request expires after `FLOW_LINK_WINDOW_MS` (15 min). Two cases the AC does not exclude now link nothing. (1) "Create Flow" on PR A, then on PR B, then A's package appears: no link, and both requests end. (2) The prompt is sent and the package appears more than 15 minutes after the press: no link.
- **Why it matters**: The AC is checksum-frozen and will be confirmed with `keryx flow ac confirm`. Literal AC9 would require linking the first package to request A even while B is pending, which is the HL-001 blocker the fix removed. The narrower rule is correct, but neither the AC, the plan's State × event matrix ("first new package linked to that session"), nor implementation-plan.md "Создание из сессии" states it. A confirmer reading AC9 against the code finds a mismatch that nobody has accepted. Not a blocker: the AC's own scenario (one request, one package) is implemented and tested, and the deviation comes from fixing a blocker, not from missing work.
- **Fix**: Have the owner amend AC9 through `keryx flow ac update` ("…linked when it is the one new package and this is the one pending request, within 15 minutes of the press; otherwise none is linked"). Or record the narrowing as an accepted deviation next to AC9 before confirming it. Update the plan matrix row and implementation-plan.md to match.

### [LG-008] Create Flow during an in-flight open registers a pending link without the flow prompt
- **Severity**: minor
- **File**: apps/desktop/src/App.tsx (`createPrFlow`)
- **Problem**: `subjectOpener` (added in T17 for HL-002) returns the in-flight open's promise to any repeat call for the same Subject, "whatever its target or prompt". `createPrFlow` awaits that promise and then calls `flowLinks.expect(id, known)` unconditionally. Trigger: press "Open in session" on PR #10, then press "Create Flow" on the same card before `session/new` answers. The session opens with the PR URL in the composer, not the flow prompt (the journal says so), yet a 15-minute pending flow link is registered for it. If any package appears in that window (another session, the CLI, the Issues board "prepare-flow"), and it is the one new package and the one pending request, `linkFlow` persists it as the session's `flow` flag. PR #10's card and the session header then show an unrelated Flow. The user never asked this session for a Flow.
- **Why it matters**: The fix round added this path. It is the LG-002/HL-001 class of wrong persisted link, reached through a new trigger. It is narrow: a double press within the open latency, plus a foreign package within 15 minutes.
- **Fix**: Register the pending link only when the flow prompt was applied. For example, have `subjectOpener` report whether it reused an in-flight open, and skip `expect` in that case, or apply the flow prompt after the reused open resolves and then call `expect`. Add a prWork or App test: an in-flight open, then createPrFlow, then one new package links nothing.

### [LG-009] A header focus for another repository fires later, unrequested
- **Severity**: minor
- **File**: apps/desktop/src/review/ReviewBoard.tsx (focus effect)
- **Problem**: After T17 the effect returns early while `snapshot.repo` differs from `focus.repo`, and App clears `reviewFocus` only through `onFocusHandled`. Trigger: a session is bound to owner/a#5 while the board shows owner/b. Clicking the header link switches to Pull requests and nothing opens, with no message. The request stays in App state. When the user later selects owner/a for any reason, the #5 panel opens. The journal accepts this ("a header focus for another repo stays armed until that repo is shown") but gives no reason. The round 1 fix proposal ("have the board select that repository") was not taken.
- **Why it matters**: The click gives no feedback, and the panel opens at an unrelated later moment. That is the shape of LG-003's repro B, now limited to a PR the user once asked for. Low impact.
- **Fix**: Have the board select `focus.repo` when it is among `snapshot.repositories` (then open the panel). Otherwise drop the request with a short notice ("owner/a is not on this board").
