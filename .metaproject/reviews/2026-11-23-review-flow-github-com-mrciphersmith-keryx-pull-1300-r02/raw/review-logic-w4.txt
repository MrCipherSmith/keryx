### Logic Bugs
[LG-013] minor: AC7 "opens the same session (newest non-archived bound session)" has no test with two bound sessions that asserts which one "latest" opens.
- File: apps/desktop/src/review/prWork.ts
- Problem: openSubjectSession resolves "latest" to `bound[0]`. I listed every test call that reaches the "latest" path:
  - prWork.test.ts: Open in session, Create Flow, keryx-answers-without-subject, subjectOpener and stores-the-subject. Each has at most one session bound to that subject. In the "New session" test, s2 exists, but s1 is then opened by id.
  - PrWorkRow.dom.test.tsx: "2 sessions for #101" only checks that the stub received the target "latest".
  - app-navigation.fixture.tsx: "2 sessions for #12" runs with two sessions bound to #12. It asserts only that the titlebar contains "PR org/project#12", which both sessions satisfy, and it does not check `loaded` there.
  boundSessions ordering is tested on its own, but the step that picks one of its results is not. Changing `bound[0]` to `bound.at(-1)` would, by reading, pass the whole suite. I did not run it.
- Impact: The AC clause is unverified, and a regression that reopens the oldest bound session would ship green.
- Fix: In app-navigation.fixture, after the "2 sessions for #12" press, assert `loaded.at(-1)` equals the id of the newest #12 session (the menu-created one, since the stored updatedAt grows with stored.size). Or add a prWork.test case with two bound sessions that have distinct updatedAt, and assert that "latest" returns the newer one.

[LG-014] info: The model invariant "every card the filters keep lands in a drawn lane" is false for a card that the DOM suite itself builds.
- File: apps/desktop/src/review/model.test.ts
- Problem: drawnLanes("role", {mine: true}) returns ["mine"]. A card authored by the viewer that also lists the viewer as a reviewer lands in "requested". The DOM test "a shown card is never dropped because its lane was ruled out by the filters" asserts exactly that. The model property test passes only because its card set has no such card. The board stays correct through `possible.has(lane) || lanes.has(lane)` in ReviewResults (W2-04 shows this is pinned). No change is asked. The model test title and the drawnLanes doc ("lanes … that can hold a card") overstate the guarantee. The fallback, not drawnLanes, is what keeps AC3's "no shown card vanishes" true.
