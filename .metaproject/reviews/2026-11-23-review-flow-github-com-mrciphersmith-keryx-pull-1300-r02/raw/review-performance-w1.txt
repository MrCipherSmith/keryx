### Regressions from the fix: none found in this lens
- `prFlows(card, flows, bound)` now builds a full `prFlowIndex` on every call. Its callers are `openPrSession` (on a click) and ReviewLaunchDialog `linked` (once per dialog render). The dialog cost is O(flows) Map inserts per render, the same order as the `.find` with a regex per Flow it replaced. Not a regression.
- `usePendingFlowLinks`: the effect returns early when nothing is pending. A pass costs O(pending × sessions + flows) and runs only on a flows or sessions change. Linking is bounded by `claimed`, and requests expire after 15 minutes. The `claimed` Set grows by one entry per linked package for the App's lifetime, and each entry comes from a user "Create Flow" press. Not a leak worth a finding.
- `withPendingSubjects` copies the session array on every memo recompute, which happens on a `state.sessions` or `pendingSubjects` change, not per render.
- App per-render `flows.cards.find(...)` for `shownFlow` is O(flows) with string equality, next to the existing `reviewFlowId` scan. Negligible.

### Findings

### [F-001] IssueWorkRow still filters and sorts every session per issue row on every render (PF-001 residual)
- **Severity**: minor
- **File**: apps/desktop/src/issues/IssueWorkRow.tsx
- **Hot path**: The Issues view is mounted only while it is the work view. It re-renders on every App render, because IssuesView and IssuesBoard are not memoised and receive inline `onWork` arrows. App renders once per flushed session-update batch (rAF, or 250 ms when hidden) while any session streams. Each render runs `boundSessions` once per rendered row: board cards plus the open detail panel.
- **Problem**: `issueSessions(sessions, issue)` is `boundSessions(sessions, issueSubject(issue))`: a full filter with `sessionFlags` and `sameSubject` over every session, then a sort, per row. The PR board got `boundSessionIndex` for this exact reason.
- **Why it matters**: Reasoned, not measured: rows × sessions cheap comparisons per frame, e.g. 200 loaded issues × 300 sessions ≈ 60k per streaming frame. This is well under a frame on its own, so it is jank risk at scale only. This is why it is minor.
- **Fix**: In `Collection`, `useMemo(() => boundSessionIndex(sessions), [sessions])` and pass the lookup (or the count) to IssueWorkRow instead of the raw list.

### [F-002] Two implementations of "sessions bound to a subject" (info)
- **Severity**: info
- **File**: apps/desktop/src/acp/types.ts
- **Problem**: `boundSessions` (filter by `sameSubject`, then sort) and `boundSessionIndex` (group by `subjectKey`, then sort) encode the same rule twice. They agree today: the same archived check, the same `newestBoundFirst`, and `subjectKey` equality matches `sameSubject` by construction. Round obligation 7 asks for one rule, one implementation. The F-001 fix would leave `boundSessions` used only by `openSubjectSession` and the tests.
- **Fix**: Define `boundSessions(sessions, subject)` as `boundSessionIndex(sessions)(subject)`. The cost is the same O(n) per call. The architecture lens owns this if it files it.

### [F-003] memo(ReviewResults) is still defeated by the inline onSubscribe (pre-existing, info)
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewBoard.tsx
- **Problem**: With a watcher target, `onSubscribe` is a new arrow on each render, so `memo(ReviewResults)` and every PrWorkRow re-render on every App render. This line is outside the diff. After the fix the per-card work is index lookups, so the remaining cost is small. It is recorded because the journal says "stable callbacks" for PF-001, while the memo on ReviewResults still cannot hit.
- **Fix (optional)**: `const subscribe = useCallback((item: ReviewCard) => setSubscriptionNumber(item.number), [])`.
