### Prior finding in this lens: FE-001 (closed)
I checked the claimed fix against the code at head.
- **The focus request now names its repository.** App.tsx declares `useState<{ repo: string; number: number; nonce: number } | null>`. The header link sets `setReviewFocus({ repo: subject.repo, number: subject.number, nonce: ++focusNonce.current })`. The nonce comes from an App-level ref and is never reused.
- **The board matches the repository and reports handling.** ReviewBoard's effect returns early on `snapshot.repo.toLowerCase() !== focus.repo.toLowerCase()`. After opening the panel it calls `onFocusHandled?.(focus.nonce)`, and App's `reviewFocusHandled` clears the request when the nonce still matches.
- **A remount cannot replay the request.** A remounted RepositoryBoard (after a repository or account switch) receives `focus=null`.
- **A DOM test pins it.** PrWorkRow.dom.test.tsx, "the session header's PR focus opens the panel only on the board of its repository, and a remount does not replay it", covers three cases:
  - a focus for another repository opens no panel and calls no handler;
  - a case-insensitive repository match opens the panel and reports handled `[2]`;
  - a remount reopens nothing.
- **What remains is deliberate.** A focus for a repository that is not shown, or for a PR missing from the snapshot, stays armed until a matching snapshot appears. The journal T17 section records this under "Behavior changes accepted by the orchestrator": "a header focus for another repo stays armed until that repo is shown". Under shared law 4 this is a decision, and I cannot show its reason wrong.
- **The filter case from round 1 no longer applies as written.** The effect checks `snapshot.cards`, not `visible`.
- **The fix introduced no regression.** `onFocusHandled` and `reviewFocusHandled` are stable (`useCallback(..., [])`), so the effect does not loop, and `setSelected` runs once per nonce.

The same class was reported as LG-003 and DG-002 (dedupe `review-focus-number-only`). The same code closes both.

### Other changes checked, no findings
- **Hook order.** `ReviewResults` calls `useMemo(newestFirst)` before the board/list branch. `usePendingFlowLinks`, `subjectOpener` (`useMemo(..., [])`) and the board callbacks are called unconditionally in App.
- **Callback stability for the `work` memo.** `openPrFromBoard`, `createFlowFromBoard`, `openFlowFromBoard` and `reviewFocusHandled` are `useCallback`s. They read `s`, the sessions and the Flow cards through latest-value refs (`acp`, `subjectSessionsRef`, `flowCards`), the same pattern as the existing `linkRef` and `latest` siblings. `prWorkIndex` is memoised on `[flows, sessions]`.
- **Effect side effects.** The `usePendingFlowLinks` effect writes links through `linkRef`. Its `claimed` set prevents a second link when the effect runs again (StrictMode double-run, or a later flows/sessions change).
- **Keys.** Lanes are keyed by lane id, tiles and rows by PR number, issue rows by `issueKey`.
- **Accessibility basics.**
  - Work-row slots and card actions have visible text, plus `aria-label`s that name the PR or issue.
  - The More button has `aria-haspopup="menu"` and `aria-expanded`.
  - The menu is portaled, and its anchor ref is set before the menu can open.
  - The quick filters use `aria-pressed`.
- **TypeScript.** The change adds no `any`, no non-null assertions and no `I`-prefix issues. Optional props are spread conditionally (`{...(sessions ? {sessions} : {})}`), which is compatible with exactOptionalPropertyTypes.
- **Leftovers of the removed card UI.** `TranscriptUpdate`, `.review-live-state`, `.review-publication-pending` and `.is-following` are all still used (ReviewRuns, SessionReviewActivity, ReviewResults). `CardReviewProgress` has no remaining importer.
