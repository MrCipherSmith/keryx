### Findings

### [F-001] The "repository" issue source hydrates the repository of every row with a GraphQL request on every page (info)
- **Severity**: info
- **File**: src/integrations/issues-board.ts
- **Hot path**: every `keryx issues list` page with `source: "repository"`. That is now the default Issues source (D5), so it covers the first load, each refresh and each "load more" of the Issues board. It is user-initiated, not per keystroke.
- **Problem**: `listIssuePage` hydrates rows that have no `repository.node_id` with `api.graphql(nodes(ids:$ids) ...)`, run after the REST page returns. For `/issues` (viewer scopes) GitHub embeds `repository`, so this was the rare path. On `/repos/{owner}/{repo}/issues` the PR's own fixture expects it to be absent (`repoRow` strips `repository`, and the AC13 test answers `/graphql` for every row). If that holds, every page of the default source makes two serial GitHub round trips instead of one. The GraphQL request resolves up to 40 nodes whose repository is one value the function already knows: the owner and name are `repository`, and only the node id is missing.
- **Why it matters**: one added serial round trip per page on the default Issues load, roughly doubling its network latency. This is reasoned, not measured. It is bounded at one request per page, not N+1, so it is not a bottleneck. The claim that GitHub's repository-issues REST response omits `repository` is about another service's behaviour and has no pinned `file:line` behind it. Under the cross-repo rule it is therefore info. It would be settled by one recorded `/repos/{o}/{r}/issues` response, or by a timing of the Issues board's first load against `source: "assigned"`.
- **Fix (optional)**: For the repository source, build `Repository` from the known `owner/name` and get its id once: a `repository(owner,name){id}` query that does not depend on the REST page and can run concurrently with it, or carry the id in the scoped cursor so that pages after the first need nothing. Keep the `nodes` hydration for the viewer scopes.

### Clean Areas
- Turn-end chain (slice-03): `PendingSubjects.apply` returns at once when no binding is pending (`if (!subject) return;`), so the added `.then(() => subjects.apply(sessionId))` costs nothing on ordinary turns. `subjects` is a `useMemo` over `[cwd, dispatch, refreshSessions]`, and `refreshSessions` is a `useCallback` over `[cwd, dispatch]`, so it is stable between renders. `bindSubject`/`linkFlow` are `useCallback`s. `pendingSubjects` changes only on a bind or a settle, not per render.
- AppShell `titleLinks`: rendered as given. No per-render work was added.
- Session flags (slice-05): `readSessionFlags` now runs `parseSessionSubject` (three anchored regexes on short strings) per session on `session/list`. That is negligible next to the existing per-session `flags.json` read. `updateSessionFlagsAt` reads and writes once per request, as before. `JSON.stringify(...).slice(0, 300)` runs only on the error path. `bindIssueSubject` adds one atomic write, only on a binding's `registered` stage.
- `projectRepository` spawns one async `git remote -v` per page through `execFile`, so it does not block. Each page is already its own `keryx issues list` process, so the spawn is marginal and not a finding.
- Pagination: the repository source keeps `per_page: 40` and cursor paging. The cursor scope now includes the repository.
- N+1 / indexes: none. Memory leaks: `PendingSubjects` deletes each entry once it settles. No listeners or timers were added in these slices. Bundle imports: none were added on the Desktop side. `issues-board.ts` imports `board-github` (Node CLI side), which `commands/issues.ts` loads only for the `issues` command.
- CSS (review.css): static rules only.
