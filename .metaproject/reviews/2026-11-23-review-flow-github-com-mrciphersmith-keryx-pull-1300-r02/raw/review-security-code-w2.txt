### Verified clean (each line names what it rests on)
- **Path/URL injection in `/repos/{owner}/{repo}/issues`** (issues-board.ts `listUrl`): the repository comes only from `git remote -v` through board-github.ts `githubRemote`, which accepts exactly one slash and `^[a-z0-9-]+\/[\w.-]+$` (no `%`, `?`, `#`, `/` in either part). The one admitted traversal shape (a name of only dots) is rejected by `projectRepository` (`/^\.+$/`), and each part is additionally `encodeURIComponent`-ed before `new URL(..., API)`. `IssueGithub.request` re-checks `url.origin === API` and no userinfo, and fetches with `redirect: "error"`, so the bearer token cannot leave api.github.com.
- **Cursor replay across repositories**: the repository (lower-cased) joins `cursorScope` for the repository source, and `readCursor` requires the `scope + "."` prefix, so a cursor from org/base is refused in org/other and in a viewer scope (the new test asserts both). The scope is a public hash, not a MAC, so a client can forge a cursor for its own scope; that is pre-existing design and harmless because the decoded cursor contributes only allow-listed `page|after|before|since_id` keys via `searchParams.set` (encoded), never a path or host.
- **Pagination link trust**: `pageLink` keeps the origin/userinfo checks; the widened `samePage` accepts `/repositories/<digits>/issues` from GitHub's `Link` header, but only the allow-listed page parameters are extracted and re-applied to the base `/repos/{owner}/{repo}/issues` URL, so a link naming another repository id cannot redirect the next request.
- **Trust of the remote-derived owner/repo**: the remote is the user's own project git config, read with `execFile` (no shell) under `reviewGitEnvironment` (GitHub credentials and git-discovery overrides stripped); remote URLs are never returned or logged (only owner/name). A remote pointing at a hostile repo yields only a read-only GET of that repo's issues with the user's token; issue titles render as JSX text (wave-1 verified). No reachable impact.
- **`_keryx/session_flags` subject input** (server.ts `handleSessionFlags`): the wire accepts object/null/omitted; the store (`updateSessionFlagsAt` -> `parseSessionSubject`) rebuilds a fresh object from five named fields only (no prototype pollution, no extra keys persisted), enforces `REPO_REF` (owner charset without dots; name not `.`/`..`), safe positive integer, `SUBJECT_URL` anchored to `https://github.com/` with kind/repo/number cross-checked, and `NODE_ID` for repositoryId. The refusal message echoes at most 300 chars of the caller's own subject back to the same local caller only.
- **flags.json writes**: `writeFlags` keeps `writeOwnerOnlyFileAtomic`; the `dir` comes from `locate` (exact session id lookup) or, for the issue binder, from `sessionDir(root, launch.sessionId)` of a binder-generated UUID; `readSessionFlags` drops an invalid stored subject (test covers it). No path is built from subject fields.
- **Issue binding** (issue-session.ts `bindIssueSubject`): runs only after the remote issue and viewer were verified (function contract, unchanged), inside the binding file lock, and stores a subject only when `parseSessionSubject` accepts it (GHE issues get none). The private `issue-link.json` marker stays the authority.
- **Desktop wiring** (slice-03): `PendingSubjects.write` sends `{ sessionId, cwd, subject }` over the existing ACP client; no new sink, no HTML, no external open; titleLinks are React nodes.
- Secrets/crypto/command injection: no token logging, `Math.random`, `eval`, or shell-string exec in either slice; test fixtures use `execFileSync` with argument arrays.

### Not in this lens
- `updateSessionFlagsAt` called from `bindIssueSubject` and `setSessionFlags` are read-modify-write without a flags-file lock (pre-existing for setSessionFlags). A concurrent write could lose a flag; that is a logic/concurrency question, not a security one, and was not rated here.
