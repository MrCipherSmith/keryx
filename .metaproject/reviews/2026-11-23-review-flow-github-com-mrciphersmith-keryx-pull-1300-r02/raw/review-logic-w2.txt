### [LG-011] A Subject open prefills the shown composer, which may be a session the user switched to while `session/new` was in flight
- Severity: minor
- File: apps/desktop/src/review/prWork.ts (`openSubjectSession`), with App.tsx `createPrFlow`
- Problem: `openSubjectSession` awaits `deps.newSession()`, then calls `deps.fill(prompt)`. `fill` is App's `fillComposer`, and `fillComposer` calls `composer.current?.setText(text)`, the composer of whichever session is shown at that moment. `openNew` (useAcpSession.ts) adds the new session without showing it when the user switched elsewhere meanwhile ("shown unless the user switched elsewhere"), and it still returns the id. In that case `bind` correctly binds the new, hidden session, but the text goes to the session the user switched to. For "Create Flow", `createPrFlow` then calls `flowLinks.expect(id, known)` on the hidden session, while the flow prompt sits in the other session's composer.
- Impact: Trigger: press "Open in session" or "Create Flow" on a PR with no bound session, then pick another session in the sidebar before `session/new` answers. Outcome: that session's draft is replaced by the PR URL or the flow prompt, because `setText` replaces the draft. If the user sends the flow prompt there, the one package it creates within 15 minutes is linked by `linkFlow` to the hidden, empty bound session. The PR card then shows that Flow, but the session that did the work is not linked to it. The window is the `session/new` latency, so the trigger is narrow.
- Suggested fix: fill only when the new session is the one shown. For example, `openSubjectSession` could take `isShown(id)` from deps and skip `fill`, and App skip `expect`, when it is false. Or keep the prompt as a per-session pending draft that is applied when that session is shown.
- Evidence: prWork.ts `const id = await deps.newSession(); if (!id) return null; deps.bind(id, subject); deps.fill(prompt);`. App.tsx:352 `const fillComposer = useCallback((text: string) => { setView("session"); requestAnimationFrame(() => composer.current?.setText(text)); }, []);`. useAcpSession.ts `openNew` doc: "The new session is added and shown unless the user switched elsewhere meanwhile", `const show = l.reg.created(r.sessionId, intent); ... return r.sessionId;`.
- Class scope: the same shape also exists in two base callers outside this diff. App.tsx `openSessionWith` (`const id = flow ? await s.workOnFlow(flow.dir, "new") : await s.newSession(); if (id) fillComposer(reference);`) and `workOn` (`const id = await s.workOnFlow(card.dir, target); if (id && target === "new") fillComposer(workPrompt(card));`). They are pre-existing and listed for the fix's scope only. Enumerated by reading every `fillComposer` and `fill:` caller in App.tsx and every `deps.fill` in prWork.ts.

### [LG-012] The Issue work row counts bound sessions by `subject`, which keryx writes only when a binding is first created
- Severity: minor
- File: apps/desktop/src/issues/IssueWorkRow.tsx
- Problem: `IssueWorkRow` labels its session slot from `issueSessions(sessions, issue)`, which counts sessions whose `flags.json` `subject` names the issue. keryx writes that subject only inside `withIssueBinding`'s `launch.stage === "registered"` branch (src/session/issues/issue-session.ts `bindIssueSubject`), so only when a binding is first made. The click (`open-session`) goes through the private per-account binding record instead. The count and the action read different sources, and they disagree in two cases:
  - An issue whose session was bound before this version has no `subject`, and the reuse path never adds one. The row says "Open in session" in the empty style on every visit, while the click opens the existing session.
  - The private binding is per account (`issueViewerKey`), but the row counts sessions bound under any account. With a second GitHub account, the row says "Session" and the click creates a new session for the current account.
- Impact: The slot misreports whether the issue already has a session, against AC12 "bound sessions found through `subject`". It does so permanently for every issue bound before the upgrade. No data is lost: the action still opens or creates the right session.
- Suggested fix: in `withIssueBinding`, write the subject on the reuse path too when `readSessionFlags(dir).subject` is absent. Mind the comment that an unlinked subject is not written back: that needs a marker, or writing only when the flags never held a subject. Or count, in the row, only the sessions of the current viewer's binding.
- Evidence: issue-session.ts `if (launch.stage === "registered") { ... bindIssueSubject(dir, issue.ref); launch.stage = "session_bound"; }`, with no other `bindIssueSubject` call. The doc on it says "Written once, when the session is bound". IssueWorkRow.tsx `const bound = issueSessions(sessions, issue).length;` and `onClick={() => onAction("open-session")}`.
