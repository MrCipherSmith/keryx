### Summary
The subject store is sound. `parseSessionSubject` checks kind, the `owner/name` charset (no `.`/`..`), a positive safe-integer number and a `https://github.com/<repo>/pull|issues/<n>` URL that agrees with all three. The store checks on both write and read, an invalid subject is refused without touching the stored one, `null` unlinks it, and `writeFlags` persists it. The ACP handler rejects a non-object and leaves field checks to the store. The issue binding writes `kind: "issue"` through `updateSessionFlagsAt` while it holds the binding lock. The Desktop wiring writes one flag at a time at turn end (flow, then subject), and `applyPendingFlow` never rejects, so `subjects.apply` always runs. The repository listing validates first and resolves the repo from the cwd. It omits `filter`/`pulls` for `/repos/{o}/{r}/issues`, drops PR rows, and scopes the cursor to the lowercased repository. It accepts GitHub's `/repositories/{id}/issues` next links but carries only the page keys, so the request path always comes from the cwd. Only `src/commands/issues.ts` calls `listIssuePage` in production, and it passes `cwd`. One new minor finding: a default "repository" source whose first remote has Issues disabled, which is the default for a fork.

### Error Handling

#### [LG-013] The default "repository" Issues source fails with "unexpected response, refresh and retry" in a fork checkout, because the origin fork has Issues disabled
- **Severity**: minor
- **File**: src/integrations/issues-board.ts (`projectRepository`), with src/integrations/issues-github.ts `failure`
- **Problem**: `projectRepository` takes `selectRepository(await reviewRepositories(cwd))` with no requested repo. `configuredRepositories` puts `origin` first, so the source always lists origin's issues, and Issues has no repository choice the way the PR board does. In the common fork workflow (origin = the user's fork, upstream = the real repo), origin is a fork. GitHub disables Issues on forks by default and answers `GET /repos/{o}/{r}/issues` with **410 Gone**. `failure()` maps 401/404/403 to `denied` and 429 to rate-limit, and turns every other status, 410 included, into `"unavailable: GitHub returned an unexpected Issues response. Refresh and retry."`.
- **Why it matters**: Trigger: first visit to Issues, with no stored source, in a fork checkout or any project whose first GitHub remote has Issues turned off. Outcome: D5 makes "repository" the default, so the board opens on an error that tells the user to refresh. Refreshing fails the same way every time. The upstream repository's issues, which the project actually tracks, cannot be selected as this source. Workaround: switch the Source select to "Assigned to me". This is distinct from UX-008, which covers a project with no GitHub.com remote at all (a `configuration:` error). Here the remote exists and the request reaches GitHub.
- **Fix**: Map 410 to a clear configuration error, e.g. `configuration: Issues are disabled for <owner>/<repo>. Choose another source.`. Then either prefer the PR board's selected repository when the project has one, or try the next configured remote (e.g. `upstream`) whose Issues are enabled. Add a test where the REST call answers 410 and assert the configuration-kind message.
- **Evidence**: issues-board.ts `const repository = selectRepository(await reviewRepositories(cwd));`. board-github.ts `configuredRepositories`: `return [...new Set([...(origin ? [origin] : []), ...choices.values()])];` and `selectRepository`: `if (!requested) return repositories[0]!;`. issues-github.ts `failure`: only 401/404/429/403 are special-cased, and the rest falls through to `invalidResponse` ("Refresh and retry"). The GitHub REST behaviour (410 when Issues are disabled, and forks have Issues off by default) is platform documentation, not observed in this run. No test in issues-board.test.ts covers a non-200 response on the repository source.
- **Class scope**: sites `src/integrations/issues-board.ts projectRepository` (repo choice) and `src/integrations/issues-github.ts failure` (410 mapping). Enumeration: `keryx ctx rg "listIssuePage\("` shows one production caller (src/commands/issues.ts). `keryx ctx rg "status ===" src/integrations/issues-github.ts` shows the complete status mapping, with no 410 branch.

### Edge Cases

#### [LG-014] An older keryx that writes the same flags.json drops `subject`
- **Severity**: info
- **File**: src/session/organize.ts (`writeFlags`)
- **Problem**: The new `writeFlags` persists `subject`. A keryx from before this change rewrites flags.json with only `{archivedAt, pinnedAt, flow}`. Any archive, pin or flow-link it performs on a bound session therefore silently unbinds that session.
- **Why it matters**: It is reached only when two keryx versions share one data dir. That can happen, for example, when a stale installed `keryx` (memory constraint `stale-installed-keryx-binary`) serves `keryx shell` while Desktop runs a newer one. I did not show that Desktop and the shell ever use different builds on the same store, so this is an observation.
- **Fix**: Optional: note the downgrade limit in the stage-1 section of implementation-plan.md, or have future `writeFlags` versions preserve unknown keys.
