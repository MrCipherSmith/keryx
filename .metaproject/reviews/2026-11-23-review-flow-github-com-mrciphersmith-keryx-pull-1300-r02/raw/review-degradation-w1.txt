## New findings (3, all minor)

### [DG-006] A pending publication on a merged or closed PR now gets the warn "waits on you" tone
- Severity: minor · Class: behaviour-delta · Evidence kind: base-diff
- File: apps/desktop/src/review/PrWorkRow.tsx
- Problem: On base, the card's publication cue showed only on open PRs: `{card.state === "open" && card.localReview?.publicationPending && <span ...>Action required</span>}` in ReviewTags, and `card.state === "open" && ...publicationPending ? "Review publication"` in ReviewAction. The head drops that guard. `waitsOnViewer` adds `is-attention` (warn colour, warn border) for `publicationPending` whatever `card.state` is, and `reviewSlotState` returns "publication pending" before it looks at anything else. `localBadge` (src/review/board-badges.ts:49) sets `publicationPending` from the run alone, with no PR-state check, so a run left at publication "pending" before the merge keeps it. `needsViewerAttention` (model.ts) still requires `c.state === "open"`. The board therefore shows "waits on you" on a merged card that the tab indicator does not count.
- Refute: I read board-badges.ts:49 (no state gate), model.ts `needsViewerAttention` (gated on open) and the base ReviewTags and ReviewAction in the slice (both gated on open). Neither the PR body nor a code comment gives a reason to show the cue on non-open PRs.
- Fix: gate the attention tone, and the "publication pending" word, on `card.state === "open"` as base did. Otherwise fall through to the run state.

### [DG-007] The fix removed a running review's "Transcript updated …" stamp from the board, but the board still re-renders when it changes
- Severity: minor · Class: behaviour-delta · Evidence kind: base-diff
- File: apps/desktop/src/review/ReviewProgress.tsx
- Problem: Base `CardReviewProgress` rendered `<TranscriptUpdate at={badge?.lastActivityAt} />` for a running review not awaiting an answer, so a stalled run could be seen from the card. Fix a34d8961b replaced it with `reviewProgressText`, which builds the slot title from wave, percent, state and label and never reads `lastActivityAt`. The stamp now appears nowhere on the board, title included. ReviewRuns.tsx:133 shows it only in the panel, from the run and not from the card badge. Yet `badgesEqual` (ReviewBoard.tsx:75) still treats a `lastActivityAt` change as a badge change. Each poll that moves only that timestamp replaces the snapshot and re-renders the memoised ReviewResults and every work row, for a value nothing on the board shows. rg over the non-test code finds that comparison as the only reader of `card.localReview.lastActivityAt`.
- Refute: the ReviewProgress doc comment explains why the progress block left the card body: AC4, and the fixed row height. That reason covers the block, not a text stamp in the slot title, and it does not explain why the change-tracking stayed.
- Fix: either append the relative "updated …" time to `reviewProgressText` for running reviews, or drop `lastActivityAt` from `badgesEqual`. Not both: keep the comparison only if the board shows the value.

### [DG-008] Two pending "Create Flow" requests link nothing, and the description says otherwise
- Severity: minor · Class: diff-vs-description · Evidence kind: consumer-trace
- File: apps/desktop/src/review/prWork.ts
- Problem: The PR body says the single new flow package that appears while a request is pending gets linked to that request's session. AC9 says "the first new flow package that appears while that request is pending is linked to the session". In the fix, `resolveFlowLinks` links only when `live.length === 1`. With two live requests, the first fresh package ends every request unlinked (`return { pending: [], links: ... }`). Trace: App `createPrFlow` → `flowLinks.expect(id, known)` for PR A, then again for PR B within 15 minutes → session A's turn creates its package → the effect runs `resolveFlowLinks` → `only` is undefined → no link, and both requests are dropped, so B's own later package is not linked either. The code comment states the reason (which package belongs to which request cannot be told), and the reason holds. The PR description and its Known gaps do not mention it.
- Refute: the PR body's Known gaps lists only "A Flow created outside the pending window is not linked". The fixture test "two link none" covers two packages, not two requests.
- Fix: add to Known gaps: "With two or more Create Flow requests pending, none is linked automatically." Or keep the other requests pending instead of ending all of them.
