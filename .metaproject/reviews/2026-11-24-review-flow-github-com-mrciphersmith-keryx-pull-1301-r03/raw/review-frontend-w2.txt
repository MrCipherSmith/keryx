### [F-001] `reload` is optional, so a caller that omits it gets the round-3 dead `Loading…` state back
- Severity: minor
- File: apps/desktop/src/metaproject/useMetaprojectTree.ts (`reload?: unknown;`)
- Rule: TypeScript safety / canonical rubric (no row; the defect is reachable only by a future caller)
- Problem: The fix parks a stale-snapshot read as `status: "stale"` (or `more: { status: "stale" }`), and the only thing that ever moves it out of that state is a change of `reload` (the useEffect comparing `loadedCatalog.current` to `reload`). `reload` is declared optional. A caller that leaves it out (it stays `undefined`, never changes) has no way out of a parked row: `ensure` skips it (folder present), `more` refuses it (`more` set and not failed), `retry` acts only on `failed`. That is exactly the dead state r3-regression-w1-F-001 described. Today the one production caller (MetaprojectView.tsx) passes `reload: catalog`; the DOM-test Harness in MetaprojectTree.dom.test.tsx omits it, so the tree-level tests run the hook in the configuration that cannot recover.
- Impact: No user-visible defect at this head. The type does not encode the contract the fix depends on, so a second consumer (or a refactor of the view's call) can silently reintroduce the permanent Loading row with no type error.
- Suggested fix: Make `reload` required (`reload: unknown`, documented as "pass the catalog object"), and pass a value from the test Harness (e.g. a `reload` prop defaulting to a constant). Alternatively keep it optional but, when it is `undefined`, fall back to treating `stale` like `failed` (show Retry) so the hook never has a state with no exit.
- Evidence: useMetaprojectTree.ts: `reload?: unknown;` in the hook's input type; the effect `if (loadedCatalog.current === reload) return;` is the sole caller of `reread(scope, parent, "stale")`. Callers enumerated with `keryx ctx rg 'useMetaprojectTree\(|useTree\('`-shaped reading of the slices: MetaprojectView.tsx (passes `reload: catalog`) and the Harness in MetaprojectTree.dom.test.tsx (`useTree({ cwd, snapshot, request, onStale, ...wait })`, no reload).
- Confidence: high

### [F-002] Hand-off rows kept in a ref written during render
- Severity: info
- File: apps/desktop/src/metaproject/MetaprojectTree.tsx (`shown.current = rows;`)
- Problem: The delta adds `shown` and assigns `shown.current = rows` in the render body; `remember()` (called from the blur microtask and the layout effect) computes `handOff(shown.current, index)` from it. React's guidance is not to write refs during render: under concurrent rendering a render that is discarded still leaves its rows in the ref, so a blur microtask in that window computes the anchor over rows that never committed. The hook already uses the same pattern (`latest.current = …`), and this Desktop tree is not rendered in a transition, so no concrete failure is reachable today.
- Impact: Observation only; no bug at this head.
- Suggested fix: If it is touched again, assign `shown.current = rows` inside the existing `useLayoutEffect` (before `remember(document.activeElement)`), which runs only for committed renders.
- Evidence: MetaprojectTree.tsx render body: `const shown = useRef(rows); shown.current = rows;`; `remember()` reads `shown.current`.
- Confidence: medium
