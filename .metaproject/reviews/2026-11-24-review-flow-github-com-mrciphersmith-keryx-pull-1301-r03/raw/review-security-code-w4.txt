No security finding in this delta. The changes are client-side state handling (a `stale` folder/page status parked until the next catalog load, a hand-off anchor for focus, a module-level `withPermitRetry`, and a permit-refusal classifier moved to the platform transport). None of them builds a query, shell command, path or HTML from untrusted input, handles credentials, or widens what the Tauri command accepts.

Points checked:
- `isMetaprojectPermitRefusal` (platform/metaproject.ts:284-286) classifies by prefix only for errors that are not `MetaprojectRequestError`, so a typed CLI error carrying the same text is not treated as a permit refusal (covered by the new platform test). The worst a spoofed message could do is cause at most 2 bounded, jittered retries per read; no privilege or data impact.
- `withPermitRetry` (useMetaprojectTree.ts:29-40): bounded at PERMIT_RETRIES = 2, checks `live()` before and after the wait, so a retired snapshot's `expectedSnapshotId` is not re-sent. `Math.random()` is used only for back-off jitter, not for a token or nonce.
- The `reload` re-read (useMetaprojectTree.ts, the `loadedCatalog` effect) fires only when the catalog object changes. MetaprojectView.tsx:410-414 returns before `setCatalog` on a quiet read with an unchanged snapshotId, so a quiet poll does not re-send parked reads and `onStale` (which only sets `snapshotMismatch`) does not start a catalog read. There is no unbounded request loop. Re-reads still go through the 3-slot limiter.
- Rendering: error messages and entry names are rendered as React text (`{row.message}`, no `dangerouslySetInnerHTML`). The delta adds no new sink.
- Bookkeeping files: no secrets, tokens or personal data beyond the owner handle already recorded in flow.json.
