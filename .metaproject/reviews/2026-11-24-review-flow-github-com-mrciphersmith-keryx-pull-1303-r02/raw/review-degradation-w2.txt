### [F-001] A newer partial attempt hides an older complete attempt as the previous round, with no fallback when it cannot be handed on

- **Severity**: minor
- **Class**: behaviour-delta
- **Evidence kind**: base-diff
- **File**: src/review/desk-run-service.ts:385
- **Problem**: Base picked `store.history(key).runs.find(...)`: the newest attempt that was completed, had complete coverage and the same options key, so a later partial attempt was skipped and an older complete one was used. Head calls `previousRoundAttempt` -> `selectPriorAttempt` (update-round.ts:15-25), which returns the FIRST attempt (newest first) of an earlier round that is completed or partial with `findingsKnown === true`. Two cases are now worse than base. (a) An earlier round holds a complete attempt A and a later partial retry B of the same range (same round, store.ts roundFor `retry`). B wins. B was itself started with A excluded as same-round (previousRoundAttempt filters `item.round < current.round`), so A's open findings are not in B's package. The update round builds on B as a weak partial delta: A's open findings are not carried and everything outside the delta is planned as new. (b) The chosen partial attempt has `findingsKnown` true but no ingested findings.json list. desk-run-service.ts:87 sets findingsKnown from summary counts alone (`Object.values(out.findings).some(count => count > 0)`). recordPartialRound returns `skipped` (round-registry.ts:263), `handOn` is false (desk-run-executor.ts:528-530), and nothing is copied. selectPriorAttempt has already returned, so no older usable attempt is tried, and the round runs as a first full review with no prior findings. In the same store, base would have handed on the older complete attempt when its options key matched.
- **Why it matters**: The update round loses the earlier complete round's open findings from its carry-forward table and costs a full or near-full review where base ran a delta. Because the code is reviewed again in full, no defect goes unreviewed, so this is cost and lost carried status, not a wrong verdict. Spec "Раунд обновления" item 1 says the previous round is "the last round with accepted findings, including partial". A partial package with no ingested findings does not meet "accepted findings", so case (b) contradicts the spec. Case (a) is not settled by the spec, which talks about rounds, not attempts within a round.
- **Fix**: In selectPriorAttempt or previousRoundAttempt, prefer a completed attempt with complete coverage over a partial one within the same round. Then, when the executor cannot hand on the chosen attempt (draft and not recordable, or draft from a completed attempt), fall back to the next candidate, for example by passing the ordered candidate list to the executor rather than one directory. At minimum, exclude a partial attempt whose package has no findings.json list from selection, so it never shadows a usable attempt.
