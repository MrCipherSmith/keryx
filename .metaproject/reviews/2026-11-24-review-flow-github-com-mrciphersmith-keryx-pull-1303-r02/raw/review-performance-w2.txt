### Findings

### [F-001] A compare result of "not ahead" is not cached, so every dialog preview on a diverged or older head spawns another `gh api compare`
- **Severity**: minor
- **File**: src/review/desk-publication.ts (`reviewedHeadInPull`, slice-02 lines 115-128)
- **Hot path**: Every `preview` request from the publish dialog. The dialog sends one per settings change or answer click. The cost applies only while the PR head has moved and GitHub reports it `diverged` or `behind`: a force-push or rebase, which is a common state for a PR.
- **Problem**: `reviewedHeadInPull` caches only the positive result (`cache.aheadHead = currentHead`). A definitive `diverged` or `behind` status for the same (reviewedHead, currentHead) pair is not recorded. `previewSubject` returns the persisted cache within the 15 s TTL without a subject read (bound account), but the compare call still runs again on every preview. The test fixture shows this: in "a head that no longer contains the reviewed commit keeps the refusal…", every one of the four previews reaches the compare stub. Before this PR, a moved head ended the request with a local `blockedReason` and made no network call.
- **Why it matters**: Each preview in that state pays one `gh` process spawn plus a GitHub round trip (typically several hundred ms). The answer cannot change while the current head stays the same, and the dialog stays blocked ("revision moved") either way. The cost is dialog latency and API quota. The result is still correct, so this is minor.
- **Fix**: Record a definitive non-ahead status per current head, for example `cache.notAheadHead = currentHead` when `status` is `diverged`, `behind` or `identical`, and return false early when it matches. Keep the `catch` path (a failed or transient read) uncached, so fail-closed still asks again on the next preview, as the docstring promises.

### Clean Areas
- **Compare and discussion reads on the ahead path.** `aheadHead` is stored on the cache object, and the preview write persists it at desk-publication.ts:263-266. `previewSubject` carries it forward with `{ ...previous, subject }` while base and head are unchanged, so an ahead head is compared once per head (re-asked at most once per 15 s TTL expiry). The discussion re-read is newly reachable with `current || headMoved` at slice-02 line 239. It is required for the as-is variant and is cached in `cache.discussion` the same way. `save` and `submit` re-read on purpose, as a freshness check.
- **Automatic publication.** It is refused before any compare or discussion read (desk-publication.ts:385). The new test at slice-02 lines 1648-1656 asserts zero reads.
- **`prior-round.ts` registry read.** `readRoundRegistryReport(repoIdentity(cwd))` was moved earlier in `findPreviousRound`, but it is still read once per call, so there is no added spawn. `localPackageCandidates` now calls `partialRoundVouch` per non-eligible package, and `packageTrust` filters the registry per candidate. Each pass is O(registry entries). The registry is compacted at 512 KiB, and this runs once per review start, not on a hot path, so I have no finding. Hoisting the `desk-partial` filter out of the loop would be a micro-optimisation.
- **`recordPartialRound` (round-registry.ts).** It runs once per attempt start that hands on a partial package: `packageFacts`, one findings read and parse, two `git` spawnSync in `repoIdentity`, and one append. Retries of the same round can append duplicate `desk-partial` entries for one package. Compaction keeps the newest entry per package, so growth is bounded.
- **`desk-run-executor.ts` hand-on.** It runs one `cp` of the previous package per attempt start, as before, now also for a vouched partial package. It is not a hot path.
- **`previousRoundAttempt` and `selectPriorAttempt`.** These are one linear filter and scan over `store.history(key).runs`, once per worker start. They replace the earlier `.find`, with the same complexity.
- **`head-move.ts`.** Pure constant-time functions.
- **`prepare` settings and digest.** Pure in-memory work, with no new I/O beyond what is noted above.
- **Not in this slice's runtime surface.** N+1, indexes, pagination (the compare call uses `per_page=1`), React re-renders, bundle imports, and leaked timers or listeners: nothing new. The test files add fixtures only.
