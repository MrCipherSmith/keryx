Concurrency & Races
### [F-001] "Update review" is silently dropped while another panel mutation is in flight
- Severity: minor
- File: apps/desktop/src/review/ReviewWorkspace.tsx
- Pattern: Concurrency A — in-flight request gate drops a mutation with no outcome
- Failure mode: Trigger: the user presses "Update review to <sha>" while the same panel's useReviewRuns still has a non-status mutation pending, for example a cancel, an answer or a start issued just before the dialog opened. ReviewRuns has already closed the dialog (`setPublishOpen(false)`). Then useReviewRuns.request hits `if (pending.current && (action.kind === "status" || pending.current !== "status")) return;` and resolves without starting, without an actionError and without a toast. The `.then` in updateReview still runs, so a board-behind case also calls onRefreshBoard. The user sees the dialog close and no new round. Nothing is duplicated or corrupted. The intent is lost with no signal.
- Fix: Disable the dialog's Update button while the panel is `working`. Pass `working` into the publication target, or use the hook's working state in ReviewRuns. Or have request return a boolean "accepted" so that updateReview can toast "Another review action is still running" when the start was not sent. Call onRefreshBoard only when the start was accepted and succeeded.

Resources — None detected. The slice adds no connection, file handle, timer or long-lived listener. The dialog's useId and useCallback additions are per mount.
Caching — None detected. The dialog uses `headMoved.currentHead` from the last preview. If the head moved again after that preview, the Update start names a superseded head. The backend start re-validates the range (verifyDeskSubject at run start) and refuses it, and the error surfaces as the panel's start actionError. That fails safe.
Lock Contention — Not relevant. The slice holds no lock and no transaction.
Async / Queues — None detected. The backend supersedes a queued attempt for a different range ("A newer review request superseded this one."), so Update presses do not grow a queue.

Idempotency & Distributed Invariants
### [F-002] Client "already has an attempt" guard is skipped for a board behind the push. The store's same-range dedupe covers it.
- Severity: info
- File: apps/desktop/src/review/ReviewWorkspace.tsx
- Pattern: Idempotency G — client-side check-then-act backed by a server dedupe
- Failure mode: None today. With a board behind the push, `action.open` describes the old range, so the client guard is skipped and a start goes out for the current head. If that head already has an active, queued or complete-completed attempt with matching options, requestAttempt returns its id (`reused: true`) and starts nothing. Only an attempt with different options, such as a rule-created `follow` run, or a partial or failed one, gets a new manual attempt. That is the existing contract for an explicit manual request. Recorded so that a future change to the store's matching does not remove the only real guard.
- Fix: No change required. Optionally, add a backend test that a manual start on a range with an active scheduled attempt of other options either reuses that attempt or is intended to queue behind it.
