## Findings

### [F-001] The update handler's `setPublishOpen(false)` is unpinned; the "dialog closed" assertions ride a remount
- Severity: minor
- File: apps/desktop/src/review/ReviewRuns.tsx:179
- Problem: Deleting `setPublishOpen(false)` (R2) leaves all 142 Desktop review tests green. The three Update-review tests assert `document.querySelector(".dialog")` is null only after `await click(...)` has flushed the start request; by then the article was replaced (new attempt becomes latest) or unmounted (`setSessionId(null)`, W1 red), so the assertion proves the remount, not that the handler closes the dialog.
- Impact: Without the call, the publish dialog stays open (with "Publish as is" clickable) for as long as the start request is in flight, and permanently when the reviewed attempt stays the rendered one. No test would catch that regression.
- Fix: In "Update review in a head-moved dialog starts the next round...", make the fixture's `start` return a held promise; click "Update review to ccccccc"; assert the dialog is gone before resolving it, then resolve and keep the existing assertions.

### [F-002] The Update review button's `disabled={writing}` is unpinned
- Severity: minor
- File: apps/desktop/src/review/ReviewPublishDialog.tsx:159
- Problem: `disabled={writing}` -> `disabled={false}` (P11) is green in both suites. No test holds a submit/save/skip request open while the head-moved dialog shows the Update review button.
- Impact: If the guard is lost, a user can start an update round while "Publish as is" is posting, then the dialog closes mid-write (via the ReviewRuns handler) and the write result arrives at an unmounted dialog. That regression would be silent.
- Fix: In "a moved head locks the dialog...", have `command` hold the `submit` request on a deferred promise; click "Publish as is for bbbbbbb" and assert `btn("Update review to ccccccc").disabled === true` before resolving.

### [F-003] The primary-action swap (Update primary, Publish as is secondary) is unpinned
- Severity: minor
- File: apps/desktop/src/review/ReviewPublishDialog.tsx:154,167
- Problem: The diff added `className={updateOffered ? "btn" : "btn btn-primary"}` (T13 decision: "Update is the primary button when offered; Publish as is becomes secondary"). Forcing it to `"btn btn-primary"` (P5) is green. So are P1 (drop `!!headMoved`) and P3 (drop `!!onUpdateReview`) from `updateOffered`, because the only other consumer of `updateOffered` is the button JSX, which re-checks both values. P1 would demote "Submit review" on every current-head dialog, and P3 would demote "Publish as is" when no caller offers an update. The tests assert the Update button's position ("first footer button"), not which button is primary.
- Impact: This is styling, kind presentation. The spec's "update is the primary action" and the current-head dialog being "unchanged" (AC3) can regress without any test failing.
- Fix: In "a moved head locks the dialog..." assert `btn("Publish as is for bbbbbbb").classList.contains("btn-primary") === false` and the Update button has `btn-primary`. In "the current head keeps the dialog's verdict choice and Submit review", mount through the workspace (which passes `onUpdateReview`) and assert `btn("Submit review").classList.contains("btn-primary")`. In the directly-mounted head-moved case without `onUpdateReview`, assert "Publish as is" stays primary.
