When a caller provides it, "Update review to <sha>" is the primary action and "Publish as is" is the secondary one. Update is hidden once the review is published.

### Logic Bugs
[F-002] (minor, confidence medium) The "already has an attempt" guard in `updateReview` covers only an active attempt or a complete one.
- File: apps/desktop/src/review/ReviewWorkspace.tsx (`updateReview`)
- Problem: the comment says "The board's current range already has an attempt: the panel shows it, and a second one is not started". The guard is `if (!boardBehind && action.open) return;`.
  - `launchAction` sets `open` only for an active attempt, or for a completed attempt with `coverage === "complete"` on the card's range.
  - If the current head's attempt is `partial`, `failed`, `cancelled` or `budget`, Update starts another attempt. For a `partial` attempt, the backend `requestAttempt` does not reuse it: it reuses only an active or queued attempt, or a completed and complete one. So a new attempt really is started.
  - When `boardBehind` is true, the guard is skipped entirely. If the current head already has an attempt with other options, for example one started by a rule, a second attempt is started.
- Trigger: the current head `c` has a partial attempt. The user opens the earlier attempt `b` from History, opens Publish to GitHub (head moved), and clicks "Update review to c". A new attempt on `c` starts and spends tokens. The code comment and the test name ("does not start a second attempt when the current head already has one") say this does not happen.
- Fix: use one of two approaches.
  - Base the guard on the runs, not the card: `if (local.runs.some(r => r.source !== "existing" && !reviewIsArchived(r) && sameRange(r, revision))) return;`. Optionally select that attempt with `setSessionId`.
  - Alternatively, narrow the comment and the test name to "an active or complete attempt", so the retry behaviour is a stated decision.

### Async & Concurrency
[F-003] (info) Update review can be dropped silently, and the board refresh runs anyway.
- File: apps/desktop/src/review/ReviewWorkspace.tsx (`updateReview`) with apps/desktop/src/review/useReviewRuns.ts:32
- Problem: `request` returns early without error when another mutation is pending (`pending.current !== "status"`). The dialog's Update button is disabled only by the dialog's own `writing` state, not by `local.working`. When an answer or cancel request is in flight, clicking Update closes the dialog and starts nothing, with no message. The `.then(() => onRefreshBoard?.())` also runs after a dropped or failed start.
- Fix: pass `local.working` into the dialog so it disables Update while a mutation is pending. Alternatively, have `updateReview` refuse with a toast when `local.working` is true.
