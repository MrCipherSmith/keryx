The new client path in this slice is the "Update review" action (T13). I traced its one input that comes from outside the webview: `headMoved.currentHead` from the publication preview becomes the `headSha` of a `start` request. That request goes through `requestDeskRun`, which calls `verifyDeskSubject(cwd, key, revision)` before admitting the run (`desk-run-service.ts:258`): the viewer, the repository id, `state === "OPEN"`, and the exact base and head against a fresh GitHub read. A forged or stale `currentHead` is therefore refused with `stale:` and starts nothing. The copied `reviewed.options` are re-parsed by `parseDeskReviewOptions` (`desk-run-service.ts:272`), which allowlists fields and model names, so the update path widens no input. The dialog renders both SHAs as React text and `title` attributes, which React escapes. The publish-as-is write path is in slice-02 and was settled in round 1. Round 1 found no security defect to re-check in this slice.

### Findings

### [F-001] "Update review" silently carries automatic publication into the new round
- **Severity**: minor
- **File**: apps/desktop/src/review/ReviewWorkspace.tsx (`updateReview`)
- **Attack vector**: none. No attacker is involved. This is an operator-consent observation about an outbound GitHub write.
- **Problem**: `updateReview` starts the next round with `reviewed.options` copied verbatim, and it does not open the launch form (the PR body records that decision). `DeskReviewOptions.autoPublish` is one of those options. The trigger is an attempt launched with **Publish to GitHub automatically**. If its head moves, automatic publication refuses, so the attempt waits in the publish dialog. One click on "Update review to <sha>" then starts a round that posts to GitHub on its own after full coverage. Nothing in the dialog or the button says the new round will auto-publish.
- **Why it matters**: the outcome is a GitHub review posted under the user's account that the user did not re-confirm for the new head. The user did choose auto-publish for the earlier attempt, so this is not a wrong write. It is a consent gap on the one-click path, which is why it is rated minor and not major. The overlay-approval gate still applies when the project requires it.
- **Fix**: either drop `autoPublish` from the copied options, so the update round waits for a publish decision, or state it in the head-moved notice or the button text (for example "Update review to <sha> (publishes automatically)").
- **Patch** (one option):
```diff
- void local.request({ kind: "start", ...revision, ...(reviewed.options && { options: reviewed.options }) })
+ const { autoPublish: _auto, ...carried } = reviewed.options ?? {};
+ void local.request({ kind: "start", ...revision, ...(reviewed.options && { options: carried as DeskReviewOptions }) })
```

There is no `dangerouslySetInnerHTML`, no `eval`, and no new shell or query construction. The preview body still renders through the existing `ReviewReportMarkdown`.
- **Auth/authz/IDOR:** the update start keeps the panel's `subject` key (repo, repositoryId, viewer, number). The backend re-verifies the viewer and the repository id before admitting the run. The PR URL gate on `draft` (`/^https:\/\/github\.com\/[^/]+\/[^/]+\/pull\/[1-9]\d*\/?$/i`) is unchanged.
- **Input validation:** `currentHead` is bound to the live PR head by `verifyDeskSubject`. Options are re-parsed with an allowlist. The update path uses `run.baseSha`, and the backend refuses it if the base moved.
- **Duplicate or unintended writes:** `updateReview` returns without starting when the board's current range already has an open attempt (tested in "does not start a second attempt").
- **Secrets/logging:** nothing new is logged. No credentials are touched.
- **Crypto, CSRF, path traversal, open redirect:** not applicable. No new randomness, endpoints, file paths or navigation targets.
- **Docs change:** it describes behaviour only. No secrets and no unsafe instructions.
