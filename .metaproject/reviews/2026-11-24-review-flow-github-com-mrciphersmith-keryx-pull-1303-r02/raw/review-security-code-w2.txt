### Main question: can data a PR commits narrow a round? No.

The TM-04 rule in the `prior-round.ts` header holds for the new desk-partial path. I checked four things.

1. **Only Desktop writes the record.** A `desk-partial` entry is written only by `recordPartialRound`. Its one caller is `executeDeskReview` (`desk-run-executor.ts`, the `handOn` line), and it reads the package from `options.previousRunDir`. That directory is `store.directory(previous.attempt.id)` in the user's run store (`desk-run-service.ts`). The registry file lives under the user's config directory, outside every checkout. The hashes cover the manifest identity, findings.json and round.json. A PR cannot create a matching entry. The most it can do is commit a byte-identical copy of a package Desktop really ran, and that copy describes a real round.
2. **The review checkout holds no PR files.** The checkout runs `sparse-checkout set --no-cone '!/*'` and then restores only the control paths from the verified default-branch commit (`desk-run-executor.ts:229-241`). `.metaproject/reviews` is not among them. So nothing the PR commits under `.metaproject/reviews/<id>` exists beside the copied package. A planted research.json, published.json or round.json cannot mix with the copy, and a symlinked destination cannot redirect the `cp` there. `localPackageCandidates` sees only what Desktop copied in.
3. **A partial round never narrows coverage.** `weakReasons` adds "not completed" for every candidate whose `completed.ok` is false (`prior-round.ts:740`). For a weak previous round, `findPreviousRound` adds all unchanged merge-base..head code to `newHunks` instead of `secondLookHunks` (`:924-929`). The test at slice line 2099 asserts this. Trusting a partial round therefore changes how hunks are labelled (fix vs new) and which prior findings are carried. It never shrinks what is read.
4. **A partial vouch cannot pass as completion.** `packageTrust` filters `desk-partial` out of the completion vouch (`registry.filter(entry => entry.event !== "desk-partial")`), and `partialRoundVouch` accepts only `desk-partial` entries that have a non-null findings hash. The test at slice line 2138 covers a branch committing the partial files marked `closed`: the result is fallback-first.

The new path reuses one existing rule: the desk-partial branch returns before the git-history merged-base check and the branch-commit check, just as `vouched` already did for finished rounds ("whatever commit carries them"). This is the stated same-user limit and adds no new exposure. If an agent edits the copied package before `review start`, the hashes stop matching, the round falls back to fallback-first, and the system fails closed.

### Findings

### [F-001] `registryVouchesPackage` counts a `desk-partial` entry as a vouch, unlike `packageTrust`
- **Severity**: info
- **File**: src/review/round-registry.ts:193-199 (in the slice's context hunk, unchanged lines whose meaning the new event type changes)
- **Attack vector**: none shown. The upgrade below needs a draft package that has a desk-partial entry and also has completion evidence, and nothing in this range produces that package.
- **Problem**: the new `desk-partial` event is excluded from the completion vouch in `packageTrust` (`prior-round.ts:344`). The registry's other reader, `registryVouchesPackage`, still calls `registryVouches` over all entries. `answerPremiseQuestion` (`premise-question.ts:193`) uses that result to decide whether to re-record the package as `decide-premise`, which is a full-strength event, after a premise answer. `recordFinishedRound` refuses any package without completion evidence (`round-registry.ts:220`), so today a partial package is never upgraded. The two readers still disagree about what a `desk-partial` entry means.
- **Why it matters**: the protection depends on one condition in another function. If `recordFinishedRound`'s completion gate is ever relaxed, a premise answer on a partial package would turn Desktop's weak vouch into a finished-round vouch.
- **Fix**: filter `desk-partial` in `registryVouchesPackage` too, or move the filter into one helper (`completionVouch`) that both readers call.
- **Settles it**: a test that answers a premise on a desk-partial-vouched draft and asserts that no `decide-premise` entry appears.
