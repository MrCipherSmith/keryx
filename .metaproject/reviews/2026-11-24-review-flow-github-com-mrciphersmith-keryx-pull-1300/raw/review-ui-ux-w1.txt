  - Session header to PR: open the bound PR's panel.

## Findings

### [UX-009] The "Link Flow #N?" question names only the number; which Flow it is shows on hover only
- Severity: minor
- Criterion: Nielsen #6 (recognition rather than recall), #1
- File: apps/desktop/src/review/PrWorkRow.tsx (`<span className="pr-work-link pr-work-offer"`)
- Evidence:
  - FlowOffer renders the visible text `Link Flow #${id}?` plus Link and Dismiss buttons.
  - The flow's title, and the fact that it appeared after Create Flow, live only in the `title` of a `<span>`. The span is not focusable, so a keyboard user cannot reach it and a touch user cannot hover it.
  - The Link button's aria-label (`Link Flow #N for #PR`) omits the title.
  - The owner chose the confirm in HL-001 because arrival time cannot tell who made the package (another window, the CLI, the Issues board), so the user needs to tell which Flow it is. In the 1/3-width slot, next to two buttons, the visible "Link Flow #517?" is also the part most likely to truncate (geometry belongs to review-layout).
- Impact:
  - Trigger: every offer.
  - Outcome: the user confirms or dismisses by number only. To check the Flow, they must go to the Flows board. A wrong Link writes the session's `flow` flag to someone else's package.
- Fix:
  - Put the title in the accessible name and in a reachable description. For example, `aria-label={`Link ${name} "${offer.flow.title}"${of}`}`, or `aria-describedby` pointing to a visually hidden span with the title.
  - Or make "Flow #N" in the offer a button that opens the Flow (as the filled slot does), so the user can inspect it before linking.

### [UX-010] Link has no pending or failure state: the offer disappears before the write, and a failed write is silent
- Severity: minor
- Criterion: Nielsen #1 and #9; State: loading and error
- File: apps/desktop/src/review/usePendingFlowLinks.ts (`offersRef.current = offersRef.current.filter(item => item !== offer);`)
- Evidence:
  - `accept` removes the offer from state, then calls `linkRef.current(...)`.
  - App wires that to `acp.current.linkFlow`, which calls `applyPendingFlow` (useAcpSession.ts). On error, `applyPendingFlow` catches and stays quiet ("not stored yet: retried after its turn") and shows no banner. The new flags lock (organize.ts) can throw after waiting 3 s: "the flags of session … are locked by another keryx process; retry".
  - Until the flags dispatch arrives, `flow` is undefined, so the slot falls back to the dashed "Create Flow" action.
  - The package is already claimed, so it is never offered again.
- Impact:
  - Trigger: every Link press shows "Create Flow" for the length of the RPC.
  - On a failed write (lock timeout, a keryx disconnect) the slot stays on "Create Flow" with no message until the session's next turn retries. Pressing Create Flow again then starts a second Flow.
  - The lock text's "retry" points to a control the board no longer shows.
- Fix:
  - Keep the offer in a "Linking…" state (buttons disabled) until `linkFlow` resolves.
  - On failure, restore the offer and show an inline error in the slot or a banner. That needs `linkFlow` to report its result to this caller.

### [UX-011] "Show issues assigned to me" silently changes the source for every project of the account
- Severity: minor
- Criterion: Nielsen #3 (user control) and #4 (a "Show" action that saves a preference)
- File: apps/desktop/src/issues/IssuesBoard.tsx (`const fallback = source === "repository" && !choice.chosen ? () => change("assigned") : undefined;`)
- Evidence:
  - `fallback` calls `change("assigned")`, which runs `save(account + ".source", next)`.
  - `account` is `"keryx.issues." + issueViewerKey(viewer)`. issues-contract.ts defines `issueViewerKey` as `[host, nodeId]`, so the key is per account and does not include the project (cwd).
  - The fallback is offered for project-specific conditions: no GitHub.com remote in this project, Issues turned off on this repository, an older keryx.
- Impact:
  - Trigger: a person with several projects presses the button once, in a project without a GitHub.com remote or with Issues off.
  - Outcome: from then on, every project, including those with a GitHub remote, opens Issues on "Assigned to me" instead of the D5 default "Project repository", with no indication why. The select still recovers it, and no data is lost.
  - The PR body's owner choice says only where the button appears, not that it persists.
- Fix:
  - Switch the source for this board only (`setChoice({ source: "assigned", chosen: false })` without `save`, with a note "Showing issues assigned to you").
  - Or key the stored source by project as well as account. Rename the button if it keeps persisting, for example "Use Assigned to me".

### [UX-012] The offer text takes the work-row button look and its hover state, but does nothing
- Severity: info
- Criterion: Nielsen #4; Slop T3 "hover only where clickable"
- File: apps/desktop/src/styles/review.css (`.pr-work-link.pr-work-offer { display: block; box-sizing: border-box; line-height: 22px; cursor: default; color: var(--fg); border-style: dashed; }`)
- Evidence:
  - The span carries `pr-work-link`, which gives it the bordered and dashed box of the slot's actions (the dashed border matches `.is-empty` "Create Flow").
  - The existing rule `.pr-work-link:hover:not(:disabled)` also matches a span, because a span is never `:disabled`. Hovering changes its background to `--bg-hover`.
  - Clicking it does nothing. `cursor: default` softens the cue but does not remove it.
  - Not observed on a render.
- Impact: the question looks like a third button. A user may click it expecting to open the Flow.
- Fix: give the offer its own class, not `pr-work-link`: no border, or a non-interactive tone. Or exclude it from the hover rule (`.pr-work-link:not(.pr-work-offer):hover`).

### [UX-013] The fallback notice shows the machine prefix "configuration:" verbatim
- Severity: info
- Criterion: Nielsen #2 (the user's language), consistency with the PR board
- File: apps/desktop/src/issues/IssuesBoard.tsx (`<p>{error}</p>`)
- Evidence:
  - The new unavailable branch renders `error` unchanged. All three errors that reach it carry the prefix:
    - "configuration: This project has no GitHub.com fetch remote."
    - "configuration: GitHub has Issues turned off for owner/repo. Choose another source, such as Assigned to me."
    - "configuration: Invalid Issues request."
  - ReviewBoard.tsx removes the same prefixes before showing them: `error.replace(/^(access|configuration|unavailable):\s*/i, "")`.
  - UX-008 noted the prefix as pre-existing elsewhere. This is a new block that repeats it.
- Impact: the first thing a user sees on first visiting the Issues tab is an internal error kind.
- Fix: strip the prefix the way ReviewBoard does, or share one `displayError` helper between both boards.

### [UX-014] The other-repository focus banner states the cause but offers no way to the PR
- Severity: info
- Criterion: Nielsen #9
- File: apps/desktop/src/review/ReviewBoard.tsx (`is not in a repository this board shows`)
- Evidence:
  - The banner reads "`owner/repo#N is not in a repository this board shows (a/b, c/d).`" and has only a Dismiss button.
  - The user arrived by clicking the PR link in the session header. App has `subject.url` there, but the focus request carries only `{repo, number, nonce}`.
  - This is an improvement on base, where the request stayed armed silently. I did not check whether the session header also offers a direct GitHub link.
- Impact: the user's intent, seeing that PR, ends in a dead end inside the app.
- Fix: pass `url` with the focus request and add "Open on GitHub" to the banner.

### [UX-015] The older-keryx hint names a setting that Settings labels differently
- Severity: info
- Criterion: Nielsen #4 and #6
- File: apps/desktop/src/issues/IssuesBoard.tsx (`" If this keryx is older than Desktop, update keryx or choose the bundled CLI in Desktop Settings."`)
- Evidence: SettingsView.tsx labels the option `"Bundled keryx"`. The hint says "the bundled CLI".
- Impact: the user has to map the two names while looking for the option. Minor friction.
- Fix: use the Settings label, "choose Bundled keryx in Settings". A button that opens that Settings tab would be better.

### [UX-016] The offer appears only on the board, while Create Flow moved the user to the session view
- Severity: info
- Criterion: Nielsen #1
- File: apps/desktop/src/review/PrWorkRow.tsx (`const offer = flow ? undefined : work.flowOffer?.(sessions);`)
- Evidence:
  - `openPrSession` calls `setView("session")`. The package is created during the session's turn, so the user is in the session when the offer comes up.
  - The offer renders only in the PR work row. Nothing in the session (header, transcript notice) or in the tab indicator mentions it, and it has no live region.
  - The owner chose the work row as the place for the offer (AC9 re-frozen), so this is filed as info.
- Impact: a user who stays in the session never sees the question. The Flow then stays unlinked, which is safe but easy to miss.
- Fix: also show the question where the user is, for example a notice in the bound session with the same Link and Dismiss. Or mark the PR tab while an offer is pending.
