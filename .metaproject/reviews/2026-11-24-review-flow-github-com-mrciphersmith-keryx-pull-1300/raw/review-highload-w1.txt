### CLI / Multi-Session

**[HL3-001] The flags-lock wait freezes the whole ACP server, not just the write** (minor). File src/session/organize.ts (slice-03).
- Pattern: Part 0 / async-patterns Rule 4: blocking the thread that serves requests.
- Failure mode: `_keryx/session_flags` → setSessionFlags → withFlagsLock → withFileLock spins in `Bun.sleepSync(15)` until it gets the lock. Under the call's options (staleMs 2 s, timeoutMs 3 s) that is up to about 2 s when a writer was killed mid-section and left `flags.json.lock` behind. For example, a Desktop window closed while its server wrote flags, or the issue-workspace child killed. It is the full 3 s, on every write, when the lock cannot be removed. Throughout that wait the ACP server's event loop is stopped. No session/update streaming, no cancel, no permission answer gets through for the running turn. Desktop also writes flags with no user action: PendingSubjects.apply at turn end, and Link on a Flow offer.
- Why minor: the PR body accepts that "flags write may wait up to 3 s for the lock". The code comment's reason, "Synchronous: callers are synchronous, and the section is one read and one atomic write", covers how long a holder keeps the lock. It does not cover how long a waiter blocks after an abandoned lock, and the accepted wording does not say that the server freezes. The trigger needs a kill inside a millisecond section, and the stall is bounded at 3 s.
- Fix: in the ACP server path, wait asynchronously. Either use lib/fs `withFileLock` (async) from an async `setSessionFlags`/`updateSessionFlagsAt`, or try once synchronously and fall back to an async retry loop with `await sleep(15)`. Keep the sync form only for the issue-workspace child.

**[HL3-002] Taking the flags lock recreates a session directory that another process trashed** (minor). File src/session/organize.ts (slice-03).
- Pattern: Part A: check-then-act (TOCTOU) between `locate()` and the write.
- Failure mode: `withFileLock` starts with `mkdirSync(path.dirname(lockPath), { recursive: true })`. Here that dirname is the session directory itself. Window A runs `_keryx/session_trash`, which moves `<sessions>/<id>` to the OS trash. If that happens between window B's `locate(cwd, sessionId)` and its lock, B's flags change (archive or pin, a turn-end subject apply, or Link) recreates `<sessions>/<id>/`, writes `flags.json` into it and reports success. Before this PR, `writeOwnerOnlyFileAtomic` failed with ENOENT and the change was refused. The orphan directory has no `summary.json`, so `listSessions` skips it and nobody sees it. It stays behind for good, and a Finder "Put Back" of the trashed session then collides with it.
- Fix: do not let the lock create the session directory. Check `existsSync(dir)` inside the lock before reading or writing and refuse with "session not found" when it is gone. Or give `withFileLock` a `createDir: false` option for this caller, so a missing directory is a refusal and not a mkdir.

### Concurrency & Races

**[HL3-003] The shown-session check and the composer fill are a frame apart** (info). File apps/desktop/src/review/prWork.ts. This is what remains of LG-011.
- `fillShown` checks `deps.isShown(id)` and then calls `deps.fill`. App's `fillComposer` defers `composer.current?.setText(text)` to `requestAnimationFrame`. A switch dispatched inside that frame, such as a keyboard shortcut, would put the prompt in the newly shown session while `filled: true` registers the request on the opened one. Since round 2 that request can only produce a "Link Flow #N?" offer that the user confirms, so nothing is written silently. The fix is optional: re-check `isShown(id)` inside the rAF callback and pass that result back, for example by making `fill` return a promise of the outcome.

**[HL3-004] Two-second, age-only stale recovery can break the lock of a holder that is still running** (info). File src/session/organize.ts (slice-03).
- `FLAGS_LOCK_STALE_MS = 2_000`, with recovery by lock-file mtime only (no PID check). If a holder's read plus atomic write stalls for more than 2 s, a waiter breaks the lock and both write. The nonce keeps the first holder from deleting the second's lock, but the read-modify-write can still lose an update, which is the HW2-001 outcome again. Causes would be synchronous I/O on a slow or network home directory, or a holder process suspended. I show no concrete trigger in this repository, so this is info. It would be settled by recording the holder PID in the lock file and breaking it only when that PID is gone, or when the lock is older than the shared LOCK_STALE_MS (10 s).

### Lock Contention
HL3-001, HL3-002 and HL3-004 above. Deadlock check: `withIssueBinding` holds the binding lock (lib/fs, async) and calls `bindIssueSubject` → `backfillSessionSubject` → flags lock (lib/file-lock, sync). The flags-lock bodies (`applyFlagsChange`, the backfill closure) only read and write flags.json and take no other lock. No path takes the flags lock and then the binding lock, so the two cannot deadlock. Because the flags lock is fully synchronous, no in-process re-entry is possible either.

### Retry / Timeout / Circuit Breaker
The lock retry is capped by its deadline (3 s), and the deadline is checked before the stale branch, as file-lock.ts requires. Desktop's `applyPendingFlow` retries a refused write only after the session's next turn, so there is no retry storm.

### Idempotency & Distributed Invariants
Link is idempotent per press: `accept` clears `offersRef` synchronously before calling `link`, so a double click before the next render writes once. Dismiss claims the package, so it is never offered again.
