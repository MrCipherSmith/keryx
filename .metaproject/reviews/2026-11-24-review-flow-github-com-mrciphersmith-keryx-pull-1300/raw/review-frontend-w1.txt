### Findings

### [FE-R3-001] A focus request for a PR the loaded snapshot does not hold still stays armed and opens later without being asked (LG-009 sibling)
- **Severity**: major
- **File**: apps/desktop/src/review/ReviewBoard.tsx
- **Rule**: canonical rubric (trigger and outcome). The fix's own comment states the intent: "so the request is not left armed for a later, unrelated switch".
- **Problem**: The round-2 fix refuses a focus for a repository the board cannot show. The other early return, `if (!snapshot.cards.some(c => c.number === focus.number)) return;`, still leaves the request armed with no notice. App's header link (`SessionSubjectLinks` -> `setReviewFocus`) fires for any PR-bound session, including one bound to a merged or closed PR. The board's default state filter is `["open", "draft"]` (model.ts), so the loaded snapshot of the right repository does not hold that card.
- **Trigger -> outcome**: open a session bound to a merged PR and click its header PR link. The board switches to Pull requests and nothing opens, with no message. Later the user changes the state filter to include Merged, or the card shows up in a later snapshot. The PR panel then opens without being asked. LG-009 was this same outcome for the other early return.
- **Fix**: once a fresh snapshot of the focused repository is loaded (not `stale`, not `loading`) and still lacks the PR, handle it the way the foreign-repo branch does. Set `focused.current`, show a notice (for example "#N is not in the current filters" with a "Show all states" action), and call `onFocusHandled(nonce)`. A stale cached snapshot keeps waiting, so a PR that was just opened still focuses after the refresh.
- **class_scope**: the focus effect's early returns at head, ReviewBoard.tsx:496 (`!focus`, already handled, `!snapshot`: a legitimate wait for the load), :497-506 (repository mismatch: fixed in this range), :508 (card absent: still armed). Enumeration: every `return` in the one `useEffect` that consumes `focus`. `focus` has no other consumer (`setSelected({ number: focus.number })` is its only effect).

### [FE-R3-002] Controls added in this range that remove themselves on activation drop keyboard focus to the document body
- **Severity**: major
- **File**: apps/desktop/src/review/PrWorkRow.tsx
- **Rule**: canonical rubric (accessibility basics, keyboard). A sibling in the same file already does this correctly: the partial-sync dismiss in ReviewBoard.tsx calls `warningToggle.current?.focus()` after hiding.
- **Problem**: In each of these, activating the control unmounts the control itself, and no focus target is set:
  1. `FlowOffer` "Link" / "Dismiss" (PrWorkRow.tsx). `accept`/`dismiss` drop the offer, and the slot re-renders as a different element (the "Create Flow" button, then "Flow #N").
  2. The focus-notice "Dismiss notice" icon button (ReviewBoard.tsx). `setFocusNotice("")` removes the whole banner.
  3. "Show issues assigned to me" (IssuesBoard.tsx). `change("assigned")` changes the `Collection` key (`source` is in `key`), so the panel and its button unmount.
- **Trigger -> outcome**: a keyboard user presses Enter on Link, Dismiss or Dismiss notice. `document.activeElement` becomes `<body>`, and the next Tab starts again from the top of the window instead of at the PR card they just acted on.
- **Fix**: after the action, move focus to the element that replaces the control. For the offer, that is the Flow slot's button: keep a ref on the slot and focus its first button in an effect when the offer disappears. For the notice, focus the board heading or the search field. For the Issues fallback, focus the source `<select>` or the Issues heading, as `title` is already used for focus return in that file.
- **class_scope**: sites PrWorkRow.tsx `FlowOffer` (two buttons), ReviewBoard.tsx focus-notice dismiss, IssuesBoard.tsx unavailable-panel button. Enumeration: every `<button` on a `+` line of slice-01. There are four (Link, Dismiss, Dismiss notice, Show issues assigned to me), and all four remove themselves. Controls only re-indented in the range (the Flow slot's own button, the session menu) keep their element, so they are not affected.

### [FE-R3-003] The repository-unavailable panel matches any `configuration:` error, not only the three reasons it was written for
- **Severity**: info
- **File**: apps/desktop/src/issues/IssuesBoard.tsx
- **Problem**: `const unavailable = fallback && /(?:^|\b)configuration:/i.test(error) ? fallback : undefined;` covers every `configuration:` reason while the default source is unchosen. That includes `readCursor`'s "configuration: Refresh before loading the next page." on a load-more (issues-github.ts). In that case the board says "This project's repository issues are not available here", drops the Retry button and the "Showing the last available snapshot." note, and offers a switch to Assigned to me that is stored for good. I could not name a realistic input that makes Desktop send a cursor outside its scope, so this is an observation and not a defect.
- **What would settle it**: a load-more scenario that produces that error in practice. Otherwise, match the three reasons the comment names (no GitHub.com remote, Issues turned off, `invalidInput`) instead of the prefix.
