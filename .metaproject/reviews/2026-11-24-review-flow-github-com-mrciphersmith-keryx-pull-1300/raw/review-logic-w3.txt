### Logic Bugs
None detected. Checked:
- Marker state machine (organize.ts): `unlinked = change.subject === null ? true : change.subject !== undefined ? false : subjectUnlinked`; `writeFlags` writes the marker only when `subjectUnlinked && flags.subject === undefined`; `readStoredFlags` honours it only when no valid subject is stored. An inconsistent file (subject plus marker) reads as linked and the next write drops the marker. A corrupt/absent file reads as `{subjectUnlinked: false}`, same as the pre-existing flag semantics.
- `backfillSessionSubject`: read and write in one locked section; returns false when a subject is present or unlinked; throws only for an unparsable subject, which `bindIssueSubject` cannot pass (it only calls it with a parsed one).
- `withIssueBinding`: `bindIssueSubject` now runs after `existsSync(dir)` on every open. Its one caller (`issues-launch.ts:99`) is reached only for `open-session`/`prepare-flow`; the `workspace` action returns at line 90 before the binding, so a board view does not write. `dir` comes from `launch.project.cwd`, so the `project_required` early return at line 101-102 still backfills the right session. A throw from the flags lock in the `registered` path leaves the binding at `registered` (not saved), and the next attempt finds the session and completes — recoverable.
- Lock nesting: the comment "The flags lock is taken inside the binding lock, never the reverse" holds — `withFlagsLock`'s callback is synchronous and calls only `readStoredFlags`/`writeFlags`, so it cannot take the async binding lock; `issues-launch.ts:116` `setSessionFlags` runs after `bindIssueSubject` released the flags lock (not re-entrant, not nested).
- `withFlagsLock` maps `withFileLock`'s `null` to a throw and wraps the value in `{value}` so a callback result is never confused with the timeout `null`.
