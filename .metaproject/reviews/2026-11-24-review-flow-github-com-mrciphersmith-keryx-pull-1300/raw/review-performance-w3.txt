### PF-R3-001 checked against the slice-03 code
- Confirmed as filed. `withFlagsLock` calls the synchronous `withFileLock` from `../lib/file-lock` with `timeoutMs: 3_000` and `staleMs: 2_000`. On contention the loop retries with `sleepSync(15)` (Bun.sleepSync). `updateSessionFlagsAt` and `backfillSessionSubject` both go through it. On the ACP path (`_keryx/session_flags`, server.ts:2964 → setSessionFlags → updateSessionFlagsAt), a wait blocks the event loop of that window's keryx process.
- One correction to the wave-1 wording: a 2 s stall does not need a holder that dies inside the section. Any lock file younger than 2 s that nobody removes is enough, because staleness is judged by mtime age only. The new test "a flags change waits for another writer's lock and takes over an abandoned one" shows this: a fresh foreign lock makes `setSessionFlags` wait at least 1500 ms, about 2 s in practice. The rating stays info. Leaving such a file still needs a crash or a foreign writer inside a sub-millisecond section, and no named input reaches it at a stated frequency.
- Same defect as HL3-001 (highload, minor: the lock wait freezes the whole ACP server). One defect across lenses (review.mdc), so dedupe PF-R3-001 into HL3-001. HL3-004 (age-only stale recovery) is the mechanism behind the correction above and is owned by highload.

### Cost checks on slice-03 production code (no finding)
- **Backfill on every issue open** (issue-session.ts): `bindIssueSubject` moved out of the `registered` branch, so every `withIssueBinding` call now runs `backfillSessionSubject`. That is one uncontended flags lock (mkdir, open `wx`, nonce write, close, unlink), one flags read, and a write only when the subject is missing and not unlinked. When a subject is already present it returns false with no write. It runs once per user-triggered issue open in the issue-workspace CLI child, never per render or per keystroke. The cost is negligible.
- **Nested locks** (issue-session.ts): the sync flags lock is taken inside the async issue-binding lock, and the comment documents that order. A flags-lock wait of up to 3 s would block only the issue-workspace child, which is a CLI process with no other work, so it is not interactive-path blocking. A timeout throws out of `withIssueBinding`. That is a correctness or degradation concern, not a cost one, and it belongs to those lenses.
- **readStoredFlags / writeFlags** (organize.ts): one extra boolean field read and written. `readSessionFlags` stays lock-free, so the cost of listing sessions does not change.
- **parseSessionSubject in backfillSessionSubject**: one validation before the lock, plus the same regexes `applyFlagsChange` already runs. The regexes are module constants, not compiled per call.

### Test code (not a hot path)

The test has a 30 s timeout. This is test-only CPU and wall time. It adds a few seconds to `bun test src/session/organize.test.ts`, which is acceptable for a lost-update regression guard.
