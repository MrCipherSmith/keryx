### Focus areas checked

1. **`withFlagsLock` lock path.** `path.join(dir, "flags.json.lock")`. `dir` comes from `locate()` (exact stored id, `summary.id === sessionId`) or from the issue binder, whose `launch.sessionId` is a keryx-minted `randomUUID()` in an owner-only binding record. No request-controlled path component. Clean.
2. **Symlink / TOCTOU on `flags.json.lock`.** The lock is taken with `openSync(lockPath, "wx", 0o600)` (O_CREAT|O_EXCL): an existing symlink at that name fails with EEXIST and is never followed, so a planted link cannot redirect the nonce write. The stale branch `rmSync`s the name (removes a link, not its target). The finally `readFileSync`s through a link only to compare the nonce. Whoever could plant a link already writes the user's data dir (same user), so there is no privilege boundary. flags.json itself goes through `writeOwnerOnlyFileAtomic` (temp + rename). Clean; see SC3-001 for the one correctness gap in stale takeover.
3. **Owner-only perms.** Lock file 0o600; `mkdirSync(dirname, { mode: 0o700 })` (a no-op on the existing session dir); flags.json owner-only atomic. The issue binder now calls `bindIssueSubject` only after `existsSync(dir)`, so `withFileLock`'s `mkdirSync(..., recursive)` cannot create a session dir that does not exist. Clean.
4. **`_keryx/session_flags` input validation.** The handler builds `SessionFlagsChange` from four named keys only (archived/pinned boolean, flow string|null, subject object|null, arrays refused). `subjectUnlinked` is not settable from the wire: the marker is set only by `subject: null` and cleared by any subject write (`applyFlagsChange`: `change.subject === null ? true : change.subject !== undefined ? false : subjectUnlinked`). `readStoredFlags` honours it only when `raw.subjectUnlinked === true` and no valid subject is present; `readSessionFlags` never exposes it (pinned by the new test `toEqual({ pinnedAt: expect.any(String) })`). `parseSessionSubject` rebuilds the subject from five known fields, so client-supplied extra keys are dropped (new test asserts the raw keys). REPO_REF refuses `.`/`..` names and out-of-charset repos even when url and repo agree (new `bad` fixtures `org/..`, `org/.`, `org/re po`). SUBJECT_URL pins `https://github.com/`. FLOW_REF needs an alphanumeric first char and no `/`. Error text truncates the echoed subject to 300 chars. Clean.
5. **Subject backfill writes.** `backfillSessionSubject` re-parses the subject, then under the lock writes only when there is no subject and no unlink marker. Its only production caller is `bindIssueSubject`, which builds the subject from the verified remote issue ref (`withIssueBinding` is "only called after the remote issue and viewer were verified"). A backfill never overwrites an existing subject, so a renamed or transferred issue cannot move a session's subject. Clean.
6. **Issue-session binding.** `bindIssueSubject` now runs on every open, after the `issueKey`/`issueViewerKey`/`cloneId` consistency check and, for a non-registered stage, after the findSession/not-archived check. Lock order: binding lock (async `lib/fs` withFileLock), then the flags lock, never the reverse. The other writer inside a binding (`issues-launch` prepare-flow `setSessionFlags`) takes the same order. No deadlock path, no authorization change: the subject names no account (stated in the doc and the PR's Known gaps).

### Findings

### [SC3-001] Stale takeover in withFileLock can admit two flags writers at once (pre-existing helper, now reached with a 2 s stale window)
- **Severity**: info
- **File**: src/lib/file-lock.ts (outside the diff; unchanged in this range)
- **Attack vector**: none. Every party that can touch the lock is a keryx process of the same user, so no attacker impact is claimed (security law: rated by trigger and outcome).
- **Problem**: Two paths let two holders run the critical section together. (a) Stat-then-remove race: waiters A and B both stat a stale lock; A removes it and creates its own; B, still acting on its earlier stat, then `rmSync`s A's fresh lock and creates its own. (b) A holder whose section outlives `staleMs` (2 s for flags: a SIGSTOPped or suspended process, a stalled disk) has its lock broken. The nonce guard stops the old holder from deleting the new lock, but not from completing its write. In both cases the later rename silently drops the other writer's flag change, which is the lost update HW2-001 set out to close.
- **Why it matters**: The trigger needs a crashed holder plus two concurrent waiters interleaving within microseconds, or a holder paused past 2 s. Both are rare, and the outcome is the narrow lost-update outcome from round 2, not data exposure.
- **Fix**: Optional. Break a stale lock by renaming it to a unique name and re-checking its nonce/mtime before deleting (or `link`-based acquisition), so a waiter never removes a lock it did not stat. Track separately, since the helper is shared with the registry and the serve credential store.

### Clean areas
Injection (no shell, SQL or template construction), authn/authz (no new entry point; the wire method's keys are unchanged), IDOR (exact-id lookup), path traversal (focus 1, 4), symlink/TOCTOU (focus 2), secrets/logging (the lock error echoes only `path.basename(dir)`; the subject echo is truncated and holds no token), crypto (`randomUUID` nonce only), CSRF/open redirect/React (not in slice).

### Follow-up (not security; other lenses)
- highload/performance: `withFlagsLock` is synchronous and waits with `Bun.sleepSync` for up to 3 s. In the ACP server (one per Desktop window), a contended or crashed lock blocks that process's event loop for every session of the window for up to 2 to 3 s.
- degradation: `bindIssueSubject` now runs on every issue open, inside the binding lock. A flags lock that cannot be taken within 3 s (for example an unremovable stale lock) now fails every issue open with "locked by another keryx process; retry". Before, this happened only on first bind.
- LG-014 (deferred): an older keryx writer also drops the new `subjectUnlinked` marker. If such a writer touches an unlinked issue session, the next open backfills the subject again. This is the mixed-version case the PR body already names.
