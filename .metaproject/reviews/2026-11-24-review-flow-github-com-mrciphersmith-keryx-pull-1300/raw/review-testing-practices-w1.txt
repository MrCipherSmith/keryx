## Findings

### [TP-R3-001] minor: the hook's synchronous guards and offer replacement are unpinned (M01, M05, M08)
- File: apps/desktop/src/review/usePendingFlowLinks.ts (tests: usePendingFlowLinks.dom.test.tsx)
- Problem: three gates added in this range survive with all 6 Desktop suites green. (a) `accept` clears offersRef at once "so a second press before the next render cannot write the link twice". The test presses accept twice, but in separate `act`s, so a re-render happens between them. (b) `dismiss` clears offersRef synchronously. No test calls dismiss and then accept before a render. (c) A new offer for a session replaces that session's older offer. No fixture gives one session two offers (Create Flow again after an offer was left unanswered).
- Impact: (a) and (b) are the double-click races the comment names: a double Link writes `flow` twice, and Dismiss then Link in one frame writes a dismissed package. With (c) undone, the row keeps showing the stale first package (flowOffer takes the first match). Nothing would catch a regression.
- Fix: in one `act`, call `accept("s1")` twice and assert `links` has length 1. In one `act`, call `dismiss("s1"); accept("s1")` and assert no link. Then: expect s1, package 101 offered, no action, expect s1 again, package 102 appears; assert `offers()` equals `["s1 102-…"]`.

### [TP-R3-002] minor: the PrWorkRow gate that hides an offer when the PR already has a Flow is unpinned (M20)
- File: apps/desktop/src/review/PrWorkRow.tsx (test: PrWorkRow.dom.test.tsx)
- Problem: `const offer = flow ? undefined : work.flowOffer?.(sessions);`. Deleting the `flow ?` guard leaves all 6 suites green. The offer test renders no Flow, so nothing separates "offer" from "Flow link".
- Impact: if the offered package (or another Flow) carries the PR's `prUrl`, the row would show "Link Flow #N?" in place of the PR's Flow link. No test would catch that.
- Fix: in the offer test, add a render with `flows: [flow("531", { prUrl: pr.url })]` and the same offer. Assert that the Flow slot reads `Flow #531 · In progress` and that there is no "Link Flow" button.

### [TP-R3-003] minor: the Issues fallback's `configuration:` filter is unpinned (M34)
- File: apps/desktop/src/issues/IssuesBoard.tsx (test: IssuesBoard.dom.test.tsx)
- Problem: `const unavailable = fallback && /(?:^|\b)configuration:/i.test(error) ? fallback : undefined;`. Replacing the regex with "any error" is green. Each AC13 fixture on the default source fails with a configuration error, and the one that keeps Retry gets it from a chosen source, not from a non-configuration error.
- Impact: a regression would hide Retry on the default source for transient failures (rate limit, offline, `unavailable:`) and offer a source switch the person does not need. No test would notice.
- Fix: add a case with no stored source whose request rejects `new Error("rate-limit: GitHub request limit reached.")`. Assert Retry is present and "Show issues assigned to me" is absent.

### [TP-R3-004] minor: the focus-refusal bookkeeping in ReviewBoard is unpinned (M24, M26)
- File: apps/desktop/src/review/ReviewBoard.tsx (test: PrWorkRow.dom.test.tsx, LG-009 case)
- Problem: on refusal, `focused.current = focus.nonce;` survives deletion. The LG-009 test's onFocusHandled clears the focus, so the effect never re-runs with the same nonce. On success, `setFocusNotice("")` survives deletion (presentation). No test refuses one focus and then opens another.
- Impact: undoing either is invisible to the suite. Without the first, a board whose owner does not clear focus re-raises a dismissed notice on every refresh. Without the second, a stale "not in a repository this board shows" notice stays above the panel that did open.
- Fix: with `focusHost(load, [], false)`, refuse `elsewhere/project`, Dismiss the notice, Refresh, and assert no `.review-focus-notice`. In the LG-009 test, after the refusal, set a new nonce for `org/repo#101` and assert that the panel opens and the notice is gone.

### [TP-R3-005] minor: the `showState` gate of the shared progressParts is unpinned (M29)
- File: apps/desktop/src/review/ReviewProgress.tsx
- Problem: the AR-style refactor moved the rule into `progressParts(state, progress, showState)`. `state: showState && ![...]` survives deletion with all 6 suites green. Every asserted caller passes showState true (reviewProgressText) or uses a running, queued or completed state.
- Impact: a regression would add "Partial · " or "Failed · " to every `<ReviewProgress>` rendered without showState. Nothing would catch it.
- Fix: render `<ReviewProgress state="partial" />` with no showState and assert the caption has no "Partial"; render it with showState and assert it does.

### [TP-R3-006] minor: issues-board pagination gates that separate the repository source from viewer sources are unpinned (M54, M51, M55)
- File: src/integrations/issues-board.ts (test: issues-board.test.ts)
- Problem: the gates `for (let fetched = 1; repository && !issues.length && fetched < REPOSITORY_PAGES; fetched++)` (M54: drop `repository &&`) and `if (repository && error instanceof Error && error.message === issuesDisabled)` (M51: drop `repository &&`) both survive across the 5 root suites. No viewer-source fixture returns an empty page with a next link, or a 410. M55 (turnPage no longer deletes earlier page keys) also survives. It is likely near-equivalent, because `set` overwrites the same keys.
- Impact: a regression could make viewer queues read up to 3 pages per request, or show "Issues turned off for null". The suite would not notice. The cost is low; the gates were added in this round.
- Fix: a viewer-source (`assigned`) page answering `[]` with a next link must make exactly one request. A viewer 410 must not mention "turned off for".

### [TP-R3-007] minor: the flags lock's timeout error and the backfill's use of the lock are unpinned (M39, M47); outside slice-02, run as the dispatch asked
- File: src/session/organize.ts (test: organize.test.ts, slice-03)
- Problem: `if (held === null) throw new Error(\`the flags of session ... are locked by another keryx process; retry\`)` survives deletion, and the code then fails with a TypeError on `held.value`. No test holds the lock past FLAGS_LOCK_TIMEOUT_MS; the wait test lets it go stale at 2 s. `backfillSessionSubject` running without `withFlagsLock` also survives: the two-process test drives only updateSessionFlagsAt. Also, the two-process test caught the unlocked updateSessionFlagsAt (M38) in only 2 of 3 runs. M38 is pinned deterministically only by the wall-clock lock-wait test.
- Impact: the "retry" message the ACP client shows, and the backfill's lost-update protection (an issue-workspace child against a Desktop flag write), could regress silently.
- Fix: inject the lock options (or a clock) and make the lock unbreakable within the test, then assert the "retry" message. Add a two-writer test where one process backfills while the other pins.
