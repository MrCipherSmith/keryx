- How Desktop reads a lock error. A lock that cannot be taken throws "the flags of session X are locked by another keryx process; retry". `refuseStore` turns that into `invalidRequest`. PendingSubjects.apply treats any throw as "not stored yet": it keeps the binding pending and tries again after the turn. So a contended lock never shows SUBJECT_NOT_SAVED and never drops the binding. That notice is shown only for a successful reply that has no `subject`, which is unchanged.

Enumerated with `keryx ctx rg setSessionFlags|updateSessionFlagsAt|backfillSessionSubject src` excluding tests: 10 matches in 4 files.
- Backfill seen from the frontend. An issue session bound by an older keryx gets its subject on the next open, so IssueWorkRow counts it. A person's unlink is respected, and linking again clears the marker. The account and Enterprise limits are recorded in the plan (g) and in the PR body's Known gaps.

### Findings

### [FE-R3-004] An issue open can now fail on the optional subject write
- **Severity**: info
- **File**: src/session/issues/issue-session.ts
- **Problem**: `bindIssueSubject` now runs on every `withIssueBinding`, not only the first. It runs inside the binding lock and is not guarded. If the flags lock cannot be taken within 3 s, `withFlagsLock` throws, and the whole open fails. The Issues board then shows "the flags of session … are locked by another keryx process; retry". The same text appears for a session directory that is not writable, because `withFileLock` catches every `openSync` error and waits until its deadline. Before this range a reopen never wrote flags.json, so a cosmetic subject could not block reopening an issue session.
- **Why it is info**: I found no realistic trigger. The stale threshold (2 s) is below the timeout (3 s), so a crashed holder's lock is broken in time, and the critical section is a single small read plus one write. Only a lock file that cannot be removed or written, or constant contention, reaches the throw.
- **Fix (optional)**: on the reuse path, treat the backfill as best effort (catch and continue, since the next open retries it). Or let `withFlagsLock` report EACCES/EROFS as a storage error rather than as "locked by another keryx process".
