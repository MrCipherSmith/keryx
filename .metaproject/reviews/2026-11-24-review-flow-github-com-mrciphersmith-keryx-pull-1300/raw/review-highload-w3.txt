### CLI / Multi-Session

HL3-001 (minor), confirmed against slice-03. withFlagsLock calls lib/file-lock withFileLock with timeoutMs 3_000 and staleMs 2_000. withFileLock's wait is `sleepSync(15)`, which is Bun.sleepSync or a busy-wait fallback, repeated until the deadline. src/acp/server.ts:2964 calls `setSessionFlags(cwd, sessionId, change, options.dataDir)` synchronously. A lock that another writer left behind therefore stops the ACP server's event loop for up to the stale window (about 2 s). An unremovable lock stops it for the full 3 s on each write. The comment's reason ("callers are synchronous, and the section is one read and one atomic write") bounds how long a holder keeps the lock, not how long a waiter blocks. The organize.test case "waits for another writer's lock" measures this wait at ≥1500 ms.

HL3-002 (minor), confirmed, with one site added. withFileLock begins with `mkdirSync(path.dirname(lockPath), { recursive: true, mode: 0o700 })`, and for `<dir>/flags.json.lock` that dirname is the session directory. trashSession renames or copies the directory away under the session lease only. Two paths can recreate it:
- setSessionFlags runs `locate()` and then `updateSessionFlagsAt(dir, …)`. A trash in another process between those two steps lets the lock recreate `<sessions>/<id>/` and write an orphan flags.json there.
- withIssueBinding checks `if (!existsSync(dir)) throw …` and then calls `bindIssueSubject(dir, …)`, which calls `backfillSessionSubject` and takes the same lock. A trash in that window has the same outcome: an empty session directory holding only flags.json. That directory has no summary.json, so listSessions skips it.

Since this range the backfill runs on every open of an issue session, not only at first bind, so the second window is opened on every open. The fix from wave 1 covers both sites. Inside the critical section, refuse when the session directory (or its summary.json) is gone. Or give withFileLock a `createDir: false` option for these callers.

HL3-004 (info), confirmed. Stale recovery in file-lock.ts checks lock-file age only (`Date.now() - age > staleMs`) against FLAGS_LOCK_STALE_MS = 2_000. It does not check the holder's PID. The nonce keeps a stalled holder from deleting its successor's lock, but both read-modify-writes still run. I still show no concrete stall trigger in the repository.

HL3-003 is in apps/desktop/src/review/prWork.ts (slice-01), not in slice-03. It is unchanged by this wave.

### Concurrency & Races
None new. backfillSessionSubject runs parseSessionSubject outside the lock and then reads, checks `subject !== undefined || subjectUnlinked` and writes, all inside withFlagsLock. That makes check-then-act atomic against setSessionFlags in another process. applyFlagsChange carries `subjectUnlinked` through every change: it is set by `subject: null`, cleared by a subject, and otherwise kept. A concurrent pin therefore cannot drop the unlink marker and let a later backfill write the subject back. The organize.test case "an unlinked subject is not backfilled" pins this.

### Resources
None detected. The lock file lives in the session directory. If trashSession moves the directory while the lock is held, the lock goes with it, and the holder's atomic write fails with ENOENT. The change is then refused, not lost silently.

### Caching
None detected.

### Lock Contention
Order: withIssueBinding holds the binding lock (lib/fs, async) and calls bindIssueSubject → backfillSessionSubject → flags lock (lib/file-lock, sync). Neither applyFlagsChange nor the backfill closure takes a lock. issues-launch.ts:116 calls setSessionFlags (flow) from inside the withIssueBinding apply callback, which is the same binding → flags order. No path takes flags → binding. The binding lock can now be held through one flags-lock wait (≤3 s) per open; that cost is covered by HL3-001.

### Async / Queues
None detected.

### Retry / Timeout / Circuit Breaker
The lock retry is capped by its 3 s deadline, which is checked before the stale branch. A timeout surfaces as a thrown "locked by another keryx process; retry". Desktop retries a refused flags write only after the session's next turn, so there is no retry storm.

### Idempotency & Distributed Invariants
Backfill is idempotent: it returns false when a subject is present or the subject was unlinked. withIssueBinding opens therefore write at most once per session. The test "a session bound before subjects existed gets its subject on the next open; an unlink still wins" covers that path.
