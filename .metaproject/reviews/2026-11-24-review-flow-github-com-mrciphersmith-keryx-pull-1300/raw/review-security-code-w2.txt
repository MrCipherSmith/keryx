### Focus areas checked

1. **Per-session `flags.json.lock` path (traversal).** The lock is `path.join(dir, "flags.json.lock")`, where `dir` comes either from `locate()` or from a caller that already holds the directory. `locate()` resolves the id through `findSession(cwd, sessionId)` and refuses unless `summary.id === sessionId` exactly, so the id is one keryx already stored and listed; a `../` id finds no stored session and throws before any path is built. `sessionDir` itself is a plain `path.join`, so the guard is the exact-id lookup, and every flags writer goes through it or through `updateSessionFlagsAt(dir)` / `backfillSessionSubject(dir)` with a binder-owned dir. All three writers (`applyFlagsChange`, `backfillSessionSubject`, via `setSessionFlags`) run inside `withFlagsLock` (enumerated: `keryx ctx rg -n "withFlagsLock|applyFlagsChange|writeFlags\(" src/session/organize.ts` → writeFlags is called only at lines 159 and 193, both inside the lock). The lock-timeout error echoes only `path.basename(dir)`. No finding.

2. **GitHub `/repos/{o}/{r}/issues` request.** The repository comes from the project's own git remotes (`selectRepository(reviewRepositories(cwd))`), not from the Desktop request. Each part is `encodeURIComponent`-encoded, and parts made only of dots are refused before any request (`/^\.+$/`), which closes the one path rewrite `encodeURIComponent` leaves open (it does not encode `.`). The new test "a remote named `..` is refused before any request" pins it with `requested === 0`. The cursor scope adds `repository.toLowerCase()`, so a cursor cannot be replayed against another project's repository. No finding.

3. **410 mapping.** `failure()` maps any 410 to the fixed `issuesDisabled` string; `issuePage` rewrites it only for the repository source, adding the owner/name from the local remote. No response body or token text reaches the message. No security finding (see follow-up for a non-security observation).

4. **Multi-page loop.** Bounded by `REPOSITORY_PAGES = 3` per request. `pageLink` keeps the origin check (`url.origin !== API`), refuses userinfo, accepts only the same path (case-insensitive for the repository source) or `/repositories/<digits>/issues`, and copies only `pageKeys` (page/after/before/since_id). `turnPage` re-validates the keys and writes them onto the base URL, so the next request always targets the base `/repos/{o}/{r}/issues` path on api.github.com; a crafted Link header cannot redirect the token-bearing request. The viewer source keeps the exact-path rule, pinned by the new test that refuses `/repositories/42/issues` and `/ISSUES` for `assigned`. No finding.

5. **Subject backfill writing to disk.** `backfillSessionSubject` parses the subject through `parseSessionSubject` (refuses invalid ones, error text truncated to 300 chars), writes under the lock with `writeOwnerOnlyFileAtomic`, and honours the `subjectUnlinked` marker. The wire refuses arrays for `subject` (-32602), pinned in `shell-session-organize.test.ts`. No finding.

6. **`issuesCommand(args, cwd, connect)` test seam.** The only production caller (`src/cli-registry.ts:128`) passes `rest` alone, so `connect` defaults to `connectIssueAccount`; the seam is not reachable from the CLI. No finding.
