### Module Boundary Violations
[AR-007] Desktop decodes the CLI error contract by category prefix and by message text, in the view.

- **Severity**: minor
- **File**: apps/desktop/src/issues/IssuesBoard.tsx
- **Problem**: The fallback decides that "This project's repository issues are not available here" from `/(?:^|\b)configuration:/i.test(error)`. It decides "this keryx is older than Desktop" from `/Invalid Issues request/i.test(error)`. Both checks sit in the Collection component; the sibling classifier `isAccessError` lives in useIssueCollection.ts. On the backend, `configuration:` is the category for many unrelated reasons, and `invalidInput` ("configuration: Invalid Issues request.") is thrown for more than an old keryx. Examples: a stale cursor (`readCursor`, issues-github.ts:120 "Refresh before loading the next page."), a malformed cursor (issues-github.ts:122), a `.`/`..` repository part or a missing cwd (issues-board.ts:115, :118), and a pagination link that fails validation (issues-board.ts:154, :168). The contract also already has a typed `problem.code` set (issues-contract.ts:115) that includes `source_unavailable`, which `isAccessError` treats as an access loss.
- **Trigger and outcome**: The Issues board is on the default (unchosen) repository source with more pages to load. The project's resolved repository changes, for example origin is re-pointed or remotes are reordered. Then "Load more" runs. The cursor scope includes `repository.toLowerCase()` (issues-board.ts:203), so the CLI answers "configuration: Refresh before loading the next page.". Desktop replaces the Retry notice with "This project's repository issues are not available here." and offers only "Show issues assigned to me". Pressing it calls `change("assigned")`, which saves `assigned` as the person's chosen source, so a transient condition becomes a stored preference. Second path: a remote whose name parses as `.`/`..` gets `invalidInput`, and Desktop tells the person to update keryx, which is wrong advice.
- **Fix**: Give the repository-source failures their own reason on the CLI side, for example a `repository_unavailable:` prefix, or a `code` on the error the way `IssueWorkspace.problem.code` does it. Use it for no GitHub.com remote (board-github.ts:45, when raised for the issues source), Issues turned off (issues-board.ts:184) and the dot-name refusal. Classify it next to `isAccessError` in useIssueCollection.ts, so one module owns the mapping from CLI reason to UI category. Keep the old-keryx text match only for the first-page request (no cursor), which is the one case an old keryx produces.
