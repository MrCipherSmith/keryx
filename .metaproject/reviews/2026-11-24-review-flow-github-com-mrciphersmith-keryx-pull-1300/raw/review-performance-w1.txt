### Findings

### [PF-R3-001] The flags lock waits synchronously on the ACP server's request thread
- **Severity**: info
- **File**: src/session/organize.ts (withFlagsLock) via src/lib/file-lock.ts sleepSync
- **Hot path**: `_keryx/session_flags` (src/acp/server.ts:2964 → setSessionFlags → updateSessionFlagsAt → withFlagsLock). Per flag write: user action, end-of-turn PendingSubjects.apply, Link on a flow offer. Not per render or per keystroke.
- **Problem**: on contention `withFileLock` retries with `Bun.sleepSync(15)` until a 3 s deadline, and a lock left by a holder killed inside the section is only broken after 2 s (`FLAGS_LOCK_STALE_MS`). The whole wait runs synchronously on the keryx process that serves one Desktop window, so every session stream of that window stalls for its length.
- **Why it is info, not major**: the uncontended cost is four small sync fs calls, the same order as the read and atomic write that were already synchronous. A contended wait lasts about one 15 ms tick, because the critical section is one read and one write. A 2 s stall needs a holder that dies inside that sub-millisecond section. No named input reaches the long wait at a stated frequency (shared law 1). The choice is deliberate: the code comment says "Synchronous: callers are synchronous", and the PR body lists "A flags write waits up to 3 s for the lock" as an owner choice (law 4).
- **What would settle it**: a timing under two Desktop windows that toggle flags on one session in a loop. If stalls above ~50 ms show up, the async `withFileLock` from lib/fs, awaited in the ACP handler, removes the block.
- **Fix**: optional. Keep it as is, or use the async lock on the ACP path only.

### Cost checks requested by the dispatch (no finding)
- **New sync lock wait**: see PF-R3-001. `readSessionFlags` (session listing) takes no lock, so listing cost is unchanged. `bindIssueSubject` now runs on every `withIssueBinding` call, so each issue open adds one uncontended lock and read. That runs per user action and is negligible.
- **Up-to-3-page issues loop** (issues-board.ts listIssuePage): bounded by `REPOSITORY_PAGES = 3`, and only for the `repository` source while every page so far held only pull requests. The pages are serial because each needs the previous Link header, which is inherent. The loop stops at the first page holding any issue. The nodes hydration runs once, after the loop, on the final page only, so it is not multiplied. The worst case is 3 REST round trips plus one GraphQL per load or "load more", which is bounded and user-triggered.
- **Issues index** (IssuesBoard.tsx): `boundTo = useMemo(() => boundSessionIndex(sessions), [sessions])` builds the index once per sessions change. Each row does one Map lookup (`boundTo(issueSubject(issue)).length`). `sessions` comes from `state.sessions`, which is stable between session changes. This closes PF-003.
- **Flow offers wiring** (App.tsx, usePendingFlowLinks.ts, ReviewBoard.tsx): `offers` gets a new identity on every sessions change because `flowOf` depends on `sessions`. When there is no offer, ReviewBoard's `flowOffer` memo returns `undefined`, so `work` keeps its identity and `memo(ReviewResults)` still hits. With an offer (rare and short-lived), `work` changes on a sessions change, and `index` changes then anyway. The per-row `work.flowOffer?.(sessions)` is O(bound sessions) and runs only while an offer exists. `flowLinkActions` is stable, so `createPrFlow`, `linkFlowOffer` and `dismissFlowOffer` keep their identity.
- **boundSessions now via boundSessionIndex** (acp/types.ts): each call groups and sorts all sessions, not only the matching ones. The callers are per click only (App openPrSession, openSubjectSession), so this is negligible.
- **Focus effect** (ReviewBoard.tsx): one `repositories.find` per snapshot or focus change. `selectRepo(listed)` with an unchanged value does not change state, so no render loop.
