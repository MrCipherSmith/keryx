## Findings

### [TP-R3-008] major: the flags-lock tests depend on wall-clock time; the lost-update test is a probabilistic detector
- File: src/session/organize.test.ts, two tests: "a flags change waits for another writer's lock …" and "two processes changing different flags …"
- Problem (tdd-workflow.mdc Rule 5, and Rule 6 in effect):
  - The lock-wait test's only evidence that the change waited is two elapsed-time assertions: `expect(Date.now() - started).toBeGreaterThanOrEqual(1500)` and `expect(Date.now() - again).toBeLessThan(1500)`. It spends the real 2 s stale window on every run.
  - The two-process test synchronises its writers with `while (Date.now() < ${startAt}) {}`, a busy-wait on a wall-clock start 1.5 s ahead. It then depends on the OS interleaving 150 unsynchronised read-modify-writes.
  - Measured: with the parent's unlocked writer, the two-process test is red in only 3 of 7 runs. With M38 at head, it is red in 7 of 8 runs here and 2 of 3 in wave 1. When a child is slow to start past `startAt`, the writers overlap less and the test passes vacuously.
  - The regression test named for HW2-001 therefore fails before the fix only some of the time. Only the elapsed-time test pins M38 deterministically.
- Law 4 (a deliberate choice is read first): commit 80ef58bd5 gives no reason for this design. The repository has siblings that assert elapsed time on locks: src/lib/config-update.test.ts:62 and src/capability/stale-snapshot-writers.test.ts:160. The pattern is precedent, not an exemption, for two reasons. First, Rule 5's severity row rates exactly this case. Second, the seam exists: withFileLock already takes `timeoutMs` and `staleMs`, but organize.ts hard-codes them. That hard-coding is also why the timeout path (M39, TP-R3-007) cannot be tested without a 3 s wait.
- Fix:
  - (1) Let a test pass the lock options. For example, an internal `withFlagsLock(dir, apply, opts = FLAGS_LOCK)` with a test-only export, or a module-level override.
  - (2) Lock-wait test: drop the elapsed-time assertions. Spawn a child that takes the lock, writes a marker, waits for a go-file, writes its own flag and releases. Assert that the parent's change lands after the child's flag, and that neither change is lost. This is ordering on file content, not on time. Use tiny injected `staleMs` and `timeoutMs` values for the abandoned-lock leg and for a timeout case that asserts the "retry" message (this also closes M39).
  - (3) Two-process test: replace the `Date.now()` barrier with a file barrier: each child writes `ready-<field>` and spins until both exist. Better, drive a deterministic interleaving: inject the critical section so that writer A pauses between its read and its write until writer B has tried. With the lock, B must wait. Without it, B's write is lost on every run.
- class_scope:
  - sites: src/session/organize.test.ts, the lock-wait test (`expect(Date.now() - started).toBeGreaterThanOrEqual(1500)` and `expect(Date.now() - again).toBeLessThan(1500)`), and src/session/organize.test.ts, the two-process test (`while (Date.now() < ${startAt}) {}`).
  - enumeration_method: `keryx ctx rg -n --all "Date\.now\(\)|setTimeout\(|sleepSync|performance\.now"` over the 11 test files changed in 88e3faba9..d7b0f7058 (from `git diff --name-only`). 11 hits:
    - organize.test.ts, 7 hits: the 3 sites above, their 2 `Date.now()` start reads, the `startAt` computation, and the utimes setup at 151, which is not an assertion.
    - ReviewBoard.dom.test.tsx, 4 hits: `git diff -U0` shows none of them was added in the range.

### [TP-R3-009] minor: backfillSessionSubject's own subject validation is unpinned (N04)
- File: src/session/organize.ts (test: organize.test.ts)
- Problem: `if (parsed === undefined) throw new Error(\`not a GitHub subject: …\`)` survives deletion with all 21 tests green. Every test passes backfillSessionSubject a valid subject. Its one caller (bindIssueSubject) parses the subject first.
- Impact: the function is exported. A later caller that passes an unparsed subject would get it written to flags.json without validation if the guard were dropped. Readers would then see it as absent and the marker logic would be skipped, and no test would notice. This is a coverage gap only: the code is correct today.
- Fix: in the backfill test, assert that `backfillSessionSubject(dir, { ...issue, url: "https://github.com/org/other/issues/7" } as never)` throws `/not a GitHub subject/` and leaves flags.json unchanged.
