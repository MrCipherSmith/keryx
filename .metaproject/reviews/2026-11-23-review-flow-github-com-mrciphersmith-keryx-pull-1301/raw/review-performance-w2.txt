### Findings

### [F-001] wikiTree copies the group array for every page (quadratic in group size)
- **Severity**: minor
- **File**: src/integrations/metaproject-explorer-v2.ts (`wikiTree`)
- **Hot path**: once per Wiki `tree` request (root and every group expand / Show more page); W wiki pages in one group cost W²/2 element copies.
- **Problem**: `groups.set(key, [...groups.get(key) ?? [], node])` allocates a new array of the group's current length for each page.
- **Why it matters**: correct today, and small wikis make it negligible (2,000 pages in one group is ~2M copies, a few ms); it is a needless O(n²) on a path that grows with the wiki. No measurement exists either way.
- **Fix**: push into the existing array: `const list = groups.get(key); if (list) list.push(node); else groups.set(key, [node]);`.

### [F-002] Each tree page pays the full explorer load (graph JSONL parse, OpenSpec read, relationship checks, snapshot hash)
- **Severity**: info
- **File**: src/integrations/metaproject-explorer-v2.ts (`tree` routed through `metaprojectExplorerV2`)
- **Hot path**: one CLI request per folder expand, per Show more page, and per ancestor while revealing a selection; each runs `loadExplorerGraph` with a `catalog` request (graphRequest default), `readOpenSpec`, `buildRelationships`, and the SHA-256 of all nodes and edges, then `graphTree` uses only the files under one prefix.
- **Problem**: this is the established v2 pipeline shared by every action (not introduced here), but the tree makes it a per-click cost rather than a once-per-view catalog read. Frequency is user-driven (human clicks), not per keystroke or per frame, so no bottleneck is shown; no timing on a large checkout was supplied.
- **Why it matters**: on a large repository each expand could take as long as a full catalog read. Worth a timing of `tree` against `catalog` on a large checkout (e.g. this repo) before deciding anything; a per-process cache is not applicable since the CLI is spawned per request.
- **Fix**: none required for this PR; track separately if a timing shows expand latency comparable to the catalog load.

### Clean Areas
- graphTree: one O(N) pass over nodes per request, sort only over the parent's children, no nested scans; paging via `offsetPage` is bounded (100 entries, 900 KiB) and the shared helper replaces duplicated search paging without changing its cost.
- Request parsing (`parseV2` tree case, `validTreeParent`): constant per request.
- `tree` does not call `freshness()` (no `git status` per expand).
- Tests: prototypes (`scrollIntoView`, `window.setTimeout`) are restored in `finally`; temp roots are removed in `afterEach`; no leaks.
- Not applicable in this slice: DB N+1/indexes, React re-render (no component source in slice-02; MetaprojectTree.tsx/useMetaprojectTree.ts are in another slice), bundle imports, pagination gaps.
