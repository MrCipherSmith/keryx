### [F-001] Keyboard focus is lost when the focused status row is replaced (Retry, Show more on the last page, snapshot change)
- **Severity**: major
- **File**: apps/desktop/src/metaproject/MetaprojectTree.tsx (flatten / row keys)
- **Rule**: canonical rubric (trigger + outcome); plan "Desktop UI": roving focus, focus never moved by data arriving
- **Problem**: status rows carry a different React key per state: `loading:${parent}`, `error:${parent}`, `more:${parent}`. When the row that holds DOM focus changes state, React unmounts that `<li>` and mounts a new one, and nothing puts focus back. `tabbable` falls back to the selected row or row 0 (tabIndex moves) but `document.activeElement` becomes `<body>`. Reachable paths:
  1. Keyboard Retry: focus on an error row, press Enter/Space -> `model.retry` sets the folder to loading -> `error:p` is replaced by `loading:p` -> focus lost. Same for a failed next page: `error:p` becomes `more:p` (loading).
  2. Keyboard Show more on the last page: focus on `more:p`, press Enter -> page arrives with no `nextCursor` -> the `more:p` row is removed -> focus lost.
  3. A user arrows onto a "Loading…" row (status rows stay in keyboard navigation by operator decision); when the children arrive the loading row is removed -> focus lost.
  4. A new snapshot (refresh/rebuild) while focus is anywhere in the tree: `useMetaprojectTree` drops every folder, the whole tree collapses to `loading:` at the root, every focused row unmounts.
- **Why it matters**: the `onKeyDown` handler sits on the `<ul role="tree">`; once focus is on `<body>` the arrow keys, Home/End and Enter do nothing, so a keyboard user who presses Retry or Show more has to Tab back into the tree from the start of the page. This is the WAI-ARIA tree behaviour AC5 claims. The existing tests drive Retry and Show more by `.click()` and only check that data arriving does not *take* focus from outside (`MetaprojectTree.dom.test.tsx` 138-169, 226-236, 315-326); none presses Enter on a status row and checks `document.activeElement`.
- **Fix**: give every status row of a parent one stable key/id (e.g. `status:${parent}`) so loading/error/more for the same parent update the same `<li>` in place and keep focus; and in the existing `useLayoutEffect`, when `focusId` no longer names a rendered row while the tree held focus (track `list.current.contains(document.activeElement)` before the update, or check `document.activeElement === document.body` after a row the tree owned vanished), focus the row that now sits at the old index (the first appended entry after Show more, the parent folder for a vanished loading row). Add a test: focus "Show more", press Enter on the last page, expect focus on the first new entry; focus the error row, press Enter, expect focus to stay in the tree.
- **Patch** (sketch):
```diff
-      rows.push({ type: "loading", id: `loading:${parent}`, level, parent });
+      rows.push({ type: "loading", id: `status:${parent}`, level, parent });
...
-      rows.push({ type: "error", id: `error:${parent}`, level, parent, message: folder.error ?? "The read failed." });
+      rows.push({ type: "error", id: `status:${parent}`, level, parent, message: folder.error ?? "The read failed." });
...
-    if (folder.more?.status === "failed") rows.push({ type: "error", id: `error:${parent}`, ...
-    else if (folder.nextCursor) rows.push({ type: "more", id: `more:${parent}`, ...
+    if (folder.more?.status === "failed") rows.push({ type: "error", id: `status:${parent}`, ...
+    else if (folder.nextCursor) rows.push({ type: "more", id: `status:${parent}`, ...
```
  plus the focus-restore in the layout effect for rows that disappear.

### [F-002] `useMetaprojectTree` writes refs during render
- **Severity**: info
- **File**: apps/desktop/src/metaproject/useMetaprojectTree.ts
- **Problem**: on a snapshot change the hook increments `generation.current` and replaces `state.current` in the render body. React asks render to be pure; the write is idempotent here (the second StrictMode render sees the new snapshot and does nothing), so there is no demonstrated wrong behaviour today. Under a discarded concurrent render (a transition that is thrown away and rendered again with the old snapshot) the loaded children would be dropped twice and re-read. No such transition exists in the explorer now.
- **What would settle it**: none needed now; if the explorer ever renders catalog changes inside `startTransition`, move the reset into a keyed state (e.g. `useState` keyed by snapshot, or derive with a `useRef` compared in `useLayoutEffect`).
