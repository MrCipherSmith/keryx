### Findings

### [F-001] Reveal of a selection pages a large folder sequentially, one CLI spawn per 100 entries
- **Severity**: minor
- **File**: apps/desktop/src/metaproject/MetaprojectTree.tsx (reveal effect)
- **Hot path**: once per (folder, snapshot) when the user selects a file from the graph, search results, Back or the details panel and its folder is not yet loaded far enough.
- **Problem**: The reveal effect resolves one step per render: read the ancestor (`model.ensure`), then, if the target is not in the loaded entries, `model.more` for the next page, and repeat. Each step is one `metaproject_request` = one CLI child process (metaproject.rs spawns per request). In this checkout `src/commands` has 479 direct files, `src/review` 374, `src/tui` 339; revealing `src/commands/<late-alphabet>.ts` from a graph click is root + `src` + up to 5 pages of `src/commands` = ~7 sequential reads. At the ~0.8 s per read the flow description cites, the row appears ~5-6 s after the click, and every intermediate page is appended to the visible tree.
- **Why it matters**: Correct and non-blocking (async; UI stays responsive), and the plan explicitly accepts "reveal pages until the row is found", with read latency out of scope. The cost lands on the next stage that tunes latency: a reveal-specific request (e.g. a `tree` request that returns the page containing a given child, or the ancestors' pages in one call) would make it one round trip.
- **Fix**: Track separately with the read-latency stage; no change required for this PR.

### [F-002] New snapshot re-reads every expanded folder concurrently with no limit
- **Severity**: minor
- **File**: apps/desktop/src/metaproject/MetaprojectTree.tsx (`for (const parent of unread) model.ensure(scope, parent)`) with useMetaprojectTree.ts snapshot reset
- **Hot path**: on a snapshot change (rebuild/refresh) while the tree is shown; rare, not per keystroke.
- **Problem**: A snapshot change drops all loaded folders and keeps the expanded set; `flatten` then reports every expanded folder whose parent is loaded as `unread`, and the effect calls `ensure` for all of them at once, level by level. Each is a separate CLI child process loading the graph. The width is the user's expanded set at that level (caller-sized, not fixed small) — async-patterns.mdc Rule 3, which rates unbounded fan-out off a hot path as `minor`.
- **Why it matters**: With a dozen expanded sibling folders a rebuild spawns a dozen concurrent CLI processes. Correct today; a bound is cheap.
- **Fix**: Cap concurrent tree reads (e.g. 4) inside `useMetaprojectTree.read`, queueing the rest; or re-read only expanded folders that are visible.

### [F-003] Every tree state change re-renders the whole Explorer
- **Severity**: info
- **File**: apps/desktop/src/metaproject/useMetaprojectTree.ts (`const [, render] = useReducer(...)` in the hook mounted by Explorer)
- **Hot path**: each expand/collapse (ArrowRight/ArrowLeft, chevron), each page arrival, each `setHandled`.
- **Problem**: Tree state lives in a ref inside the Explorer and is published by forcing an Explorer render, so a folder toggle re-renders the Explorer (graph canvas, panels) and the whole tree (all visible rows, no row memoization). The Explorer's expensive derivations are memoized (graphIndex, nodes, results, layout in RelationshipGraph), so the extra cost is VDOM diffing; no measurement shows it noticeable.
- **Fix**: None needed now; if the tree gets slow with many rows, move the state into a small external store subscribed only by MetaprojectTree, and memoize row components.

### [F-004] Revealing a symbol leaves a scroll request that is never satisfied
- **Severity**: info
- **File**: apps/desktop/src/metaproject/MetaprojectTree.tsx (`scrollRequest.current = selected.kind === "module" ? ... : \`n:${selected.id}\``)
- **Hot path**: every tree render after a symbol is selected elsewhere, until another reveal overwrites it.
- **Problem**: The tree never renders symbol rows, so `n:<symbolId>` is never found; the no-deps `useLayoutEffect` keeps running `querySelectorAll("[data-row]")` and a linear find on every render. Cost is one DOM query per render (small); noted because it is also an unreachable request.
- **Fix**: For a symbol, scroll to its file row (`n:<file id>` is not known from the symbol; alternatively set no scroll request for symbols).

### Clean Areas
- CLI/TUI hot paths: keyboard handling is O(visible rows) per key (`rows.find`/`indexOf`), local `setFocusId` only; focus `onFocus` sets the same id (React bails out). No sync I/O on interactive paths.
- Rust (metaproject.rs): `Tree` validation is O(input length), same as the existing variants; required-action set unchanged.
- Platform transport: `validTree` bounded by `METAPROJECT_PAGE_SIZE_V2`; response size check reuses the existing 1 MiB bound; `actions.includes("tree")` once per negotiation.
- Duplicate reads: `ensure` and `more` are idempotent while a read is in flight (map entry / `more.status === "loading"`); late answers dropped by generation; page append dedupes with one Set per page.
- Memory: loaded folders bounded by the project's index and reset per snapshot; no listeners/timers added; no new dependencies or large imports.
- CSS: no expensive selectors of note.
- N+1 / indexes / pagination: not applicable on the client; server-side tree paging is in a slice not assigned to this reviewer.
