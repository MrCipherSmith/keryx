None forwards a timing value, and handleSessionFlags builds `change` only from archived/pinned/flow/subject, so an ACP client cannot shorten staleMs (which would let it break another writer's lock) or the timeout.
   - `createDir` on FileLockOptions is set only by organize.ts lockOptions (`createDir: false`); every other withFileLock caller keeps the default (mkdir 0o700).
2. Lock file perms/ownership. Unchanged: the lock is still created `openSync(lockPath, "wx", 0o600)` with a per-attempt randomUUID nonce, shared by the sync and async waits (LockAttempt). With createDir false no directory is created at all, so no new directory with default mode appears; the session directory is the store's own. Release still removes only a lock holding this attempt's nonce. Tests: lock files and barrier files live under fresh mkdtempSync dirs in tmpdir (0700); child scripts embed paths only through JSON.stringify, so no path text is evaluated as code. Barrier dirs and organize `project()` roots are not removed after the test (hygiene, not security; the latter predates the range).
3. Error texts sent over ACP (refuseStore -> invalidRequest reason = error.message). New texts: lockedError `the flags of session <id> are locked by another keryx process; retry` and goneError `no session <id> in this project` — both name only the session id the client sent and locate() validated. A raw ENOENT is rethrown only when the session directory still exists after the failure (a race in which it was recreated); that text and other fs errors (e.g. EISDIR from writeOwnerOnlyFileAtomic) carry the absolute session path, as before this range, to the same-user local client that owns that data dir — not a disclosure across a trust boundary, so no finding. issues-board `unusableRemote` is a constant naming no repository.
