### DG-R4-002 trace (the question asked)

1. Dispatch is concurrent. src/acp/server.ts readLoop calls `dispatch(line)` for every framed line without awaiting; `dispatch` starts `dispatcher.handleLine(line)` and only tracks it in `inflight`. The comment above it says handlers "START in wire order" and replies "may land in completion order", and claims "Not awaiting does not reorder anything that matters". `_keryx/session_flags` is wired as `(params) => handleSessionFlags(params)` in the shell-profile request table.
2. Before this range the handler was synchronous: a contended request blocked the whole loop, so the next request could not even start, and wire order was apply order by construction. Now `handleSessionFlags` awaits `setSessionFlagsAsync`, so a second request starts and runs its own wait while the first is parked.
3. Waiters retry on independent timers, not a queue. `withFileLockAsync` does one synchronous `attempt.step()`, then `await setTimeout(RETRY_MS=15)` and `step()` again. Each waiter's ticks are on its own 15 ms grid from its own start. When the foreign holder releases, whichever waiter's next tick comes first takes the lock: request A started at t=0 ticks at 15, 30, …; request B started at t=7 ticks at 22, 37, …; a release at t=16 lets B in at 22 and A at 30. B's change is written first and A's last: wire order A,B, apply order B,A.
4. Without a foreign holder, order is kept: the critical section (`whileStored(dir, apply)`) is synchronous, so a request that gets the lock on its first step writes before anything else runs; a request arriving while it is held (only during the one microtask before `release`) waits 15 ms and goes in after. Waiters started in the same tick fire in registration order.
5. Reachability from one Desktop window. The senders of SESSION_FLAGS are useAcpSession.ts setFlags (sidebar Pin/Unpin, Archive/Unarchive), archiveIdle (archived:true, sequential awaits), applyPendingFlow and linkFlow (flow), and PendingSubjects.write (non-null subject). The sidebar label comes from server-confirmed flags (`label: pinned ? "Unpin" : "Pin"`, `onSelect: () => onSetFlags(s.sessionId, { pinned: !pinned })`, and the state is updated only from the reply via `dispatch({ t: "flags", ... })`), so while a Pin is parked on the lock a second click sends Pin again, not Unpin. Opposite values for one field are therefore not in flight together; requests for different fields commute because each is a read-modify-write under the lock. Desktop sends no `subject: null`. Two different `flow` values for one session (pending flow from a flow-opened new session plus a Link offer on the same session) would be needed for the flow field, and I found no path that puts both on one session at once.
6. Across windows (two processes) there was never a defined order, so that is not a regression of this range.

Conclusion: the reordering is real at the server, and it drops the dispatcher comment's premise for this handler. No current client path produces a wrong final state, so under shared law 1 it is `info`. It becomes `major` (lost user intent on a shared state file) as soon as a client makes the toggle optimistic or adds an unlink while a bind can be in flight.
