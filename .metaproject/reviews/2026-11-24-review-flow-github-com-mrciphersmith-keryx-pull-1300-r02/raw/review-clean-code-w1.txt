#### Functions
[CC4-002] minor — src/session/organize.ts `setSessionFlagsAsync` / `setSessionFlags` / `updateSessionFlagsAt` / `updateSessionFlagsAtAsync`: the test-only `timing` was added as a trailing positional after the optional `now` (and `dataDir`), so setSessionFlags(Async) take 6 positionals and the update pair 4, and test call sites read `setSessionFlags(cwd, id, { pinned: true }, dataDir, undefined, held)` / `updateSessionFlagsAt(trashed, { pinned: true }, undefined, quick)`. Fix: fold the injection knobs into one trailing options object `{ now?, timing? }` on the four functions.

#### Comments
[CC4-003] minor — src/lib/file-lock.ts: `withFileLock`'s doc still says the function "Returns `null` when the lock could not be taken ... rather than a throw", while the new `createDir: false` option (documented on `FileLockOptions`) makes `step()` throw ENOENT, which `withFlagsLock(Async)` catches. `prepare()`'s doc says "Whether the lock's directory is there" but with `createDir: false` it returns `true` without checking. Fix: add the ENOENT throw for `createDir: false` to the `withFileLock` doc (withFileLockAsync points at it), and say in `prepare()` that it creates the directory only when asked.

#### Error Handling
No error-handling issues found. The silent `catch` in `bindIssueSubject` is a fallback with a comment giving the reason (error-handling.mdc: not a finding); `goneError` replacing ENOENT is a plain contextual error inside the module.

#### DRY
[CC4-001] minor — apps/desktop/src/review/ReviewBoard.tsx focus effect: the round-3 fix adds a third copy of the settle sequence `focused.current = focus.nonce; setFocusNotice(...); onFocusHandled?.(focus.nonce);` (lines ~504-506, ~512-514, ~517-520). Before the fix there were two; the threshold (3 copies) is now crossed. Each new refusal branch must remember all three steps; missing `onFocusHandled` leaves the App's request armed (the FE-R3-001 shape). Fix: a local `settle(notice: string)` that marks the nonce, sets the notice and calls `onFocusHandled`, used by all three branches.

withFlagsLock / withFlagsLockAsync repeat their catch-and-map block twice: 2 copies, under threshold, not reported.

No SOLID issues found. `LockAttempt` holds one responsibility (one acquisition's rules) and both waits share it. `bindIssueSubject(dir, ref, firstBind)` takes a boolean that selects fail-loud vs best-effort, but its one call site passes a named variable, not a literal (under the threshold's stated condition).
