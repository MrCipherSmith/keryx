### DG-R4-002 (asked to settle): no finding
- The server can now apply two flags requests for one session out of arrival order. server.ts:3356-3385 starts each line's handler in wire order and does not await it. handleSessionFlags now awaits `setSessionFlagsAsync`, and each request runs its own `LockAttempt` that retries on a separate 15 ms `setTimeout` (file-lock.ts withFileLockAsync), with no queue per lock path. While another process holds `flags.json.lock`, the first timer to fire after the release wins. Without contention nothing is reordered: `step()` and the synchronous section run in the same tick as the request starts (prepare → step → `await fn()` with a synchronous fn), and the release happens on the microtask queue before the next I/O macrotask. A reply is written after its section has run, so replies leave in the order the changes were applied.
- No Desktop path produces a lost or wrong result from that reordering. These are every sender of `_keryx/session_flags` (found with `keryx ctx rg "SESSION_FLAGS"` and `setFlags\(` in apps/desktop/src):
  - SessionSidebar.tsx:183/190 sends `{pinned: !pinned}` and `{archived: !archived}`. `pinned`/`archived` come from the stored flags, and useAcpSession.setFlags updates them only from the reply, without an optimistic update. A second click while the first request is pending sends the same value again. Opposite values (pin, then unpin) can be sent only after the first reply, when the first change is already applied.
  - Requests for different fields: archiveIdle (`archived: true`), applyPendingFlow and linkFlow (`flow`), PendingSubjects.write (`subject`). Each runs applyFlagsChange, which reads the current flags inside the lock, so both changes survive in either order. `pinnedAt ??=` and `archivedAt ??=` make a repeated `true` independent of order.
  - The last reply holds the merged state, because replies leave in the order the changes were applied.
- So the pin-then-unpin case DG-R4-002 describes cannot be produced by the current client. A client that toggled optimistically would expose it. That is a hypothetical, so it is not filed (shared law 2).
