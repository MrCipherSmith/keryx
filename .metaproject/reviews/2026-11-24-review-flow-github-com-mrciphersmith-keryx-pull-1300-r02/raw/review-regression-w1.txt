## What was checked (scope B: what existing behaviour the fixes could break)

1. Shared `src/lib/file-lock.ts` refactor (withFileLock split into LockAttempt + withFileLock/withFileLockAsync, new `createDir` option).
   Callers enumerated with `keryx ctx rg --all 'from "(../)*(lib/)?file-lock"|from "./file-lock"' src`:
   src/lib/project-registry.ts, src/mcp-servers/credentials.ts, src/lib/serve-credential.ts, src/worktree/ports.ts,
   src/worktree/promote.ts, src/lib/config-update.ts, src/lib/permission-mode-config.ts (all `withFileLock`, default options),
   src/session/organize.ts (the only `createDir: false` / async user), src/lib/serve-credential.waiting.test.ts (LOCK_STALE_MS only).
   (The many other `withFileLock` hits — slate, flow/service, learning/store, external-slate — import the different
   primitive in `src/lib/fs.ts` and are untouched.)
   Default-option behaviour compared line by line against base:
   - mkdir of the lock directory (mode 0o700) still runs first when `createDir` is absent; a mkdir failure still returns null.
   - deadline is still checked before every attempt, including the first; timeout still returns null.
   - exclusive create + nonce write; a nonce write failure still closes and removes the half-made lock and retries.
   - every open failure (EEXIST, EACCES, ENOENT …) still falls through to the stale check, the one-time onWaiting
     announcement after 1 s, and a 15 ms sleepSync — the ENOENT rethrow is gated on `createDir === false` only.
   - release still removes the lock only when it holds this holder's nonce; fn's throw still propagates after release.
   - the inline options type became the exported `FileLockOptions` with the same four fields plus optional `createDir`,
     so no caller's argument stops type-checking.
   Result: no default-option caller changes behaviour on any reachable path.
   Below-threshold observation (not filed; law 1, no reproducible trigger): on base, a closeSync/rmSync failure in the
   nonce-write-failed branch was swallowed by the outer catch and the loop retried; on head it escapes `step()` and
   withFileLock throws instead of returning null. Reaching it needs a write failure right after an exclusive create
   succeeded AND the close or unlink of that same file then failing — no input in this codebase reaches that.

2. `handleSessionFlags` becoming async in `src/acp/server.ts`.
   Its only caller is the request table entry `[KERYX_ACP_EXTENSION_METHODS.sessionFlags]: (params) => handleSessionFlags(params)`
   (server.ts:3307), in the same table as the already-async `handleSessionNew` / `handleSessionLoad` / `handleSessionPrompt`,
   so the dispatcher already awaits promises and maps rejections; `refuseStore`'s throw becomes a rejection with the same error.
   Uncontended, `withFileLockAsync` takes the lock synchronously and only awaits microtasks, so no other request can
   interleave where it could not before; under contention it now yields instead of freezing the event loop (the HL3-001 fix).
   A concurrent `_keryx/session_trash` during that wait now lands before the flags write; the write then sees ENOENT
   (createDir false) or a missing summary.json and refuses with "no session … in this project" — the intended outcome.
   The sync `setSessionFlags` keeps its signature (new trailing optional `timing`) for its other production caller,
   src/session/issues/issues-launch.ts:116; that caller first locates the session through findSession, so the new
   `whileStored` summary.json check is no stricter than what it already required.

3. Issues source storage key (`apps/desktop/src/issues/IssuesBoard.tsx`).
   New key `keryx.issues.<viewer>.source.<JSON cwd>`; the read is `stored(sourceKey) ?? stored(account + ".source")`, so a
   choice an existing user stored per account under the earlier Desktop is still honoured in every project until they
   choose in that project; the old key is never deleted or overwritten. `keryx ctx rg --all '\.source"|keryx\.issues\.'
   apps/desktop/src` finds no other reader of the per-account key. Behaviour shift for an explicitly chosen "repository"
   source (the fallback button now shows for it too) is the recorded owner choice, not a regression.
