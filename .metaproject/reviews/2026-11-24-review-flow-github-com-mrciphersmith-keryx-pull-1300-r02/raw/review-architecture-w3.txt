### Summary
The backend half of the fix round does four things. It splits lib/file-lock into one `LockAttempt` (exclusive create, nonce, deadline before stale, stale takeover, nonce-checked release) driven by a blocking loop (`withFileLock`) and a yielding loop (`withFileLockAsync`). It gives the session flags store a matching async entry (`setSessionFlagsAsync` / `updateSessionFlagsAtAsync`) that the ACP server now awaits. Taking the flags lock no longer creates the session directory (`createDir: false` plus `whileStored`). The issue-subject backfill is fatal only on the first bind. Dependency direction stays inward: acp/server → session/organize → lib/file-lock, and session/issues/issue-session → session/organize. lib/file-lock imports nothing from the domain. No new findings in this lens. AR-R4-001..003 are not filed again.

### Design Pattern Misuse
None detected. Sync and async lock drivers: the shared `LockAttempt` is the single implementation of the locking rules, and the two exported functions differ only in how they pause (sleepSync vs setTimeout). The lock-file protocol is the same, so a sync holder in the issue-workspace child excludes the async server waiter and the reverse. The docstrings state this choice, and I accept it (law 4). The two near-identical wrappers `withFlagsLock` / `withFlagsLockAsync` (try/catch → goneError, null → lockedError) are a duplication question. They belong to review-clean-code under this lens's Scope Boundaries, so I do not file them here.
