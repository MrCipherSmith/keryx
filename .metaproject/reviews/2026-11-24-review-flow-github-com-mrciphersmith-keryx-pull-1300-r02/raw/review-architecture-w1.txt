### Module Boundary Violations
[AR-R4-001] minor: Desktop's repository-unavailable classifier matches backend prose instead of a shared contract value (residual of AR-007).
- File: apps/desktop/src/issues/useIssueCollection.ts (repositoryUnavailable)
- Problem: `repositoryUnavailable` decides the fallback from three regexes over human-readable sentences. Each is defined in a different backend module: "This project has no GitHub.com fetch remote." in src/review/board-github.ts:45 (the PR board's resolver), "GitHub has Issues turned off for ${repository}" in src/integrations/issues-board.ts:188, and the new exported `unusableRemote` in src/integrations/issues-board.ts:114. The "older keryx" case still matches the `invalidInput` text from src/integrations/issues-github.ts. The fix exported `unusableRemote` as a constant, but Desktop does not import it. Desktop already imports runtime values (issueKey, issueViewerKey) from src/integrations/issues-contract, so a shared constant or a reason code is one import away.
- Why it matters: trigger: any rewording of one of those sentences, most likely the PR board's message in board-github.ts, which is edited for PR-board reasons. Outcome: the Issues board silently drops the "Show issues assigned to me" fallback and shows Retry for a project with no GitHub.com remote. Nothing goes red. The backend tests pin the backend strings, and IssuesBoard.dom.test.tsx:469-471 repeats the literals by hand, so no test spans the boundary.
- Fix: give these failures a contract-level reason, for example a `repository_unavailable:` prefix or exported constants in src/integrations/issues-contract.ts that issues-board.ts and board-github.ts throw. Then have `repositoryUnavailable` (and its test fixtures) import them instead of restating the prose.
