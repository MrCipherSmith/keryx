### Logic Bugs

#### [F-001] Single-quote fix for `--task-text` is stated at 1 of 6 instruction sites; the other 5 give no escape rule

- **Severity**: major
- **File**: src/gdskills/bundled/skills/orchestration/task-implementer/SKILL.md
- **Problem**: The r02 security finding was that a double-quoted task description lets the shell run backticks and `$(...)`. The fix switches every site to single quotes, but only flow-orchestrator adds the rule that makes single quotes safe: "Write the text single-quoted (a `'` inside it becomes `'\''`)". task-implementer, job-orchestrator (2 sites), orchestrator-prompt (2 sites) and tests-creator now say only `--task-text '<...>'`. A worker substituting a description that contains an apostrophe, which task descriptions routinely do, produces a broken command. Example: `--task-text 'Don't touch the user's menu' --out x` parses as `Dont` (one argument) then `touch the user` as stray arguments then `s menu`; `optionValue` takes `Dont` and the rest of the text never reaches the resolver, so a keyword in the cut-off part cannot promote its reference. The failure is silent for even-apostrophe text and a hung or failed shell for odd-apostrophe text. In the odd case the unquoted remainder is also exactly the `$(...)` execution path the change was meant to close.
- **Why it matters**: The feature's purpose is that a keyword in the task text promotes a document to `must_read`. With the text silently cut at the first apostrophe, the promotion is lost for those tasks, and the prior security major is only partly closed.
- **Fix**: Put the escape sentence at every site, or better, point each site at one place that states it (or pass the text via a file or stdin if the CLI supports it). Minimal wording for each site: "single-quoted; a `'` in the text becomes `'\''`".
- **Evidence**: `keryx ctx rg "'\\\\''"` over `src/gdskills/bundled/skills` and `.metaproject/skills/gdskills/orchestration` returns only the two flow-orchestrator files. The other sites were listed with `keryx ctx rg "task-text [\"']"` and the `grep -o` of the tests-creator line (`--task-text '<task description>' --out <project-relative path>`).
- **Quote**: `--task-text '<task.description>'`
- **Confidence**: medium (the harm depends on the worker not escaping unprompted; the instruction is what the worker is told to follow)
- **class_scope**:
  - sites: `src/gdskills/bundled/skills/orchestration/task-implementer/SKILL.md` (line 182), `src/gdskills/bundled/skills/orchestration/job-orchestrator/SKILL.md` (lines 749, 1307), `src/gdskills/bundled/skills/orchestration/job-orchestrator/orchestrator-prompt.md` (lines 132, 188), `src/gdskills/bundled/skills/quality/tests-creator/SKILL.md` (line 93), and the managed copies of each under `.metaproject/skills/gdskills/` (byte-identical, `cmp` confirmed for the four orchestration files); `src/gdskills/bundled/skills/orchestration/flow-orchestrator/SKILL.md` (line 323) already states the rule
  - enumeration_method: `keryx ctx rg --hidden "task-text [\"']"` over README.md, docs, src, .metaproject/skills, .metaproject/core excluding reviews and flows (19 matches, 13 files), then `keryx ctx rg -c "'\\\\''"` to find which carry the escape rule (2 files, both flow-orchestrator). The literal examples in docs and live-run.md are fixed strings and are safe.

### Async & Concurrency

#### [F-002] `applied` is advanced after the subscribers run, so a throwing subscriber lets an older load overwrite a newer status

- **Severity**: minor
- **File**: src/tui/project-context-inspector.ts
- **Problem**: In `reload`, `current = next` and the `for (const listener of [...listeners]) listener(next)` loop run before `applied = Math.max(applied, mine)`. If a listener throws (the sidebar repaint or modal paint on a destroyed renderable, as in review-clean-code-w5:F-003), the function exits before `applied` is updated. A slower, older load that finishes next then passes `mine > applied` and replaces `current` with older data. The ordering guard this delta adds is therefore bypassed in exactly the case the subscribers are failing. The throw also skips any listener after the failing one and is reported by `poll` as a failed load.
- **Why it matters**: Narrow trigger (a throwing subscriber plus overlapping loads), outcome is a stale sidebar or tab until the next poll five seconds later.
- **Fix**: Advance `applied` before notifying, and isolate listener errors:
  ```diff
  -    if (mine > applied && !sameStatus(current, next)) {
  -      current = next;
  -      for (const listener of [...listeners]) listener(next);
  -    }
  -    applied = Math.max(applied, mine);
  +    const fresh = mine > applied;
  +    applied = Math.max(applied, mine);
  +    if (fresh && !sameStatus(current, next)) {
  +      current = next;
  +      for (const listener of [...listeners]) {
  +        try { listener(next); } catch { /* one broken subscriber must not starve the others */ }
  +      }
  +    }
  ```
- **Evidence**: Read at head, `reload` lines 172-182; R7 test (project-context-inspector.test.ts line 515) covers ordering only with non-throwing subscribers.
- **Quote**: `applied = Math.max(applied, mine);`
- **Confidence**: medium

#### [F-004] The new `polling` latch never clears if a load never settles

- **Severity**: info
- **File**: src/tui/project-context-inspector.ts
- **Problem**: `poll` returns early while `polling` is true and clears it only in `finally`. If `options.load` returns a promise that never settles (the load reads project files, so a stalled network or FUSE mount would do it), no later tick ever loads again and the sidebar and open tab stop following the project for the rest of the session. Before the latch, each tick started its own load. No path in this repo is known to hang: `loadProjectContextStatus` is plain file reads. I could not reproduce it, so this is an observation.
- **Why it matters**: Only on a stalled filesystem; the trade-off against the pile-up the latch removes is reasonable.
- **Fix**: Optional: reset the latch after a timeout (for example 3 x `pollMs`), or document the assumption on the latch comment.
- **Evidence**: Read `poll` at lines 184-197. Settling would be shown by a load wrapper with a deadline; none exists.
- **Quote**: `if (polling) return;`
- **Confidence**: low
