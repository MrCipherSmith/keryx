CONFIRMED, severity major (by the project table, which the reviewer is required to apply verbatim).
- Line 204 is a time-based assertion on real elapsed time; line 203 drives a real 50 ms setTimeout through compareHeads. No fake clock is installed. Both match the table's "finding when" column, and neither matches the "not a finding" column. The table gives no lower severity for this row.

Part of the stated impact is overstated (does not change the verdict):
- The claim that head d can be reported late if 50 ms pass before its task runs is effectively unreachable. mapPool (src/lib/map-pool.ts:10) starts both workers synchronously inside Array.from, so `left` at line 91 is computed in the same synchronous run as line 87 (left = 50 unless a >=50 ms stop-the-world pause hits between two adjacent statements). Then Promise.race against an already-resolved Promise.resolve settles in a microtask, which always precedes the timer macrotask even if left were 1 ms. So `commits: 1` is not a realistic flake source.
- The reachable flake source is line 204 alone: it bounds the whole readReviews call (SQLite store open, card read, compare) at 2 s, tighter than bun's default 5 s per-test timeout. Observed run: 16 tests in 8.79 s (about 0.55 s per test average), so a single test approaching 2 s under heavy machine load is plausible, not demonstrated.

Is the elapsed assertion needed to catch a broken deadline? No, for the realistic breaks:
- Deadline removed (no race / timer never resolves): head e's compare never settles, readReviews never resolves, bun's 5 s per-test timeout fails the test. Line 207/208 also could not pass.
- compareBudgetMs ignored (falls back to REVIEW_COMPARE_BUDGET_MS = 60_000): readReviews takes 60 s, bun timeout fails the test.
- Mutant R2-R08 (late flag not set on timeout): line 208 fails (warning missing).
- The only breaks caught by line 204 and by nothing else are a deadline that fires late but within 2-5 s (for example the budget scaled by 40-100x). That is a narrow, unlikely mutant class. The reviewer's suggested fix (drop line 204, rely on the per-test timeout, control the deadline via fake timers or a seam) loses essentially no detection power.
- Note: the `left <= 0` branch (R2-R07) is not driven by this test at all, as the reviewer already says; a deterministic clock would make it drivable.
