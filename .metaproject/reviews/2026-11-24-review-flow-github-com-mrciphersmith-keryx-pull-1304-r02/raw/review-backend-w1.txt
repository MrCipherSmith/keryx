## Minor & Info

### [R2-BE-001] The compare deadline does not end the `gh` children, so the process outlives the budget
- **Severity**: minor
- **File**: src/commands/review-reviews.ts:94 (compareHeads), :133 (compare closure)
- **Problem**: `Promise.race([compare(...), expired])` stops waiting at the deadline, but the losing `compare` is still a running `boardGh` → `exec(gh, ..., { timeout: 18_000 })` child. The CLI ends by setting `process.exitCode` (cli.ts:214), not by calling `process.exit`, so the event loop stays alive until those children end. That can take up to 18 s after the JSON is written, with up to 4 of them in flight. Desktop's `run_bounded_with_stdin` (child.rs:71) waits for the process to exit within 150 s, not for stdout. The card phase also has no budget: there are ceil(batches/3) slots of up to 18 s each. Worst case is 18 (identity) + cards + 60 + 18. That passes 150 s once there are more than about 120 open Reviews and GitHub stalls, and Desktop then shows an error instead of the list.
- **Why it matters**: F-025 asked for an end-to-end bound under the host's 150 s reader. The budget only bounds how long the function waits, not how long the process runs.
- **Fix**: Give the comparison the time that is left. Add `timeoutMs` to `CompareHeads` and pass `Math.min(left, 18_000)` to `boardGh(cwd, args, auth, timeoutMs)` in runReviewReviews, so the child is killed at the deadline. Optionally start the deadline when readReviews starts, so the card phase is inside it too.
- **Disposition link**: F-025 → partial.

### [R2-BE-002] `headComparison` says it is "the one rule" for freshness, but `summarizeReview` does not use it
- **Severity**: minor
- **File**: src/review/review-entity.ts:156-157, :190
- **Problem**: `headComparison` returns null for a closed Review (closed locally, or merged or closed on GitHub). `summarizeReview` still computes `freshness(referenceHead(row), card?.headSha, compare)` with no closed check. A merged PR whose final head differs from the reviewed head, or a locally closed Review read with `--include-closed`, therefore reports `freshness: {kind:"behind", commits:null}` while no comparison is made. The new test "summarizeReview reports behind exactly when a comparison is needed" covers only an open Review, so it cannot catch this.
- **Why it matters**: F-015 asked for one domain rule used by both the command and summarizeReview. The command uses it and summarizeReview does not, and the docstring states otherwise.
- **Fix**: Either derive freshness in summarizeReview from `headComparison` (a closed Review with a known card is `current`, or skip the behind state for closed Reviews), or narrow the docstring to "the rule for which pairs the command compares". Add a closed-or-merged case to the "exactly when" test.
- **Disposition link**: F-015 → partial.

### [R2-BE-003] The cap warning still says "Refresh to read more", but a refresh compares the same 25
- **Severity**: minor
- **File**: src/commands/review-reviews.ts:60
- **Problem**: The comparisons now follow list order, newest activity first, which is deterministic. Refreshing without new activity compares the same 25 pairs again, so the warning promises an action that does nothing.
- **Fix**: Drop "Refresh to read more." (for example: "Commit counts are shown for the 25 most recently active Reviews behind their pull request."), as F-022 already suggested.
- **Disposition link**: F-022 → partial (the ordering is fixed; the warning text is not).

### [R2-BE-004] The header comment still calls `review reviews` a "Read-only list"
- **Severity**: minor
- **File**: src/commands/review-reviews.ts:1
- **Problem**: The CLI reference and the PR body now say the read opens the store for writing and migrates an older `runs.sqlite`. The module header still says "Read-only list of local Reviews", and F-020 named this exact comment.
- **Fix**: `// List of local Reviews for the Desktop Reviews tab: \`keryx review reviews --json\`. Opens the store writable, so a pre-Reviews store is migrated by the first read.`
- **Disposition link**: F-020 → partial.

### [R2-BE-005] The PR body's store rule no longer matches round placement
- **Severity**: info
- **File**: PR body (pr-context.md:14), against src/review/desk-run-store.ts:243-256
- **Problem**: The body says "the same base..head joins its existing round as a retry". After the F-008 fix, `roundFor` treats only a repeat inside the current highest round as a retry. A return to an earlier range (A, B, A) opens the next round, which the new store test pins.
- **Fix**: Change the bullet to "the same base..head within the current highest round is a retry; any other range, a return to an earlier one included, opens the next round."

### [R2-BE-006] A fully archived Review that was published reports `state: "ready"` and `publication: null` in the JSON
- **Severity**: info
- **File**: src/review/desk-run-store.ts:619, src/review/review-entity.ts (summarizeReview)
- **Problem**: reviewRows reads no publication for archived attempts, so they get null. When every attempt is archived, summarizeReview takes its state from them, and `reviewState` returns `ready` rather than `published`. The CLI reference says archived attempts "do not decide the state", but in the all-archived case they do. Desktop hides this by showing "Archived", so only JSON consumers see it.
- **Fix**: Read the publication for archived attempts too, and leave them out only of `reviewNeedsViewer`. Or document that a fully archived Review's state ignores its publication.
