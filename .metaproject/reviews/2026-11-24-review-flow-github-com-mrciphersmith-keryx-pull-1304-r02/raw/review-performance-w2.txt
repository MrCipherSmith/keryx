### Findings

### [P2-001] Turning "Show closed" off runs a full GitHub-backed list read, although the list on screen already contains every Review it needs
- **Severity**: minor
- **File**: apps/desktop/src/reviews/ReviewsView.tsx:175 (load effect deps), :152
- **Hot path**: once per click of the "Show closed" toggle, and once when `resetView()` turns `showClosed` back off after an identity change. These are user actions, not a hot loop.
- **Problem**: `showClosed` is now a dependency of the load effect, and its value is passed to the CLI as `--include-closed`. Turning it on needs a new read, because the PR cards of locally closed Reviews are only fetched with the flag. Turning it off does not: the snapshot read with `includeClosed=true` already contains everything the list needs, and `filterReviewList(..., showClosed=false)` hides closed and archived Reviews on the client (model.ts `isClosedOrArchived`). The effect still spawns `keryx review reviews` again. That read runs the identity GraphQL query, ceil(N/20) card batches and up to 25 compares. The read lane does not dedupe it, because `includeClosed` is part of the lane key (platform/review.ts:117-119).
- **Why it matters**: each click that turns the filter off costs one CLI spawn and several GitHub round trips, which takes seconds and uses API budget. During that time the toolbar spinner shows, for a change the client could make instantly. The cost grows with lifetime Review history (round-1 F-023, still partial). It is correct today; the cost is on interaction latency and the GitHub budget.
- **Fix**: read with the flag only when it adds data. Keep a ref with the `includeClosed` value of the current snapshot, and skip the reload when `showClosed` goes from true to false while that snapshot already holds the closed cards. Alternatively, key the effect on a derived "needs closed cards" value that stays true once a closed-inclusive snapshot is held, until the next refresh. Do not change the request on toggle-on.

### [I2-001] Opening a closed or archived Review from the Pull requests tab costs a second full list read
- **Severity**: info
- **File**: apps/desktop/src/reviews/ReviewsView.tsx:238 (`if (isClosedOrArchived(found)) setShowClosed(true);`)
- **Hot path**: one "Open in Reviews" click on a PR whose Review is closed locally or archived.
- **Problem**: the tab-show refresh reads the list without `--include-closed`. The focus effect then finds the Review and sets `showClosed`, and that triggers a second full `review reviews` read so the PR card can be fetched.
- **Why it matters**: it costs one extra read for each such click. The first read cannot be avoided in this design, because the closed state is only known after it, so this is not a defect.
- **Fix**: optional. A `ReviewsFocus` could carry a hint (the board knows the badge is archived) so the first read includes closed Reviews.

### Clean Areas
- **React re-renders.** `onIdentityChange` fires only on identity change, because `watcherTarget` is a `useMemo` on primitives (ReviewBoard.tsx:421). `openReview` depends on the primitives `boardRepo` and `boardRepositoryId`. `consumeIntent` returns the same object when there is no intent, so it causes no extra render. `openPullRequestLink` is a `useCallback`. The ReviewBrowserLink click closure is per render on a single anchor, which is negligible. App's `watcherPolls` state re-renders App once per watcher poll (at least 1 min apart), which is negligible.
- **Memory leaks.** The interval is cleared. `subscribeSessionReview` returns its unsubscribe. The keydown listener is removed. `mounted` refs are reset on unmount.
- **Hot paths, CLI and Rust.** The new argument checks in `reviewBoardArgs` and `board_read_args` are constant-time.
- **Bundle imports.** The one new import (`githubPr` in ReviewBrowserLink) was moved from ReviewDetail, so it adds no net code.
- **N+1, indexes, pagination.** This slice has no database or list query code. The backend is in other slices.
- **Synchronous blocking.** None was added.
