### Module Boundary Violations

#### [F-001] `freshness()` and `headComparison()` still decide "behind" by two rules; the helper's doc claims one
- **Severity**: minor
- **File**: src/review/review-entity.ts:155-162 (helper), :110-115 (`freshness`), :187 (`summarizeReview` freshness call)
- **Problem**: FA-5 asked for one domain helper used "by the command and by `freshness`". `headComparison` (used by `src/commands/review-reviews.ts:57`) returns null for a closed Review (`!reviewClosed(row, card)`), but `summarizeReview` computes `freshness(referenceHead(row), card?.headSha ?? null, compare)`, which shares only `headsDiffer` and has no closed check. The doc comment at :155-156 says "The one rule for the command's comparisons and for `freshness`", which the code does not do. The test "summarizeReview reports behind exactly when a comparison is needed" (review-entity.test.ts, slice lines 778-785) only checks open Reviews, so the "exactly" claim is unpinned for the closed case.
- **Why it matters**: For a Review closed locally or a merged/closed PR whose head differs from the reviewed head (visible under "Show closed" with `--include-closed`), the summary reports `behind` with `commits: null` while no comparison is ever made, i.e. a permanent "unknown count" that no refresh resolves. The duplication round 1 named (F-015) is narrowed, not removed: a future change to the closed rule changes the comparison set but not reported freshness.
- **Fix**: Derive freshness from the helper: in `summarizeReview`, `const pair = headComparison(row, card); freshness = !card?.headSha ? unknown : pair ? behind(compare) : current` (or have `freshness` take the pair), or drop the "one rule ... for `freshness`" sentence and decide explicitly what a closed Review's freshness is. Extend the "exactly" test with a closed Review.

#### [F-002] Desktop `reviewedCommit` fallback still re-derives the domain's reference head from rounds
- **Severity**: minor
- **File**: apps/desktop/src/reviews/model.ts (slice lines 266-271: `review.reviewed?.headSha ?? review.rounds[0]?.headSha`)
- **Problem**: F-005's fix makes Desktop render the domain's `reviewed` (closed for the stated trigger). When `reviewed` is null, Desktop falls back to `rounds[0].headSha` (the highest-numbered round's first attempt, built by `roundsOf(row.attempts)` over all attempts, archived included), while the domain's freshness is measured from `referenceHead(row)`'s fallback: the head of the newest unarchived attempt (`stateAttempts`, review-entity.ts:137-140). The two coincide in the common case but diverge when the highest round is wholly archived, or when a continuation of an older attempt joins a lower round after a higher one exists (`roundFor` keeps continuations in their predecessor's round, desk-run-store.ts:107-108). The rule "which head is the Review measured from" is again computed on both sides of the CLI boundary, which is the class F-005 was about.
- **Why it matters**: In those cases the card shows one commit and a freshness measured from another, with no error. Narrow trigger (no finished reviewed attempt, plus archive or late continuation), hence minor.
- **Fix**: Emit the reference head itself on `ReviewSummary` (e.g. `referenceHead: string | null` from `referenceHead(row)`, or make `reviewed` fall back explicitly in the domain) and render only that in Desktop; delete the `rounds[0]` fallback.

#### [F-003] Review-rules fallback from the PR board can target another repository when the Reviews tab is on its default repository
- **Severity**: minor
- **File**: apps/desktop/src/reviews/ReviewsView.tsx:273-276 (`rulesTarget` fallback), App.tsx:227/643 (`boardIdentity` -> `rulesTarget`)
- **Problem**: Sibling of round-1 F-001's class (cross-tab repository identity). FB-10 passes the PR board's verified identity to the Reviews tab for when the list read fails. The guard checks the repository only when the Reviews tab has an explicit selection: `(!repo || boardRules.repo.toLowerCase() === repo.toLowerCase())`. Both views hold independent `repo` state initialised to undefined (= default repository) (ReviewsView.tsx:88, ReviewBoard.tsx:95). If the user switched the Pull requests board to repository B and the Reviews tab is still on its default A when its read fails (non-access error), `!repo` is true and the Review rules button in the Reviews toolbar opens B's rules.
- **Why it matters**: The rules dialog the Reviews tab offers belongs to a repository other than the one the tab shows. Only in multi-repository projects with a failed Reviews read; the dialog's own target is the guard against acting blindly.
- **Fix**: Compare against the repository the failed read was for (the default repository's name, or the identity of the last successful Reviews read) instead of skipping the check when `repo` is undefined; or accept the board identity only when `boardRules.repo` is the project's default repository while `repo` is undefined. Add a DOM test with a board on repository B.
