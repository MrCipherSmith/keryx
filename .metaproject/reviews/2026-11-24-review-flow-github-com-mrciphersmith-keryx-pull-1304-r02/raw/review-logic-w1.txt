### Logic Bugs

#### [F-001] The locally-closed card skip keys on `reviews.closed_at`, which nothing writes
- Severity: minor
- File: src/commands/review-reviews.ts (`const cards = await readCards(snapshot, includeClosed ? rows : rows.filter(row => row.closedAt === null), query);`)
- Problem: FA-7 / the operator answer ("locally closed Reviews fetch their cards only while 'Show closed' is on") is implemented as a filter on `row.closedAt`, which comes from `reviews.closed_at`. Across `src`, `apps/desktop/src` and `apps/desktop/src-tauri`, `closed_at` appears only in the `CREATE TABLE reviews` DDL (desk-run-store.ts:155) and the `reviewRows` SELECT (:593); the only writer is the test helper `editStore("UPDATE reviews SET closed_at=? ...")` in review-reviews.test.ts:225. No product path closes a Review locally in this PR.
- Impact: In production every Review has `closedAt === null`, so the filter never removes a row: a Review whose PR is merged or closed on GitHub (the population round-1 F-023 was about) still has its PR card read on every `review reviews` call (window open, tab show, focus, watcher-poll signal, the 60 s running reload). Turning "Show closed" on now triggers an extra full read with `--include-closed` that returns the same cards. F-023 is recorded fixed; only its parallel-batch half (mapPool, CARD_PARALLEL=3) changes behaviour. No wrong value is shown, so minor.
- Suggested fix: Either say in fix-round-1 / the CLI reference that the skip is plumbing for the stage-3 "close Review" action and record F-023 as partly addressed, or give `closed_at` a writer now (e.g. set it when a read observes the PR card `merged`/`closed`, from a write lane rather than this read), so merged PRs stop being re-read.
- Evidence: `keryx ctx rg --all -n "closed_at|closedAt\s*[:=]|closeReview|close_review" src apps/desktop/src apps/desktop/src-tauri`: DDL at desk-run-store.ts:155, read at :593/:612, test write at review-reviews.test.ts:225, nothing else.
- Confidence: high

#### [F-002] `freshness` and `headComparison` still disagree for a closed Review, despite "one rule"
- Severity: minor
- File: src/review/review-entity.ts (`if (!headsDiffer(reviewedHead, prHead) || compare?.status === "identical") return { kind: "current" };`)
- Problem: FA-5 / round-1 F-015 asked for one domain rule deciding "needs a commit-count comparison", and `headComparison`'s doc says "The one rule for the command's comparisons and for `freshness`". But `freshness` does not call `headComparison`; it uses `headsDiffer` only. For a Review whose PR is merged/closed with a head past the reviewed head, `headComparison` returns null (never compared) while `summarizeReview(...).freshness` is `{ kind: "behind", commits: null }`.
- Impact: Named input: a PR merged after more commits were pushed since its last review, listed under Show closed. Its card reads "behind" with no count, permanently, and none of the warnings is added, while the CLI reference says unknown counts come with a warning. The new test "summarizeReview reports behind exactly when a comparison is needed" only uses open cards, so it does not see this; the previous test in the same describe already asserts `headComparison(row, card({ headSha: c, state: "merged" }))` is null.
- Suggested fix: Derive freshness from the same predicate (e.g. in `summarizeReview`, a closed Review with differing heads reports a defined kind, or `freshness` takes `headComparison`'s result), and add the merged-card case to the "exactly" test.
- Evidence: review-entity.ts:110-115 (freshness), :155-162 (headComparison, its doc comment), :190 (summarizeReview uses freshness, not headComparison); review-entity.test.ts headComparison describe.
- Confidence: high

#### [F-003] Reviewed commit and freshness can name different heads when the newest round is archived
- Severity: minor
- File: apps/desktop/src/reviews/model.ts (`const head = review.reviewed?.headSha ?? review.rounds[0]?.headSha ?? "";`)
- Problem: With no finished reviewed attempt, Desktop falls back to `rounds[0].headSha`. `rounds` is built from `row.attempts` including archived ones (review-entity.ts:193), while the domain's `referenceHead` (the head freshness is measured from) uses only unarchived attempts (`stateAttempts`). The comment says the fallback is "the latest requested head".
- Impact: Input: round 1 has unarchived failed attempts on head X, round 2 (head Y) has only archived attempts, nothing finished. Card, list and panel show `Y` as the reviewed commit while freshness was computed from `X`. Wrong value, rare input, low cost.
- Suggested fix: Have the backend expose the reference head it used (e.g. `reviewed` stays the finished range, plus the fallback requested head from `referenceHead`), or compute the fallback from the newest unarchived attempt on the Desktop side.
- Evidence: model.ts:54-56; review-entity.ts:132-141 (stateAttempts, referenceHead), :193 (`rounds: roundsOf(row.attempts)`).
- Confidence: medium

- Confidence: high

#### [F-005] Fallback Review rules can target the board's repository while the Reviews tab is on the default one
- Severity: info
- File: apps/desktop/src/reviews/ReviewsView.tsx (`(!repo || boardRules.repo.toLowerCase() === repo.toLowerCase()) ? boardRules : null);`)
- Problem: When the Reviews list read fails and no repository was picked in the Reviews tab (`repo` undefined, so the default repository was requested), the fallback accepts the Pull requests board's identity whatever repository the board is on. If the board was switched to a non-default repository, the Reviews toolbar opens Review rules for that repository while the tab (with no snapshot, so no repository label) is about the default one.
- Impact: Possible confusion about which repository's rules are edited; only while the list read fails in a multi-repository project.
- Suggested fix: Pass the board's default-repository flag, or accept the fallback only when `boardRules.repo` equals the first entry of the board's repositories when `repo` is undefined.
- Evidence: ReviewsView.tsx:273-276; App.tsx passes `rulesTarget={boardIdentity}` fed by ReviewBoard `onIdentityChange(watcherTarget)`.
- Confidence: medium
