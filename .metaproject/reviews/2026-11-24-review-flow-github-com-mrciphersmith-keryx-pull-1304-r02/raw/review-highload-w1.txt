### [F-001] A refresh that should pick up a just-made change can join an older in-flight read
- Severity: minor
- File: apps/desktop/src/reviews/ReviewsView.tsx:198 (also :199-204 and the panel-mutation observer below :258). Root: apps/desktop/src/platform/review.ts:117-119 with apps/desktop/src/platform/reviewReadLane.ts:13-14
- Pattern: Caching C1, a stale read after a write. Coalescing drops the re-run.
- Failure mode: `refresh()` bumps `attempt`, and the load effect calls `fetchReviews(cwd, repo, viewer, showClosed)`. The lane key does not change with the trigger (`[cwd, expectedViewer, repo, includeClosed]`), so `reviewLists.read` returns the promise already in flight (`const current = this.active.get(key); if (current) return current;`). That CLI read its store rows (`readReviewRows` runs right after the identity query) before the event. The card and compare phases then take seconds, and up to 60 s or more under load. The new request number is accepted (`request === sequence.current`), so the pre-event snapshot becomes current and nothing reads again.
  - Trigger: a read is in flight (the 60 s running timer, a tab show, or an earlier event) when one of these lands: a session publish decision (`publishSessionReview` at SessionReviewActivity.tsx:156), a session continuation (:138), a launch (App.tsx:683), a PR watcher poll that scheduled a review (`reloadSignal`), or a decision in the panel.
  - Outcome: the Reviews indicator and list keep the pre-event state. Examples: still lit after the user skipped or published from a Session, or unlit and not `running` for a review the watcher just queued, in which case the 60 s timer does not start either. This lasts until the next independent trigger, which is the next watcher poll that completes, a tab show, or a manual refresh.
  - This is the case FB-4 added these triggers for, and the DOM tests inject `load`, so they bypass the lane and cannot see it.
- Fix: Add an invalidation version to the Reviews-list lane key, as `reviewRun` already does for histories (`histories.read(JSON.stringify([mutationVersion, cwd, key, ...]))` in platform/reviewRuns.ts). Bump it from event-driven refreshes, so an event starts a new read. The lane's single waiting slot still bounds the spawns. Alternatively, ReviewsView can set a `dirty` ref when `refresh()` lands while `read.loading` is true, and refresh once more when that read settles. Pin it with a test that uses the real `fetchReviews` (mocked `invoke`): hold the first invoke, publish a session event, resolve the first, and expect a second invoke.
- class_scope (optional for minor): sites ReviewsView.tsx:198 (subscribeSessionReview), :199-204 (reloadSignal), the seenRuns observer (panel mutations), :185 (tab show); enumeration: `keryx ctx rg "refresh|subscribeSessionReview|reloadSignal" apps/desktop/src/reviews/ReviewsView.tsx` (36 matches, read 148-260). The 60 s timer at :194 is a sibling with no event to miss. ReviewBoard's `watcherPolled` refresh through the `boards` lane has the same shape, but it predates this delta and is out of scope.
- Confidence: medium. The coalescing path was read in code. The overlap window was not measured.

### [F-002] `readReviews` has no overall deadline: the card phase grows with history, and abandoned compares outlive the compare deadline
- Severity: minor
- File: src/commands/review-reviews.ts (readReviews, readCards, compareHeads)
- Pattern: Retry/Timeout F2, one timeout for the whole chain.
- Failure mode: FA-9's deadline covers only the compare phase, and it starts after the cards are read. `readCards` runs ceil(N/20) GraphQL batches three at a time, with no deadline. Each `boardGh`/`boardGraphql` call can take up to 18 s (board-github.ts:133). When the compare deadline passes, `Promise.race` returns "late", but the `gh api .../compare` children are not killed. Up to 4 can still be running, for up to 18 s each. `runReviewReviews` returns through `process.exitCode` and no `process.exit`, so the CLI exits only when they do.
  - Worst case under a GitHub stall: 18 (identity) + 18 x ceil(ceil(N/20)/3) (cards) + 60 (compares) + 18 (tail).
  - That is 114 s for N <= 60 and 132 s for N <= 120. It reaches the Desktop bound of `Duration::from_secs(150)` (review.rs:123) at N > 120.
  - N counts every stored Review that is not closed locally. Merged or closed PRs count too, until the user closes or archives them (F-023 residual).
  - Trigger: a GitHub or network stall, with more than about 120 such Reviews for one account and repository.
  - Outcome: the host kills the read, so the whole Reviews list fails instead of degrading to "count unknown". It also holds a lane slot for the full 150 s. This is degradation, not data loss, and it recovers on the next read. Round 1's stated trigger (22+ behind) is now inside the bound.
- Fix: Take one deadline at the start of `readReviews` (for example 90 s), and use it for both phases. Stop admitting card batches past it, and report their Reviews with `card: null` plus the existing "could not be loaded" warning. Give the compare phase `min(REVIEW_COMPARE_BUDGET_MS, deadline - now)`. Pass a shorter per-call timeout to `boardGh` for compares, for example 8 s, or an AbortSignal that kills the child at the deadline, so the process exits on time. Add a test where the card query hangs for one batch, then check the elapsed time and the warning.
- Confidence: medium. The arithmetic comes from the code. It assumes `child::run_bounded_with_stdin` waits for the process to exit; that helper was not read.

### [F-003] info: the hidden-tab 60 s reload is a deliberate cost
- Severity: info
- File: apps/desktop/src/reviews/ReviewsView.tsx:192-196
- What changed: FB-4 dropped the `active` gate, so the 60 s timer now runs whenever any Review is queued or running, on any tab while the window is visible.
- Cost: each tick is one `review reviews` spawn: an identity query, ceil(N/20) card queries, and up to 25 compares, per project window. A long scheduled review keeps it running for its whole duration.
- Why info: this follows FB-4 and has no failure mode beyond the GitHub budget, which F-002 bounds. If it proves costly, read only the store (no compares) on timer ticks while the tab is hidden.
- Confidence: high.
