### Summary
The slice routes "Open in Reviews" through a repository-named focus request that the outer `ReviewsView` holds and takes once. It adds an intent-consumed callback from `ReviewWorkspace`, passes the `include_closed` opt-in through both bridges with matching refusals, shows archived Reviews under Show closed, and opens the Review panel's PR link in the system browser.

I traced these paths at head and found them correct:
- The focus hand-off: App nulls the focus on `onFocusHandled`, and a remount keyed by viewer or repository cannot replay it.
- `refreshedFor`/`sequence`: the request written by the refresh is always greater than `after`.
- The Rust/dev parity of `include_closed`.
- `selectRepository`: the Reviews read and the board read share one repository source, so `focusRepo` cannot pick a repository the CLI refuses unless the remotes changed in between.

I found two new items, both below major. Neither duplicates waves 1 to 6.

### Logic Bugs

#### [F-001] A focus request resolved while the Reviews tab is hidden keeps its intent and acts on it at the next visit
- **Severity**: minor
- **File**: apps/desktop/src/reviews/ReviewsView.tsx:225-256
- **Problem**: The pending-focus effect (`:225-251`) has no `active` guard. When the matching Review is found, it calls `setSelected({ id: found.id, intent: pending.intent })`. The only code that strips an intent without the panel is `useEffect(() => { if (!active) consumeIntent(); }, [active, consumeIntent])` (`:256`), and it fires only when `active` changes. Scenario:
  1. The user clicks a card's answer action on the Pull requests tab. `openInReviews` sets the focus and switches to Reviews.
  2. The tab-show refresh starts. It reads from GitHub and runs compares within the compare budget, so it takes seconds.
  3. The user switches to another tab before the read returns. `consumeIntent` runs now, while nothing is selected, so it does nothing.
  4. The read returns, and the effect selects the Review with `intent: answer` while the tab is hidden. `ReviewPanel` renders only when `active` is true (`:349`), so nothing can consume the intent.
  5. When the user next opens Reviews (minutes later, say), the panel mounts with the intent. `ReviewWorkspace` (`ReviewWorkspace.tsx:1013-1030`) opens the answer dialog unprompted, if the PR range is unchanged and questions are still pending.

  The comment at `:253-254` says the selection keeps only the Review once the tab is left. That holds only for a selection made while the tab was shown. Hidden-tab resolution also resets filters and the search query, and can turn Show closed on (`:238-242`) while the user is elsewhere.
- **Why it matters**: A dialog the user did not just ask for opens on a later visit, from an action taken on another tab. No data changes, because the answer still needs the user's input, so this is minor.
- **Fix**: Strip the intent when the effect resolves the focus while the tab is hidden, e.g. `setSelected({ id: found.id, ...(active && { intent: pending.intent }) })`. Alternatively, keep `pending` until `active` is true by adding `!active` to the early return at `:226`. Add a DOM test: focus with `intent: answer`, flip `active` to false before the load resolves, resolve it, flip `active` back, and assert the answer dialog is not open.

### Edge Cases

#### [F-002] `ReviewWorkspace`'s `start` intent branch is now unreachable, yet the Reviews tab comment lists `start` as a handled intent
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewWorkspace.tsx:1016,1027-1028 (slice lines); apps/desktop/src/reviews/ReviewsView.tsx:253
- **Problem**: `ReviewWorkspace` is mounted only by `ReviewPanel.tsx:132`. The only producer of a `ReviewsFocus` intent is `ReviewBoard.openReview` (`ReviewBoard.tsx:462`), and after this delta it routes `kind === "start"` to the PR panel (`ReviewDetail`, which keeps its own start effect). It sends only `view` or `answer` to the Reviews tab. The `next.kind === "start"` conditions in `ReviewWorkspace`'s intent effect therefore cannot be met. The comment "An intent (answer, view, start) is acted on once" describes a case that never occurs.
- **Enumeration**: `keryx ctx rg '<ReviewWorkspace|openInReviews\(|onOpenInReviews\(|setReviewsFocus\('` over apps/desktop/src (non-test). The result is one ReviewWorkspace mount (ReviewPanel), one focus producer with an intent (ReviewBoard:462, start excluded), and one without an intent (ReviewBoard:557).
- **Why it matters**: There is no runtime defect. A later editor may assume the Reviews tab can start a review from a board click.
- **Fix**: Drop `start` from the comment, or narrow `ReviewIntent` for the Reviews path to `view | answer`. Keep the start branch only if a planned producer will use it, and say so.
