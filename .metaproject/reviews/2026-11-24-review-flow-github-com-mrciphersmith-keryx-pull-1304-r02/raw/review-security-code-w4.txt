### What was checked
- SQL injection. Every interpolation in the new SQL is built from code constants, never from caller data:
  - `ALTER TABLE runs ADD COLUMN ${name} ${type}` iterates the literal `reviewColumns` tuple.
  - `placement()` substitutes either a fixed column name or `NULL`. The alias is the literal `"r."` or `""`.
  - `${questionRows}`, `${neverStarted()}`, `${scheduledReservation}` and `${liveStates}` are module constants.
  - `${pending}` in attachBadges is built from `sqlite_schema` names that are filtered by a literal `IN ('review_questions','reviewer_questions')`.
  - All values (repo, pr, viewer, review id, rowid) are bound parameters: in reviewFor, assignReviews' UPDATE, reviewRows and the json_each card batch.
- Forged placement and integrity. `storedDetails` strips `reviewId`, `round` and `previousRunId` on every write path in the slice (`save`, `recordExisting`). The new-attempt INSERT stringifies a freshly built run that has no placement fields. `decode` and `history` take placement only from the columns. The test "projected fields it carries are ignored" pins that an imported run carrying `reviewId: "forged", round: 9` is placed by the store. The same test checks that no stored `details` row carries the fields. An imported package therefore cannot attach itself to another account's or PR's Review.
- Authz and cross-account isolation:
  - Reviews are keyed `UNIQUE(repo, pr, viewer)`, and viewer compares case-insensitively, which matches GitHub's case-insensitive logins.
  - `reviewFor` places each attempt by its own row's (repo, pr, viewer).
  - `reviewRows` filters `v.repo=? AND v.viewer=?` and joins runs only through `review_id=v.id`, so a viewer's Reviews contain only that viewer's attempts. Deleted attempts are excluded.
  - The only production caller (review-reviews.ts:49) passes the repositoryId and viewer returned by the GitHub identity query, never CLI input.
  - attachBadges still scopes by `r.repo=?2 AND r.viewer=?3`. The migration test pins that the colleague's history stays out ("Another account's history stays out").
- Untrusted input reaching the store. `recordExisting` takes runs from `readExistingReviews`:
  - Packages are read under the realpath of the project's `.metaproject`, and each one is matched to the PR by an anchored URL regex.
  - SHAs are normalized by `sha()`, and findings come from `countFindings`.
  - `JSON.parse(item.findings)` in reviewRows therefore parses a store-written counts object, not free text.
  - `tokens` is accepted only as a safe integer.
- Data exposure. `reviewRows` and the badges return no report body, reviewer sessions or worker identity. The new `outdated.round` is a small integer, and `flowId` and `tokens` are not secrets.
- Migration path. The read-only store never migrates: the test asserts that `review_id` and `reviews` are absent from the read-only copy afterwards. The writable migration runs in one `atomic` transaction. `readReviewRows` does not create a missing store. The store root is `deskRunRoot()` or a test temp dir, never user input, so there is no path traversal.
- Identifiers. Review ids use `crypto.randomUUID()`, not `Math.random()`.
- Not applicable to this slice: XSS/React patterns (no UI code), command injection (no process spawn added), crypto, CSRF, open redirect, NestJS patterns.
