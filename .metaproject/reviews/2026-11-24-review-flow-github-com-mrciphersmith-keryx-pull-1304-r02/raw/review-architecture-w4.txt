### Layer Violations

#### [F-001] The store re-derives "finished" and "offered for publication" itself, and its publication rule contradicts the publication service

- **Severity**: minor
- **File**: src/review/desk-run-store.ts:30, :423-435, :618
- **Problem**: The delta adds `FINISHED_STATES` to the store (desk-run-store.ts:30). This is a fourth definition of a finished attempt. The others are `FINISHED` in review-entity.ts:96, `runFinished` in board-badges.ts:15 (exported, from a module the store already imports) and the SQL literal at desk-run-store.ts:513. The delta also rewrites `publication()`. Its doc says "only a complete review without one is `pending`, because only it is offered for publication", and the code returns `pending` only for `completed` with `coverage === "complete"` (:434). That is a business rule (which attempts are offered for publication) placed in the repository. It is also not the rule the publication boundary enforces: `desk-publication.ts:297` accepts `completed` **or** `partial`, and Desktop `ReviewRuns.tsx:103` drafts a publication for both. The archived side of the rule is split as well. The store nulls an archived attempt's publication (:618–619), while `review-entity.ts` `stateAttempts` decides which attempts state and publication come from. That split is the root of backend-w1 R2-BE-006: a fully archived, published Review reads `ready` with `publication: null`. This finding does not re-file R2-BE-006. It names the placement behind it.
- **Why it matters**: The operator settled the behaviour (FA-2: `ready` lights only on `pending`), so no new user-visible defect is claimed here. The cost is structural. `reviewNeedsViewer` (review-entity.ts:117–124) depends on a meaning of `pending` that only the repository's private method produces, and its doc restates that rule as fact. The next change to publication eligibility, for example letting stage 3's publish dialog offer partial results per D1, has to find and change the store, the service and the view separately. Today the three already disagree.
- **Fix**: Keep the store as I/O. Have `publication()` report only the recorded outcome (`published`/`skipped`/none) for a finished attempt with a reviewed range. Decide "pending" in `review-entity.ts` from `state`, `coverage`, `source` and `archived` with one exported predicate (for example `publicationOffered(attempt)`), and import the finished-state test from one place (`runFinished` or an exported `FINISHED`) instead of `FINISHED_STATES`. Then either align the predicate with `desk-publication.ts:297` or state there that partial publication is a manual-only exception. Correct the store comment either way.
- **class_scope**: sites `src/review/desk-run-store.ts:30`, `src/review/desk-run-store.ts:434`, `src/review/desk-run-store.ts:513`, `src/review/desk-run-store.ts:618`, `src/review/review-entity.ts:96`, `src/review/board-badges.ts:15`, `src/review/desk-publication.ts:297`, `src/review/desk-run-service.ts:440`, `apps/desktop/src/review/ReviewRuns.tsx:37`, `apps/desktop/src/review/ReviewRuns.tsx:103`. Enumeration: `keryx ctx rg` over `src/review` and `apps/desktop/src` (tests excluded) for `FINISHED`, `"completed", "partial", "budget"`, `coverage === "complete"`, `coverage')='complete'`, and `state === "completed"`/`state !== "completed"` in desk-publication.ts, desk-run-service.ts and ReviewRuns.tsx. 4 finished-set definitions, 5 publication-eligibility checks.
