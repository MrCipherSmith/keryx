### Findings

### [PC-W4-001] The body's "What changes → Indicators" bullet still states the pre-fix indicator rule

- **Severity**: minor
- **File**: apps/desktop/src/reviews/ReviewsView.dom.test.tsx:613 (slice-04 :612-624)
- **Problem**: The body, What changes → Indicators: "The Reviews tab lights for `needs_answer`, `ready` with publication undecided, and `stopped`." The delta changes that rule. Its test is renamed from "the indicator lights for needs_answer, ready without a publication decision and stopped" to "... ready with a publication to choose and stopped". `[{ state: "ready", publication: null }, "attention"]` becomes `[{ state: "ready", publication: null }, null]`, and new cases `[{ state: "stopped", publication: null, archived: true }, null]` and `[{ state: "stopped", publication: null, card: null }, null]` follow. The fixes section of the same body ("lights `ready` only when publication is pending. A Review that is archived, or whose PR card could not be read, does not light it unless it asks a question") agrees with the code. The two bullets disagree. This is the same shape as PC-001 (Store bullet against the Round rule bullet).
- **Why it matters**: The What-changes bullet is what a merger or a stage-1 author reads as the indicator contract. Read alone, it says a `ready` Review with no publication decision (a partial, budget or imported run) and any `stopped` Review light the tab. The code no longer does that.
- **Fix**: Reword the bullet to: "lights for `needs_answer`; for `ready` with publication `pending`; and for `stopped`. An archived Review never lights it. A Review whose PR card could not be read lights it only with a question."

### [PC-W4-002] specification.md's reworded migration rule omits the superseded-request exception that implementation-plan.md states in the same delta

- **Severity**: minor
- **File**: docs/requirements/keryx-desktop-review-v2/specification.md:75 (slice-04 :1634)
- **Problem**: specification.md:75 (new): "раунды идут в порядке `createdAt`: запуск с `continuation.previousId` попадает в раунд предшественника, запуск с той же парой base..head, что у текущего последнего раунда, — в этот раунд, любой другой (в том числе возврат к более раннему диапазону, A, B, A) открывает следующий раунд". implementation-plan.md:35 (new, slice :1550) adds: "Запрос, вытесненный из очереди до старта, своего раунда не держит: следующий запрос получает его номер, а в списке Review такой запрос не показывается." The code follows the plan: src/review/desk-run-store.ts:27 `neverStarted` (state `skipped`, phase `Superseded`, never started) is selected as `superseded` at :187 and :195 and excluded from round counting. It is also filtered out of `reviewRows` at :606. Under the spec's wording, a superseded request on a new range "открывает следующий раунд"; under the code, it holds no round.
- **Why it matters**: The specification is the document stage 3 builds the update round on ("Смена head", round selection). Its storage section now states a numbering rule that the code and the plan contradict for superseded requests. A stage-3 author working from it would expect a round number the store never assigns.
- **Fix**: Add the plan's sentence to specification.md:75: "a request superseded before it started holds no round, the next request takes its number, and the Review list does not show it."

### [PC-W4-003] desktop-app.md has no description of the Reviews tab, though the delta sends readers there for archived runs and adds "Show closed" / "Archived"

- **Severity**: minor
- **File**: docs/docs/desktop-app.md:93 (slice-04 :1373-1374)
- **Problem**: The body says "The minors are fixed too: docs and shortcuts" and "Archived Reviews: they are reachable again, under 'Show closed'." The delta's own doc edits only point at the tab. desktop-app.md:93 reads "the Review's panel in the **Reviews** tab holds the review interface", and :169 reads "In the Review's panel in the **Reviews** tab, a scheduled attempt records…". The page's headings (`keryx ctx rg '^#'`: :70 "Find a pull request in Review", :88 "Run a review from a card", :113 "Publish a review to GitHub", :145, :155, then Install … :394 "Flows board", :425 "Explore Metaproject") have no section for the Reviews tab. `keryx ctx rg` for "Show closed" or a review-run Archive/Restore in desktop-app.md finds nothing; its only "Archived" hits (:363-371) are about sessions. The delta adds user-visible behaviour that only that tab explains:
  - "Show closed" with a count title, `button("Show closed").getAttribute("title")).toBe("Show closed (1)")` (slice :1029);
  - an "Archived" badge in the Closed column (slice :1032, model.test.ts :1134);
  - an archived run now offering "Open in Reviews" in the PR panel, with the comment "An archived run still has a Review in the Reviews tab (under Show closed), where History offers Restore and Delete" (slice :926-929).
- **Why it matters**: A user who archives a review run and opens the PR panel is sent to the Reviews tab. Nothing in the user docs says that archived Reviews are hidden until **Show closed** is on, or that Restore lives in the Review panel's History. The board columns, filters and the indicator rule are not documented either. Part of the gap predates the delta (the tab arrived in round 1). The delta adds the archived-Review path, and the body says the doc minors are fixed.
- **Fix**: Add a "Reviews" section to desktop-app.md (beside "Flows board"). It should cover the columns (Running · Waiting on you · Behind · Published, plus Closed with **Show closed**), the list view, search and the state, freshness and source filters, the **Archived** label and Restore through History, the rounds timeline, and when the tab's indicator lights. Alternatively, narrow the body's "docs" claim.
