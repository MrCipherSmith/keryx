### Logic Bugs

### [F-001] A retry on an earlier range puts the newest attempt in a lower round, and the read model and Desktop read round number as recency
- **Severity**: major
- **File**: src/review/desk-run-store.ts:195 (roundFor retry branch); src/review/review-entity.ts:138 (roundsOf sort), :159 (latestRound); apps/desktop/src/reviews/model.ts:53-64 (latestReviewed / reviewedCommit)
- **Problem**: `roundFor` places an attempt on a range already seen in the Review into that range's round (`ORDER BY round DESC LIMIT 1`, then `return { round: retry.round, ... }`). T5 step 2 asks for exactly this. The Review can then have a newer attempt in round 1 than the attempts in round 2. The consumers assume round number tracks time:
  - `roundsOf` sorts by number and is documented "Newest round first" (review-entity.ts:68). Round 2 is listed first although round 1 holds the newest attempt.
  - `summarizeReview.latestRound = latest.round`, where `latest` is the newest attempt by createdAt. It is 1 while `rounds[0].number` is 2. ReviewsView (:275, :321) and the ReviewPanel header (:106) show "Round 1", and the timeline puts Round 2 on top.
  - Desktop `latestReviewed` walks `review.rounds` in order and takes the first attempt with `reviewed`. That is the round-2 attempt on B. The server's `referenceHead`, `findings` and `publication` use the newest finished attempt by createdAt, which is the round-1 retry on A.
- **Trigger**: Round 1 on range A ends `partial` or `budget`, or the user re-runs A with other options. Either way `previousAttempt` does not reuse it (requestAttempt reuses only `completed` with `complete` coverage and matching options). The PR moves to B, and round 2 on B completes. The author force-pushes back to A, so the PR's base..head is A again, and the user starts a manual review on A. The new attempt lands in round 1 with `previous_run_id` = the old round-1 attempt. It completes.
- **Outcome**: The server summary has freshness `current` (reference head A = PR head A), the A retry's findings and publication, and `latestRound: 1`. The Desktop card and row show reviewed commit B (from round 2) next to "current" and A's findings. The panel says "Round 1" above a timeline that starts at Round 2 and hides the newest result in the lower entry. The view gives a wrong result with no error.
- **Relation to earlier findings**: review-logic w2 F-001 (stopped attempt chosen by `latestReviewed`) has a patch that adds a finished-state filter. That patch does not fix this, because B's attempt is finished too. w2's alternative, a server-provided `reviewedHead` (`referenceHead(row)`), does fix the commit label. It does not fix `latestRound` or the round order. review-degradation w3 F-001 reaches the same inconsistency through a late CLI import, which the plan records as a known limitation. This trigger is native to Desktop and is not covered by that note. review-testing-practices w2 noted that no A,B,A fixture exists. That note is about a missing test, not this consumer defect.
- **Fix**: Choose one rule and apply it to every consumer.
  - (a) Keep the T5 placement. Then order rounds by their newest attempt's createdAt in `roundsOf`, define `latestRound` as `rounds[0].number`, or keep "round of newest attempt" and label it that way. Have the CLI emit `reviewedHead: referenceHead(row)` and have Desktop render it instead of walking `rounds`.
  - (b) Change T5 step 2 so that a same-range match joins only the current highest round, and any other range opens `max+1`. Round number then follows time and every current consumer stays correct. Rows already placed are not renumbered, because `assignReviews` touches only unassigned rows.
  - Either way, add an A,B,A fixture through `reviewRows` → `summarizeReview` → model `reviewedCommit`.
- **Patch** (option b, store side):
  ```diff
  -    const retry = this.db.query<{ round: number }, [string, string | null, string | null]>(`SELECT round FROM runs
  -      WHERE review_id=? AND round IS NOT NULL AND json_extract(details,'$.baseSha') IS ? AND json_extract(details,'$.headSha') IS ?
  -      ORDER BY round DESC LIMIT 1`).get(reviewId, run.base, run.head);
  +    const retry = this.db.query<{ round: number }, [string, string, string | null, string | null]>(`SELECT round FROM runs
  +      WHERE review_id=? AND round=(SELECT max(round) FROM runs WHERE review_id=?1)
  +        AND json_extract(details,'$.baseSha') IS ? AND json_extract(details,'$.headSha') IS ? LIMIT 1`).get(reviewId, reviewId, run.base, run.head);
  ```
  (The plan's T5 text and the migration fixture expectations must change with it.)

### [F-002] A queued attempt superseded before it started opens a round of its own
- **Severity**: minor
- **File**: src/review/desk-run-store.ts:196-199 (roundFor new-range branch), with requestAttempt's supersede path (~:700)
- **Problem**: `requestAttempt` places the new row as soon as it is inserted. Take a Review with round 1 running on A. The user requests B, which is queued and placed as round 2. The head moves to C before round 1 finishes, and the user requests C. The B row is ended `skipped`/"Superseded" with `startedAt` null, and C opens round 3 with `previous_run_id` = the never-started B row. The store's own `previousAttempt` excludes exactly this row shape (`NOT (state='skipped' AND phase='Superseded' AND startedAt IS NULL AND result IS NULL AND usage IS NULL)`) as not an attempt. Round placement counts it anyway, and `reviewRows` lists it, because only archive and delete are filtered.
- **Why it matters**: After two reviews the Review shows "Round 3", and Round 2 holds a stopped request that never ran. Round 3's "after" link points at that request, not at the review it actually follows. No data is lost.
- **Fix**: In `roundFor`, leave never-started superseded rows out of the `max(round)` and `newest()` lookups (reuse the `previousAttempt` predicate). Or place a queued row only when it is dispatched. The row still needs a Review, so it would join the current round, not open one.
