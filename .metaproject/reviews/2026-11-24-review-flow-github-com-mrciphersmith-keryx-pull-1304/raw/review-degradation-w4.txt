### [F-001] The CLI reference does not document the `unknown` freshness that `review reviews` emits

- **Severity**: minor
- **Class**: diff-vs-description
- **Evidence kind**: base-diff
- **File**: docs/docs/cli-reference.md:5197
- **Problem**: The new paragraph describes freshness as "`current`, or `behind` with the number of new commits, `null` when unknown". Commit 98bec5904 is in the range (ancestor of 20e4281a2, not of a5d1ab236). It added `{ kind: "unknown" }` (review-entity.ts `freshness()`: `if (!prHead) return { kind: "unknown" }`), and `review reviews` returns it when the PR card cannot be read. That commit did not touch cli-reference.md. As a result the reference names only two kinds.
- **Why it matters**: A script or host written from the CLI reference would treat freshness as `current | behind` and mishandle the third kind. specification.md and the PR body do document `unknown`.
- **Fix**: List three kinds: `current`; `behind {commits (null when unknown), rewritten}`; `unknown` when the PR head cannot be read.

### [F-002] The specification still says the CLI protocol version is raised and machine schemas arrive in stage 2; the stage kept `version: 1`

- **Severity**: minor
- **Class**: diff-vs-description
- **Evidence kind**: base-diff
- **File**: docs/requirements/keryx-desktop-review-v2/specification.md:226
- **Problem**: The PR edits specification.md in three hunks (lines 2, 70 and 210). Two sentences stay as they were. Line 226 says "Версия протокола ответов CLI повышается", and line 8 says machine schemas "добавляются на этапе 2 вместе с повышением версии протокола". implementation-plan.md, changed in the same PR, records the opposite decision: `review reviews` keeps `version: 1`. The code agrees with the plan: `ReviewsSnapshot.version: 1` in review-entity.ts.
- **Why it matters**: Agents in stages 3 and 4 read the spec as an input, and two documents in this PR now give opposite protocol rules.
- **Fix**: Amend lines 8 and 226 to say that stage 2 kept version 1 and added no schema, or link the plan's decision.

### [F-003] (info) The 25 commit-count comparisons go to the highest PR numbers, not to the Reviews the list shows first

- **Severity**: info
- **Class**: behaviour-delta
- **Evidence kind**: consumer-trace
- **File**: src/commands/review-reviews.ts:50
- **Problem**: `behind` keeps the order from `readReviewRows`, which is `ORDER BY v.pr DESC` (desk-run-store.ts:587). `behind.slice(0, MAX_REVIEW_COMPARES)` then compares the first 25. The output is sorted afterwards by the newest attempt's `createdAt`. With more than 25 Reviews behind, the rows shown first can be the ones with an unknown count.
- **Fix**: Sort by the latest attempt's `createdAt` before slicing.
