### Summary
Slice-02 adds a `reviews/` feature (ReviewsView, ReviewPanel, presentation model), extracts the Keryx review interface from the PR detail panel into a shared `review/ReviewWorkspace.tsx`, routes PR-card view/answer actions to the Reviews tab, and adds a `reviews_only` mode to the `review_board` bridge (Rust and dev mirror, with matching refusals). Layering is sound: the domain rule for the indicator (`reviewNeedsViewer`) stays in root `src/review/review-entity.ts`, which has only type imports, so the desktop bundle pulls no Node/SQLite code; the desktop `reviews/model.ts` holds only presentation mapping; I/O stays in `platform/review.ts`. Overloading `review_board` instead of registering a new Tauri command is a decision recorded in the flow plan (plan.md:90), so it is not raised. No blocker or major findings. Two minor findings on dependency direction and a hidden required dependency, and three info notes.

### Dependency Direction
[F-001] (minor) `ReviewsTabIndicator` is declared in the shell and imported by the feature, the reverse of the existing PR-tab pattern. `apps/desktop/src/reviews/ReviewsView.tsx` imports `ReviewsTabIndicator` from `../shell/AppShell`. The sibling `ReviewTabIndicator` is declared by the feature (`review/ReviewBoard.tsx`) and imported by the shell (`AppShell.tsx` imports `../review/ReviewBoard`). So the shell now depends on `review/` for one indicator, and `reviews/` depends on the shell for the other. It is type-only and has no runtime cycle today. But a feature that depends on the app shell cannot be rendered or tested without the shell's module, and the two tabs now use opposite rules. Fix: declare `ReviewsTabIndicator` in `reviews/ReviewsView.tsx` (or `reviews/model.ts`), import it into `AppShell.tsx` the way `ReviewTabIndicator` is, and update `ReviewsView.dom.test.tsx`.

### Module Boundary Violations
[F-002] (minor) The PR feature now needs the Reviews tab to work, but its props do not say so. `onOpenInReviews` is optional on `ReviewBoard`/`ReviewDetail`. When it is absent, `openReview` in `ReviewBoard.tsx` still calls `setSelected` with a `view`/`answer` intent, and `ReviewDetail.tsx` now drops every non-`start` intent (`reviewIntent?.kind === "start" ? reviewIntent : undefined`). In that case "View review"/"Answer question" opens a panel with no review interface, and for a PR with a Review the primary button is the disabled launch action. App.tsx always passes the callback, so production is not affected today. The weakness is the contract: the fallback branch is dead code that looks supported. Fix: make `onOpenInReviews` required on both Props, or route only `start` through `setSelected` and leave the view/answer actions out when the callback is absent.

### Design Pattern Misuse
[F-004] (info) `review/ReviewWorkspace.tsx`, the shared review interface now also rendered by `reviews/ReviewPanel.tsx`, imports `./ReviewDetail.css`, the PR detail panel's stylesheet. `SessionReviewActivity.tsx` does the same, but that import predates this PR. The shared component therefore depends on its former host's styles. Consider moving the workspace rules into their own stylesheet (or `styles/review.css`) when it next changes.

[F-005] (info) The extraction is partial. `ReviewDetail.tsx` keeps its own copy of the `start` callback, the `initialLaunch` consume-once effect, the `associatedFlowId/associatedFlow` derivation and the revision-changed banner, alongside the same logic in `ReviewWorkspace.tsx` (only `RunLaunchDialog` is shared). This is a duplication concern that belongs to review-clean-code. It is noted here only because it weakens the "one shared component" boundary the PR describes.

### Dependency Inversion
None detected. The I/O seams (`load`, `runCommand`, `publishCommand`, `rulesCommand`) are injected as props with platform defaults, which matches the existing board.

### Framework-Specific (NestJS / React+MobX)
[F-003] (info) `ReviewDetail` Props keep `onOpenReviewSession` ("Accepted from the board"), but the component no longer reads it, and `ReviewBoard.tsx` still forwards it. That leaves a dead edge in the component interface. Remove it from `ReviewDetail` Props and from the `ReviewBoard` call site, since `ReviewsView` now receives it directly from App.
