### Edge Cases
### [F-001] info: the "merged PR awaiting a Keryx answer" board test keeps `expect(actions).not.toContain("start")`, which no longer guards the path it was written for
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewBoard.dom.test.tsx (slice-03 lines 477-490)
- **Problem**: Before this change, clicking "Answer question for #101" opened the PR panel with an `answer` intent. The `not.toContain("start")` assertion proved that the panel did not auto-launch a review. The test now passes `onOpenInReviews`, so `openReview` hands the `answer` intent to the callback (ReviewBoard.tsx:456) and never mounts `ReviewDetail`. The only remaining caller of `command` is the board's badge polling (`withRunBackoff(runCommand, …)`, ReviewBoard.tsx:340), and it never sends `start`. The routing is now guarded by the new `opened` assertion. The `start` assertion can only fail if badge polling starts reviews.
- **Why it matters**: There is no defect. The question removed from this test is now pinned in ReviewsView.dom.test.tsx ("an answer intent carried from Pull requests…"). A later reader may still think this line covers the auto-launch guard. That guard is `initialLaunch` = start-only in ReviewDetail.tsx:175. It is pinned by testing-practices w1 mutation M09 only if a test drives an `answer` intent into ReviewDetail, and none in this slice does.
- **Fix**: Drop the line or add a comment saying it now guards badge polling only. Or add one ReviewDetail test that mounts the panel with `reviewIntent: { kind: "answer", … }` and asserts no `start` request.
