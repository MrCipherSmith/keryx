### [F-001] A consumed "answer" intent stays in the Reviews selection and reopens the answer dialog on every return to the tab
- Severity: major
- File: apps/desktop/src/reviews/ReviewsView.tsx
- Problem: "Open in Reviews" stores the card's intent in `selected` (`setSelected({ id: found.id, intent: pending.intent })`). Nothing ever clears `intent` after `ReviewWorkspace` consumes it: `ReviewWorkspace` only clears its own `initialLaunch` ref. The panel is rendered only while the tab is active (`{active && review && target && <ReviewPanel ...>}`), so leaving the tab unmounts it. Coming back remounts `ReviewPanel` and `ReviewWorkspace` with `reviewIntent={selected?.intent}`, and the replay effect runs the intent again. The selection is kept on purpose (matrix: "list and selection kept"), but its intent is not.
- Trigger: on the Pull requests board, click "Answer question" on a card. Reviews opens and shows the run dialog. Close the dialog without answering, switch to any other tab, then press ⌘3.
- Outcome: the answer dialog opens again by itself, and it does so on every return while the question is pending. ReviewBoard avoids this because it calls `setSelected(null)` when its tab goes inactive.
- Fix: drop the intent once it has been handed over. For example, `ReviewPanel`/`ReviewWorkspace` can take an `onIntentConsumed` callback that runs `setSelected(s => s && { id: s.id })`. Or clear `intent` in a ReviewsView effect when `active` turns false. Add a DOM test: answer intent → close dialog → active false → active true → no dialog.

### [F-002] A cross-tab focus request replays whenever RepositoryReviews remounts (base-repository switch or account change)
- Severity: major
- File: apps/desktop/src/reviews/ReviewsView.tsx
- Problem: `RepositoryReviews` is keyed by `[cwd, viewer, repo]`, and `ReviewsView` is keyed by `reviewViewer` in App. The focus effect `useEffect(() => { if (focusNonce !== undefined && focusRef.current) setPending({ ...focusRef.current }); }, [focusNonce])` runs on every mount. App's `reviewsFocus` is never reset to null, so every remount re-applies the last "Open in Reviews" request.
- Trigger: use "Open in Reviews" for PR #N (App now holds `reviewsFocus = {number: N, ...}`). Then pick another entry in the Reviews tab's "Base repository" select, or change the account.
- Outcome: in the new repository the view selects that repository's #N Review if one exists, opening a panel for a PR the user never asked for. If none exists, it forces an extra list reload and shows "Pull request #N has no Keryx review in this list."
- Fix: treat a focus as consumed. App can clear `reviewsFocus` once ReviewsView acknowledges it through an `onFocusHandled` callback. Or the child can remember the last handled nonce in state that outlives the keyed child, for example lifted into `ReviewsView` next to `repo`, and ignore a nonce it has already handled.

### [F-003] The Reviews card's aria-label hides the card's state and facts from assistive technology
- Severity: minor
- File: apps/desktop/src/reviews/ReviewsView.tsx
- Problem: the card button carries `aria-label={`Open review of #${review.number} ${reviewTitle(review)}`}`. That label replaces the accessible name computed from the content, so the state badge, author, round, reviewed commit, freshness ("behind 3"), findings, publication and source inside the button are not announced. The sibling PR board card (`review/ReviewResults.tsx` ReviewTile) has no aria-label, so its content is read.
- Trigger: a screen-reader user tabs through the Reviews board.
- Outcome: only "Open review of #N title" is heard. Which Reviews wait on the user or are behind cannot be told apart.
- Fix: remove the aria-label and let the content name the button, as on the PR board. Or include state and freshness in the label.

### [F-004] info: the Reviews indicator only updates on mount, activation and Refresh, though App's comment says it "stays current on every tab"
- Severity: info
- File: apps/desktop/src/App.tsx
- Observation: the list reloads on mount, on activation and on Refresh, plus every 60 s, but the 60 s reload runs only while the tab is active (`if (!active || !running) return;`). There is no `subscribeSessionReview` subscription like ReviewBoard has. A review that reaches `needs_answer` while the user is on another tab does not light the Reviews dot until the user visits the tab. This matches plan T7's stated reload cadence, which is a deliberate choice. Before this PR the PR board's badge polling also ran only while that board was active. So this is not a new regression, but the comment `{/* Mounted like the PR board, so the Reviews indicator stays current on every tab. */}` overstates it. To settle it, decide whether the indicator should poll while hidden (AC8 wording), and either add a hidden-tab reload or word the comment as "reflects the last load".

### [F-005] info: `ReviewDetail` keeps an unused `onOpenReviewSession` prop
- Severity: info
- File: apps/desktop/src/review/ReviewDetail.tsx
- Observation: the prop is still declared (`/** Accepted from the board; the review interface that opens review sessions lives in the Reviews tab. */`), and ReviewBoard still passes it. `ReviewDetailSheet` no longer destructures or uses it. It is dead API surface. Remove it from Props and from the ReviewBoard call site, or leave it until the stage 1 merge settles this file.
