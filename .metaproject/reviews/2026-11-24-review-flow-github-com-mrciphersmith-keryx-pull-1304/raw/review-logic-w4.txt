### Logic Bugs
### [F-001] One failed card batch discards every card already read, and Reviews of merged PRs then leave Closed and light the Reviews indicator
- **Severity**: minor
- **File**: src/commands/review-reviews.ts:44-49 (the `listActiveReviewCards` try/catch in `readReviews`)
- **Problem**: `listActiveReviewCards` (board.ts:201) reads PR cards in sequential batches of 20 and returns one array only after every batch succeeds. If any batch throws a non-access error (for example `unavailable:` on a rate limit or a 502), `readReviews` catches it, adds a warning, and leaves `cards` empty. The batches that already succeeded are dropped. With `card === null`, `reviewClosed` (review-entity.ts:127) sees only `closedAt`. Every Review whose PR was merged or closed on GitHub, but that the user did not close locally, then gets its attempt state (`ready`, `stopped`) instead of `closed`. That state moves it from Closed into "Waiting on you", and `reviewNeedsViewer` lights the Reviews indicator (ReviewsView.tsx:134 counts every Review in the snapshot, whatever the filters).
- **Why it matters**: Trigger: a stored history with a merged-PR Review whose last round is `ready` with an undecided publication, or `stopped`. This is the common end state of a reviewed PR. One transient GitHub error on any card batch then lights the Reviews indicator, and those Reviews show up in an active column until the next good refresh. AC8 says the indicator stays off otherwise. A warning is shown, so the result is not silent. With more than 20 Reviews, an error in a later batch also discards the cards of the batches that succeeded.
- **Fix**: Keep the cards each batch returns, either by reading the batches here or by letting `listActiveReviewCards` return partial results together with a failure flag. For a Review whose card could not be read, do not take its attention from attempt state that depends on the PR still being open: let only `needs_answer` light the indicator when `card === null`, or carry a `cardUnread` flag that the Desktop excludes from the indicator.

### [F-002] `stopped` is taken from the latest attempt alone, although the spec ties it to the round having no accepted findings; this slice's test pins that reading
- **Severity**: minor
- **File**: src/review/review-entity.test.ts:103-107 (`summarizeReview` "groups attempts into rounds" expects `state: "stopped"`); behaviour in src/review/review-entity.ts `reviewState` (called with `latestAttempt(row)` only)
- **Problem**: The specification's state table defines `stopped` as the last attempt ending `failed`/`cancelled`/`blocked`/`budget`/`skipped` "и у раунда нет принятых находок" (and the round has no accepted findings). `ready` and `published` are defined from the last round. `reviewState` looks only at the newest attempt. Round 2 can hold a completed (even published) attempt followed by a failed or cancelled attempt on the same range. The Review then reads `stopped`, while `findings` and `publication` (taken from `latestReviewed`) still show round 2's accepted result. The test fixture in this slice is exactly that case (`second` completed and published, then `retry` failed in round 2), and it asserts `stopped`.
- **Why it matters**: This is reachable. `requestAttempt` (desk-run-store.ts:690-700) reuses a completed range only under the same options, so a manual start with different options on an already-reviewed range creates a new attempt in the same round. A continuation of a `partial` attempt also joins the same round. If that attempt is cancelled or fails, a Review that was `published` becomes `stopped`. It moves from Published to "Waiting on you" and lights the Reviews indicator, even though the round's accepted, published result is unchanged. The spec sentence can also be read so that its last clause attaches to `skipped` only, so the intent is ambiguous.
- **Fix**: Confirm the reading with the spec owner. If the clause covers the whole row, derive the state from the latest round: when the latest attempt is a non-live failure but an earlier attempt of the same round has a reviewed result, report that attempt's `ready`/`published`. Optionally add a `lastAttemptFailed` mark for the panel. Then update the test at review-entity.test.ts:103-107. If the reading that only `skipped` needs no accepted findings is intended, note it in the spec table.
