### Findings

### [F-001] Reviews list is read twice at every project window open
- Severity: minor
- File: apps/desktop/src/App.tsx (ReviewsView mount)
- Hot path: once per project window open (and per project switch), not per render.
- Problem: `githubAccount` starts `null` and loads asynchronously (App.tsx `refreshGitHubAccount`). On first render `reviewViewer` is undefined, so the always-mounted `<ReviewsView key={reviewViewer ?? "active-gh"}>` mounts and its effect starts `fetchReviews`. When the account resolves with a login, the key changes, the view remounts and reads again. The read lane key includes `expectedViewer`, so the second read is not deduplicated. Each `keryx review reviews` call is a CLI spawn, a GraphQL identity query, a batched card read, and up to 25 REST compares (`MAX_REVIEW_COMPARES`, 4 in parallel).
- Why it matters: one wasted CLI spawn and GitHub round-trip set per window open, on top of the PR board, which already does the same thing (pre-existing, outside this diff). It also counts against the GitHub rate limit.
- Fix: render ReviewsView only once the account read has settled, for example `githubAccount !== null &&`, or the same gate the board would use. Alternatively, skip the load while `expectedViewer` is undefined and an account read is still pending.
- Confidence: medium. Mount order and key change were read from code and not observed at runtime. The first read might also fail fast if project registration has not finished yet; it is still a wasted spawn either way.

### [F-002] Every visit to the Reviews tab and every run-state transition re-reads the whole list
- Severity: info
- File: apps/desktop/src/reviews/ReviewsView.tsx
- Hot path: tab switch (user-paced) and a run's state, publication or decision transition while the panel is open. Not per keystroke and not per render.
- Problem: the "read again whenever the tab is shown again" effect, plus `observeRuns` → `refresh()`, each trigger a full `keryx review reviews` read (bounded as in F-001). Rapid tab toggling re-reads every time; there is no minimum age.
- Why it matters: the cost is bounded (≤25 compares, at most 1/60 s polling and only while the tab is active and a run is queued or running). This is noted only as a possible throttle, for example skipping a tab-show refresh when the snapshot is younger than N seconds.
- Fix: optional. Compare `snapshot.fetchedAt` to now before the tab-show refresh.

### Clean Areas
- CLI/TUI hot paths: `projectViewForKey` is an O(1) regex check plus an index per keydown. The keydown listeners in ReviewsView are cleaned up and gated on `active`.
- Polling: the RUNNING_RELOAD_MS interval is cleared, and runs only while active and running. ReviewWorkspace's `useReviewRuns(..., true)` polls at 15 s/3 s, as the old board "Keryx review" tab did. The board panel and the Reviews panel are each rendered only while their tab is active, so the same PR is never double-polled. ReviewDetail now passes visible=false, so it polls less than before.
- Re-renders: `ReviewList` is memoized, and its inputs (`visible` useMemo, stable `openReview`, primitive props) are stable. `target` and `subject` are memoized by fields. `Rounds.known` is memoized. `observeRuns` uses JSON.stringify of a small runs array per poll, which is negligible.
- Memory: `seenRuns` Map is keyed by PR number and bounded by reviews viewed in one mount. All intervals and listeners have cleanup.
- Bundle: no new heavy imports. Rust/TS argument builders are O(1).
- Pagination: the CLI side caps compares at 25 (outside the slice; read for context only).
