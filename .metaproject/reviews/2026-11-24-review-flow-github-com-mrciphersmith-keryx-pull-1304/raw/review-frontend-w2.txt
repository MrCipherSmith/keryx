### [F-001] info: the fixture's `reviewDot()` helper also matches the Reviews tab dot, and that dot comes first in the nav
- Severity: info
- File: apps/desktop/src/test/app-navigation.fixture.tsx
- Observation: `const reviewDot = () => host.querySelector("nav .review-tab-dot")?.getAttribute("data-indicator");` is meant to read the Pull requests dot. AppShell renders the Reviews dot as `className="review-tab-dot reviews-tab-dot"` with the same `data-indicator="attention"` value, and Reviews (MOD+3) now precedes Pull requests (MOD+4) in `PROJECT_VIEWS`. Once the Reviews dot is lit, `querySelector` returns it first. The assertions at lines 186 ("Review requests reach the navigation on Sessions") and 209 ("Flows keeps the project notice") would then pass on the Reviews dot even if the PR dot were gone. Today the reviewsOnly mock always returns `reviews: []`, so the helper does read the PR dot. This is latent: it breaks if the mock gains a waiting Review, which testing-practices w1 F-003 suggests.
- Fix: scope the helper to the PR tab, for example `.review-tab-dot:not(.reviews-tab-dot)`, or select the button whose label starts with "Pull requests".

### [F-002] info: if wave 1's aria-label fix is taken, four ReviewsView test selectors must change with it
- Severity: info
- File: apps/desktop/src/reviews/ReviewsView.dom.test.tsx
- Observation: the new suite opens Review cards through `[aria-label^="Open review of #N"]` at four sites (state-matrix tests ×3, AC7 rounds test). review-frontend w1 F-003 proposes removing or rewording that aria-label. The tests would then fail to find the card and look like a regression. This is a coordination note for whoever fixes F-003, not a new defect.
- Fix: when F-003 is addressed, switch these selectors to the card's content (for example `.review-summary-card` filtered by `.flow-id` text) or to the new accessible name.
