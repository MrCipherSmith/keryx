### Findings

### [PC-001] cli-reference omits the `unknown` freshness kind that the PR body and spec add
- **Severity**: minor
- **File**: docs/docs/cli-reference.md
- **Problem**: The PR body says: "Freshness is `current`, `behind {commits, rewritten}`, or `unknown` when the PR head cannot be read; `unknown` is an operator decision recorded in the spec." The CLI reference the diff adds for the same command says: "its freshness (`current`, or `behind` with the number of new commits, `null` when unknown, and whether the branch was rewritten)". The code emits a third kind: review-entity.ts:105 `if (!prHead) return { kind: "unknown" };`.
- **Why it matters**: The CLI reference is the only public description of `keryx review reviews --json`. Someone writing a consumer from it would handle two kinds and get an unexpected `{kind:"unknown"}` whenever a PR card cannot be read or the PR is missing. Its "`null` when unknown" wording also invites confusion with `commits: null`.
- **Fix**: Add `unknown` (the PR head could not be read) to the freshness list in cli-reference.md.

### [PC-002] The listing command `review reviews` migrates an older store in place, but neither the PR body nor the CLI reference says so
- **Severity**: minor
- **File**: src/review/desk-run-store.ts
- **Problem**: The PR body says "Existing databases are migrated in place when opened for writing" and "Read-only badge reads still work on an unmigrated database". The CLI reference describes `review reviews` only as a listing: "Without a local review store the list is empty and no store is created." The source header calls it "Read-only list of local Reviews", and the Rust test is named `reviews_list_is_a_separate_read_only_query`. But `readReviewRows` opens the store writable (`const store = new DeskRunStore(root);`), and review-reviews.test.ts pins "a store that predates Reviews is migrated when it is read". Desktop runs this read whenever a project window opens, because ReviewsView is always mounted. So the first launch of the new Desktop rewrites the schema of the operator's `runs.sqlite`, before any review is started.
- **Why it matters**: A reader of the body or the CLI reference expects a list read to leave the store untouched. Someone who points the command or a dev build at a store they want to keep unmigrated will get it migrated. The journal for T11 shows the author had to steer around exactly this with a scratch data directory. The body also does not say that the migration is one-way for the new columns.
- **Fix**: State in the PR body's Store/CLI bullets and in cli-reference.md that `review reviews` (and so opening Desktop) migrates a pre-Reviews store in place. Also correct the "Read-only list" header comment. Alternatively, open the store read-only in `readReviewRows` with the same NULL-substitution as the badge path, if a migration on read is not intended.

### [PC-003] info: "Its title names the round it follows" holds only when the badge carries a round
- **Severity**: info
- **File**: apps/desktop/src/review/ReviewResults.tsx
- **Problem**: The body says: "Outdated-review action: relabelled 'New review round'. Its title names the round it follows (decision d)." The code is conditional: `${outdated.round ? `Round ${outdated.round} reviewed` : "Reviewed"} ${outdated.headSha.slice(0, 7)} — start a new round on the current head`. The journal records the fallback ("Title wording without a round ... was the worker's choice"). The body does not mention it.
- **Why it matters**: A tester following the body can see "Reviewed abc1234 — ..." without a round, for example from a badge read through the read-only path, and would report it as a defect.
- **Fix**: Add "when the badge carries the round" to that body line.

### [PC-004] info: the implementation plan's stage 3 hand-off still names the old label
- **Severity**: info
- **File**: docs/requirements/keryx-desktop-review-v2/implementation-plan.md
- **Problem**: The PR body says the action is "relabelled 'New review round'". The same document, edited by this diff (T13), keeps the hand-off line "**Этап 3.** Действие «Review again» заменяется раундом обновления того же Review". After stage 2 no action has that label on the PR card (ReviewResults.tsx: `card.localReview?.outdated ? "New review round"`).
- **Why it matters**: The stage 3 agent starts from this section, which the plan describes as checked against the code. It would look for an action label that the PR card no longer uses.
- **Fix**: Change «Review again» to «New review round» on implementation-plan.md:74, and update the matching clause on :73.
