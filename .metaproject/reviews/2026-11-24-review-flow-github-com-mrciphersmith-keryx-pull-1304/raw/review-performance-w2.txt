### Findings

### [F-001] Every list read fetches GitHub cards for the whole local Review history, closed Reviews included, in sequential batches
- **Severity**: minor
- **File**: src/commands/review-reviews.ts:369 (`listActiveReviewCards(snapshot, [...new Set(rows.map(row => row.number))], query)`)
- **Hot path**: each `keryx review reviews` call: window open, every Reviews tab show, every run transition, and the 60 s reload while a run is active (wave-1 findings name these triggers). Cost per call scales with the number of Reviews this account ever recorded in the repository, not with the open ones.
- **Problem**: `readReviewRows` returns every Review of the viewer in the repo with no bound (no state filter, no limit), and `readReviews` passes every distinct PR number to `listActiveReviewCards`. That function (board.ts:206) awaits one GraphQL query per 20 numbers, in sequence, each selecting the full card fields (assignees, reviewRequests, last-commit status rollup). Reviews closed locally (`closedAt`) are read too, although their state is already `closed` without a card, and closed/merged Reviews are hidden by default ("Show closed" off). The same row set also drives `reviewRows`, which runs `this.publication()` per completed attempt: up to one receipt read plus one `existsSync` per attempt across the whole history (desk-run-store.ts:410-414), every call.
- **Why it matters**: the list grows by one Review per reviewed PR and never shrinks. The plan records 13 Reviews in the working copy of the store today; at a few hundred historic Reviews a read is ~10-15 sequential GraphQL round trips (each 20 aliased pullRequest selections) plus hundreds of small file reads, repeated on every refresh, and it spends GraphQL rate-limit points on PRs the default view does not show. Not measured; rated minor because the current size is small ("could grow").
- **Fix**: skip the card read for Reviews with `closedAt` set (state is already `closed`), and consider caching or skipping cards for Reviews whose PR was last seen merged/closed unless "Show closed" is requested; run the card batches through `mapPool` like the compares instead of in sequence. In `reviewRows`, compute `publication` only for the attempts of the latest reviewed round, which is all `summarizeReview` needs for state.
- **Confidence**: medium. Sequencing and unbounded row set read from code; latency figures are estimates, no timing was taken.

### [F-002] Commit-count comparisons for an unchanged (reviewed head, PR head) pair are re-fetched on every read
- **Severity**: info
- **File**: src/commands/review-reviews.ts:382-389
- **Hot path**: same triggers as F-001; up to MAX_REVIEW_COMPARES = 25 `gh api .../compare` child processes per call.
- **Problem**: a compare result for two full object IDs is immutable, but each call recomputes it for every behind Review. The wave-1 highload finding addresses how often the read happens; this is the separate point that the comparison itself is cacheable.
- **Fix**: optional. Cache `{reviewed, head} -> ReviewCompare` (for example in the review store or a small file next to it, keyed by both SHAs) so a refresh with no new push spawns no `gh` process for that Review.
- **Confidence**: high on the shape; the benefit is bounded by the existing 25-compare cap.

### [F-003] `latestCreated` is recomputed inside the sort comparator
- **Severity**: info
- **File**: src/commands/review-reviews.ts:394, 398-399
- **Hot path**: once per read, O(n log n) comparator calls, each flattening all attempts of two Reviews.
- **Problem**: the newest `createdAt` per Review is rebuilt with `flatMap` + `reduce` on every comparison instead of once per Review.
- **Fix**: optional. Compute the key once (`map(r => [latestCreated(r), r])`) before sorting. Negligible at current sizes; noted only because it sits next to F-001's growth axis.
