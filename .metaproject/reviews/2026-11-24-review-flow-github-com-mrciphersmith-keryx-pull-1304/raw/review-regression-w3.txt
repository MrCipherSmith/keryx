Parity of SQL `attachBadges` with `localBadge` holds:
- Desktop's ReviewBoard calls `localBadge(runs.runs, revision)` on `history()` runs. `history()` now projects `round` from the same `runs.round` column through `place()`.
- The SQL path selects `${placement("r.").round}` from that same column.
- Both paths choose the outdated row the same way: the newest finished run with a reviewed result, ordered by created DESC and then seq DESC. `round` only rides along on that row.
- On an unmigrated database opened read-only, both paths give no round. The SQL path reads NULL, and `place()` does nothing without a `review_id`.
- I found one asymmetry, and it cannot be reached. `place()` sets `round` only when `review_id` is a string, while SQL reads `round` whenever the column exists. A row with a round but no review_id cannot exist: `assignReviews` always writes all three columns together.
