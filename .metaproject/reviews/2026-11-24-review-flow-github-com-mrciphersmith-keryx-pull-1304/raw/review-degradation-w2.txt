### [F-001] The CLI reference does not document the `unknown` freshness that `review reviews` emits

- **Severity**: minor
- **Class**: diff-vs-description
- **Evidence kind**: base-diff
- **File**: docs/docs/cli-reference.md:5197
- **Problem**: The new paragraph describes freshness as "`current`, or `behind` with the number of new commits, `null` when unknown". Commit 98bec5904 then added `{ kind: "unknown" }` (review-entity.ts:105): `review reviews` returns it whenever the PR card cannot be read or GitHub does not return the PR (review-reviews.test.ts covers both cases). That commit did not change cli-reference.md; `git show --stat 98bec5904` lists no docs file. The reference therefore names two kinds, and the only "unknown" it mentions is a `null` commit count inside `behind`.
- **Why it matters**: The Desktop was updated in the same commit (reviews/model.ts). A script or other host written from the CLI reference would take freshness as `current | behind` and mishandle the third kind. The PR body and specification.md do describe `unknown`, so the CLI reference is the only document that disagrees.
- **Fix**: In cli-reference.md, list the three kinds: `current`; `behind {commits (null when the count is unknown), rewritten}`; and `unknown` when the PR head cannot be read.

### [F-002] The specification still says the CLI protocol version is raised and machine schemas arrive in stage 2; the stage kept `version: 1` and added no schema

- **Severity**: minor
- **Class**: diff-vs-description
- **Evidence kind**: base-diff
- **File**: docs/requirements/keryx-desktop-review-v2/specification.md:226
- **Problem**: The spec says "Версия протокола ответов CLI повышается" at line 226, and at line 8 "Машинных схем в черновике нет; они добавляются на этапе 2 вместе с повышением версии протокола". The PR edits this spec (version 0.1.3, the `unknown` freshness) but leaves both sentences as they were. Meanwhile implementation-plan.md (stage-2 state) records the decision "Ответ `review reviews` сохраняет `version: 1`". The code matches the plan: `ReviewsSnapshot.version: 1` (review-entity.ts:80) and `{ version: 1 }` in review-reviews.ts.
- **Why it matters**: Stage 3 and 4 agents read the specification as an input (implementation-plan "Как запускать"). Two documents changed in the same PR now give contradictory protocol rules. The next stage could bump the version, or skip a bump it needs, on the strength of the stale line.
- **Fix**: Amend specification.md:8 and :226 to say that stage 2 kept `version: 1` and added no schema, and when a bump is planned (or link the plan's decision).

### [F-003] (info) The 25 commit-count comparisons go to the highest PR numbers, not to the Reviews the list shows first

- **Severity**: info
- **Class**: behaviour-delta
- **Evidence kind**: consumer-trace
- **File**: src/commands/review-reviews.ts:50
- **Problem**: `behind` keeps the order of `readReviewRows`, which is `ORDER BY v.pr DESC` (desk-run-store.ts:587), and `behind.slice(0, MAX_REVIEW_COMPARES)` compares the first 25. The output is then sorted by newest attempt `createdAt` (review-reviews.ts:68). With more than 25 Reviews behind, a recently re-reviewed older PR at the top of the list can show an unknown count while lower rows show theirs. The docs promise no order ("up to 25 Reviews per call"), so nothing is broken. It is only a matter of which Reviews get the counts.
- **Fix**: Sort `rows` (or `behind`) by latest attempt `createdAt` before slicing, so the counts go to the Reviews shown first.
