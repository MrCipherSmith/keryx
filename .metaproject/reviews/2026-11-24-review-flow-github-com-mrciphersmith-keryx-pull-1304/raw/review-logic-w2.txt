### Logic Bugs

### [F-001] The reviewed commit on Reviews cards, rows and panel comes from a stopped attempt, while freshness, findings and publication come from the last finished one
- **Severity**: major
- **File**: apps/desktop/src/reviews/model.ts (latestReviewed / reviewedCommit)
- **Problem**: `latestReviewed` picks the newest attempt whose `reviewed !== null`. `reviewedCommit` shows that attempt's `reviewed.headSha`. The domain read model, `src/review/review-entity.ts`, defines the reviewed attempt as `FINISHED.has(a.state) && a.reviewed !== null`, where FINISHED is completed, partial or budget. From that attempt it derives `freshness` (via `referenceHead`), `findings` and `publication`. Attempts in other states also carry `reviewed`. `finishExecution` (desk-run-service.ts) sets `result.reviewed` from `checkedBase`/`checkedHead` for every outcome. The executor (desk-run-executor.ts:373-374, 445) fills those from the package manifest even when the outcome is `cancelled` or `blocked`. `reviewRows` copies `result.reviewed` regardless of state.
- **Trigger**: Round 1 completes on head A. The PR moves to head B. Round 2 starts on B, and the user stops it after the package exists, or it ends `blocked`. That attempt is `cancelled` with `reviewed = {.., headSha: B}`. The entity gives state `stopped`, freshness `behind` (reference A versus PR head B), and round 1's findings and publication. The desktop card, list row and panel header show commit `B` followed by "· behind 1".
- **Why it matters**: The result is silently wrong. The card says the PR's current head is the reviewed commit and that it is behind. Findings and publication refer to A, but the commit label says B, so the user cannot tell which revision the findings belong to.
- **Fix**: Use the entity's rule. Pick the newest attempt with `reviewed !== null` and a finished state (`completed`, `partial`, `budget`). Better still, have the CLI put the reference head on `ReviewSummary`, e.g. `reviewedHead: referenceHead(row)`, and render that, so the desktop and the domain cannot diverge. Add a model test with a cancelled attempt that has `reviewed` set and comes after a completed one.
- **Patch**:
  ```diff
  -    const attempt = round.attempts.find(item => item.reviewed !== null);
  +    const attempt = round.attempts.find(item => item.reviewed !== null && (item.state === "completed" || item.state === "partial" || item.state === "budget"));
  ```

### [F-002] A digits-only search never matches PR titles in the Reviews tab
- **Severity**: minor
- **File**: apps/desktop/src/reviews/model.ts (matchesSearch)
- **Problem**: `if (/^\d+$/.test(number)) return String(review.number).startsWith(number);` returns before the title check. The placeholder says "Search by title or #number", and plan T7 says "search by title/#number". The PR board's `filterReviews` matches title OR number. Here, a query such as `404` hides "Fix 404 page" (#1290), and `2` hides "Desktop review v2 stage 2" unless its number starts with 2. The number match is also prefix-only, while the board uses substring, so `04` finds #1304 on the PR board but not in Reviews.
- **Fix**: Match the title as well when the query is all digits: `return String(review.number).startsWith(number) || reviewTitle(review).toLowerCase().includes(text);`. Alternatively, treat only a `#`-prefixed query as number-only.

### Async & Concurrency

### [F-003] A focus request whose re-read fails with an access error stays pending and fires on a later manual retry
- **Severity**: minor
- **File**: apps/desktop/src/reviews/ReviewsView.tsx (accessLost / pending focus effect)
- **Problem**: When the Review is not in the list, the pending effect records `after = sequence.current` and refreshes. It settles only when `read.request > pending.after`. `accessLost` writes `request: old.request`, which is the request of the previous good read, not the failed one. So an access or configuration failure of that re-read never satisfies the check, and `pending` is never cleared. Also, when the very first load fails with an access error, the guard lets the effect through (`read.error` is set), and it fires one automatic extra read against a failing account.
- **Trigger**: "Open in Reviews" for #N while the list lacks #N, then the re-read returns `access:`. Later the user clicks "Try again" or switches account and back without remounting. The next good read then selects #N and opens its panel, resetting filters and search, or it posts "Pull request #N has no Keryx review in this list.", long after the user asked.
- **Fix**: Clear `pending` in `accessLost` (call `setPending(null)` there, or move pending into a ref that accessLost resets). Alternatively, have accessLost write the failed request number so `read.request > pending.after` holds.
