### Summary
Slice-05 adds the Review persistence and read model. It adds a `reviews` table and the `review_id`/`round`/`previous_run_id` columns on `runs`, an in-place migration, and round assignment after every insert (`assignReviews`/`roundFor`). It also adds `DeskRunStore.reviewRows` and `readReviewRows`, the pure read model `src/review/review-entity.ts`, and the stale run's round on the board's `outdated` badge. The dependency direction is sound. The store imports only types from review-entity (`ReviewRow`, `ReviewAttemptSummary`). review-entity imports only protocol and run types (board-types, desk-run-types, desk-publication-types), not the store, so there is no cycle. The callers of review-entity are the CLI command and Desktop. Desktop imports types from `src/review/*` through relative paths, as `apps/desktop/src/platform/review.ts` already did at base. No blocker, major or minor findings. There are three info notes.

### Layer Violations
[F-001] (info) `src/review/desk-run-store.ts` `roundFor` (around diff line 288) holds the domain rule that places an attempt in a round. A continuation joins its predecessor's round, a known range is a retry in its round, and any other range opens the next round. The rule is written as SQL over `details` JSON inside the persistence class. The "pure" read model `review-entity.ts` then only groups by the stored `round`. Under clean-architecture.mdc, business rules belong in the domain, so this would normally be a minor. Plan T5 places the rule in the store on purpose ("one function, used both for the migration ... and after every insert"), and I name no defect. I record it as info: the rule can be tested only through a real SQLite store. Optional fix: move the decision into a pure `assignRound(candidate, priorAttemptsOfReview)` in review-entity.ts. The store would then only fetch the prior attempts and write the result.

### Design Pattern Misuse
[F-002] (info) The invariant "an attempt's Review placement lives in these columns only; `details` never carries it" (desk-run-store.ts, the `reviewColumns`/`storedDetails` block) is enforced at two of the three writers of `runs.details`. `save` and `recordExisting` go through `storedDetails`. `requestAttempt` still writes `JSON.stringify(run)` (slice line 658). That is correct today, because the run is built fresh in that method and has no placement fields. But the invariant holds there only by circumstance, not by construction. Enumeration: `keryx ctx rg "UPDATE runs SET|INSERT INTO runs|details="` over src and apps. The non-test writers of `details` are desk-run-store.ts:346 (save), :383 (recordExisting) and :730 (requestAttempt). :170 and :801 write other columns only. Optional fix: use `storedDetails(run)` in `requestAttempt` as well, so every writer strips placement.

[F-003] (info) Transaction ownership is now split. `requestAttempt` relies on the caller's transaction ("Inside the caller's dispatch transaction: no transaction of its own"). `recordExisting` now opens its own `this.atomic(...)`, but its only caller, desk-run-service.ts:260, already wraps it in `store.atomic(...)`. The inner transaction therefore runs nested, which bun:sqlite handles as a savepoint. I see no defect. The two insert paths that both end in `assignReviews()` just follow different conventions. Optional fix: pick one convention. Either both rely on the caller, or both own their transaction and the service stops wrapping `recordExisting`.
