### [F-001] History imported later gets the next round number, even when it is older than rounds already placed

- **Severity**: minor
- **Class**: diff-vs-description
- **Evidence kind**: consumer-trace
- **File**: src/review/desk-run-store.ts:161 (assignReviews), :186 (roundFor), recordExisting (~:380)
- **Problem**: The assignReviews docstring and AC1 say rounds are numbered "in creation order" (by first appearance of a base..head pair). That holds only within one assignReviews batch. `recordExisting` imports CLI review packages, and the `createdAt` it stores is the package's own timestamp (desk-run-legacy.ts:71, `stamp(data.createdAt ?? data.startedAt, …)`). It then calls `assignReviews`, and `roundFor` gives any range not seen before `max(round)+1`. Its `previous` points to the newest attempt of the last round. History scans run per (cwd, repo, pr, viewer) and at most every 5 min (requestDeskRun status → claimHistoryScan → recordExisting, desk-run-service.ts:258-260). Two cases follow. A package from another worktree, or a CLI review that finished after the last scan, is placed after Desktop attempts that are newer than it.
  - It becomes round N+1 even though it is the oldest attempt.
  - Its `previousRunId` points forward in time.
  - If the package's range matches an existing round, it joins that round as a retry. By `createdAt` it is then the round's first attempt, so `roundsOf` reports the round's `previousRunId` as a later attempt of the same round.
  - The summary also stops agreeing with itself. `latestRound` is the round of the newest attempt by createdAt (`latest.round`), which is lower than `rounds[0].number`.
- **Why it matters**: The Reviews panel orders the rounds timeline by round number. After such an import it shows an older review as the newest round, and its "after <id>" link points to a later attempt. No data is lost. The numbering is wrong, and the docstring and AC1 promise creation order.
- **Fix**: Choose one. (a) Make roundFor place by createdAt: when the new row is older than the Review's newest placed attempt, give it the round of the newest older attempt on the same range, or record it out of band without renumbering. (b) Keep "numbered when recorded" and say so in AC1, in the assignReviews docstring and in the spec. Then sort rounds in roundsOf/latestRound consistently, and pin it with a fixture that imports an older package after a Desktop attempt.
- Refutation attempt: read desk-run-store.test.ts:926-928. The only import fixture uses a same-range package (it joins round 1) and no older range. Read desk-run-legacy.ts:71: createdAt comes from the package, not from the import time. Read desk-run-service.ts:258: scans are per cwd and run after Desktop attempts can exist. No guard re-sorts placement.

### [F-002] (info) Round placement reads `details` (report included) for every attempt of the Review, and the migration does this once per pending row

- **Severity**: info
- **Class**: performance
- **Evidence kind**: consumer-trace
- **File**: src/review/desk-run-store.ts:186-200 (roundFor)
- **Problem**: On every new attempt (request → assignReviews inside the dispatch transaction), `roundFor` runs these queries over all of the Review's rows:
  - the `retry` query: `json_extract(details,'$.baseSha') IS ? AND json_extract(details,'$.headSha') IS ?`;
  - `newest()`: `ORDER BY json_extract(details,'$.createdAt')`.

  `details` embeds the full report (attachBadges' own comment at :491 calls a second pass over it costly). The migration calls roundFor once for each unassigned row, so it parses O(n²) report-laden JSON per PR, inside one immediate transaction that holds the write lock. On base, request parsed no other rows.
- **Why it matters**: The operator database (17 attempts) is trivial. The cost grows only with attempts per PR, and the lock is held while other windows wait under busy_timeout 8000.
- **Fix**: Optional. Select base/head/createdAt once per Review into a small in-memory list during assignReviews, or add generated columns or an index for base/head/created.
