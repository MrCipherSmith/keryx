### Summary
The F-027 fix seeds the carried attention set from every replacing load and closes the reported case (first mount with saved Merged/Closed/period filters: the first load of a mount always uses EMPTY_FILTERS, i.e. the open scope). Traced across the whole state machine, the remaining gap is the assumption that a replacing load is an open load: `replaceAttention` is also true when the identity is unknown or changed, and after `accessLost` (which keeps the state filter) or an identity change detected on a historical scope, the set is seeded from a Merged/Closed/period snapshot that cannot hold the open requests, and no open load follows when saved filters keep that scope. This is pre-existing on the merge base, but it is the next case of the F-027 shape (minor). One info: the unavailable-error path shows a cached older snapshot of the scope, and the write-back now persists attention judged on that stale snapshot. The backend change `be26765ae` cannot change `localBadge` output: its only reader of `publication` requires the same reviewed range that the new guard checks, and the `cardByPr` lookup is built per 200-card chunk from the same `cards` slice the query was given.

### Backend `be26765ae` (checked, no finding)
- Readers of `publication` in `src/review/board-badges.ts`: one, line 49: `...(same && latest.publication === "pending" && sameRange(latest.result?.reviewed ?? null, revision) && { publicationPending: true })`. `revision` is the card (attachBadges calls `localBadge(runs, card)`), and the row's `result.reviewed` is built from `row.base`/`row.head` only when both are truthy — the same precondition the guard keeps. The new guard `card?.baseSha === row.base && card.headSha === row.head` is exactly `sameRange(result.reviewed, card)`, so every skipped row is a row whose publication line 49 can never read. `ready`, `outdated`, `runState`, `awaitingAnswer`, `progress` do not read `publication`. `this.publication()` (desk-run-store.ts:325-334) only reads files, no side effect is lost. Output identical.
- `cardByPr`: built from `cards = snapshot.cards.slice(i, i + 200)`, the same slice passed to `json_each(?1)`; rows can only carry `pr` values of that chunk (`r.pr=w.n`), so a lookup never misses a card of another chunk. `row.pr` (INTEGER column) and `card.number` are both JS numbers. Duplicate card numbers inside one chunk would make the Map keep the last card, but a board snapshot carries one card per PR, and `byPr` already merges such rows under one number.
