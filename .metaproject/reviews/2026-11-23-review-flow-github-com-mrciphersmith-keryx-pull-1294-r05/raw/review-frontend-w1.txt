## Seed effect and stale, as checked

- Dependencies `[seedFor, cwd, repo, expectedViewer, load]` are complete for what the effect reads (identity and seeded are refs). `load` defaults to `fetchReviewBoard` (stable); the main effect already depends on it, so an unstable prop would already loop there.
- Cleanup sets `current=false` and aborts, so a late result of a superseded or unmounted seed writes nothing; the catch also checks `current`. No state update after unmount.
- StrictMode: `main.tsx` does not use it (comment there). Were it on, the seed would run twice, the first result is discarded by `current`, the second applies; harmless apart from one extra request.
- The result guard (`key !== seedFor.identity || identity.current !== key || seeded.current === key`) rejects another account's seed and a seed that lost the race to an open load. An open load that finishes first calls `setSeedFor(null)`, which aborts the seed.
- Reply-based attention: the seed uses `attentionNumbers` on a card-only snapshot without `addressedReplyIds`, like any first open load; for an unseeded identity there is nothing to carry. Same blind spot as before, not introduced by T22.
- `stale` at every setRead site: updateRunSummary, noteDiscussion and the badge poll spread `old` (keep; right, the snapshot is still the cached one); the loading set keeps it when scope and snapshot are unchanged and drops it on a scope change; accessLost spreads `old` but sets snapshot null, so a leftover true is inert and the next loading set drops it; the success set drops it; the unavailable catch sets it only for a cache fallback and leaves a fresh kept snapshot unmarked. No path found that leaves stale true on a fresh snapshot.
- Known limit, not reported: while stale, a receipt read removes a number from the derived set but does not write back, so a non-replacing view may keep it until the next open load.
