### Findings

### [F-001] The per-wave head check is a `gh` call, which the same skill says asks the operator in a trust/auto session
- **Severity**: minor
- **File**: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.detail.md (§ "Head moved", step 1); mirrored in SKILL.md Round plan step 5 and the bundled copies
- **Hot path**: once per wave boundary (before each `keryx review next`), plus once before `complete` and once before publishing. A round has a few waves, so this is about 3–6 extra `gh pr view` calls per round. That is small in wall-clock time (one GitHub API round-trip each).
- **Problem**: SKILL.md "Shell calls in a `trust` or `auto` session" (unchanged context line in the diff) says "A `gh` call still asks: that is expected, so make it once and reuse what it printed." The new step 1 instead requires a fresh `gh pr view <n> --json headRefOid` at every wave boundary. In those sessions, each check turns into a permission prompt between waves. "Between waves" rule 2 forbids exactly this kind of pause while the plan is authorized.
- **Why it matters**: the cost is not the API call. It is operator latency: a round that is meant to run without stopping waits for an approval before each wave. The "make it once" guidance and the "check every wave" guidance now contradict each other.
- **Fix**: either (a) name the per-wave head read as an allowed exception to "make it once" and say the prompt is expected, or (b) use a read-only git probe that the routine-command rule already admits, e.g. `git ls-remote origin refs/pull/<n>/head`, and keep `gh pr view` for the checks before `complete` and before publish.
