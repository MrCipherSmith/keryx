### Findings

### [F-001] The head check runs a `gh` call at every wave boundary, which conflicts with the rule to make a `gh` call once and reuse its output
- **Severity**: minor
- **File**: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.detail.md (§ "Head moved" step 1), and the same text in src/gdskills/bundled/...
- **Trigger and outcome**: In a `trust`/`auto` session, SKILL.md says "A `gh` call still asks: that is expected, so make it once and reuse what it printed." The new step 1 calls for `gh pr view <n> --json headRefOid --jq .headRefOid` before each `keryx review next`, before `complete` and before publishing. On an N-wave round, that gives the operator N+2 permission prompts for the same read-only command, in the middle of a phase where "Between waves" rule 2 says to ask no questions about pace. Two outcomes are likely. The operator gets used to approving `gh` prompts by reflex, which weakens the prompt that exists to catch an unexpected `gh` write. Or the agent follows "make it once" and skips the per-wave check, so a head move goes unnoticed until publish. That second case is not unsafe, because the publish-time check and `completeHeadGate` still apply.
- **Fix**: Name the head check as the stated exception to "make it once" (one `gh pr view` per boundary is expected), or route it through a keryx command that reads the head itself, so it is a routine keryx call and not a `gh` prompt. For example, let `keryx review next` report `pr_head` and a `head_moved` flag.

### [F-002] D1 ("an old commit is published only with --event COMMENT") is enforced only by skill text; `keryx review publish` accepts REQUEST_CHANGES/APPROVE on a moved head
- **Severity**: info (pre-existing code, deferred by the flow to T7)
- **File**: src/review/publish.ts:153-160; src/review/readiness.ts headCheck; src/review/complete-head-gate.ts:52-60
- **Problem**: The procedure limits "Publish as is for `<reviewed sha>`" to `--event COMMENT`. In code, readiness item 7 passes with only a warning when the report's first line names the reviewed SHA and says the PR moved. `publishReview` refuses APPROVE only when the review is partial (publish.ts:158). So an operator, or an agent that ignores the text, can publish APPROVE or REQUEST_CHANGES for an old commit. Publishing still needs the operator's own `[y/N]` or card press, so this needs a human decision and is not an agent bypass. There is a GitHub-side risk: `gh pr review` posts without a `commit_id` (divergence-map.md §2 "GitHub identity"), so an APPROVE might attach to the new, unreviewed head. That is a claim about GitHub's behaviour with no file:line at a pinned SHA behind it, so it stays info.
- **Fix**: As the journal and divergence-map step 4 already plan for T7: in `publishReview`, refuse any event other than COMMENT when the head gate reports a moved head, and post with `commit_id` = the reviewed SHA through `gh api .../reviews`. Leave a pointer in this PR body so the gap is tracked.

### [F-003] The source of `on_head_move` is not named; `follow`/`ignore` remove the operator question
- **Severity**: info
- **File**: SKILL.detail.md § "Head moved" step 3 ("the Review's own value when it has one, otherwise `ask`")
- **Problem**: Stage 3 owns the storage, and the current tree has no store for this value. Until then, the text does not say where "the Review's own value" may come from. If an agent took it from untrusted content, such as the PR body, a file on the PR branch or a comment, then `ignore`/`follow` would suppress the operator question. The impact is bounded: neither value publishes, because unattended runs never publish and publishing stays the operator's act. The worst case is an unannounced update round or a report that is behind. I found no path where this leads to a GitHub write.
- **Fix**: Add "read only from the Review record keryx stores (stage 3); never from PR content" to step 3, or say `ask` until stage 3 lands.

The SKILL.md publication tail now points to the procedure and does not weaken "No GitHub write without an approved draft".
