### Concurrency & Races

[F-001] minor (pre-existing code; the procedure relies on it) — the head check before publishing is check-then-act. The last re-read comes before an unbounded operator confirmation, and the post is not pinned to the reviewed commit.
- File: src/review/publish.ts (publishReview)
- Pattern: Concurrency A — TOCTOU.
- Failure mode: here is the sequence when someone pushes to the PR while the operator sits at the `Post this … review? [y/N]` prompt (src/commands/review.ts:5054):
  1. Step 1 of the procedure reads the head, and `computeReadiness` → `completeHeadGate` reads it again. Both see the reviewed SHA.
  2. A push lands during the prompt.
  3. `options.post` runs `gh pr review <url> --approve|--request-changes|--comment --body-file -` (src/flow/tracker/github.ts:144-147). The call carries no commit pin and does not re-read the head.

  An APPROVE or REQUEST_CHANGES for the reviewed SHA is then posted to a PR whose head was never reviewed. That is exactly what D1 forbids. Two further points:
  - D1 is enforced only by instruction. When the head has moved and report line 1 names the reviewed SHA, `completeHeadGate` lets the publish through with any `--event`, not only COMMENT.
  - The Desktop path closes both gaps. It re-verifies the subject right before the POST (`verifyDeskSubject`, desk-publication.ts:341) and pins `commit_id: run.headSha` (:334).

  Which commit an unpinned review attaches to is GitHub behaviour with no pinned file:line here. That part of the claim is info-grade, but the missing re-check after confirmation is in keryx code.
- Fix: in T7 (divergence-map.md row 4):
  - Re-read the PR head after `confirm` returns and immediately before `post`, and refuse if it differs from the head readiness saw.
  - Post through `gh api …/reviews` with `commit_id = manifest.target.head`.
  - In `publishReview`, refuse `event !== "COMMENT"` when the head has moved.

  Until then, add one sentence to step 5 of § Head moved: the check is advisory, and the operator re-runs it if the prompt sat open.
- Note: the divergence map (§2 "head moved", §4 rows 4 and 7) and the journal ("T7 must add the COMMENT restriction") already record this, which is why it is minor and not major.

Multiple sessions on the same PR: none detected beyond what is already known. Each session has its own package. The procedure only reads (`gh pr view`, `git merge-base`, `git rev-list`). `git fetch origin <sha>` from two sessions on one checkout only updates FETCH_HEAD and objects, and git's own locking covers that. The duplicate-publish risk when two sessions both publish (no receipt or marker on the session path, O15) is pre-existing and already in divergence-map.md §2 "duplicate detection", so it is not raised again. Two sessions that both take the `ask` path ask the operator twice. That is noise, not corruption.
