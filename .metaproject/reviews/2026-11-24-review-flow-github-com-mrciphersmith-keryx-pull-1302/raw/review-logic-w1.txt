### Summary
The new `## Head moved` section is mostly faithful to the spec and to D1/D2. It is copied byte-for-byte into both trees, and the preflight tests assert every AC1–AC3 element by string. One path does not work today. "Stop and start on the new head" combined with the `keryx review plan` fallback does not carry the stopped round forward the way the text claims. The current prior-round rules drop a partial or uncompleted package, so its findings and its uncovered area are silently lost. Smaller issues: the question is asked again at every wave boundary, the procedure never mentions the `complete-head-gate` first-line requirement, step 3 and step 5 overlap at publish time (so the D1 restriction can be skipped), merge-base exit codes other than 0 and 1 are not handled, and the unattended default differs from the spec.

### Logic Bugs

#### [F-001] major — "Stop and start on the new head" promises a carry-over that the fallback command cannot deliver today
- File: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.detail.md:604 and :608 (the same text in src/gdskills/bundled/.../SKILL.detail.md:604, :608)
- Problem: Step 3 says to "ingest what finished as a partial round, then step 4; the area it did not cover enters the new plan as unchecked". Step 4's fallback (`keryx review plan --target <pr-url> --head <new sha>`) is said to "attach the prior findings" and pick `delta`. Today's prior-round selection does neither for a stopped round:
  - `localPackageCandidates` drops any package that is not `eligible` (prior-round.ts:414). `REVIEWED_STATUSES` excludes draft and partial packages (round-record.ts:207, "a draft or partial package is never a previous round").
  - A package that is eligible but has no completion evidence (no `review complete`, no published.json, no scopeReviewed ledger) is untrusted. It is used only when no trusted round exists, and then as `fallback-first` with "findings as context only" (prior-round.ts:880-886). When an older trusted round exists, the stopped round is ignored entirely.
  - Nothing in `review plan` adds an earlier round's uncovered area as unchecked.

  Spec "Раунд обновления" item 1 explicitly lists these three rules as changes stage 3 has to make. The skill states the stage-3 behaviour as if it were current. The PR body does not mention the limitation; only journal.md does. Step 5.1 has the same issue: it says "The operator's answers per finding carry over by finding id", which is also stage-3 behaviour with no current mechanism in the `review plan` fallback.
- Why it matters: Take the input `on_head_move=ask`, operator picks "Stop and start". The agent tells the operator that the work done so far and the uncovered area carry into the new round. The fallback plan then starts from an older round, or from round 1 with no prior findings, and the stopped round's findings are never rechecked or closed. Nothing reports this.
- Fix: Until `keryx review --help` lists `advance`, state the limitation in the procedure. Either (a) offer "Stop and start" only once `advance` exists, and otherwise recommend "Update after this round finishes", which reaches `complete` and so produces a trusted prior round; or (b) keep the option but tell the agent to say that the stopped round's findings reach the new round only as context, that its uncovered slices must be named in the new report, and that per-finding answers do not carry over yet.

Checked each claim against prior-round.ts:410-420 and :872-890 and round-record.ts:207.

#### [F-002] minor — the `ask` question repeats at every later wave boundary
- File: SKILL.detail.md:599-605 (both copies)
- Problem: Step 1 compares the PR head with the round's pinned `head` before each `keryx review next`. Once the operator answers "Update after this round finishes", the round continues on the old head. At the next boundary the head still differs, so step 3 asks again, and the Between-waves stop list (line 587) stops the round again. The procedure never says to remember the answer, or to ask again only when the head moves beyond the SHA the operator already answered for.
- Why it matters: An agent that follows the text literally stops a three-wave round twice more with the same question, which is the pace-question pattern "Between waves" forbids. For a Telegram operator, each stop is another poll to wait on.
- Fix: In step 1 or step 3, add: "Compare with the last head the operator answered for (or the round's `head` before any answer); ask again only when the PR moved past it."

#### [F-003] minor — "the round runs to `complete`" after a move, but `complete` refuses unless the report's first line names the reviewed SHA
- File: SKILL.detail.md:603, :605, :606 (both copies)
- Problem: For "Update after this round finishes", `follow` and `ignore`, the round finishes on its pinned head. `completeHeadGate` (src/review/complete-head-gate.ts:52-61) throws on a moved head unless the report's first line names the reviewed SHA and says the PR moved. The section names that line only for step 5 ("Publish as is"), not for completing a round whose head moved.
- Why it matters: The agent reaches `keryx review complete` and gets a refusal. The error text says what to write, so this costs an extra round-trip and is not lost data.
- Fix: In step 3 (or step 1's "before `keryx review complete`"), add that the report's first line is the `templates/review-report.md` moved-head line before `complete`, as SKILL.md:235 already says.

#### [F-004] minor — step 3 and step 5 overlap at publish time, so the D1 restriction can be skipped
- File: SKILL.detail.md:599-609 (both copies)
- Problem: Step 1 runs the check "before publishing" and the text flows into step 3, which decides by `on_head_move`. Step 5 holds the D1 options and applies only "when the head moved after the round completed". The text does not say which step applies at publish time. It also does not say what happens when the head moved during the round under `ignore`, which ends with the report "behind" and then a publish that step 5's wording does not cover. In that case nothing restricts the event to COMMENT, and the session `review publish` path does not enforce it either: readiness item 7 only warns when the first line names the SHA (divergence-map.md §2, "head moved"). Today, with no stored `on_head_move`, `ignore` cannot be reached in a session, so this is latent.
- Why it matters: D1 says an old commit is published only as a Comment. Once `ignore` is stored (stage 3), `ignore` followed by publish can post REQUEST_CHANGES or APPROVE for an outdated commit.
- Fix: Say that step 3 applies while a round runs and that any publish of a package whose `head` differs from the PR head goes through step 5, whatever `on_head_move` is.

#### [F-005] minor — `git merge-base --is-ancestor` exit codes other than 0 and 1 are not handled
- File: SKILL.detail.md:600 (both copies)
- Problem: The text maps exit 0 to ancestor and exit 1 to rewritten history. If `git fetch origin <new sha>` failed or the reviewed SHA is not present locally, `--is-ancestor` exits 128. The procedure does not cover that case. An agent may treat any non-zero exit as "history was rewritten" and report a force-push that did not happen.
- Fix: Add "any other exit: the count is unknown (fetch failed); report `head moved, count unavailable` and do not call it a rewrite."

#### [F-006] info — unattended default vs spec "Конфигурация"
- File: SKILL.detail.md:601, :607 (both copies)
- Problem: Step 3 defaults to `ask` when the Review has no value, and the unattended rule opens an update round only under `follow`. The spec (specification.md:84) makes `follow` the default for rule-triggered runs. An unattended session run started by a trigger rule therefore never opens an update round, where the spec's default would. D2 covers only manual reviews, so the procedure's reading is defensible while no stored value exists. Recording it so stage 3 aligns the two.
