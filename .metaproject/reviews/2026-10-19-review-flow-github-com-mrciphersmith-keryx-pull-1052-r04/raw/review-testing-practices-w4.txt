### [F-001] The shell hop that turns the pressed Telegram user into `pressedBy`/`pressedAt`, and the card-log orchestration around the race, have no test

- Severity: major
- File: src/tui/tui-shell.ts:572 (remoteApproval), 6100-6148 (mirrorApprovalToTopic card branches), 6088
- Problem: `remoteApproval(fingerprint, fromId)` is the only producer of `{ via: "remote", pressedBy, pressedAt }` on the ApprovalResponse, and `mirrorApprovalToTopic` is the only place that calls `operatorCards.ask/answer/markUndelivered/settle` and `io.onSystem` for an undelivered card. Both are closure-private or module-private in tui-shell.ts and nothing in the test suite exercises them: `keryx ctx rg 'remoteApproval|operatorCards|markUndelivered|onUndelivered' --glob '*.test.ts' src` finds only operator-confirmations.test.ts (the log class in isolation) and mirror-undelivered.test.ts (raceApproval with a hand-written callback, plus `withMirrorNote`). The tui-shell.test.ts source-string test at line 2963-2969 still passes unchanged and pins none of the new branches. The upstream hops are tested (shell-bridge.test.ts:617-621 pins `mapApprovalAnswer` keeping `fromId`; operator-confirm-tools.test.ts feeds `{ via: "remote", pressedBy }` by hand), so the one link nobody tests is `answer.fromId -> remoteApproval -> ApprovalResponse`.
- Why it matters: the PR's claim is that the durable record says who pressed. If the shell passed `undefined` instead of `outcome.answer.fromId`, dropped `pressedAt`, or took the `unmirrored` branch for a delivered card, every test stays green and the record is silently empty or wrong. The same holds for the card log: a `finally` that stops calling `settle` leaves a card "waiting" in the sidebar forever, and no test notices. This is the sibling of the D-12 gap (consumers asserted for 4 of 9 specs) one hop earlier, where the value is produced.
- Fix: make the seam testable instead of pinning source text. Move `remoteApproval` (take a `now: () => Date` default) and the card-lifecycle code into an exported helper, for example `runMirroredCard({ log, bridge, tool, meta, race: raceApproval, dock, topic, aborted })` in src/tui/approval-mirror.ts or operator-confirmations.ts, and test it with the real `OperatorConfirmationLog` and a fake topic: (1) topic allow with fromId 9 and a fingerprint returns `{ approved: true, fingerprint, via: "remote", pressedBy: 9, pressedAt: <injected ISO> }` and the log entry is `telegram`/`pressedBy: 9`; (2) a topic deny without fromId returns false and logs `yes:false`; (3) a topic that answers `undelivered: true` calls `markUndelivered` so `log.waiting()` is empty and `io.onSystem` receives the "Telegram mirror not delivered" line; (4) `mirrorUndeliveredNote` defined takes the unmirrored branch, asks the dock with the note inside the card, and logs `shell` or, on an aborted turn, `withdrawn`; (5) a throwing race leaves the card `withdrawn` (the `outcome === undefined` path). If extraction is out of scope, the minimum is a tui-shell.test.ts source-string pin of `remoteApproval(meta.fingerprint, outcome.answer.fromId)` and `operatorCards.settle(cardId`, but that is weaker.
- Evidence: tui-shell.ts:6147 `return meta?.fingerprint !== undefined ? remoteApproval(meta.fingerprint, outcome.answer.fromId) : true;`; tui-shell.ts:572-574 `remoteApproval` uses `new Date().toISOString()` directly, so even a closure-level test could not pin `pressedAt`; search for `remoteApproval|operatorCards` in `*.test.ts` returns no tui-shell test.
- Confidence: high (that no test reaches it); medium on severity.

### [F-002] The option-threading seams for the cards (sidebar count, status tab, /decisions modal) are untested; the tests cover only the pure formatters

- Severity: minor
- File: src/tui/operator-confirmations.test.ts:129-165 (the /remote-control and /decisions tests), src/tui/decisions-surface.ts:450 and 621, src/tui/remote-control-surface.ts:262 and 453, src/tui/tui-shell.ts:4584, 4632, 7355
- Problem: the sidebar test calls `projectRemoteRow(..., 2)` directly, the status test calls `formatRemoteStatusLines(status, undefined, lines)` directly, and the modal test calls `withConfirmationLines` and then `presentDecisions` with prebuilt text. None goes through `presentRemoteControl({ getConfirmationLines })`, the sidebar's `getWaitingCards`, `openDecisions({ confirmationLines })` or the decisions sidebar's `openWith` that forwards `confirmationLines`. Each of those one-line forwards (`options.getConfirmationLines?.()` at remote-control-surface.ts:262, `options.getWaitingCards?.() ?? 0` at 453, `confirmationLines?.() ?? []` at decisions-surface.ts:450, the spread at 621) can be deleted and every test here still passes.
- Why it matters: AC6 is "the cards show where the operator already looks". The three surfaces are exactly what the forwards feed; the formatters are right in isolation and the feature still shows nothing if a forward is lost. decisions-surface.test.ts and remote-control-surface.test.ts already have harnesses for these presenters (test seams `count`, `backfilled`, `interval`), so the cost is small.
- Fix: in decisions-surface.test.ts, call `openDecisions` with a fake `openModal`-compatible host and `confirmationLines: () => ["Operator confirmations (Telegram cards)", "  waiting  X"]` and assert the painted text contains it, and assert `openDecisionsArms` does not. In remote-control-surface.test.ts, call `presentRemoteControl` with `getConfirmationLines` and `createRemotePanel`'s row with `getWaitingCards: () => 2` and assert the rendered row/lines contain "2 cards waiting" and the card heading; add one case where the callback changes after open and the `subscribeChange` repaint shows it.
- Evidence: forwards at the cited lines; the three tests named above call only `projectRemoteRow`, `formatRemoteStatusLines`, `withConfirmationLines` and `presentDecisions`.
- Confidence: high.

### [F-003] `raceApproval`: the `if (settled) return` guard ahead of `onUndelivered` is not pinned by any test

- Severity: minor
- File: src/tui/approval-mirror.ts:51-52 (tests: src/remote/mirror-undelivered.test.ts:94-132, src/tui/approval-mirror.test.ts unchanged)
- Problem: the change put `onUndelivered` after the `settled` guard on purpose, so a topic leg that comes back "undelivered" after the dock already answered does not print "◇ Telegram mirror not delivered ... Answer it here." over a card that is already answered. Both new raceApproval tests resolve the topic leg before the dock returns (`topic: async () => undelivered` while the dock waits 10 ms); no test makes the dock win first and then lets an undelivered answer arrive. Moving the `onUndelivered` line above the guard would pass both.
- Why it matters: the spurious system line and a `markUndelivered` call on an answered card are exactly what the ordering prevents; `markUndelivered` itself ignores answered entries, so the only visible symptom is a misleading transcript line, which is why nothing else would catch it.
- Fix: add a test in approval-mirror.test.ts where the dock resolves first and the topic promise is resolved by hand afterwards with `{ decision: "deny", always: false, undelivered: true }`, then `await` a microtask flush on the already-returned `raceApproval` promise and assert `told === 0`. Drive the ordering with a deferred promise, not a timer (the fixed 10 ms timers in the existing tests are already filed).
- Evidence: approval-mirror.ts:51 `if (settled) return;` then 52 `if (answer.undelivered === true) options.onUndelivered?.();`.
- Confidence: high.

### [F-004] Test placement: `withMirrorNote` drags the whole shell module into a remote-layer test, and the surface assertions sit in a module-named catch-all file

- Severity: info
- File: src/remote/mirror-undelivered.test.ts:10; src/tui/operator-confirmations.test.ts:129-165
- Problem: `mirror-undelivered.test.ts` imports `withMirrorNote` from `../tui/tui-shell` (a 476 KB module with the OpenTUI surface) to test a three-line pure array helper, so the remote-layer unit test depends on loading the whole shell and a shell refactor can break it. Separately, operator-confirmations.test.ts holds tests of `formatRemoteStatusLines`, `projectRemoteRow`, `presentDecisions`, help-groups and agent-commands, which belong beside remote-control-surface.test.ts, decisions-surface.test.ts and help-groups tests where a person changing those modules would look.
- Why it matters: discoverability and load cost only; no behaviour risk.
- Fix: move `withMirrorNote` next to `mirrorUndeliveredNote` (src/remote/shell-bridge.ts) or into approval-mirror.ts and import it from there; when F-002 is done, put the surface cases in the two surface test files and keep operator-confirmations.test.ts for the log and the line formatters.
- Evidence: import line quoted above; `projectRemoteRow`/`formatRemoteStatusLines` imports in operator-confirmations.test.ts:11.
- Confidence: medium.
