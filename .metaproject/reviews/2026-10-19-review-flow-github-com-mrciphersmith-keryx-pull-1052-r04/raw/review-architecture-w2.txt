### Findings

#### [AR-W2-001] review_complete assembles package facts in the command layer with its own manifest reader that disagrees with the gate's
- Severity: minor
- File: src/commands/operator-confirm-review.ts:658 (completionFacts), :665 (head)
- Problem: `completionFacts` parses manifest.json with an inline ad-hoc type, reads report.md, and parses research.json `dispatch` with `readFileSync` inside the command file. Every sibling card in this file delegates reading to a review/ function. The package already has typed readers for the same data (`getManagedReviewStatus` returning `ManagedReviewManifest`, `readManifestHead`, `recordedPackageHead` in src/review/managed.ts:173-181). The head is the concrete divergence: `recordedPackageHead` only accepts a 7-40 hex string (trimmed, lowercased); `completionFacts` accepts any non-empty string and shows it as `reviewed head: ...` after `cardSafe`.
- Why it matters: AC4 and TM-04 present the card as the package's own facts. A manifest whose `target.head` is not a valid SHA makes the card claim a reviewed head the gate ignores (the gate treats it as not recorded). The covering test ("a recorded head with a line break cannot add a line to the card") asserts that the card shows `HEAD\nwaivers: none` as the reviewed head, which pins the mismatch. A third reader of the same field will drift further as the gate evolves.
- Fix: move the read into src/review/ as one function (for example `readCompletionFacts(dir)` next to `evidence-level.ts` / `coverage-complete.ts`), built on the existing typed manifest and on `recordedPackageHead`, so card and gate share the head rule. The command spec keeps only rendering (`cardSafe`, lines) and the digest.
- Evidence: `keryx ctx rg -n "async function recordedPackageHead|readManifestHead" src/review` finds the existing readers; src/review/managed.ts:176-177 applies `/^[0-9a-f]{7,40}$/i` that operator-confirm-review.ts:665 does not.
- Confidence: medium (the layering point is a judgement call, the head-rule mismatch is verified in the source)

#### [AR-W2-002] The review_complete audit record is a write-only side file written after the close, outside the gate and undocumented
- Severity: minor
- File: src/commands/operator-confirm-review.ts:650 (COMPLETION_FILE), :780 (write)
- Problem: Every other card records who confirmed (`confirmedVia`, `pressedBy`, `pressedAt`) through the review/ library function that applies the decision, in a record the gates and readers use (manifest waivers, operator-decisions.json, plan-confirmation.json). `review_complete` closes the round through `completeReviewGated`, then the command layer writes `completion-confirmation.json` in a second, non-atomic step. No src code reads that file (`keryx ctx rg completion-confirmation src` matches only operator-confirm-review.ts and its test), it is not in the manifest `artifacts` list, and it appears in no doc (TM-04 6a, cli-reference, flow 464 files and CHANGELOG: no match). A close through the CLI leaves no equivalent record.
- Why it matters: TM-04 6a promises that "the record keeps pressedBy ... beside confirmedVia" for the card-gated acts, and the closing act is the one the PR exists to make attributable. A failed write leaves a closed round with no attribution (the code reports it, the test pins it), and nothing downstream (`review status`, the report, flow gates) can show who closed the round.
- Fix: pass the confirmation into `completeManagedReview` (an optional `confirmation: { quote, confirmedVia, pressedBy?, pressedAt? }`) and record it on the closed manifest in the same write as the status, as `readiness_waivers` entries already do. If the side file is kept, name it in the manifest artifacts and in TM-04 so a reader knows where to look.
- Evidence: src/commands/operator-confirm-review.ts:775-781 writes after `completeReviewGated` returns; test at operator-confirm-review-tools.test.ts:1947 builds a directory at that path to force the failed-write branch.
- Confidence: medium (design preference on where the record lives; the absence of any reader and of documentation is verified)
