### [R-001] Orchestrator skill still tells the shell agent to run `keryx review complete` after a waiver card

- Severity: major
- File: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.md:782 (the sibling SKILL.detail.md:386 and both bundled mirrors carry the same text)
- Problem: the PR changes the close path for an agent in keryx shell: SKILL.md:136 ("Done when", edited by this PR) now says an agent never runs `keryx review complete` and calls the `review_complete` card, and SKILL.detail.md:669 says the same. Two imperative lines in the same files were not updated. SKILL.md:782: "in keryx shell call `review_waive_coverage` (a card, never a terminal), then run `keryx review complete`". SKILL.detail.md:386 (memory-outside-stage repair): "in keryx shell call `review_waive_readiness` (the operator answers a card, never a terminal), then run `keryx review complete <package>`". Weaker, descriptive sites of the same wording: SKILL.md:124 ("A refused `review complete` ... fix that with a command and run it again"), SKILL.md:134 and SKILL.detail.md:866 ("the tail ... `keryx review complete`. Every managed round finishes them"), SKILL.md:59 (Round plan step 9, "`readiness`, `complete`").
- Why it matters: after a coverage waiver or a memory-outside-stage repair, an agent following those lines runs plain `keryx review complete <package>` through shell_exec. Plain complete has no TTY check and no command-risk floor (TM-04 section 8), so the round reaches `closed` with no `review_complete` card, no operator press, no `confirmedVia`, no `pressedBy`. The head, evidence, routing and readiness gates still run; the operator's final yes and its press record are what is bypassed. The CHANGELOG entry for 0.3.124 states that "both review-orchestrator skill copies ... tell the agent to call the card"; these lines make that false. Same finding as wave-1 R-001; re-found here because both files are in slice-02.
- Fix: in SKILL.md:782 and SKILL.detail.md:386, and in both bundled copies, replace ", then run `keryx review complete`" / ", then run `keryx review complete <package>`" with ", then call the `review_complete` card". Reword SKILL.md:124 to "run the failing command again, or call the `review_complete` card again", and make SKILL.md:134, SKILL.detail.md:866 and step 9 say "the `review_complete` card (outside keryx shell, `keryx review complete`)".
- Confidence: high

### [R-002] The agent can no longer record finding dispositions at close: the rule forbids the CLI and the card takes none

- Severity: major
- File: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.md:284
- Problem: SKILL.md:284 still instructs "`review complete --finding <id> --disposition <state> --evidence <ref>` records what became of a finding when the fix round closes". Before this PR the shell agent ran exactly that and the package closed with the dispositions. This PR's "Done when" bullet (SKILL.md:136) and SKILL.detail.md:669 now say an agent never runs `keryx review complete` and closes only through the `review_complete` card. The card cannot carry dispositions: completeSpec's inputSchema has only `package` (operator-confirm-review.ts:707-714) and apply calls `completeReviewGated(ctx.projectRoot, prepared.dir, { prLookup, prFiles, now })` (line 756) with no `dispositions`; `completeManagedReview` records dispositions only from `options.dispositions` (managed.ts:1017-1019) and writes the dismissed-incorrect review notes from them. The only writer of dispositions is the CLI `--finding/--disposition/--evidence` path (review.ts COMPLETE_FLAGS, runComplete).
- Why it matters: a shell agent that follows the new rule closes the fix round through the card and every finding stays `unknown`: no `acted-on` or `dismissed-*` is recorded and no review-note is written for `dismissed-incorrect`. That outcome record is the signal managed.ts:937-940 says the close exists to capture (83 findings once went unrecorded) and it feeds the precision measurement and the learning loop named in SKILL.md:281-290. If the agent instead follows SKILL.md:284 it breaks the rule at SKILL.md:136. The job-orchestrator loop also gates on this: its table row "every finding has a terminal disposition | `keryx review complete --finding ...`" (job-orchestrator SKILL.md:1002, orchestrator-prompt.md:27 and :193) has no card route either. A package already closed by the card can still be re-closed from the CLI (completeManagedReview has no already-closed guard), but only a human at a terminal may do that under the new rule.
- Fix: choose one and state it in SKILL.md:284 and SKILL.md:136: (a) let `review_complete` take an optional `dispositions` array (finding, disposition, evidence) shown on the card and passed to `completeReviewGated`; or (b) say that dispositions are recorded by the operator with `keryx review complete <package> --finding ... --disposition ... --evidence ...` in a terminal, before or after the card, and have the report list the findings still `unknown`. Update job-orchestrator SKILL.md:1002 and orchestrator-prompt.md to match.
- Confidence: medium (the card path and the missing argument are read in code; whether an agent in a real session follows line 136 or line 284 is not something I ran)
