### Findings

#### Naming
[CC5-005] minor, src/tui/operator-confirmations.ts:11 (and the call sites below). The concept "operator confirmation card" carries two vocabularies in one diff, and the status vocabulary is misleading.
- Sites: type `CardAnswerPlace` has the member "withdrawn" (a withdrawn card has no place it was answered; it was not answered); `answered` holds withdrawn cards too, and `confirmationLines` prints them under the prefix `answered` (operator-confirmations.ts:11, :19-24, :148-155). The exported function `confirmationLines(entries, now, heading)` (operator-confirmations.ts:148) shares its name with the option `confirmationLines?: () => readonly string[]` (decisions-surface.ts:439, a different signature: zero args, no heading), so tui-shell.ts has to alias the import (`confirmationLines as operatorConfirmationLines`, tui-shell.ts:126) and then adds a third name `operatorCardLines` (tui-shell.ts:3941). The log is `operatorCards` (tui-shell.ts:3940) but its class is `OperatorConfirmationLog`; the remote surface says `getWaitingCards` / `waitingCardsText` / `getConfirmationLines` side by side.
- Impact: a reader grepping "confirmationLines" lands on two unrelated things; the alias exists only to hide the collision.
- Fix: pick one noun ("card" is what the operator sees). Rename the option and the function apart (for example `formatCardLines` for the function, `cardLines` for the option), move "withdrawn" out of the place enum (a separate `withdrawn: true` or a distinct `state`), and print withdrawn cards under their own prefix.

#### Functions
[CC5-001] minor, src/tui/tui-shell.ts:6097. The `mirrorApprovalToTopic` closure is now about 52 lines (6097-6148, it was about 20) and holds five jobs at different levels: classifying the call as a card, the no-topic card path with its own ask/answer/finally bookkeeping (6102-6111), the inactive/too-long passthroughs, the race with its own try/finally and `onUndelivered` wiring (6120-6139), and applying a topic answer to the shell (6140-6147).
- Quote: `const unmirrored = isCard ? mirrorUndeliveredNote(bridge) : undefined;`
- Also in this function: `isCard` is a plain boolean, so TypeScript cannot narrow `meta.card` from it and the code re-checks `meta?.card !== undefined` twice (6102, 6120) and re-derives the card title `meta.card[0] ?? tool` twice (6103, 6120).
- Impact: the next change to card handling (for example wiring the Telegram-turn path, which another reviewer already noted lacks the log) has to be made inside a 50-line closure that already mixes abstraction levels.
- Fix: compute `const cardTitle = isCard ? (meta.card[0] ?? tool) : undefined` once from a type guard (see CC5-002), and extract two named helpers next to the closure: one for the unmirrored card (`askCardInShellOnly`) and one that runs the race and settles the log (`raceCardInTopic`). The closure then reads as the dispatch it is.

[CC5-003] minor, src/tui/remote-control-surface.ts:120. `formatRemoteStatusLines(status, posture?, confirmations?)` takes two optional positional arrays of the identical type `readonly string[]`.
- Quote: `export function formatRemoteStatusLines(status: RemoteStatus, posture?: readonly string[], confirmations?: readonly string[]): string[] {`
- Evidence: the test already has to write a placeholder, `formatRemoteStatusLines(status, undefined, confirmationLines(log.entries(), T0 + 60_000))` (operator-confirmations.test.ts), and the production caller at remote-control-surface.ts:262 passes `options.getPostureLines?.(), options.getConfirmationLines?.()`. Swapping the two arguments compiles and silently prints the posture lines under the "Operator confirmations" slot.
- Impact: Clean Code B2 (three positional parameters, two interchangeable). Cost is a transposition bug that the type checker cannot see.
- Fix: take an options object, `formatRemoteStatusLines(status, { posture, confirmations })`; the existing two callers (168, 262) are the only ones.

#### Comments
[CC5-007] info, src/tui/operator-confirmations.ts:86-90. The doc says "waiting first (oldest first), then the answered ones (newest first)", but `entries()` orders answered cards by when they were asked (`items` is appended at `ask` time and `answer` replaces in place), and the retention in `answer` (lines 57-60) drops the oldest-asked answered card, not the oldest-answered one.
- Quote: `const done = this.items.filter((item) => item.answered !== undefined).reverse();`
- Reproducible only if two cards overlap in time (card A asked first and still open, card B asked and answered, then A answered): A sorts after B although it was answered last, and with five answered cards already held, A is the one trimmed the moment it is answered. I found no path in the diff that overlaps two cards (the dock serializes them), so this is `info`. What settles it: whether `trackApproval`/parallel tool calls can hold two approvals open at once; if yes, sort by `answered.at` and trim by it, or reword the doc to "in the order asked".

#### Error Handling
No error handling issues found. The log's `settle(undefined, ...)` maps a thrown race to "withdrawn", and both card paths record the answer in a `finally`, so a throw cannot leave a card marked as waiting.

#### DRY
[CC5-002] minor, src/tui/tui-shell.ts:5555, :5563, :6100. The "is this approval an operator card" decision is written out at three sites with three different rules.
- 5555: `if (isUserPromptApprovalCard(tool) && meta?.alwaysAsk === true && meta.card !== undefined) {`
- 5563: `if (meta?.alwaysAsk === true && meta.card !== undefined) {` (relies on the branch above for excluding user_prompt)
- 6100: `const isCard = meta?.alwaysAsk === true && meta.card !== undefined && meta.card.length > 0 && !isUserPromptApprovalCard(tool);`
- Divergence already present: a call whose `card` is an empty array is an operator card to the dock (5563 shows `confirmOperatorCard(meta.card, ...)`), but not a card to the mirror (6100 requires `length > 0`), so the log, the sidebar count and the undelivered note skip a question the operator is in fact being asked.
- Fix: one exported predicate `isOperatorCardApproval(tool, meta): meta is Meta & { card: readonly string[] }` next to `isUserPromptApprovalCard`, used by all three sites (it also removes the re-checks in CC5-001). Sites enumerated with `keryx ctx rg "alwaysAsk === true" src/tui/tui-shell.ts` (4 matches, 3 of them this shape).

[CC5-004] minor, src/tui/operator-confirmations.ts:105 and :113. The new module copies two time helpers that already exist beside it and renders them differently in the same tab.
- Quote: `function age(ms: number): string {` and `function clock(at: number): string {`
- Sites: `clock` is the same expression `new Date(at).toISOString().slice(11, 19)` at remote-control-surface.ts:144 and (with a " UTC" suffix) channels-surface.ts:128, so three copies including the new one. `age` re-implements `formatAge` (remote-control-surface.ts:102) with different rounding: formatAge rounds minutes and prints "2h", `age` floors and prints "2h05m"; for 90 seconds formatAge says "2m" and `age` says "1m".
- Impact: the `/remote-control` Status tab now shows "Last heartbeat: 90s ago -> 2m ago" from formatAge and "asked 1m ago" from age for the same elapsed time; whoever fixes one rounding will not know about the other.
- Fix: export `formatAge` and `clock` from one place. remote-control-surface.ts already imports operator-confirmations.ts, so import them from a small shared module (or the surface that owns them) rather than from remote-control-surface to avoid a cycle; if the "h05m" form is deliberate for the 1-hour token, add a second named function and say so.

#### SOLID
[CC5-006] minor, src/tui/decisions-surface.ts:467 (ISP, F4). `OpenDecisionsOptions` is shared by `openDecisions` and `openDecisionsArms`, but the new member is silently dropped by one of them.
- Quote: `const { cwd, confirmationLines: _cards, ...rest } = options;`
- Evidence: `openWith` in the sidebar always passes `confirmationLines` (decisions-surface.ts ~330) and `showArms` goes through the same `openWith`, so the arms modal receives a callback it never calls; the type's doc ("appended under the report") is true for one of the two openers.
- Impact: the option reads as supported on the arms modal; a later reader may add cards there or wonder why the callback is never called.
- Fix: keep `confirmationLines` out of the shared type (an `OpenReportOptions = OpenDecisionsOptions & { confirmationLines? }` for `openDecisions` only), and let `openWith` pass it to `openDecisions` alone.
