## Security Review - slice-04 (press fields, undelivered flag, completeReviewGated)

Scope: slice-04 of PR 1052, head b1c6da0e6992, base 062aa9c36484. Code level only.

Guarantees I tried to break, and what I found:

- Forged or missing pressedBy: not accepted. operatorConfirmTool.invoke (src/commands/operator-confirm-tools.ts) refuses a remote answer when pressedBy or pressedAt is undefined, when the id is not in allowedUserIds (read fresh from loadRemoteConfig in src/commands/shell.ts), and when the card is older than 1 hour. The press fields reach invoke only through per-call locals of the driver in src/commands/agent.ts, set from the approval response, so they cannot leak across calls. The press source is the serve hub frame, which the hub checks against allowedUserIds (src/remote/hub.ts) and the client and bridge validate as a safe integer. A topic allow with no fromId aborts the dock and is then refused at invoke, which is a usability matter, not a bypass.
- Undelivered mirror treated as an answer: no. mapApprovalAnswer keeps undelivered only on a deny; an undelivered deny has no fromId, so isTopicPress is false and the dock stays the only place to answer. OperatorConfirmationLog.markUndelivered only changes the display.
- Close-path bypass: none. The only callers of completeManagedReview are completeReviewGated itself; keryx review complete (src/commands/review.ts) and the review_complete card (src/commands/operator-confirm-review.ts) both call completeReviewGated, which runs the run-profile and narrowed-routing refusals first. The card also recomputes a facts digest at apply time and refuses if the head, evidence level or waivers changed after the card was shown.
- Tampering with signature records: the token store and signature record are plain files, and consumeConfirmationToken copies pressedBy and pressedAt from the stored file. This is the same trust model as before (the hash, target and acChecksum are equally file-held), so it is not a new vector. See SEC-W4-001.
- Nested agent shells: nestedAgentCardRefusal still blocks cards when KERYX_TOOL_CALL=1.

Findings: two INFO notes; no blocker, major or minor.

Clean areas checked: injection, authn/authz of the remote answer, IDOR, secrets, crypto (sha256 token hash, randomUUID card token), CSRF, path traversal, open redirect. React and NestJS patterns are not touched by this slice.
