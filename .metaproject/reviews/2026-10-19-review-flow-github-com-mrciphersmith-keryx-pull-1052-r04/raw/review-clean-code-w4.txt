### Findings

#### Naming
No naming issues found.

#### Functions
[CC4-002] `answerChunkEstimate` and `recordCoverageWaiver` take `confirmedVia` and `press` as two separate trailing optional positionals (src/review/chunks-estimate.ts:160, src/review/coverage-complete.ts:215). `answerChunkEstimate` now has 6 parameters, `recordCoverageWaiver` 5, and the two optionals describe one fact (how the yes arrived), so every caller has to pass the same source twice: `confirmation.confirmedVia, cardPressFields(confirmation)` (src/commands/operator-confirm-review.ts:157 and :294). A caller that forgets the last argument records a remote-card answer with no press fields and nothing flags it. Fix: replace the pair with one `confirmation?: { confirmedVia: ConfirmedVia } & CardPress` (or an options object with `now` and `confirmation`). `waiveReadiness`, `recordPlanConfirmation` and `recordPremiseDecision` in the same diff already take it as one object.

[CC4-004] `mapApprovalAnswer` reads the new field through a second inline cast instead of widening the local type (src/remote/shell-bridge.ts:208). `o` is already cast to `{ decision?; approvalId?; fromId? }` three lines earlier; the added line casts it again to `{ undelivered?: unknown }`. Fix: add `undelivered?: unknown` to the first cast and write `o.undelivered === true`.

#### Comments
[CC4-005] The doc comment of `ReadinessWaiver` is separated from it by two declarations and a function (src/review/types.ts:87). The line `/** A readiness item the operator waived ... */` sits above `ConfirmedVia` (already detached on the base), and this diff inserts `CardPress` and `cardPressFields` between that stack and `ReadinessWaiver` (line 102), so the sentence now documents a type 15 lines above the one it describes. Fix: move the comment to directly above `export type ReadinessWaiver` and leave `ConfirmedVia` with its own doc.

#### Error Handling
No error handling issues found.

#### DRY
[CC4-001] The `pressedBy` / `pressedAt` pair is declared and conditionally spread by hand at many sites although `CardPress` and `cardPressFields` exist (src/review/types.ts:92-100). Sites in this slice that restate it instead of using the helper: src/flow/confirm-token.ts:76-77 (stored token type), :120 and :140-141 (mint binding and spread), :235-236 (consume spread); src/flow/types.ts:188-189 and :785; src/flow/service.ts:1681-1682; src/harness/external/write-land.ts:173 and :229 (one 330-character line with a three-level nested spread); src/learning/decisions.ts:33-34; src/review/estimate.ts:199-200 (`PlanConfirmation`, which src/review/plan-confirmation.ts:33 declares a second time as `& CardPress`, so one record shape was extended in two different ways in the same diff). The cost is that adding a third press field, or changing the rule for an unset value, means editing about ten places and the copies drift. The helper lives in src/review/types.ts, which src/flow, src/harness and src/learning probably should not import, and that is likely why they were not used. Fix: move `CardPress` and `cardPressFields` to a neutral module (for example src/lib/card-press.ts), re-export from src/review/types.ts, and use `& CardPress` plus `...cardPressFields(x)` at the sites above. The operator-confirm-other.ts duplicate is CC3-005 and is not repeated here.

[CC4-003] The same 100-character clause is pasted three times in `nextStep` (src/review/completion-gate.ts:756, :759, :761): "then call the `review_complete` card (the operator answers it; you never run `keryx review complete` yourself)". The wording was just changed once to follow the TM-04 rule and is the sentence most likely to change again (D-01 and D-03 were exactly this class). Fix: hold it in one `const CLOSE_VIA_CARD = ...` and interpolate it into the three returns.
