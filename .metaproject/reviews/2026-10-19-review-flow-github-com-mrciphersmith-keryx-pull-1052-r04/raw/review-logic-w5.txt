### Logic Bugs

### [F-001] A topic leg that ends without a press leaves the card "waiting in Telegram"

- **Severity**: major
- **File**: src/tui/approval-mirror.ts:50-54 (consumer: src/tui/operator-confirmations.ts:81-84, src/tui/tui-shell.ts:6127-6130)
- **Problem**: `raceApproval` calls `onUndelivered` only when the answer carries `undelivered: true`. Every other non-press end of the topic leg falls through at `if (!isTopicPress(answer)) return;` and the log is not told. Those ends are real. `RemoteClient.failApprovals()` resolves `{ decision: "deny" }` when the event stream drops (client.ts:820) and when the client is stopped, which is what `/remote-control off` does (client.ts:404). Neither answer is flagged undelivered, and neither carries a fromId. The 1-hour server wait also ends this way. The log entry keeps `mirrored: true` and `answered: undefined`, so `waiting()` counts it, the Remote sidebar row says `<topic> · 1 card waiting` in the attention role, and the status tab prints `waiting ... N m left of the 1-hour token`.
- **Why it matters**: After a stream drop and reconnect, or after `/remote-control off` followed by `on`, the sidebar and the status tab send the operator to Telegram for a card that nobody listens to any more. The topic leg promise is gone, and the client documents that a late press finds nothing. The operator presses in the topic and gets no effect. The text only changes after the full hour ("Telegram token expired") or when the dock is answered. This is the same signal AC6 exists to give, and it is wrong for as long as the dock stays open. It is not the filed H4-01 (cutoff applied only on repaint) or PC-008 (failed send after open): the send succeeded and the leg ended later.
- **Reproduction scenario**: Run `/remote-control on` and let `review_complete` ask a card. The card is posted to the topic. The serve connection drops and reconnects. `failApprovals` resolves the waiter with deny. The sidebar still shows "1 card waiting" and the dock is still open. Probe output above: `waiting(): 1 mirrored: true` after the leg returned a plain deny.
- **Fix**: Treat any topic-leg end that is not a press and not caused by this shell (`settled` false, `topicAbort.signal.aborted` false) as "no longer waiting in the topic". Either widen `onUndelivered` into `onTopicEnded(reason)` and call it for every non-press while `!settled`, or have `markUndelivered` accept a reason and render "Telegram card closed, answer in the shell". The timeout case at the 1-hour mark then also drops out of `waiting()` without the repaint dependency. Add a test with a topic leg that resolves `{decision:"deny"}` and assert `waiting().length === 0`.
- **Patch**:
  ```diff
  -          if (answer.undelivered === true) options.onUndelivered?.();
  -          if (!isTopicPress(answer)) return;
  +          if (answer.undelivered === true) options.onUndelivered?.();
  +          if (!isTopicPress(answer)) {
  +            // the leg ended on its own (stream drop, remote off, 1-hour wait): the topic no longer holds this question
  +            if (answer.undelivered !== true) options.onTopicClosed?.();
  +            return;
  +          }
  ```
  with `onTopicClosed` wired in tui-shell.ts next to `onUndelivered` to call a log method that sets `mirrored: false`.

### Edge Cases

### [F-002] Answered-entry pruning keeps the newest asked, not the newest answered

- **Severity**: minor
- **File**: src/tui/operator-confirmations.ts:57-60 and 87-91
- **Problem**: `answer()` prunes `answered.slice(0, length - 5)`, where `answered` is in ask order, and `entries()` reverses the same order and the doc says "newest first". Both use the ask id, not the answer time. A card asked first and answered last is the first one pruned and sorts below cards answered earlier.
- **Why it matters**: The log is serial today (one dock at a time), where ask order equals answer order, so this is latent. It bites when two cards overlap: a long-waiting card answered in Telegram after six faster ones is pruned the moment it is answered, and the "who pressed" line the log exists to show vanishes. Probe output: after answering Q1..Q6 and then Q0 (with `pressedBy: 9`), `entries()` is `Q6,Q5,Q4,Q3,Q2`. The serial-order test at operator-confirmations.test.ts:1448 does not cover it.
- **Fix**: Sort answered entries by `answered.at` (ties by id) for both the prune and the listing, or keep a separate array appended in answer order.

### [F-003] The log records a yes for an allow that the tool then refuses

- **Severity**: info
- **File**: src/tui/operator-confirmations.ts:68 (against src/commands/operator-confirm-tools.ts:211-216)
- **Problem**: `settle` maps any topic `allow` to `yes: true`, with `pressedBy` undefined when the answer lacks a fromId. The tool refuses a remote answer that does not name who pressed, or whose user is not on the allowed list (operator-confirm-tools.ts:214-216), and refuses a token older than the hour. The log line still reads `yes · pressed by a Telegram user`.
- **Why it matters**: No defect while the server always sends fromId. If it does not, the surfaces report a confirmation while the tool did not apply. The log records the press, not the outcome, which may be the intent. Say so in the line, or leave it.
- **Fix**: Optional. Record `yes: false` with a short reason, or label the entry "press not accepted" when `fromId` is undefined on an allow.
