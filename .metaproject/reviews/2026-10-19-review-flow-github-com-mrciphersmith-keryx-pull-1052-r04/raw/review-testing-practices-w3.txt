### F-001 Three of the four undelivered sites in RemoteClient.askApproval, and both deliberate non-undelivered denies, are unpinned
- Severity: minor
- File: src/remote/mirror-undelivered.test.ts:46 (production: src/remote/client.ts:441, 450, 453, 457; non-flag denies at 477 and 480)
- The AC5 contract is that the flag is set exactly when the question never reached the topic. askApproval has four returns that set it: not connected or already aborted (client.ts:441), a non-ok response to the POST (450), a response without a usable approvalId (453) and a thrown POST (457). The only test drives the first one (fetchImpl rejects, but the client never connected, so the early return fires and `post` is never reached). Under the same file's own name "an unreachable client reports undelivered", dropping `undelivered: true` from 450, 453 or 457 leaves every test green: grep for `undelivered` under src finds test hits only in this file, and the existing askApproval/requestApproval tests (approval.test.ts, approval-edit.test.ts, telegram-permissions.test.ts, shell-bridge.test.ts) compare only the `decision` (requestApproval returns the bare decision). The opposite boundary is unpinned too: when the question WAS posted and the stream then dropped (client.ts:477, `if (!this.connected) return { decision: "deny" }`) or the turn was aborted after posting (480), the topic holds live buttons and the flag must stay absent, otherwise the operator would be told "Answer it here" while the topic can still take a press. A change that adds the flag at those two returns is also invisible to the suite.
- Why it matters: the flag is the only signal that tells the operator the mirror failed; it is set at four places by hand and the test covers one.
- Fix: in mirror-undelivered.test.ts add a table over a connected client (see the existing connected-client harness in telegram-permissions.test.ts or approval.test.ts) whose fetchImpl answers the approval POST with (a) status 500, (b) 200 with `{}`, (c) a rejection, each expecting `toMatchObject({ decision: "deny", undelivered: true })`; and two cases that post successfully then (d) drop the stream, (e) abort the signal, each expecting `answer.undelivered` toBeUndefined().

### F-002 The two raceApproval tests wait on fixed 10 ms timers
- Severity: minor
- File: src/remote/mirror-undelivered.test.ts:106 and :125
- Both dock stubs do `await new Promise((resolve) => setTimeout(resolve, 10))` to give the topic leg time to settle before the test reads `told` or asserts `race.signal.aborted === false`. Fixed sleeps are banned in this lane. It cannot flake in practice, because the topic stub resolves immediately and its `.then` microtasks drain before any timer fires, so the timer buys nothing a condition would not; but the test then says "10 ms is enough" instead of "the topic leg has finished". This copies the pattern already in src/tui/approval-mirror.test.ts (lines 82 and 97 use 15 ms and 5 ms), so the convention is inherited, not introduced.
- Fix: make the topic stub signal completion and have the dock wait on that: `let topicDone!: () => void; const settled = new Promise<void>((r) => { topicDone = r; });` with `topic: async () => { queueMicrotask(topicDone); return undelivered; }`, and in the dock `await settled; await new Promise((r) => setImmediate(r));` (a macrotask yield after the leg ended, not a duration) before the `aborted` assertion. In the second test assert `told` after `await settled` the same way.

### F-003 bridge.connected is only ever tested as false
- Severity: info
- File: src/remote/mirror-undelivered.test.ts:84 (production: src/remote/shell-bridge.ts `get connected()`)
- The new getter `this.client?.connected === true` feeds mirrorUndeliveredNote in tui-shell. The test asserts `bridge.connected` toBe(false) for a bridge with no client; no test constructs a bridge with a connected client and expects true, and none drives a connected client whose `askApproval` returns `{ decision: "deny", undelivered: true }` through `bridge.askApproval` (only mapApprovalAnswer is tested in isolation). A getter that always returned false would put the "channel is not connected" note on every card while the suite stays green. shell-bridge.test.ts has a fake-client harness (line 99) where this is a two-line case.
- Fix: in shell-bridge.test.ts (or here) start a bridge over the fake client, expect `bridge.connected` true, then make the fake `askApproval` return `{ decision: "deny", undelivered: true }` and expect `bridge.askApproval("card")` toMatchObject the same.
