### Details

### [CC3-001] review_complete `apply` mixes gate execution, closure inference, record writing and output composition

- **Severity**: major
- **File**: src/commands/operator-confirm-review.ts:741
- **Principle**: Clean Code - Functions B1 (size, one thing, one level of abstraction)
- **Problem**: `apply` of `completeSpec` spans lines 741-797 (57 lines). It (1) re-reads facts and compares the digest, (2) runs `completeReviewGated` inside try/catch into `done` and `gateError`, (3) infers "closed" by re-reading the manifest when the gate threw, (4) builds and atomically writes `completion-confirmation.json` inside a second try/catch into `recordError`, and (5) composes a multi-line output with two kinds of "closed but ..." problems. Three nullable variables (`done`, `gateError`, `recordError`) are carried across the blocks, and the reader has to hold the four outcome combinations (gate ok/threw x closed/not closed x record written/failed) in mind to follow the end.
- **Fix**: Extract three helpers and leave `apply` as the orchestration: `runCompletionGates(...)` returning `{ done, gateError, closed }`; `writeCompletionRecord(dir, record)` returning the error or undefined; `completionOutput({ closedLine, problems, done })` building the text. Each is then testable alone and `apply` drops below 25 lines.

### [CC3-002] `completionFacts` reads five sources and also writes card wording that is hashed into the digest

- **Severity**: minor
- **File**: src/commands/operator-confirm-review.ts:658
- **Principle**: Clean Code - Functions B3 (abstraction level consistency)
- **Problem**: One 35-line function parses manifest.json, report.md and research.json, reads operator decisions, and formats display lines such as "evidence level: the report has no `Evidence level:` line; the gate will refuse" and "could not read research.json (...); the research gate will refuse". Presentation strings thereby become part of the "facts" object whose JSON is hashed by `factsDigest`, so rewording a card line changes what counts as "the package moved".
- **Fix**: Split into a pure reader returning raw values (head, evidence line or undefined, readiness waivers, coverage waiver or read error, decisions, status) and a small `describeFacts(raw)` that builds the card lines. Hash the raw value.

### [CC3-003] `operatorConfirmTool.invoke` grew to 43 lines and uses two `as` casts to get around narrowing

- **Severity**: minor
- **File**: src/commands/operator-confirm-tools.ts:198 (casts at 206 and in the confirmation record, `pressedBy as number`, `pressedAt as string`)
- **Principle**: Clean Code - Functions B1/B3
- **Problem**: The remote-press validation (who pressed, allowed list, one-hour TTL) sits inline between token lookup and applying the effect, which puts a security policy, the bookkeeping of a `pending` map and the effect call in one body at the 40-line threshold. `pending.delete(token as string)` and `pressedBy as number` exist because the `remote` boolean does not narrow the `let` variables; the casts hide the fact that they can be undefined if the checks are reordered.
- **Fix**: Extract `remotePressRefusal(ctx, entry, now, allowed)` returning `{ refusal } | { pressedBy, pressedAt }`. The caller then spreads the returned press object and needs no cast; take the token from `entry` (store it in the map value) instead of casting `token`.

### [CC3-004] agent.ts carries one remote answer as three loose variables and repeats the same guard three times

- **Severity**: minor
- **File**: src/commands/agent.ts:5816 (declarations), 6123 (assignments), 6190-6192 (spreads into `tool.invoke`)
- **Principle**: Clean Code - DRY E1 (2 spreads share one guard) / data clumps
- **Problem**: `confirmationVia`, `confirmationPressedBy` and `confirmationPressedAt` always travel together, yet are three `let` variables set in three statements and passed through three spreads that each repeat `confirmationToken !== undefined && confirmationVia === "remote" && ...`. The next field added to the press (a message id, say) has to be added in four places.
- **Fix**: Hold one `confirmation?: { via: "local" | "remote"; pressedBy?: number; pressedAt?: string }` and build the `invoke` context with a small helper, or spread `cardPressFields(remote)` once under a single guard.

### [CC3-005] operator-confirm-other.ts `record()` hand-writes what `cardPressFields` already does, and inlines the `CardPress` shape twice

- **Severity**: minor
- **File**: src/commands/operator-confirm-other.ts:109 and :625
- **Principle**: Clean Code - DRY E1
- **Problem**: `record()` repeats the two `=== undefined ? {} : {...}` spreads, and both its return type and the `recordScheduleDecision` line type spell `pressedBy?: number; pressedAt?: string` by hand. `src/review/types.ts:92-100` exports `CardPress` and `cardPressFields` for exactly this, and operator-confirm-review.ts uses them at nine call sites in the same PR. Two shapes for one concept can drift (the shared type allows `| undefined`).
- **Fix**: `function record(confirmation): { confirmedVia: string; quote: string } & CardPress { return { confirmedVia: ..., quote: ..., ...cardPressFields(confirmation) }; }` and type the log line `... & CardPress`.

### [CC3-006] Magic number 12 for the abbreviated head, three times in one spec

- **Severity**: minor
- **File**: src/commands/operator-confirm-review.ts:723, :734, :784
- **Principle**: Clean Code - DRY E2 (magic numbers)
- **Problem**: `facts.head.slice(0, 12)` / `prepared.head.slice(0, 12)` appears three times in `completeSpec` (card title, subject, result line). The tests assert the 12-character form (`HEAD.slice(0, 12)`), so the length is a contract, but it is written as a bare literal.
- **Fix**: `const SHORT_HEAD_CHARS = 12;` and a `shortHead(head)` helper next to `clip`.

### [CC3-007] The error-to-message expression is written again next to an existing helper

- **Severity**: minor
- **File**: src/commands/operator-confirm-review.ts:675 and :743
- **Principle**: Clean Code - DRY E1
- **Problem**: This diff adds a local arrow `const reason = (error: unknown): string => (error instanceof Error ? error.message : String(error))` (line 743) and an inline copy (line 675), while the same file already has `failed` (line 87) doing the same conversion and operator-confirm-other.ts:82 has `errorText`. Counting operator-confirm-tools.ts:183 and :235 the expression exists seven times in three sibling files. The local name `reason` also collides in meaning with the `reason` field the sibling specs pass around.
- **Fix**: Export one `errorText` from operator-confirm-tools.ts (the framework file both spec files already import from) and use it at 675, 743, 786-787; name it `errorText`, not `reason`.

### [CC3-008] The five review card names are hardcoded in two slash-command descriptions

- **Severity**: minor
- **File**: src/commands/agent-commands.ts:187 and :304 (the same list also at src/standard/help-groups.ts:582 and :600, outside this slice - reported as additional sites only)
- **Principle**: Clean Code - DRY E2 (repeated string literal)
- **Problem**: "review_confirm_plan, review_decide_premise, review_waive_readiness, review_waive_coverage, review_complete" is pasted into four descriptions. This PR is itself a case of the list changing (review_complete was added); the next card has to be found by text search in four strings, and a missed one gives a help text that omits a card that is waiting.
- **Fix**: Define the list once (a constant exported next to the Helyx card tool names) and interpolate it into the descriptions, or say "the review cards" without listing names in the one-line description.
