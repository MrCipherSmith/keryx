### What I tried to break, and why it held

1. Allowed user id. The hub drops senders outside `config.allowedUserIds` before routing (src/remote/hub.ts route). The record repeats the check in `operatorConfirmTool.invoke` against `binding.allowedUserIds()`, which the shell reads fresh from `loadRemoteConfig()` (src/commands/shell.ts). It fails closed in three cases: no binding, config not loadable (undefined), or `pressedBy` missing. The remote fields only reach the invoke context when `confirmationVia === "remote"` (agent.ts), and only `operatorConfirmTool` consumes them. A local press carries no pressedBy and records no press fields.
2. One press per card. The token is deleted from `pending` synchronously in `invoke` before any await and before the remote checks, so a concurrent or replayed press cannot reach `apply` twice. At the hub, `pressApproval` accepts only an approval id the hub generated for that session and `dropApproval` makes it single-use (src/remote/http-surface.ts).
3. One hour. `REMOTE_CARD_TTL_MS` is compared against `entry.issuedAt` taken from the shell clock via `now()`. A stale card is refused after the token is already burned, so a late press cannot be retried.
4. Token burned on refusal. Every refusal path (input changed, missing press fields, user not allowed, card expired) happens after, or together with, `pending.delete`. An input mismatch deletes the token as well.
5. pressedBy / pressedAt. `pressedAt` is stamped by the shell (tui-shell.ts `remoteApproval`), not by the sender. `cardPressFields` spreads both into every recorder: chunk estimate, publish, coverage waiver, readiness waiver, operator decisions, plan confirmation, premise decision and the schedule decision log. The new tests cover the remote case for the chunk, premise and plan cards and for review_complete.
6. review_complete head binding. `completeSpec` takes no head from the model: the input schema has no `head` property and a model-supplied `head` is ignored (test "the model cannot supply a head"). `completionFacts` reads the head from `manifest.target.head`, and the card shows that head. `factsDigest` over head, evidence line, readiness waivers, coverage waiver and operator decisions is recomputed in apply, so a waiver or decision added after the card refuses (tests "a waiver added between the card and the yes", "an operator decision added between..."). Apply runs `completeReviewGated`: the run-profile refusal, the narrowed-routing refusal, then `completeManagedReview` (head gate, evidence level, research, readiness). A merged PR or a moved head is refused unless the report's first line names the SHA. Card lines are single-line sanitized (test "a recorded head with a line break cannot add a line to the card").
7. Package path. `resolvePackage` confines the package to the project through `placeReviewPath`, and a bare id resolves under the review roots via `resolveReviewPackagePath`. The card cannot point review_complete at a directory outside the project.
8. Parity with the terminal. `review.ts runComplete` now goes through the same `completeReviewGated`, so the card and the command meet the same gates. The card meets the premise-decisions rule and never waives it.
9. Roster. `review_complete` is registered in the unattended exclusion list and the roster tests (19 tools) keep it out of MCP, ACP, subagent and readline rosters.

### Residual observations (not filed, consistent with TM-04)
- The review_complete facts digest covers the evidence line but not the rest of the report body, and the `pending` map has no sweep, so unanswered cards stay in memory for the session. Neither gives an attacker anything beyond what TM-04 section 4 and section 8 already state: a same-user agent with shell access can write the stores directly, and the card is a record of the operator's answer, not a lock. No attack vector in the changed code, so below the INFO bar of Iron Law 1.
