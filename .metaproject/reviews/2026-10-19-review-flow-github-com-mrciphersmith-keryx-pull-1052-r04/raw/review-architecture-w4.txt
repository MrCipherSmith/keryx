### Summary
The slice adds an in-memory view model (OperatorConfirmationLog) and feeds it to three TUI surfaces (Remote sidebar row, /remote-control status tab, /decisions modal). Dependency direction is sound: the view model sits in tui/, imports one constant from commands/, and no cycle exists (operator-confirm-*.ts import nothing from tui/). unattended.ts keeps its list-not-import rule and is covered by the roster test. The one real structural gap is that the log is wired into only one of the two approval pipelines in tui-shell.ts, so the "pending/who pressed" view is incomplete for cards answered in a Telegram-started turn. Two smaller observations are info-level.

### Findings

[F-001] The operator-card view log is wired into only one of the two approval pipelines
- Severity: minor
- File: src/tui/tui-shell.ts:6028 (requestApprovalForTelegramTurn) vs :6095-6138 (mirrorApprovalToTopic)
- Problem: operatorCards.ask / settle / markUndelivered are called only inside mirrorApprovalToTopic (the dock-plus-topic race for turns typed in the shell). requestApprovalForTelegramTurn, the topic-only pipeline for turns that started in Telegram, is a second, separate implementation of the same approval step. It builds the same remote approval (remoteApproval(meta.fingerprint, answer.fromId) at the end of that function) and records pressedBy in the durable store, but it never touches operatorCards. A review_complete / review_confirm_plan / waiver card raised during a Telegram-started turn is therefore absent from the Remote sidebar "N cards waiting" count, the /remote-control status tab and the /decisions modal, and its "pressed by Telegram user N" line never appears there. That is the case where Telegram is the only place the operator answers.
- Why it matters: AC6 says the TUI shows each pending remote confirmation and shows pressedBy on an answered one. The view is built per call site instead of at the one place both pipelines share, so the surfaces silently under-report in a mode the feature exists for. The next change to either pipeline can drift further.
- Fix: move the ask/settle bookkeeping to a small helper used by both pipelines (for example `trackOperatorCard(meta, tool, mirrored): { settle(...) }`), and call it from requestApprovalForTelegramTurn around `bridge.askApproval(...)` with place "telegram" and pressedBy = answer.fromId. For the operatorCardTooLongForTopic early return in both pipelines, either log the card as mirrored:false or state in a comment that it is intentionally absent from the view.
- Evidence: `keryx ctx rg "operatorCards\."` over src/tui/tui-shell.ts lists only ask (:6103, :6120), settle (:6138), the getWaitingCards/entries readers and subscribe; no hit inside requestApprovalForTelegramTurn (:6028-:6167). The diff hunk for that function changes only the final return (remoteApproval(...)).
- Confidence: medium (the code path is clear; whether review cards are in practice raised during Telegram-started turns depends on usage, but the pipeline accepts any alwaysAsk+card).

[F-002] The unmirrored branch re-implements the log's settle rules inline
- Severity: info
- File: src/tui/tui-shell.ts:6100-6112
- Problem: for a card whose mirror was not delivered, the branch computes the answered place itself (`foregroundOperation.signal.aborted || verdict === undefined ? "withdrawn" : "shell"`, `yes: verdict !== undefined && verdict !== false`). OperatorConfirmationLog.settle(id, { from: "dock", result }, aborted) already owns exactly this mapping for the mirrored branch (src/tui/operator-confirmations.ts, settle). Two copies of the rule can diverge (for example if a dock result gains a new shape).
- Fix: call `operatorCards.settle(unmirroredId, verdict === undefined ? undefined : { from: "dock", result: verdict }, foregroundOperation.signal.aborted)` in the finally block.
- Evidence: tui-shell.ts diff lines 1219 and 1254; operator-confirmations.ts settle (diff lines 417-422).
- Confidence: high that the logic is duplicated; info because behavior is currently equivalent.

[F-003] TTL policy constant is imported from the command registry into a pure view-model module
- Severity: info
- File: src/tui/operator-confirmations.ts:6
- Problem: REMOTE_CARD_TTL_MS lives in src/commands/operator-confirm-tools.ts, the registry module that statically imports operator-confirm-review.ts and operator-confirm-other.ts. operator-confirmations.ts (and through it remote-control-surface.ts, which now imports waitingCardsText from it) takes a value import on that whole graph for one number. No cycle and no runtime cost in the shell (tui-shell.ts already loads the module), but the surface modules lose their standalone, light import graph, and the TTL policy (enforced in the registry) is mirrored by the view through an import rather than a small shared constants module.
- Fix: optional. Move REMOTE_CARD_TTL_MS to a leaf module (for example src/remote/protocol.ts or a new src/commands/operator-confirm-limits.ts) that both operator-confirm-tools.ts and the TUI import.
- Evidence: `keryx ctx rg REMOTE_CARD_TTL_MS src` (definition at operator-confirm-tools.ts:117, enforcement at :218, view use at operator-confirmations.ts:6/:83/:125); operator-confirm-tools.ts imports at lines 30-33.
- Confidence: high on the facts, info on the severity.
