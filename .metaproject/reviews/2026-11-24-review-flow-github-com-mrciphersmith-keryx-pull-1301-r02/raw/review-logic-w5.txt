### Logic Bugs

#### [F-001] A folder refused as stale-snapshot stays "Loading…" forever when Refresh catalog returns the same snapshot id
- Severity: minor
- File: apps/desktop/src/metaproject/useMetaprojectTree.ts
- Problem: After this round's change, a stale-snapshot answer calls `onStale()` and returns. The folder keeps `status: "loading"`, or its `more` stays `{status:"loading"}`. Only a change of the `snapshot` prop clears it (the generation bump in `useMetaprojectTree`). Snapshot ids are content hashes (`src/integrations/metaproject-explorer.ts:174`, sha256 of nodes/edges/pages/layerStats). Refresh catalog does a non-quiet read that calls `setCatalog(result)` and `setSnapshotMismatch(false)` even when the id is unchanged (MetaprojectView.tsx:410-416). If the project's content goes A→B→A between the tree read and the Refresh click, the tree's snapshot stays the same, so nothing is reset. The banner disappears and the row stays "Loading…". `ensure` will not re-read because `folders.has(parent)`, `more()` refuses because `more.status === "loading"`, and no Retry is offered. Repro: expand a folder at s1. Save a wiki page (s2) before the folder answers, so the read is refused as stale-snapshot and the banner shows. Undo the save (back to s1). Click Refresh catalog. The folder (or its Show more) stays "Loading…" until some other content change. Before this round the folder showed an error with a Retry, which would have succeeded here.
- Impact: The UI is stuck with no way to recover for that folder or page until another project change happens. The tree state outlives leaving the view, so leaving and returning does not clear it. No data is lost.
- Suggested fix: Record the parents and pages that ended stale (for example a `stalled` set on the ScopeTree). When the explorer finishes a catalog load, re-issue them even if the snapshot id did not change. For example, give `useMetaprojectTree` a `revision` input bumped by `setCatalog` and treat a new revision like a new snapshot for the stalled entries only. Do not delete the folder on stale: that would make `flatten` report it unread and re-read it in a loop while the CLI is still at another snapshot. Add a view test: stale refusal, then Refresh catalog returning the same snapshotId, then the folder is read again.
- Evidence: useMetaprojectTree.ts catch branch (quoted below); generation reset only on `state.current.graph.snapshot !== snapshot`; MetaprojectView.tsx:410-416 and :881; explorer.ts:174 content-hash id.
- Quote: `if (cause instanceof MetaprojectRequestError && cause.code === "stale-snapshot") {\n        latest.current.onStale();\n        return;\n      }`
- Confidence: medium (the A→B→A trigger is rare but reachable; I traced the code path and did not run it)

#### [F-002] Focus anchor that is itself a status row replaced in the same commit falls back to the raw index
- Severity: minor
- File: apps/desktop/src/metaproject/MetaprojectTree.tsx
- Problem: The hand-off anchors to `lost.before`, the row just before the focused one. For a `more:P` row, that is the last row of P's subtree. When P's last entry C is an expanded folder still loading, the anchor is `status:C`. If C's children and P's next page arrive in one commit, `status:C` and `more:P` are both removed. `anchor < 0` then sends focus to `elements[lost.index]`, which now holds one of C's newly inserted children, not P's first appended entry. This is the same class as r2-logic-w1-F-001, narrowed to the case where the anchor itself leaves.
- Impact: In this concurrent case, keyboard focus lands on an unrelated row one level deeper. The case is rare: it needs Show more focused, the last entry expanded and still loading, and both answers in one commit.
- Suggested fix: Anchor a status row to an entry of its own parent rather than to whatever row precedes it. For `more:P`, record the id of P's last entry row (an `entry` row with `parent === P`) and focus the next `entry` row with `parent === P` after it. For `status:P`, anchor to `d:P`, which is already the preceding row. Fall back to the index only when that entry is gone.
- Evidence: MetaprojectTree.tsx layout effect (quoted below); `before` is set in onFocus as `rows[index - 1]?.id` and in `remember` as `elements[index - 1]?.dataset.row`.
- Quote: `const next = anchor < 0 ? elements[Math.min(lost.index, elements.length - 1)] : elements[anchor + 1] ?? elements[anchor];`
- Confidence: medium
