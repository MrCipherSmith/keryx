### [UX-001] Stale-snapshot row can stay "Loading…" forever after Refresh catalog
- **Severity:** minor (missing error/recovery state on a secondary view, and only when the snapshot id does not change)
- **Criterion:** Nielsen #1, #9
- **File:** apps/desktop/src/metaproject/useMetaprojectTree.ts, the stale-snapshot branch in read()'s catch
- **Evidence:** the branch returns with the folder or page still "loading". `ensure`, `more` and `retry` all skip a loading entry, and only a change of snapshot id resets the tree. Refresh catalog clears the banner even when it gets the same snapshot id back. The PR's view-test fixture keeps snapshot s1 through Refresh and never checks that src recovers.
- **Fix:** reset or re-read the stale entries when Refresh catalog runs, whether or not the id changed, and assert that recovery in the view test.

### What works (keep)
- Separate `status:` and `more:` ids, plus the anchor on the row before the focused one: focus lands on the first child, in the right folder, when two folders answer in one commit. A DOM test covers each case.
- Focus that has left the tree is never pulled back. Both the Show more and Loading variants are tested.
- A permit refusal is retried quietly with a short jittered wait. The row stays "Loading…" during the wait, and only a refusal that outlasts the retries shows the inline error.
- The stale banner is the only error surface, with no Retry that cannot succeed, which matches search Load more.
