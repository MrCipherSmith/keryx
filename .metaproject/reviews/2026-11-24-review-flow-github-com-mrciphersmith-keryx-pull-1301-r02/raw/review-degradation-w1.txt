## Findings (fix hunks reviewed as new code)

### [F-001] A stale-snapshot tree read now leaves its folder stuck in "Loading…" when Refresh catalog returns the same snapshot
- Severity: major
- Class: behaviour-delta
- Evidence kind: base-diff (plus consumer-trace)
- File: apps/desktop/src/metaproject/useMetaprojectTree.ts (read() catch)
- Problem: this answers r2-ui-ux-w2-UX-001 and r2-frontend-w2-F-001. On base f43a13c3f, a stale-snapshot read called onStale() and then marked the folder (or its next page) `failed` with a Retry. On head it returns right after onStale(), so the folder stays `status: "loading"`, or `more: { status: "loading" }` for a page. Only a change of the hook's `snapshot` prop clears that state (useMetaprojectTree.ts:95-99). Refresh catalog (MetaprojectView.tsx:881, setRevision) runs a non-quiet catalog read: setCatalog(result) and setSnapshotMismatch(false) (:414-416). When that catalog has the same snapshotId as the pinned one, the tree state is not reset and the banner goes away. Nothing then re-reads the folder:
  - ensure() returns because folders.has(parent) (:209);
  - retry() needs status "failed" (:224);
  - more() refuses while more.status is "loading" (:216);
  - the Loading row is aria-disabled and has no action (MetaprojectTree.tsx flatten :42-45);
  - the reveal effect stops at a loading folder (:124).
- Trigger: the snapshot id is a content digest (src/integrations/metaproject-explorer.ts:174). A tree read can land while the knowledge has moved A→B, for example during a wiki edit or a graph rebuild. If the state is back at A when the user clicks Refresh catalog, for example after the edit is reverted or the rebuild gives identical output, the catalog answers A again. The PR's own view test reaches this state: in "a tree answer for another snapshot, or a stale-snapshot refusal…" (MetaprojectView.dom.test.tsx:2139-2162), treeExplorer keeps state.snapshot at "s1" across Refresh catalog. After the click, src stays "Loading…". The test checks only that the banner disappeared and never looks at src again, so it cannot catch this (blind-test aspect of the same defect).
- Outcome: the expanded folder, a Show more row, or the whole root (when the root read was stale) shows "Loading…" indefinitely, with no banner, no Retry and no other control. In the session it recovers only when the knowledge changes again (a later catalog with a new snapshot) or when the explorer remounts (a project switch). On base the same trigger left a Retry that re-sends A, which the CLI now accepts.
- Fix: keep the banner as the only remedy, but make Refresh catalog re-read what the stale answer left loading even when the snapshot is unchanged. For example, record the parents (and pages) that got stale-snapshot in a per-scope set. On the next catalog load, whether or not the snapshotId changed, drop those folders (or reset their `more`) so the tree's `unread`/ensure path reads them again. This can be passed as a `refresh`/revision input to useMetaprojectTree that retires the stale-marked entries the way a snapshot change does. Extend the view test: after Refresh catalog with an unchanged "s1", src's children (or a fresh read of src) must appear and no "Loading…" row may remain under src.
- Refute attempt: read useMetaprojectTree.ts:95-99, :183-190, :208-231; MetaprojectTree.tsx:36-58, :114-116, :118-140; MetaprojectView.tsx:390-437, :757-758, :878-883. I found no other path that clears a loading folder. A quiet catalog read with the same snapshot only sets freshness (:410-412), and a non-quiet one does not change `snapshot`. Leaving and returning to the view keeps the tree state (it is held by the explorer). Deleting the folder instead (the other option the prior finding suggested) would loop: flatten would list it as unread and ensure() would re-send the retired snapshot. So the fix needs a refresh signal, not a delete. Not run (read-only, exec_budget 0).
- class_scope sites:
  - apps/desktop/src/metaproject/useMetaprojectTree.ts read() catch, first read (`cursor` undefined): folder left `status: "loading"`;
  - apps/desktop/src/metaproject/useMetaprojectTree.ts read() catch, next page (`cursor` set): `more: { status: "loading" }` left in place;
  - apps/desktop/src/metaproject/useMetaprojectTree.ts read() then-branch `page.snapshotId !== pinned` throw, which reaches the same catch;
  - apps/desktop/src/metaproject/MetaprojectView.tsx loadMoreSearch: not affected, because a later search re-runs.
- class_scope enumeration_method: every path into the catch's stale-snapshot branch in read() (one catch serves the folder reads, page reads and retry, since ensure(), more() and retry() all call read()), plus the one consumer that passes onStale, MetaprojectView.tsx:757-758 (the graph-listed importer; App.tsx only mounts MetaprojectView). Found with `keryx ctx rg "setSnapshotMismatch|useMetaprojectTree\(|snapshotId" MetaprojectView.tsx`.
- Confidence: medium. The code path is certain; how often the snapshot returns to the pinned digest in real use is the open part.

## Summary

Verified clean:
- **Permit retry.** isPermitRefusal matches the raw Tauri rejection string "unavailable: Too many Metaproject reads. Retry shortly." (metaproject.rs:199). requestMetaprojectV2 rethrows it unchanged because "unavailable" is not in METAPROJECT_ERROR_CODES (platform/metaproject.ts:292-296), so the startsWith check sees it. Other "unavailable" answers are not retried (test "a permit refusal that outlasts…"). A retired generation stops retrying (the current() checks around pause). A slot is held for at most about 0.75 s extra of back-off per refused read; this is bounded and happens only on refusal.
- **useMetaprojectTree signature.** The new optional `wait` defaults to sleep. Its only production consumer, MetaprojectView.tsx:758, passes none, so its behaviour is unchanged.
- **limit() catch.** It now reports unexpected throws with console.error instead of swallowing them, and the slot accounting is unchanged.
- **Focus anchor.** When the focused row leaves (`before`/anchor+1 with an index fallback), I traced: a Loading row replaced by children, a Loading row whose folder answered with a next page (now a separate `more:` id, so focus goes to the first child, which is the documented intent), Show more appending a page, two folders answering in one commit, an empty folder (focus goes to the next sibling, the same as base's index rule), and a new snapshot (`before` is gone, so it falls back to the index, the same as base). I found no regression. onFocus's `rows.findIndex` matches the DOM order, because every row is rendered with `data-row` from the same `rows`.
- **statusId/moreId split.** The more and page-error rows share moreId, and the first-read loading and error rows share statusId, so a Retry or Show more still updates the focused row in place.

Consumers: the graph lists App.tsx, MetaprojectView.tsx, MetaprojectTree.dom.test.tsx and MetaprojectView.dom.test.tsx (depth 2, `truncated` empty, so the cap dropped nothing). A cross-module search found none, which is not a finding.
