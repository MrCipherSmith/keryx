### [F-001] A stale-snapshot tree read now leaves its row loading, and Refresh catalog does not re-read it when the snapshot id comes back unchanged
- **Severity**: minor
- **File**: apps/desktop/src/metaproject/useMetaprojectTree.ts (read catch, stale-snapshot branch)
- **Rule**: canonical rubric (stale UI state with no recovery in an edge case the change admits); no code-style-patterns row covers it
- **Problem**: This fix answers r2-ui-ux-w2-UX-001 and r2-frontend-w2-F-001. After `onStale()` the catch now returns, so the folder stays `status: "loading"`, or for a page read `more: { status: "loading" }`. The only way out is a new snapshot: the hook resets folders only when `state.current.graph.snapshot !== snapshot`. Refresh catalog (`setRevision`) reloads the catalog. If the reloaded catalog has the same snapshotId as the one pinned, nothing changes. That happens when the content digest flips back, for example a wiki edit that is reverted, or a mid-rebuild state followed by the finished rebuild. In that case the banner clears, but the row keeps "Loading…" for good. `ensure()` returns early because the folder exists, so collapsing and re-expanding does nothing. `more()` returns early while `more.status === "loading"`. Retry is gone too. Before the fix, a Retry row was still offered in this case.
- **Why it matters**: In this edge the tree shows a permanent `role="status"` "Loading…" row (or a disabled Show more) with no control that can recover it. Recovery comes only with the next real snapshot change or a remount of the explorer. The common case is correct: the snapshot changes and the tree re-reads.
- **Fix**: Let Refresh catalog reset the tree even when the snapshot id is unchanged. For example, have the hook expose `reload()`, which bumps `generation` and applies the same `keep()` reset, and have MetaprojectView call it from the Refresh catalog handler. Another option is to pass the catalog revision into the hook's reset key. Add a view test: a tree read refused as stale-snapshot, then Refresh catalog returning the same snapshotId, then assert that the folder's children load.
