### Findings

### [F-001] Per-card session and Flow derivation runs on every App render; the new `work` memo can never hit
- **Severity**: minor
- **File**: apps/desktop/src/review/PrWorkRow.tsx (sites also in ReviewBoard.tsx, App.tsx, IssueWorkRow.tsx)
- **Hot path**: while the Review view is shown (`active={workView === "review"}`), every App render. App re-renders on every flushed batch of session updates (one per animation frame, or every 250 ms when hidden) whenever any held session is streaming a turn in the background, and on every `session/list` refresh.
- **Problem**: `PrWorkRow` derives per card, in render, `boundSessions(work.sessions, subject)` (filter + sort over every session, up to 5 pages of `session/list`) and `prFlows(card, work.flows, sessions)` (filter over every Flow with two `replace(/\/$/)` + `toLowerCase()` per Flow that has a `prUrl`, then a sort), plus a `MenuItem[]` built even when the menu is closed. That is O(cards x (sessions + flows)) per render: up to 150 list rows, or up to 30 per lane x 6 lanes. `ReviewBoard` wraps `work` in `useMemo`, but its deps `onCreateFlow` and `onOpenSubjectSession` arrive as inline arrows from App (`onCreateFlow={(card, subject) => void createPrFlow(card, subject)}`), and even their targets `openPrSession`/`createPrFlow` depend on `s` (a new object every `useAcpSession` render) and `flowLinks` (a new `{known, expect}` object every render). So `work` changes identity on every App render, `memo(ReviewResults)` re-renders, and every `PrWorkRow` redoes the derivation. The memo is complexity with no possible effect. `IssueWorkRow` has the same per-row shape (`issueSessions(sessions, issue)` per issue row per render), though there `sessions` is `state.sessions` and `sameSubject` short-circuits on kind/number, so its cost is small.
- **Why it matters**: reasoned count, not measured: 150 cards x ~200 Flows is ~30k regex replaces and lowercasings, plus 150 sort calls, per frame while a background turn streams and the board is visible. Probably a few milliseconds per frame on a large project, not an outage. Note that `memo(ReviewResults)` was already defeated before this PR (inline `onOpenSession`), so the re-render itself is not new; the per-card derivation is.
- **Fix**: derive once per `(sessions, flows)` change instead of per card per render: in `ReviewBoard` (or `ReviewResults`), build `Map<subjectKey, SessionInfo[]>` from `sessions` and `Map<normalisedPrUrl, FlowCard[]>` from `flows` in a `useMemo`, and pass the lookup into `PrWorkRow`. Make the callbacks stable so the `work` memo can hit: in App, pass `openPrSession`/`createPrFlow` through refs (as `subjectSessionsRef` already does for sessions) or wrap them so their identity does not depend on `s`/`flowLinks`. Build the menu `items` only when `menu` is open.

### [F-002] A new bound session's first turn now lists sessions twice
- **Severity**: info
- **File**: apps/desktop/src/session/useAcpSession.ts
- **Hot path**: once per newly bound session (its first turn end), not a hot path.
- **Problem**: after a turn, `applyPendingFlow(...).then(() => subjects.apply(sessionId)).finally(() => void refreshSessions())`. When a subject binding is pending, `subjects.apply` calls `onFlags`, which itself returns `refreshSessions()` (deliberately: the comment says the pending binding is dropped only after the stored list is read), and then `finally` runs `refreshSessions()` again: two `session/list` calls (each up to 5 RPC pages) back to back. The double call is redundant, but it happens once per binding, and the first refresh is a deliberate choice whose reason holds.
- **Fix** (optional): skip the trailing refresh when `subjects.apply` already refreshed, e.g. have `apply` resolve to whether it refreshed.

### Clean Areas
- N+1 / DB queries, indexes, pagination: none in this slice (client-side only; `session/list` paging unchanged at 5 pages).
- Memory leaks: `PendingSubjects` entries are removed on success or replacement; `usePendingFlowLinks` drops entries on link/clear; the focus effect in `ReviewBoard` keeps one ref; no new listeners, timers or subscriptions without cleanup. A pending subject for a session that keryx never stores stays in the map for the window's life; it is bounded by user clicks, so no finding.
- Bundle imports: `react-dom` `createPortal` is already a dependency; no large-library imports added.
- Synchronous blocking: `readReviewGrouping`/`saveReviewGrouping` are single `localStorage` calls on snapshot change or user click, not per render.
- Expensive render work: `newestFirst` is memoized on `cards`; `drawnLanes`, `issueGroups`, `withPendingSubjects` (memoized on `state.sessions`/`pendingSubjects`) are cheap.
- Redundant API calls: `openSubjectSession` reads sessions through a ref, with no extra fetch; `bindSubject` makes one flags write per bind (plus one retry after the turn).
