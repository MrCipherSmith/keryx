## Performance Review (round 2, slices slice-01, slice-02, slice-03)

F-006 is closed: the rewritten `attachBadges` statement parses each run once and the evidence supports the claim that it returns to base cost. No new performance defect was found. Only the F-014 and F-012 dispositions below stay `open`.

### F-006 judgement (src/review/desk-run-store.ts, attachBadges)
- Parse count. `scoped AS MATERIALIZED` reads `details` once per run of the requested PRs, through the `review_history (repo, viewer, pr)` index. `flagged` and `picked` work only on the extracted scalar columns, so the window functions never touch the report blobs. The final SELECT re-reads `details` only for kept rows through `r.rowid=p.seq`. Those are active runs, runs requested for the card's range, and at most one outdated candidate per card.
- Plan. The `after` plan in outdated-lookup-measurement.md shows one `SEARCH r USING INDEX review_history`, one `MATERIALIZE scoped`, and a `SEARCH r USING INTEGER PRIMARY KEY (rowid=?)` for the kept rows. It no longer has the per-card correlated subquery with its own `USE TEMP B-TREE`. The temp b-trees that remain sort narrow rows, not report blobs.
- Timing. The back-to-back run 2 shows about 395-402 ms (after) against 401-411 ms (base) and 741-771 ms (head), with identical badge digests for head and after. That supports "back to base cost". Run 1 (about 450-474 ms) was noisier and ran alone.
- Semantics against `localBadge` (board-badges.ts). `kept` equals the old WHERE (active, requested range, or reviewed range). `supersedes` mirrors `latest` (active or requested range) plus `ready` (finished with reviewed range = card range). So the outdated row is dropped exactly when `localBadge` would discard it (`stale = latest || ready ? undefined : ...`). `finished` requires both reviewed SHAs, which matches the row mapping `result: row.base && row.head ? ... : null`. NULL card SHAs coalesce to "not requested", which matches the old `IS` handling.
- Not verified: I did not re-run the measurement or the SQL. The data is one machine, a warm cache and one synthetic shape (30 runs per PR, each on its own head). A PR with hundreds of runs makes `scoped` larger, but the cost still scales linearly in the same way as base.

- Memory and subscriptions: no new listeners, timers or caches.
