### The rewritten `attachBadges` SQL (the check asked for in the dispatch)
- **Parameter binding.** Every value that comes from outside reaches SQLite as a bound parameter. `?1` is the card batch as a JSON string, read by `json_each`. `?2` is `snapshot.repositoryId` and `?3` is `snapshot.viewer` (desk-run-store.ts:447). The query text interpolates only two things: `visible("r")`, which is only ever called with the literal alias `"r"`, and `pending`, whose table names come from `sqlite_schema` filtered by the literal list `IN ('review_questions','reviewer_questions')` (lines 395-398, unchanged). Values from GitHub (card number, baseSha, headSha) never reach the SQL text, so there is no injection path.
- **Repository, viewer and pull-request scoping.**
  - `scoped` is the only CTE that reads `runs`, and it filters on `r.repo=?2 AND r.viewer=?3 AND r.pr=w.n AND visible(r)` (line 413).
  - `flagged` and `picked` read only from `scoped`.
  - The final `FROM picked p JOIN runs r ON r.rowid=p.seq` (line 442) re-reads `runs` only through rowids that `scoped` produced, so it cannot bring in a run from another repository, viewer or pull request.
  - The window functions partition by `card` (the `json_each` key), so one card's runs never suppress or pick another card's outdated row. The new test "in one batch, an active run or a reviewed range suppresses the outdated badge only for its own card" covers this.
  - Viewer matching is still exact equality, as before.
- **What crosses the SQLite boundary.**
  - The materialized `scoped` CTE holds only rowid, state, createdAt, the requested and reviewed SHAs, and the card SHAs. It holds no report or session text.
  - The final projection has the same columns as at round-1 head and base: id, pr, awaitingAnswer, state, source, coverage, the reviewed and requested SHAs, and progress counters.
  - Rows from other revisions are still limited: active runs, plus at most one newest finished run per card. That run must have both reviewed SHAs and must not be superseded.
  - No reports or session histories are returned. The boundary is no wider than before.
- **Read-only.** The statement only reads. It changes no schema, index or write path.

### Other areas of the delta checked
- **React / XSS.** `reviewNote` text (`outdated.headSha.slice(0, 7)`), the `.review-note` spans and `filter-count` are rendered as React text children. There is no `dangerouslySetInnerHTML`, `eval` or other raw HTML.
- **`inBoardOverlay`.** It uses a constant selector (`.project-review-rules, .review-watcher`; both classes exist in ProjectReviewRules.tsx:63 and ReviewWatcher.tsx:103). It only reads the DOM and decides where focus goes back to. It handles no data.
- **Account change and access loss.**
  - `accessLost` still clears `carriedAttention`, the snapshot cache, `pendingBadges` and the private view.
  - On an identity change, the load callback replaces the carried set (`replaceAttention` is true when `identity.current !== nextIdentity`).
  - The derived `attentionPrs` is only PR numbers and is used only for the tab indicator.
  - Nothing from a previous account survives in the shown set.
- **localStorage and sessionStorage.** The delta adds no new storage.
- **Docs, flow and journal files.** They hold no secrets or tokens. They name the repository owner, which is already public in the PR. Nothing in them misstates the security-relevant code.
