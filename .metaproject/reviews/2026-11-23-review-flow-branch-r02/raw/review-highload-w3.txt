### Quiet re-read (answer to round-1 F-004), checked as new code

- Return while the first catalog read is in flight: `!loaded.current` returns early, nothing is queued, the result applies on arrival.
- Return, then hide and return again before the quiet read ends: each return sets `quietRead` and bumps `revision`; the effect cleanup does `project.current++`, so the first read is dropped and the second runs quiet. The flag is read and cleared at the start of the run, so it cannot leak to a later read in this path.
- Return during a rebuild: the quiet read runs, the rebuild keeps running (`mounted` ref, not tied to `visible`), and its end bumps `revision` with `quietRead` already false, so it takes the full path, calls `setCatalog` and `setFreshness(null)`. Pinned by 'a return during a rebuild ...' (reads 2 then 3, control enabled again).
- Rebuild ends while a quiet read is in flight: the bump cleans up the quiet read and starts a full one; no stale write.
- Quiet read with an unchanged snapshotId updates only `freshness`; `graphState` uses it only while `freshness.snapshotId === catalog.snapshotId`, and a changed snapshot goes through the full path, which also clears freshness. snapshotId is a hash over nodes, edges, page digests and layerStats (metaproject-explorer.ts:174), so catalog fields other than the graph freshness cannot change under an unchanged id; moving the freshness-only fields out of `catalog` is therefore sound.
- A failed quiet read shows the existing error banner with Retry and keeps the catalog; Retry is a full read. Acceptable.
- Remaining read of `catalog.graph` at line 496 (`if (catalog.graph === "missing" && protocol !== 2) return;`) is not switched to `graphState`; a graph going missing/ready changes nodes and edges and so the snapshotId, which takes the full path, so I could not construct a state where it matters.
