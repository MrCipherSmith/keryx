## F-001 disposition: closed

Fix read at head: `placeFiltersPopover(rect, needed)` (MetaprojectView.tsx 184-194), `FiltersPopover` re-places on `resize`. `.menu` is `overflow-y: auto` and `* { box-sizing: border-box }` (styles.css 3 and 143), so an inline max-height bounds the outer box and the overflow scrolls inside.

Arithmetic check against the journal's measurements (T17 entry, 720x480):
- Details expanded, button 331 to 355: below = 480 - 8 - 359 = 113; above = 331 - 4 - 8 = 319; needed 229 > 113 and above > below, so it goes above: bottom = 480 - 331 + 4 = 153 (journal: inline bottom 153), max-height min(420, 319) = 319, box = 229 high, 98 to 327 (journal: 98 to 327). Matches. WKWebView 135 to 327 is the same bottom with a shorter content (192), consistent.
- One-line banner: button bottom 225: below = 480 - 8 - 229 = 243 (journal: top 229, max-height 243), needed 229 fits, so it goes below. Matches.
- The round-1 clip (bottom 531, 51 px past the window) cannot recur at either state: the box edge is bounded by the window height minus 8 by construction.

Cases the measurements do not cover:
1. Button near the top, little room on both sides: derived from code. If above is not larger than below, the popover goes below with max-height min(420, below), scrolling inside; if above is larger it goes above with max-height above. Either way the box is inside the window and scrolls. E.g. window 300, button 140 to 164: below 124, above 128, goes above, 128 px, bottom edge 4 px above the button. Button at the very top (top 10): above is -2, below 434, goes below, no flip. Degenerate only when both sides are negative (a button outside the window): the upward branch could then emit a negative max-height, which the browser ignores, leaving the `.menu` cap. Not reachable in a 720x480 window; not filed.
2. Window shorter than the popover (content 229 against, say, 300 px of window): derived from code, as case 1; the cap is the room on the chosen side, and the popover scrolls inside (the unit test 'stays 8 px inside a short window, scrolls inside and is placed again on resize' pins top + max-height = innerHeight - 8, at 480 and at 400 after a resize, with stubbed layout). The inline max-height replaces `.menu`'s `min(420px, 100vh - 80px)` rather than combining with it; the new cap is the tighter bound only when the room is smaller, otherwise up to 420 where the CSS gave 400 at 480 px of height, still inside the window. Not measured in an engine with a window shorter than 480 (below the supported minimum).
3. Content height changing while open: derived from code, see LY-001. Bounded by the cap (never leaves the window), not re-placed; the flip decision is not revisited. The symbol-layer note is static per catalog and chip wrapping is fixed by the 320 px width, so neither changes while open; the Reset filters row does.
4. Page scroll under the button: derived from code, see LY-002; no scroll listener exists. The popover keeps a window-valid fixed position, so no clipping.

Also derived: `scrollHeight` is measured in the layout effect on first render with the popover parked at -9999; scrollHeight is the full content height independent of max-height or transforms, and the `.menu` has no border, so `needed` is exact.
