## What the change does to rendered geometry

The layout surface is `apps/desktop/src/review/ReviewPublishDialog.tsx` only. The PR changes no CSS.

1. The new status paragraph `p.review-detail-muted.review-publish-head-moved` is a direct grid child of `.review-publish`. It therefore picks up `.review-publish > p { margin: 0 }` and the grid's `gap: var(--sp-3)`, the same as the existing blockedReason and savedAt paragraphs. Its only inline `<code>` elements are 7-character short SHAs, with the full SHA in `title`, so it has no unbreakable run. No `.md` code chrome applies, because the paragraph is not inside `.md`. No layout risk was found.
2. The primary button now holds `Publish as is for <code>bbbbbbb</code>`. `.btn` is `inline-flex` with `gap: 6px` and `white-space: nowrap`. The text run and the `<code>` become two flex items, so the trailing space in "for " collapses and the 6px gap separates them instead. This is visually equivalent and not a defect. The fixed `height: 28px` and `line-height: 1` hold, because `code` changes only the font family (styles.css `code, pre, kbd { font-family: var(--mono) }`) and not the size.
3. The footer is `.dialog-foot` (flex, wrap, justify-end, padding 24px inline, from components.css) wrapping `.review-publish-footer` (flex, wrap, gap var(--sp-2), margin-inline-start auto, from ReviewDetail.css). The buttons are `flex: none; white-space: nowrap`, so the footer wraps whole buttons and never shrinks or clips them.
   - Static estimate at the Desktop `minWidth: 720` (tauri.conf.json), with overlay and dialog-foot padding of 24px each side: about 624px of footer content width.
   - Today's four buttons (Close, Skip publication, Save locally, Publish as is for xxxxxxx) come to about 535px and fit on one row.
   - With the optional "Update review to xxxxxxx" button, which no caller passes yet, the five buttons come to about 730px and wrap to two rows. Nothing clips. Each single button (≤ about 205px) is narrower than the footer at any supported width, so nothing scrolls sideways.
4. RTL: the PR adds no physical property. The existing `margin-inline-start: auto` is logical.
5. Locale: Desktop strings are hard-coded English with no translation catalog, so Rule 3 does not apply.

## Findings

### [LY-001] With the optional Update button, the footer may wrap and split the two head-moved actions across rows (unmeasured)

- **Severity**: info (unverified, no measurement)
- **File**: apps/desktop/src/review/ReviewPublishDialog.tsx
- **Problem**: When `onUpdateReview` is passed, a fifth nowrap button is added as the first footer item. A static estimate puts the five buttons at about 730px against about 624px of footer width at the 720px minimum window. The footer would then wrap, leaving "Update review to …" (and maybe Close) on one row and "Publish as is for …" on another.
- **Measurement**: none. The figures are estimated from tokens: `--fs-md` 13px, `.btn` padding `var(--sp-3)`, `--sp-5` 24px, `minWidth` 720. Rendering the dialog with `onUpdateReview` set in the app or a Playwright probe at 720px and 1180px, and reading the footer's `getBoundingClientRect` per button, would settle it.
- **Why it matters**: Nothing clips, and there is no user impact today because no caller passes `onUpdateReview` until item 3. The PR already calls the placement provisional, since the spec makes Update the primary action. Revisit the row order when item 3 wires it.
- **Fix**: None needed now. When item 3 lands, measure the footer at 720px. If the two head-moved actions must stay together, group them in their own nowrap flex container, or order the primary last as the spec says.
