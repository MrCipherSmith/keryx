### Findings

### [F-001] Automatic publication on a moved head fetches the full PR discussion, then always refuses
- **Severity**: minor
- **File**: src/review/desk-publication.ts (the `discussion` condition in `prepare`)
- **Hot path**: `publishCompletedDeskReview` runs once per completed auto-publish run (`desk-run-service.ts:440-443`, refusal swallowed by `.catch`). This needs a project overlay of kind `slots` with `rereadDiscussion`. It is not on an interactive path.
- **Problem**: The guard changed from `current` to `(current || headMoved)` and still includes `request.kind === "automatic"`. When the head has moved, an automatic request now calls `publicationDiscussion`: three `gh api --paginate --slurp` reads (reviews, review comments, issue comments). On base, `!current` skipped these reads. The same `prepare` then always sets `blockedReason` to "This review needs a publication decision in Desktop." because `request.kind === "automatic" && (headMoved || ...)`. The fetched hash is never used, and an automatic request never writes the preview cache (lines 205-210 are preview-only).
- **Why it matters**: Each such run spends three paginated GitHub reads that cannot affect the outcome. The page count grows with the PR's discussion size, and the reads count against the viewer's rate limit. The cost is small because it happens once per run.
- **Fix**: Leave `automatic` out of the discussion read when `headMoved` is set. For example, use `(current || (headMoved && request.kind !== "automatic"))`. Alternatively, return the automatic refusal for a moved head before rendering.

### Clean Areas
- Head-moved preview and submit, GitHub calls. On submit, `verifyDeskSubject` is called the same number of times as on the current-head path. Only the expected revision changes (`expected`), not the number of calls. Inline placement is skipped (`settings.inline` is forced false, and the guard still requires `current`), so no diff read is made. The test confirms this: `FIXTURE_DIFF_READS` is absent. The discussion reread on the dialog's preview and submit costs the same as on the current-head path. It is intended (the stale-discussion guard), and the preview cache (15 s TTL, kept while base and head are unchanged) serves repeated previews. Submit's two reads (in `prepare`, then with `auth`) predate this PR and are not made worse.
- Preview cache: the key is the run revision, and the cached subject is reused only while base and head match. The moved head does not add entries or grow the cache. The file is a single file with a size cap.
- Digest: appending `headMoved.currentHead` costs one string inside an existing hash.
- Dialog re-renders (`ReviewPublishDialog.tsx`): there is no new state, effect or context. `headMoved` is derived from `draft`. The new `disabled` props and the `shortSha` slices are trivial per render. `onUpdateReview` is passed through without being wrapped. The dialog is not a high-frequency surface.
- `head-move.ts`, `update-round.ts`: `selectPriorAttempt` is a single early-exit loop over the attempt list, and `parseOnHeadMove` searches a three-element array. Neither runs on a hot path.
- N+1, indexes, pagination, leaks, bundle imports, sync I/O: nothing new in the diff. Test-only `cpSync` and `spawnSync` are fixture setup.
