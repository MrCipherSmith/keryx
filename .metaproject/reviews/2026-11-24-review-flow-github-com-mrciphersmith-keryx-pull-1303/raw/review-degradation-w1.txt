### [F-001] Automatic publication after a head move now reads the PR discussion before refusing

- **Severity**: minor
- **Class**: performance
- **Evidence kind**: base-diff
- **File**: src/review/desk-publication.ts
- **Problem**: On base, `discussion` was computed only when `current` was true, so automatic publication with a moved head made no discussion reads. On head the guard is `(current || headMoved)`, and `request.kind === "automatic"` is still included. Automatic publication with a moved head therefore runs `publicationDiscussion`, which makes three paginated `gh api --paginate --slurp` reads (reviews, review comments, issue comments). Then `blockedReason` refuses it with "needs a publication decision in Desktop", and the hash is never used.
- **Why it matters**: The cost is extra GitHub API calls and latency on a path that is always refused. It applies to projects whose overlay is `slots` with `rereadDiscussion`. No result is wrong, lost or blocked.
- **Fix**: Exclude the automatic kind from the head-moved case, e.g. `(current || (headMoved && request.kind !== "automatic"))`. Or check the automatic + headMoved refusal before computing `discussion`.

### [F-002] The new prior-attempt rule sits beside the live one and treats a missing findingsKnown more strictly than the other readers

- **Severity**: info
- **Class**: debt
- **Evidence kind**: consumer-trace
- **File**: src/review/update-round.ts
- **Problem**: `selectPriorAttempt` is a second previous-attempt rule. The live one is in `desk-run-service.ts`: completed, complete, same options key. Nothing calls the new rule yet, and the PR says so: it is wired with item 3. It skips any result whose `findingsKnown !== true`. The other readers of the field treat `undefined` as known: `pr-context.ts:184` and `ReviewOutcome.tsx:9` use `findingsKnown !== false`. `desk-run-legacy.ts:134` counts findings when the field is undefined and some count is > 0. So a record without the field, such as an older run, is "known" everywhere else but rejected here.
- **Why it matters**: Nothing changes today because the rule is not wired. When stage 2 wires it, older completed attempts that lack the field would not be chosen as the previous round, and the rule would differ from the one it replaces.
- **Fix**: When item 3 wires it, align the rule with the sibling readers (`findingsKnown !== false`, or the legacy normalisation), or state why it should be stricter. At that point, remove or delegate the old selection in `desk-run-service.ts`.
