### The two choices made without the operator

1. A quiet re-read that finds a changed snapshot replaces the catalog and does not cancel a wiki-link lookup in flight.
   - What the user sees when the lookup's answer comes from the new snapshot: the catalog is already the new one (its `setSnapshotMismatch(false)` ran first), then the lookup's id differs from the one captured at click time, so `setSnapshotMismatch(true)` shows "Project knowledge changed while loading." with Refresh catalog, and the link does not open. Refresh runs a loud read of the same snapshot and clears the banner; clicking the link again, which captures the new id, opens it. The banner is true in the sense that knowledge changed, a little redundant (the catalog is current), and it costs one click. If the lookup's answer comes from the old snapshot, it opens its target from that snapshot; the node may be gone from the new catalog, in which case the detail read reports its normal error for that page. If the lookup answers before the quiet read does, the catalog replace clears the banner by itself.
   - Acceptance criteria: AC16 (one lookup read, opens the target, a message for an unresolved path) is met for every case except that overlap, where the link does not open on the first click and the explorer shows the existing mismatch banner; no other criterion is touched. No state is corrupted: selection, route and caches stay consistent. A narrow window (a snapshot change between a click and its answer, across a leave and a return); a defensible default, not a defect.
2. A return while a catalog read is in flight starts no quiet read.
   - What the user sees: the first load, a Retry or the reload after a rebuild finishes and shows its own result or its own failure; the failed-first-read case shows its error and Retry unchanged, with no read started on return (pinned by the new test). The only thing missed is a change of the project that lands after the in-flight read was issued and before the user returns; the next return, Refresh or Rebuild reads it (the same bound the explorer had on base, where nothing was read on return).
   - Acceptance criteria and state: AC14 (a rebuild never leaves its control stuck, and the catalog is read again) and AC15 (a failed negotiation is recoverable) are unaffected: `catalogPending` is reset only in the `finally` of the read that still owns the generation, so it cannot stay true after a read settles, and a superseding loud read sets it again. AC10 (state survives leaving the view) holds. A read that never settles keeps `catalogPending` true and blocks quiet reads, which is the same state the Loading banner already shows.
