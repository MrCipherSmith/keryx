### Findings

### [PERF-W3-1] Every registration deletes and re-copies the whole session package, `layers/` included, into the Desktop store
- **Severity**: minor
- **File**: src/review/session-attempt.ts:119
- **Hot path**: once per `keryx review complete`, once per `keryx review publish`, and once per `review_publish` card build (buildCard calls `attemptOf` → register); a round that completes, shows a card and publishes copies the package 3 times. Not a loop.
- **Problem**: `register` runs `rm(target, { recursive: true, force: true })` then `cp(own, target, { recursive: true, ... })` with a filter that drops only `desk-attempt.json`, `publication.lock` and `publication-receipt.json`. The copy therefore carries `layers/graph` (the PR-head graph) and `payloads/`, which are not what Desktop's publish reads (manifest, report.md, findings, verdict/premise/readiness inputs). Measured: layers is 52.8 of 55–58 MB in the largest packages here.
- **Why it matters**: tens of MB of disk I/O per registration (sub-second on SSD, but repeated 2–3 times per round on an interactive path), and a second persistent copy of every PR round in the keryx data dir (`desktop-review/attempts/<id>/package`), in addition to the copy under `.metaproject/reviews`. Whether a Desktop delete decision reclaims that directory was not verified.
- **Fix**: skip the copy when nothing changed (compare a cheap fingerprint such as manifest + report.md + findings.json mtimes/hash recorded in `desk-attempt.json`), and exclude bulk directories Desktop publication never reads (`layers/`, `payloads/`, `slices/`) from the filter; or copy only the files `desk-publication.ts` `prepare` reads.

### [PERF-W3-2] info: `publishReview` reads the PR head before the readiness checklist, which reads it again
- **Severity**: info
- **File**: src/review/publish.ts:195
- **Note**: `readPullRequest` (195) and the readiness head gate (`computeReadiness` at 202 → readiness.ts:367) each call `prLookup` for the same ref within the same call; the test "a push while the operator reads" pins three reads (`at(REVIEWED, REVIEWED, NEWER)`). One extra `gh` round trip per publish. The command-level duplication this belongs to is reported as review-performance-w2-1; this entry only records the in-function site so a fix that memoizes `prLookup` covers it.
