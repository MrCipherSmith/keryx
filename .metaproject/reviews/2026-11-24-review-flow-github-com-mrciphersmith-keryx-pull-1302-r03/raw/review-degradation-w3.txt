## Findings

### F1 (minor, default-change, consumer-trace) `keryx review publish` now refuses a merged or closed PR, while the skill and the report template still send a post-merge review there

New `refuseClosed` (publish.ts:62-65, called at :196 and :244) throws for state MERGED or CLOSED. Base `publishReview` had no such refusal; it posted through `gh pr review --comment` (github.ts:144), which GitHub accepts on a merged PR. The unchanged consumers still direct that publish: `SKILL.md:908` (both copies) "`--event COMMENT` on a merged or closed PR"; `templates/review-report.md:23` (both copies) "PR already merged or closed | a plain PR comment"; `complete-head-gate.ts:28-30` keeps such a round closable "because a round on a merged PR is still worth closing", and Preflight 4 calls it "a post-merge audit".
Refute: the PR body and divergence-map.md row 4 name "refuse a closed PR" as intended, so the code change itself is deliberate; this is filed because its consumers (the skill text and the template the agent follows) were not updated, so a post-merge audit round now ends in a refused publish with no documented path. Severity kept at minor because the change is announced.

### F2 (minor, behaviour-delta, base-diff) The session publish transport accepts only `https://github.com/...` refs; the base posted whatever `gh pr review` accepts

Base: `githubPostReview(url, ...)` ran `gh pr review <ref> --comment|--approve|--request-changes --body-file -` (github.ts:144), so a `pr`-kind package whose `target.ref` is a PR number, a branch, `owner/repo#N` or a GitHub Enterprise URL was publishable. Head: `githubPostPullReview` (session-publish-github.ts:30) returns `not a GitHub pull request URL` unless the ref matches `^https://github\.com/.../pull/N` (line 8), and posts with `--hostname github.com` (line 35). `isPrBound` (complete-head-gate.ts:18) treats every `kind === "pr"` package as publishable regardless of ref shape, and `samePrRef` (managed.ts:232-237) exists because refs come in more than one form.
Refute attempted: did not find a normaliser that forces `--target pr` refs to github.com URLs at `review start`; not proven either way, hence medium confidence.

### F3 (minor, performance, consumer-trace + measurement) Every registration deletes and re-copies the whole package, `layers/` included, into the user data directory

`register` (session-attempt.ts:116-122) runs `rm(target, recursive)` then `cp(own, target, recursive)` on every call. It is called by default on every terminal `keryx review complete` of a PR package (review.ts:5171-5178), every terminal `keryx review publish` (review.ts:5073-5074) and every publish-card build (operator-confirm-review.ts:191-192). PR packages here are 55-57 MB, 52 MB of it `layers/` (graph data Desktop's publication never reads), so each complete/publish copies ~55 MB into `<keryxDataDir>/desktop-review/attempts/<id>/package`, one copy per round, kept until Desktop deletes the attempt. In addition, `registerSessionPackage` creates the Desktop store (`new DeskRunStore()` at line 71 runs `ensureKeryxConfigDir` + `CREATE TABLE`, desk-run-store.ts:107-110) before `resolveKey` can fail, so a project with no GitHub binding gets a store and a warning on every complete. Base `complete`/`publish` wrote nothing outside the package.
Refute: read the cp filter (session-attempt.ts:121-122): it skips only `desk-attempt.json`, `publication.lock`, `publication-receipt.json`.

### F4 (minor, behaviour-delta, base-diff) A failed head re-read after the operator's yes now refuses the publish as "stale"

publish.ts:241-249: after `confirm`, when a tracker is configured, `readPullRequest` runs again; it maps any lookup error or `exists: false` to `undefined` (publish.ts:54-59), and `after === null` with a known `before` throws `stale: The pull request head changed while the review was being confirmed (… → unknown)`. A transient `gh` failure on that third read therefore refuses a publish the operator already approved, and reports it as a head change. Base posted after the yes with no re-read.
Refute: the first read uses the same mapping but only skips the check (`before === null`); only the post-confirm read fails closed.

### F5 (minor, behaviour-delta, consumer-trace) A receipt written before registration is not carried into the Attempt, so Desktop can publish the same package a second time

When registration fails (warning, publish continues), `publishReview` keeps the receipt in the package (`receiptDir = packageDir`, publish.ts:222) and marks the body with `sessionPublicationId(reviewId, round)`. A later successful registration (the next `complete`, `publish` or card) copies the package with `publication-receipt.json` filtered out (session-attempt.ts:121-122) into an Attempt directory that has no receipt. Desktop reads only the Attempt directory's receipt (desk-run-store.ts publication(), desk-publication.ts prepare) and looks for its own marker (the Attempt id), so it shows the attempt as `pending` and allows a submit: a second review on the PR. `keryx review publish` itself is safe (it reads both directories, publish.ts:229-230). Base could not publish a session package from Desktop at all, so this duplicate path is new. The PR body notes the unregistered fallback but says "Desktop cannot see such a package anyway", which stops holding once the package is registered later.

### F6 (info, debt) Re-registering a decided session Attempt still replaces its package copy

`recordSession` (desk-run-store.ts:404-414) leaves a row whose `decision` is set untouched, but `register` has already `rm`+`cp`'d that attempt's `package/` (session-attempt.ts:116-122). An archived or completed-by-operator session attempt then holds a package that no longer matches its stored report and counts.
