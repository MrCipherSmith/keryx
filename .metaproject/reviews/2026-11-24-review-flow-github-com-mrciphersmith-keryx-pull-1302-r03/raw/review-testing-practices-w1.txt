## Findings

### TP-W1-1 (minor) An `advance` refusal's mapping to `start` is unpinned

- File: apps/desktop/src/review/useReviewRuns.ts:68
- Problem: the gate this change added, "an update round is a start of the next round: its refusal shows where a
  start's does", survives deletion with the Desktop suite green (TP1-M1, 49/49). The mapping matters because
  `staleRange` is `actionError?.kind === "start" && /^stale:/` (useReviewRuns.ts:112); it drives `revisionChanged`
  (ReviewWorkspace.tsx:121, ReviewDetail.tsx:186) and hides the raw error banner (ReviewDetail.tsx:302). The only
  failing-advance fixture ("a failed Update review start shows its error...", ReviewPanel.dom.test.tsx:745) throws
  "The selected Keryx CLI refused the start." with no `stale:` prefix, so it cannot separate `advance` from `start`.
  `keryx review advance` answers exactly with `stale:` in two of its refusals (src/review/review-advance.ts:41, :76:
  "A later round of this Review already exists", "The pull request revision has changed").
- Why it matters: the next edit to the error kind (or to `staleRange`) can turn a stale update round into a bare
  error banner instead of the "revision changed / refresh the board" path, with no test going red.
- Fix: add a fixture whose `advance` throws `stale: The pull request revision has changed. Refresh the board...` and
  assert the panel shows the revision-changed state (the Refresh board offer) and not the raw banner text.
