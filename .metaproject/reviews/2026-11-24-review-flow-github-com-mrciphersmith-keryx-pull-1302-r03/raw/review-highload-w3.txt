### CLI / Multi-Session

#### [review-highload-w3-1] A receipt kept beside the package is invisible to Desktop once the package is registered — Desktop can publish it a second time
- Severity: major
- File: src/review/session-attempt.ts:121
- Pattern: Idempotency G1 — dedup state not shared by both writers
- Failure mode: `keryx review publish` writes the receipt in the package directory whenever `publication` is undefined (registration skipped or failed: session-attempt.ts:156-159 turns a failure into a warning; publish.ts receiptDir = packageDir) — also every package published before flow 521. Its marker is then `sessionPublicationId(...)` (or none pre-521), not the attempt id. A later `keryx review complete` or `publish` registers the package: the copy into `<attempt>/package` explicitly filters out `publication-receipt.json` (session-attempt.ts:121-122), and Desktop reads the receipt only from the attempt directory (desk-publication.ts:145; board status desk-run-store.ts:424). Desktop therefore shows the attempt as unpublished, its marker search (`findPreviousPublication` with the attempt-id marker) cannot match the earlier post, and a Desktop submit posts a second review of the same round. Only the session path reads both places (publish.ts:229); the comment there documents the case for one path only.
- Fix: at registration, under `<attempt>/publication.lock`, carry an existing package-side receipt into the attempt directory (keep its url / `{}` state) instead of filtering it out; or make Desktop's receipt read also consult the registered package's original directory (recorded in the attempt row). Also have Desktop's lost-response search look for the session marker `sessionPublicationId(reviewId, round)`.
- class_scope: sites ["src/review/session-attempt.ts:121", "src/review/desk-publication.ts:145", "src/review/desk-run-store.ts:424", "src/review/publish.ts:229"]; enumeration_method: `keryx ctx rg "PUBLICATION_RECEIPT|receipt" src/review/desk-publication.ts src/review/desk-run-store.ts` plus `readPublicationReceipt` call sites — 3 receipt readers, only publish.ts:229 reads the package directory; one writer of the copy (session-attempt.ts:119-122).

#### [review-highload-w3-2] The session publication lock directory depends on per-process registration success, so two publishers of one package can hold different locks
- Severity: major
- File: src/review/publish.ts:227
- Pattern: Concurrency A4 — check-then-act guarded by a lock whose key is not stable
- Failure mode: `publishReview` locks `<receiptDir>/publication.lock` where receiptDir is the attempt directory when `sessionPublication` returned a record, else the package directory. Two concurrent publishers of the same package (two sessions, or the CLI and the `review_publish` card) where one's registration succeeded and the other's failed (resolveKey's GitHub read failed, SQLite busy past 8 s) — or the card's execution path (operator-confirm-review.ts:259, no registration) reading desk-attempt.json before the other process's registration wrote it (session-attempt.ts:125, written after the DB upsert) — take different lock directories. Process A reads receipts in attempt dir + package dir, process B reads only the package dir; neither sees the other's `{}` before both pass the check, and they use different markers (attempt id vs sessionPublicationId), so the lost-response search cannot reconcile either. Both POST: a duplicate review on the pull request.
- Fix: make the lock key independent of registration: always take `<packageDir>/publication.lock` first (the package is the stable identity), and additionally the attempt lock when registered, in that fixed order; under the locks, re-read desk-attempt.json and both receipts. Alternatively refuse to publish when registration fails but a desk-attempt.json or attempt row may exist.
- class_scope: sites ["src/review/publish.ts:227", "src/review/session-attempt.ts:156", "src/review/session-attempt.ts:159", "src/commands/operator-confirm-review.ts:259", "src/commands/review.ts:5074"]; enumeration_method: `keryx ctx rg "sessionPublication\(" src --all` — 4 call sites (two register, one reads only, one is complete's registration), and the single lock acquisition in publish.ts.

#### [review-highload-w3-3] Re-registration replaces `<attempt>/package` with rm + cp outside any lock while Desktop renders it under the publication lock
- Severity: minor
- File: src/review/session-attempt.ts:119
- Pattern: Part 0 — state-directory rewrite not serialised with its readers
- Failure mode: `register` does `rm(target)` then `cp(own, target)` with no lock; Desktop's publication `render()` reads report/findings/manifest from `<attempt>/package` under `publication.lock`. A `keryx review complete` or `publish` (both re-register) running while Desktop previews/submits makes Desktop read a missing or half-copied package: a failed preview/submit or a spurious "stale" digest refusal. Two concurrent registrations of the same package interleave their rm/cp on one target (one's rm deletes the other's partial copy, its cp then fails with ENOENT and degrades to a warning). Not a data-loss path: submit's digest check refuses a body that changed.
- Fix: copy into a sibling temp directory and rename it over `package` (atomic swap), and take `<attempt>/publication.lock` around the swap.
- class_scope: sites ["src/review/session-attempt.ts:119", "src/review/session-attempt.ts:120"]; enumeration_method: read of register(); single writer of `<attempt>/package` for session attempts.

#### [review-highload-w3-4] `keryx review publish` holds the shared publication lock across the operator's terminal prompt; Desktop's lock waits time out after 5 s
- Severity: minor
- File: src/review/publish.ts:240
- Pattern: Part D — lock held across a human interaction
- Failure mode: `options.confirm` (runPublish's `promptYes`, src/commands/review.ts:5069) runs inside `withFileLock(<attempt>/publication.lock)`; the heartbeat keeps the lock fresh for as long as the operator leaves the y/N prompt open. Every Desktop save, skip or submit of that attempt (desk-publication.ts:394, default `timeoutMs` 5000 in src/lib/fs.ts:102) fails meanwhile with a raw "Timed out waiting for lock: <path>" error, which carries none of the `stale:`/`configuration:` prefixes Desktop maps. Before this change the session path took no lock. Correctness is kept (no duplicate); availability of Desktop's publish dialog is not.
- Fix: take the lock only for the receipt check and again for check + begin receipt + POST after the operator's yes (re-checking the receipt under the second acquisition), so the prompt runs unlocked; or map a lock timeout in Desktop to "another publish of this review is in progress".
