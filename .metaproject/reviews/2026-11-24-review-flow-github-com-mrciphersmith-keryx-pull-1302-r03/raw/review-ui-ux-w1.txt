Findings

[UX-1] minor: an "Update review" refusal that is not about a moved head shows "The PR revision changed" and disables the start button
- Criterion: Nielsen #9 (help users recognize, diagnose and recover from errors) and #1 (visibility of system status). Error state: the cause shown is wrong, and the remedy offered does not clear it.
- File: apps/desktop/src/review/useReviewRuns.ts:68 `else setActionError({ kind: action.kind === "advance" ? "start" : action.kind, message });` together with :112 `staleRange: actionError?.kind === "start" && /^stale:/i.test(actionError.message)`.
- Evidence: src/review/review-advance.ts:39 and :41 refuse with `stale: This pull request is no longer open.` and `stale: A later round of this Review already exists. Refresh the Review and update from its latest round.` Neither means the range changed. Both match the staleRange test once the error is stored as kind "start". ReviewWorkspace.tsx:203-206 then renders "The PR revision changed. Refresh the board to load the latest range." (role=status), and ReviewRuns.tsx:211 renders the raw CLI text, `stale:` prefix included, in a second banner (role=alert). The primary button at ReviewWorkspace.tsx:195 is disabled by `(!action.open && revisionChanged)`. The "later round" case can be reached from the UI: the publish dialog of an earlier attempt opened from History offers Update review (ReviewPublishDialog.tsx:157, ReviewRuns.tsx:180), and ReviewWorkspace.tsx:139 only checks for attempts on the target range, not for a later round on another range. The workspace is keyed by base and head SHA (ReviewPanel.tsx:117), and actionError is cleared only by the next non-status action or by a remount (useReviewRuns.ts:44, :87). So "Refresh board" on an unmoved PR leaves both banners and the disabled button in place.
- Impact: the user reads two contradictory messages, one of which is false ("revision changed"). They follow its remedy (Refresh board), nothing changes, and the primary action stays disabled until they leave the PR.
- Fix: map only the range-moved refusal to staleRange. For example, store an advance refusal as kind "start" only when the message is the revision-changed one (review-advance.ts:76), or give advance its own error kind whose banner shows the CLI's cause without the machine prefix. Alternatively, change the CLI prefix for "later round exists" and "no longer open" (for example `conflict:` / `closed:`). Add a panel test where advance throws the "later round" refusal and check that no "PR revision changed" banner appears.
- class_scope: not required (minor). The only site is the single advance call (ReviewWorkspace.tsx:152), enumerated with `keryx ctx rg '"advance"|onUpdateReview' apps/desktop/src`.
- Confidence: medium. Read from code; no render was supplied to confirm the two banners on screen.

[UX-2] info: `keryx review publish` writes its session-registration warning to stdout, while `keryx review complete` writes the same warning to stderr
- File: src/commands/review.ts:5074 `(text) => console.log(\`warning: ${text}\`)` against :5178 `(text) => console.error(\`warning: ${text}\`)`.
- Evidence: the same sessionPublication warning callback is wired to different streams in the two commands.
- Impact: a script or agent that reads publish's stdout gets a warning line mixed into its output, and the two commands behave differently for the same condition.
- Fix: send both warnings to stderr.
- Confidence: high on the inconsistency; low on user impact, because publish's output is human-readable, not JSON.
