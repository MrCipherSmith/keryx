### Findings

### [SEC-001] Skill tells the agent both to supply `--reason` and never to write the operator's reason
- Severity: minor
- File: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.md (Wave D bullet and Hosts "Operator decisions" bullet)
- Attack vector: no outside attacker. The weakness is attribution. A prompt-injected or careless agent follows the command template, which requires `--reason "<why>"`, and writes the reason itself. The record stores it in `operator.reason` next to `actor: "operator"`, so agent-authored text reads as the operator's reason.
- Problem: the same SKILL.md says `plus --reason "<why>" on waive-mutation, override-reviewers and decide-premise` (the CLI refuses a missing `--reason`, per the help text in review-operator.ts), and in Wave D says "Record only an answer they gave and never write their words or their reason yourself." Both cannot hold: the verb needs a reason and the skill forbids the agent to write it. The previous wording ("never write their reason") assumed the operator ran the command. The schema description of `operator` still calls it "the operator's answer ... An audit trail".
- Why it matters: the host-question path is already weaker evidence. A reason that the agent wrote and the record attributes to the operator weakens it further, and the instruction cannot be followed as written.
- Fix: say where the reason comes from. Either the question asks the operator for the reason and `--reason` is their words, or the record marks it as agent-supplied (a separate `hostQuestion` field), and the skill says which one.

### [SEC-002] Skill has the agent paste verbatim question and answer text, which can carry untrusted content, into double-quoted shell arguments
- Severity: minor
- File: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.md (Hosts "Operator decisions" bullet), same template in SKILL.detail.md (readiness item 11, Preflight 4 step 4) and the Wave D bullet
- Attack vector: a PR author puts `$(cmd)` or a backtick expression in code or a PR comment. A reviewer quotes it in a finding. The held finding's `question` (premise judge output) or the agent's own question text carries it. The agent copies "the question as asked" into `--question-text "..."` in a Bash call, and the shell expands it with the agent's privileges. An operator answer containing `"` or a newline also breaks the command.
- Problem: the template is `--answer-text "<their words, verbatim>" --question-text "<the question as asked>"`. Double quotes expand `$()` and backticks. Earlier templates (`--quote "<their words>"`) did the same, but they carried only the operator's own typing. `--question-text` now carries text derived from reviewed code. The skill does not say to escape it or pass it another way.
- Why it matters: the agent already has a shell, so this is not new privilege. It is a trust-boundary crossing from third-party PR text into a command line. It is reachable only when the agent pastes verbatim without escaping.
- Fix: tell the agent to pass the texts with single quotes (escaping embedded `'`), or add `--answer-text-file` / `--question-text-file` or stdin input and name it in the skill and help.
- Confidence: medium. The path needs an agent that does not escape; nothing in the diff stops it.

### [SEC-003] The skill points keryx shell at the host-question path, but that shell always refuses `--answered-by`
- Severity: minor
- File: .metaproject/skills/gdskills/review/review-orchestrator/SKILL.md (Hosts "Operator decisions" bullet)
- Attack vector: none. The risk is an agent that hits a refusal and works around it (for example, unsetting `KERYX_TOOL_CALL`), because the skill sent it down a path that cannot succeed.
- Problem: the skill lists `ask_user` (a keryx shell tool) among the host question tools and `keryx-shell` among the `--answered-by` sources. But `src/harness/process/shell-spawn.ts:140` sets `env.KERYX_TOOL_CALL = "1"` for every `shell_exec` child, and `src/commands/review-operator.ts:332` refuses `--answered-by` when it is set. Inside keryx shell the verb therefore always refuses, and the only working path is the card. The sibling sentence says to call the card there, so the text is inconsistent. The `keryx-shell` source value can then never be recorded by the shell itself.
- Why it matters: weak, and only a contract mismatch. A refused command with a skill saying to run it invites a bypass attempt. `command-risk.ts` already guards `env -u KERYX_TOOL_CALL`, which limits the harm.
- Fix: state in the skill that in keryx shell the card is the only path and `--answered-by` is refused there. Drop `ask_user` from the host-question list for these four acts, or say what `keryx-shell` is for (for example a Claude Code session whose own environment was cleaned).

### [SEC-004] Schema does not enforce the coupling between `confirmedVia: "host-question"` and `hostQuestion`
- Severity: info
- File: .metaproject/core/gdskills/contracts/review-finding.schema.json (the `operator` object)
- Attack vector: none in the current code path. The runtime validator (`viaConsistent` in src/review/operator-decisions.ts) requires a complete `hostQuestion` exactly when the record says `host-question`, but the schema does not.
- Problem: the description says `Set with confirmedVia host-question only`, yet the schema accepts `hostQuestion` with `confirmedVia: "terminal"` or `"tui-card"`, and `confirmedVia: "host-question"` with no `hostQuestion`. The `operator` object sets `additionalProperties: false`, so the author meant it to be strict. `time` and `ref` also have no format or length bound.
- Why it matters: a consumer that trusts the schema (the PR comment renderer, `/decisions` report) could show a host-question record with no question, or a card record carrying a forged question block. Ingest strips `operator` from input findings, so no outside input reaches it today. This is why it is info.
- Fix: add an `allOf` entry: `if confirmedVia const host-question then required hostQuestion`, and `if confirmedVia not host-question then hostQuestion absent` (`not: { required: [hostQuestion] }`).
