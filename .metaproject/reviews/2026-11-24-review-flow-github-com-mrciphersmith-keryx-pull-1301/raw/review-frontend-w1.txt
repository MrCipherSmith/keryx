### Findings

### [F-001] A Loading row that resolves to a partial page keeps focus, but on the Show more row past the new children
- **Severity**: minor
- **File**: apps/desktop/src/metaproject/MetaprojectTree.tsx:41 (and :55)
- **Rule**: `code-style-patterns` accessibility (roving focus); canonical rubric, since no table row covers it
- **Problem**: This is a defect introduced by the fix for frontend-w1-F-001. The loading row and the Show more row of a parent now share the key `status:${parent}`. Suppose a keyboard user arrows onto a folder's Loading row, and the folder's first page then arrives with a `nextCursor` (a folder with more than 100 children). React keeps the keyed `<li>` and inserts the up to 100 new entries before it, so DOM focus stays on that element, which now reads "Show more" and sits after every new child. The restore path in the layout effect never runs, because the element stays connected. The sibling case (the last page arriving without a cursor, where the row is removed) moves focus to the first new row. So the two outcomes differ, and the first one is never tested: both new tests hold a read that has no `nextCursor` after it.
- **Why it matters**: Focus stays in the tree, which closes F-001's loss to `<body>`. But a browser does not scroll a focused element that did not move, so the focused row ends up up to 100 rows below the viewport. The user's next ArrowUp/ArrowDown starts from the end of the page, not from the top of the folder they opened. That is inconsistent with the Retry and last-page paths, which land on the first child.
- **Fix**: When a parent's status row changes from `loading` to `more`, move focus to the first child row if that row held focus. For example, the layout effect can remember the type of the focused row next to its index, and focus `elements[lost.index]` when a loading row became a more row. Alternatively, give the loading row and the more row distinct ids again, while keeping one id across error/loading on Retry and more/more-loading on Show more. Then the existing index-based restore lands on the first child. Add a DOM test: arrow onto a Loading row whose answer carries `nextCursor`, release it, and assert that focus is on the first child.

### [F-002] A tree that drops to its empty state keeps a stale focus record that can pull focus back later
- **Severity**: info
- **File**: apps/desktop/src/metaproject/MetaprojectTree.tsx:136
- **Problem**: When the root answers empty, the component returns the `<p>` empty state, so the `<ul>` unmounts. The layout effect returns early at `if (!root) return;`, so `focused.current` keeps the removed row. If a later snapshot brings files back while `document.activeElement` is still `<body>`, the condition `lost && !lost.element.isConnected && active === body` holds, and the first commit focuses a tree row. That is data arriving and moving focus. It requires the tree to have held focus when it emptied, and focus to be on `<body>` afterwards (for example after a click on a non-focusable area, which fires no blur on the unmounted list).
- **Impact**: This is a narrow edge case. Nothing was observed in a render.
- **Suggested fix**: Clear `focused.current` before the early return, or in a cleanup when the list unmounts.
