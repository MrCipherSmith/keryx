### Findings

### [F-001] Tree read limiter is FIFO and shared, so a user's expand or Show more waits behind queued re-reads
- **Severity**: info
- **File**: apps/desktop/src/metaproject/useMetaprojectTree.ts:122-145
- **Hot path**: once per tree read; worst case right after a new snapshot, when every expanded folder of both scopes is re-read.
- **Problem**: `limit` (new in the fix round, MAX_TREE_READS = 3) runs reads in arrival order from one queue shared by the graph and wiki scopes. After a snapshot change with N expanded folders, a read the user starts (expand, Show more, Retry) waits about ceil(N/3) read round-trips. Reads queued under a retired snapshot are skipped cheaply (`current() &&`), so only reads for the current snapshot add to the wait.
- **Why it matters**: The wait is bounded and the cap protects the read permits the tree shares with the explorer, which is the reason it was added. Read latency is a stage the operator has kept out of scope (the round-1 decision on performance-w1-F-001), and no timing was supplied, so this is info.
- **Fix**: None needed now. If a later latency stage measures it, put user-started reads (ensure on an expand, more, retry) ahead of background re-reads in the queue.

### [F-002] Each focus move now queries every rendered row two or three times
- **Severity**: info
- **File**: apps/desktop/src/metaproject/MetaprojectTree.tsx:104, 137, 155, 185
- **Hot path**: per arrow, Home or End keystroke, and per commit. moveTo queries all rows (`rowElements().find`), onFocus → remember queries them again (`rowElements().indexOf`), and the dependency-free layout effect queries them on every commit (`const elements = rowElements()`) plus once more through remember. The base version queried only while a scroll request was pending.
- **Problem**: These are O(rows) DOM scans added by the focus-restore fix for frontend-w1-F-001 and logic-w1-F-001. Each keystroke already re-flattens and re-renders the whole row list (`setFocusId`), which is also O(rows), so the scans change a constant factor and not the complexity. Row count is bounded by the expanded folders × pages of at most 100.
- **Why it matters**: Not measurable at realistic sizes, and nothing was timed. Recorded so a later virtualisation pass knows the scans exist.
- **Fix**: None needed. If one is ever wanted: in the layout effect, take `elements` once and pass the index into remember; in moveTo, use `list.current.querySelector('[data-row="…"]')` with CSS.escape.

### Clean Areas
- CLI/TUI hot paths: wikiTree grouping is now an in-place push (O(W), was O(W²)); the stale-snapshot check moved from matchesRequest to the end of requestMetaprojectV2 at the same cost.
- Memory leaks: limiter slots are released in `finally` on success and on failure. Its queue holds at most one closure per issued read and is drained as slots free up. onBlur's queueMicrotask holds no lasting reference. The `focused` ref is replaced on every commit and focus change.
- Re-renders: the Module label and status-row ids add no new props or objects per render. The shared `status:${parent}` id now keeps a status `<li>` mounted instead of unmounting and remounting it.
- Redundant calls: a read queued under a retired snapshot never calls the CLI.
- N+1, indexes, pagination, bundle imports, sync blocking, MobX: not relevant to this delta (no DB, no new imports beyond the contract helper, no sync I/O).
