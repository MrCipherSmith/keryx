## First attempt — invalid, recorded so the result is not mistaken for the second

The first reproduction put the CSS in an inline `<style>` and the probe in an inline
`<script>`. Both were themselves blocked (`style-src 'self'` / `script-src 'self'`), so the
rule never applied and the data: image was never requested: computed `appearance` came back
`auto` and `background-image` `none`. That attempt proves nothing about the finding. The
server was rewritten to serve external same-origin assets, which is attempt 2 below.

Console (5 identical errors, one per element that requested the image):

  viewBox='0 0 16 16' fill='none' stroke='%2361756b' stroke-width='1.5'%3E%3Cpath
  d='M4 6l4 4 4-4'/%3E%3C/svg%3E' violates the following Content Security Policy directive:
  "default-src 'self'". Note that 'img-src' was not explicitly set, so 'default-src' is used
  as a fallback. The action has been blocked.

## What this establishes, and what it does not

Established: under exactly the header `src/hub/server.ts:175` sends, a real Chromium refuses
the chevron's data: URI, by the `default-src 'self'` fallback for a missing `img-src`. The
select keeps `appearance: none` and the 40px (2.5rem) reserved inline-end padding, so the
reserved space stays and nothing is painted in it. An `Image()` load of the same URI also
fails, so the block is on the image request, not on the CSS parse.

Not established here: that the production Hub serves `apps/hub-web`'s built stylesheet under
that same header (the header is on the `webAssets` branch, which serves every non-`/hub/v1/`
GET, including the HTML document — read at `src/hub/server.ts:173-176`), and that no later
rule in the real stylesheet restores an arrow. Those are reads of the repository, not of this
run. Also not established: what a user sees on a Vite dev server, which sends no CSP — the
pull request's own verification note says Chrome at 1366 and 390 px without saying which
origin it used.
