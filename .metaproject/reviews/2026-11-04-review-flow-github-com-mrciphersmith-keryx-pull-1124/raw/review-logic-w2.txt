## Logic review: slice-02, PR #1124 round 1

**client.ts: is the PR's claim true?** Yes. In `verifyAuthorizationGrant` the three guards are all still strict conjuncts:
- Absolute expiry is untouched: `expires > now`, so a grant whose `expiresAt` equals `now` is refused.
- The monotonic window is untouched: `elapsed >= 0 && elapsed < LIMITS.grantMs`. `authorization()` takes `startedAt` before the request goes out, so a grant carrying a lead still cannot be used for longer than 5000 ms of local time from the request start.
- The lead is bounded at 250 ms (`issued <= now + MAX_HUB_CLOCK_LEAD_MS`).
- `expires > issued` is new and needed. Without it a grant with `issued` up to 250 ms ahead and `expires` before `issued` would pass, since `expires - issued <= grantMs` is satisfied by a negative span.
- `expires - issued <= LIMITS.grantMs` still bounds the span, and the Hub issues exactly 5000 ms from one clock read (`remote-v2/index.ts:348`), so the test grants (lead + 5000) are realistic.

**Does the new test pin it?** Yes, deterministically, since `now` is passed in:
- lead 75 and 250 are accepted and 251 is refused, so the bound is exact;
- lead 75 with `now + 5075` is refused (`expires === now` fails the strict `>`), so the absolute deadline is not extended by the lead;
- lead 75 with `elapsed = 5000` is refused, so the monotonic window is not extended;
- `grant(200,100)` and `grant(100,100)` are refused and `grant(0,100)` accepted, so the new `expires > issued` guard is pinned (the span is -100 and 0, which `expires - issued <= grantMs` alone would let through).

Two limits to the pin: it exercises the function, not `authorize()`, and the combined lead-plus-window behaviour rests on the conjuncts being independent, which they are. F-001 is about the first limit.
