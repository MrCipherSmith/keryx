## Architecture summary, slice-01

No blocker or major. The change keeps the layering it found: no new import cycle in `features/remote` (checked: `sessions.tsx` imports `work`, `settings`, `session-timeline`; `work.tsx` imports `settings` and `session-timeline`; `settings.tsx` imports only `session-timeline`), `useRemoteQuery` gains a data-aware `enabled` without changing existing callers, the launch form seeds the composer through exported `messageDraftKey` and `prepareFlowMessageDraft`, and the launch gating is a pure function (`firstUnmetLaunchCondition`). Component-level data fetching is the established convention here (siblings do the same), so it is not flagged.

What I would tidy, none of it blocking:

- **F-001** The "eligible Flow" rule and its query now exist in three places (`sessions.tsx`, `work.tsx`, `association.tsx`).
- **F-002** The Flow-to-pin field mapping is written twice in `work.tsx`.
- **F-003** `Commands` is now a composer child but still lives in `settings.tsx` and takes a `focusToken` counter prop.
- **F-004** `Commands` follows its operation without the settled gate that `OutcomeItem` introduced, on the same query key, so the gate does not hold for the newest command.
- **F-005 (info)** The `prepared` draft flag is a hidden state machine; the typing-during-opening path with an empty first message may raise a stale notice. Unconfirmed; a test would settle it.
- **F-006** Feature CSS depends on `Panel` markup and on nesting, and TSX depends on a class name for focus.

Not covered: slice-02 (tests, machine client). Local test failures noted in the dispatch were not examined, as they are outside this slice. No git history was needed; the one deliberate-looking choice read in full was the `settled` gate (comment and code in `OutcomeItem`), which I did not dispute, only its missing counterpart in `Commands`.
