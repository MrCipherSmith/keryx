## High-Load Review (slice-02)

**Verdict:** no concurrency, resource or load defect in this slice.

**The clock-lead change.** `verifyAuthorizationGrant` now accepts `issued <= now + 250` and rejects `expires <= issued`. I checked whether the lead lengthens the window in which a grant can be applied. It does not. `elapsed < LIMITS.grantMs` is monotonic and counted from before the Hub request (`started` in `authorize()`, `startedAt` in `authorization()`), so a grant is unusable 5 s after the request began no matter what the Hub stamped. `expires > now` is unchanged, and the Hub-ahead case cannot push the true expiry past `request start + 5 s`. A Hub behind the machine is still stricter, as before. `expires > issued` closes a zero-length or negative-length grant, which the old `expires - issued <= grantMs` check admitted when expires was before issued.

**Clean areas.** No shared mutable state, retry, queue, cache, pool, transaction or unbounded collection is added in `client.ts` or elsewhere in the slice. The `Bun.sleep(wait)` is capped at 500 ms and is not held under a lock (pre-existing, 565866111). CSS, i18n and test files carry no runtime load surface. The polling and fetch fan-out for command outcomes live in slice-01 and were not reviewed here; the tests in `session-command-outcomes.case.tsx` assert that a settled outcome stops being fetched.
