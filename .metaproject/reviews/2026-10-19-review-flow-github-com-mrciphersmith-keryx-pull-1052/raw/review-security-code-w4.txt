## Checked and clean (lens questions)

1. TUI-originated approval labelled remote or carrying pressedBy: no. `remoteApproval` (src/tui/tui-shell.ts) is called from exactly two places, both after `bridge.askApproval` produced a topic answer (the Telegram-turn path and the `from: "topic"` branch of the mirror race). The dock side, `confirmOperatorCard`, returns `Promise<boolean>`; agent.ts:6120-6124 maps a non-object response to `confirmationVia = "local"` and drops pressedBy/pressedAt, and operator-confirm-tools.invoke only writes them when `ctx.confirmationVia === "remote"`. A dock answer that lands in the same tick as a topic press cannot be relabelled either: microtasks drain before the next network frame, so the earlier human wins, as before this PR.
2. fromId source and fail-closed: `fromId` is the numeric `callback.fromId` that serve's hub took from the Telegram update after `allowedUserIds`, `chatId` and registered-thread checks (hub.ts:1085-1097), passed through `mapApprovalAnswer` (Number.isSafeInteger only). Allow with no fromId yields `via:"remote"` without pressedBy, and `invoke` refuses it ("did not say who pressed it"). A missing fingerprint falls back to a bare `true`, which is recorded as tui-card with no pressedBy (understates, never overstates).
3. Different user / chat / topic / stale callback: users, chat and topic are refused in hub.route; `pressApproval` rejects another session's approval id, accepts only an id this server issued (`ap` + 48 random bits), still inside its window, and `dropApproval` makes it single-use; a replay or late press finds the `finished`/`awaiting` entry and changes nothing. The shell side keeps one waiter per approvalId, so a press for question A cannot resolve question B. The callback itself carries no fingerprint: the fingerprint in `remoteApproval` is copied from the question being asked, so the binding of answer to question is the approvalId, not the fingerprint. That is sound here and unchanged by this PR.
4. Unmirrored-card wrapper: it only runs `inner` (the dock) with a copy of `meta` whose card gained one note line above the subject; it cannot produce a remote response, does not touch the token, and the topic is never asked in that branch. The note is not part of the stored `shown` card or the quote (those come from `confirmation()` in operator-confirm-tools.ts). `isCard` excludes `user_prompt`.
5. operator-confirmations.ts: in memory only (no file, no path handling); holds the card title and a numeric Telegram id, no tokens, fingerprints, input JSON or secrets; answered entries capped at 5 (open entries are not, see F-002); pressedBy shown only for place `telegram`, and it is set from `outcome.answer.fromId`, never from model input. Text is flattened and clipped to 80 characters.
6. remote-control-surface.ts / decisions-surface.ts: only append pre-built lines and a waiting count; no input is parsed, nothing is written.
7. Expiry: the topic leg waits MAX_APPROVAL_TIMEOUT_MS (60 min) and the record check is `now() - issuedAt > 60 min` against a value held in the tool closure, so a press at the edge is refused, not accepted.
