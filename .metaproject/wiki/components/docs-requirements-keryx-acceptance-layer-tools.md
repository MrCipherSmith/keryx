## Summary

`docs/requirements/keryx-acceptance-layer/tools` holds two standalone Python scripts that measure how the acceptance criteria of keryx flows are verified: one describes the criteria text itself, the other compares criteria against the diffs of the flows that delivered them.

## Overview

This module owns the measurement tooling behind the keryx acceptance-layer requirements study. It contains no application code and is not imported by the app: both scripts are run by hand with `python3`. They answer factual questions about the flow corpus (how many acceptance criteria name a test, a command or a file, and how often the named artefacts are absent from the delivering change) without calling a model.

## How it works

The two scripts are independent and share only a regex vocabulary. `measure-criteria-shape.py` is the simpler one: it globs `.metaproject/flows/*/acceptance-criteria.md` in the working tree, parses `AC<n>:` lines, and classifies each criterion with flags (`claims`, `names_test`, `runnable`, `no_artefact`). It prints overall percentages and a breakdown by flow-number bucket (1-100 through 301+), since flow numbers are chronological.

`measure-disagreement.py` works from git history rather than the working tree. It lists `flow.json` and `acceptance-criteria.md` under `origin/main`, keeps only flows with `status` `done` and a PR number, and resolves each PR to its squash commit by matching `(#N)` in the `git log` subjects. Its extraction and marker rules are described in its docstring as ports of `src/flow/check-ac.ts` (flow 328). A criterion is first screened as not checkable when a marker phrase (live check, CI green, health passing, docs published, manual verification, operator confirmation) appears; otherwise its named artefacts (backticked tokens, bare file paths, `keryx <sub>` commands) are looked up in the squash commit's diff text and changed file names. The script appears to set `REPO = "~/keryx"` and pass it as the subprocess `cwd`, which does not expand `~`, so it may need an absolute path before it runs.

## Key concepts

- **Acceptance criterion**: a line `AC<n>: ...` in a flow's `acceptance-criteria.md`. It is the unit both scripts count.
- **Named artefact**: a token a criterion points at, such as a backticked string, a bare `dir/file.ext` path or a `keryx <subcommand>`. A criterion with none is "no artefact at all".
- **Runnable**: a criterion that names a `*.test.*`/`*.spec.*` file or a backticked `bun`, `npm`, `pnpm`, `keryx`, `tsc` or `git` command. The script labels this an upper bound, because a backticked command is often the subject of the criterion rather than its check.
- **Not checkable**: a criterion whose clauses are all verified by a non-diff marker (live check, CI green, manual verification, operator confirmation and similar). No diff can record these.
- **Confirmed criterion**: an entry in a flow's `acConfirmed` map. Disagreement is counted only for confirmed criteria, meaning the flow was accepted but its named artefacts are missing from the delivering change.

## Main flows

1. **Criteria shape (1b/1c).** Working-tree files are globbed, each `AC` line is parsed and classified, and counters are accumulated overall and per bucket. The output is the share of criteria that claim coverage, name a test file, name any runnable command, or claim coverage while naming nothing runnable.
2. **Retrospective disagreement (1).** For each done flow on `origin/main`, the PR number is mapped to its squash commit. Each criterion is screened for markers; criteria with no named artefact are counted separately. For the rest, tokens found in the commit's diff or file names count as present. A confirmed criterion whose tokens are all absent is counted as a disagreement, and the disagreement rate is reported over criteria the facts can judge.
3. **Clause splitting.** Within the disagreement flow, a criterion is split on commas and semicolons. It is treated as not checkable only when every clause matches a marker, and the first clause's label is reported.
