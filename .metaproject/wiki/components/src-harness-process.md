# Module src/harness/process

## Summary

`src/harness/process` is the harness module for running commands through a contained process execution boundary. It defines public types for describing a command, observing process activity, and returning a final outcome, and it provides helpers for shell-oriented sandbox and spawn configuration.

## Overview

This module owns the contract used by other harness areas when they need to launch a command without depending directly on the host process layer. Its public API centers on `runContainedProcess`, which coordinates a caller-supplied execution plan through process adapters and dependency objects.

In addition to the generic process abstraction, the module contains shell-specific support for sandbox modes, restricted masks, deny roots, environment construction, and spawn planning. The file graph shows it is closely tied to `src/harness/process/sandbox` and is consumed by command tooling and built-in tool integrations.

## How it works

The module can be understood as three related layers:

- **Execution entry points** — `runContainedProcess` is the main public function. `RunContainedProcessInput` and `RunContainedProcessDeps` describe what should run and which dependencies are available for the execution.
- **Process abstraction** — `ProcessAdapter` isolates the harness from the actual host process implementation. `real-process-adapter.ts` provides a concrete adapter for real process execution.
- **Observation and result types** — `ProcessObservation`, `ProcessObservationKind`, and `ContainedProcessOutcome` provide structured representations of intermediate process activity and final results.

Shell behavior is planned through dedicated helper functions:

- `resolveShellSandboxMode` determines the shell sandbox mode.
- `resolveShellRestrictedMasks` and `extraReadDenyRoots` expose filesystem restriction inputs.
- `resolveShellEnv` constructs or resolves the environment for the process.
- `resolveShellSpawn` produces a `SandboxSpawnPlan` for launching a shell.

The `executor.ts` file is the central implementation and is imported broadly across the codebase. The `shell-spawn.ts` file packages shell planning logic, while `real-process-adapter.ts` connects the public adapter interface to real process behavior.

## Key concepts

- **ContainedCommand** — A command representation intended to be executed under contained process rules.
- **ProcessAdapter** — The boundary abstraction that performs or participates in actual process execution on behalf of the harness.
- **ProcessObservation** — A structured record describing something observed during process execution; `ProcessObservationKind` classifies those records.
- **ContainedProcessOutcome** — The final result returned after a contained process finishes or fails to produce a normal result.
- **RunContainedProcessInput** — The request-level input needed to start a contained process.
- **RunContainedProcessDeps** — The injectable dependency surface used by the execution path.
- **ShellSandboxMode** — The selected sandboxing mode for shell execution.
- **SandboxSpawnPlan** — A plan describing how a shell process should be spawned under sandbox constraints.
- **Resolution helpers** — Functions such as `resolveShellEnv` and `resolveShellSpawn` translate harness and sandbox settings into concrete execution parameters.

## Main flows

### Run a contained process

A caller supplies command and dependency information to `runContainedProcess`. The executor uses the supplied process abstraction, obtains process observations during execution, and returns a `ContainedProcessOutcome`. This gives callers a uniform result shape without depending directly on host process details.

### Resolve a shell spawn plan

When a shell command needs sandboxed execution, the module can resolve a sandbox mode, apply restricted masks, identify extra read deny roots, build the process environment, and produce a `SandboxSpawnPlan`. The resulting plan can then be used by process execution code to start the shell.

### Real adapter interaction

Concrete process behavior is isolated behind `ProcessAdapter`. `real-process-adapter.ts` provides an implementation suitable for real process execution, while classification behavior is exercised in `real-process-adapter.classify.test.ts`. This keeps host process details behind a testable boundary used by the executor.
